# @delo/plugin-changes

## Summary

`@delo/plugin-changes` keeps the agent from changing which plugins the harness runs. With its C16 switch `plugin_changes_pending` on, a `plugin_manager` call whose action is `install_bundle` or `remove_bundle` does not run: a `tools/pre-execute` listener records it in the profile's change log as a pending change ([C21](../../docs/contracts/c21-changes.md#the-agent-and-plugins)) and denies the call with a result the model reads, `Recorded as a change waiting for the person's review at their computer: delorun changes show <id>. Nothing was installed.` The tool never reaches its own full-access approval for these actions, and the person applies or discards the change at their computer with `delorun changes`. The agent's other `plugin_manager` actions that change what runs (`set_bundle`, `set_plugin`, `configure`, `set_version_exemption`, `undo`, `restore`) are denied with `PLUGIN_CHANGE_AT_COMPUTER` and record nothing. Whatever the switch says, the plugin provides upstream hot reload's `profileReconcileCheck`, which checks every recomposition of the profile before anything stops ([C21](../../docs/contracts/c21-changes.md#reloads-and-restores)). Whatever the switch says, it also registers the studio's Changes routes under `/delo/changes/`, which upstream's boot page reads for its recovery screen ([C21](../../docs/contracts/c21-changes.md#routes-and-the-recovery-screen)), and its browser half adds the Changes section in Settings and the work-session badge, which act through the same routes ([C21](../../docs/contracts/c21-changes.md#the-studios-changes-section)). With the switch off, the default and the parity value, the plugin registers no listener or guard and the tool runs and asks as upstream's does.

## Contract

- **What is held.** `install_bundle` records a `plugin-install`, or a `plugin-update` when the spec is a registry version of a plugin the profile already has; the tool offers no update action, so this is how the agent asks for one. `remove_bundle` records a `plugin-remove`. Every other action and tool goes on to the next listener.
- **What is recorded.** `recordPluginRequest` of `@delo/changes/install` writes one pending entry with `subject.spec` and, when the spec names it, `subject.plugin`, under the profile write lock, into the profile the Host runs (`ctx.profileContext`). It writes no manifest, lockfile, `node_modules` or approval. A request that still waits keeps its id; a repeat of a decided request is a new change.
- **What the model reads.** A recorded request is denied with error code `PLUGIN_CHANGE_PENDING` and the change's id; an update says `Nothing was installed or updated.` and a removal `Nothing was removed.` A call with no target, a spec pnpm would not accept, a removal of a name that is no dependency, a Host without a profile, or a log that cannot be written is denied with `PLUGIN_CHANGE_UNRECORDED` and the reason, and records nothing. The denial is the tool call's logged result, so no session event is added.
- **What the person makes.** `set_bundle`, `set_plugin`, `configure`, `set_version_exemption`, `undo` and `restore` do not run: the model reads that the person makes that change at their computer, in the studio or with `delorun plugin`, with error code `PLUGIN_CHANGE_AT_COMPUTER`, and nothing is recorded.
- **The guard.** A `pre-execute` listener that allowed such a call without calling `next()` would skip the plugin's listener. The plugin's tool guard, which runs after every listener and cannot be overruled, denies every such call its listener did not handle.
- **The check before a reload.** `profileReconcileCheck.check(profile)` runs `prepareReload` of `@delo/changes` for the profile the Host runs: a `link:` dependency that names a folder is moved to the plugin's active directory where the profile write lock allows, and a link or active directory that differs from what Changes keeps refuses the recomposition with `LOAD_REFUSED`, so nothing stops and nothing loads. A link counts as the harness's own when it is into the runtime store or names the directory the Host already loads that package from (`loadedLinks`).
- **The studio's routes.** Once the web server and Connection are present, [`src/routes.ts`](src/routes.ts) registers `GET /delo/changes/state` and `show`, and `POST` `apply`, `discard`, `undo`, `off`, `on`, `work`, `done` and `safe-mode`, and the plugin names their prefix to the boot page through the index global `dshRecoveryRoutes`. Every request is admitted by Connection first; any admitted session reads, and an action acts only for a request at the computer (a loopback `Host`, the credential, and a session Connection's `isReachPeer` does not name; a Connection without `isReachPeer` gets no route), which it attests with `attestStudio`, and refuses any other with `403 LOOPBACK_REQUIRED` and a request another site sent with `403 CROSS_SITE`, both before the body is read. `apply` and `done` answer `409 CONFIRM_RISK` until the person confirms a flagged change again, `apply` leaves the agent's plugin requests to `delorun changes apply`, `apply`, `discard` and `undo` refuse a change to Delo itself from the harness's log with `409 DECIDE_AT_TERMINAL` and its terminal command, and an action reloads the Host in its own process with `reloadProfile`. No route changes the protection setting. `state` reads the records only (`recordedChanges` of `@delo/changes` and the harness's log), writing nothing and reading no plugin's folder; `show?id=` of a change to Delo itself reviews its two versions from the store; `show?pending` reads the folders and stores their content. An answer never carries the Delo home's path: a refusal whose words name it answers its code and a fixed sentence and logs the words, and a recorded failure names the home as `<Delo home>`.
- **The wire.** [`src/wire.ts`](src/wire.ts) holds the routes' paths, their refusal codes and the JSON fields each answers with, and imports nothing; the routes build those fields and the browser half reads them, so a field the Host stops sending fails the Host's typecheck. An entry left out at a start carries the failure the start recorded as `leftOut`.
- **No decisions elsewhere.** Apart from the routes, the plugin imports no function that applies, discards or undoes a change, opens or ends a work session, or changes the protection setting; `delo/packages/changes/tests/reach.spec.ts` holds it to that, and holds the routes to `attestStudio` without `attestTerminal` or the protection setting's writers.

## The studio's Changes section

The browser half, [`src/client/index.ts`](src/client/index.ts) (`@delo/plugin-changes/client`), loads with the `delo-plugin-changes` row and registers:

- the `settings.section` `delo-changes` ([`ChangesSection.tsx`](src/client/ChangesSection.tsx)): the work session with Done, or the plugins of the last start with Start working; the changes a start left out with Apply again and Undo; the changes waiting for review, each opened by Review ([`ChangeDetail.tsx`](src/client/ChangeDetail.tsx)) with Apply and Discard; the agent's plugin requests with the terminal command and Discard; the recent changes with Undo; the changes to Delo itself with a read-only Review and the terminal command that decides each; and the protection setting with the terminal command that changes it and no control. A change the checks flagged asks a second confirmation, opened by the route's `409 CONFIRM_RISK` and naming the kinds and the files the diff does not show, before Apply or Done sends `confirmedRisk`. With `atComputer: false`, or once an action is answered `403 LOOPBACK_REQUIRED`, every action is disabled and the section says "This needs you at your computer.";
- the `sidebar.footer.action` `delo-changes.work-badge` ([`WorkBadge.tsx`](src/client/WorkBadge.tsx)), which names the plugin while a work session lasts, after Delo's undo notice;
- a `shell.overlay` toast ([`ChangesToast.tsx`](src/client/ChangesToast.tsx)) for each action's outcome.

[`controller.ts`](src/client/controller.ts) owns every request and the state both read; it reads `state` at load, after each action and every `STATE_REFRESH_MS` (15 seconds) while the page is visible. The section reads the folders through `show?pending` when it opens, after each action and when the person asks, never on the 15-second read. The copy is in typed English and Chinese dictionaries ([`locales.ts`](src/client/locales.ts)), namespace `deloChanges`.

**Building.** The harness half runs from `src/index.ts` like Delo's other plugins without a studio face; `pnpm --filter @delo/plugin-changes run build` writes only the browser half, `lib/client.js`, with upstream's client preset ([`tsdown.config.ts`](tsdown.config.ts)). The compiler faces are `tsconfig.host.json` (the harness half and its specs), `tsconfig.client.json` (the browser half) and `tsconfig.tests.client.json` (its specs), under the solution `tsconfig.json`.

## Configuration

| Field | Default | Meaning |
| --- | --- | --- |
| `enabled` | false | Delo's C16 switch `plugin_changes_pending`. `@delo/bundle-local` mounts the plugin with `enabled: true` in its `delo-plugin-changes` row; the parity overlay restates that row disabled. |
| `installationBundles` | `[]` | The bundles safe mode from the studio keeps loading. `@delo/bundle-local`'s row restates Delo's profile bundle list, which this plugin cannot import, and its `plugin-changes-row.spec.ts` holds the two equal. Empty, the safe-mode route answers `503 SAFE_MODE_UNAVAILABLE` and names `delorun recover safe-mode`. |

## Known limitations

- A profile whose configuration leaves the `delo-plugin-changes` row out reloads without the check until its next start.

## Tests

[`tests/plugin-changes.spec.ts`](tests/plugin-changes.spec.ts) runs upstream's `plugin_manager` tool through the real tool pipeline: an install, an update and a removal each record a pending change, leave the profile's files byte for byte as they were and never reach the approval; a call that cannot be recorded is denied; a listener that allows the call first is overruled by the guard; other actions keep upstream's approval; the actions the person makes are denied; and with the switch off, install and remove ask the tool's approval as upstream does. [`tests/reload-check.spec.ts`](tests/reload-check.spec.ts) boots a real profile with the plugin manager and hot reload: a tampered active directory, a restore naming a folder and another process's `link:<folder>` install load nothing, and under Block upstream evaluates nothing of a plugin with no approved content. [`tests/unrecorded.spec.ts`](tests/unrecorded.spec.ts) covers a failure that is not an `Error`; [`tests/loaded-links.spec.ts`](tests/loaded-links.spec.ts) the harness-link rule. [`tests/routes.spec.ts`](tests/routes.spec.ts) serves the routes on a loopback port: a caller without the credential, a remote session and another site are refused with the body withheld, each answered within 2 seconds, no route changes the protection setting, malformed requests are refused, and no answer names the home's path; [`tests/routes-state.integration.spec.ts`](tests/routes-state.integration.spec.ts) holds `state` to writing nothing and reading no folder; [`tests/routes.integration.spec.ts`](tests/routes.integration.spec.ts) acts on a real profile with its history, the second confirmation of a flagged change included; [`tests/routes-plugin.spec.ts`](tests/routes-plugin.spec.ts) covers the registration, and no registration without `isReachPeer`. [`tests/changes-section.client.spec.tsx`](tests/changes-section.client.spec.tsx) renders the browser half against a stand-in harness: each part of the state, a review with its risk summary, the files the diff does not show and the diff, the second confirmation before a flagged change is applied or approved, Undo, Apply again, Discard, Start working and Done with exactly the version shown, each outcome's toast, a remote session that sees everything and acts on nothing, and the work-session badge while a session lasts and gone after.
