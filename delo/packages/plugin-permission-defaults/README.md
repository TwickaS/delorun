# @delo/plugin-permission-defaults

English | [中文](README.zh.md)

## Summary

Upstream composes one permission for the whole deployment: every new chat starts on the same preset, and choosing `danger-full-access` takes effect at once. This plugin makes the preset a property of the workspace instead. A new chat starts on the preset the person chose for its folder — `workspace-write` for a workspace nobody has chosen for — whatever the deployment default is, and full access happens only after one consent for that workspace. The person gives it at the home's own computer: in the studio when picking full access, from the approval card of a request that asks for full access, or in Settings, Permissions, or with `delorun workspace full-access`. The consent is written to the home's protected state, so it covers that folder until the person chooses another preset there; explicitly choosing the safer preset withdraws it, so returning to full access asks again.

The guard that refuses an unconseted full-access switch runs before the session records anything. A refused switch therefore appends no `sandbox/mode` event and no preset identity, the session keeps resolving the mode it had, and a command started in the same synchronous step runs inside the sandbox. The guard covers the whole selection, not only a mode change: a preset that keeps the mode and drops the approval policy is refused too, so the approval prompts are not a way around the consent. A per-call `sandbox_permissions` escalation is not a mode switch: it goes through upstream's per-call approval, which this guard does not see. The refusal's words name the workspace and where the person allows full access — the approval card's "Allow full access for this workspace", the studio's Settings, Permissions, or `delorun workspace full-access "<folder>" on` with the workspace's folder ([`fullAccessRefusal`](src/index.ts)) — so the model reads them rather than a stack trace.

The plugin also gives each workspace a [network for its sandboxed commands](#the-network-of-sandboxed-commands), `open`, `allowlist` or `off`, which `web_fetch` follows too.

Everything, the routes included, sits behind the switch `permission_defaults`, off by default; `@delo/bundle-local` turns it on in the CLI profile that `delorun` starts and `@delo/bundle-headless` in the profile `delorun headless` runs, so a headless task in a folder without a grant cannot switch to full access; the desktop app runs upstream's profiles without it. Off, the plugin mounts nothing: the deployment default reaches every new chat exactly as upstream seeds it, and every mode switch is recorded, which is what the parity composition asserts.

## Which preset applies

Three tiers decide a chat's permission, strongest first:

1. The chat's own log. A preset identity or a knob event the chat already holds outranks its workspace's default, so a resumed, forked or seeded chat keeps the permission it recorded. An explicit `sandbox/mode` switch also outranks the preset identity — another surface's control, an approved escalation or a delegation seed — and the chat then reports `custom` while its knobs match no configured preset; `select()` re-asserts the chosen preset when the person picks again.
2. The workspace's default. `select()` records it, and this plugin seeds it into new chats only: the seed runs on a chat that holds no permission choice yet and was never seeded.
3. The deployment default. `sandbox-policy`'s mode and the approval policy's default sit beneath both: they apply to a chat whose workspace has no entry, and to any knob a chat never overrode.

## What it provides

- `permissionDefaults` — the service behind the switch. `defaultPreset(cwd)` and `granted(cwd)` read a workspace's recorded preset and whether it holds a full-access grant, `select(agent, preset)` is the one write path a surface uses to choose a workspace's preset, and `review(session, mode)` is the guard's verdict. The entries are kept in memory, so the guard answers synchronously; before every decision (a full-access switch, the preset of a new or restored chat, a surface's listing) the service compares the store file's identity (device, inode, size, modification time) with the one it read, and reads the file again synchronously when another process changed it. A grant withdrawn by another profile's Host, `delorun workspace full-access` or a running `delorun headless` task therefore stops counting at this service's next decision, and the open chats of the workspace that lost it are set back to the safer preset right after. `storeProblem` names a store that could not be read.
- `sandboxModeGuard` — the mode-switch hook of `@deepseek-ai/dsh-sandbox-policy`'s session-mode seam, mounted so `setSandboxMode` refuses a switch to full access in a workspace nobody consented to. It is the seam's one provider, so a composition turns on this consent or another plugin's guard, never both.
- The store — [`src/store.ts`](src/store.ts) holds the format and the file handling: one entry per workspace, keyed by the workspace's canonical path ([`src/workspace.ts`](src/workspace.ts)), in the home's `secrets/` directory at mode 0600, changed only while holding its lock file `workspaces.json.lock` (`@delo/home`'s lock file, waited for up to 10 seconds), so a change never overwrites another process's change it did not read; so a confined command can neither read the consents nor grant itself one; on Windows, where the runner does not confine reads, it cannot write them but can read them. A store that is a symbolic link, is laxer than 0600, or holds another format is refused, and no consent counts until the person fixes it.
- `select()` asks through the composed approval service, naming the folder and what full access drops, and refuses with `FullAccessConsentRefusedError` on every answer but a grant: nothing is recorded and the workspace keeps the safer preset. Choosing the safer preset withdraws the workspace's grant, so a later full-access selection asks again. The approval service asks only inside a chat's open turn, so no studio surface calls it.

## The consent surfaces

The studio and the CLI ask the consent themselves and record the answer through the service, at the home's own computer only. The consent's words come from [`fullAccessNote`](src/review.ts): commands in the workspace may then run outside the sandbox and write anywhere, read everything the person's user can, Delo's home with its keys and tokens included, and reach the Docker supervisor and Delo's update channel; the answer covers that workspace only.

- **Service calls.** `workspaces()` lists every workspace a surface shows — the registered ones, those the store holds and the folders of open chats — each with its full access and a review id ([`src/review.ts`](src/review.ts)); `reviewChat(sessionId)` is one open chat's workspace. `setFullAccess({ workspace, reviewId, on, confirmed, chat })` records the person's answer (the Host cannot verify who set `confirmed`; it enforces the loopback arrival the routes check); turning full access on for a folder Delo never adds as a workspace (a filesystem root, the home folder, the Delo home, the stock home, or a folder containing one) is refused with `UNKNOWN_WORKSPACE`, as the CLI refuses it: on records the grant and the full-access preset and, with `chat`, the open chat the consent was asked from, switches that chat to full access so it stops asking; off withdraws the grant and sets every open chat of the workspace that runs with full access back to the safer preset, which appends that chat's `sandbox/mode` and `permission/preset` events. It refuses with `FullAccessChangeError` and records nothing for `UNCONFIRMED` (no `confirmed: true`), `UNKNOWN_WORKSPACE`, `UNKNOWN_CHAT` (a `chat` that is not open in the workspace), `STALE_REVIEW` (the workspace's full access changed after the consent was shown) and `STORE_REFUSED`. Each change reads the store from disk first, so a change the CLI wrote is never undone, and logs one line without the folder's path.
- **Reading the store again.** `reload()` reads the store after `delorun workspace full-access` wrote it, sets the open chats of a workspace that lost its grant back to the safer preset, and answers the entries' digest so the CLI can check that the Host holds what it wrote, with how many workspaces gained (`added`) and lost (`lost`) a grant; the CLI asks the home process of every running profile; the home process calls it for the update channel's `permission.reload` ([C19](../../docs/contracts/c19-home-process.md)).
- **Routes.** Where a Connection serves the studio, three exact routes under `/api` ([`src/wire.ts`](src/wire.ts), [`src/routes.ts`](src/routes.ts)): `GET /api/deloPermission.workspaces`, `POST /api/deloPermission.review` and `POST /api/deloPermission.setFullAccess`. Each answers only a request that arrived on the loopback listener under a loopback `Host`; a reach device is refused with `403 LOOPBACK_REQUIRED` before the body is read ([C14](../../docs/contracts/c14-oidc-passkeys.md#tailnet-membership)). The studio's consent, the approval card's full-access action, its Permissions section and the `permissionSwitchConsent` question upstream's permission control asks live in [`@delo/bundle-local`](../bundle-local/README.md#the-consent-surfaces).

## The network of sandboxed commands

Each workspace also has a network for the commands the model runs in the sandbox: `open`, the host's network as stock gives it; `allowlist`, only the hosts the person listed; or `off`, none. A workspace without its own setting has the row's default, `open` unless `network` says otherwise, so a fresh install behaves as stock. [`src/command-network.ts`](src/command-network.ts) is the `deloCommandNetwork` service:

- It mounts the `sandboxNetwork` resolver of `@deepseek-ai/dsh-sandbox-policy`, so each confined command's policy carries `off`, or under `allowlist` the socket of the egress proxy for that list. `open` carries no network, which is upstream's policy unchanged. The sandbox enforces `off` and `allowlist` under bwrap and refuses every command of such a workspace on Landlock, Seatbelt and Windows ([sandbox-local](../../../packages/sandbox/sandbox-local/README.md#network)).
- One [egress proxy](src/egress-proxy.ts) per distinct allowlist listens on a Unix socket under `secrets/permission-defaults/proxy/<pid>/` before any policy names it, and closes when no setting names its list, so a running command loses hosts its list no longer has. It serves `CONNECT host:port` and absolute `http://` requests; it refuses a host the list does not admit before any lookup, refuses a listed name that resolves to an address the fetch guard's matrix refuses, connects only to the addresses it checked, answers each refusal with a sentence the command prints, and logs it. An entry is a host name of at least two labels, a `*.` name that matches every name below its domain but not the domain, or a public IP address ([`src/network.ts`](src/network.ts)).
- A monotonic tool guard refuses `web_fetch` under `off`, and under `allowlist` for a URL whose host is not listed; `web_fetch` follows same-origin redirects only, so the URL's host is every hop's.
- [`src/network-store.ts`](src/network-store.ts) keeps the settings in `secrets/permission-defaults/network.json` at mode 0600, under the same refusal rule as the permission store. While a store that exists cannot be read, every workspace counts as `off` and no change is recorded.
- Two Fetch routes serve the studio's Network section: `GET /api/deloNetwork.list` and `POST /api/deloNetwork.set`. Both refuse with `LOOPBACK_ONLY` a request that did not arrive on the loopback listener under a loopback `Host`, before its body is read. A change that loosens the network, to a less restrictive access or with a host the old list did not admit, is refused with `NETWORK_UNCONFIRMED` until the request carries the person's confirmation; a tightening applies at once. The model has no tool that reaches the setting, and plugin management cannot reconfigure this row.

## Configuration

| Option | Default | What it does |
| --- | --- | --- |
| `enabled` | `false` | Delo's C16 switch `permission_defaults`, off in the parity composition; on, the plugin seeds each new chat from its workspace, mounts the guard that refuses full access for a workspace nobody consented to, and gives each workspace's sandboxed commands its network. |
| `network` | `open` | The network of a workspace without its own setting: `open`, `allowlist` or `off`. |
| `allowedHosts` | `[]` | The list of a workspace without its own setting, used under `allowlist`; an invalid entry fails the load. |
| `proxyConnectTimeoutMs` | `30000` | How long the egress proxy waits for a connection to a listed host to open. |

## Tests

`tests/store.spec.ts` covers the store's path, its format's round trip, the refusals that make a store count for nothing (a laxer mode, a symbolic link, another format), the entry lookups, and the workspace key that makes one directory one workspace. `tests/permission-defaults.spec.ts` covers the switch off, the seed a new workspace gets, the consent asked once per folder, the refusal that records nothing, the mode switch the guard refuses, and the workspace that already holds a grant. `tests/surfaces.spec.ts` covers the surfaces' calls and routes: the workspaces listed, a grant that lets the switch through and switches the chat the consent was asked from, and only that chat, to full access, a withdrawal that sets open chats back, a store the CLI wrote kept and read again, and the denial cases — a reach device, an unconfirmed answer, a stale review and a chat that is not open in the workspace record nothing. `tests/network.spec.ts` covers allowlist entries, host matching, which changes loosen, and the network store; `tests/egress-proxy.spec.ts` runs the proxy on a real socket with documentation addresses mapped to local listeners; `tests/command-network.spec.ts` mounts the service and covers the resolver, the store, confirmations, the refused store, the `web_fetch` guard and the routes; and `tests/egress.integration.spec.ts` runs confined commands under a real bwrap through the whole chain, skipping where bwrap is unusable.
