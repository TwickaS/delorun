# @delo/home-auth

English | [中文](README.zh.md)

## Summary

This package is the home of the authenticator provider of [contract C4](../../docs/contracts/c04-admission.md#authenticator), with the owner claim and device approval of [C5](../../docs/contracts/c05-device-approval.md), the identity factors of [C14](../../docs/contracts/c14-oidc-passkeys.md) and the server-side reach sessions of C4. It provides the `authenticator` with sign-in by an approved device's key, the approval window and local approval, the `tailnet-membership` identity factor and the allowlist of what an approved device may call, and every CLI profile loads it as the row `delo-home-auth`. The loopback studio is still admitted by upstream's launch token and cookies, and a reach listener serves only while a reach provider asks for it, so with reach off no reach route answers. The first half is the owner claim and device list: the records under `~/.delo/secrets/home-auth/`, the routes that answer them, and the removal that ends a device's live sessions. C4's admission denial suite proves the upstream half of the seam and lives with the CLI, which composes the studio, in `delo/apps/cli/tests/denial/`: upstream's connection declares the `Authenticator` Service Definition and opens reach listeners with `ctx.connection.openReachListener`, and the web server runs each reach listener's dispatcher before any route, upgrade or the fallback. The contract's identifiers, codes and limits come from [`@delo/contract-admission`](../contract-admission/README.md).

## The owner claim and device list

`src/home-auth.ts` is the coordinator over `~/.delo/secrets/home-auth/`, and `src/service.ts` mounts it as the `homeAuth` service, which registers `POST /auth/owner/claim`, `GET /auth/devices` and `POST /auth/devices/remove` with the web server inside `ctx.effect()`. Each rule below is what one spec under `tests/` pins:

- **The owner code** (`owner-code.json`). 128 bits written as 26 base32 characters, printed once and kept only as a SHA-256 digest. A code is single-use and expires 10 minutes after it was printed; a wrong code leaves the outstanding one in place, and a new code replaces it.
- **The claim** (`owner.json`, `devices.json`). Loopback only, and a `Host` naming a reach address is refused even when nothing stamped the request. The claim records the listener's own origin, `http://127.0.0.1:3080`, whatever spelling of loopback the request used — `localhost`, `127.0.0.1`, `[::1]`, a `.localhost` name, with or without a port, through SSH port forwarding — and refuses a `Host` that is no authority at all with `BAD_REQUEST`, so a header an attacker wrote never becomes a device's address. One home has one owner: a second claimant with a fresh valid code is refused with `ALREADY_OWNED` and the first owner keeps the home, and two claims that race are serialised, so exactly one wins the owner seat. The code is consumed before a record is written, so a code that claimed a home never claims a second one, and a home that records devices but no owner refuses a claim with `STORE_INVALID` rather than taking ownership of them.
- **The arrival**. A request is a loopback request only when it carries no reach listener's stamp and the loopback listener's own socket accepted it: its local port is the web server's bound port and its local address a loopback address. Anything else is never loopback (the `a request without a listener stamp is not loopback` spec), so a forwarded request that missed its stamp gains nothing.
- **The arrival of the device routes**. `GET /auth/devices` and `POST /auth/devices/remove` answer on the loopback listener only: both decide the arrival before they read anything, answer a request a reach listener admitted with `403 LOOPBACK_REQUIRED`, refuse a `Host` that names another address with `421 HOST_MISMATCH`, and the removal additionally refuses a page on another origin — an `Origin` other than the request's own, or a foreign `Sec-Fetch-Site` — with `403 ORIGIN_MISMATCH`. That is what keeps a page served from a name that resolves to `127.0.0.1` (DNS rebinding) from reading the home's records or removing a device, and a cross-site form from posting the removal. Every device route on loopback — the list, the removal, the approval window, the pending requests and the approval — also needs the studio's own credential, which `connection.requestRejection` checks as it does for upstream's own routes: the browser's signed launch cookie or a live API credential. A request without it is refused with `401 NOT_SIGNED_IN`, so another program on the computer, a command a chat runs or another user reaches the port and nothing else. A state change also needs an `Origin` equal to the studio's own loopback origin; a request without one is refused with `403 ORIGIN_MISMATCH`. `delorun devices` uses the home socket's `devices.approve` and `devices.remove`, never these routes. No route returns a match code: the pending list carries the request's label, platform, address and times only.
- **The device list**. The owner and every trusted device, without key material. An unclaimed home refuses the listing and the removal with `NO_OWNER`, rather than answering as if it had an empty device list. The owner record and the device list are cross-checked, so a copied `owner.json` naming a first device this home does not record is a `STORE_INVALID` failure rather than an owner, and no listing, session or removal acts for it.
- **The sessions** (`sessions.json`). A token is handed out once and kept as the SHA-256 digest that keys its record, so a copy of the file signs nobody in. A session is minted only for a recorded device at the address it is trusted on: a home with no owner refuses with `NO_OWNER`, an owner record that cannot be read with `STORE_INVALID`, and a key this home does not record — a device of another home, one at another address, or one just revoked — with `DEVICE_NOT_TRUSTED`. A session reads as live only while its device is still recorded at the session's address, so a token whose device is gone answers nothing even when its own record survived.
- **The removal**. Deletes the device's record, invalidates every live session of its tokens, rotates every other session, disposes the device's Peers and closes the reach connections those sessions admitted through `ctx.connection.closeReachConnections({ deviceId })`, all before it returns; a device with no record still has its sessions ended.
- **The limits**. A home trusts at most 32 devices (`DEVICE_LIMIT_REACHED`, `429`) and one device holds at most 16 live sessions (`SESSION_LIMIT_REACHED`, `429`); a session record whose lifetime passed is dropped before the bound is counted, so a device that signs in again after its sessions expired is never refused by them.
- **The records**. Every file is read through [contract C1](../../docs/contracts/c01-home-layout.md)'s protected-file check, so a file another user can read, or one that is not this package's JSON, refuses with `STORE_INVALID` instead of reading as empty and letting a claim replace it.

## Reach sign-in

`src/authenticator.ts` is the provider of upstream's `authenticator` ([C4](../../docs/contracts/c04-admission.md#authenticator)), which the service loads as a child plugin. It keeps upstream's admission on the loopback listener and serves a reach listener only while a reach provider asked `homeAuth.serve()` for it, with the identity factor the provider declares; only `tailnet-membership` on a `ts.net` address of the Tailscale private listener is accepted (`TAILNET_IDENTITY_UNAVAILABLE` otherwise). `admit` is synchronous over an in-memory copy of the stores, which every change rereads before it returns; it stamps each request with its listener, answers the pre-login routes, and admits a `__Host-delo-session` cookie as one Peer per device and listener, which speaks for the device's `reach-device` principal and never for the owner, refusing `SESSION_EXPIRED` past 12 hours unused or 14 days old and `ROTATION_REQUIRED` after a device approval or removal; the session's open reach connections close at those same moments, without waiting for a request. A request without `Upgrade` on a session whose token is 24 hours old receives a new token in `setCookie`; the old token admits for 30 more seconds and is then deleted, and neither extends the absolute limit.

- **The approval window and local approval** ([C5](../../docs/contracts/c05-device-approval.md#approval-window)). `POST /auth/devices/window` on loopback, or the home socket's `devices.approve`, opens a 5-minute window and claims a home that has no owner for the local person. `POST /auth/device/request` outside a window answers `APPROVALS_CLOSED` before it reads the body. `GET /auth/devices/pending`, `POST /auth/devices/approve` and `POST /auth/devices/cancel` are the loopback approval form, behind the studio's credential; the third wrong match code cancels that request only, `Approvals.cancel` cancels a pending request at the person's choice (the home socket's `devices.approve` with `cancelRequestId`), and an approval records the approver `local`, rotates every session and closes the window. A full home refuses a sixth request and replaces none. A label or platform carrying a control or bidirectional formatting character is refused with `BAD_REQUEST`.
- **Sign-in**. `POST /auth/device/challenge` and `POST /auth/session` check an ECDSA P-256 signature over `delo-signin-v1`, the address and a single-use 60-second challenge; on the Tailscale private listener the signature of an approved device alone creates a full session with the factor `tailnet-membership`. The sign-in page (`GET /auth/sign-in`) loads two content-hashed assets from `assets/`, keeps the device key non-extractable in IndexedDB and computes the match code with the same derivation as `src/match-code.ts`. A browser that opens any other page of the address without a live session, the address itself, a deep link or a mistyped path, is sent to the page with `303`, and the page's `next` keeps the target when it is a plain path outside `/auth`, so the device lands there once signed in. The page answers any other `next`, an absolute or scheme-relative URL included, with `303` to itself without it, so it never sends a device off the address. A script's request, a state change and an upgrade keep the `401` JSON refusal, and the loopback listener never redirects. Its markup, `assets/sign-in.html`, has no text and no inline script, style or handler; `assets/sign-in.js` holds every text in English and Chinese, chosen from the browser's languages, and shows one view per state: checking the device, the steps and device name of a new device, the match code to type at the computer with its remaining time while the page reads the request's state every 2.5 seconds, signing in, and each refusal with its next step (approval closed at the computer, five requests waiting, too many requests, a device holding its most sign-ins, cancelled, expired, the home unreachable, a browser without WebCrypto or IndexedDB key storage, and any other refusal with its code). `assets/sign-in.css` repeats the studio's Soft palette and type stacks by value for light and dark, since the studio's bundle does not load before sign-in.
- **The refusals of the home's own computer** ([C14](../../docs/contracts/c14-oidc-passkeys.md#tailnet-membership)). The window, approval and removal routes answer a reach session `403 LOOPBACK_REQUIRED` naming the action. The provider also supplies upstream's `remoteAnswerGuard`: a granting answer (any answer but `rejected`, `cancelled` or `unavailable`) from a reach Peer to an approval prompt that carries `grants: "full-access"` (an escalation to `danger-full-access`, `plugin_manager`'s included, or a workspace's full-access consent) or `grants: "workspace-management"` (the main chat's account tools and its guarded tool calls, and an instruction-layer write that `@delo/plugin-instruction-consent` asks about) is refused with `LOOPBACK_REQUIRED` naming `full-access-escalation` or `workspace-management` and not applied, so the prompt stays open for the studio on the home's computer. A refusal from the device applies. Another Delo plugin's route that only the home's computer may use calls `requireComputer` (`src/computer-only.ts`) from its `connection/request` listener: a request that did not arrive on the loopback listener under a loopback `Host`, or any request while no `homeAuth` is mounted, is answered `403 LOOPBACK_REQUIRED` naming the action before the route reads its body.
- **Pop-up pairing** (C5, [Pop-up pairing](../../docs/contracts/c05-device-approval.md#pop-up-pairing)). `src/pairing.ts` resolves the plugin's `pairing` configuration in one `resolvePairing` step (Delorun's defaults; the schema holds the bounds, so a value out of bounds fails the load or the Settings write; the section is a volatile field, read at each use, so a change applies without a restart) and reads the `Tailscale-User-Login` and `Tailscale-User-Name` headers `tailscale serve` sets. Outside an approval window, `POST /auth/device/request` is accepted only for an identity that `pairing.mayAskWithoutWindow` allows (`own-user` compares with `ServedListener.computerUser`, which `@delo/reach` reads from `tailscale status --json`), with at most `pairing.pendingPerIdentity` waiting per Tailscale user and the global cap of 5, of which requests without a window hold at most 4, so a request through a window the person opened always has room; any other request is answered `APPROVALS_CLOSED` before its body is read. The headers are a quota and display hint, never authorisation: a request still needs the match code typed at the computer. `GET /auth/devices/pending` (loopback only) returns each request's identity, window-less mark and wrong-code count, and the `pairing` values the studio's notice follows. The service registers the `pairing` section as a computer-only setting, so a reach device cannot write it.
- **What a device may call** ([C14](../../docs/contracts/c14-oidc-passkeys.md#what-a-device-may-call)). `src/reach-access.ts` declares the `reach-device` principal, whose fields are the device id and the listener its Peer sits on, and the remote access policy the provider registers for it with upstream's `remoteAccess.registerPolicy`. Upstream's Gateway asks the policy before it dispatches each call of a reach Peer and before it forwards each event to one. The policy refuses by default: it binds the actions of `REACH_ALLOWED_ACTIONS` (what the person does at the computer with chats and workspaces, by the owner's rule that an approved device can already prompt the agent) and of `REACH_ELEVATED_ACTIONS` on the global resource, on every Workspace of the Workspace registry and on every Session of a Workspace or live in the Host, for a device that holds a Peer on the principal's listener; snapshots are recomputed when a Session or Workspace changes. `createCondition` decides per call: an elevated action is refused with `elevation-required: <action>` unless the device holds an unlock on that listener; a `session/create` outside the known workspaces is refused the same way with `CREATE_OUTSIDE_WORKSPACES`; a settings write that could turn a computer-only switch off (a field a mounted plugin registered with `HomeAuthService.registerComputerOnlySwitch`, such as the external-agent consent's `enabled`, written other than as a literal `true`, or arguments it cannot read) is refused with `switchOffRefusal(label)`, a settings write that would loosen a permission-preset row's `defaultPreset` (a looser sandbox mode or approval policy than the current preset's, an unknown preset, a removed field, or any change while the current preset cannot be read, read by `defaultPermissionOf` from the running presets) with `DEFAULT_PERMISSION_REFUSAL`, `pluginManager/setPluginEnabled` on a protected row (one whose module the `plugin-manager` row's `protectedPlugins` names, read from the Loader by `protectedEntryIdsOf` through `protectedPluginsIn`, the reader the CLI's update check shares) with `PROTECTED_ROW_REFUSAL`, and a `commands/execute` whose line the commands service's parser does not resolve to a name of `REACH_DEVICE_COMMANDS` with `UNLISTED_COMMAND_REFUSAL`, each under an unlock as well; and a workspace-file call is refused when its path's real path lies outside the chat's workspace or inside the Delo home (`HomeAuthService.deloHome`, two levels above the secrets directory), which the service itself would follow wherever it points, through a symbolic link included. The unlock (`src/elevation.ts`, C14's [Elevation](../../docs/contracts/c14-oidc-passkeys.md#elevation); `src/elevation-routes.ts` serves the device's request, state and lock on its reach listener and the computer's list, approval and revoke on loopback only) lives in the memory of this profile's Host against the device, the listener and the session that asked, starts only with the 8-digit code the device shows typed at the computer, and ends at its minutes, a revoke at the computer, the device's lock, the session's end, the device's removal, the listener's stop or the Host's; its end closes the device's reach connections, since the Gateway decides a stream only when it opens, and each start, ending and admitted call is logged. Every other action, each one of `REACH_DENIED_ACTIONS` with its reason or one no table names, is refused with `remote-access/denied` and the reason `loopback-required: <action>`; an allowed or elevated action on a Session the policy cannot name, such as a stored Session outside every Workspace that is not live, is refused with `resource-unlisted: <action>`.
- **Loosened settings** ([C14](../../docs/contracts/c14-oidc-passkeys.md#elevation)): a default-preset loosening or a consent turn-off an unlocked device makes under dangerous mode is recorded in `reach-dangerous-settings.json` (`src/dangerous-settings.ts`) before it proceeds, and `HomeAuthService` sets the previous value back through the settings service at the first read of the mode that finds it ended and at start; a field the person changed since stays.
- **Terminals** ([C14](../../docs/contracts/c14-oidc-passkeys.md#elevation)) always need an unlock: the condition refuses every `terminal/*` action to a locked device on every resource, whatever dangerous mode, a workspace's full-access grant or an earlier version's `reach-terminal.json` says. Nothing reads that file now; a home that still has it keeps working, and the file can be deleted. `reachFullAccessGrants`, declared in `src/full-access-grants.ts`, supplies dangerous mode's state only.
- **Which paths a device reaches** ([C4](../../docs/contracts/c04-admission.md#pre-login-allowlist)). After sign-in, `admit` passes a reach request only when its target is a plain path on `REACH_DEVICE_PATHS` (`src/reach-paths.ts`), a table with one reason per entry: the studio page `/`, its `/assets` and install-time files, `/api` with its `/api/remote.mux` upgrade, the client plugin bundles under `/plugins`, this package's `/auth` routes and `/delo/reach/status`. Every other target, of any exact, prefix or upgrade route or the fallback, is refused with `403 LOOPBACK_REQUIRED` before its route runs, after the session's own refusals and without rolling the session, so a route that only checks that its request was admitted, such as upstream's `open-in-app`, never answers a device. A target is plain when parsing it changes nothing and it holds no empty segment and no escaped `/` or `\`; only its path is matched, never its query. Under `/api`, each exact Fetch route answers a device only when it admits that Peer, and none of Delo's does. `delo/apps/cli/tests/denial/reach/reach-paths.integration.spec.ts` boots the whole CLI composition, requests every registration of the web server as a signed-in device, and fails on a registration the device reaches that it does not list and on an exact Fetch route without a recorded decision.

Not built here: passkeys, OpenID Connect, the recovery kit, reset, alerts, and the records of loopback credentials with their idle limit that C4 describes. Loopback credentials are upstream's launch cookie and API credential, admitted by upstream's built-in admission; no per-credential record exists, so no loopback request is refused for lacking one.

## The admission denial suite

`delo/apps/cli/tests/denial/admission/` boots the web composition of Delo's CLI profiles in the test process: upstream's web template, which Delo's profiles extend, with the web server on a port the operating system assigns. Delo's own bundle layer is left out of that composition; `delo/apps/cli/tests/denial/reach/reach-paths.integration.spec.ts` boots the whole CLI profile, Delo's bundles and their web routes included, and requests every registration as a signed-in device. The suite then loads a stand-in provider, `StandInHomeAuth`, which admits one session cookie and delegates the loopback listener to Connection's built-in admission, and a fixture community plugin with an exact route, a prefix route and an upgrade route. It opens all three reach listeners: `reach-tailscale-private` and `reach-tailscale-funnel` on `127.0.0.1` ports, and `reach-self-hosted-relay` on streams a local TCP server hands to it with a certificate from the stand-in stack's test authority.

The tests are named after C4's denial table:

| Test | What it proves |
| --- | --- |
| `every route and upgrade answers 401 before sign-in on each reach listener` | Every exact route, prefix route, upgrade route and the fallback the booted composition registers, and the fixture plugin's, answers 401 on each reach listener, and no fixture handler runs; with a session the same fixture route and upgrade run. |
| `a plugin route is pre-login only when the profile lists it` | A fixture route the provider answers as pre-login is refused until the listener's policy lists it, and refused again when the listing is removed. |
| `a pre-login request never reaches the fallback or another route` | An allowlisted path with no registered route is refused rather than served by the fallback. |
| `a cookie minted with upstream's secret is refused on a reach listener` | A `dsh-auth-*` cookie that upstream minted for the reach listener's own authority, and that admits on the loopback listener, is refused with `UPSTREAM_COOKIE_REFUSED`, also beside a session cookie. |
| `launch tokens and /connect are refused on a reach listener` | The process launch token in a `token` query and requests for `/connect` are refused, and no cookie is set. |
| `a loopback Host is refused on a reach listener` | `localhost`, `127.0.0.1` and `[::1]` in `Host` are refused with `HOST_MISMATCH`, on requests and upgrades. |
| `each listener refuses a Host its rule does not allow` | Each reach listener refuses the other listeners' addresses and a foreign name; the relay listener refuses an SNI other than its name with `SNI_MISMATCH`; the loopback listener refuses a foreign `Host` with upstream's 403. |
| `an upgrade with a foreign or absent Origin is refused` | An upgrade to `/api/remote.mux` without `Origin`, with another origin or with `null` is refused with `ORIGIN_MISMATCH`; the listener's own origin reaches the upgrade handler. |
| `removes Tailscale identity headers before admission` | The provider never sees a `Tailscale-*` header on any reach listener, on a request or an upgrade, and the Gateway's WebSocket still accepts the upgrade. |
| `no reach listener runs without home-auth` | Removing the provider closes every reach listener and its open connections; no reach listener opens without a provider, the loopback listener admits as upstream does, and a replacement provider that serves no reach listener opens none. |

A type-level check holds C4's `Admission` and `ListenerPolicy` types assignable to the upstream seam's, and a spec holds the dispatcher's refusal statuses equal to C4's.

## The reach access denial suite

`delo/apps/cli/tests/denial/reach/` boots the same web composition, loads this package's service, opens a session for an approved device and admits it through the provider, then calls the Gateway with the Peer it returns. Each family `REACH_DENIED_ACTIONS` lists is refused naming the action, a settings write in every settings namespace the composition describes included; reading the chat list, the redacted settings, the plugin list and the files of a chat's own workspace, starting a chat, sending a message, choosing a preset and stopping the run succeed, and the device's event stream carries the chat events and no plugin management event. The suite also lists every Remote method the composition registers and every event it forwards, and fails on one that neither table names and on a table entry that names none, so a new method is refused by default and its classification is a decision.

## Dangerous mode

While dangerous mode holds, an unlocked, signed-in device does what the computer does. The fact is `HomeAuthService.dangerousMode()`, read when asked from the `reachFullAccessGrants` service that [`@delo/plugin-permission-defaults`](../plugin-permission-defaults/README.md) provides: true only when the row sets `fullAccessEverywhere` and the grant file `delorun setup` wrote is valid, and false without that plugin or while its store cannot be read. Removing the grant file or turning the row off restores every refusal at the next call. A device whose unlock has ended keeps every refusal it has today, and each lifted refusal below still needs an unlock.

| Refusal | Safer prompts and Same as stock | Dangerous mode |
| --- | --- | --- |
| A settings write that turns a computer-only switch off (`loopback-required: turning … off`) | Refused, unlocked or not | Decided by the unlock |
| A settings write that loosens the permission new chats start in | Refused, unlocked or not | Decided by the unlock |
| `pluginManager/setPluginEnabled` on a protected row (the plugin manager still refuses a change to a guard plugin itself) | Refused, unlocked or not | Decided by the unlock |
| `commands/execute` of a command a device does not run | Refused, unlocked or not | Decided by the unlock |
| An approval prompt marked `full-access`, `workspace-management` or `external-agent` answered from a device | `LOOPBACK_REQUIRED` | Given by an unlocked device |
| The permission-defaults routes that review and grant a workspace's consent (`deloPermission.workspaces`, `.review`, `.setFullAccess`) | `LOOPBACK_REQUIRED` before the body is read | Admitted for an unlocked device |
| The network routes (`deloNetwork.list`, `.set`) | `LOOPBACK_REQUIRED` | Admitted for an unlocked device |
| The MCP consent routes (`deloMcpConsent.pending`, `.accept`, `.decline`, `.revoke`) | `LOOPBACK_REQUIRED` | Admitted for an unlocked device |
| The external-agent consent routes (`deloDelegationConsent.*`) | `LOOPBACK_REQUIRED` | Admitted for an unlocked device |
| Provider keys (`credentials/describe`, `.set`, `.unset` and the two `credentials` events), which answer presence and writability and never a saved key | `loopback-required` | Admitted for an unlocked device |
| Opening a chat's folder in an application on the computer (`session/openWorkspacePath`, `session/workspacePathApplications`) | `loopback-required` | Admitted for an unlocked device |
| A workspace-file call (`workspaceFiles/*`, `officeKit/render`) with a path outside the chat's workspace | `loopback-required: … with a path outside the chat's workspace` | Admitted for an unlocked device; the Delo home stays out of reach. The lift equals what full access already gives a chat in the mode |

Each consent and permission route above calls `requireComputerUnlessDangerous` from its `connection/request` hook and registers `admitUnlockedDevice` as its `admitPeer`, both in `src/computer-only.ts`. The hook lets a request through that arrived on a reach listener only while the mode holds, and the Peer check admits only a `reach-device` that holds a running unlock then; a request the home cannot place, or that names a foreign `Host` on the loopback listener, is refused in both modes. The reach policy decides the actions: `REACH_DANGEROUS_ACTIONS` lists the credential and application actions, which the role lists and the condition refuses with `loopback-required` while the mode is off and with `elevation-required` to a locked device, and the workspace-file path bound moves only for an unlocked device while the mode holds. A computer-only settings switch is lifted only when `DANGEROUS_LIFTABLE_SWITCHES` names its namespace (the external-agent consent today); registering a switch lifts nothing, so the reach and pairing settings stay at the computer in every mode. The workspace-file service does not consult the chat's permission; the chat's own tools do.

These stay at the computer in every mode: turning the mode on (only `delorun setup` writes the grant, and no route or call does), approving a device and opening the approval window, the device sign-in, approving or revoking an unlock, removing a device, and the home's reset, recovery kit and reach settings. Account actions and opening the settings document stay in `REACH_DENIED_ACTIONS`. `tests/dangerous-mode.spec.ts` proves each lifted refusal in both modes and fails when one of the routes that approve, sign in, remove a device or change remote access reads the mode.

## PIN mode

PIN mode lets a person who holds an approved device unlock a page with a PIN or passcode instead of typing a code at the computer ([C14, "PIN mode"](../../docs/contracts/c14-oidc-passkeys.md#pin-mode)). Version 1 serves the Tailscale private address only. The mode is off until the person sets a PIN at the computer; while it is off, every route and refusal of this package is as described above, and `POST /auth/pin/unlock` answers `PIN_MODE_OFF`.

- **Store.** `src/pin-mode.ts` keeps `pin-mode.json` (whether the mode is on, the secret's kind, a salted `scrypt` hash with its parameters, the idle minutes) and `pin-attempts.json` (wrong tries per device and across the home), both through the protected-file helpers at mode 0600. A PIN is 6 to 128 digits that is not a repeat, a run or a common PIN; a passcode is 10 to 128 characters. The hash is compared in constant time, and the secret is registered with the log redactor while it is handled and appears in no error or log line. The limits are `PIN_MODE_LIMITS` of `@delo/contract-oidc-passkeys`.
- **Unlock.** `src/pin-unlocks.ts` verifies the secret and starts an elevation for the device, listener and session, so the reach policy's `elevationOf` admits the unlock table of C14. The page receives a 32-byte token once; the home keeps its SHA-256 digest and binds it to that device, listener and session. A token presented by anything else is refused with `UNLOCK_INVALID` and ends the unlock. The page sends it in the `Delo-Unlock` header only.
- **Ends.** An unlock ends after the idle minutes (15 by default, 60 at most) without `POST /auth/pin/touch`, at the 12-hour cap however active the page is, on `POST /auth/pin/lock`, when the PIN changes or the mode turns off, and with every ending an elevation has.
- **Wrong tries.** A try is counted and written before the secret is compared, one at a time per device. The fifth wrong try removes the device exactly as a removal at the computer does. Ten wrong tries across the home within 24 hours pause PIN unlocks until the computer resumes them. A restart keeps both counts.
- **Routes.** `src/pin-routes.ts` answers `GET /auth/pin/state`, `POST /auth/pin/unlock`, `/touch` and `/lock` for a device on the private listener. `GET /auth/pin/mode` and `POST /auth/pin/set`, `/off` and `/resume` answer the person at the computer only; a device is refused with `LOOPBACK_REQUIRED`. `delorun` reaches the same changes through the home process's `pin.set`, `pin.off` and `pin.resume`.
- **What is not built.** The page-unlock token does not yet bind a single tab: the unlock admits the device on its listener, as an unlock approved at the computer does. The client's lock screen, the `Delo-Unlock` header on API requests and WebSocket upgrades, the lifts of dangerous mode for an unlocked page, the answer guard, step-up, passkeys, the Funnel and relay addresses, and setting the PIN from a device are not built.

`tests/pin-mode.spec.ts` proves each defence by a test that fails without it: the count before the comparison, the device removal, the home-wide pause, the address rule, the token binding, the idle end and the cap, the computer-only routes, and that the PIN is in no file, log or answer.

## Notes for the provider

- **Pre-login asset routes.** A handler for `GET /auth/assets/<asset>` resolves the segment against a fixed table of built asset names. It never decodes the segment and then joins it to a directory path, because a decoded `..` or separator would leave the asset directory.
- **The claim's arrival.** The claim route decides where the request arrived before it reads the body, and its refusal names the loopback listener and SSH port forwarding; a reach listener answers the same refusal through `reachClaimRefusal()` before any route is consulted.
- **The device routes' arrival.** The listing and the removal decide the arrival before they read anything, and both refuse a request whose `Host` names another address; the removal also refuses a page on another origin. A device is listed, approved and removed only at the home's own computer, so a reach session's request is answered `LOOPBACK_REQUIRED`.
- **Revocation.** Removing a device or ending a session calls `ctx.connection.closeReachConnections({ deviceId })` or `({ sessionId })` before it returns, so streams and upgraded sockets that carry no Peer, such as `/plugins/events` and plugin upgrade routes, end with the session; disposing the device's Peer ends the streams that speak for it.
- **Expiry and rotation.** A rotation trigger closes every session's reach connections with `({ sessionId })` before it writes the rotation marks. Each session also has one unref'd timer for the earliest of its idle limit, its absolute limit and, for a token a roll replaced, the end of its 30-second grace; when it fires with no request admitted since, it closes that session's connections whether or not a request arrives, and stopping the service clears every timer. Use is an admitted HTTP request or upgrade on the session's token: bytes on a connection admitted earlier never reach `admit`, so an open stream or WebSocket keeps nothing alive. Frames a client sends on an open WebSocket do not count either, because neither the reach dispatcher nor this provider sees them, and the connection layer cannot tell a Remote call from the automatic Pong answering the Gateway's heartbeat Ping; the served studio sends its unary calls over HTTP, so a person using it keeps the session live. Connections close per session, never per device, because a device holds up to 16 sessions. A session a re-sign-in replaced keeps its open connections until its own idle or absolute limit, so the sign-in's own response is never cut.
- **Loopback credentials.** Upstream's connection emits `authenticator/minted` for each loopback mint, before it writes the response that sets the credential. This package does not listen to the event; a provider that records loopback credentials must record each mint before that response is written.
