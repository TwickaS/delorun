# @delo/plugin-mcp-consent

English | [中文](README.zh.md)

## Summary

This package is the `mcpAddConsent` provider of Delo's MCP add-time consent, the protection the C16 switch [`mcp_add_consent`](../../docs/contracts/c16-parity-composition.md) turns on. A stdio MCP server command runs as a local child process outside the agent sandbox, so before such a server starts, the mcp-client plugin asks the mounted `mcpAddConsent` service whether the configured start is granted. This package answers from the acceptance store, one JSON file under the home's protected state that holds one acceptance per configured server name: a server whose acceptance covers exactly the command, arguments, working directory and configured environment under review, and the absolute executable path, command shell and working directory they resolve to, starts at once, and every other review holds the server stopped with a refusal that names the command. The person accepts a held server at the home's own computer, in the studio's Settings, Permissions, or with `delorun mcp accept`, and the server then starts without a restart; the person declines it, or revokes an acceptance there or with `delorun mcp revoke`, and that server stays stopped until its start changes or the person accepts it ([Pending reviews](#pending-reviews)). Off, or without a mounted provider, an mcp-client starts every configured server exactly as upstream does; `@delo/bundle-local` mounts it on in the CLI profile that `delorun` starts, `@delo/bundle-headless` mounts it on in the profile `delorun headless` runs, and the desktop app runs upstream's profiles, which do not mount it.

## The service

`DeloMcpConsent` extends the abstract `McpAddConsent` service of the `@deepseek-ai/dsh-mcp-client` seam, whose `review` the mcp-client consults before it starts each configured stdio server. The review never waits for a person: allowing a start starts the server, and refusing one fails the mcp-client's activation with the typed refusal that names the command and its arguments and carries the provider's reason, so the server stays stopped. A refusal repeats at every boot of the server row until the start is accepted, and an acceptance given after a refusal lets the next boot start the server.

A review is shown the server's whole start: the server name, the command, its arguments, its working directory and its configured environment entries, with the absolute executable path and canonical working directory the mcp-client resolved them to, and on Windows the canonical `COMSPEC` that runs a `.cmd` or `.bat` file. The mcp-client resolves an empty or relative working directory against the Host's working directory and looks a bare command up in the `PATH` the server would be started with, then spawns the server with those resolved paths, so an accepted start runs the executable the person accepted even when the Host starts in another directory or its `PATH` changes. A command it cannot resolve stops the server with `McpServerStartUnresolvedError` before any review. The refusal names the resolved executable, the working directory and the names of the configured environment variables but none of their values, because a value may be a credential. The review compares those paths, not the contents of the files: when the accepted executable or a script argument lies where chats can write, such as a workspace or `node_modules/.bin`, whatever is written there later runs outside the sandbox at the next start or reconnect, and the review says so instead of refusing it.

The module exports `providesMcpAddConsent` as `true`, the declaration the mcp-client's consent lookup reads under the Loader: an mcp-client row that finds no `mcpAddConsent` service waits until every row has imported its module and this row has started, so a server never starts unreviewed because its row started before this one. If this row fails to start, the server stays stopped with `McpConsentUnavailableError`; with the switch off, the row starts and registers nothing, and the server starts as upstream starts it.

The service resolves the home the process runs with for every review: `resolveDeloHome` of [`@delo/home`](../home/README.md) resolves it from `DELO_HOME` or `~/.delo`, so a home that cannot be resolved is one more review that asks again.

## The acceptance store

The store is `secrets/mcp-add-consent/acceptances.json` under the resolved home. It is a protected file of contract C1 ([`@delo/home`](../home/README.md)): it is read through the refusal rule and written at mode 0600 into a directory created at mode 0700, under the home's `secrets/` directory, which the sandbox's confinement rules deny to confined commands on Linux and macOS (the Windows runner does not confine reads) — a command an acceptance would let run outside the agent sandbox can neither read the list nor add itself to it.

The file is one JSON object `{ v, acceptances, setAside, commandKeyed }` whose `v` is the format version, 5:

- `acceptances` maps a configured server name to the start accepted for it: the command, the argument list, the configured working directory, the absolute executable path and canonical working directory they resolved to, for a Windows batch file the canonical `COMSPEC` as `resolvedShell` (absent otherwise), the environment as each variable's name with a SHA-256 digest of its name and value, and the acceptance time. Different server names never share or overwrite an acceptance, so two servers started with `npx` keep separate acceptances; accepting a changed start of the same server replaces its acceptance. An acceptance's id ([`acceptanceIdOf`](src/store.ts)) is a digest of the server name and the whole start, resolved paths included, so a revoke names one acceptance.
- `setAside` maps a server name to the start the person declined or whose acceptance the person revoked: the state, `declined` or `revoked`, and a digest of the whole start, resolved paths included ([`startDigest`](src/store.ts)). A review of that exact start is refused in that state without waiting for an answer, across restarts; a review of another start of the server, or of the same start that now resolves elsewhere, drops the entry and waits, and accepting the server drops it.
- `commandKeyed` keeps the acceptances of a version 4 store, which were keyed by the command alone, as that version wrote them, resolved paths included. They never allow a start. A start that one of them covers exactly, resolved paths included, is reviewed with the change `upgraded`, once per server, and accepting such a start drops the record it matches.

The store holds no environment value in plain text, and the digests are the same whatever order the environment's keys were written in. A version 4 store is read as a store with no acceptance whose acceptances are the `commandKeyed` records, and the next write turns it into a version 5 store that keeps them. A store of version 1, written before an acceptance covered the working directory and the environment, of version 2, written before it covered the resolved executable path and working directory, or of version 3, written before it covered the command shell or kept one acceptance per server without resolved paths, is superseded: no review counts any of its acceptances, and the next write replaces it with a version 5 store that holds only that write. Any other store that exists but is not one of these formats — no JSON document, not an object, another version, an unknown field, a wrong entry, a resolved path that is not absolute — is refused as a whole: no review counts anything as accepted, and the provider never writes into a refused store, so the person fixes or removes the file first.

## Reviews

`review(command)` answers one configured server start:

- the server name's acceptance of exactly the reviewed command, arguments, working directory, environment, resolved executable path, command shell and resolved working directory allows the start;
- an absent store, an unreadable, superseded or not this version's format store, a server with no acceptance, a changed command, argument list or working directory, an added, removed or changed environment variable, a command that now resolves to another executable, a batch file that now runs through another `COMSPEC` or none, a working directory that now resolves to another directory, a start the person set aside, and a home that cannot be resolved all refuse with the reason that asks the person again. A reason names changed variables and resolved paths but no environment value, and another server name's acceptance of the same start never counts.

The review covers the executable's path, not the file's contents or a symbolic link's target, and the interpreter a script's `#!` line names is looked up in the server's own `PATH` after the spawn.

Every refusal's reason ends with where the person accepts the server: `delorun mcp accept <name>` at the home's computer while Delo runs, or the studio's Settings, Permissions ([`acceptHint`](src/review.ts)).

## Recording an acceptance

`accept(start)` records that the person accepted a server start — the server name, the command, its arguments, its working directory, its configured environment and the resolved executable path, command shell and working directory a review was shown — as that server name's acceptance; a start whose resolved paths are not absolute is refused. Accepting a server again replaces its earlier acceptance, so a changed start is granted by accepting it as it now is. The acceptance drops the server's declined or revoked start and the `commandKeyed` record that covers the start exactly. The store's acceptances grow only through it; `acceptReview` calls it with the start a pending review showed.

## Pending reviews

Every refused review is kept, in this process, as the server's pending review: one per server name, the latest, so a start that changed after a review replaces that review. The service is also provided as `mcpReviews` ([`src/review.ts`](src/review.ts)):

- `pending()` lists each pending review as a surface shows it ([`PendingServer`](src/wire.ts)): the server name, the command, its arguments, its working directory, the absolute executable (`resolvedCommand`) and canonical working directory (`resolvedCwd`) the start resolves to and, on Windows, the command shell that runs a batch file (`resolvedShell`), so a surface shows the file that runs before the person answers, the configured environment variables, the refusal's reason, what the review asks about, the changed variables, its state, when it was reviewed and its review id — a digest of every field of the start, the environment through its digest ([`mcpReviewId`](src/review.ts)). An environment variable's value is shown only when [`showsEnvValue`](src/wire.ts) holds for its name: `NODE_OPTIONS`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `PATH`, `PYTHONPATH` and every `DYLD_` variable, which change what runs; every other value is never shown. `change` is one of [`SERVER_CHANGES`](src/wire.ts): `new` for a server with no acceptance, an absent store or a superseded one; `command`, `arguments`, `directory` or `environment` for the first part of the start that differs from the server's acceptance, with `changedVariables` naming each variable added, removed or changed; `resolved` for a start configured as accepted whose command now resolves to another executable, whose working directory resolves to another directory, or whose batch file runs through another command shell; `unreadable` for a refused store or a home that cannot be resolved; `upgraded` for a start a version 4 record covers exactly. `state` is one of [`SERVER_STATES`](src/wire.ts): `waiting`, `declined` or `revoked`.
- `acceptReview(serverName, reviewId, confirmed)` first resolves the shown start's command and working directory again with the mcp-client's `resolveServerStart`; when they now resolve to another executable, directory or command shell, or no longer resolve, it records nothing and refuses with `STALE_REVIEW`, and a start that resolves elsewhere is reviewed again, so the list shows the new paths under a new review id. Otherwise it records exactly the start that review showed through `accept`, in any state, removes the review, and starts each Loader row that this consent refused for that server again with its own configuration, so the server runs without a restart of the studio; without a Loader, the next start runs it. `declineReview(serverName, reviewId)` keeps the review listed as `declined`, records the start as declined and records no acceptance; the server stays stopped until its start changes or the person accepts it. While the store cannot be read or written, the decline holds in this process only and a warning says so.
- `accepted()` lists each acceptance ([`AcceptedServer`](src/wire.ts)): its id, the server name, the command, its arguments, its working directory, the executable, working directory and command shell it resolved to, its environment variables, the acceptance time, and whether a configured Loader row has the server name; a variable's value appears only where `showsEnvValue` holds and the server's configured row sets the value whose digest the acceptance holds. It lists none while the store is absent or cannot be read. `revokeAcceptance(acceptanceId, confirmed)` removes that acceptance, records its start as revoked, then applies each Loader row of that server name again with its own configuration, so its review refuses the start as `revoked` and the server stops until its start changes or the person accepts it again; it answers how many rows stopped and leaves every other acceptance.
- The answers refuse with `McpReviewError` and record nothing for `UNCONFIRMED` (an accept or revoke without `confirmed: true`), `STALE_REVIEW` (the server has no pending review with that id because it was reviewed again or accepted after it was shown, its start now resolves to other paths than the review showed, or no acceptance has the revoked id because it was replaced or revoked) and, for an acceptance or a revoke, `STORE_REFUSED`, which also refuses a shown start whose resolved paths are not absolute. Each answer logs one line.
- Where a Connection serves the studio, five exact routes under `/api` carry them ([`src/wire.ts`](src/wire.ts), [`src/routes.ts`](src/routes.ts)): `GET /api/deloMcpConsent.pending` (the pending reviews and the accepted starts), `GET /api/deloMcpConsent.waiting`, `POST /api/deloMcpConsent.accept`, `POST /api/deloMcpConsent.decline` and `POST /api/deloMcpConsent.revoke`. Each but `waiting` answers only a request that arrived on the loopback listener under a loopback `Host`; a reach device is refused with `403 LOOPBACK_REQUIRED` before the body is read, so a server is accepted or revoked only at the home's computer. `waiting` also admits the Peer of a device that reach admitted (`admitPeer`) and answers only the name and `change` of each review in state `waiting`, never a declined or revoked one and never a command, arguments, directory or environment, so a phone can say that a server waits and is approved at the computer. The studio's Permissions section, the MCP server review and the waiting-server notice live in [`@delo/bundle-local`](../bundle-local/README.md#the-consent-surfaces); `delorun mcp` reaches the same calls through the home process's `mcp.list`, `mcp.accept`, `mcp.decline` and `mcp.revoke` ([C19](../../docs/contracts/c19-home-process.md)), which only the person's own command may answer.

## The mcp_add_consent switch

The `enabled` config field, the C16 switch `mcp_add_consent`, decides whether the plugin registers the service. It defaults to off — the parity value — and Delo's composition turns it on; a `cordis.yml` row mounts the package and names the switch's value. Off, the plugin registers nothing and every configured server starts exactly as upstream starts it.

## Development

`tests/consent.spec.ts` covers the store, its version 1 and version 2 predecessors and the reviews; `tests/reviews.spec.ts` covers the pending reviews with what changed, which variables and which values are shown, the declined and revoked states across a new service instance, the restarted row, the accepted starts kept apart per server name and their revoke, and the routes, with the denial cases: a reach device reads only the waiting servers' names and what changed and is refused every other route, and an unconfirmed or stale answer or revoke records nothing. `tests/restart.spec.ts` runs the acceptance and the revoke under a real Loader. The specs run with `node_modules/.bin/vitest run --config delo/vitest.config.ts delo/packages/plugin-mcp-consent`, and the package typechecks with `node_modules/.bin/tsc --noEmit -p delo/packages/plugin-mcp-consent/tsconfig.json`.
