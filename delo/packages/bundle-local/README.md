# @delo/bundle-local

English | [中文](README.zh.md)

## Summary

`@delo/bundle-local` is the bundle that Delo's CLI profiles add after upstream's `web` profile template. Its patch holds Delo's local integration rows, each listed with its reason in [`LOCAL_ROWS`](src/rows.ts), so a Delo CLI profile composes upstream's web profile with those rows changed or added and nothing else. It turns off upstream's two opt-ins, DeepSeek's session-log upload and the desktop app's analytics, and adds the Privacy section in Settings, where the person turns each one on after a consent dialog and off again ([C11](../../docs/contracts/c11-setup-answers.md)). It mounts Delo's consent and guard plugins with their switch on — the instruction-layer write consent, the MCP add-time consent, the per-workspace permission defaults with the one full-access consent, the scheduled-task consent and the fetch guard — mounts the update gate, which refuses new turns while `delorun update` or `delorun stop` waits for running chats, and sets C1's home protection on upstream's sandbox row, so a confined command cannot read the consent stores under the home's `secrets/`.

## Use this bundle

- **The bundle list.** [`DELO_PROFILE_BUNDLES`](src/profile.ts), exported from `@delo/bundle-local/profile`, is the ordered `dsh.profile.bundles` list of a Delo CLI profile: upstream's `web` template, read from `@deepseek-ai/dsh-official-bundles`, followed by `@delo/bundle-local` and then [`@delo/bundle-studio`](../bundle-studio/README.md) (`STUDIO_BUNDLE`), which mounts the studio additions. Upstream's own templates do not list this bundle, so `dsh --profile web` and the recorded-session replay compose upstream's bundles alone.
- **What `delorun` owns.** `delorun`, which creates the CLI profiles under `~/.delo/profiles/` ([C1](../../docs/contracts/c01-home-layout.md#profiles)), writes `DELO_PROFILE_BUNDLES` into each CLI profile it creates, and refuses to start a CLI profile when upstream's profile loader reports this bundle in `skippedBundles`, because the privacy defaults hold only while the bundle loads. This package does neither itself.
- **Layer order.** The bundle applies after every upstream bundle and before the profile's own `cordis.patch.yml`, the home patch and `--patch` overlays, so a person's setting in the profile still wins over a row here ([upstream's profile layers](../../../apps/cli/README.md#profiles)). The Privacy section writes to the profile's `cordis.patch.yml`.
- **Reading the composition.** `dsh --profile <name> --dump-config` prints every composed row under a `# ==` line naming the bundle that inserted it and each bundle that patched it; a row this bundle writes names `@delo/bundle-local` there.
- **Loading.** The bundle declares no `engines.dsh` range and no upstream peer, so upstream's compatibility check never skips it after a version change; a profile whose bundle list names it and cannot resolve it reports the bundle as skipped.
- **The update gate.** The `delo-update-gate` row mounts [`@delo/bundle-local/update-gate`](src/update-gate.ts), the C16 switch `update_turn_refusal`, which provides the `deloTurnGate` service. `delorun`'s Host attaches its chat gate's held state with `attach(isHeld)`, whose disposer detaches it; while any attached source is held, the plugin's `agent/pre-step` listener, which runs before every other, refuses the first step of every new turn by throwing `UpdatePendingError` (code `UPDATE_PENDING`). The loop ends that turn as `error` with the error's message, which says that the message was not sent and to send it again once Delo is back, and makes no model request; a later step of a turn that was already running goes on. With the switch off, the plugin's default, it provides no service and refuses nothing ([C19](../../docs/contracts/c19-home-process.md)).
- **The version row.** The harness half prints Delo's version (from `delorun`'s `DELO_VERSION`) and the DeepSeek Harness version upstream reports into each page as the global `deloVersions`; the browser half validates it and then registers Settings' version row under the stock row's id `current-version` at rank -1, so it takes that row's place and reads "Delo version" and "DeepSeek Harness version". A harness that `delorun` did not start prints nothing and keeps the stock row.
- **The notice service.** The browser half provides `ctx.deloNotice` (`acknowledged()`, `acknowledge()`), so a flow that shows the preview notice's copy itself, such as `@delo/plugin-onboarding`'s first screen, records the acknowledgement and this bundle's notice step completes without showing a second time.
- **Statements.** The `./statements` export is the Privacy section's English dictionary ([`src/client/locales.ts`](src/client/locales.ts)), which the CLI's setup reads so its questions and the section state the same sentences.
- **Building.** `pnpm --filter @delo/bundle-local run build` writes `lib/index.js`, the Host half of the `delo-privacy` row, and `lib/client.js`, the Privacy section. Upstream's `pnpm run build:artifacts` does not build Delo's packages.

## Rows

[`LOCAL_ROWS`](src/rows.ts) lists each row in which a Delo CLI profile differs from upstream's web profile, and the row's form in the C16 parity composition:

| Row | Kind | In a Delo CLI profile | In upstream's web profile | In the parity composition |
| --- | --- | --- | --- | --- |
| `session-log-deepseek` | changed | `config.enabled: false`: model requests carry no `dsh_session_log` field | the plugin's default, `true` | upstream's composition: the overlay leaves the row out, because it follows each replay's root configuration, which sets the upload per corpus |
| `deepseek-account` | changed | `disabled: true`: no DeepSeek account sign-in, Platform, Usage or Top-up page; `llm-deepseek-account` stays inert without an account | enabled | upstream's composition: the overlay leaves the row out |
| `product-analytics` | changed | `config.enabled: false`, with upstream's `appVersion` restated and upstream's `disabled` condition kept, so the row mounts only in the desktop profile and accepts no event there | `config.enabled: true` | as written here; the replay mounts no desktop Host |
| `session-telemetry-otel` | changed | `disabled: true`: no session-log prefix leaves the machine with feedback; upstream's feedback exporter sends it to DeepSeek's collector | enabled, `FEEDBACK_ONLY` | upstream's composition: the overlay leaves the row out |
| `sandbox` | changed | `config.protectedHome` is the harness home, which C1 sets to the Delo home for every runtime process, with C1's read exemptions (`runtimes`, `skills`, `dsh-runtimes`): a confined command cannot read the consent stores under `<home>/secrets`, and `read`, `read_image`, `apply_patch`, `glob` and `grep` refuse the same paths from every row that mounts them, each agent preset's rows included | the row is mounted bare, so the provider protects no home and the tools refuse nothing | upstream's composition: the overlay leaves the row out, so the replay runs upstream's confinement and the tools search as upstream's do |
| `command-feedback` | changed | `disabled: true`: no `/feedback` command | enabled | upstream's composition: the overlay leaves the row out |
| `ui-message-feedback` | changed | `disabled: true`: no Like, Dislike or feedback dialog; upstream offers no row that opens an external page | enabled | upstream's composition: the overlay leaves the row out |
| `ui-settings-account` | changed | `disabled: true`: no account menu entry, sign-in dialog or account section | enabled | upstream's composition: the overlay leaves the row out |
| `account-controller` | changed | `disabled: true`: the API controller over the account service requires `deepseekAccount`, which no enabled row provides once `deepseek-account` is disabled, so it would never activate | enabled | upstream's composition: the overlay leaves the row out |
| `ui-settings-models` | changed | `config.welcomeNotice: false`: upstream's preview notice is off; `credentialOnboarding` keeps upstream's value | `welcomeNotice: true` | upstream's composition: the overlay leaves the row out |
| `delo-privacy` | added | the Privacy section in Settings, the Delo sidebar brand (the product name as text, no mark), and Delo's own preview notice | absent | present and disabled, because recorded web scenarios compare upstream's interface output, brand and notice |
| `delo-instruction-consent` | added | `@delo/plugin-instruction-consent` with `config.enabled: true`: a model-authored write to a skill, a preset or an `AGENTS.md` asks, with the effect and the diff, before it commits | absent | present and disabled: the switch's parity value, off, so the write path runs unasked |
| `delo-mcp-consent` | added | `@delo/plugin-mcp-consent` with `config.enabled: true`: a stdio MCP server command starts only once the acceptance store holds an acceptance for it | absent | present and disabled: the switch's parity value, so every configured server starts as upstream starts it |
| `delo-permission-defaults` | added | `@delo/plugin-permission-defaults` with `config.enabled: true`: a new workspace starts on the safer preset, full access needs one consent per workspace, and this plugin is the seam's one `sandboxModeGuard` | absent | present and disabled: the switch's parity value, so the deployment default reaches every new chat and every mode switch is recorded |
| `delo-schedule-consent` | added | `@delo/plugin-schedule-consent` with `config.enabled: true`: an approval names the recurrence and its target, and a due delivery is refused when the target chat left the preset the approval named | absent | present and disabled: the switch's parity value, so approvals and deliveries keep upstream's text and behaviour |
| `delo-fetch-guard` | added | `@delo/plugin-fetch-guard` with `config.enabled: true`: `web_fetch` refuses loopback, link-local, private-network and unique-local destinations with a typed reason | absent | present and disabled: the switch's parity value, so the recorded fetch scenarios call their loopback fixtures unchanged |
| `delo-update-gate` | added | `@delo/bundle-local/update-gate` with `config.enabled: true`: while `delorun`'s chat gate is held, the first step of every new turn is refused with `UPDATE_PENDING` | absent | present and disabled: the switch's parity value, so every turn starts as upstream starts it |

The [parity overlay](../../apps/tools/src/parity/composition/parity.overlay.yml) mounts this bundle by restating its patch in that form; [`parityPatches`](src/rows.ts) derives the form from this bundle's `cordis.patch.yml`, and `parity-switches` fails when the overlay differs from it. Delo's composition sends nothing to DeepSeek's feedback collector: the feedback exporter, the `/feedback` command and the feedback surfaces are disabled or hidden, because Delo has no feedback destination yet. Upstream's composition keeps them, and the parity composition keeps upstream's rows. No row names a Delo host.

## The Privacy section

The browser half ([`src/client/index.ts`](src/client/index.ts)) also registers Delo's preview notice ([`src/client/DeloNotice.tsx`](src/client/DeloNotice.tsx)) in the `settings.onboarding` slot, ahead of the model-provider onboarding. Its copy is in the locale dictionary, and it shows once per notice version on a browser (`NOTICE_VERSION`), recorded in local storage as a per-viewer convenience. The studio's document title is built from `DSH_CLIENT_TITLE`, which `delo/apps/tools/src/build-web.ts` sets to `Delo`. It also registers the `settings.section` `delo-privacy` ([`PRIVACY_SECTION_ID`](src/client/index.ts)), after upstream's Plugins section, and the sidebar brand occupants `sidebar.brand.name` and `sidebar.brand.mark` ([`src/client/brand.tsx`](src/client/brand.tsx)), which show the product name as text and no mark. Both come from the one `delo-privacy` row, so the parity composition, which disables that row, keeps upstream's brand. The document title is a build setting, `DSH_CLIENT_TITLE`, outside the slot system. It shows C11's statements (Delo has no telemetry of its own; both opt-ins are off unless the person turns them on; sending feedback includes a session-log prefix and happens only on sending), then one row per opt-in:

- **DeepSeek session-log upload** edits `session-log-deepseek`, and **Desktop analytics** edits `product-analytics`, each through upstream's configuration form for that row ([`OPT_IN_ROWS`](src/client/index.ts), from `@delo/contract-setup-answers`). A write changes only that row's `config.enabled`.
- **Turning on** opens a dialog that names what is sent and where; nothing is written until the person chooses Turn on, and Cancel writes nothing. **Turning off** writes at once.
- The switch shows the value the Host accepted. A refused or failed write leaves it unchanged and says so in the row.
- A profile that does not serve an opt-in's row shows no switch for it; for desktop analytics, the row says that only the desktop app collects it.

Setup and other surfaces open the section with `ctx.settingsShell.openSection('delo-privacy')`. Upstream's own **Settings → General** switch for session-log upload stays, and it edits the same row without the dialog. The section's copy is in English and Chinese.

## Tests

`node_modules/.bin/vitest run --config delo/vitest.config.ts delo/packages/bundle-local` runs the package's specs, which import upstream's built packages and so need `pnpm run build:artifacts`; Delo's check runner starts it when the build is missing.

- [`composition.spec.ts`](tests/composition.spec.ts) builds a Delo CLI profile under a temporary `DSH_HOME` and reads it through upstream's real `dsh --profile <name> --dump-config`: every bundle of the list loads and none is skipped; the dump prints every row under a label whose writers are bundles of the list, prints nothing before the first label and nothing on stderr, and lists exactly the rows of `LOCAL_ROWS` as written by this bundle; the composition equals upstream's `web` profile row for row, except the rows of `LOCAL_ROWS`, which are changed in place or added after upstream's rows as each entry says. It also holds every enabled row to the DeepSeek hosts it names: only `api.deepseek.com`, the model provider's API under the person's own key, may appear, and the feedback exporter, the account surfaces and the feedback surfaces are not composed.
- [`privacy-defaults.spec.ts`](tests/privacy-defaults.spec.ts) mounts upstream's own plugins with the rows each profile composes, against local network fixtures. With a Delo CLI profile's rows, no model request body to a mock DeepSeek API carries `dsh_session_log`, and a local OTLP collector receives no analytics record; with upstream's web profile rows, the same fixtures receive both. No string in the composition, `!!js` expressions included, names a Delo host, and the rows naming a Delo package are this bundle's own browser half, the five consent and guard plugins it mounts, its update gate and the trash.
- [`confinement.spec.ts`](tests/confinement.spec.ts) reads the composed `sandbox` row and configures upstream's local sandbox provider with it: the row's `protectedHome` is the Delo home and its `protectedHomeReadable` C1's read exemptions, and a workspace command confined by that provider cannot read a canary under `<home>/secrets`, while the same command unconfined reads it and a file under an exemption stays readable. The home sits outside the OS temporary directory, which upstream's profiles replace with a private `/tmp`, so the denial is the protected home's and not the private directory's.
- [`update-gate.spec.ts`](tests/update-gate.spec.ts) runs the update gate on upstream's production agent loop with a scripted model: while an attached source is held, a new turn ends with `UPDATE_PENDING` before any model request and before any other `agent/pre-step` listener, and the next turn runs once the source is released; a turn whose tool holds the gate takes its next step; the gate is held while any attached source is held and a detached source no longer counts; with the switch off no service is provided and no turn is refused.
- [`rows.spec.ts`](tests/rows.spec.ts) derives the parity form of a patch list from `LOCAL_ROWS` and refuses a patch that is neither an id patch nor an insert, an inserted row that is not a mapping and an unlisted row.
- [`notice.client.spec.tsx`](tests/notice.client.spec.tsx) renders Delo's preview notice: it states Delo's own status, shows once per notice version on a browser, and reports its onboarding step complete when acknowledged.
- [`privacy-section.client.spec.tsx`](tests/privacy-section.client.spec.tsx) renders the section: each opt-in turns on only after the dialog's Turn on, writes only its own row, and turns off again from the same switch; Cancel writes nothing; a failed write keeps the accepted value; an unserved analytics row shows its reason; the plugin registers the section, the Delo sidebar brand occupants, and writes each opt-in to its upstream row.
- `apps/web/tests/delo-privacy-consent.e2e.ts` builds this package, boots the studio with it as a profile bundle against a mock DeepSeek API and drives the section in Chromium: the first model request carries no session log, desktop analytics and session-log upload each turn on alone after consent, the next request carries the session log, and turning upload off again from the section removes it from the following request.

## Limits

- The bundle list is a constant for `delorun` to write; no shipped upstream template names it, so the recorded-session replay mounts this bundle only through the parity overlay.
- A profile created before a change to `DELO_PROFILE_BUNDLES` keeps the list it was created with.
- The privacy defaults hold only while the profile loads this bundle. Upstream reports a bundle it cannot load as skipped and starts without it, and session-log upload is then on; `delorun`'s refusal to start such a profile is what keeps the defaults.
- Desktop analytics mounts only in upstream's `desktop` profile, which `delorun` does not run, so a Delo CLI profile's section shows that row's reason instead of a switch.
