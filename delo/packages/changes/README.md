# @delo/changes

## Summary

A person's harness is the signed release plus the changes they approved at their computer. This package keeps the approved copy of every plugin the profile links from a folder, computes what a folder changed against that copy, and makes the profile load the approved copy, never the folder. It also keeps the person's changes to the harness itself: their writable copy of an installed release, the files they approved, and the composed tree a start runs instead of the signed installation, which it never writes. The contract is [C21](../../docs/contracts/c21-changes.md).

## Use this package

```text
import { enforceApprovedContent, pluginChange, startNotice } from '@delo/changes'

const changes = await enforceApprovedContent({ home, profile, profileDir })
output(startNotice(changes))
```

`delorun start` and `delorun headless` call `enforceApprovedContent` through `delo/apps/cli/src/changes/start.ts` in their pre-start step `changes`, before upstream prepares the profile. `enforceApprovedContent` ends by checking the links and active directories (`checkLoadedContent`), refusing with `LOAD_REFUSED` when one is not what Changes keeps, and by collecting the store (`collectStore`, [C21](../../docs/contracts/c21-changes.md#collecting-the-store)). `prepareReload` is the same check before every recomposition of a running Host, which `@delo/plugin-changes` provides to upstream's hot reload as `profileReconcileCheck` and `delorun plugin` runs after upstream's operation: it moves links to folders to their active directories where the profile write lock allows and refuses anything else that differs. `checkChangesInvariants` adds that every approved version reads back from the store, for `delorun verify` and `delorun doctor`, and the composition's approved plugin content step refuses a start when it returns any invariant that does not hold. `changesStatus` gives what `delorun verify` and `delorun doctor` report and writes nothing; `writeBootRecord` and `readBootRecord` keep `run/<profile>/changes-boot.json`, which plugins under Changes loaded at the last start.

## Where the files are

Everything is under `changes/` in the Delo home, which confined commands can neither read nor write (contract C1). `store/objects/` holds file contents by SHA-256 and `store/versions/` the file list of each content version, named by the SHA-256 of its entries. `profiles/<profile>/active/<plugin>/` is the directory the profile's `link:` dependency names; `active.json` says what each holds, `log.json` is the change log and `work-session.json` the work session. `protection.json` holds the protection setting and `migration.json` the profiles the home held at the first start under Changes. The profile's `package.json` records each approved plugin's folder and version under `delo.changes`, so every profile history version holds it.

## How the profile loads approved content

pnpm resets the `node_modules` link of a `link:` dependency on every operation, so the start moves the recorded dependency itself: `package.json`, the lockfile's importer entry and the link name the active directory. Under Block the active directory holds the approved version, or nothing for a plugin with none, so upstream skips it; under Warn and Off, and in a work session, it holds the folder's content. Files that differ from what the directory should hold are replaced in place, so upstream's hot reload replaces exactly the changed modules.

The first start under Changes of each profile the home held when Changes began approves every linked plugin as it is (`migratesAtUpgrade`), and starts name those plugins until a terminal showed them (`markShownAtUpgrade`). A plugin linked later, or by a profile created later, waits for review. Links into the runtime store and to the directory the running installation carries for that package are the harness, not plugins, and are left alone: a source checkout runs the whole harness from the checkout. A plugin's links to sibling workspace packages (a directory with a `package.json` linked at `node_modules/<name>`) and to installed packages (below a `node_modules` directory) are included in its content by hash, an installed package with the dependencies installed beside it, within 50,000 files, links and directories and 512 MiB, each file read no further than the size counted. Any other link out of the folder, and any link into the Delo home, `/proc`, `/sys` or `/dev`, is left out of the copy. A link whose folder is missing is moved to its empty active directory like any other, so a folder created there later waits for review. A folder over the limits, or one that cannot be read, never stops a start: under Block the approved content keeps running and the start names the plugin; under Warn and Off a folder over the limits only with its installed packages loads them from where they are installed.

## Pending changes and the risk summary

`pluginChange` stores the folder's content as a version and compares it with the approved one: the files added, changed and removed, a unified diff bounded at 256 KiB with files larger than 1 MiB and binary files named only, and a risk summary. The change id is derived from the plugin, its folder and both versions, so applying an id applies exactly the content that was shown. `reviewChange(input, checks)` runs the seven built-in checks, `not-shown` among them, which names each new file whose lines the diff leaves out: a binary file Node loads, a file above or past the diff's limits, and a dependency's files inside the folder; it is the one place a later extension point adds registered checks. The summary is a help to the reader and not a protection: a plugin's code can do anything Delo can.

## Records and who writes them

Every record is a 0600 file whose reader refuses an unknown field, value or mode with `RECORD_UNREADABLE`. `setProtection` accepts only a proof from `attestTerminal`, which requires standard input and output to be terminals. `attestStudio` issues the studio's proof for a request at the computer (the loopback listener under a loopback `Host`, with the studio's credential, not a remote session), which only `@delo/plugin-changes`' routes call; the actions and `openWorkSession` and `closeWorkSession` accept either proof, and `setProtection` refuses a studio one. A proof is refused unless an attest function issued it. The proof does not tell a person from a model, whose terminal tool has a real pseudo-terminal; a confined model is kept out by the sandbox, which lets it write nothing under the home. `pluginSlug` refuses a name that is not a package name before any path is built from it. `noteLoaded` and `noteFailed` record what the Host loaded or failed to load in the open work session and need no proof. `writeWorkFailure` and `readWorkFailure` keep `run/<profile>/changes-work.json`, the last failed reload in a work session.

## What a person does with a change

`src/actions.ts` holds the operations `delorun changes` and the studio's Changes routes call. `listChanges` computes what each plugin's folder holds against its approved content, hides a change discarded for that content, and returns the changes a failed start left out (`leftOut`) and the other logged changes newest first, the plugins whose folder is gone, the protection setting and any work session; `showChange` returns one change or its log entry. `recordedChanges` (`src/state.ts`) gives the studio's `state` route the plugins under Changes with their folders and the agent's requests waiting for review from the approved record and the change log alone, writing nothing and reading no folder. `applyChange`, `discardChange`, `undoChange`, `turnOff`, `turnOn` and `changeProtection` take an `AtComputer` proof and refuse one the attest functions did not issue before they read anything. `applyChange` approves exactly the version the id names and refuses with `CHANGED_SINCE_REVIEW` when the folder holds anything else; `turnOff` and `turnOn` edit only `dsh.profile.bundles` and refuse Delo's own bundle.

`src/install-actions.ts` (also the entry `@delo/changes/install`) holds the agent's plugin requests ([C21](../../docs/contracts/c21-changes.md#the-agent-and-plugins)). `recordPluginRequest`, which `@delo/plugin-changes` calls when the agent's `plugin_manager` would install, update or remove a plugin, writes one pending `plugin-install`, `plugin-update` or `plugin-remove` entry with `subject.spec` and nothing else. `applyInstallChange` takes an `AtComputer` proof, runs the injected upstream plugin operation (`add <spec>` or `remove <name>`, given the folder a spec names so the operation checks its package) under the profile write lock, records one history version and reloads the Host; after a failed or refused operation it puts `package.json` and `pnpm-lock.yaml` back, records the build scripts pnpm held back with upstream's `recordPendingBuilds`, and leaves the request pending with the failure; a spec that names a folder is linked to the plugin's active directory, empty until the person applies the folder's content, which it records as a pending folder install. `listChanges` returns the waiting requests as `requests`; `applyChange` refuses them and `undoChange` refuses an applied one.

Each runs under upstream's profile write lock and records one profile history version naming the change id; discarding and the protection setting record none. An action that changes what the Host runs then calls the injected `ReloadHost`, which `delorun changes` implements with the update channel's `changes.reload` and which answers `undefined` when Delo is not running; the home process's answer to `changes.reload` and the studio's routes both reload with `reloadProfile(hmr)` ([reload](src/reload.ts)), upstream's hot reload in the Host's own process. When the reload fails, the action goes back: the approved record, the active directory and `active.json`, or the bundle list, return to what they held, a second history version records it, the change is pending again with `lastFailure`, and the Host is reloaded once more.

## Work sessions

`startWork(ctx, plugin, proof, { reload, minutes })` opens a work session on an approved plugin for 1 to `WORK_SESSION_MAX_MINUTES` (480) minutes, records its end as `endsAt`, and loads its folder's content at once. `reviewWork(ctx, plugin)` stores the folder's content and returns it with its difference from the approved content the session started from, for `done` to show; `finishWork(ctx, plugin, proof, { reload, approve })` approves exactly the content `approve` names as one applied `plugin-edit` change and one history version `Work on <plugin>: <from> → <to>`, loading it first when the Host does not run it yet, and refuses with `CHANGED_SINCE_REVIEW` when the folder holds anything else. Both refuse a proof the attest functions did not issue. While the session lasts, `loadWorkSession(ctx, reload)` loads the folder's content when it is new to the session: it copies it into the active directory and reloads the Host, and when the reload fails it puts the content that last loaded back, reloads again, notes the failure and writes `changes-work.json`, leaving the session open; after `endsAt` it loads nothing, and a start that finds the session past `endsAt` ends it without the person before it loads anything. `workSessionFact(home, profile)` gives the open session, its end and its last failed reload for `delorun status` and the studio's badge.

The plugin keeps loading from its active directory, so the home process watches the folder itself (`delo/apps/cli/src/changes/work-watch.ts`) instead of setting upstream's `hmr.root`, which would watch files that are not loaded. When Delo stops, when a start finds a session a home process that did not stop left open, and at `endsAt`, `finishWorkWithoutPerson(ctx, why, reload?)` ends the session without the person and approves nothing: the approved content stays the version the session started from, the active directory holds it again, and the folder's content waits for review as the ordinary pending change. It needs no proof, so it is exported only from `@delo/changes/stop`, which only the CLI's start module imports.

## When a start fails

`src/left-out.ts` leaves out the change that broke a start ([C21](../../docs/contracts/c21-changes.md#when-a-start-fails)). `newestLeavableChange(ctx)` names it: the newest decision that changed what runs, when it applied a person's `plugin-edit`, `plugin-install`, `plugin-update` or `plugin-on` to a plugin linked to its active directory that holds the change's content; otherwise nothing, so a second failure leaves nothing more out. `leaveOutNewestChange(ctx, failure)` writes only the change log under the profile write lock, marking the entry `left-out-at-start` with the failure; it takes no proof, and only `delo/apps/cli/src/changes/retry.ts` calls it. From then on `enforceApprovedContent` makes the plugin's active directory hold the change's `from`, or nothing, with `active.json` kind `left-out`, and names it with `leftOutWords` in `startNotice`, until `applyChange` loads it again or `undoChange` undoes it. `listChanges` returns such changes as `leftOut`; `leftOutFacts(home, profile)` gives them to the studio and `changesStatus` to `delorun doctor`.

## Changes to the harness itself

`src/harness.ts` keeps the person's edits of an installed runtime's `app/` files ([C21](../../docs/contracts/c21-changes.md#harness-edits)). Every function takes a `HarnessContext`: the home, the running runtime version and `signed()`, the installation with the signed file list the runtime store's start check verified, read only when needed; every byte read from the installation is checked against that list. `createHarnessCopy` makes `changes/harness/<runtime>/copy/app/`; `harnessChanges` computes one pending `harness-edit` change per file of the copy that differs from what runs; `showHarnessChange` stores both sides and reviews them; `applyHarnessChange`, `discardHarnessChange`, `undoHarnessChange` and `discardAllHarnessChanges` decide under `withHarnessLock`, each taking a proof of presence, and log in `changes/harness/log.json`. `listHarness` gives `list` the waiting, left-out and logged changes. `src/harness-tree.ts` builds and checks the composed tree (`prepareComposedTree`, `checkComposedTree`), removes the trees and directories no start needs (`retainHarness`), and reports a runtime's harness for `verify` and `doctor` without writing (`harnessStatus`). `newestLeavableChange(ctx, runtime)` and `leaveOutNewestChange(ctx, failure, runtime)` leave a harness change out when it is the newest decision across both logs.

## Harness changes across an update

`src/harness-merge.ts` decides what an update does with each approved file of the harness ([C3](../../docs/contracts/c03-update-report.md#reasons)). `mergeHarnessFile({ base, mine, theirs })` merges the running release's signed file, the approved content and the target's signed file, each with its execute bit or `undefined` for no file: `same` when the target already holds the approved content, `carried` with the content the target runs when the target left the file as it was or the patch from the base to the approved text (jsdiff's `structuredPatch`) applies to the target's text with no fuzz and no line-ending conversion, and `conflict` with its reason otherwise. Both sides changing a file that is binary, not UTF-8 or larger than `DIFF_FILE_LIMIT` conflicts, and so do a file the target removes after the person changed it, a file the person removed after the target changed it, and a file both add with different content. `planHarnessCarry(home, record, readSigned)` reads each file's base and approved content from the store by the record's `signed` and `version`, asks `readSigned` for the target's verified file, and returns a `HarnessCarryPlan` with all three sides and the outcome of every file, in path order; it writes nothing. A version that is not a one-file version of its path is refused with `RECORD_UNREADABLE`. The update report's `harness` items are built from the plan by `delo/apps/cli/src/update/harness-items.ts`; applying the plan, the target's record and the `<file>.mine` files, is not built.

## Not covered

- Plugin code runs with the harness's full authority; nothing here confines it.
- A changed file of the signed installation is refused by the runtime store's start check in every protection setting; the person's edits run only from the composed tree, once applied.
