# Delo release tooling

English | [中文](README.zh.md)

`@delo/release` is Delo's release tooling, a private package in `delo/apps/release`. It holds the changelog gate, the release-notes assembly, the published recipe that builds the runtime closures, the comparison of two builds that signing requires, the release's SBOM, the dependency advisory check, the signing and verification of release metadata, the release log, and the S2 and S3 images. The [release manifest contract](../../docs/contracts/c02-release-manifest.md) (C2) defines the release files, the reproducibility scope and the signing rules this package implements.

## Modules

- `src/changelog/paths.ts` classifies a path as a product file, which needs a changelog entry, or as a fragment.
- `src/changelog/fragment.ts` parses a fragment's front matter and body, and lists the unreleased folder.
- `src/changelog/version.ts` accepts release versions.
- `src/changelog/check.ts` is the gate `gates:changelog`. It checks each commit of a range and every fragment in the working tree.
- `src/changelog/assemble.ts` assembles a release's notes, its `CHANGELOG.md` block and its moved fragments.
- `src/build-closure.ts` is the closure recipe's command; `src/closure/` holds its steps: the recipe files (`config.ts`), the pinned downloads (`sources.ts`), Delo's packages in the closure (`delo.ts`), the files the launcher starts a closure with (`launch.ts`), the staged tree and the runtime file list (`tree.ts`), the native-code check (`native.ts`) and the archiving (`archive-closure.ts`).
- `src/local-release.ts` builds one signed release into a directory laid out as a release channel; `src/local/release.ts` holds its steps (see [Local release](#local-release)).
- [`@delo/release-formats`](../../packages/release-formats/README.md) holds the formats this tooling shares with the shipped verifiers: the deterministic tar, gzip and ZIP writers and readers and the inspection of the deterministic form (`archive/`), the signature envelope, canonical JSON, the readers of each signed file and client verification (`sign/`), the release-log entry, bundle, signed notes, Merkle proofs and tiles (`log/`), and the version and digest brands. Nothing it ships depends on this package, so the runtime closure carries none of the tooling.
- `src/compare-rebuild.ts` is the rebuild comparison's command; `src/rebuild/` holds the comparison; the PE normalisation of its first exception is `@delo/release-formats/archive/pe`.
- `src/record-rebuild.ts`, `src/sign-release.ts`, `src/sign-root.ts` and `src/sign-timestamp.ts` are the signing commands; `src/rebuild/record.ts` holds the rebuild record's facts and `src/sign/` the timestamp content and signing.
- `src/sbom/` writes the SPDX SBOM from the runtime archives; `src/check-advisories.ts` and `src/advisory/` run the dependency advisory check.
- `src/build-images.ts` and `src/images/` build the S2 and S3 images from `images.json` and `images/`; `src/log-release.ts` and `src/log/client.ts` submit the release-log entry and write its bundle.
- `tests/` holds the specs. The changelog specs run both entry points on temporary git repositories; the archive, closure and rebuild specs build fixture closures in temporary directories and serve pinned downloads from a local HTTP stand-in, the signing specs sign fixture releases with keys generated in the test, and the release-log specs run a local log and witness stand-in, so none needs the network or a real key. `tests/images/images.docker.spec.ts` builds both images twice and runs only with `DELO_DOCKER_SPECS=1`, because the check runner has no Docker lane. `tests/closure/boot.closure.integration.spec.ts` sets up a new home from a built closure, starts the CLI profile and requires every `@delo/` row to be active; it runs only when `DELO_CLOSURE_ARCHIVE` names a built `linux-x64` closure archive, and the release workflow must run it on the `linux-x64` archive it publishes.

## The gate

`node_modules/.bin/tsx delo/apps/release/src/changelog/check.ts --base <rev>` checks each commit after `<rev>`. A commit that changes a product file adds a fragment under `delo/changelog/unreleased/` or carries a `Changelog: none (<reason>)` trailer. Product files are every path outside the documentation, tooling, release, workflow and changelog trees, except Markdown files and bilingual pairing records (`*.i18n.yaml`), which are documentation wherever they are. The gate also refuses a reason-less trailer and every fragment that does not parse. It prints one line per violation and exits 1.

## Assembly

`node_modules/.bin/tsx delo/apps/release/src/changelog/assemble.ts --version <version> [--date <YYYY-MM-DD>] [--dry-run] [--first-public-release]` assembles the unreleased fragments into one version. The version is a preview sub-version `0.x.y-preview.N` (N from 1), a release `0.x.y`, or an `-alpha.N`, `-beta.N` or `-rc.N` pre-release; `1.0.0` is refused unless `--first-public-release` is passed. Assembling `0.x.y` folds the entries of its previews into it.

The assembly writes `delo/changelog/changelog.json` (the standing comparison with the upstream release in `upstream.ref` of `delo/upstream-patches.json`, and every version), renders `CHANGELOG.md` at the repository root from it, writes the release notes to `delo/changelog/releases/<version>.md`, and moves each consumed fragment into `delo/changelog/releases/<version>/`. Pending fragments are never assembled. A version that is already assembled is refused. The first release that commits `CHANGELOG.md` adds its divergence-ledger entry in the same commit.

`--dry-run` prints the entry and the notes and writes nothing; `--list-unreleased` prints the unreleased fragments by area and the pending ones with what each waits for. The fragment format, the areas and the data file are described in [`delo/changelog/README.md`](../../changelog/README.md).

## Runtime closures

A runtime closure is one platform's installable runtime: the pinned Node executable and its licence under `node/` (`node/bin/node`, or `node/node.exe` on Windows), pnpm under `pnpm/`, and the closure root package's `package.json`, `pnpm-lock.yaml` and production dependencies under `app/`. The root package is the one `closure.json` names, [`@delo/runtime-closure`](../runtime-closure/README.md): upstream's `dsh-python-runtime-closure` (`python/sdk-runtime`), the dependency-only manifest whose dependencies are the `dsh` command with every plugin its shipped profiles load and their workspace peers, which upstream's `verify-runtime-closure` check keeps complete, and `@delo/cli` with Delo's packages. The `delorun` command's entry file is `app/node_modules/@delo/cli/src/bin.js`, and the `dsh` command's `app/node_modules/@deepseek-ai/dsh/lib/bin.js`.

`closure.json` also names the client title, `Delo`, which the client artifacts present as the page title, the home-screen title and the web manifest's name, and the install anchor: `@deepseek-ai/dsh`, whose `package.json` upstream's runtime resolution reads to decide what a profile's plugin rows can import, with the Delo bundles it must declare (`@delo/bundle-local` and `@delo/bundle-studio`, every `@delo/` bundle a new CLI profile lists). Without that declaration, `delorun` refuses every start because a Delo plugin row fails to import.

`node_modules/.bin/tsx delo/apps/release/src/build-closure.ts --version <version> --out <dir> [--commit <rev>] [--platform <platform>]... [--cache <dir>]` builds the closures of every platform, or of the named ones, from a commit (`HEAD` by default). It runs on Linux or macOS and refuses to run under a Node or pnpm version other than `toolchain.json` pins. For each build it:

1. exports the commit's tree to the build root `closure.json` fixes, `/var/tmp/delo-release-build/source`, so the absolute paths that bundlers embed in client artifacts are the same on every builder; the build holds the lock file `/var/tmp/delo-release-build.lock`, which records its process id, so a second build on the computer refuses and names the holder instead of removing the first one's tree, and a directory at that path that the command did not create is refused, never removed;
2. runs `pnpm install --frozen-lockfile` and `pnpm run build:artifacts` there with only the builder's `PATH`, `HOME`, `USER`, `TMPDIR` and proxy variables, plus `SOURCE_DATE_EPOCH` (the commit's committer time), `-ffile-prefix-map=<build root>=.` in `CFLAGS` and `CXXFLAGS`, `TZ=UTC`, `LC_ALL=C` the commit id the client artifacts embed and `DSH_CLIENT_TITLE` set to the client title, so upstream's own client build presents it; then it builds Delo's packages that have a `build` script (`pnpm --filter ./delo/packages/* run build`), which `build:artifacts` does not build;
3. for each platform, runs `pnpm deploy --prod --ignore-scripts` of the root package with that platform's `--os`, `--cpu` and `--libc`, a hoisted `node_modules` and copied files, replaces package links with files, shares each workspace package between its consumers as upstream's executable build does, removes pnpm's deploy metadata and the root package's other files; transpiles each `@delo/` package's `src/**/*.ts` to JavaScript beside itself, with relative imports and `package.json` entry points rewritten to `.js`, and removes the package's `tests`, because Node does not run TypeScript from `node_modules`; stamps the release version into `@delo/cli`'s `package.json`, where `delorun --version` and the plugin version checks read it (the workspace holds `0.0.0`); adds each Delo bundle the anchor must declare to its `package.json` dependencies at the bundle's staged version; and replaces each workspace package `prebuilt-pins.json` lists under `substitutes` with its published tarball, after checking the tarball's integrity and that its version equals the deployed source version;
4. adds the Node executable from the distribution archive `toolchain.json` pins by SHA-256, and pnpm from the tarball it pins by integrity, each downloaded once into the cache (`~/.cache/delo-release` by default) and used only when its bytes match;
5. checks every ELF, Mach-O and PE file outside `node/` against the platform's `files` entry in `prebuilt-pins.json`: an unlisted file, a changed digest or a listed file that is absent stops the build;
6. refuses to archive a closure that lacks launch protocol 1's files, `node/bin/node` (`node/node.exe` on Windows) and `app/node_modules/@delo/cli/src/bin.js`, which the runtime store requires before the launcher starts a runtime; then writes `delorun-<version>-<platform>.tar.gz` (`.zip` for `win32-x64`) and its unsigned runtime file list `delorun-<version>-<platform>.files.json` to `--out`, which never replaces an existing file; after building every platform, it writes the SBOM `delorun-<version>.spdx.json` there too.

`--write-pins` records the native files of the built platforms in `prebuilt-pins.json` instead of checking them; the recorded change is reviewed like any other change to the recipe.

`--artifacts existing` builds a closure for a local release from artifacts already built in the worktree, instead of running `pnpm run build:artifacts` in the exported tree. It refuses unless the worktree is at `--commit`, its tracked files are clean, and every package whose `main` names a file under `lib/` has that file and a `lib/` newer than its `src/` (the artifact build through the check runner, `run-checks.ts --only build:artifacts`, makes them current). The ignored `lib/` directories, the client bundles and the native addon are then copied into the exported tree. Such a closure embeds the worktree's paths and keeps the worktree's own native addons instead of the pinned publications, and its native files are not checked against `prebuilt-pins.json`, so it is for a local release only, never for signing. Because its paths are local anyway, it builds in a fresh directory `/var/tmp/delo-release-build-<suffix>` of its own, removed when the build ends, and holds no lock, so local builds of several worktrees run side by side. The recipe's own build stops today at the pinned `@deepseek-ai/node-addon-system-*` publication, version 0.1.2, which differs from the 0.2.0 of the deployed source.

Every native addon in a closure is a prebuilt file: upstream's `@deepseek-ai/node-addon-system` platform packages come from their npm publications, and the other addons from the npm tarballs the lockfile pins by integrity. `toolchain.json` therefore names no compiler or linker, and the prefix map applies only if a build step compiles code.

### Archive format

Both formats hold only regular files, in byte-wise UTF-8 path order, with no directory, link or device entry, and with mode `0644`, or `0755` for a file that any execute bit marks in the staged tree.

- **tar.gz**: POSIX ustar headers with uid and gid 0, empty user and group names and every mtime `SOURCE_DATE_EPOCH`; a path the name and prefix fields cannot hold gets a pax header with one `path` record. The archive ends with two zero blocks. The gzip member has mtime 0, no file name, operating system byte 255, and deflate at level 9.
- **ZIP**: "version made by" Unix 2.0 with the mode in the external attributes, UTF-8 names, no extra fields, comments, data descriptors or ZIP64 records, DOS time `SOURCE_DATE_EPOCH` in UTC rounded down to an even second, and each entry deflated at level 9 unless storing it is smaller. An archive holds at most 65,535 entries.

An archive is at most 1 GiB, the download limit of [C1](../../docs/contracts/c01-home-layout.md).

## Local release

`node_modules/.bin/tsx delo/apps/release/src/local-release.ts --version <version> --out <channel dir> --root <root file>... --targets-key <targets.pem> --timestamp-key <timestamp.pem> --state <state.json> --log-submit <url> --log-checkpoint <url> --log-tiles <url> [--commit <rev>] [--closures-from <dir>] [--cache <dir>]` builds and signs one release from a commit into a directory laid out as a release channel, for a launcher built with that directory's origin as its channel origin (`delo/apps/npm-launcher`). It composes the steps above and adds no cryptography:

1. It checks the roots as a client does and that `--targets-key` is the newest root's one active targets key.
2. It builds the Linux x64 closure from `--commit` (`HEAD` by default) with `build-closure.ts`'s recipe and the same toolchain checks, or, with `--closures-from`, takes the `delorun-<version>-linux-x64.tar.gz` and `.files.json` that a `build-closure.ts --platform linux-x64` run left there. `--version` names the release whatever the commit holds, so the same commit builds as two versions and an update exists to take.
3. It signs the file list and writes the manifest, signed by the targets key, as `sign/release.ts` does. The manifest's source is the public repository, the tag `v<version>` and the commit; its builder is "local release (no independent rebuild)". The manifest schema requires files that a local release does not build (the other platforms' runtimes, the desktop installers, the images, the SBOM, the install scripts, the rebuild record, the advisory report), and those are zero-length placeholders that the channel does not serve. `source.tag` need not exist.
4. It submits the manifest's Rekor v2 entry to the log that `--log-submit`, `--log-checkpoint` and `--log-tiles` name, as `log-release.ts` does, and writes the bundle when it verifies with the root's log and witness keys. The command asks for a witnessed checkpoint at most 60 times, 30 seconds apart. Name only a log you run, unless this release is meant for the public log.
5. It signs the next timestamp with `--timestamp-key` from the signer's state in `--state` (created on the first release, as `sign-timestamp.ts --init-state --first` does, and replaced after each signing), naming the release for both channels. A version below the one the channel serves is refused.

The channel directory then holds `timestamp.json`, `root/<n>.root.json` for each `--root` and, for each version, `releases/download/v<version>/` with the manifest, its log bundle and entry request, and the archive and signed file list. The release files go in first and the timestamp last, so a failed build leaves the channel serving what it served, and a version already in the channel is never replaced. Serve the directory with any static server, and build the launcher with `--channel-origin` set to its origin, as the [launcher's README](../npm-launcher/README.md#building-the-package) describes.

A local release is not a published one: no second builder rebuilt it, no advisory check ran, and its keys are whatever `--root`, `--targets-key` and `--timestamp-key` name. `tests/local/e2e.integration.spec.ts` runs the whole path on throwaway keys and local servers: it signs a release with this command, builds and packs a launcher for it, installs the release through `npm exec` with the log unreachable and checks the printed steps and the warning, the record in `trust/release-log.json` and the runtime's start. Its runtime is a fixture whose entry file prints its stamped version. With `DELO_CLOSURE_FILES` naming a directory that holds the `delorun-0.1.0-linux-x64` archive and file list a `build-closure.ts --version 0.1.0` run wrote, one more spec installs that real closure through the packed launcher and runs its `delorun --version`. `tests/closure/boot.closure.integration.spec.ts`, with `DELO_CLOSURE_ARCHIVE` naming the archive (and `DELO_CLOSURE_EXISTING_ARTIFACTS=1` for a build from existing artifacts), sets up a home from the closure, starts the CLI profile with every Delo row active, and starts the Host as the home process and requests the studio's index on loopback.

## Rebuild comparison

`node_modules/.bin/tsx delo/apps/release/src/compare-rebuild.ts <first> <second>` compares two output directories of the same release, such as the release workflow's and the targets-key holder's rebuild. It exits 0 when the two hold the same file names and every file matches, printing each difference that an entry of `rebuild-exceptions.json` accepts with that entry's id. It exits 1 on any other difference, printing each one, and signing refuses such a rebuild. It exits 2 on a usage error, an unreadable directory or an exceptions file that does not validate.

- A runtime archive matches when both copies are in the deterministic form (re-encoding the entries reproduces the archive's bytes), hold the same paths with the same modes and mtime, and every entry has the same bytes or a difference an exception accepts.
- A runtime file list matches when each copy equals the list derived from its own archive, and the SBOM when each copy equals the SBOM derived from the archives beside it.
- Any other file matches when it is byte-identical.

`rebuild-exceptions.json` lists each accepted difference with an id, the comparison it applies (`pe` is the only one) and its reason; unknown fields fail validation. Its first entry, `pe-authenticode`, applies only to the Windows archive: it compares a PE file without its Authenticode certificate table, the security data directory entry and the header checksum, padded with zeros to 8 bytes, because the release workflow signs the Windows closure's PE files and a rebuild outside it cannot. The table must consist of `WIN_CERTIFICATE` entries of revision 2.0 and type PKCS #7 SignedData that fill it to the end of the file, each holding one DER SEQUENCE followed by fewer than 8 zero bytes, with only zero bytes padding entries to 8 bytes; any other appended or hidden bytes are a difference.

## SBOM

`delorun-<version>.spdx.json` is an SPDX 2.3 JSON document derived only from the runtime archives and `toolchain.json`: one package per archive with its SHA-256, the pinned Node and pnpm, and one package per installed npm package version found as `node_modules/<name>/package.json` in an archive, with its `pkg:npm` purl, its declared licence when that is a licence expression, and the SHA-512 the closure's lockfile records for it. Each package's SPDX id is its kind and the first 128 bits of the SHA-256 of its kind, name and version, so names that differ only in characters an SPDX id cannot hold stay distinct, and an id that two packages would share fails the build. `created` is the archives' `SOURCE_DATE_EPOCH`, so the same archives always give the same document. When the output holds `delorun-<version>.images.json`, the document also describes the S2 and S3 images by index digest, each descended from the digest-pinned base, with the S3 image containing the Linux closures; it does not list the Debian packages inside the base.

## Dependency advisory check

`node_modules/.bin/tsx delo/apps/release/src/check-advisories.ts --version <version> --release <dir> [--commit <rev>] [--feed <url>]` reads every runtime archive in `--release` and sends every package version it holds to npm's bulk advisory API: each registry version `app/pnpm-lock.yaml` locks, each installed package version the SBOM lists, which includes dependencies bundled inside another package that the lockfile does not list, and the pnpm version `toolchain.json` pins at `--commit`. Local `file:` and `link:` packages are the release's own source and are left out. The API is `https://registry.npmjs.org/-/npm/v1/security/advisories/bulk`, and writes `delorun-<version>.advisories.json`. An advisory affects a checked version when the version satisfies the advisory's vulnerable range; a range the check cannot read is a malformed answer, which fails the check rather than matching nothing. The check passes only when each affecting advisory has an entry in [`delo/release/advisory-acceptances.yaml`](../../release/advisory-acceptances.yaml), as committed at `--commit` (`HEAD` when omitted; the release's tag in the release workflow and its commit when signing), with the same advisory and package, a range the locked version satisfies, a `lapsesAfter` at or above the release, and an `approver` whom `.github/CODEOWNERS` at the same commit names as an owner of that file. Each entry also records `added`, the date it was added (`YYYY-MM-DD`), which the release notes show. It fails on any other affecting advisory, on a lapsed acceptance or one whose approver is not an owner, on an entry without `added`, on an acceptances file with an unknown field or a duplicate key, and when the feed cannot be reached or answers malformed; it exits 1 then.

The report holds `schema` (`delo.release-advisories/1`), `version`, `feed`, `packages` (how many locked versions were checked), `findings` (each affecting advisory with its package, version, severity, title and vulnerable range, and the covering acceptance, or why its acceptance lapsed in `lapsed` or was refused in `unapproved`), `result` (`pass` or `fail`) and `problems`. Signing runs the check again and refuses unless the published report is, as JSON, the report its own run gives. `assemble.ts --advisories <report> --manifest <signed manifest>` adds the section "Accepted advisories" to the release notes, listing each accepted advisory with its package, range, reason, approver, date and lapse release; it refuses a report other than the file the signed manifest names by length and SHA-256, one whose accepted ids differ from the manifest's, a report of another release and one that failed.

## Signing

Signing happens on the targets-key holder's machine, outside CI, after the release workflow has built the release from the tag `v<version>` and the holder has rebuilt it:

1. Download the release workflow's files of the draft release, including its `manifest-draft.json`, into a directory, such as `release/`.
2. Check out the tag in the repository and build it with the same recipe, attesting the output: `node_modules/.bin/tsx delo/apps/release/src/build-closure.ts --version <version> --commit v<version> --out rebuild/ --attestation-key ~/.config/delo/rebuild-attestation.key --attestation rebuild.attestation.json`, then the images over the same output: `node_modules/.bin/tsx delo/apps/release/src/build-images.ts --version <version> --out rebuild/ --oci rebuild-oci/ --attestation-key ~/.config/delo/rebuild-attestation.key --attestation rebuild.attestation.json`, which first checks that the attestation verifies with the key and covers exactly the files in `rebuild/`, and then extends it, with its commit, to the images file and the rewritten SBOM; it gives no attestation to a directory this machine's build did not write.
3. Record the rebuild: `node_modules/.bin/tsx delo/apps/release/src/record-rebuild.ts --version <version> --release release/ --rebuild rebuild/ --record delorun-<version>.rebuild.json --builder <name> --compared-with <workflow run URL>`. It compares every rebuilt file with the workflow's file of the same name under `rebuild-exceptions.json` as committed at the tag, writes the record to `--record` outside `release/`, and exits 1 when the comparison finds a difference. It refuses to run with `CI` or `GITHUB_ACTIONS` set, and refuses a rebuild that lacks any platform's archive or file list or the SBOM.
4. Sign: `node_modules/.bin/tsx delo/apps/release/src/sign-release.ts --release release/ --rebuild rebuild/ --record delorun-<version>.rebuild.json --attestation rebuild.attestation.json --attestation-key ~/.config/delo/rebuild-attestation.key --key <targets.pem>`.

`sign-release.ts` refuses with a message naming the required source, "a rebuild made by the targets-key holder on their own machine, outside CI, with the published recipe", when the rebuild record is missing or does not read; when `release/` already holds `delorun-<version>.rebuild.json`, or `--record` or `--rebuild` lies in `release/`; when the record says `ci: true` or reports a difference; when `CI` or `GITHUB_ACTIONS` is set; when `--rebuild` is not a directory on this machine, its files do not reproduce the record's digests, or it lacks any platform's runtime archive or file list or the SBOM; when the record's commit is not the commit the tag names, or its recipe digest or toolchain (Node.js, pnpm, compiler and linker) is not the recipe's at that commit; when the attestation is missing, lies in `release/` or `rebuild/`, or does not verify with the attestation key over the version, the commit and every file in `rebuild/`; or when comparing the workflow's files with the rebuild again finds a difference. It also runs the dependency advisory check again against npm's feed, with the acceptances committed at the release's commit, and refuses when it fails or accepts other advisories than the draft's `advisories.accepted`. It also refuses a draft whose SBOM is not `delorun-<version>.spdx.json`, whose runtime entries are not `delorun-<version>-<platform>.tar.gz` (`.zip` for `win32-x64`) and `delorun-<version>-<platform>.files.json` for their own platform, or whose files are not in the release directory with the lengths and digests it lists. When every check passes, it writes each signed runtime file list, the record as `delorun-<version>.rebuild.json` and `delorun-<version>.manifest.json`, whose `rebuild` names the record and the holder with `ci: false`, under temporary names in `release/`, then renames them into place with the manifest last; a failure before the renames leaves `release/` unchanged.

### The targets key

The targets key is an Ed25519 private key in a PKCS #8 PEM file that only its owner can read; `sign-release.ts` refuses a key file with any group or other permission. The repository holds no key. The owner creates the key in the signing ceremony on the offline machine that signs releases, for example with OpenSSL 3:

```sh
umask 077
openssl genpkey -algorithm ed25519 -out targets.pem
openssl pkey -in targets.pem -pubout -out targets.pub.pem
```

The public key goes into the root metadata's `keys` and `roles.targets`, signed by the root key ([C2](../../docs/contracts/c02-release-manifest.md#root-metadata)); the private key never enters CI, a cloud service or a machine the release workflow can reach.

### The rebuild attestation key

The attestation key is a secret of at least 32 bytes at `~/.config/delo/rebuild-attestation.key` on the holder's signing machine, readable by its owner only; it never leaves that machine. The holder creates it once:

```sh
mkdir -p ~/.config/delo && umask 077
openssl rand -out ~/.config/delo/rebuild-attestation.key 32
```

`build-closure.ts --attestation-key` writes an HMAC-SHA256 over the release version, the commit and the length and SHA-256 of every file in `--out`, and `sign-release.ts` checks it. It catches the mistake of pointing `--rebuild` at a directory this machine's build did not write, such as a downloaded copy of the release workflow's output. It cannot stop a holder who sets out to cheat, who holds the key and can attest any directory; C2 already states that a rebuild's independence cannot be proven.

### Root and timestamp metadata

`node_modules/.bin/tsx delo/apps/release/src/sign-root.ts --draft <file> --key <root.pem>... [--previous <root file>] --out <root/<n>.root.json>` signs root metadata in the owner's ceremony: the draft is the root's `signed` content, and the file is written only when it verifies with its own root threshold, has not expired and, for a rotation, verifies as the version after `--previous` with that root's threshold too.

`node_modules/.bin/tsx delo/apps/release/src/sign-timestamp.ts --state <state.json> --root <file>... [--first] --stable <manifest> --beta <manifest> [--replaced <manifest>]... --out <timestamp.json>` signs the next timestamp with the online key from the `DELO_TIMESTAMP_KEY` environment variable, continuing from the last timestamp the state holds, and writes the new state before the timestamp. `--root` starts at the root the state trusts and repeats after a rotation, newest last. The state's last timestamp must match the digest and version the state records and verify with the timestamp key of the root it names and with that root file's digest; it may have expired. No caller passes a previous timestamp. `--first` signs without one, only while the state records none. Each channel's manifest must verify with the newest root's targets keys; the stable channel names a stable release and the beta channel a beta or stable release; and no channel moves to a lower version. A channel moves to another manifest of the release it names only when that named manifest, passed with `--replaced`, differs from the new one in signatures alone, or also in `published` once the named one no longer verifies with the newest root's targets keys, as after a targets-key rotation; any other change to the signed content is refused. The new version is one above `--previous` and expires 3 days after issue.

The state file (`delo.release-timestamp-state/1`) holds the root the signer trusts and the last timestamp signed, with its version, SHA-256 and bytes, so a genuine older timestamp served by the untrusted metadata host cannot roll a channel back. The owner writes it once in the root ceremony with `node_modules/.bin/tsx delo/apps/release/src/sign-timestamp.ts --init-state --root root/1.root.json --state state.json`, and stores its content as the variable `DELO_TIMESTAMP_STATE` of the release workflow's protected `release` environment, never on the metadata host. Each signing job restores the variable to a file, signs, and writes the new state back to the variable with a token that may write that environment's variables and is available only to jobs in it. The owner's release workflow file, which is not written yet, must:

- put every job that signs a timestamp in one `concurrency` group, so two signings never start from the same state;
- write the new state back to `DELO_TIMESTAMP_STATE` before it publishes the timestamp, so a published timestamp is always the one the state holds.

## Verification

`@delo/release-formats/sign/verify` applies C2's client verification: `trustRootChain` walks root versions from the root the caller holds, each signed by the previous root threshold and its own, issued before it expires, living at most 365 days, and with the newest not past its expiry; a root that gives one key two roles or does not have exactly one `active` targets key fails to read; `verifyTimestamp` checks the timestamp role's signature, the 3-day lifetime, an issue time not after the local clock, expiry with no clock tolerance (its refusal names the expiry and the local clock), the stored version, and the root version and file digest it names; `verifyChannelManifest` accepts only the manifest file the fresh timestamp names for the channel, at the release and on the channel the timestamp names (the beta channel also names stable releases), signed by a targets key valid for the release (an `active` key, or a `retired` key whose `lastRelease` is at or above it; never a `revoked` one); `verifyFileList` and `checkFileRef` check each file's length and SHA-256 against the manifest. Every signed file is read with its size limit before parsing, and a duplicate JSON key, an unknown field or an unknown `schema` fails the read. `@delo/release-formats/sign/json` holds the RFC 8785 serialization that signatures cover.

## Images

`node_modules/.bin/tsx delo/apps/release/src/build-images.ts --version <version> --out <dir> --oci <dir> [--attestation-key <file> --attestation <file>]` runs after `build-closure.ts` on the same output. It builds the images `images.json` names, each for `linux/amd64` and `linux/arm64` from the Debian base it pins by digest, with BuildKit's `rewrite-timestamp` at the closures' `SOURCE_DATE_EPOCH`, no cache and no provenance or SBOM attestation, whose build times and invocation ids would differ between builds. The Dockerfiles pin their frontend by digest.

- The S2 workspace image (`images/s2/`) adds the empty helper socket directory `/run/delo-helper`. The S2 helper and the egress proxy are not in it yet.
- The S3 harness image (`images/s3/`) adds the users `delo` (uid 1000) and `delo-harness` (uid 1001) and each architecture's Linux runtime closure, read-only, at `/opt/delo/runtime`, and runs as `delo-harness`.

The command writes the OCI layout of each image to `--oci` and `delorun-<version>.images.json` to `--out`: each image's repository with its index and per-platform manifest digests, the Docker Engine and BuildKit versions that built them, and each image's installed Debian packages per platform, read from the dpkg status of the topmost layer that carries one. The rebuild comparison compares the file byte for byte, so a rebuild by another Docker or BuildKit version, or with other packages, differs; the command also refuses to build with versions other than `toolchain.json`'s `images` pins. When `--out` holds every platform's closure, it rewrites the SBOM to describe both images, the base and their Debian packages as `pkg:deb/debian` purls. The release workflow pushes the layouts by digest, and the manifest's `images` copies the file's image references. The images file is one of the files every rebuild and signing comparison must cover, signing refuses a draft whose `images` differ from it, and signing derives the SBOM's image entries with the base that `images.json` names at the release's commit.

Each image's entry in `images.json` also names its seccomp profile and the profile's licence, committed files in this directory: `images/seccomp.json` for both images, Docker Engine 29.9.2's default profile (`github.com/moby/profiles/seccomp` v0.2.4, `default.json`), under the Apache-2.0 licence in `images/seccomp.LICENSE`. The command copies them to `delorun-<version>.<image>.seccomp.json` and `delorun-<version>.<image>.seccomp.LICENSE` in `--out`, so the release publishes the licence beside each profile, and the image's reference in the images file carries the profile as the `seccomp` file reference that contract C9's supervisor runs the image's containers under. Each listed profile and its licence are files every rebuild and signing comparison must cover, and the rebuild record the manifest signs lists their digests; and signing refuses a profile whose length or SHA-256 differs from the draft's reference.

## Release log

`sign-release.ts` also writes `delorun-<version>.manifest.entry.json`, contract C18's Rekor v2 `hashedRekordRequestV002`: the manifest file's SHA-512, the targets key's Ed25519ph signature over the manifest file's bytes with key details `PKIX_ED25519_PH`, and the targets public key in DER. Node's crypto has no Ed25519ph, so `src/log/entry.ts` signs and verifies it with `@noble/curves`. `node_modules/.bin/tsx delo/apps/release/src/log-release.ts --root <file> --manifest <file> --entry <file> --submit <url> --checkpoint <url> --tiles <url> --out <bundle>` runs in the release workflow: it submits the request to `--submit`, the log's `/api/v2/log/entries`, polls `--checkpoint` every 30 seconds, at most 60 times, for a signed-note checkpoint that a witness the root lists has cosigned and that covers the entry, computes the entry's inclusion proof in that checkpoint's tree from the tiles the log serves below `--tiles` (C2SP `tlog-tiles`, as Rekor v2 serves its tree, reading a partial tile from its full tile once the log no longer serves it), and writes `delorun-<version>.manifest.log.json` only when the bundle verifies; otherwise it exits 1 and the release is not published.

`@delo/release-formats/log/bundle` verifies a bundle offline in C18's five steps: the manifest digest, the entry's Rekor v2 format and its targets Ed25519ph signature, which refuses a pure Ed25519 entry, the RFC 6962 inclusion proof, the checkpoint's origin, size, root hash and log signature, and cosignatures from at least the root's threshold of listed witnesses. A checkpoint without such a cosignature fails, whatever its log signature says, and each failure carries C18's reason code. `log/note` reads C2SP signed notes with Ed25519 note keys and `cosignature/v1` witness keys, `log/merkle` verifies inclusion and consistency proofs, and `log/tiles` computes an inclusion proof from a log's tiles.
