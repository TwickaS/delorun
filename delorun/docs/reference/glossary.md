# Delorun glossary

English | [中文](glossary.zh.md)

The words every Delorun document, skill, interface string and pull request uses, one canonical term per concept. It extends upstream's [glossary](../../../docs/glossary.md), which owns the harness's own terms (agent, session, turn, step, tool, preset, plugin, bundle, profile); this page owns what Delorun adds.

Each entry starts with one plain-English sentence, then adds a technical note where it helps and, where they differ, the name the code uses. Interface text uses the term; code and maintainer docs may add the code name in backticks. A new concept gets its entry in the same pull request that introduces it.

Some entries define terms for capabilities that Delorun does not include, such as the Delorun relay and the catalogue; the [roadmap](../guide/roadmap.md) lists them.

## The product

The words the [user guide](../guide/README.md) uses most come first, in plain English. Home, studio, workspace, chat, reach, trusted device, safe mode and trash are defined further down, in the sections named at the end of this list.

- **plugin** — a piece of software that adds one feature to Delorun, such as a sidebar, a tool the assistant can use or a connection to a model company. Delorun is made of plugins, and you can turn each one on or off. Technical note: upstream's plugin is a Cordis plugin; `delorun plugin` installs one from the registry. <a id="plugin"></a>
- **provider** — the company or service whose AI model answers your chats, such as DeepSeek or OpenAI. The studio's welcome screen takes your DeepSeek key; Settings → Agent → Models and `delorun setup key` choose another provider. Technical note: setup offers eleven providers ([C11](../contracts/c11-setup-answers.md#model-providers)). <a id="provider"></a>
- **API key** — the secret code a model company gives you so that Delorun can use your account with it; the guide also calls it the model key. The studio and `delorun setup key` check a key you type with one request for the provider's model list, never a chat, and store it in `.credentials.yaml` in your home, which only you can read. A key Delorun reads from an environment variable is not stored. Technical note: [Model providers](../guide/providers.md) lists the variable each provider reads. <a id="api-key"></a>
- **preset** — a saved choice of how the assistant works. Delorun uses the word twice: an **agent preset** picks the assistant's tools and instructions (Standard is the default one; Settings → Modes lists them), and a **permission preset** picks what the assistant's commands may do: **Read Only**, **Workspace Write**, **Full access** or **Auto review**. Technical note: upstream's agent preset registry holds the first kind; the sandbox mode and the approval policy make up the second. <a id="preset"></a>
- **permission preset** — one of four choices of what the assistant's commands may do in a chat: **Read Only**, **Workspace Write**, **Full access** or **Auto review**. Technical note: the sandbox mode together with the approval policy; Delorun's setting for new workspaces is Workspace Write ([Safety](../guide/safety.md#full-access)). <a id="permission-preset"></a>
- **sandbox** — a fence around the commands the assistant runs, so they can change files only where you allow and cannot reach Delorun's own secrets. Technical note: the operating system enforces it (bwrap, Landlock, Seatbelt or Windows access lists), and what it enforces differs by system, as [Safety](../guide/safety.md#the-sandbox) lists. <a id="sandbox"></a>
- **Workspace Write** — the permission preset every new workspace starts on: the assistant's commands run inside the sandbox and can write only inside that workspace and the permitted temporary folders. Technical note: the sandbox mode `workspace-write`, with the approval policy `ask`. <a id="workspace-write"></a>
- **full access** — the permission preset that lets the assistant's commands run outside the sandbox, with everything your user account can do, Delorun's home and secrets included. With setup's Ask me first, Delorun asks you once per workspace at your own computer before it applies. Technical note: the sandbox mode `danger-full-access`; the consent is the one `@delorun/plugin-permission-defaults` records per workspace. <a id="full-access"></a>
- **approval card** — the box in a chat that asks whether the assistant may do something, with the choices Reject, Allow once and, for a request that needs more access than the chat has, Allow for this chat. **Allow for this chat** switches that chat to the permission preset the request asked for, and later commands in that chat run in it without asking until you lower it. Technical note: upstream's approval card, with Delorun's choice added through the `conversation.approval.choice` slot. <a id="approval-card"></a>
- **consent** — a yes you give, at your own computer, before Delorun does something risky, such as switching a workspace to full access, starting an added MCP server or letting an external agent run. A phone signed in over remote access cannot give one. Technical note: each consent is one parity switch with a plugin ([parity checklist](parity.md)). <a id="consent"></a>
- **external agent** — another coding assistant, such as Claude Code or Codex, that Delorun's assistant can hand a task to. It runs as its own program outside the sandbox and on your own account, so Delorun asks before each run. Technical note: a delegation provider without a local child session; the consent is `@delorun/plugin-delegation-consent`. <a id="external-agent"></a>
- **MCP server** — a program that gives the assistant extra tools, which Delorun starts on your computer. One that runs a command runs it with your access, outside the sandbox, so Delorun holds a new one stopped until you allow it. Technical note: MCP is the Model Context Protocol; `delorun mcp accept` allows a server. <a id="mcp-server"></a>
- **unlock** — a phone holds no unlock window: each sensitive action asks for [Face ID](#face-id) or your PIN when you take it, and a code from your computer unlocks nothing on a phone. Technical note: the reach elevation, which a phone can no longer use ([contract C14](../contracts/c14-oidc-passkeys.md#face-id-unlock)). <a id="unlock"></a>
- **Face ID** — how an approved phone confirms one sensitive action with its own lock, a passkey that stays on the phone, instead of a code from your computer. Face ID, Touch ID, Windows Hello, a fingerprint and a screen lock all count. One confirmation covers one action, once, within 30 seconds, and the PIN confirms the same way when Face ID fails. See [Confirm with Face ID](../guide/reach.md#confirm-with-face-id). Technical note: [contract C14](../contracts/c14-oidc-passkeys.md#face-id-unlock). <a id="face-id"></a>
- **device** — a browser or the desktop app that you approved to open your studio. See **trusted device** under [Signing in](#signing-in). <a id="device"></a>
- **release** — one numbered version of Delorun, signed so the launcher can check it before installing it. An **update** installs a newer release beside the running one and switches to it when the new one passes its health check. A **rollback** goes back to the release before, with the profile as it was before the update. Technical note: `delorun update` and `delorun recover rollback`; Delorun keeps two releases installed. <a id="release"></a>
- **release channel** — the line of releases an installation follows, `stable` or `beta`. An installation checks for updates only on its own channel, and no setting moves it to another. Technical note: the channel is part of the signed release manifest ([Updates](../guide/updates.md#channels)). <a id="release-channel"></a>
- **launcher** — the small program that `npx delorun` runs. It checks a release's signatures, installs the release and starts it; once a release is installed it starts without the network. Setup installs the `delorun` command at the version you ran. Technical note: the npm package `delorun`, `@delorun/npm-launcher`. <a id="launcher"></a>
- **cost meter** — an optional estimate under the message box of what a chat has cost, with the chats it started added up. It is off until you turn it on under Components on the Delorun studio page of the sidebar's Plugins, and it makes no request of its own. Technical note: `@delorun/plugin-cost-meter`; prices are a bundled table you can override. <a id="cost-meter"></a>
- **prompts answer** — the choice between **Ask me first**, the default, and **Ask less (like DeepSeek Harness)**. Ask me first turns on Delorun's consents for full access, instruction files, added MCP servers and scheduled tasks; Ask less (like DeepSeek Harness) leaves them off, as in DeepSeek Harness. It is on **Ask me first** unless you change it with `delorun setup prompts`. <a id="prompts-answer"></a>
- **Ask me first** — the default answer to setup's prompts question: Delorun asks you first before it switches a workspace to full access, writes an instruction file such as `AGENTS.md`, starts an added MCP server that runs a command, or creates a scheduled task. <a id="ask-me-first"></a>
- **Ask less (like DeepSeek Harness)** — the other answer: those four questions are off, as in DeepSeek Harness. The `web_fetch` guard and the check before an external agent runs stay on with either answer. `delorun setup prompts` switches between the two ([Ask less (like DeepSeek Harness)](../guide/switching.md#ask-less-like-deepseek-harness)). <a id="ask-less"></a>
- **setup** — the few questions Delorun asks in the terminal the first time you run `delorun`: whether to use it from your phone, whether to copy your DeepSeek Harness chats, and the studio's port when 3080 is busy. It applies the answers, starts Delorun and opens the studio, where the welcome screen asks for your model key. `delorun setup <section>` asks one question again, `delorun setup --list` lists them and `delorun setup --yes` accepts every default without asking. Technical note: `delorun setup --config <file>` reads the answers from a file ([setup answers contract](../contracts/c11-setup-answers.md)). <a id="setup"></a>
- **first-run guide** — the dialog the studio shows the first time you open it, which ends in a chat. The first time it has three steps, Welcome, Models and Ready; Settings → General → Getting started opens the full guide, which adds Look, Agents, Recommended plugins, Browser, Phone access, PIN and Workspace, and a step that setup already covered can be left out. **Finish later** closes it and keeps your place. Technical note: `@delorun/plugin-onboarding`. <a id="first-run-guide"></a>

Defined in other sections: home, studio, workspace and chat under [Where things run](#where-things-run), the home process and the network setting there too, reach and tailnet under [Reaching a studio](#reaching-a-studio), trusted device under [Signing in](#signing-in), safe mode under [Changing the harness](#changing-the-harness), and prompt injection and trash under [Keeping work safe](#keeping-work-safe).

- **Delorun** — the open-source project, app, with the `delorun` command: built on DeepSeek Harness. <a id="delorun"></a>
- **Delo Run** — the hosted service at delorun.com: the website with its release-news sign-up, and, with the Delorun relay ([roadmap](../guide/roadmap.md)), its accounts (email code, GitHub, optional passkey), sign-in and device approvals through Delorun. Public text names the contact support@delorun.com only. <a id="delorun-run"></a>
- **stock DSH** — DeepSeek Harness as upstream releases it. **stock look** — Delorun with its studio additions turned off. <a id="stock"></a>
- **studio** — the harness's web interface, the same in a browser and in the desktop app. Code: upstream's Web client. <a id="studio"></a>
- **studio additions** — Delorun's theme, sidebar, chat states, settings layout and onboarding; they are on by default, and one Settings switch turns them off. Code: `@delorun/bundle-studio`. <a id="studio-additions"></a>
- **main chat** — one chat outside every workspace, from which the person asks about and steers their other chats and starts work in a workspace; it asks the person before every change that outlasts a turn. Code: `@delorun/plugin-main-chat`. <a id="main-chat"></a>
- **augmentation** — an opt-in addition beyond the stock workflow, such as reach, Docker isolation or extra machines. <a id="augmentation"></a>
- **the person** — the one owner of a home. Maintainer docs say "the person"; interface text says "you". Not "user", which upstream uses for the model conversation's user role. <a id="the-person"></a>

## Where things run

- **home** — the one place that holds a person's studio, harness configuration, machine list and chat history: their own computer or server. Code: the Delorun home directory `~/.delorun`. <a id="home"></a>
- **machine** — a computer where chats run; the home computer is the first one. Extra machines run a headless Delorun agent configured by home. <a id="machine"></a>
- **workspace** — a project; it can have a copy on several machines. <a id="workspace"></a>
- **chat** — a conversation bound to one machine, whose agent loop runs there. Code: upstream's session. <a id="chat"></a>
- **target** — a device that does not run Delorun, reached by the agent through tools, such as a phone over adb. <a id="target"></a>
- **runtime** — where a machine runs commands. **native** — with the person's own access and upstream's OS sandbox where available, which confines file writes; Delorun's contract requires its profiles also to keep confined commands from reading Delorun's secrets or tokens, or connecting to its control sockets and the Docker socket, where the dialect can enforce it; other Unix sockets and the network stay reachable. **Docker** — in containers, in one of the Docker shapes: **S2** harness on the machine and each Docker workspace in its own container; **S3** one container for everything, which isolates the computer, not workspaces from each other, and offers no reach; **S1** harness and each workspace containerised, which requires a hosted home. <a id="runtime"></a>
- **Docker supervisor** — the only Delorun component that calls Docker, through a fixed-schema API on a socket under `~/.delorun` that accepts only callers holding the token each home-process start writes there, so confined commands cannot reach it where the dialect enforces the native rule; where it cannot, `delorun verify` reports it and setup labels Docker mode. Delorun's contract requires it to run workspace images pinned by digest and to report which limits Docker enforces on that machine. Code: `@delorun/supervisor`. <a id="supervisor"></a>
- **home process** — the background program that runs your studio. `delorun` starts it and opens the studio, `delorun status` shows whether it is running and `delorun stop` stops it. Technical note: it is the background process that holds the CLI profile's lock under `~/.delorun` and runs its Host; `delorun start` and `delorun stop` start and stop it, and updates reach it through the update handshake, which never switches the runtime under a running chat. **update channel** — the socket under `~/.delorun` that `delorun update` and the studio's "Update now" use, guarded like the Docker supervisor's by the per-start token and the native rule. The lock is per profile: the desktop Host neither takes it nor joins its drain, and each surface updates on its own. <a id="home-process"></a>
- **runtime closure** — one signed release of everything the `delorun` command runs, installed under `~/.delorun/runtimes/<version>`. **runtime store** — those installations, with a pointer to the active one and the previous one kept for rollback. The desktop app carries its own copy in its signed resources. <a id="runtime-closure"></a>
- **start token** — the 32-byte random token that each home-process start writes to `run/<profile>/start-token`; the Docker supervisor and the update channel accept a request only with it, and only while that start runs. <a id="start-token"></a>
- **capability report** — the statement of what a machine runs and enforces, with each limit `enforced`, `not-enforced` or `unknown` and its evidence; setup shows it before the person chooses a Docker shape. Code: the runtime provider's `report()`. <a id="capability-report"></a>
- **read exemption** — a directory that confined commands may read and execute: `runtimes/`, `skills/` and `dsh-runtimes/`, and the running profile's approved plugin copies under `changes/profiles/<profile>/active/`, which commands cannot write. No secret is written under one. <a id="read-exemption"></a>
- **launch protocol** — the number in a runtime's signed manifest that fixes its entry file, the arguments the launcher passes and the environment variables it sets; the launcher runs a runtime only when it supports that number. <a id="launch-protocol"></a>
- **network setting** — also called the **workspace network**: a workspace's choice of which hosts the commands the model runs, and `web_fetch`, may reach. **Open** is the default, as in DeepSeek Harness; **Allowlist** reaches only the hosts you list; **Off** reaches none. It changes only in Settings → Safety → Network at the computer that runs Delorun ([Prompt injection](../guide/prompt-injection.md#the-network-setting)). Technical note: for the commands the model runs in its sandbox, and for `web_fetch`: `open`, the host's network as stock gives it, the default; `allowlist`, only the listed hosts, through an egress proxy; or `off`, none. It changes only in the studio at the home's computer. Code: `delorunCommandNetwork` in `@delorun/plugin-permission-defaults`. <a id="workspace-network"></a><a id="network-setting"></a>
- **egress proxy** — an HTTP proxy that is a workspace's only route out and refuses non-public addresses. A native workspace whose network is `allowlist` reaches one per list, which the Host runs on a socket under `~/.delorun` and the sandbox binds into each command, and which checks a name against the list before resolving it; each Docker workspace runs its own on its own network. <a id="egress-proxy"></a>
- **egress allowlist** — the default egress mode of a Docker workspace: the model providers in its profile, the package registries and Git hosts on the default list, and the workspace's own additions. <a id="egress-allowlist"></a>
- **container denial marker** — the line that a file denial by a Docker workspace's read-only root carries, stating that the environment denies the access and that no sandbox mode allows it, so it offers no escalation. <a id="container-denial-marker"></a>
- **S2 helper channel** — the SSH helper inside each S2 workspace container, which carries the workspace's file, process, terminal, LSP and PTC calls. <a id="s2-helper-channel"></a>
- **supervisor roots** — the file listing at most 16 parent directories under which the Docker supervisor creates workspace roots; only `delorun setup` writes it. <a id="supervisor-roots"></a>

## Reaching a studio

- **reach** — opening a studio from another device or network. **reach option** — one way to do it: Tailscale private, Tailscale Funnel, a self-hosted relay or the Delorun relay. <a id="reach"></a>
- **tailnet** — your own private network of devices that Tailscale sets up for you: only devices signed in to your Tailscale account can reach each other on it. Delorun's reach option opens your studio to your tailnet only. Technical note: `tailscale serve` publishes the studio on the computer's `ts.net` name for tailnet devices ([Reach](../guide/reach.md)). <a id="tailnet"></a>
- **Tailscale reach** — reach through the person's tailnet: `tailscale serve` for tailnet devices only, Funnel for the public internet. Delorun's contract requires it to use no Delorun infrastructure; Tailscale's coordination service and certificates are trusted instead, and Tailscale can add a device to the tailnet unless Tailnet Lock is on. <a id="tailscale-reach"></a>
- **Delorun relay** — Delo Run's relay, on `delo.run` names. **relay control** — its Cloudflare Workers part (names, key bindings, tunnel authorisation, limits, abuse). **relay data plane** — its stateless passthrough servers that forward encrypted bytes they cannot read. <a id="delorun-relay"></a>
- **self-hosted relay** — the same relay data plane run by a person on their own server and domain, end-to-end while the domain's CAA record binds issuance to the home's ACME account (`accounturi`) and the home answers no certificate challenge through the relay. Its operator is its owner, so the Delorun relay's per-account limits do not apply to it. <a id="self-hosted-relay"></a>
- **studio address** — the address that reaches a home's studio, such as `k7x2p9.delo.run`, a person's own domain or a `ts.net` name. <a id="studio-address"></a>
- **reach listener** — the Host listener that serves one reach option: bound to `127.0.0.1` or a Unix socket with no host override, it authenticates every request and upgrade before any route, and before sign-in serves only its pre-login allowlist. The loopback listener is upstream's own. Code: the listener ids in `@delorun/contract-admission`. <a id="reach-listener"></a>
- **host id** — the studio's identifier of one connection to a home's Host process. The browser generates it and never sends it to a home. Code: `hostId` in `@delorun/contract-host-qualified-keys`. <a id="host-id"></a>
- **host-qualified key** — a persisted browser key or client state key that carries the host id and, for a session or workspace, the upstream id unchanged. Code: the key forms in `@delorun/contract-host-qualified-keys`. <a id="host-qualified-key"></a>
- **end-to-end encrypted reach** — reach where TLS ends on the person's home, so the relay or provider cannot read studio traffic. Interface text says exactly what each option can still see. "Zero-trust" is never used for the Delorun relay; it may describe only options with no Delorun involvement (Tailscale, a self-hosted relay), and the exact statement of what the provider can see is preferred. <a id="end-to-end"></a>
- **tunnel token** — the short-lived token on the relay protocol that authorises one tunnel attempt for one name and one home key. <a id="tunnel-token"></a>
- **certificate alert** — the blocking warning a running home raises, on its own screen, in the desktop app and on its other trusted devices, when a public certificate log shows a certificate covering its name, wildcards included, that it did not request. <a id="certificate-alert"></a>

## Signing in

- **owner code** — the one-time code a home prints in its terminal so the first device can claim it; it is accepted only on the home's own computer (loopback, SSH port forwarding included), and on the tailnet-private path only where the reach contract trusts Tailscale identity headers. <a id="owner-code"></a>
- **home key** — the home's own signing key, which names the home to its devices and its relay, signs its alerts and is kept across a devices reset. **match code** — the 8 digits that a new device and a trusted device both show during device approval, derived from both devices' view of the keys; the person types the new device's code on the trusted device. <a id="home-key"></a>
- **approval window** — the minutes (5 by default) in which a home accepts a request to pair from any device, opened by **Add a device** or `delorun devices approve` at the home's own computer. **pop-up pairing** — a request from a device signed in to Tailscale as the computer's own user (or, if allowed, any tailnet device) without a window; the studio at the computer shows it, and the person still types the match code. <a id="approval-window"></a>
- **trusted device** — a browser or desktop app a home has approved for one studio address; it holds a device key bound to that address's origin, so a new address approves it again. **device approval** — approving a new device from a trusted one, in a live session, by typing the code the new device shows. <a id="trusted-device"></a>
- **identity factor** — the sign-in that proves who the person is for reach: a passkey, the person's own OpenID Connect provider or, with the Delorun relay, a Delo Run account, enrolled for each studio address when reach is turned on. A local-only home needs none; public reach requires one, and tailnet-private reach may use tailnet identity instead. It never replaces device approval. <a id="identity-factor"></a>
- **recovery kit** — the saved key that restores approval rights when every trusted device is lost; using it needs the identity factor and replaces it with a new kit. The home's own terminal (`delorun devices reset`) is the other way back, and without an identity factor it is the only one. <a id="recovery-kit"></a>
- **owner claim** — the first device's claim on a home that has no owner, made with the owner code and accepted only on the home's loopback listener; reach stays off until the home has an owner. <a id="owner-claim"></a>

## Changing the harness

- **profile** — a saved set of Delorun's settings and plugins that decides how the studio and the assistant are put together. The `delorun` command and the desktop app each keep their own profile, as upstream's do, and share chats and workspaces. Technical note: upstream's profile. **layer** — a bundle, the profile patch, the home patch or an overlay. <a id="profile"></a>
- **local bundle** — the bundle that Delorun's CLI profiles add after upstream's web profile template, holding Delorun's local integration rows; a profile's `--dump-config` names it beside each row it writes. Code: `@delorun/bundle-local`. <a id="local-bundle"></a>
- **profile history** — every saved version of the profile, naming what changed and who changed it. **undo** — restoring the version before the latest. <a id="profile-history"></a>
- **row** — one entry in a profile's configuration. It names one plugin and holds that plugin's settings, and a profile is a list of rows. A row has an id, such as `tool-todo`, which Settings → Plugins shows under the plugin's name; a patch changes a row by that id. Technical note: a Cordis plugin entry; `disabled: true` turns one off. <a id="row"></a>
- **bundle** — a package that adds a ready-made group of rows to a profile, such as a plugin you write together with its settings. The package's own `cordis.patch.yml` inserts its rows when the profile lists it. Technical note: upstream's bundle, declared by `dsh.bundle` in the package's `package.json`; upstream's [glossary](../../../docs/glossary.md) owns the term. <a id="bundle"></a>
- **patch** — the file `cordis.patch.yml` in your profile's folder, where you change or turn off any plugin's row by its id and leave the rest alone. A patch replaces the row's whole `config`, so it restates every key the plugin needs, and an edit made by hand loads at the next start. Technical note: upstream's profile patch; a bundle carries a patch of its own. <a id="patch"></a>
- **overlay** — a patch file applied for one start only, with `delorun start --patch <file>`. It changes nothing saved in the profile, and Delorun refuses one that turns off a protection of its own. <a id="overlay"></a>
- **changes protection** — the setting that decides whether a change to what Delorun runs loads at once or waits for your review. Off, the default, loads each change and records it so you can undo it; on, a change waits until you apply it at your computer. `delorun changes protection on` or `off` sets it in a terminal, and the studio sets it at your computer and, with a fresh unlock or Face ID, on a phone. Technical note: `changes/protection.json`, [contract C21](../contracts/c21-changes.md#the-protection-setting). <a id="changes-protection"></a>
- **change** — one recorded alteration to what Delorun runs: an edited plugin folder, a plugin installed or turned off, or a file of Delorun itself. Each has an id, such as `c3f09a1b2c4`, and `delorun changes list` shows whether it waits, is applied, was discarded or was undone. <a id="change"></a>
- **work session** — the time, two hours unless you give `--for` up to 480 minutes, during which edits to one plugin's folder load live without review even with protection on. `delorun changes work <plugin>` starts it and `delorun changes done <plugin>` ends it by approving the folder's version. <a id="work-session"></a>
- **safe mode** — a start that leaves out every plugin and bundle you added and keeps Delorun's own, so you can find out whether one of yours stops Delorun from working. It changes no file. `delorun recover safe-mode` turns it on for the next start and `delorun recover exit-safe-mode` turns it off. <a id="safe-mode"></a>
- **eject** — copying a plugin's source into the profile as an editable replacement for the original. <a id="eject"></a>
- **source mode** — running Delorun from a git checkout of the person's own fork, updated by merging signed release tags. This mode is not offered; interface text does not use the term. <a id="source-mode"></a>
- **update report** — what a new release would change or break, shown before an update applies. <a id="update-report"></a>
- **update check** — the request a running installation makes for the release channel's newest release, verified as an update verifies it and sending nothing about the person; Settings → General → Updates turns it off. **update notice** — the line in the terminal and the quiet notice in the studio's sidebar that a newer release exists; it applies nothing. <a id="update-check"></a>
- **update journal** — the file `run/<profile>/update.json`, which the home process writes at the start of each update phase from `snapshot` on and which the next start reads to finish an interrupted update. <a id="update-journal"></a>

## Keeping work safe

- **trash** — where deleted chats and workspaces wait, restorable, until purged. <a id="trash"></a>
- **untrusted chat** — an imported chat. Delorun's contract requires it to show a banner that names its source and to keep its history out of model context until the person marks it trusted. <a id="untrusted-chat"></a>
- **export file** — an export of workspaces with their chats and customisation, secrets excluded, that imports without overwriting anything and applies customisation only after showing its diff. Code and maintainer docs: archive (`@delorun/archive`); interface text says "export file", because upstream's interface uses Archive for a session action. <a id="archive"></a>
- **verification status** — the result of Delorun's checks on a home (release, files, isolation, exposure, sign-in, plugins, data sharing) with its mode: `warn` by default, `enforce` or `off`. Code: `@delorun/integrity`, `delorun verify`. <a id="verification"></a>
- **release manifest** — the signed file that describes one Delorun release: its runtime archives, installers, image digests, SBOM, npm packages and install scripts, each with its length and SHA-256 digest. Code: `delorun-<version>.manifest.json`. <a id="release-manifest"></a>
- **root metadata** — the signed file that names every release role's keys and thresholds, the release log's keys, the witness keys and each rotation. <a id="root-metadata"></a>
- **key roles** — the four signing roles of a release: `root` (offline, held by the owner), `targets` (offline, signs each release manifest), `timestamp` (online, attests freshness) and `catalogue` (online, signs the catalogue index and revocation list). <a id="key-roles"></a>
- **release log** — Sigstore's public Rekor log, which holds an entry for each signed release manifest; clients check an entry against a witnessed checkpoint. <a id="release-log"></a>
- **witness** — a key in the root metadata that cosigns a release-log checkpoint; a checkpoint counts as witnessed when at least one listed witness has cosigned it. <a id="witness"></a>
- **advisory acceptance** — a reviewed entry in `delorun/release/advisory-acceptances.yaml` that lets the dependency advisory check pass for one advisory and one locked version range, until its `lapsesAfter` release. <a id="advisory-acceptance"></a>
- **snapshot** — a profile history version made automatically before an update, migration or recovery. <a id="snapshot"></a>
- **fetch guard** — the Delorun plugin that makes `web_fetch` and the HTTP fetch provider refuse loopback, link-local (cloud metadata addresses included) and private-network targets with a typed reason; Delorun's contract requires it to be on by default, off in the parity composition, and switchable. <a id="fetch-guard"></a>
- **prompt injection** — text the assistant reads, such as a web page, a file or an issue, that carries instructions meant to make it do something you did not ask for, like sending your private data to a stranger. The assistant cannot reliably tell such text from your own instructions, so Delorun limits what follows instead: the sandbox, the consents and the network setting. See [Prompt injection and data exfiltration](../guide/prompt-injection.md). <a id="prompt-injection"></a>
- **install check** — the check of a plugin and every package it brings, before its code loads, for integrity, known advisories, very new versions and lookalike names; it warns, and refuses only a known critical advisory the person has not allowed. **install record** — the SHA-256 of every file of an installed plugin, which each start and `delorun verify` compare with the installed files. **trust status** — the result of the last such comparison per plugin: unchanged, changed or unrecorded. Code: `@delorun/plugin-install-check`. <a id="install-check"></a>
- **instruction-layer file** — a skill, a preset or an `AGENTS.md`: text that loads as instructions in every future chat of its scope, so Delorun's contract requires a model-authored write to one to ask first, with its diff. <a id="instruction-layer"></a>
- **operational log** — the file where one of Delorun's processes (the CLI home process, the desktop Host, the Docker supervisor, the self-hosted relay) records how it behaved; Delorun's contract requires that it rotate, never hold a secret, and be shown by `delorun logs`. Not the session log, which records a chat and is permanent. Code and maintainer docs: the operational-log contract. <a id="operational-log"></a>
- **session and turn keys** — upstream's session and turn ids, which an operational-log record carries when it belongs to a session and a turn, so a chat's turn leads to the process failure behind it; session-log events carry no extra id. <a id="log-keys"></a>
- **activity history** — a read-only view of what every chat did, built from the session log, with `delorun history`. Not offered; interface text does not use the term. **system-stats panel** — live CPU, memory and process use per machine, beside the activity history. Not offered. <a id="activity-history"></a>
- **telemetry** — usage data without content that Delorun would send to Delo Run. Delorun sends none of its own; any telemetry Delorun adds is opt-in, with default No and its exact payload shown. Upstream's product analytics and DeepSeek session-log upload are separate; Delorun's contract requires them to stay available and off unless the person opts in. <a id="telemetry"></a>

## Community

- **catalogue** — the public index of plugins Discover lists first. **compatibility badge** — "tested with Delorun X": the plugin passed the compatibility corpus on that release; not an endorsement. **revocation list** — the signed list of plugin versions Delorun disables at their next load with a visible reason. **listed findings** — findings a catalogue entry lists for a plugin, shown as the author's or a reviewer's claims, which Delorun does not verify; Delorun runs no plugin audit. **plugin security review** — an optional agent preset the person runs on a plugin before installing it, which can contribute its findings to a shared database and is not fully reliable. Not offered; interface text does not use the term. <a id="catalogue"></a>
- **documentation website** — `docs.delorun.com`: the user guide and reference in English and Chinese, each page naming the Delorun version it describes and also published as Markdown, with `llms.txt` indexes for a person's coding agent. Code: `delorun/apps/docs`. <a id="documentation-website"></a>

## Building Delorun

- **upstream** — DeepSeek Harness as its maintainers release it. **divergence ledger** — `delorun/upstream-patches.json`: every changed upstream file with its reason and class. **[divergence record](divergence/README.md)** — the page explaining a substantial change to one upstream plugin and how to merge the next upstream release. <a id="upstream"></a>
- **parity baseline** ([`parity-baseline.md`](parity-baseline.md)) — the recorded results of the parity runs at `dsh-v0.2.2-rc.1`, with the environment and failure classification that page states. <a id="parity-baseline"></a>
- **parity checklist** ([`parity.md`](parity.md)) — every stock feature at the recorded upstream tag, with its evidence, and every deliberate difference. **parity composition** — Delorun's runtime with the studio bundle and every model-visible Delorun change switched off. **parity replay** — upstream's recorded scenarios run unchanged against the parity composition. <a id="parity"></a>
- **parity switch** — one registered switch of the parity composition: a model-visible Delorun change, with its default value and its parity value. Code: the registry `PARITY_SWITCHES` in `@delorun/contract-parity-composition`. <a id="parity-switch"></a>
- **switch sweep** — the check that turns each parity switch on, replays its own Delorun scenario, and the static scan that finds model-visible input under `delorun/` with no registered switch. <a id="switch-sweep"></a>
- **extension-point-first rule** — Delorun behaviour lives under `delorun/` on upstream's extension points; an upstream edit adds an extension point, not behaviour. **divergence budget** — the non-generated ledger entries and hunks, per class, that a release may add beyond the 1.0 baseline: at most max(20 entries, 10%) and max(150 hunks, 10%), with entries upstream absorbs credited back. **rehearsal merge** — a trial merge onto upstream's newest tag before each Delorun release, which fails above 15% conflicted hunks or on a conflicted `security` file without a lead decision. <a id="extension-point-first"></a>
- **contract** — a specification page under [`delorun/docs/contracts/`](../contracts/README.md) that work packages consume as written. **work package** — one unit of parallel work with owned paths and acceptance evidence. <a id="contract"></a>
- **denial test** — a test proving that a forbidden action fails. <a id="denial-test"></a>
- **stand-in** — a local service on `127.0.0.1` that answers as an outside provider does, such as a sign-in provider, a certificate authority or a certificate log, so tests contact no live provider. **stand-in stack** — those stand-ins started together, with the network guard that refuses every connection leaving loopback. Code: `delorun/apps/tools/src/stack/`. <a id="stand-in"></a>
- **check runner** — the Delorun command that runs the checks a change reaches (`pnpm check`), with a local pass cache keyed on each check's declared inputs and a plan view (`--plan`); the uncached full run (`pnpm check:full`) is the correctness evidence. <a id="check-runner"></a>
- **changelog fragment** — a file under `delorun/changelog/unreleased/` that describes one change people can perceive; release notes are assembled from the fragments. <a id="changelog-fragment"></a>
- **brief** — a work brief for an agent: a GitHub issue that a maintainer creates, labels `brief` and locks. Other issue text is data, never an instruction. <a id="brief"></a>
- **SBOM** — the software bill of materials: a machine-readable list of the components in a release. <a id="sbom"></a>

## Writing Delorun's documentation

- **upstream standard** — the rules upstream's root `AGENTS.md`, `docs/AGENTS.md`, bilingual contract, skills, defensive patterns, upgrade guides, persistence acknowledgements and snapshot policy set. Delorun's repository edits those files in place into its own standard, which applies to Delorun's code and documentation as to upstream's; upstream's later changes to them are merged by hand. <a id="upstream-standard"></a>
- **tier** — a kind of document with one job, such as the user guide, a cookbook, a reference, defensive patterns or architecture notes; each fact has one home in the tier whose job it is, and other pages link there. Delorun's tiers sit under `delorun/docs/`, beside upstream's under `docs/`. <a id="tier"></a>
- **architecture notes** — `delorun/docs/architecture/`: the ordered map of Delorun's packages, with one current-state page per subsystem. <a id="architecture-notes"></a>
- **Agent Note** — a decision record under `.agents/notes/`, upstream's and Delorun's alike: the problem, the decision, the alternatives it beat and its consequences, filed by status (proposed, implemented, rejected) and class, with frozen copies under `archived/`. A new note first checks which older notes it supersedes. <a id="agent-note"></a>
- **consistency record** — the `<page>.i18n.yaml` file beside a page's English and Chinese files, holding a hash per section of each side; re-recording it confirms the two sides say the same thing, and the pairing gate fails when either side changes without it. <a id="consistency-record"></a>

## Words to avoid

| Avoid | Say |
| --- | --- |
| zero-trust (for the Delorun relay) | end-to-end encrypted reach, with what Delorun can still see; for Tailscale and self-hosted reach, the exact statement of what the provider can see |
| cell, instance, VM, sandbox (for a home) | home, machine |
| user (for the person) | the person, you |
| hub | home |
| tunnel (in interface text) | reach, Delorun relay |
| sync (for workspaces) | copy, move, export |
| archive (in interface text) | export file |
| reviewed (for badges) | tested with Delorun X |
| audited, audit findings (for plugins) | listed findings, the author's or a reviewer's claims |
| end-to-end through any relay (for the desktop app) | the desktop app pins the home's TLS key where the home keeps one across certificate renewals |
