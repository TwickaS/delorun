# Delorun threat model

English | [中文](threat-model.zh.md)

Delorun has no release; this page describes the code in this repository.

## Summary

This page states what Delorun protects, against whom, how, and where it cannot. It extends upstream's [safety statement](../../../SAFETY.md) and [process sandbox reference](../../../docs/subsystems/sandbox.md), which apply to Delorun unchanged, with Delorun's assets, parties, trust boundaries and limits. Each boundary states the defence that is built and links the contract that specifies it; a defence that is not built is named as not built, with the design or contract that holds its rules. Report a suspected vulnerability through [SECURITY.md](../../../SECURITY.md).

## Goal

Delorun's goal is to be never less safe than stock DSH on any path, and safer where it changes a default. Delorun runs upstream's code at a named DSH release and keeps upstream's approval, permission and sandbox decisions, including the rule that an approval request with no answerer is denied ([approval](../../../docs/subsystems/approval.md)). Delorun adds protections around them, and each Delorun change that moves an approval, a refusal or an escalation follows [the rules below](#how-changes-keep-this-true). The [parity composition](../contracts/c16-parity-composition.md) switches every model-visible Delorun change off and replays upstream's recorded scenarios, so stock behaviour stays reachable and checked.

Upstream's safety statement holds for Delorun as written: sandboxing, approvals and permission controls reduce risk and do not guarantee isolation. In a native workspace, commands run with the person's own access.

The CLI profile changes these defaults. The [parity checklist](../reference/parity-with-deepseek-harness/parity.md) lists each one with its evidence.

| Default | Stock DSH | Delorun's CLI profile | Effect on safety |
| --- | --- | --- | --- |
| Confinement of native commands | The sandbox confines file writes; reads, Unix sockets and the network stay open | The sandbox also denies confined commands writes under Delorun's home and reads under it except three exemptions on bwrap, Landlock and Seatbelt, and connections to the update channel's socket and the Docker context's socket on bwrap and Seatbelt ([C1](../contracts/c01-home-layout.md)); on Windows only writes are confined | Safer on Linux and macOS; nothing reports per machine which rules hold |
| Network of sandboxed commands | Commands reach any host | Each workspace's network is `open`, `allowlist` or `off`, `open` unless the person or the profile's configuration chooses otherwise; `allowlist` reaches only the listed hosts through Delorun's egress proxy, `off` reaches nothing, and `web_fetch` follows the same setting. Both hold on bwrap; on Landlock, Seatbelt and Windows a workspace set to either refuses every command | As in stock by default; safer for a workspace set to `allowlist` or `off` |
| Full access | A new workspace starts on `workspace-write`, and full access needs no consent | Stock's `workspace-write` default; a switch of a workspace's preset to full access is refused until the person grants that workspace at the home's computer, in the studio's consent, which names Delorun's home, its keys and tokens and its channels, or with `delorun workspace full-access`; withdrawing it sets the workspace's open full-access chats back to `workspace-write` in every running profile within a second, because each Host watches the permission store (where the watch cannot run, at that Host's next permission decision), without any Host reading another profile's token, and reaches a running `delorun headless` task at its next permission decision; an approval card's "Allow for this chat" choice switches the chat and records nothing once the card cannot be answered; a per-call escalation goes through upstream's approval prompt, which does not name Delorun's home | Safer for preset switches; per-call escalation as in stock; "Ask less" turns the refusal off |
| `web_fetch` targets | Loopback, link-local and private-network hosts are fetched in every mode without confirmation ([web-fetch-http](../../../packages/web/web-fetch-http/README.md)) | The fetch guard refuses those targets, cloud metadata addresses included, before any connection, with a typed reason the model reads | Safer; setup's prompts answer leaves it on |
| Scheduled tasks | One approved call creates turns that recur unattended | Creating or editing a task asks with the recurrence, the target session and its permission preset, and a delivery is refused when the target chat's preset differs from the approved one | Safer under setup's default prompts answer; "Ask less" turns it off |
| Instruction-layer files | A model-authored write to a skill, a preset or an `AGENTS.md` is approved, if at all, as a file write | A write through the file tools asks with the effect, that the text loads as instructions in every future chat of its scope, and the diff; a shell command or PTC code writes without asking. The review matches the target against the roots the skill providers and the profile launcher read by device and inode of its existing directories, so a link or another letter case reaches the same answer, and folds case for the missing part where the volume is case-insensitive; a hard link asks only when it names the instruction file itself, not a file elsewhere linked to it. It is a prompt for file-tool writes, not a boundary against a model with a shell | Safer for the file tools only; "Ask less" turns it off |
| MCP servers | Each server command runs as trusted code outside the agent sandbox | A new stdio server is refused, naming its command, arguments, working directory and the names of its configured environment variables, and the absolute executable and canonical directory they resolve to, which are the paths it is started with; the review shows a value only for a variable that changes what runs (`PATH`, `NODE_OPTIONS`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `PYTHONPATH`, `DYLD_*`). An acceptance belongs to one server name and covers its whole start: a change to any part, a change of the Host's working directory or `PATH` included, such as `PATH`, `NODE_OPTIONS` or `LD_PRELOAD`, is asked again naming the changed variables or paths, another server name never shares it, an acceptance store of another format is refused as a whole (on Windows the lookup uses `PATH` and `PATHEXT` without searching the working directory first, and a `.cmd` shim is reviewed with the canonical `COMSPEC` that runs it, so a changed `COMSPEC` is asked again), and a server row waits for the consent row whatever their order. An acceptance also pins the files the start runs by canonical path and SHA-256 of their contents: the executable, with every symbolic link (such as a `node_modules/.bin` entry) followed to the file itself, and each argument that names an existing regular file, by itself or as the value of an `--option=value` argument such as `--import=./hook.js`, such as the script `node server.js` runs; a rewritten file, a retargeted link, or an argument that names a file now or no longer is asked again with the change `contents`, at every boot and before every reconnect respawns the server, and the allowed server is spawned with the canonical path of the pinned executable, so when a chat rewrites a pinned file or retargets the executable's link and then kills the server, the person is asked again before the changed file runs. What stays unpinned: the files the program loads by itself (a module `server.js` imports, the rest of a package, shared libraries, the interpreter's own modules, a module `python -m` names, a file `NODE_OPTIONS` names), a directory an argument names, the interpreter a `#!` line looks up on `PATH`, code a package runner (`npx`, `pnpm dlx`, `bunx`, `uvx`, `pipx run`) downloads each time it starts, and, between the last check and the spawn, an in-place rewrite of a pinned file or a retargeted link an argument passes through, which the next review catches. The person accepts a held server at the home's computer, in the studio's Settings, Permissions or with `delorun mcp accept`, which show the same start with the executable, directory and command shell it resolves to, and an answer to a review whose start now resolves elsewhere is refused as stale, and declines it or revokes its acceptance there or with `delorun mcp revoke`, which keeps that server stopped until its start changes; a remote device reads only the waiting servers' names and what changed, and every answer from it is refused. A server whose working directory or pinned file sits in a workspace of the profile or a temporary directory still loads unpinned files from there, which run whatever a chat writes there later at the next start or reconnect; the review names those paths before the person answers, and does not refuse them. A chat with full access can write elsewhere, which the review does not detect | Safer; a new stdio server starts after one acceptance; "Ask less" turns the refusal off |
| Guard plugins under `plugin_manager` | In full access the tool runs without a prompt and can disable, reconfigure or remove every plugin except plugin management's own components | Plugin management also protects Delorun's consent and guard plugins, the update gate, the update check, the plugin install check, `dsh-sandbox-local` and `dsh-sandbox-policy`. In every mode the tool refuses a change that, judged on the profile's composed rows before and after it, would drop, replace, reconfigure, disable or duplicate a protected row, give another row its id or add a row of a protected module, through `set_plugin`, `configure`, a bundle's install, selection, deselection or removal, `undo` or `restore`, and refuses packages that provide a protected module. A full-access command can still edit the profile's files directly and a shadowing package nested in another bundle's dependencies is not checked; a version exemption of a guard's package cannot be revoked or restored away | Safer |
| Changes to plugins linked from a folder and to the harness | A plugin linked from a folder loads from the folder, and edits load at the next recomposition without review | Changes protection is off by default: the plugin loads from a copy of the folder's content under the home, each start and each save while Delorun runs loads the folder's new content without review, the person's edits of the harness's own files apply at the next start, and the agent's `plugin_manager` calls run as stock's; each change is logged and can be undone. With `delorun changes protection on`, a change loads only after the person applies it ([C21](../contracts/c21-changes.md#the-protection-setting)) | Same as stock by default for review, with every change recorded; safer with protection on |
| Data sharing | Desktop analytics and DeepSeek session-log upload on | Session-log upload off; Delorun has no telemetry of its own. Desktop analytics belongs to the desktop app, which is upstream's and keeps it on | Safer in the CLI profile |
| Studio additions | Stock look | Delorun's theme, settings layout, chat states, sidebar and onboarding; the main chat is not mounted | No change to approvals or confinement |
| Home directory | `~/.dsh` | `~/.delorun`, at mode 0700 on Linux and macOS; `delorun` never reads or writes `~/.dsh` | Separates the two homes |

The parity registry also declares switches for a container denial marker, `plugin_manager` read actions without escalation, `preset_inspect` and profile history; the CLI profile turns none of them on, so stock behaviour stands for each.

## Where Delorun's protections apply

- **The CLI profile.** The profile `delorun setup` creates and `delorun` or `delorun start` boots: upstream's web template with `@delorun/bundle-local` and `@delorun/bundle-studio`. Every protection this page names as built applies here.
- **`delorun headless`.** It boots the home's `headless` profile: upstream's `headless` template with `@delorun/bundle-headless`, under C1's sandbox overlay. The fetch guard, the instruction write, MCP and schedule consents, the full-access consent, each workspace's network setting, the hold on the agent's plugin changes while Changes protection is on, and the turn gate apply, plugin management cannot turn them off, and DeepSeek's session-log upload is off, as in the CLI profile. A guard that asks a person refuses, because the profile composes no approval answerer. The full-access consent refuses full access for a working directory without a full-access grant recorded at the home's computer; a request for it in the arguments or `DSH_PERMISSION_MODE` is also refused early, before boot. The composition refuses a `headless` profile without the bundle, and the task starts only after Delorun checked the bundle's rows and services. The pre-start step `changes` brings each plugin the profile links from a folder to the content Changes keeps, with protection off loading the folder's content without review and logging it, and with protection on the agent's `plugin_manager` installs, updates and removals wait for the person's review as in the CLI profile ([C21](../contracts/c21-changes.md#the-agent-and-plugins)); a headless run does not reload plugin folders live. The template mounts no MCP client and no schedule runtime; the MCP and schedule consents guard one that the person's own patch adds.
- **`delorun plugin`.** It runs upstream's pnpm operation with none of Delorun's rows: no protected home, no denied sockets, no consents, no fetch guard and no privacy defaults. Before pnpm runs it sets the profile's packages to be copied from pnpm's store, and after a successful operation it runs the [plugin install check](#plugins) over what the operation installed, with the settings of the profile's `delorun-plugin-install-check` row. Making every command that boots a Host apply Delorun's layer is in the [native confinement design](../design/native-confinement.md#every-way-a-host-boots).
- **The desktop app.** It is upstream's, unchanged, and none of Delorun's rows apply to it.
- **Windows.** The sandbox confines writes only. Confined commands can read the whole home, Delorun's secrets, upstream's credential files and the start token included, and no mode or access-list check of the home runs.

## Assets

- **The person's files and workspaces**: workspace roots on the machine.
- **Model-provider keys and other secrets**: upstream's `.credentials.yaml`, which also holds the browser session secret, and `.env` under the home; Delorun's files under `~/.delorun/secrets/`, which hold the home key `delorun export` creates and the consent records of Delorun's consent plugins.
- **Sessions**: chat history, which often holds secrets, with attachments, the full-text index, spill files and drafts in the browser.
- **Delorun's home**: `~/.delorun` with its secrets, the per-start token, the update channel's socket, the verified release root and checkpoint, and the runtime store.
- **Release integrity**: signed release manifests, runtime files and the npm launcher, and the offline root and targets keys that sign them.
- **The plugin supply**: installed plugins. The profile's `pnpm-lock.yaml` records each version's tarball integrity or git commit, and pnpm holds a tarball to it only when it fetches one; nothing in pnpm checks the installed files afterwards. Delorun's install record of each plugin from npm, a tarball or git, written when the [install check](#plugins) passes it, holds the SHA-256 of every installed file, and each start and `delorun verify` compare the installed files with it.

## Parties and trust

### The person

The person owns the home and the machine. They can see and do everything their operating-system user can: every file under the home, every chat and secret, and `delorun` and Docker where their account can run them. `delorun verify` reports and changes nothing. The person approves escalations, consents and updates; Delorun's own prompts state their effect before the person answers, and the per-call escalation prompt is upstream's.

### The model and its tool calls

The model sees the system prompt, the chat's history, tool descriptions and tool results. Any of that text can carry instructions injected through web pages, files, repositories, issues, other chats or tool output. An imported chat reaches no model request, because nothing opens imported chats ([C8](../contracts/c08-archive-and-trash.md#untrusted-imported-chats)). The model can call the tools its preset gives it, each through upstream's approval and the workspace's sandbox mode, and request an escalation that only the person can approve; it does not see the escalation prompt. Its commands run with the person's own access. In the CLI profile they are confined as [C1](../contracts/c01-home-layout.md) states, and its `web_fetch` calls reach only targets the fetch guard allows. A shell command or PTC code it runs can write an instruction file in a writable root without the instruction consent.

### Plugins

Plugins are code the person installs, trusted to the extent of their install. A Host plugin runs in the harness process with the harness's authority: it can read what the Host reads, including the credentials the Host loads and the start token the home process holds in memory, and can send the update channel any request in its fixed request set. A client plugin runs in the studio's page with the browser's access. Delorun does not sandbox plugins and does not read their code. Delorun checks each plugin's DSH and Delorun version requirements at install and at start ([C17](../contracts/c17-plugin-versions.md)); it pins nothing beyond upstream's lockfile, and the catalogue and revocation list are not built ([C13](../contracts/c13-catalogue-revocation.md)). The plugin install check ([`@delorun/plugin-install-check`](../../packages/plugin-install-check/README.md)) runs once an installation is resolved into the lockfile and before any of its files are fetched or any install script runs, in plugin management and in `delorun plugin`, and again before a bundle is selected, enabled or restored, so before its code loads: for the plugin and every package its installation adds to the lockfile it warns about a missing integrity or a git source without a full commit, a plain `http:` registry or download URL, a GitHub advisory, a version published less than 24 hours ago and a name close to one the profile or Delorun already has, and it refuses a known critical advisory until the person allows it with `--allow-advisory` or the studio's "Install anyway". An advisory or registry lookup that fails is a warning that the check could not run. A plugin from a scope or git owner the person lists as trusted shows critical advisories only, and a linked or local folder is not checked. Each start compares every recorded plugin's files with its record by file identity, and `delorun verify` hashes every file; a changed plugin is a warning, not a refusal. The npmmirror fallback that upstream asks when the first registry fails is off until the person turns it on in Settings → Plugins or with `delorun plugin mirror on`; in the studio, a package the mirror resolved is refused when its lockfile integrity differs from the one the primary registry lists, and needs the person's acceptance when the primary registry cannot confirm it. A plugin's install scripts, which pnpm runs only for builds the person allowed, run after the check passed. Each MCP server command runs as trusted code outside the agent sandbox, as upstream states; in the CLI profile a new stdio server, or one whose command, arguments, working directory, environment or pinned files changed, is refused, also before a reconnect.

### Other local processes under the same user

A process of the person's user that runs outside the sandbox can read and change everything under the home, read the start token, and run `delorun` and `docker` whenever the person can. With the start token it can use every operation of the update channel ([C19](../contracts/c19-home-process.md#the-update-channel)), including `devices.approve`, `devices.remove` and `studio.open-token`: it can open the approval window and approve a pending device request with its match code, cancel a request, remove a device, and obtain a fresh studio sign-in link. When it also controls a device that asks to be approved, it can approve that device with nobody present, and that device then signs in over reach. The Host's own channel token is refused for these operations, and a confined command cannot read the token file or reach the socket ([C1](../contracts/c01-home-layout.md#sockets-and-the-start-token)); that confinement is all that keeps the agent from the same actions, and a command that runs outside the sandbox, such as one approved under `danger-full-access`, has them. It can also write a runtime's approved harness record `changes/harness/<runtime>/approved.json`, the content store under `changes/store/` and the harness's change log ([C1](../contracts/c01-home-layout.md#the-home-tree)): the next start then runs its code from the composed tree with every start check passing, because the composed tree is checked against that record ([C21](../contracts/c21-changes.md#harness-edits)), and only the list of approved harness files that `delorun verify` and `delorun changes list` print shows it. With Changes protection off, the default, it needs none of this: a file it writes in the harness's writable copy, or in a linked plugin's folder, loads at the next start without review, logged as such ([C21](../contracts/c21-changes.md#loading-without-review)). Delorun claims no protection against such a process. The home's modes protect against other users, not against it, and no root-owned helper exists. The launcher's start check detects a changed runtime file only when the tampering does not also alter the launcher, the stored root or the runtime's identity record under `trust/runtime-files/`.

### Other users on the machine

On Linux and macOS, other non-administrator users cannot read the home, whose directories have mode 0700 and protected files 0600, and cannot connect to the update channel's socket, which has mode 0600 inside a 0700 directory. On Windows Delorun checks no access list, and the home has the access the operating system gives a new directory in the person's profile. Other users can open a TCP connection to the studio's loopback listener, which admits a launch token and upstream's signed cookies ([C4](../contracts/c04-admission.md#sessions)). In the CLI profile the launch token is one-time: `delorun` obtains each from the home process with the person's start token, it expires after 60 seconds, and its first presentation consumes it ([C4](../contracts/c04-admission.md#launch-tokens)). It still travels in the URL handed to the browser launcher, whose command line other users can read on Linux without `hidepid`, so another user can race the browser to it in the seconds before the browser's first request. A cookie obtained that way, or copied from the browser, admits for 30 days. `delorun headless` and the desktop app run upstream's profiles, where the launch token stays reusable for the life of the Host process. An administrator or root can do everything the person can. On a rootful Docker engine, membership of the `docker` group is equivalent to root.

### The network

A party on the network sees the machine's connections. Installing and updating fetch the release's public signed files, and every start through the npm launcher checks the release log when the network is reachable. These requests carry no personal data, and they reveal the machine's IP address, the request times and the Delorun version to their hosts. The files are verified by signature, so their hosts are not trusted: a changed file fails verification, and a withheld one is noticed at install or update when its timestamp expires. No setting turns the release-log check off. The studio listens on loopback; it listens on the person's tailnet as well only after the person turns on Tailscale private reach, which is off until then.

### Tailscale, a self-hosted relay and an OIDC provider

With reach off, no Tailscale node, relay or identity provider is in any path to the studio. With Tailscale private reach on, Tailscale carries the traffic: its coordination service sees the machine's name, the IP addresses of the machine and of each device, connection times and traffic volume, can add a device to the tailnet unless Tailnet Lock is on, and obtains the `ts.net` certificate. An added device can open the sign-in page and ask for approval, and opens no chat until the person approves it at the computer. The self-hosted relay and the OpenID Connect provider are not built, so neither is in any path. The [reach design](../design/reach.md) and contracts [C5](../contracts/c05-device-approval.md), [C6](../contracts/c06-relay-protocol.md), [C7](../contracts/c07-reach-providers.md) and [C14](../contracts/c14-oidc-passkeys.md) state what each sees and does, each with a status of what exists.

### Delo Run, the project

Delo Run holds the offline root and targets keys and the online timestamp key. It can publish a release, signed and entered in a public log. No client installs it until the person confirms: the npm launcher installs only into an empty runtime store, and `delorun update` applies only after the person confirms. An update never goes to a lower release: the runtime store refuses a channel release or a requested version lower than the running one with `TARGET_LOWER` before anything installs, `delorun update` refuses such a report, and only `delorun recover rollback` goes back. The timestamp command refuses to lower a channel, and clients refuse a timestamp older than the one they stored, so a channel host that holds no key can only withhold newer releases, and only until the last timestamp it served expires 3 days after issue; a start keeps running the installed release meanwhile ([C2](../contracts/c02-release-manifest.md#freshness-and-rollback-protection)). Delo Run cannot reach a home: no Delorun infrastructure is in any path to the studio, and it holds no key of the home. The person's residual trust in Delo Run covers its releases and the `delorun.com` names that serve their metadata.

### Upstream and dependency authors

Upstream's code is the harness, so its authors are trusted as the harness is. Delorun merges each upstream release, records a verdict for every changed file, and reruns the parity replay and the plugin corpus. Dependencies are pinned by the lockfile, and the signing command checks the lockfile against an advisory feed before it signs. A malicious change in the tagged source or a pinned dependency is reproduced by the rebuild and signed; the signature and the log entry show where a release came from, not that it is free of defects.

### A party holding a stolen device

A device the person approved gives its holder the chats and the actions the allowlist permits for as long as the device is unlocked and its session lives: 12 hours without a request, 14 days at most. The allowlist is wide on purpose: an approved device can already prompt the agent, so every action no riskier than a prompt is allowed, and a holder reads and drives the chats, chooses their preset and model, organises chats and workspaces, sets goals and scheduled follow-ups and reads the files of their workspaces. It grants no access on its own: a preset grants nothing, a workspace's full access stays the computer's answer, and every approval prompt still applies. Settings writes, slash commands, plugin changes, terminals (in every folder, full-access workspaces included), the folder picker, new folders and dynamic plugin code need an unlock the person approves at the computer by typing the code the device shows; an unlock lasts 15 minutes by default and 60 at most, admits nothing on another listener or in another profile, and closes the device's connections when it ends. Credentials, the account, full-access grants and device approval stay the computer's, unlocked or not ([C14](../contracts/c14-oidc-passkeys.md#elevation)). The person removes a lost device at the computer, which ends its sessions at once. A browser profile on the home's computer that holds a loopback cookie admits as the person for up to 30 days from minting, across restarts, and no command revokes it. A stolen computer that runs the home gives its holder everything the person's user holds; Delorun relies on the operating system's login and disk encryption there.

### Confinement of native commands

[C1](../contracts/c01-home-layout.md) defines the rules that the CLI profile adds to upstream's sandbox for every command that runs under `read-only` or `workspace-write`; `wsl-interop`, `vsock` and the session rules are stated below. The first five are: no writes under the home (`home-write`), no reads under it except `runtimes/`, `skills/` and `dsh-runtimes/` (`home-read`), no read of the start token (`token-read`), and no connection to the home's channels (`home-connect`) or to the Docker socket at its real path (`docker-connect`).

- bwrap enforces all five. Landlock enforces `home-write`, `home-read` and `token-read`, and cannot express the two socket rules. Seatbelt enforces all five. windows-acl enforces `home-write` only.
- Delorun's secrets live in files under `secrets/`, mode 0600 inside 0700 directories on Linux and macOS, and never under a read exemption, in a profile, a command line, a command's environment or a log. Upstream's credential files lie under the home and fall under `home-read`. Delorun does not use the OS key store, because confined commands can reach the Linux Secret Service over D-Bus and run the `node` executable a macOS keychain item trusts.
- `workspace-write` is refused when a writable root equals, lies inside or contains the home.
- The person's session services listen on sockets that a process of the person's user can use without any other credential, and several of them start a program outside every namespace and mount rule: `systemd-run --user` through the session bus or the user manager's `systemd/private` starts any program as a user unit with the host's network and the whole home, Delorun's `secrets/` included; a tmux or screen server runs a command in the person's terminal; the X server takes input for the person's other windows. Others act with the person's authority: the ssh-agent and gpg-agent sign with the person's keys, the keyring hands out secrets, and the system bus carries the polkit authorisations of the person's session. Docker Desktop's backend API and tailscaled's LocalAPI act with the authority of the `docker` group and of tailscaled's operator. `delorun start` names their directories (`/run/user/<uid>`, `/run/dbus`, `/tmp/tmux-<uid>`, `/run/screen`, `/tmp/.X11-unix`, `/mnt/wslg`, `/mnt/wsl/docker-desktop/shared-sockets`, `~/.docker/desktop`) as escape socket directories (`session-escape`), denies `/run/docker-cli.sock` and tailscaled's socket (`daemon-connect`) and the agent socket that `SSH_AUTH_SOCK` names (`agent-connect`), and sets `privateTmp`, so bwrap gives every confined command a `/tmp` without the host's files and sockets (`private-tmp`). bwrap hides each directory and every other mount of it, Seatbelt denies the entries present at each wrap, and Landlock, which cannot hide them, refuses every confined command while one of the directories exists, as it does under WSL. Sockets elsewhere, such as under the person's home, abstract sockets, among them an X server's on a Linux desktop and a session bus `dbus-launch` started on an abstract address, through which `systemd-run --user` starts a program outside the sandbox, group-owned daemon sockets that grant root other than Docker's, Docker Desktop's macOS control directories beyond its engine sockets, and the network of a workspace whose network is `open` stay reachable ([C1](../contracts/c01-home-layout.md#what-this-does-not-prove)).
- Each workspace has a network setting for its sandboxed commands, kept in the home's protected state by `@delorun/plugin-permission-defaults` ([C1](../contracts/c01-home-layout.md#confinement-rules), [guide](../guide/safety-and-updates/prompt-injection.md)). `off` starts every command in a network namespace of its own with nothing but loopback, which also cuts it off from abstract Unix sockets and the host's loopback services. `allowlist` adds Delorun's egress proxy, which listens on a socket under the home that bwrap binds into the command, one per list; the command's proxy variables name it, and a program that opens the network itself and ignores them reaches nothing. The proxy checks a name and port against the list before any lookup, refuses a listed name that resolves to an address the fetch guard refuses, connects only to the addresses it checked, sends a plain-HTTP request with the host it checked, caps its connections, closes idle ones and logs every refusal; an entry admits ports 80 and 443 unless it names another. It does not read a tunnel's bytes, so a listed host serving several names behind one address can be asked for another of them in the TLS handshake or an inner request. Under both settings bwrap also hides the sockets through which a daemon resolves names or sends traffic for the command: systemd-resolved's varlink directory, nscd, avahi, snapd, CUPS, the system D-Bus and tailscaled (`sandbox-local`'s `networkDeniedSockets` and `networkDeniedSocketDirectories`), so the command cannot reach those daemons and cannot send data out through DNS. The namespace does not cut off pathname sockets: those the bullet above names as reachable stay reachable, and a daemon behind one can open connections for the command, such as an ssh ControlMaster socket, or gpg's `S.dirmngr` where gpg has no runtime directory, under the person's home. A session bus on an abstract address is out of reach under both settings, since the namespace holds its own abstract sockets. Landlock, Seatbelt and windows-acl cannot express either setting, so they refuse every command of such a workspace rather than run it with the network. The setting is read and changed only in the studio at the home's computer; a loosening needs the person's confirmation there, the model has no tool for it, and plugin management cannot reconfigure its row. A network store that cannot be read counts every workspace as `off`. A command under full access reaches the network whatever the setting; a terminal or job keeps the network it was wrapped with until it ends, except that one whose list was removed loses its proxy.
- The approval prompt for `danger-full-access` is upstream's; it does not state that full access reaches Delorun's home.
- Nothing reports per machine which rules hold: no probe runs at start, and `delorun verify` reports the `confinement-rule` check as not run.
- Under WSL, interop would let a confined command start a Windows program, which runs outside every Linux namespace, mount rule and protected home with the person's Windows account and can read Windows processes' command lines. `delorun start` names WSL's interop directory `/run/WSL` as an escape socket directory (`wsl-interop`); where it exists, bwrap hides it, so no Windows program starts through the interop sockets, whether by path, by bare name, as a copy, through `/init` or with `WSL_INTEROP` set, and Landlock, which cannot hide it, refuses every confined command instead. Under bwrap a seccomp filter also refuses vsock sockets, the transport between WSL and Windows under the interop sockets, and io_uring, whose requests create sockets the filter does not see (`vsock`); it applies on any virtual machine whose kernel offers vsock, where a program that requires io_uring fails and a 32-bit program that creates sockets through `socketcall` gets none. Abstract Unix sockets stay reachable on every dialect; WSL listens on none, and a program the person runs that listens on one is reachable ([C1](../contracts/c01-home-layout.md#what-this-does-not-prove)).
- The harness itself runs git over a workspace's repository to record each turn's changed files. Each of those commands runs in the Session's sandbox with the Session's writable roots plus the plugin's snapshot directory, or with only that directory writable when the Session is `read-only`, and always with the Session's network; it runs unconfined only when the Session's commands do, and a command the sandbox cannot confine, or a confined Session with no sandbox mounted, records nothing. The snapshot directory lies in the per-user cache directory, outside Delorun's home; no dialect grants it to confined commands unless a Session's writable root contains it. Each snapshot and copy first checks it against the writable roots of every live Session and records nothing on an overlap, the harness checks the device and inode of every directory in it before each use, and its file operations there refuse a final-component link, named pipes and entries it did not create. A command run through an approved full-access escalation is not covered. Every command runs with every inherited `GIT_*` variable removed and with command-scope configuration that switches off the file-system monitor, hooks, every filter and diff driver the repository's configuration defines, the pager, editors, credential helpers and transports, so a `.git/config`, `.gitattributes`, hook or `.git` file that a confined command writes starts no program ([workspace-changes](../../../packages/deliverables/workspace-changes/README.md#git-hardening)). Stock runs these commands unconfined with the repository's configuration in effect.
- The person's own git and editors are not hardened. Under `workspace-write` a confined command can write a repository's `.git/config`, its hooks and its attributes, and the next time the person runs git or an editor's git integration in that repository outside the sandbox, a program such a setting names runs with the person's full access. A [design option](../design/workspace-git-state.md) for keeping those files read-only to confined commands is open for decision.
- The file tools apply `home-read` and `home-write` themselves. `read`, `read_image`, `apply_patch` and `str_replace_editor` refuse a path under the home or another path that reaches it, outside the read exemptions, and the local filesystem confirms that the file or directory it opens is the one it checked, so a workspace directory replaced by a link to the home between the check and the open fails the read: on Linux by the descriptor's own path, elsewhere by its device and inode, where a link swapped in and restored between those lookups is not detected. The write fence refuses the home and every other mount of it the provider finds, and the local filesystem holds the target's directory open and confirms it for every edit, write, create, move and delete, creating missing directories one at a time, so a directory swapped for a link to the home after the fence's check fails the change instead of reading, creating or removing a file there; outside Linux it confirms by path, and a link swapped in and restored between those checks is not detected. `glob` and `grep` resolve their root before ripgrep starts and run ripgrep confined under `read-only`, so the dialect's `home-read` holds for a search at every depth, as for a command; where no runner can confine, the search fails, and on Windows, which confines no reads, a link swapped in and restored during a search is not detected. The tools may also read their own chat's directory under `spill/`, where tool output too long for that chat is saved and which the spill notice tells the model to read, and no other chat's, which also leaves a forked chat unable to read the spill files it inherited; confined commands cannot read `spill/` at all. Spill files are written only under `spill/` (mode 0700, tightened if looser): when the home cannot hold it, the output stays in the chat instead of going to a temporary directory that confined commands could read.
- Commands and the other processes the harness starts through its subprocess service inherit its environment without the entries upstream's filter drops: names that hold credentials, such as `*_TOKEN`, `*_CREDENTIALS`, `*PASSPHRASE*`, `MYSQL_PWD`, `KUBECONFIG` and `KRB5CCNAME`, and values holding a URL with user information, a token alone such as `https://<token>@host` or a Sentry DSN included. A search list such as `PATH` loses only its elements that name a credential file or an agent socket. A credential under a name and in a form the filter does not know is inherited.
- Some tools start programs outside the sandbox in the workspace: the Claude Code and ACP subagent tools start their agent processes, and the stdio language-server tool starts language servers, unconfined. Those programs read the workspace's files and configuration with the person's full access, so a file a confined command wrote there can change what they do.
- An external agent, such as Claude Code or Codex, also runs with its own settings and the person's own sign-in and account, and can read and change Delorun's home. With the C16 switch `external_agent_consent` on, as in Delorun's profiles until the person turns it off in Settings, External agents on the home's own computer (a reach device cannot write settings, and setup's prompts answer does not change it), `@delorun/plugin-delegation-consent` reviews each start before the agent runs: a `read-only` chat, a chat without a workspace folder and a composition without a sandbox policy never start one, a run directory outside the chat's workspace is refused, and the agent starts only after the person allows that run at the home's own computer or allowed the agent for the workspace; a reach device cannot answer the ask. Each run stops after its time limit, 30 minutes by default, and the model's `plugin_manager` cannot install, enable or configure any external-agent package (every `@deepseek-ai/dsh-subagent-*` package but the in-process ones, ACP's included), however the target spells it; a full-access chat can still install one with a command. Once started, the agent is not confined: the review decides whether it runs, not what it does ([plugin](../../packages/plugin-delegation-consent/README.md)).

The probes, the check, the prompt's statement, Docker Desktop's macOS control-socket directories, Windows and the same rules under `delorun headless` are in the [native confinement design](../design/native-confinement.md).

### The home's control channels

The update channel ([C19](../contracts/c19-home-process.md)) listens on the socket `run/<profile>/update.sock`. It accepts a request only with the token of the current home-process start: 256 bits from the operating system's random source, compared in constant time, and never in a command line, an environment variable, a response or a log. It does not pass a request through: an update request carries no path, archive, URL or command, so a caller holding the token can only choose a version: one the home process fetches and verifies from the channel, or one already installed in the runtime store. The protection rests on confining the agent's commands, as C1 states, and holds only where the dialect denies reads of the token. The Docker supervisor's channel of [C9](../contracts/c09-runtime-supervisor.md) does not listen, because no command launches the supervisor, and no named pipe exists on Windows.

### Container isolation

Docker workspaces are not built. [C9](../contracts/c09-runtime-supervisor.md) specifies them and the supervisor that would create them; the supervisor package exists, and `delorun start` never launches it.

### Admission and listeners

[C4](../contracts/c04-admission.md) defines admission. The loopback listener, `127.0.0.1:3080` in the CLI profile, runs upstream's admission with one-time launch tokens turned on: a launch token that works once within 60 seconds, `/connect`, and stateless signed cookies that expire 30 days after they are minted, with no idle limit, no server-side record and no revocation. A reader of the home's `.credentials.yaml` can sign such a cookie without any launch token. Every browser holding a cookie acts as the one owner, and the loopback studio sends no Content Security Policy. Setup's `--yes` and `--config` forms never turn reach on ([C11](../contracts/c11-setup-answers.md)); `delorun reach on tailscale` and the yes answer in setup's Full mode do. With reach on, the reach listener's dispatcher authenticates every request before any route, upgrade or the fallback. Loopback credentials are upstream's launch cookie and API credential, admitted by upstream's built-in admission; no per-credential record exists, so nothing refuses a valid credential for lacking one. Recording each loopback credential with a 7-day idle limit is in the [reach design](../design/reach.md#loopback-credentials) and is not built.

### Device approval

[C5](../contracts/c05-device-approval.md) specifies device approval and `@delorun/home-auth`, which every CLI profile loads, builds it for the Tailscale private route. A new device is approved only at the home's computer: the person opens a 5-minute approval window there, and the device is approved by typing the 8-digit match code its screen shows, either in the studio on loopback, which needs the studio's own credential, or with `delorun devices approve` over the update channel, which needs the start token. The home cannot verify where a request comes from, because every request on the route has the source `127.0.0.1`; the match code is what binds an approval to the device whose screen the person read, and it does not prove who holds that device. A reach session cannot approve or remove a device, open a window or claim the home ([fundamentals](fundamentals.md) F12 and F13). Passkeys, the recovery kit, reset and alerts are not built.

### Reach providers

The Tailscale private provider is built ([C7](../contracts/c07-reach-providers.md)): it serves a fixed local port through `tailscale serve`, refuses Funnel, removes serve rules on its port that it does not own, and rechecks Tailscale every minute. The Funnel and own-domain providers are not built, and the self-hosted relay's server is built and no home connects to it ([C6](../contracts/c06-relay-protocol.md)). The specs fake `tailscale`; the [reach design](../design/reach.md#never-run-on-a-real-tailnet-or-phone) lists what no real tailnet or phone has exercised.

### Sign-in

The loopback studio signs in with a launch token from `delorun open`. A reach session signs in with an approved device's key alone, the identity factor `tailnet-membership` ([C14](../contracts/c14-oidc-passkeys.md#tailnet-membership)). C14 also specifies the passkey and OpenID Connect identity factors, which are not built.

### Releases, the log and the rebuild

[C2](../contracts/c02-release-manifest.md) and [C18](../contracts/c18-release-log.md) define release integrity.

- The offline targets key signs each release manifest, and the offline root key signs every role's keys and each rotation. The online timestamp key signs only freshness, and its file expires 3 days after issue; a client refuses an expired or older timestamp.
- Installing or updating needs a verified inclusion proof in the release log, cosigned by a witness the root lists. At each start, a verified release-log failure, or a missing stored bundle, stops the start; an offline or unknown online check never blocks one. A release whose online check did not complete at install is shown as `unchecked` in the update report, and `delorun update --yes` does not confirm it.
- The targets-key holder signs a published release only through `sign-release.ts`, which refuses when any of these fails: a matching rebuild record made outside CI from the tagged source with the published recipe, a commit on the release branch, a targets key that `delorun/release/production-keys.json` lists, and a tag signature by a key `delorun/release/allowed-signers` lists, both files read as the release branch commits them. The timestamp command refuses a timestamp key the same registry does not list; the registry ships empty, so production signing stays stopped until the owner records the keys. `local-release.ts` signs a release with no rebuild for a channel of its own: its manifest names the builder `local release (no independent rebuild)`, it refuses a root or key listed in `delorun/release/production-keys.json`, and a launcher fetching from the production publication refuses its manifest unless it is a 0.x release verified under the preview root. Until 1.0 the maintainer builds and signs releases on the maintainer's PC with no independent rebuild, so the rebuild check above does not apply to them; a 1.0 release or a release under a later root is refused.
- The signing command checks the lockfile against the GitHub Advisory Database and refuses on an advisory without a valid acceptance.
- Nothing lands under `~/.delorun/runtimes/` before the signature, digest and log checks pass. At every start the npm launcher checks every installed runtime file against the signed file list: it hashes each file, or compares the file's identity with the one recorded after its last hash, and hashes every file at least every 7 days by default. Storage corruption that leaves a file's change time alone is found by that full pass or `delorun verify`, not by the next start. The composed tree a start runs when the person approved harness edits is checked against the signed file list and the approved harness record under `changes/harness/`, both read from the home, so it finds a changed tree file but not a record a same-user process rewrote (see the same-user process above).
- The npm launcher is the pre-install trust anchor: `npx delorun` runs the launcher npm serves before any Delorun check. Each start anchors on the newest root the launcher ships, never an older stored one, so a targets key a shipped root revoked stops verifying. Setup installs the `delorun` command pinned to the running launcher's version, and the [Trust page](../guide/safety-and-updates/trust.md#checking-it-yourself) describes the out-of-band check of that version.

No release workflow exists: re-signing the timestamp every 24 hours, publishing to npm with a build attestation and without a token, and the install scripts are in the [release workflow design](../design/release-workflow.md). The desktop app's updater is upstream's and checks no Delorun signature or log entry ([update and rollback design](../design/update-and-rollback.md#the-desktop-app)).

### The catalogue and revocation

The catalogue and the revocation list are not built ([C13](../contracts/c13-catalogue-revocation.md)): Delorun pins no plugin version beyond upstream's lockfile and can disable no installed version. [C17](../contracts/c17-plugin-versions.md) refuses at install, and disables at start, a plugin whose DSH or Delorun version requirement is unmet or unreadable, and never imports plugin code to decide. Delorun does not read plugin code; the [install check](#plugins) reads the lockfile, the advisory feed and the registry's publish times, and records each installed file.

### Updates and rollback

[C3](../contracts/c03-update-report.md) and [C19](../contracts/c19-home-process.md) define how an update of the CLI home applies. Before an update, `delorun update` shows every plugin, bundle and profile row the target would disable, remove or change, and whether the chat data's format changes, marks what Delorun cannot predict as unverified and never counts it as safe, and applies nothing until the person confirms. A snapshot is written first; the switch waits until no chat runs on the old runtime, and new turns are refused meanwhile; a health check within 120 seconds rolls back automatically when it fails, and the person can roll back later with `delorun recover`. `delorun recover restore` applies a profile history version at once, without an approval prompt or the install-time plugin checks. The desktop app updates through upstream's updater.

### Archives and untrusted chats

[C8](../contracts/c08-archive-and-trash.md) defines export files and trash. An import validates the whole archive in staging before it writes anything and never overwrites a workspace or chat. Customisation is data under a closed schema: no `!!js` expression is evaluated, no `insert` row is accepted, and no row can set a sandbox mode, a credential reference, a reach option or egress. An archive without a signature that the importing home vouches for imports only after the person accepts it as unverified. No customisation row is applied, and imported chats are kept where nothing reads them, so they reach no model request. Opening imported chats as untrusted chats and applying customisation are in the [imported chats design](../design/imported-chats.md). A purge removes an item from every store C8 lists, the request-image cache excepted; a purge in the studio removes the chat's drafts in that browser, and a purge from `delorun trash` or at the end of the retention reaches no draft.

### Logs and redaction

[C20](../contracts/c20-operational-logs.md) defines Delorun's operational logs. Every record passes a redactor that replaces the registered secret values, which are the start token and the relay key, secret-named fields and listed credential forms before the record is written. A secret that matches no listed form and is not registered, such as a model key in an unrecognised form, can reach a log. Delorun's own records hold no chat text, prompt, model output, tool argument or file content. Log files have mode 0600 under the home, where confined commands in the CLI profile cannot write them and, where `home-read` is enforced, cannot read them. Each `delorun` invocation deletes logs written more than 14 days before; a home process that runs for longer keeps them until the next invocation.

### Verification

[C15](../contracts/c15-verification-checks.md) defines `delorun verify`. It runs two checks: `release-signature`, which anchors the stored root on the roots the launcher ships and checks the manifest's signature, the timestamp's freshness and the release-log bundle, with the online log check unless `--offline`; and `runtime-files`, which hashes every installed file against the signed file list. Every other check of C15's list is reported as not run. The checks run with the person's access, and every report states that a program running with that access can change them. A result is `pass`, `fail`, `not-enforced` or `unknown`; `not-enforced` and `unknown` never count as a pass. Nothing reads a verification mode: `delorun verify` reports in `warn` and blocks nothing, and the launcher always stops on a verified signature, file or release-log failure. No detail holds a secret, a token, a cookie, a key or file content.

### Parity

[C16](../contracts/c16-parity-composition.md) defines the parity composition. Its overlay loads only when the replay lane sets `DSH_SNAPSHOT_PATCH`; no shipped profile, configuration or command-line option selects it. In the parity composition the fetch guard, the protected home of the sandbox and of the search, `read` and `present` tools, the scheduled-task, instruction-layer, MCP and full-access consents and the update gate are off, and their protections are absent there; the CLI profile keeps each on.

### The web_fetch guard

In the CLI profile the fetch guard makes `web_fetch` and the HTTP fetch provider refuse loopback, link-local and private-network targets, cloud metadata addresses included, before any connection, with a typed reason the model reads; the tool stays in the model's tool list ([decision](../../../.agents/notes/proposed/feature/2026-11-06-delorun-web-fetch-private-targets.md)). It checks each redirect and connects only to the addresses it approved. `web_fetch` also follows the calling workspace's network setting: under `off` every call is refused, and under `allowlist` a URL whose host is not listed is refused before any lookup, through a tool guard that no other listener's answer can turn into permission. The guard limits `web_fetch`'s targets; the workspace's network limits what its sandboxed commands reach.

### Data sharing

Delorun has no telemetry of its own. In the CLI profile, DeepSeek's session-log upload is off until the person turns it on in the Privacy section of Settings, and DeepSeek's feedback send is removed; setup cannot turn upload on ([C11](../contracts/c11-setup-answers.md)). Under `delorun headless` session-log upload is off by default as well, and the desktop app keeps upstream's analytics. The release checks run whenever a release is installed, updated or started; their requests reveal the machine's IP address and version to their hosts, as [the network](#the-network) states. The update check fetches the release channel's signed files once a day, and at start when a day has passed, until it is turned off in the Privacy section of Settings; it sends no identifier. A new default-on request to a Delorun host needs the lead's approval and an entry in the network test's allowlist, [`network-requests.json`](../../apps/tools/src/checks/network-requests.json), which names each request Delorun makes without being asked with its hosts, purpose, switch and disclosure; its spec fails when a shipped source file that opens a network request is not listed, and does not catch a new request added to a file already listed. `delorun verify` reports the `data-sharing` check as not run.

## What Delorun does not protect against

Each limit below is stated in the contract that owns it. `delorun verify` reports only the release's signature, log state and files, so no other limit is reported per machine.

| --- | --- |

Text the model reads can ask for full access, and nothing asks you |
| The debugger of `delorun start --inspect` | While Node's inspector listens on `127.0.0.1:9229`, any process on this computer that reaches the port, the commands the agent runs inside the sandbox included, can run code as Delorun outside the sandbox, so C1's confinement guarantees do not hold. The start asks first, with a question that says so and starts on no, or takes `--inspect --yes` without a terminal; safe mode refuses it, and `delorun status` shows it while it listens |
| Same-user processes outside the sandbox | They can read and change everything under the home, mint loopback credentials, run `delorun` and `docker`, use the update channel with the start token (approve a device, remove devices, obtain a studio sign-in link), and alter the launcher, the stored root and the checks |
| Process memory on macOS and Windows | Protection of the home process's memory rests on the operating system's rules, which no Delorun test checks |
| The loopback studio's credentials | In the CLI profile a launch token works once within 60 seconds, yet travels on the browser launcher's command line, where another user or a confined command under Landlock or Seatbelt can race the browser to it within that minute; a cookie admits for 30 days, survives restarts and cannot be revoked; a reader of `.credentials.yaml` can sign one; every holder acts as the owner, and no Content Security Policy applies |
| Plugins | A plugin runs with the harness's authority; Delorun pins nothing beyond upstream's lockfile and can revoke nothing. The install check knows only published advisories and warns about the rest, and the install record detects a change made outside the plugin, not one the plugin's own code makes as the person |
| Running from a source checkout | A source checkout is a developer mode, not an installed release: the whole harness, Delorun's own bundles included, runs from the checkout, so a model working inside the repository can edit the code the Host runs; Changes leaves the checkout's own packages alone ([C21](../contracts/c21-changes.md#loading-approved-content)) |
| Changes protection off, the default | Nothing reviews a change before it loads. A model working in a full-access workspace, a downloaded program, or any process of the person's user that writes a linked plugin's folder changes the code the harness runs at the next start, or at once while Delorun runs, and a process outside the sandbox can do the same through the harness's writable copy; a confined workspace's commands and file-tool writes still go only where the sandbox allows, so they can change a plugin folder inside a writable root but never `~/.delorun`. Each such change is logged as loaded without review, named by `delorun verify`, `delorun doctor` and `delorun changes list`, and undone with `delorun changes undo`; content the person undid or discarded does not load again ([C21](../contracts/c21-changes.md#the-protection-setting)) |
| Full access and Changes | A workspace with full access runs commands with the person's own authority, so a model working there can turn protection off and approve changes, as the person can: the terminal check passes in the model's own pseudo-terminal, and only the sandbox's home-write rule stops a confined model ([C21](../contracts/c21-changes.md#who-may-do-what-from-where), F16) |
| Approved plugin code | A plugin approved under Changes runs with the harness's authority; the risk summary shown before applying is heuristics over the change, not a limit on the code ([C21](../contracts/c21-changes.md#the-risk-summary)) |
| Installed packages a plugin links | Changes copies an approved plugin's installed packages by hash, with the dependencies each lists that are installed beside it, so a write to a workspace's `node_modules` does not change what runs. A module imported without such a listing, such as a package pnpm hoisted, is resolved from the active directory's parent directories, which include the person's home folder, where a confined command may place one. Under `warn` and `off` a plugin over 50,000 files or 512 MiB loads its installed packages from where they are installed, and every `warn` start names it and says when they are under the home folder; under `block` it does not load ([C21](../contracts/c21-changes.md#loading-approved-content)) |
| Reloads while Delorun runs | Before every recomposition the Host moves `link:` dependencies naming folders, as a restore, an undo or `delorun plugin --profile default add link:<folder>` writes them, to the plugins' active directories and refuses one whose links or active directories differ from what Changes keeps. The check is provided by `@delorun/plugin-changes`; a profile configured without that row reloads unchecked until its next start, and a profile configured to watch an active directory as module source replaces modules without it, though only Delorun writes active directories ([C21](../contracts/c21-changes.md#reloads-and-restores)) |
| The approved-content store | The store keeps what a record references; a profile history version older than the approved records may name content collection removed, and restoring it loads nothing for that plugin until the person applies a change again ([C21](../contracts/c21-changes.md#collecting-the-store)) |
| Work sessions | While a work session lasts, at most 480 minutes, whatever the plugin's folder holds loads without review, whoever wrote it: the person, the agent after the per-chat ask, or another process. A session that ends without the person approves nothing, and `done` approves only the version it showed ([C21](../contracts/c21-changes.md#work-sessions)) |
| Model-authored commands that write plugin folders | A shell command or PTC code can change an approved plugin's folder without the plugin-write ask, which covers the file tools only; with protection on the change does not load until the person applies it, with protection off it loads without review at the next start or, while Delorun runs, when the folder settles, and during the plugin's work session it loads live ([C21](../contracts/c21-changes.md#the-agent-and-plugins)) |
| Clock trust | A clock set back accepts a release timestamp or log checkpoint past its real expiry; a clock set forward refuses fresh metadata, and the refusal names the expiry and the local time |
| A home that never connects | Its release stays `unchecked` against the log, and a different view of the log shown to it goes undetected |
| Witness independence | A listed witness's cosignature is checked; its independence from the log and from Delorun rests on which witnesses the root lists |
| What a log entry or a rebuild shows | A logged, rebuilt release came from the tagged source; it can still carry a defect or a vulnerability, and the rebuild cannot show that the signer's machine and toolchain are uncompromised |
| Advisory coverage | The advisory check does not cover the Node binary, the native addon's toolchain or a vulnerability without a published advisory |
| A withheld release | A channel host without keys cannot move a home to a lower release, which the runtime store and `delorun update` refuse; it can hold a home on its release until the last timestamp it served expires, 3 days after issue, and a start keeps the installed release meanwhile |
| Redaction | A secret that is not registered and matches no listed form can pass into a log; captured output can hold chat and file text until retention or purge removes it |
| Log retention | Expired records stay until the next `delorun` invocation or `delorun logs --prune` |
| Purge residue | Fragments of a purged chat stay in process logs until their retention removes them, unless the person clears them at purge; resized images stay in the request-image cache; drafts in another browser profile, and every draft after a purge from `delorun trash`, stay |
| The fetch guard's reach | Commands reach any address their workspace's network allows; a request through a configured proxy or a remote fetch provider resolves its target outside the guard |
| Code on the studio's origin | A client plugin, or injected script, runs with the browser's full access to the studio; the loopback studio enforces no Trusted Types |
| The parity composition | The protections its switches turn off are absent there; no shipped profile selects it |

## How changes keep this true

- A change that moves an approval, a refusal or an escalation is a `security`-class entry in the [divergence ledger](../../upstream-patches.json), carries the lead's verdict, and includes a denial test that fails before the change and passes after it ([decision](../../../.agents/notes/implemented/process/2026-11-06-delorun-never-less-safe-than-stock.md)). A Delorun exemption from a stock check is narrow, names the check and the case it covers, and sits behind a switch that is off in the parity composition.
- A trust-boundary change, to sign-in, devices, the relay, runtimes, archives, updates or signing, is marked Lead in its brief and gets line-by-line review, and human code owners approve security paths ([rules](../../../AGENTS.md)).
- Denial tests run against local stand-ins and never contact real services.
- This page changes in the same change as a boundary, a party's access or a limit it states, and a defence that a change builds moves from not built to built here in that change.
- Security reports go through [SECURITY.md](../../../SECURITY.md), never a public issue.

## Consent and network seams when their service fails

A consent or network row that is on but whose service failed to start fails closed: the MCP client refuses every stdio server, the external-agent and scheduled-task consents mount a service that refuses every start or delivery, and the per-workspace network gives confined commands no network. With the row's switch off, the seam is absent and behaves as stock. A stand-in carries a marker that `delorun`'s boot check reads, so the check still reports the row as failed and the Host does not start as healthy. A scheduled task the stand-in refuses stays paused until the row works again. The stand-ins mount only when the row's plugin loads and its service fails to start or its configuration is refused, including on a hot reload. A seam whose plugin never loads (for example a package that fails to load) or whose `inject` never resolves leaves the seam absent while the Host runs, and stock behaviour applies until a restart; the boot check at `delorun start` is the only cover for those two cases, and it refuses to start the Host.
