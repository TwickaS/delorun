# Contract C5: device approval

English | [中文](c05-device-approval.zh.md)

<a id="summary"></a>
## Summary

A home admits a browser or desktop app only as a trusted device: a device whose key the home has approved for one studio address. The first device claims the home with the owner code on the home's own computer. Every later device is approved from a trusted device in a live session, by typing the code the new device shows. This page defines the keys and where they are stored, the binding of device keys to their origin and of passkeys to their relying-party ID, owner claim and reset, the approval request and the approval with their match code, signatures, expiry and rate limits, sign-in, revocation, the recovery kit, the desktop app's TLS pin on another home, and how alerts reach a person whose home has no screen. The types package [`@delorun/contract-device-approval`](../../packages/contract-device-approval/README.md) carries the message types, codes and limits.

<a id="status"></a>
## Status

Device approval is built for the Tailscale private route only, and reached while the person has turned reach on.

- **Built and reached:** `@delorun/home-auth`, which every CLI profile loads, holds the single-use owner code, the owner claim answered only on the loopback listener, the approval window, the pending requests, the match code, local approval (the loopback studio's form and `delorun devices approve`), sign-in with the device key on the Tailscale private listener, the device list and device removal (`delorun devices list | approve | remove | code`). The home key that `delorun export` creates at `secrets/home-auth/home-key.pem` signs archives only ([C8](c08-archive-and-trash.md)).
- **Not built:** approval from a trusted device in a live session and its approval prompt, removal from another device by a device that holds no passkey, `delorun devices reset`, the recovery kit, passkeys and OpenID Connect sign-in, the desktop app's connection to another home and its TLS pin, and alerts. The rules for the private tailnet route are in the [reach design](../design/reach.md).

The requirements and denial tests below that this list names as not built or reached by nothing protect no one until a change builds and wires them.

## Contract

<a id="keys-and-storage"></a>
### Keys and storage

Every byte string on the wire is base64url without padding. Every signed object is serialised with the JSON Canonicalization Scheme (RFC 8785) without its `signature` field before it is signed or verified.

| Key or secret | Type | Held by | Storage |
| --- | --- | --- | --- |
| Home key | Ed25519 | The home | `~/.delorun/secrets/home-auth/home-key.pem`, PKCS #8, mode 0600 ([C1](c01-home-layout.md#secrets)). Generated at the home's first start and kept across resets. |
| Home key id | SHA-256 of the 32-byte raw home public key | Everyone | Not secret. It names the home in approvals, alerts and the relay binding of [C6](c06-relay-protocol.md). |
| Browser device key | ECDSA P-256 with SHA-256, generated by WebCrypto with `extractable: false` | One browser origin | That origin's IndexedDB, database `delorun-device`, store `keys`. The private key never leaves the browser. |
| Desktop device key | ECDSA P-256 with SHA-256 | The desktop app | A file per home in the desktop app's profile directory, `delorun/device-keys/<home key id>.bin`, encrypted with Electron's `safeStorage`. |
| Device id | RFC 7638 SHA-256 thumbprint of the device public key | Everyone | Not secret. |
| Passkey | A WebAuthn credential, algorithm ES256, EdDSA or RS256, with user verification | The authenticator | The authenticator; the home keeps the credential id, public key and address in `~/.delorun/secrets/home-auth/passkeys.json` ([C14](c14-oidc-passkeys.md#passkeys)). |
| Owner code | 16 random bytes | The home and the person | Shown once in a terminal; the home keeps only its SHA-256 hash and expiry in `~/.delorun/secrets/home-auth/owner-code.json`. |
| Recovery kit | 32 random bytes, written `DELORUN-RK1-` followed by 52 base32 characters | The person | Shown once in the studio; the home keeps only its SHA-256 hash in `~/.delorun/secrets/home-auth/recovery.json`. |

Device records live in `~/.delorun/secrets/home-auth/devices.json`: for each device its id, public key, studio address, label, platform, approval time, approving device and last sign-in time. The owner record lives in `~/.delorun/secrets/home-auth/owner.json`: the claim time, the first device and the pinned identities of [C14](c14-oidc-passkeys.md#owner-subject). Each file has mode 0600 and a `v` field with the value `1`.

<a id="binding-to-an-address"></a>
### Binding to an address

A device key is bound to the origin it was generated on, and a passkey is bound to its relying-party ID ([C14](c14-oidc-passkeys.md#relying-party-ids)). A device approved for one studio address is not trusted on another, and the home refuses its key there with `DEVICE_NOT_TRUSTED`.

- **Adding an address.** Each device that is to use the new address generates a key on that origin and is approved for it like a new device. The identity factor is enrolled for the new address before the home accepts sessions there other than enrolment sessions ([C14](c14-oidc-passkeys.md#enrolment)).
- **Changing an address.** Changing an address removes the old address with its device records, passkeys and sessions, and adds the new one.
- **Loopback.** On the loopback origin, a browser with a loopback session ([C4](c04-admission.md#sessions)) registers its device key without an approval, because the loopback credential already proves local access. A loopback device can approve devices for every address.

<a id="owner-claim"></a>
### Owner claim

A home has no owner until a device claims it, and reach stays off until it has one. Owner claim is accepted only on the loopback listener, reached on the home's own computer or through SSH port forwarding.

- **Owner code.** When the home has no owner, `delorun setup` and `delorun start` print an owner code to their terminal, and `delorun devices code` prints a fresh one. A code is 26 characters of the RFC 4648 base32 alphabet (`A`–`Z`, `2`–`7`), printed as one run. Each command prints a code only when its standard output is a terminal; otherwise it prints the instruction to run `delorun devices code` in a terminal. A new code replaces the previous one. A code is single-use and expires 10 minutes after it is printed. Input is accepted in either case, with spaces and hyphens ignored. No service logs a code, and C20's redactor treats every registered code as a secret ([C20](c20-operational-logs.md#redaction)).
- **Claim with the code.** `POST /auth/owner/claim` on the loopback listener carries `{ "v": 1, "ownerCode", "devicePublicKey", "label" }`. The home compares the code's hash in constant time, consumes the code, creates the owner record and records the device as the first trusted device. A wrong, used or expired code receives `403 OWNER_CODE_INVALID`. There is no lockout: the code has 128 bits of entropy, and claim attempts are limited to 10 a minute per source.
- **Claim from a loopback session.** A request on the loopback listener with an upstream launch-token credential may claim the home without a code, as the first step of turning reach on.
- **Local claim.** Opening the first [approval window](#approval-window) at the home's own computer, from the loopback studio or the person's own `delorun devices approve` through the home socket ([C19](c19-home-process.md#requests-and-responses)), claims a home that has no owner for the local person: the owner record names `local` as its first device, and no device record is written.
- **Reach listeners.** Every reach listener answers `POST /auth/owner/claim` with `403 OWNER_CLAIM_LOOPBACK_ONLY` and a message that names the loopback listener and SSH port forwarding, without reading the body ([C4](c04-admission.md#pre-login-allowlist)). This is the current contract, because C7's [fallback](c07-reach-providers.md#tailscale-serve-target) is in force: no identity factor exists before reach is on, and identity headers are trusted on no listener.
- **Claim on the Tailscale socket variant.** Where C7 adopts its socket variant, `reach-tailscale-private` also accepts a claim with an owner code from a request whose Tailscale identity headers C7 trusts. The claiming tailnet login becomes the first entry of the tailnet login allowlist ([C7](c07-reach-providers.md#identity-headers)).

<a id="approval-request"></a>
### Approval request

A new device on a reach address sends `POST /auth/device/request`:

| Field | Value |
| --- | --- |
| `v` | `1` |
| `devicePublicKey` | The device public key as a JWK (`kty` `EC`, `crv` `P-256`). |
| `deviceNonce` | 16 random bytes. |
| `label` | A name the person gives the device, 1 to 64 characters. |
| `platform` | The browser and operating system the page reads, at most 64 characters. |

The home binds the request to the listener's studio address and answers `201` with `requestId` (16 random bytes), `requestSecret` (16 random bytes), `homePublicKey` (the 32-byte raw home public key), `homeNonce` (16 random bytes) and `expiresAt`. A request expires 5 minutes after it is created. A home holds at most 5 pending requests; a sixth is refused with `429 APPROVAL_PENDING_LIMIT` and replaces none of them. A pending request leaves only when it is approved, expires, is cancelled by 3 wrong codes, or is cancelled by the person at the home's own computer ([local approval](#local-approval)), which frees its place. A source may make at most 10 requests a minute; an eleventh is refused with `429 APPROVAL_RATE_LIMITED`. A source is the address that the [approval prompt](#approval-prompt) shows. A `label` or `platform` that carries a C0 or C1 control character, DEL, U+2028 or U+2029, or a bidirectional control (U+061C, U+200E, U+200F, U+202A to U+202E, U+2066 to U+2069) is refused with `400 BAD_REQUEST`, and so is such a `label` in a claim. Device records are read as written, and `delorun` prints every such character in a label, platform or id as a `\uXXXX` escape.

The new device reads its request's state with `GET /auth/device/request/<request id>` and the header `Authorization: Delorun-Request <request secret>`, at most once every 2 seconds. The states are `pending`, `approved`, `cancelled`, `recovery-pending` and `expired`. An unknown request and a wrong secret are both answered `410 APPROVAL_EXPIRED`, and a request stays readable for 5 minutes after it expires.

<a id="approval-window"></a>
### Approval window

On a listener whose identity factor is `tailnet-membership` ([C14](c14-oidc-passkeys.md#tailnet-membership)), the home accepts approval requests only while an approval window is open, which replaces the standing queue there: every request on that route has the source `127.0.0.1`, so any device on the tailnet could otherwise keep the 5 pending slots full. The person opens a window at the home's own computer only, with the loopback studio's "Add a device" (`POST /auth/devices/window` on the loopback listener, from the studio's own origin) or with `delorun devices approve`. A window lasts 5 minutes and closes at the first approval. Outside a window `POST /auth/device/request` answers `403 APPROVALS_CLOSED` without reading the body. A request accepted in a window keeps its own 5-minute expiry. While a window is open, a request that names a Tailscale login is counted per login: it makes at most 10 requests a minute, at most `pairing.pendingPerIdentity` of its requests wait, and all logins together make at most 50 requests a minute; a request that names none shares its source's budget. The home cannot verify where a request comes from: any device on the tailnet can ask while a window is open, and the match code is what binds an approval to the device whose screen the person reads.

<a id="pop-up-pairing"></a>
### Pop-up pairing

A device may ask to pair without an approval window, and the studio at the home's own computer then shows the request. The `pairing` configuration of `@delorun/home-auth` decides who may ask; every field is validated at load and named with its bounds when it is out of range.

| Field | Values | Delorun default |
| --- | --- | --- |
| `pairing.mayAskWithoutWindow` | `own-user`: devices signed in as the Tailscale user this computer is signed in as. `tailnet`: any device on the tailnet. `window-only`: no one (a window is needed). | `own-user` |
| `pairing.showRequest` | `notice`: a notice with **Enter code** and **Decline**. `dialog`: the code box opens at once, never taking focus from a field being typed in. `none`: only Settings → Devices and `delorun devices approve` list it. | `notice` |
| `pairing.windowMinutes` | 1 to 15 | 5 |
| `pairing.requestExpiryMinutes` | 1 to 10 | 5 |
| `pairing.pendingPerIdentity` | 1 to 5 requests waiting from one Tailscale user | 1 |

Fixed, with no field: approval only at the home's own computer and never from a reach session, also in dangerous mode; the 8-digit match code, with no one-click approve; the cancel after 3 wrong codes; the global cap of 5 waiting requests, of which requests without a window hold at most 4, so one through an approval window always has room; and the rotation of every session on approval. A reach session can neither list nor answer a request and never receives the notice's data, which only the loopback routes answer. A reach device cannot write the `pairing` section: the home registers it as a computer-only setting. The studio at the computer writes it from Settings → Devices, and the home applies a change at once, without a restart; and `delorun setup reach` writes it from the command line.

**Identity.** `tailscale serve` sets `Tailscale-User-Login` and `Tailscale-User-Name` on each request it forwards from a user's device and replaces any copy the client sent (checked against Tailscale 1.104 on 2026-11-13, with a forged copy sent through the serve port). A tagged device has no user, so it sends none. The computer's own user is the `User` entry that `Self.UserID` of `tailscale status --json` names, read when the listener starts; when it cannot be read, `own-user` accepts no one. A request without a window is accepted only when it names an identity that the mode allows, and is otherwise answered `APPROVALS_CLOSED` without its body being read.

**The identity headers are a quota and display hint, never authorisation.** Any local process can reach the loopback listener behind `tailscale serve` and send the headers itself. That gains it one waiting request, which still needs the 8-digit code from its own screen typed at the computer, and three wrong codes cancel it.

<a id="match-code"></a>
### Match code

The match code is 8 decimal digits derived from both public keys, both nonces and the address:

`SHA-256("delorun-match-v1" ‖ 0x00 ‖ home public key ‖ device id ‖ homeNonce ‖ deviceNonce ‖ address)`, whose first 8 bytes, read as an unsigned big-endian integer modulo 10⁸, are written with leading zeros as `1234 5678`. The home public key is its 32 raw bytes; the device id and both nonces are the bytes their base64url text decodes to; the address is its UTF-8 text. A typed code is compared after removing spaces and hyphens.

The new device computes the code from the home public key it received and shows it. The trusted device computes it from the home public key it was approved with and the request it reads from the home. A home key substituted between the new device and the home therefore produces a code that the trusted device does not compute.

<a id="approval"></a>
### Approval

A trusted device approves a request only through `POST /auth/device/approve`, an authenticated request of its own live session; this is not a pre-login route. The approval is:

| Field | Value |
| --- | --- |
| `v` | `1` |
| `requestId`, `homeNonce` | As in the request. |
| `homeKeyId` | The home key id the approving device holds. |
| `deviceId`, `address` | The new device's id and the address its request was bound to. |
| `typedCode` | The 8 digits the person typed from the new device's screen. |
| `issuedAt`, `expiresAt` | Times in milliseconds; `expiresAt` is no later than the request's. |
| `approverDeviceId` | The approving device's id. |
| `signature` | ECDSA P-256 signature by the approving device key. |
| `webauthn` | On a reach listener whose address has passkeys ([C14](c14-oidc-passkeys.md#relying-party-ids)): a WebAuthn assertion with user verification whose challenge is the approval hash, the SHA-256 hash of the approval without `signature`, `webauthn` and `oidcReauth`. |
| `oidcReauth` | On a reach listener whose address has no passkeys: an ID token from an OpenID Connect sign-in with `prompt=login` and `max_age=0` whose `nonce` is the approval hash ([C14](c14-oidc-passkeys.md#re-authentication)). |

The home accepts the approval only when all of these hold: the request is admitted on a live session whose device is `approverDeviceId`; the signature verifies with that device's key; on a reach listener, either the assertion verifies for a passkey enrolled for the approver's address with the user-verified flag set, or the re-authentication token verifies for the owner's pinned identity with an `auth_time` within 120 seconds; an approval on a reach listener with neither is refused, and a device on such an address is approved from the loopback listener; the request is pending and unexpired, and `homeNonce`, `homeKeyId`, `deviceId` and `address` equal the request's; `typedCode` equals the match code; and `issuedAt` is within 60 seconds of the home's clock. After 3 wrong codes for one request, the home cancels the request. On acceptance the home records the device, every session rotates ([C4](c04-admission.md#rotation-and-revocation)) and the home raises a `device-approved` alert.

<a id="approval-prompt"></a>
### Approval prompt

The trusted device's prompt shows the new device's label and platform, the time of the request, its source address and the match code field, which the person must fill. The source address is the socket peer address of a direct connection, shown as verified, or an address that a relay, `tailscaled` or a forwarding header asserted, shown with the label "unverified" or omitted. A relay-asserted address is never shown as a plain fact. The prompt derives no place name from an address.

<a id="local-approval"></a>
### Local approval

At the home's own computer a request is approved without a session or a device signature: the person's presence there stands in for both. The two forms are the loopback studio's approval form (`GET /auth/devices/pending`, `POST /auth/devices/approve` and `POST /auth/devices/cancel` on the loopback listener, from the studio's own origin) and `delorun devices approve`, the home socket's `devices.approve` operation, which C19 accepts only with the person's own token. Each shows every pending request with its label, platform and time, and the person chooses the one to approve and types the 8-digit match code shown on that device; either form lets the person cancel a chosen request (the form's `POST /auth/devices/cancel`, or `devices.approve` with `cancelRequestId`, for which `delorun devices approve` shows the first 8 characters of each request id), which the new device then reads as `cancelled`. The home checks that the request is pending and unexpired and that the typed code equals the match code; after 3 wrong codes it cancels that request, and every other request stays pending. On acceptance it records the device with the approver `local`, every session rotates ([C4](c04-admission.md#rotation-and-revocation)) and the window closes. The acceptance also mints a single-use enrolment ticket bound to that device, its listener and its session, and the device then offers to set up Face ID: the ticket lets `POST /auth/passkey/register/options` and `/register` create the device's passkey once ([C14](c14-oidc-passkeys.md#face-id-unlock)). A device paired earlier adds a passkey without a ticket by asking for a code at `POST /auth/passkey/add/request` and having the person type it at the computer. A request a reach listener admitted is answered `403 LOOPBACK_REQUIRED` on every one of these routes ([C14](c14-oidc-passkeys.md#tailnet-membership)). Presence is shown by the studio's own credential, not by the loopback address: every loopback device route (window, pending, approve, cancel, list, removal) requires what upstream's `connection.requestRejection` accepts, the browser's signed launch cookie or a live API credential, and is refused with `401 NOT_SIGNED_IN` without it; each state change also requires an `Origin` equal to the studio's own loopback origin (`403 ORIGIN_MISMATCH`). No loopback route returns a match code or the values it derives from. The match code proves that the approved request came from the device whose screen the person read; it does not prove who holds that device.

<a id="sign-in"></a>
### Sign-in

A trusted device signs in on a reach listener with a fresh challenge.

1. `POST /auth/device/challenge` with `{ "deviceId" }` returns a 32-byte `challenge` that expires after 60 seconds. A device holds at most 5 unused challenges.
2. `POST /auth/session` carries `deviceId`, `challenge`, `signature` over `"delorun-signin-v1" ‖ 0x00 ‖ address ‖ challenge` and either an identity-factor proof for the address (a passkey assertion or an OpenID Connect sign-in ticket, [C14](c14-oidc-passkeys.md)) or the session token being rotated. On an address with no enrolled identity factor, a request with neither creates an enrolment session ([C14](c14-oidc-passkeys.md#enrolment)).

A challenge is single-use. A device id with no record for the listener's address receives `401 DEVICE_NOT_TRUSTED`, and a reused, expired or foreign challenge, or a signature that does not verify, `401 CHALLENGE_INVALID`; a failed attempt uses its challenge up. A valid identity-factor proof without an approved device key creates no session. On a listener whose factor is `tailnet-membership` the signature alone creates a full session with that factor, and no enrolment session exists there, because no factor is enrolled on that address. The session cookie a sign-in request carries names the session it rotates when that session is the device's on that listener; any other cookie is left alone and the signature creates a fresh session.

<a id="removal"></a>
### Removal

A trusted device in a live session, or the person through `delorun devices remove <device id>` while the home runs, removes a device. Removal deletes its record, passkeys enrolled from it and sessions, disposes its Peers, rotates every other session and raises a `device-removed` alert, all before it returns. A trusted device that holds a passkey removes another device at `POST /auth/devices/remove` with a Face ID grant for exactly that request ([C14](c14-oidc-passkeys.md#face-id-unlock)); a PIN never confirms it. A device that makes five wrong PIN tries while [PIN mode](c14-oidc-passkeys.md#pin-mode) is on is removed the same way, by the home.

<a id="reset"></a>
### Reset

`delorun devices reset` restores approval rights from the home's terminal. It refuses with `HOME_RUNNING` while the home process holds its lock ([C19](c19-home-process.md)). Otherwise it turns reach off in the profile, deletes the owner record, every device record, session, pending request, passkey record and pinned identity, invalidates the recovery kit, replaces the loopback browser session secret ([C4](c04-admission.md#rotation-and-revocation)) and writes a `reset` alert. It keeps the home key and the reset alert's list of former device ids, so a former device that connects later is shown that the home was reset. The next claim follows [owner claim](#owner-claim).

<a id="recovery-kit"></a>
### Recovery kit

The recovery kit restores approval rights when every trusted device is lost. It exists only on a home with an enrolled passkey or OpenID Connect identity factor.

| Configuration | Ways back | What setup and the devices screen say |
| --- | --- | --- |
| No reach, or reach without an enrolled passkey or OpenID Connect sign-in | The home's terminal (`delorun devices reset`) | Recovery is from the terminal only. |
| A passkey or OpenID Connect sign-in enrolled for a reach address | The recovery kit and the home's terminal | The kit and the terminal. |

- **Issue.** The home issues a kit when the first passkey or OpenID Connect sign-in is enrolled, and shows it once.
- **Use.** A new device with a pending approval request sends `POST /auth/recovery` with its `requestId`, `requestSecret`, the kit and an identity-factor proof for the listener's address, which must be the owner's pinned identity. A home with no such factor refuses with `403 RECOVERY_NEEDS_FACTOR` and a message that recovery is from the terminal only. A kit that does not match receives `403 RECOVERY_KIT_INVALID`.
- **Single use.** A matching kit is consumed when it is presented, whatever follows; it fails every later use.
- **Cancel delay.** The request enters `recovery-pending` for 72 hours, and the home raises a `recovery-started` alert to every trusted device. Any trusted device can cancel from a live session, and so can `delorun devices recovery-cancel` from the terminal. A cancel raises `recovery-cancelled` and offers the cancelling device a new kit.
- **Completion.** After 72 hours without a cancel, the device is approved, every session rotates, the home raises `recovery-completed`, and the recovered device receives a new kit, shown once.

<a id="desktop-app-on-another-home"></a>
### Desktop app on another home

A desktop app running the home on the same computer is that home's loopback device. A desktop app connecting to another home is approved like any device: it sends an approval request, shows the match code computed from the home public key it observed, and is approved from a trusted device.

- **TLS pin.** A home that keeps one TLS key across certificate renewals sends, after the approval, a TLS key statement `{ "v": 1, "address", "spkiSha256", "issuedAt" }` signed by the home key. The app verifies it with the home key its match code committed to and pins `spkiSha256`, the SHA-256 hash of the leaf certificate's SubjectPublicKeyInfo. A connection whose leaf key differs is refused with `TLS_PIN_MISMATCH`.
- **Re-pin.** The app replaces a pin only with a new statement signed by the home key it pinned with, received over a connection that passed the old pin. Without one, the app is approved again.
- **No pin.** On a `ts.net` address, where Tailscale holds the TLS key, and on a home that does not keep its TLS key, the app pins nothing, shows that no pin applies, and claims no end-to-end protection through a relay.
- **Substituted home key.** An approval response whose home public key differs from the key of an earlier approval for the same address makes the app refuse with `HOME_KEY_MISMATCH`.

<a id="alerts"></a>
### Alerts

An alert records an event the person must see. The kinds are `unrequested-certificate`, `second-tunnel-refused` and `tunnel-rebound` ([C6](c06-relay-protocol.md)), `device-approved`, `device-removed`, `recovery-started`, `recovery-cancelled`, `recovery-completed` and `reset`. `unrequested-certificate`, `second-tunnel-refused` and `recovery-started` are blocking; the others are notices.

Every home delivers every alert through all of these channels; a home with no screen anyone watches relies on the last three.

1. **The home's own screen.** The studio on the loopback listener and the desktop app running the home show a blocking alert over every screen until it is acknowledged there.
2. **Alert file.** The home writes `~/.delorun/alerts/<alert id>.json` with mode 0600 ([C1](c01-home-layout.md)). The file holds `{ "v": 1, "id", "kind", "severity", "raisedAt", "homeKeyId", "subject", "signature" }`, where `id` is 16 random bytes written as 32 lowercase hexadecimal digits, `subject` holds the kind's details and `signature` is the Ed25519 signature by the home key. The file holds no secret. Delorun never deletes an alert file, and `delorun verify` reports unacknowledged alerts ([C15](c15-verification-checks.md)).
3. **Alert page.** On each trusted device's next authenticated connection, on any listener, the home answers the studio's index request with the alert page, which lists every alert raised since that device's last connection, until that device acknowledges it. Acknowledgement on one device does not acknowledge on another.
4. **Command or webhook.** The person may configure either or both; both are off by default.
   - **Command.** `alerts.command` is an argument list whose first element is an absolute path. The home runs it without a shell, as the person, with the alert file's JSON on standard input and only `PATH`, `HOME`, `DELORUN_ALERT_ID` and `DELORUN_ALERT_KIND` in its environment, and stops it after 30 seconds.
   - **Webhook.** The webhook URL is a secret in `~/.delorun/secrets/alerts/webhook-url` and must use `https`. The home sends `POST` with the alert JSON and the header `Delorun-Alert-Signature: ed25519=<signature>`, waits at most 10 seconds and retries a failed delivery 3 times, after 1, 5 and 15 minutes. The result of each attempt, without the URL, goes to the operational log.

<a id="delorun-mailbox"></a>
### Delorun mailbox

The Delorun mailbox, which carries device-signed approvals between devices through the [hosted service](../reference/glossary.md#hosted-service), is not part of Delorun ([roadmap](../guide/roadmap.md)). Every approval reaches the home directly, as an admitted request of the approving device's live session. A mailbox would carry only messages it cannot forge, and would refuse an approval that arrives only through it, outside a live session.

<a id="compatibility"></a>
## Compatibility

The message version is `1` and every stored file carries `v: 1`. A home refuses a message of another version with `400`. A change to the match code derivation, a signed object or a limit is a change to this contract and a new message version. A new alert kind is additive; a reader shows an unknown kind as a blocking alert with its raw subject.

The spike result on `ts.net` relying-party IDs decides whether passkeys are an identity factor on `ts.net` addresses ([C14](c14-oidc-passkeys.md#compatibility)), and the spike result on the Tailscale serve target decides whether `reach-tailscale-private` accepts an owner claim ([C7](c07-reach-providers.md#compatibility)). Until a spike result is recorded in those pages, this page's current contract holds: owner claim is loopback-only, and an approval on a `ts.net` address carries an OpenID Connect re-authentication, because C14's current contract makes no passkeys available there.

<a id="security"></a>
## Security

Requirements:

- Device keys are non-extractable and bound to their origin, and passkeys are bound to their relying-party ID; a device approved on one address is refused on another, and adding or changing an address approves devices and enrols the identity factor again for it.
- The match code commits to both public keys and both nonces and is shown on both devices; the approval carries the code the person typed.
- Approvals count only inside a live session, carry the approving device's signature, carry a user-verified WebAuthn assertion on reach listeners (or, on an address without passkeys, an OpenID Connect re-authentication bound to the approval), and are bound to the request's nonce, expiry, home key and address.
- An approval prompt shows device, time and source address, and an address that a relay or a forwarding header asserted is marked unverified or omitted.
- Owner claim, first and after reset, is accepted only on the loopback listener, SSH port forwarding included; under C7's fallback, a claim on the Tailscale private target is refused with a message directing the person to loopback.
- Owner codes have 128 bits of entropy, are single-use, expire after 10 minutes, are printed only to a terminal and are never logged.
- `delorun devices reset` refuses while the home runs, turns reach off and notifies former devices.
- On a `tailnet-membership` listener, approval requests are accepted only within a window opened at the home's own computer, and a device is approved only there, by a local approval.
- The recovery kit is single-use, needs the enrolled passkey or OpenID Connect sign-in, is replaced on completion, and waits 72 hours during which any trusted device can cancel it; without such a factor it is refused, and setup and the devices screen say that recovery is from the terminal only.
- A desktop app on another home is approved like any device, its match code commits to the home key it observed, it pins the TLS leaf key only on a home that keeps it, re-pins only with the home key's signature, and states that no pin applies on `ts.net`.
- Alerts are written to a signed file and shown on the home's screen and on every trusted device's next connection, never only through Delorun infrastructure.

Denial tests:

| Test name | Behaviour proven |
| --- | --- |
| `an approval outside a live session is refused` | A correctly signed approval sent without an admitted session of the approving device is refused with `APPROVAL_NOT_IN_SESSION`, and the device is not recorded. |
| `the reach listener has no claim route` | A valid owner code posted to `/auth/owner/claim` on each reach listener claims nothing, and the response is `OWNER_CLAIM_LOOPBACK_ONLY`. |
| `owner claim on the serve target is refused under the fallback` | With C7's fallback in force, a claim on `reach-tailscale-private` carrying forged Tailscale identity headers is refused with a message naming loopback and SSH port forwarding. |
| `a device key approved on loopback is refused on a reach address` | A device key with a loopback record signing a challenge on a reach listener receives `DEVICE_NOT_TRUSTED`. |
| `a device approved on one reach address is refused on another` | A device key approved for one address is refused on a second address of the same home until it is approved there. |
| `a valid identity without a device key creates no session` | A valid passkey assertion or OpenID Connect ticket with an unknown device id creates no session. |
| `an approval with a wrong typed code is refused and the third cancels` | Wrong codes are refused with `APPROVAL_CODE_MISMATCH`, and after the third the request is cancelled while every other pending request stays. |
| `an approval on a reach listener without user verification is refused` | An approval whose assertion lacks the user-verified flag, has none, or carries a re-authentication token whose `nonce` is not the approval hash or whose `auth_time` is older than 120 seconds, is refused. |
| `a request outside a window is refused unread` | On the Tailscale private listener, `POST /auth/device/request` without an open window answers `APPROVALS_CLOSED` while its announced body is still unsent. |
| `an unapproved device on the tailnet route gets no session` | A key with no record, with or without forged `Tailscale-*` headers, receives `DEVICE_NOT_TRUSTED` and no cookie. |
| `a tailnet-route session cannot approve a device` | A `tailnet-membership` session's window, approval and removal requests answer `LOOPBACK_REQUIRED`, and no window opens. |
| `approval limits hold` | A sixth pending request and an eleventh request in one minute from one source are refused, and the sixth replaces no waiting request; after the person cancels one at the home's own computer, the sixth is accepted and the cancelled request reads `cancelled`. A label or platform carrying a control or bidirectional formatting character is refused with `BAD_REQUEST`. |
| `a used owner code fails a second time` | An owner code that claimed the home, or one older than 10 minutes, receives `OWNER_CODE_INVALID`. |
| `owner codes never reach a log` | A claim with a planted code leaves no occurrence of it in any operational log. |
| `devices reset refuses while the home runs` | `delorun devices reset` exits with `HOME_RUNNING` while the lock is held, and changes nothing. |
| `a used recovery kit fails a second time` | A kit presented once, whether the recovery completed or was cancelled, receives `RECOVERY_KIT_INVALID` when presented again. |
| `a recovery kit without an enrolled factor is refused while reset works` | On a home with no passkey or OpenID Connect enrolment, the kit is refused with `RECOVERY_NEEDS_FACTOR`, and `delorun devices reset` restores a claim. |
| `a cancelled recovery approves nothing` | A recovery cancelled from a trusted device within 72 hours leaves the requesting device untrusted after the delay. |
| `a desktop shown a substituted home key refuses the connection` | A desktop app whose approval response carries a different home key than its earlier approval refuses with `HOME_KEY_MISMATCH`, and its match code differs from the trusted device's. |
| `a desktop refuses a substituted certificate and an unsigned re-pin` | A pinned app refuses a leaf key other than the pinned one, and refuses a new pin not signed by the home key. |
| `a relay-asserted address is marked unverified` | An approval request arriving through a relay that asserts a planted client address renders that address with the unverified label, or omits it. |
| `a headless alert reaches its channels` | An alert on a fixture home with no screen produces an alert file whose signature verifies with the home key, the alert page on a trusted device's next connection, and one command run and one webhook delivery when configured. |

<a id="what-this-does-not-prove"></a>
### What this does not prove

- **Per-source limits on forwarded paths.** On the relay, Funnel and Tailscale paths, the source address of a request is asserted by the relay, `tailscaled` or a forwarding header, and under the fallback a local process can forge it. The per-source limits are advisory there; the limit that holds is 5 pending requests per home.
- **User verification under `attestation: "none"`.** The home reads the user-verified flag that the authenticator sets and does not verify which authenticator made the assertion, so the flag is only as trustworthy as that authenticator.
- **The alert page on an intercepted relay path.** A party that intercepts a relay path can serve its own page and drop the alert page; the alert file, the home's own screen and the configured command or webhook do not depend on that path. Detection of a certificate also waits until a log includes it ([C6](c06-relay-protocol.md#certificate-monitoring)), and no alert is raised before that.
- **The person's own processes.** A process of the person's user outside the sandbox can read the home key and the device records and can approve devices; these rules protect against other parties, not against it ([C1](c01-home-layout.md#security)).

<a id="decided-values"></a>
## Decided values

- Owner codes: 128 bits, 26 base32 characters, single use, 10-minute expiry, no lockout.
- Approval requests: 5-minute expiry, at most 5 pending per home and 10 requests a minute per source.
- The recovery kit's cancel delay: 72 hours, cancellable from any trusted device.
- Alerts on a headless home: a signed alert file under `~/.delorun/alerts/`, an authenticated alert page shown to every trusted device on its next connection, and an optional command or webhook the person configures.
- Key types: Ed25519 for the home key, ECDSA P-256 for device keys, ES256, EdDSA or RS256 for passkeys.
- The match code: 8 decimal digits, with 3 wrong attempts per request.
