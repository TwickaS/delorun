# C21 Changes

## Summary

What a person's harness runs is the signed release plus the changes they made, each recorded; with protection on, only the changes they approved at their computer. A plugin the profile links from a folder loads from a copy of its approved content, kept under the Delorun home. Protection is off by default: each start, and each save in the folder while Delorun runs, makes the folder's content the approved content and logs it as an applied change the person lists, shows and undoes ([The protection setting](#the-protection-setting)). With protection on, edits in the folder are pending changes until the person applies them. The person's edits to the harness itself are made in a writable copy of the installed release and run, once applied, from a composed tree beside the signed installation, which is never edited ([Harness edits](#harness-edits)). The library is [`@delorun/changes`](../../packages/changes/README.md); `delorun start` and `delorun headless` apply it in their pre-start step `changes`, before upstream prepares the profile, and hold the prepared profile to its invariants in the composition's approved plugin content step.

## The home's changes directory

`changes/` is a Delorun entry of the home ([C1](c01-home-layout.md#the-home-tree)) at mode 0700; every file in it is a protected file at 0600.

| Path under `changes/` | Holds |
| --- | --- |
| `protection.json` | `{"schema":"delorun.changes-protection/1","level":"on"\|"off","setAt":<ISO time>}`; absent means `off` |
| `store/objects/<sha256>` | One file's bytes, named by their SHA-256, never rewritten |
| `store/versions/<sha256>.json` | One content version: `{"schema":"delorun.changes-version/1","entries":[…]}`, entries sorted by path; its name is the SHA-256 of its canonical entries |
| `store.lock` | The store's lock, holding its holder's process id: storing a folder and collection hold it ([Collecting the store](#collecting-the-store)) |
| `profiles/<profile>/active/<plugin>/` | The directory the profile's `link:` dependency on the plugin names; `@scope/name` is written `@scope+name` |
| `profiles/<profile>/active.json` | What each active directory holds: a version and `approved` or `work-session`, or `left-out` with a version or none ([When a start fails](#when-a-start-fails)) |
| `profiles/<profile>/log.json` | The change log: `{"schema":"delorun.changes-log/1","migratedAt"?,"entries":[…]}` |
| `profiles/<profile>/work-session.json` | The work session while one lasts ([Work sessions](#work-sessions)) |
| `profiles/<profile>/scan-cache.json` | File digests by inode, size and times; an optimisation never trusted for a decision |
| `harness/log.json` | The change log of the harness's own files, one for the home, every profile's lists show it ([Harness edits](#harness-edits)) |
| `harness/<runtime>/approved.json` | `{"schema":"delorun.changes-harness/1","runtime","files":{"<path>":{"version","signed"?,"change","approvedAt"}}}`: the runtime's files under `app/` whose approved content differs from the signed release's |
| `harness/<runtime>/copy/app/` | The person's writable copy of the runtime's `app/` directory |
| `harness/<runtime>/scan-cache.json` | The copy's scan cache |
| `harness/<runtime>/run/<digest>/` | The composed tree a start of the runtime runs |
| `harness.lock` | The lock every harness decision, composition and retention holds |

A version entry is a file (`path`, `digest`, `size`, `executable`) or a link (`path`, `target`, `outside`). The profile's `package.json` records each approved plugin under `delorun.changes` as `{"schema":"delorun.changes-approved/1","plugins":{"<name>":{"source","version","approvedAt","approvedAtUpgrade"?}}}`, so every profile history version holds the approved version and upstream's undo and restore bring it back.

## Change kinds and states

| Kind | What changes |
| --- | --- |
| `plugin-edit` | A linked plugin's folder differs from its approved content |
| `plugin-install`, `plugin-update`, `plugin-remove` | A plugin is added, moved to another version or taken out |
| `plugin-off`, `plugin-on` | One plugin is turned off or on again |
| `harness-edit` | A file of the harness itself differs from the signed release's |
| `guard-weakening` | A setting weakens a consent or a guard, or protection is turned off |

A change is `pending`, `applied`, `discarded`, `left-out-at-start` or `undone`. A decision's `decidedFrom` is `terminal` or `studio` for the person's own decision, `upgrade` for the first start under Changes, `start` for a change a failed start left out, `update` for a harness file an update the person confirmed carried to the runtime it installed, and `unreviewed` for content Delorun loaded without review while protection was off ([The protection setting](#the-protection-setting)). Its id is `c` and ten hexadecimal digits of the SHA-256 of its kind, subject and both versions, so an id names exactly the content that was shown. Each applied change is one version of the profile's history.

## Loading approved content

Before upstream prepares the profile, the start takes upstream's profile write lock (`package.json`'s file lock) and, for every `link:` dependency:

1. A link into the runtime store, or to the directory the running installation carries for that package name, is the harness and is left alone.
2. Any other link is moved to the plugin's active directory in `package.json`, the lockfile's importer entry and `node_modules/<name>`, because pnpm resets the link to the recorded dependency on every operation. With protection on, the moved plugin waits for review as a pending `plugin-install` from that folder unless the folder is its approved one; with protection off, its folder's content loads as step 3 says. A link whose folder is missing, or names a file, is moved too and waits for review as a pending `plugin-install` from that folder whose `to` is the empty version, in either setting, so a folder created there later loads nothing before a start or a reload reads it.
3. The active directory is made to hold: in a work session for the plugin, the folder's content; while a change a failed start left out stays out, the content from before it, or nothing ([When a start fails](#when-a-start-fails)); with protection on, the approved version, or nothing for a plugin with none, which upstream then skips; with protection off, the folder's content, which becomes the approved content as [Loading without review](#loading-without-review) states, unless the person declined exactly that content, which keeps the approved version. A file that differs is replaced in place, so hot reload replaces only changed modules.
4. The start checks that every link names its plugin's active directory, that `node_modules/<name>` resolves there when it exists, and that each active directory holds what `active.json` records, which with protection on, outside a work session and a change left out, is the approved version; otherwise it refuses with `LOAD_REFUSED` and the profile does not boot.

A plugin's content is every file under its folder except `.git` and names holding a backslash, with the targets of its links included by hash: a link that stays inside the folder, judged both as written and by where it resolves on disk, stays a relative link; a link to an installed package (a real path below a `node_modules` directory, such as one in pnpm's `.pnpm` store), to a sibling workspace package, or into a `.git` directory of the folder or of a package it includes, is copied under the link's path. A sibling workspace package is a directory holding a regular `package.json` that the link reaches at a path `…node_modules/<name>`, `<name>` a package name, as a pnpm workspace links one. An installed package included this way brings the dependencies its `package.json` lists (`dependencies`, `optionalDependencies`, `peerDependencies`) that are installed beside it, as pnpm installs them, under `<its path>/node_modules/<name>`, by the same rules, so the copy resolves them as Node resolves the original. A link that does not resolve, any other link out of the folder, and every link to a target in the Delorun home or in `/proc`, `/sys` or `/dev` is left out of the copy and listed among the paths the scan could not include: a copy that kept such a link would load whatever is there when it runs, and the Delorun home holds the person's secrets, which the store and a diff a remote session reads must never hold. A scan never walks into the Delorun home either. Each file is read up to the size its status gave when it was opened, which is what counts against the limits, and the store's copy reads no more; a file that holds more is refused with `CHANGED_WHILE_READING`, so a file that never ends cannot stall a start.

One content version holds at most 50,000 files, links and directories and 512 MiB (`CONTENT_ENTRY_LIMIT`, `CONTENT_BYTE_LIMIT`), its included packages counted. A folder that passes a limit, changes while it is read, or cannot be read never stops a start:

- The plugin keeps its approved content, or loads nothing without one, and the start names the plugin and the reason (for a limit, `CONTENT_TOO_LARGE`): a plugin over the limits is refused until it is smaller.
- With protection off, a folder over the limits only with its installed packages is the exception: it is stored with those packages kept as links to where they are installed, and each start that loads it says so, adding when one of them is below the person's home folder, where a confined command can write.
- A link a start moves whose folder cannot be read waits for review as a pending `plugin-install` whose `to` is the empty version, in either setting, and the next start reads the folder again; the first start under Changes approves no such plugin.
- Approved content the store no longer holds, such as a version a restored history version names after collection removed it, loads nothing, and the start names the plugin.

## Harness edits

The person can change the harness itself: the files under the installed runtime's `app/` directory. The signed installation under `runtimes/<runtime>/` is never edited, and the runtime store's start check of it is not relaxed in any protection setting. Harness edits are per runtime version and home-wide, not per profile; `node/` and every path outside `app/` is never a harness file. The library is [`harness.ts`](../../packages/changes/src/harness.ts) and [`harness-tree.ts`](../../packages/changes/src/harness-tree.ts); `delorun` reaches them through [`harness-command.ts`](../../apps/cli/src/changes/harness-command.ts) and [`harness-start.ts`](../../apps/cli/src/changes/harness-start.ts).

| Part | What it is |
| --- | --- |
| The signed file list | Every action that reads the installation reads the runtime store's verified file list: the start check under the root the launcher anchors, as `checkStoredRuntime` runs it, and each byte read from the installation is checked against that list's length and SHA-256 again |
| The record | `harness/<runtime>/approved.json`: each file whose approved content differs from the signed file, as a one-file content version in the store (`version`, the empty version for a removed file), with the signed file's version (`signed`), the change that approved it and when. A runtime without the record runs its signed release |
| The writable copy | `delorun changes edit-harness` creates `harness/<runtime>/copy/app/` for the running runtime: a copy, never a hard link, of the installation's `app/` with the record's approved files in place and its removed files absent; files 0600, executable ones 0700, directories 0700. A second run prints the folder and changes nothing. Before copying anything it counts, from the signed file list and the record, the entries and bytes the copy would hold as the copy's scan counts them, and refuses with `CONTENT_TOO_LARGE`, naming the limit and that harness edits cannot be made for this release, when either passes the scan's limits |
| Pending changes | Each file of the copy whose content or execute bit differs from what the runtime runs (the record's version, or the signed file) is one pending `harness-edit` change, subject `{file, runtime}`, `from` the one-file version of what runs (the empty version when nothing does) and `to` the copy's (the empty version when the person deleted it). Added files count. Links, FIFOs, sockets, devices and paths outside `app/` are listed as skipped and never followed; files named `*.mine`, which an update writes beside a file it could not merge, are listed as kept beside. The scan has the plugin scan's limits and its own scan cache. A copy that is not a directory, passes the limits or holds an entry that cannot be read refuses every read of it with `HARNESS_COPY_UNREADABLE`, subject the copy's `app/` directory, its detail naming the reason and `delorun changes edit-harness --discard`; a file that changes while it is read refuses with `CHANGED_WHILE_READING`. Pending changes are computed on every read and logged only when decided |
| The log | `harness/log.json`, a change log of the same schema as a profile's, whose entries carry `subject.runtime`; every profile's `list` and `show` include it |

Every decision runs under `harness.lock` and is logged with `decidedFrom`; each of the person's decisions takes a proof of presence and refuses one the attest functions did not issue before it reads or writes anything:

- **Apply.** Both sides are stored first; the copy's content becomes the file's approved content in the record, the entry removed when it equals the signed file or the signed release has no such file and the copy holds none. It prints the review and risk summary and asks the second confirmation as a plugin's apply does. `runtimes/` is never written. The change runs from the next start. A change a failed start left out is applied again while the record still holds its content.
- **Discard.** The copy holds what the runtime runs for the file again: the approved or signed bytes, or no file. The change is logged discarded.
- **Undo.** Only while the record's content of the file, or the signed file when the record names none, is the change's `to`: the file goes back to the change's `from`, the entry removed when that is the signed file, the copy holds it, and the change is logged undone. Otherwise `NOT_ALLOWED` names the later change.
- **Discard every change.** `delorun changes edit-harness --discard` asks whether the harness returns to the signed release, logs every pending change discarded and every applied or left-out change whose content the record holds undone, empties the record and removes the copy, its directories made writable first and a link where it was removed, not followed. A copy that cannot be read (`HARNESS_COPY_UNREADABLE` or `CHANGED_WHILE_READING`) does not stop it: the changes waiting there are removed with the copy without being logged, and the command prints why the copy could not be read. The next start runs the signed release unchanged.
- **Apply without review.** With protection off, the start that decides the hand-off below applies every change waiting in the copy without a proof of presence, before it composes the tree (`applyUnreviewedHarnessChanges`): under `harness.lock` it reads the protection setting again and applies nothing when it is on; otherwise each change is stored, its content recorded in `harness/<runtime>/approved.json` and logged applied with `decidedFrom: "unreviewed"`, and the start prints `Delorun itself (<file>) changed without review, because protection is off: delorun changes show <id>`. `list`, `show` and `undo` reach these changes as any other. A copy that cannot be read (`HARNESS_COPY_UNREADABLE` or `CHANGED_WHILE_READING`) applies nothing, and the start prints `Delorun could not read your copy of Delorun <runtime>, so it runs what it ran: <reason>` and goes on.

The composed tree is `harness/<runtime>/run/<digest>/`, `<digest>` the SHA-256 of the canonical list of path and version pairs a start runs: the record's versions, with each change a failed start left out that stays out replaced by its `from`, and an entry dropped when that is the signed file. It is a full tree of the installation: every signed path that is not approved is a hard link to the installation's file (a copy of its verified bytes only where the filesystem refuses the link with `EXDEV`, `EPERM` or `ENOTSUP`), every approved file is written from the store's verified object at 0444 (0555 when executable), removed files are absent, and every directory is 0555 once filled. It is built in a temporary sibling directory and renamed into place under the lock; a path in the way of the build (`ENOTDIR` or `EEXIST`: a file where a directory belongs, or what another builder wrote) refuses the start with `HARNESS_CHANGED` naming that path, for `ENOTDIR` the nearest parent that is not a directory. Each start that builds or reuses a tree sets the tree directory's time under the lock. Before every run it is checked: each signed path that is not approved is the installation's file (the same device and inode, compared as 64-bit integers, or a regular file with the signed length, SHA-256 and execute bit), each approved path a regular file with the approved digest and execute bit, and nothing else exists. A tree that fails is rebuilt once; a second failure refuses the start with `HARNESS_CHANGED` naming the path.

| Step | What happens |
| --- | --- |
| Who decides | Only the signed code: `delorun start --foreground` running from the store's installation, not from a composed tree, for a profile not in safe mode, whose runtime's records compose any file, after it applied the copy's changes without review when protection is off. A profile in safe mode (`run/<profile>/safe-mode.json`) runs the signed installation without any harness change and applies none, until safe mode ends |
| The hand-off | Its first act, before any lock, token or log: the installation's start check, the composed tree built or checked, retention, then the tree's `node` runs the tree's `delorun` entry with the same arguments as a child with this terminal, in this process's process group, descriptor 3 passed on when it is open (an update's successor handover), `SIGTERM` and `SIGHUP` forwarded, and the child's exit code returned. Before the child starts, the hand-off writes `run/<profile>/hand-off-<pid>`, `<pid>` its own process id; every start removes the file its parent process wrote as its first act. A child that exits with a code other than 0 while the file is still there failed before its start ran |
| Which entry | `startEntry` is the one function: the hand-off starts the composed tree's entry; `delorun start` in the background and the retry after a start left a change out start the signed installation's, so the signed code composes again. A background start that hands off waits for the home process the child started, whose process id is not the child's |
| In the composed tree | `runtimeOfFile` maps a file under `harness/<runtime>/run/<digest>/` to the runtime with `store: true` and `composed` set. Update support and the release channel check the signed installation; the fresh start's runtime check and C3's health check H1 check the installation and then the composed tree, which must be the tree the records compose now. The closure's pnpm, its install anchor and Delorun's bundles resolve inside the composed tree |
| Retention | After a hand-off, the runtime's other composed trees are removed, unless a home process of any profile runs, which may run from one, and except a tree whose time a start set within the last hour (`TREE_RETENTION_GRACE_MS`): a concurrent start may have chosen it and not yet started the home process that marks it in use. The `harness/<runtime>/` directory of every runtime the store no longer has installed is removed too. Directories are made writable first. A failure is printed and the next start tries again |

**A bad start.** When the newest decision across the profile's change log and the harness's log for the running runtime is an applied `harness-edit` whose content the record still holds, the start's retry ([When a start fails](#when-a-start-fails)) leaves that change out: its harness log entry becomes `left-out-at-start` with the failure, the profile's files are untouched, the relaunched signed entry composes without it, and the words name it as `Delorun itself (<file>)` with `delorun changes apply <id>` and `undo <id>`. A harness change has no Loader rows of its own; the start's failure decides it.

**A composed tree that fails before its start.** When the composed tree's `delorun` exits with a code other than 0 before its start ran, as when a changed file throws while Node imports it, and the hand-off is not an update's successor's, the signed process does what the composed tree's start cannot ([`retry.ts`](../../apps/cli/src/changes/retry.ts) `retryHandOff`): `leaveOutNewestHarnessChange` marks the runtime's newest harness decision `left-out-at-start` with the failure when it is an applied `harness-edit` whose content the record still holds, whatever the profile's log holds; the words name it as above, and the start runs once more in the same process through the same hand-off, with the retry marker set, which composes without the change or runs the signed installation. A start that already carries the retry marker, or finds nothing to leave out, prints "Delorun did not start with your changes to Delorun itself.", "To undo the newest one: delorun changes undo `<id>`." for the newest applied harness change ("See them with: delorun changes list." without one) and "To start the installed release without any of them: delorun changes edit-harness --discard.", and exits with the child's code. A home process `delorun start` started in the background exits with the left-out code instead, and its starter names the change and starts once more. An update's successor is never retried: the update's health check and rollback decide it, and stopping the successor stops the composed child with it ([C19](c19-home-process.md#the-update-handshake)).

**Across an update.** An update carries the files the running runtime runs other than its signed ones to the runtime it installs, by a three-way merge with the target's signed file, as [C3](c03-update-report.md#harness-files-across-an-update) states: it refuses with `HARNESS_CHANGES_PENDING` while a change waits for review in the copy and with `HARNESS_COPY_UNREADABLE` when the copy cannot be scanned, shows a file merged into content neither side had with its diff and needs the person's confirmation for it, refuses with `HARNESS_REPORT_STALE` when the merge planned again under the harness lock differs from the report the person confirmed, replaces whatever an earlier install left under `harness/<to>/`, writes the target's record with each carried file and logs it as an applied `harness-edit` of the target runtime with `decidedFrom: "update"`, and keeps the person's content of each conflicted file as `<file>.mine` in the target's writable copy. The running runtime's record, copy and log entries stay, so a rollback runs them again. The library is [`harness-merge.ts`](../../packages/changes/src/harness-merge.ts).

**The studio.** The Changes section lists the harness's logged changes with their diff, read from the store, and the terminal command for each decision; no route decides a harness change ([The studio's Changes section](#the-studios-changes-section)).

## Reloads and restores

Every recomposition of the running profile is checked before anything stops: upstream's hot reload awaits the optional `profileReconcileCheck` service in `reconcileProfile`, and `@delorun/plugin-changes` provides it whatever its switch says. That covers `changes.reload`, a work session's reload, the person's plugin changes in the studio (Plugin Manager's install, removal, `set_bundle`, `set_plugin`, `configure`, `set_version_exemption`, `undo` and `restore`), and the profile's own file watch after `delorun plugin` or any edit of `package.json`. The check, `prepareReload`:

1. moves every `link:` dependency that names a folder, a missing one or a file included, as a restore or undo writes back `link:<folder>`, a plugin manager install of a folder writes, and `delorun plugin --profile default add link:<folder>` writes, to the plugin's active directory as a start does; with protection on it logs a pending `plugin-install` unless the folder is the approved one and approves nothing, and with protection off it approves and logs the folder's content as a start does ([Loading without review](#loading-without-review)); it records no history version;
2. makes the active directory of a plugin it moved hold what a start would load, and never rewrites any other;
3. checks the links and active directories as step 4 of [Loading approved content](#loading-approved-content) does, and refuses the recomposition with `LOAD_REFUSED` when one is not what Changes keeps, such as an active directory written between starts. Everything keeps running.

The profile write lock decides whether it may write. When the Host's own process holds the lock, Plugin Manager is changing the profile and reloads inside its lock, so the check writes without taking it. When no process holds it, the check takes it, waiting at most two seconds (`RELOAD_LOCK_WAIT_MS`). When another process holds it, as `delorun changes` does while it waits for the reload's answer and a `pnpm` run does, the check writes nothing and only verifies, so a link to a folder refuses the recomposition until the holder is done.

`delorun plugin` runs the same check in its own process after upstream's operation, whether that succeeded or not, unless the profile's first start under Changes has not run: with protection on, `delorun plugin --profile default add link:<folder>` leaves the plugin linked to its empty active directory and prints `<plugin> is not loaded until you review it: delorun changes show <id>`; with protection off, the active directory holds the folder's content and the command prints `<plugin> loaded without review, because protection is off: delorun changes show <id>`. The command exits 1 when upstream's operation failed or the check refused.

With protection on and `plugin_changes_pending` on, the model's `plugin_manager` calls that would change what runs other than installs and removals do not run ([The agent and plugins](#the-agent-and-plugins)).

## Collecting the store

At the end of each start, under the profile write lock and after the check, `collectStore` removes every version file and object that no profile under Changes references: each profile's approved record, its change-log entries in state `pending`, `applied` or `left-out-at-start` (`from` and `to`), its `active.json` and its work session (`from`, `lastLoaded`, `lastFailed`). A version file written within the last hour (`COLLECT_GRACE_MS`) is kept, so a change computed for review but not yet decided keeps its content. Collection takes the store's lock without waiting and does nothing while another process stores a folder, removes nothing when any of those records cannot be read, stops after two seconds (`COLLECT_TIME_LIMIT_MS`) and leaves the rest for the next start; a failure to remove a file leaves it and the start goes on. Versions referenced only by `discarded` or `undone` entries, or by an older profile history version, are removed, so restoring such a history version loads nothing for that plugin until the person applies a change again.

## The first start under Changes

The first start under Changes of a profile whose log has no `migratedAt` approves every linked plugin as it is, when the profile is one the home held at the first start under Changes of any profile: that start writes `changes/migration.json`, `{"schema":"delorun.changes-migration/1","at","profiles":[…]}`, naming every profile in `profiles/` then, by an exclusive create. Each plugin is stored, recorded with `approvedAtUpgrade` and logged as an applied `plugin-install` decided at `upgrade`; one profile history version records the move. A profile created after that record is new: none of its linked plugins is approved at upgrade. Like a plugin linked after the first start, each is a pending `plugin-install` change that loads nothing until applied with protection on, and loads without review with protection off.

Each start names the plugins approved at upgrade until a terminal showed them: the entry gains `shownAt` only when the start's output reached a terminal (`delorun start` runs the home process with its output in the log only) or `delorun changes list` printed them at one. Until then `delorun status` and `delorun changes list` name them too.

## The protection setting

`changes/protection.json` holds `on` or `off`; a home without the record is `off`, the default, and review is something the person turns on. Only a terminal proof changes it: `delorun changes protection on|off` ([Commands](#commands)), or setup's Full mode, which only turns it on ([C11](c11-setup-answers.md)); turning it off is logged in the profile's change log as an applied `guard-weakening` change with `subject.setting` `protection` and the summary `Protection turned off: changes load without review`. Every decision that depends on the setting reads it when it decides: a start, the check before a reload, the home process's watcher, the start's harness step and `@delorun/plugin-changes` at each `plugin_manager` call. A change of the setting takes effect at the next decision, without a restart.

- **Protection off.** Changes load without review and are still recorded ([Loading without review](#loading-without-review)). Any writer of a linked plugin's folder, or of the harness's writable copy, changes code the harness loads without anyone reviewing it first: a model working in a full-access workspace, a downloaded program, or any other process of the person's user. Each such change is an applied change in the log, which `delorun changes list`, `show`, `verify` and `doctor` name and `undo` takes back. What stays protected: a confined workspace's commands and file-tool writes still go only where the sandbox allows, and a confined command still cannot write the Delorun home (`~/.delorun`), `changes/` and the harness's writable copy included ([C1](c01-home-layout.md#security)); a plugin folder the sandbox lets a confined workspace write, such as one inside that workspace, loads what it writes without review. A file tool's write into the profile's active directories is refused in both settings ([The agent and plugins](#the-agent-and-plugins)).
- **Protection on.** A changed plugin loads its approved content until the person applies the change, and a plugin with no approved content loads nothing; a harness edit runs only once applied; the agent's plugin installs and removals wait for the person; and the agent's first file-tool write in a chat to an approved plugin's folder asks ([The agent and plugins](#the-agent-and-plugins)). The terminal check and the sandbox's home-write rule keep a confined model from turning protection off or approving a change ([Who may do what from where](#who-may-do-what-from-where)).

A changed file of the signed installation is refused by the runtime store's start check in both settings; a home process started from the store checks its runtime at a fresh start as the launcher does. A person's edit of a harness file runs only as an applied harness change, from the composed tree ([Harness edits](#harness-edits)), in both settings.

### Loading without review

With protection off, Delorun approves content without review at these points only, and each writer reads the setting again under the profile write lock, or `harness.lock` for the harness, and writes nothing when it is on ([`unreviewed.ts`](../../packages/changes/src/unreviewed.ts)):

- **At each start.** The pre-start step stores each linked plugin's folder. When its content differs from the approved content, it becomes the approved content in the profile's `delorun.changes` record and `active.json`, and the log gains an applied `plugin-edit`, or a `plugin-install` for a new link or a plugin with no approved content, with `decidedFrom: "unreviewed"` and a summary starting `Loaded without review:`. A start that changed anything records one profile history version whose subject names the plugins, such as `Changes: loaded without review my-plugin, other-plugin`, and prints for each `<plugin> loaded changes without review, because protection is off: delorun changes show <id>` (`<plugin> loaded without review, …` for an install). `delorun headless` does the same in its pre-start step.
- **Before a reload.** A link the check before a reload moves, as a plugin manager install of a folder, `delorun plugin --profile default add link:<folder>` or a restore writes it, is approved and logged the same way, without a history version ([Reloads and restores](#reloads-and-restores)).
- **While Delorun runs.** The home process watches the folder of every plugin the profile links to its active directory, recursively and without `.git`, and follows `changes/protection.json` and the profile's `package.json`, so turning protection on or off and linking or removing a plugin change what it watches without a restart; with protection on it watches no folder. Once a folder's events have been quiet for 300 milliseconds it loads the folder's content through the same Host reload as `changes.reload` ([`unreviewed-watch.ts`](../../apps/cli/src/changes/unreviewed-watch.ts)). A successful reload approves the content and logs one applied change decided `unreviewed` with one profile history version. A failed reload goes back: the approved record, the active directory and `active.json` hold what they held, a history version `Went back: <id> failed to load` records it, the Host reloads once more, and the change is `pending` with `lastFailure` and is not tried again until the folder holds other content. The home process's log names each load and failure. No work session is needed; a plugin in a work session is left to the session, and `delorun headless` does not watch folders.
- **The harness's writable copy.** The signed installation's start applies the copy's changes ([Harness edits](#harness-edits)).

Content the person declined does not load again: when the newest decided content change of a plugin (`plugin-edit` or `plugin-install`, not an agent's request) was undone or discarded and brought exactly what the folder holds, the plugin keeps its approved content and the folder's content waits for review as with protection on, until the folder holds something else. A change a failed start left out stays out while the folder still holds what it brought ([When a start fails](#when-a-start-fails)); new folder content loads and ends it.

## Work sessions

A work session loads one approved plugin's folder live while the person works on it, for at most 480 minutes, with protection on or off; with protection off, the plugin it covers is left out of [Loading without review](#loading-without-review) while it lasts. Its record is `{"schema":"delorun.changes-work-session/1","plugin","source","from","startedAt","startedFrom":"terminal"|"studio","endsAt","lastLoaded"?,"lastFailed"?}`: `from` is the approved content when it started, `endsAt` when it ends without the person, `lastLoaded` the folder content that last loaded, and `lastFailed` folder content whose reload failed after that. One session at a time per profile; opening is an exclusive create.

- **What loads.** The plugin still loads from its active directory. Each load stores the folder's content, makes the active directory hold it with `active.json` kind `work-session`, replacing only the files that differ, and asks the running Host to reload as `changes.reload` does. A success records `lastLoaded` and removes `run/<profile>/changes-work.json`.
- **Live reload.** The home process watches `work-session.json` and, while a session is open, the plugin's folder recursively without `.git`, and loads each change once events have been quiet for 300 milliseconds. Delorun watches the folder itself instead of setting upstream's `hmr.root`, because the Host loads the plugin from its active directory, so a source watch of the folder would watch files that are not loaded. Folder content that is already active, or equals `lastFailed`, is not loaded again, and nothing loads once `endsAt` has passed.
- **Opening.** `startWork` takes the session's length, whole minutes from 1 to `WORK_SESSION_MAX_MINUTES` (480), and refuses any other with `NOT_ALLOWED` before it reads anything; it needs a plugin the profile loads from its active directory with approved content and whose folder exists (`NOT_LINKED` otherwise), opens the record with `endsAt` that many minutes after `startedAt` (`WORK_SESSION_OPEN` when one is open) and loads the folder's content at once. When Delorun is not running for the profile, it closes the session again, puts the active directory and `active.json` back, and refuses with `NOT_ALLOWED`.
- **The length.** `delorun changes work <plugin> --for <minutes>` sets it, 120 minutes when `--for` is absent; a value that is not whole minutes from 1 to 480 is a usage error. The length is an option of the command rather than a configuration field, because the CLI's home process runs the session and no validated configuration of the CLI's own settings exists for a profile.
- **A failed reload goes back.** The active directory holds `lastLoaded` again, or `from` when nothing loaded yet, the Host reloads once more, the record notes `lastFailed`, and `run/<profile>/changes-work.json` is written: `{"schema":"delorun.changes-work/1","plugin","at","error"}`, a protected file that `delorun doctor` and the studio read and nothing decides from. The session stays open.
- **Ending at the person's word.** `reviewWork` stores the folder's content and returns it with its difference from `from`; `delorun changes done` prints its first 7 digits, its files, the risk summary and the bounded diff, every line through the terminal escaper, asks, and asks a second time naming the kinds when a check found something. `finishWork` then approves exactly the content it was given: when the folder holds anything else, the folder gone included, it refuses with `CHANGED_SINCE_REVIEW`, approves nothing and leaves the session open. When the active directory does not hold that content yet and Delorun runs, it loads first, and a load that goes back approves nothing and leaves the session open. A folder that is gone keeps `from`. When the approved content changed, one profile history version `Work on <plugin>: <first 7 digits of from> → <first 7 digits of the new version>` records it, and the log gains one applied `plugin-edit` change from `from` to the new version with that summary, created at `startedAt`. `active.json` records the content as `approved`, and the record and `changes-work.json` are removed.
- **Ending without the person.** The Host's `close` stops the watcher and ends the open session; a start of the home process that finds a session open, which a home process that did not stop left, ends it first and says so, and `delorun headless` leaves it alone until its `endsAt`; any start that finds a session past its `endsAt` ends it before it loads anything from the folder and says so; the watcher ends a session at `endsAt` and logs that it ended at its time limit. Each goes through `finishWorkWithoutPerson`, the separate entry `@delorun/changes/stop`, and approves nothing: the approved content stays `from`, the active directory holds it again with `active.json` kind `approved` (at `endsAt` the running Host reloads), the record and `changes-work.json` are removed, nothing is logged and no history version is recorded, and the folder's content is the ordinary pending `plugin-edit` against `from`, which with protection off loads without review at the next start or save. The folder is not read, so an unreadable folder never keeps a session open.
- **Where it shows.** `delorun status` prints `work session: <plugin> since <startedAt>, ends at <endsAt>`, `delorun changes list` prints `Working on <plugin> since <startedAt>, until <endsAt> at the latest: edits in its folder load live.`, and `workSessionFact` gives the same for the studio.

## When a start fails

A start that fails right after a change starts again without that change, and the profile's files are not rewritten for it ([`left-out.ts`](../../packages/changes/src/left-out.ts), [`retry.ts`](../../apps/cli/src/changes/retry.ts)).

| Step | What happens |
| --- | --- |
| Which starts | A fresh start of the home process: never an update's or a rollback's successor, never the second start itself, and not `delorun headless` |
| What counts as failing | Upstream's profile runner throws; the booted Host is refused (a row of a Delorun bundle did not activate, or an invariant of the composition does not hold); or an enabled row of the plugin of the change it may leave out did not activate |
| Which change | The newest decision that changed what runs (`applied`, `undone` or `left-out-at-start`, by `decidedAt`, then by its place in the log), when it applied a `plugin-edit`, `plugin-install`, `plugin-update` or `plugin-on` the person made or Delorun loaded without review, not an approval at upgrade, to a plugin linked to its active directory whose active directory holds approved content, for a change of content the change's `to`, which is also the approved version. Otherwise the start fails as before, so a run of failures leaves out one change at most |
| Leaving it out | `leaveOutNewestChange` writes only the change log, under the profile write lock: the entry becomes `left-out-at-start` with `decidedAt`, `decidedFrom: "start"` and `leftOut {at, failure}`, the error's message without a stack, at most 2 KiB of UTF-8. It needs no proof of presence; only `apps/cli/src/changes/retry.ts` names it, and `leaveOutNewestHarnessChange`, outside the package |
| The second start | A new `delorun start --foreground` process with `DELORUN_CHANGES_RETRY=1`: in the terminal, the first process prints the words and runs it with the same terminal, passing on `SIGTERM` and `SIGHUP`, and exits with its code; `delorun start` in the background marks its child `DELORUN_CHANGES_STARTER=detached`, which exits with code 4 instead, and starts it once more. Both markers are removed from the home process's environment. The second start never leaves a change out |
| What every later start loads | Its pre-start step `changes` makes the plugin's active directory hold the change's `from` with `active.json` kind `left-out`, or nothing (no `version`) for an install or a plugin turned on, until the person applies the change again or undoes it, or the approved version is no longer the change's `to`; with protection off, only while the plugin's folder still holds the change's `to` or is gone, or the change turned the plugin on, so new folder content loads without review and ends it. A work session on the plugin loads its folder as before |
| What the person reads | "Delorun did not start with your latest change to `<plugin>` (`<id>`): `<failure>`." / "It starts without it now; your files are unchanged." / "To try it again: delorun changes apply `<id>`. To undo it: delorun changes undo `<id>`.", the failure on one line and cut at 200 characters, at the failed start and at every later start; a second failure prints "Delorun did not start again. Start without third-party plugins: delorun recover safe-mode, then delorun start." |
| Applying it again | `apply <id>` makes the active directory hold the approved content again, which is the change's `to`, and the entry `applied`; a failed reload keeps it left out with `lastFailure` |
| Undoing it | `undo <id>` undoes it as an applied change: the approved version goes back to `from`, or none for an install; a `plugin-on` turns the plugin off |

With protection on, the invariants accept `left-out` content holding a version only when a change left out of the plugin that stays out holds that version; `left-out` content holding nothing loads nothing and is always accepted. `delorun changes list` names each change that stays out in its own group, `delorun doctor` names the plugin, the change and the failure with both commands, and `leftOutFacts` gives the same for the studio.

## The risk summary

Nine built-in checks read the new and changed lines of a change and its `package.json` on both sides: registers or replaces a consent, guard or the sandbox policy; adds a listener that answers approval prompts (`answers-approvals`); installs, removes or loads plugins itself (`manages-plugins`); adds a tool the model can call; runs commands; opens network connections; reads under the Delorun home; adds or changes a dependency or a build or install script; has content the diff does not show (`not-shown`). `not-shown` names each added or changed file whose lines the diff leaves out: a binary file whose name ends in an extension Node loads (`.js`, `.jsx`, `.mjs`, `.cjs`, `.ts`, `.tsx`, `.mts`, `.cts`, `.json`, `.node`, `.wasm`), a text file above 1 MiB, a text file past where the diff reached 256 KiB, and, once per package, the files below a `node_modules` directory inside the folder. Any finding asks a second confirmation before applying, and the second question lists each `not-shown` file. The summary is heuristics, a help to the reader and not a protection: plugin code has the harness's full authority. `reviewChange(input, checks)` is the one function a later extension point extends with registered checks.

## The agent and plugins

Two behaviours in Delorun's composition decide what the agent may do to the plugins the harness runs. Each sits behind its own [C16](c16-parity-composition.md) switch, on in the composition a person runs and off in the parity composition, where the agent's writes and `plugin_manager` calls run as upstream runs them. Each reads the protection setting at every call and holds or asks only with protection on.

- **Writes to an approved plugin's folder ask once per chat with protection on** (switch `approved_plugin_write_consent`, `@delorun/plugin-instruction-consent`'s `approvedPluginWrites`). With protection on, before the agent's first write in a chat to the `source` folder of a plugin the profile approved, the person is asked: "The agent is changing what your harness runs: <plugin>. The change will wait for your review in Changes.", with the diff the tool carries. The protection setting and the folders are read from the home and the profile the Host runs at every write. A write is compared on the path the file backend writes, the target's `targetKey`, which upstream's local backends set to the real path (the file's own, or for a file that does not exist yet its deepest existing ancestor's with the rest appended); the folder's real path is computed the same way. The target counts as inside the folder when that path or its lexical path lies at or below the folder, ignoring case when a probe of the folder's own path in another case finds the same directory on its volume, or when an existing ancestor of the target is the folder's directory (the same device and inode), so a symbolic link, a `..` after a link and a case variant into the folder ask too. A write through a dangling link asks nothing: the backend keys it by the link's own path and refuses it as no regular file. After the person allows it, later writes to that plugin's folder in the same chat pass until the Host restarts; another chat asks again. A refused, cancelled or unanswerable ask leaves the file unchanged, and the model reads the typed refusal `FS_CONSENT_DENIED`, such as `the user refused the write to "<path>", which changes the plugin <plugin>; it stays unchanged, so stop and explain instead of working around it`. A protection or profile record that cannot be read refuses the write. A file tool's write into the profile's active directories (`changes/profiles/<profile>/active/`) is refused without asking in both settings, approved plugin or not, because only Changes writes there and such a write would never become the person's plugin; the model reads `FS_CONSENT_DENIED` with `the write to "<path>" was not run: it is inside the directory Changes loads the harness's plugins from, which only Changes writes, …; change the plugin's own folder instead`. The writes the person allows are pending changes like anyone's and load only when the person applies them, or live during a work session. With protection off, no write to a plugin's folder asks, and what the agent writes there loads without review as any folder content does ([Loading without review](#loading-without-review)).
- **Shell writes are not asked.** Only the file tools' writes are reviewed. A shell command or a PTC script the sandbox lets write a plugin's folder changes it without asking; with protection on that change is a pending change that does not load until the person applies it, with protection off it loads without review at the next start or, while Delorun runs, when the folder settles, and during a work session for that plugin it loads live, because the person opened the work session.
- **The agent's plugin installs, updates and removals wait for the person with protection on** (switch `plugin_changes_pending`, `@delorun/plugin-changes`). With protection on, a `plugin_manager` call whose action is `install_bundle` or `remove_bundle` does not run and never reaches the tool's full-access approval: it is recorded in the change log as a pending `plugin-install`, `plugin-update` (an install of a registry version of a plugin the profile has; the tool has no update action) or `plugin-remove` with `subject.spec` and, when the spec names it, `subject.plugin`, and the model reads `Recorded as a change waiting for the person's review at their computer: delorun changes show <id>. Nothing was installed.` (for an update `Nothing was installed or updated.`, for a removal `Nothing was removed.`), with the error code `PLUGIN_CHANGE_PENDING`. A call that names no target, a spec pnpm would not accept, a removal of a name that is no dependency, or a log that cannot be written is denied with `PLUGIN_CHANGE_UNRECORDED` and records nothing. Repeating a request that still waits returns its id; a repeat of a decided one is a new change. A call whose action is `set_bundle`, `set_plugin`, `configure`, `set_version_exemption`, `undo` or `restore` does not run either and records nothing: the model reads that the person makes that change at their computer, in the studio or with `delorun plugin`, with the error code `PLUGIN_CHANGE_AT_COMPUTER`. With protection off, every such call runs as upstream runs it, with the tool's own full-access approval alone deciding, except that a chat never starts a plugin that is not running, at any protection level: an install is recorded, and a turn-on (`enabled` anything but the boolean `false`), an `undo` and a `restore`, which can bring a plugin back, are denied with `PLUGIN_CHANGE_AT_COMPUTER`: an install from a folder comes under Changes at the recomposition it causes, where the check before a reload links the plugin to its active directory and logs the folder's content as an applied change decided `unreviewed`, and a registry install or a removal is recorded only in the profile history upstream writes. A protection record that cannot be read denies every such call, naming that the setting cannot be read. A tool guard denies any such call the plugin's listener did not handle, so a `tools/pre-execute` listener that allows the call without calling `next()` cannot run it; a call the listener passed on with protection off counts as handled. The CLI profiles mount the plugin through `@delorun/bundle-local`'s `delorun-plugin-changes` row, and `delorun headless` through `@delorun/bundle-headless`'s row of the same id, both protected from the `plugin_manager` tool; the headless profile serves no studio, so no Changes route is registered there, and its approval of the agent's first write to an approved plugin's folder is refused because no one answers it.

Applying such a change, at a terminal or in the studio at the computer after a second confirmation ([Routes and the recovery screen](#routes-and-the-recovery-screen)), runs upstream's profile plugin operation `runProfilePnpm` under the profile write lock, as the plugin manager's `installBundle` runs it, with the checks `installBundle` runs: `add <spec>` for an install or update, `remove <name>` for a removal, which also removes the plugin's approval. A spec that names a folder, a path, `file:<path>`, `link:<path>`, `<name>@file:<path>` or `<name>@link:<path>`, is never linked to the folder: the plugin is linked to its active directory, which holds nothing, and the folder's content is recorded as a pending `plugin-install` from that folder, applied like any other, so with protection on nothing the agent asked for loads before the person reviewed its content, and with protection off it loads without review as [Loading without review](#loading-without-review) states; `<name>` must be the package the folder holds. A `<name>@<range>` spec whose range is no registry version, range or dist-tag and no such folder, such as `workspace:`, `npm:`, a git or URL source or a path, is refused with `INVALID_REQUEST` when the agent asks and when it is applied, because pnpm installs it from that source while upstream's parser reads it as a registry install.

| `installBundle` step | Applying the agent's request |
| --- | --- |
| pnpm runs with no terminal and a scrubbed environment (`execution: 'service'`), with no option that allows a build script | The same: `execution: 'service'` and no build option, so the profile's `pnpm-workspace.yaml` `allowBuilds` entries alone decide which scripts run and pnpm cannot ask |
| Builds are approved only when the person passes the pending names (`approvedBuilds`) | Nothing approves a build; the person decides by editing `allowBuilds` |
| A failed run records the build scripts pnpm reports blocked as `set this to true or false` (`recordPendingBuilds`) and returns them | The same function records them, and the change's `lastFailure` names each with where to decide it |
| A failed run puts `package.json` and `pnpm-lock.yaml` back; downloaded files stay | The same files go back after any failed or refused operation |
| `runProfilePnpm` refuses a version incompatible with this Delorun or DSH before or after pnpm runs | The same function, and the failure names the version; for a folder spec, whose link holds nothing yet, the folder's `package.json` is checked with upstream's `evaluatePluginCompatibility` and the profile's exemptions before pnpm runs |
| An install that changes more than one dependency (`ambiguous-install`), or a package without `dsh.bundle.patch` (`not-bundle`), is refused | The same refusals, after which the files go back; a folder spec's package must declare `dsh.bundle.patch` |
| The optional `pluginAudit` service audits the bundle when the profile mounts one | Not consulted: no Delorun composition mounts one ([C13](c13-catalogue-revocation.md)) |
| Registries asked in the plan order (`registryPlan`), a GitHub connection check and a Git transport choice | pnpm's own configured registry and transport only; these steps decide where a package is fetched from, not whether it runs |

At a terminal pnpm's output goes to the command's streams; in the studio the Host runs the operation from its own directory with the profile launcher's pnpm, its output in the Host's log. A failed or refused operation leaves the change pending with `lastFailure`; a successful one records one history version `Applied <id>: …` and reloads a running Host, whose failure leaves the change applied for the next start.

The model reads only the tool results above, each logged as the tool call's result like any other, so neither behaviour adds a session event; the asks are logged as upstream's `approval/asked` and `approval/decided`.

## Who may do what from where

| Action | Allowed from |
| --- | --- |
| Turn protection on or off | `delorun changes protection on\|off` at a terminal only, and setup's Full mode, which only turns it on, through the same terminal proof; no studio route changes it |
| Apply, discard or undo a change; turn one plugin off or on | `delorun changes` at a terminal, or the studio at the computer ([Routes and the recovery screen](#routes-and-the-recovery-screen)) |
| Make the harness's writable copy; apply, discard or undo a harness change; discard every harness change | `delorun changes` at a terminal only, from an installed release; no studio route and no model tool decides one |
| Open or close a work session | `delorun changes work` and `done` at a terminal, or the studio's `work` and `done` routes at the computer; Delorun stopping, a start after a crash and the session's end time close one without a person, approving nothing |
| Start safe mode | `delorun recover safe-mode`, or the recovery screen at the computer |
| Read changes | The person's own commands, and any session the studio admits, a remote one included |
| Leave a change out | A fresh start whose boot failed ([When a start fails](#when-a-start-fails)), with no proof of presence; it writes only the change log |
| Load content without review | With protection off only: a start's pre-start step and the check before a reload for plugin folders, the home process's watcher for saves while Delorun runs, and the signed installation's start for the harness's writable copy ([Loading without review](#loading-without-review)), each with no proof of presence |

A proof of presence is issued only by `attestTerminal` (standard input and output are terminals) and `attestStudio` (a studio request at the computer, which only the studio's Changes routes call), and a writer refuses any value they did not issue. The protection setting's writer also refuses a studio proof.

The terminal check does not tell a person from a model: a model's terminal tool gives its commands a real pseudo-terminal. Two rules together keep a model in a confined workspace from turning protection off or approving a change: the terminal check, and the sandbox's home-write rule, under which a confined command can write nothing under the Delorun home, `changes/` included, and a workspace that contains the home is refused ([C1](c01-home-layout.md#security)). A workspace with full access runs commands with the person's own authority: a model working there can turn protection off and approve changes, as the person can, and with protection off its writes to a linked plugin's folder load without review. Fundamental [F16](../security/fundamentals.md) therefore stays designed: as worded it also covers full-access workspaces, which nothing here prevents, and it applies when protection is on.

## Routes and the recovery screen

`@delorun/plugin-changes` registers the studio's Changes routes with the web server once the web server and Connection are present, whatever its switch says, and names their prefix to the boot page through the index global `dshRecoveryRoutes`.

| Route | Who | What it does |
| --- | --- | --- |
| `GET /delorun/changes/state` | Any session the studio admits, a remote one included | From the records only, writing nothing and reading no plugin's folder: what failed at the last start (`changes-boot.json`), the changes left out at a start with the failure each start recorded (`leftOut`), the plugins under Changes with their folders (`folders`, `plugin-install` while nothing of the plugin is approved), the agent's requests waiting for review, the 20 newest decided changes with whether each can be undone, the 20 newest decided changes to Delorun itself from the harness's log (`harness`: id, state, file, runtime, summary, times and a left-out failure), the protection setting, safe mode, the work session, a sentence per record that cannot be read, and `atComputer` |
| `GET /delorun/changes/show?id=<id>`, `?work=<plugin>`, `?pending` | The same | One change: its plugin, folder, files, risk summary and bounded diff, or its log entry; for an id no plugin change has that the harness's log has, the entry with the files, risk summary and bounded diff of its two versions, without them when collection removed a discarded or undone change's content; the open work session's folder version against the content it started from; or every change waiting for review in the plugins' folders with its file count, risk kinds and last failure. Each reads the folders it names and stores their content, as `delorun changes list` does |
| `POST /delorun/changes/apply`, `discard`, `undo` | The studio at the computer | `{ "id", "confirmedRisk"? }`: as `delorun changes`; `apply` answers `409 CONFIRM_RISK` with the kinds and each file the diff does not show until `confirmedRisk` is `true`, and for an agent's plugin request answers `409 CONFIRM_RISK` naming its spec, whose content Delorun does not show before pnpm resolves it, until `confirmedRisk` is `true`, then applies it as [The agent and plugins](#the-agent-and-plugins) states and answers the entry, how the running Host reloaded and, for a spec that names a folder, the change that holds the folder's content; each refuses an id the harness's log has with `409 DECIDE_AT_TERMINAL` and `delorun changes apply\|discard\|undo <id>` before any action runs, and no route calls a harness action |
| `POST /delorun/changes/off`, `on` | The same | `{ "plugin" }`: turns the plugin off or on |
| `POST /delorun/changes/work`, `done` | The same | `work` takes `{ "plugin", "minutes"? }`, 120 minutes by default; `done` takes `{ "plugin", "version", "confirmedRisk"? }`, the version `show?work=` showed, refuses another with `409 CHANGED_SINCE_REVIEW` and asks the second confirmation as `apply` does |
| `POST /delorun/changes/safe-mode` | The same | `{}`: profile safety's safe mode with the `installationBundles` of the plugin's row, Delorun's profile bundle list; without one, `503 SAFE_MODE_UNAVAILABLE` names `delorun recover safe-mode` |

No route changes the protection setting; `state` names it read only, and the studio says from it whether changes load without review. Every request is first admitted by Connection, the Host/Origin fence and then the studio's signed cookie or the `authenticator` provider: a request without the credential is answered `401 NOT_SIGNED_IN` or `403 FORBIDDEN` and nothing else runs. A `POST` then needs the person at the computer, decided before the body is read: the request arrived under a `Host` that names a loopback authority, carried the credential, and Connection's `isReachPeer` does not name its session. The gate rests on those two checks: every reach listener refuses a `Host` other than its own address, which is never a loopback one, and `isReachPeer` names every session a reach dispatcher admitted. The routes also read the listener stamp `REQUEST_LISTENER` of `@delorun/home`, which `home-auth`'s authenticator sets on every request a reach listener admits, and refuse a request stamped with another listener. A Connection without `isReachPeer` registers no route. No session factor exists yet, and a later change to reach replaces this with the session factor. Any other request is answered `403 LOOPBACK_REQUIRED` with "This needs you at your computer.". A browser request another site sent, by `Sec-Fetch-Site` or by an `Origin` that is not the request's own loopback origin, is answered `403 CROSS_SITE`, also before the body is read. The body is then one JSON object of at most 16 KiB with only the fields above, and the route attests the request with `attestStudio`. An action that changes what the Host runs reloads it in the Host's own process with `reloadProfile` and the Host's hot reload. Answers are JSON with `cache-control: no-store`, with person-facing fields only: no path under the home and no content version except the one `done` approves; file names, diffs and failures are JSON strings. A refusal whose words name the Delorun home answers its code with "Its details name files Delorun keeps; the Host log has them.", a part of `state` that cannot be read for such a reason names the part with that sentence, and the Host log keeps the words; a recorded failure's text (a failed load, start or reload) names the home as `<Delorun home>`. A refusal of Changes keeps its code, with 404 for `UNKNOWN_CHANGE`, 403 for `NOT_AT_COMPUTER`, 500 for an unreadable record and 409 otherwise.

The recovery screen is part of upstream's boot page and needs no client plugin. On a page whose index names `dshRecoveryRoutes`, it shows below the failure report when a client entry fails to load or activate or the boot throws before the studio mounts, when the studio has not mounted 30 seconds after the boot began, and at `/recovery`, which upstream's frontend-static server renders as the index behind the same fence only while an index injection row names `dshRecoveryRoutes`, and otherwise answers as any missing path; there the boot page loads no client plugin. It reads `state` and shows what failed, the plugins of the last start with Turn off, the recent changes with Undo where one can be undone, and Start in safe mode; each action asks the browser's confirmation and posts to its route. A remote session reads the screen and is told "This needs you at your computer." when `atComputer` is false and when an action is answered `403 LOOPBACK_REQUIRED`. Its words are English or Chinese by the browser's language, it builds its elements with DOM text only, so it runs under the reach listener's Content Security Policy and Trusted Types, and it is a labelled region with a heading that takes focus, an alert for refusals and a polite status for results.

## The studio's Changes section

The browser half of `@delorun/plugin-changes` (`@delorun/plugin-changes/client`) registers the `settings.section` `delorun-changes`, a `shell.overlay` toast and the `sidebar.footer.action` `delorun-changes.work-badge`; the `delorun-plugin-changes` row loads it, so the parity composition, which disables that row, shows none of them. It reads and acts only through the routes above, with the paths and fields of [`src/wire.ts`](../../packages/plugin-changes/src/wire.ts), and reads `state` when it loads, after each action and every 15 seconds while the page is visible; it reads the plugins' folders through `show?pending` when the section opens, after each action and when the person chooses Read the folders again, never on the 15-second read.

- **What it shows.** The work session, the changes left out at a start with the failure the start recorded, the changes waiting for review with their folder, file count and risk kinds, the agent's plugin requests with Apply and Discard, the recent changes with Undo where one can be undone, the group "Changes to Delorun itself" with each logged harness change's file, state, time and version, a read-only Review of its diff and the terminal command that decides it (`delorun changes list` names the ones waiting in the copy), each record that cannot be read, safe mode, a failed last start, and the protection setting read only, with `delorun changes protection on|off` and no control; with protection off a note says that changes load without review and that a linked plugin reloads live each time it is saved.
- **Review and Apply.** Review reads `show?id=` and shows the folder, the files with their status, the risk kinds with the places each check found, the fixed sentence "This summary is a help to read the change, not a protection: a plugin's code can do anything Delorun can.", each file the diff does not show, the paths the scan could not include, and the bounded diff with the files it left out, all as text. Apply posts `{ id }`; when the route answers `409 CONFIRM_RISK`, a second dialog names each kind and each file the diff does not show from that answer and repeats the sentence, and only its Apply anyway posts `confirmedRisk: true`. Discard posts from the review. Apply on an agent's plugin request asks a confirmation naming the request, posts `apply`, and asks the second confirmation the route answers for every request, which says Delorun cannot show what it installs before it runs.
- **Undo, Apply again, Start working.** Each asks a confirmation first. Apply again posts `apply` for a change left out at a start, and Undo posts `undo`; Start working posts `work` with the route's default length for a plugin of the last start.
- **Done.** Done reads `show?work=<plugin>`, shows the folder's version by its first 7 digits with its difference from the content the session started from, and posts `done` with exactly that version; a flagged version asks the second confirmation as Apply does. A folder that is gone offers no approval.
- **Not at the computer.** When `state` says `atComputer: false`, or an action is answered `403 LOOPBACK_REQUIRED`, the section shows "This needs you at your computer." and disables every action; Review still reads.
- **The badge.** While `state` names a work session whose `endsAt` has not passed, the badge names the plugin at the sidebar's foot, a dot with the same words as its tooltip in the narrow rail; it is gone once `state` names none.
- **Outcomes.** Each action's outcome is a toast that outlives the Settings dialog: applied, discarded, undone, Delorun not running, a reload that went back with its failure, a folder changed since review, a refusal with its sentence, and no answer. Every copy is in English and Chinese dictionaries.

## Commands

`delorun changes` is the terminal's way to the actions of `@delorun/changes` (`listChanges`, `showChange`, `applyChange`, `discardChange`, `undoChange`, `turnOff`, `turnOn`, `changeProtection`, `startWork`, `finishWork`).

| Subcommand | What it does |
| --- | --- |
| `list` (the default) `[--json]` | The changes waiting for review, computed from each folder now, and the agent's plugin requests waiting for review (`requests`, marked `asked in a chat`), then the changes a failed start left out that stay out (`leftOut`), then every other logged change newest first, each plugin whose folder is gone, the protection setting and any work session |
| `show <id> [--diff] [--json]` | One change: the plugin, its folder, its files with dependency files grouped, the risk summary's lines and, with `--diff`, the bounded diff, saying when it was cut short |
| `apply <id>` | The plugin's approved content becomes the version the id names; `CHANGED_SINCE_REVIEW` when its folder holds anything else. For an agent's plugin request, upstream's plugin operation runs for its spec ([The agent and plugins](#the-agent-and-plugins)); `OPERATION_FAILED` when it fails. A change left out at start loads again ([When a start fails](#when-a-start-fails)) |
| `discard <id>` | The change becomes `discarded`: it never loads and is not listed while the folder holds that content; the folder is never written |
| `undo <id>` | An applied plugin change, or one left out at start: the approved content goes back to the change's `from`, or the plugin has none after undoing its install, and its active directory holds that; with protection off, the folder's content it undid does not load again until the folder holds something else ([Loading without review](#loading-without-review)); a `plugin-off` turns the plugin on and a `plugin-on` turns it off; `NOT_ALLOWED` when a later change of the plugin was applied, and for the other kinds |
| `off <plugin>`, `on <plugin>` | The package name leaves, or is appended to, `dsh.profile.bundles` in the profile's `package.json`, as upstream's plugin manager writes it; `NOT_ALLOWED` for `@delorun/bundle-local` and for a plugin the profile does not have in that state |
| `protection [on\|off]` | Prints the setting and what it means, or changes it after saying what the new setting means and asking; turning it off is logged as an applied `guard-weakening` change ([The protection setting](#the-protection-setting)) |
| `work <plugin> [--for <minutes>]` | Opens a work session lasting `--for` minutes (120 by default, at most 480) and prints `Working on <plugin>: edits in <folder> load live until delorun changes done <plugin>, at the latest until <endsAt>.`; when the folder's content fails to load at once it also reports the failure and exits 1 with the session open |
| `done <plugin>` | Prints the folder's version, its files, the risk summary and the bounded diff against the approved content, asks (twice when a check found something), and approves exactly that version; `CHANGED_SINCE_REVIEW` when the folder changed meanwhile, and exits 1 with the session open when the version fails to load |
| `edit-harness [--discard]` | Creates the writable copy of the running runtime's `app/` directory and prints its folder, or prints it and changes nothing when it exists; `--discard` asks, then discards every harness change of the running runtime ([Harness edits](#harness-edits)). Refused in a source checkout, which has no installed release to change |

`list`, `show`, `apply`, `discard` and `undo` reach a harness change by its id after no plugin change has it: `list` names each waiting one as `<id>  Delorun <runtime> itself: <file> (<status>)`, then the harness's left-out and logged changes, the copy's folder, its skipped entries and the files kept beside; `show --diff` prints the bounded diff over the two one-file versions, the file counting as the harness's own, not a dependency's, though it lies below `node_modules`. A copy that cannot be read, such as one over the scan's limits, is named in the list instead of failing it.

- **Presence and confirmation.** Every subcommand that changes something first needs standard input and output to be terminals and otherwise refuses with "This needs you at your computer: run it in a terminal." before it reads or writes anything. It then asks a yes-or-no question; anything but `y` or `yes` changes nothing. `apply` first prints the change's summary and risk lines and the bounded diff, a page at a time at a terminal (Enter for the next page, `a` for the rest), and when the checks flagged the change asks a second question naming the kinds and each file whose content the diff does not show. `protection off` first says "Changes will load without your review." and what off means, and `protection on` says "Changes will wait for your review." and what on means; both then ask, and the command says it takes effect at Delorun's next decision, without a restart.
- **One history version.** Each action runs under upstream's profile write lock and records one profile history version (`kind: person`) whose subject names the change id: `Applied <id>: …`, `Undid <id>: …`, `Turned off <plugin> (<id>)`. Discarding and the protection setting change no profile file and record none.
- **Reloading a running Home.** When the profile's home process answers, the action runs under the profile write lock and then sends [C19](c19-home-process.md)'s `changes.reload`, which carries nothing: the Host recomposes the profile through upstream's hot reload. The reload fails when hot reload is off, a plugin fails to load or start, or the change needs a restart. When no home process answers, the command holds the profile's home lock for the action, so no start runs meanwhile, and the next start loads the change.
- **A failed reload goes back.** The approved record, the plugin's active directory and `active.json`, or the bundle list, return to what they held before the action; a second history version `Went back: <id> failed to load` records it; the entry returns to `pending`, or for an undo stays `applied`, with `lastFailure` `{at, failure}`; the Host is reloaded once more; and the command reports the failure and exits 1. A plugin turned off or on that failed to load is listed with its failure and applied again by its id.
- **A plugin in a work session.** `apply` and `undo` of a plugin with an open work session are refused with `NOT_ALLOWED`.
- **Text from files.** File names, folders, diff lines, summaries, specs and failure messages are printed with every control, line or paragraph separator and bidirectional character written as `\uXXXX`, and a line longer than 200 characters continues on the next, starting with `  ↪ `; `--json` writes the same characters as JSON escapes. `off` and `on` refuse a name that is not a package name as a usage error, and every path under `changes/` is built only from a package name.

## What verify and doctor report

`delorun verify` prints a Changes block after the release's check lines: the protection setting, which is not a fault in either setting; the changes the person approved, each plugin with its folder and marked when the first start under Changes approved it; then, apart from them, the group "N changes loaded without review (protection is off)", or "(while protection was off)" when it is on now, listing each plugin whose approved content was brought by a change decided `unreviewed`, with its folder and that change's id; then everything present that they did not approve: each plugin whose folder differs from its approved content and each invariant that does not hold. A run from outside the runtime store says it is a source checkout or a development build with no signed release to compare its files with. The summary line gains a clause for each part present, how many changes the person has not approved are present, how many changes loaded without review, and how many parts of their changes are not as Changes keeps them, so it never reads as a plain pass for content nobody reviewed. The run exits 1 only while an invariant does not hold or the composed tree fails its check; pending changes and changes that loaded without review are reported, not faults. `--json` carries the same report under `changes`.

`delorun doctor` prints `changes` lines: the protection setting as `pass` in either setting, an open work session, the last failed reload in a work session from `run/<profile>/changes-work.json` as `warn`, and for each plugin under Changes whether it loaded at the last start, what its active directory holds (for content a change decided `unreviewed` brought, `it runs content that loaded without review (<id>)`), the `engines.dsh` and `engines.delorun` its active `package.json` declares, and what the built-in consent, guard and sandbox check finds in its active content. When the last start failed or a plugin did not load, a line names the plugin and its newest applied change with `delorun changes undo <id>`; a failure that names no plugin under Changes names the newest applied change of any plugin. Each change a failed start left out that stays out is named with its plugin, the start's time, its failure and `delorun changes apply <id>` and `undo <id>`, and its plugin's line says it runs the content from before that change, or nothing. A pending change, a change left out and a plugin that did not load are `warn`; an invariant that does not hold is `fail`. Every line is escaped as `delorun changes` escapes its text, and a failure message a plugin or a record carries is cut at 200 characters, saying how many were left out.

A run from the runtime store also reports the person's changes to the harness of the release it checks: `verify` counts each approved harness file among the changes the person approved as `Delorun <runtime> itself: <file>`, or, when a change decided `unreviewed` approved it, in the group of changes loaded without review with that change's id; it lists each change waiting in the copy among what they did not approve (it does not run), says when the next start builds the composed tree, and reports a composed tree that fails its check as a part not as Changes keeps it, so the summary never reads as a plain pass and the run exits 1. A tree whose release did not verify is named as not checked. `doctor` reports the record's files, on one `pass` line for those the person approved and another for those that loaded without review while protection was off, the writable copy, each change waiting there, each change left out at start, and the composed tree's state: `fail` when it fails its check, `warn` when it was not checked. Neither reads the copy with its scan cache.

`delorun status` names, before its home-process lines, each plugin approved at upgrade that no terminal has shown and each change waiting for review, because `delorun start` shows its start's lines only in the log.

Neither command writes. A folder is read without the scan cache, so a pending change carries its id only when the store already holds the folder's content, and otherwise points to `delorun changes list`. A record that cannot be read is reported as an invariant that does not hold.

After each start the home process writes `run/<profile>/changes-boot.json` ([C1](c01-home-layout.md)), a protected file `{"schema":"delorun.changes-boot/1","at":<ISO time>,"plugins":[{"plugin","rows":[{"id","state"}],"loaded","error"?}],"failure"?}`: for each plugin under Changes (approved, or waiting for review as an install), the Loader rows whose module is the package or a path inside it, and whether it has an enabled row and every enabled row became active; `failure` is set when the profile did not boot. A failure to write it is logged and the start goes on; no start reads it.

## Consumers

`delorun/apps/cli` (`delorun start` with the home process's watcher of plugin folders, `delorun headless`, `delorun changes`, `delorun plugin`, `delorun verify`, `delorun doctor`, and `delorun setup`'s Full mode, which can turn protection on); `@delorun/plugin-changes`' routes and upstream's boot page, whose recovery screen reads and acts through them; later the studio's Changes section.

## Compatibility

A profile from before Changes is migrated at its first start without changing what it runs. Every record carries a schema tag; a reader refuses an unknown tag, field or value with `RECORD_UNREADABLE`, and a start then stops rather than guess. A `delorun.changes-protection/1` record whose `level` is neither `on` nor `off` is such a value.

## Security

### Requirements

Requirements 2 and 8, and the person's decision in requirement 1, hold with protection on; requirements 20 to 22 hold with protection off; the others hold in both settings.

1. Outside a work session, a plugin linked from a folder never loads from the folder: the profile's dependency, lockfile entry and link name its active directory, which holds the approved version. With protection on, only the person's decision changes the approved version.
2. A plugin with no approved content loads nothing.
3. A confined command cannot write `changes/`: it is under the protected home and not a read exemption ([C1](c01-home-layout.md#security)). So a confined command run in a pseudo-terminal, which passes the terminal check, still cannot turn protection off or approve a change ([F16](../security/fundamentals.md)), and cannot write the harness's writable copy.
4. Only a terminal proof changes the protection setting. Only a terminal proof or a studio proof at the computer opens or closes a work session, apart from ending one without the person (Delorun stopping, a start after a crash, its end time), which approves nothing and goes through `@delorun/changes/stop`, an entry no module but the CLI's start module imports.
5. The store's objects and versions are checked against their names on every read.
6. Every action that changes what the profile runs refuses a proof the attest functions did not issue before it reads or writes anything, `delorun changes` gets its proof only at a terminal, and no module of Delorun or upstream other than `delorun changes` (`delorun/apps/cli/src/changes/`, setup's section that only turns protection on included), `@delorun/changes` and the studio's Changes routes (`delorun/packages/plugin-changes/src/routes.ts`) imports an action or an attest function; the routes import neither `attestTerminal` nor a writer of the protection setting.
7. In a work session, a reload that fails leaves the content that last loaded, or the approved content, running, and the session open. Ending a session without the person approves nothing: the approved content stays the version the session started from. `done` approves only the version it showed. A session ends at its `endsAt`, at most 480 minutes after it started, and no start loads its folder after that.
8. With protection on and `plugin_changes_pending` on, an agent's `plugin_manager` install, update or removal changes no profile file and never reaches the tool's approval; an agent's spec that names a folder loads nothing before the person reviews the folder's content, and one whose range names another source is refused; with protection on and `approved_plugin_write_consent` on, the agent's first file-tool write in a chat to an approved plugin's folder asks, however the path is spelt; with that switch on, a file-tool write into the profile's active directories is refused in both settings. Applying the agent's request runs no build script that the profile's `allowBuilds` does not allow and installs no version incompatible with this Delorun.
9. What `delorun changes`, `verify`, `doctor` and `status` print from a file, a log entry or a plugin's failure cannot move the cursor, start a line of its own or reorder the text around it. A change whose new content the diff does not show, a binary file Node loads, a file above or past the diff's limits or a dependency's file inside the folder, asks the second confirmation and names the file. A profile created after the first start under Changes approves none of its links at upgrade.
10. Before every recomposition of the running profile and at every start, each link names its plugin's active directory and each active directory holds what Changes keeps, or nothing loads: a link to a folder is moved first where the profile write lock allows it, and anything else that differs refuses the start or the reload ([Reloads and restores](#reloads-and-restores)). An approved plugin's installed dependencies load from the approved copy, by hash, never from where they are installed, apart from a plugin over the content limits only with its installed packages while protection is off.
11. A folder that cannot be read as one content version leaves the approved content running and never stops a start; the store keeps only what a record references, apart from versions written within the grace period ([Collecting the store](#collecting-the-store)).
12. A start that fails right after a change leaves out only that change, by writing the change log alone, and loads only content approved before it, or nothing, until the person applies it again or undoes it, or, with protection off, the folder holds other content; the second start leaves nothing out ([When a start fails](#when-a-start-fails)).
13. A Changes route answers only a request Connection admits with the studio's credential. An action acts only for a request at the computer, on the loopback listener under a loopback `Host` that no reach dispatcher admitted, and refuses any other, and a request another site sent, before it reads the body; no route changes the protection setting ([Routes and the recovery screen](#routes-and-the-recovery-screen)).
14. Storing a plugin's content never reads a file in the Delorun home or in `/proc`, `/sys` or `/dev`, follows a link out of the folder only to an installed package, a sibling workspace package or a `.git` directory it includes, and reads each file no further than the size counted against the content limits ([Loading approved content](#loading-approved-content)).
15. No harness action writes under `runtimes/`, and the signed installation's start check is the same in both protection settings. Every byte read from the installation is checked against the verified signed file list ([Harness edits](#harness-edits)).
16. A pending harness change never runs: a start runs the signed installation, or the composed tree of the record, which only an applied change writes.
17. A start runs a composed tree only after checking that every unedited path is the installation's file and every approved path holds the approved content, and nothing else exists; a tree that fails twice refuses the start. Only the signed installation's code hands a start off to a composed tree, and a start's second run after a failure starts the signed installation.
18. Only a terminal proof makes the writable copy or decides a harness change; a confined command cannot write `changes/harness/` (requirement 3), and no route or model tool reaches a harness action, apart from the start's apply without review while protection is off (requirement 22).
19. Discarding every harness change empties the runtime's record, so the next start runs the signed release unchanged. A failed start right after a harness change leaves out only that change, in the harness's log, and writes no file of the profile; so does a composed tree whose `delorun` fails before its start ran, and a second such failure leaves nothing more out. A profile in safe mode runs the signed release without any harness change.
20. With protection off, content that loads without review is recorded before the Host loads it: it is the approved content in the profile's `delorun.changes` record, or in the runtime's harness record, and an applied change decided `unreviewed` in the change log, which `delorun changes list`, `show`, `undo`, `verify` and `doctor` reach; a start that loads any and each live reload also record a profile history version.
21. With protection off, content the person declined does not load: while a plugin's newest decided content change was undone or discarded and brought exactly what its folder holds, the plugin keeps its approved content. Content whose live reload failed is not loaded again until the folder holds other content, and a change a failed start left out stays out while the folder holds what it brought.
22. Only a start's pre-start step and the check before a reload, the home process's watcher of plugin folders (`loadUnreviewed`, named outside `@delorun/changes` only by `delorun/apps/cli/src/changes/unreviewed-watch.ts`) and the signed installation's start for the harness's writable copy (`applyUnreviewedHarnessChanges`, named only by `delorun/apps/cli/src/changes/harness-start.ts`) load content without review. Each reads the protection setting under the profile write lock, or `harness.lock`, and writes nothing when it is on; no route, model tool or plugin names them.

### What this does not prove

- Review by default: protection is off unless the person turns it on, and with protection off nothing here reviews what loads. Any writer of a linked plugin's folder, or of the harness's writable copy (a process outside the sandbox), changes the code the harness runs at the next start or save; the requirements for off prove only that each such change is recorded, can be undone, and that declined content does not load again ([The protection setting](#the-protection-setting)).
- A process of the person's user outside the sandbox: it can write a runtime's approved harness record, the content store and the change logs under `changes/` ([C1](c01-home-layout.md#the-home-tree)), and the next start runs what it wrote from the composed tree with every check passing; only the approved files that `delorun verify` and `delorun changes list` name show it ([threat model](../security/threat-model.md)). The same holds for an approved plugin's content under `changes/store/`.
- At the computer in the studio: the routes decide it from where a request arrived, so a request through SSH port forwarding to the loopback listener counts as at the computer, as [C5](c05-device-approval.md) counts it for the owner claim, and so does a local program that holds the studio's cookie; no session factor exists yet.
- Full access: a workspace with full access runs commands with the person's own authority, so a model working there can turn protection off and approve changes. Changes protects against a confined model, not against the person's own access.
- Registry, `file:`, git and tarball plugins: only plugins linked from a folder are under Changes; the others load as upstream installs them.
- Dependencies a plugin does not link: an installed package is copied with the dependencies its `package.json` lists that are installed beside it. A module the plugin or a copied package imports without that, such as a package pnpm hoisted, is resolved by Node from the active directory's parent directories up to the filesystem root, which include the person's home folder; a package placed in a `node_modules` directory there, which a confined command may be able to write, would load. With protection off, a plugin over the content limits only with its installed packages loads them from where they are installed, and the start says when that is under the home folder.
- A running Host's modules changed through a source watch: Delorun sets no `hmr.root`; a profile whose own configuration watches an active directory would replace modules without the check, though only Delorun writes active directories.
- Client plugin code: the code a plugin serves to the studio's browser is not reviewed by Changes.
- Running from source: a source checkout runs the whole harness from the checkout, so a model working inside the repository can edit the code the Host runs.
- Plugin code, once approved, can do anything Delorun can; the risk summary does not limit it. The same holds for an approved harness change.
- The composed tree's unedited files are hard links to the installation's, so they share its inodes and modes: a process with the person's authority that rewrites one in place changes the installation's file too, which the installation's start check then refuses. A confined command cannot write either.
- A release whose `app/` passes the scan's limits (50,000 entries or 512 MiB) cannot be edited: `edit-harness` refuses it before copying. A copy that grew past them afterwards cannot be read as pending changes; `list` names it and `edit-harness --discard` removes it. Whether a released closure's `app/` stays within those limits is not checked by a spec.
- Retention keeps every composed tree of the runtime while a home process of any profile runs, so trees accumulate until a start finds none running.
- Only `delorun start` and a bare `delorun` hand off to the composed tree. `delorun headless` and every other command run the signed installation, so the person's approved harness changes do not apply to them.
- A source checkout is a developer mode, not an installed release: Delorun's bundles included, Changes leaves those packages alone.
- Only the file tools' writes are asked about; a shell command's write to a plugin's folder is not asked ([The agent and plugins](#the-agent-and-plugins)). Applying the agent's request runs no `pluginAudit`, because no Delorun composition mounts one; a profile whose own bundles provide one is not audited when the request is applied.
