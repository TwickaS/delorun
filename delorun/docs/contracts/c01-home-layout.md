# C1 Home layout and runtime store

English | [中文](c01-home-layout.zh.md)

## Summary

This contract fixes where Delorun keeps a person's home on disk and how the `delorun` command finds and switches the runtime it runs. It defines the `~/.delorun` tree and the owner of each entry, the modes of the home and its protected files with the rule that a component refuses a laxer file, the place of secrets and of the two sockets that refuse confined commands, the token each home-process start writes, the CLI profile beside the desktop app's own profile, the runtime store with its `current` and `previous` pointer files, the override variables and the npm launcher's download and verification. It states which confinement rules each operating system and sandbox dialect enforces. The types package [`@delorun/contract-home-layout`](../../packages/contract-home-layout/README.md) carries the names, codes and limits as constants.

## Status

The home, its modes on Linux and macOS, the update channel, the lock, the runtime store, the npm launcher and the confinement rules of the CLI profile on bwrap, Landlock and Seatbelt are built; the checks that report the rules, Windows and the Docker supervisor's channel are not.

- **Built and reached:** home resolution and its refusals; the home's directories and protected files with their modes and the refusal rule on Linux and macOS; the update channel's socket and the start token; the home lock; the runtime store with install, switch and the start check; the npm launcher's download and verification; and, in the CLI profile, the `home-write`, `home-read` and `token-read` rules on bwrap, Landlock and Seatbelt, the `home-connect` and `docker-connect` rules on bwrap and Seatbelt, and the refusal of a writable root that holds the home; the `wsl-interop` rule under WSL on bwrap, with Landlock refusing confined commands there; the `vsock` rule on bwrap wherever the kernel offers virtual-machine sockets; and the `session-escape` rule on bwrap and Seatbelt for pathname sockets, with Landlock refusing confined commands wherever one of its directories exists, the `daemon-connect` and `agent-connect` rules on bwrap and Seatbelt, and the `private-tmp` rule on bwrap.
- **Built, reached by nothing:** the Docker supervisor's socket, which `delorun start` adds to the denied sockets but which no process creates, because no command launches the supervisor ([C9](c09-runtime-supervisor.md)).
- **Not built:** Delorun's rules under `delorun plugin`, which runs upstream's pnpm operation with none of them; the probes at each start and the `confinement-rule` and `home-modes` checks, which `delorun verify` reports as not run; setup's Docker labels; the full-access prompt's statement of what full access reaches; the denial of Docker Desktop's control-socket directories on macOS; on Windows the DACL check, the named pipes and any read confinement; the install scripts, the launcher copy under `bin/` and login items; and the npm build attestation. These rules are in the [native confinement design](../design/native-confinement.md) and the [release workflow design](../design/release-workflow.md).

The requirements and denial tests below that this list names as not built or reached by nothing protect no one until a change builds and wires them.

## The home directory

The Delorun home is one directory per person and machine. Upstream's harness uses it as its home (`DSH_HOME`), so upstream's data and Delorun's data share one tree.

- **Resolution.** `delorun` resolves the home from `DELORUN_HOME` when it is set and not blank, otherwise from the OS home directory joined with `.delorun` (`~/.delorun`, on Windows `%USERPROFILE%\.delorun`). A leading `~` is expanded as upstream's `expandHomePath` expands it, and the result is normalised to an absolute path. Every symbolic link in the home's parent path is resolved, as far as that path exists, and the home's own name is kept, so the resolved home names the same directories that the files under it report. A home that is itself a symbolic link is refused with `HOME_MODE`. The refusals below compare paths with every symbolic link resolved, the home's own included.
- **Refusals.** `delorun` refuses a resolved home that is not absolute, that equals the filesystem root or the OS home directory (`HOME_INVALID`), or that equals or lies inside upstream's default home `~/.dsh` (`HOME_IS_DSH_HOME`).
- **Upstream's variable.** `delorun` sets `DSH_HOME` to the resolved home in the environment of every runtime process it starts. An inherited `DSH_HOME` is ignored, and `delorun status` names it when it differed.
- **Upstream's home.** Delorun never reads, writes or migrates `~/.dsh`. A person moves upstream data into Delorun only through an explicit import.
- **Override variables.** `DELORUN_HOME` selects the home. `DELORUN_PROFILE` selects the CLI profile ([profiles](#profiles)). No other variable changes the layout; the runtime store has no override variable, and a runtime other than `current` runs only through the switch rules below.

## The home tree

Delorun adds the entries marked Delorun at the top of the home. Every other entry is upstream's, keeps upstream's layout and modes, and is described by upstream's documentation.

```text
~/.delorun/                         0700  the home; upstream's DSH_HOME
  .credentials.yaml              0600  upstream credentials provider: model keys, the browser session secret
  .env                           0600  upstream credentials fallback, never written by Delorun
  cordis.patch.yml                     upstream home patch
  AGENTS.md, skills/                   upstream user instructions and skills
  profiles/default/                    the CLI profile, in upstream's profile layout
  profiles/desktop/                    the desktop app's upstream profile and its lock
  profiles/headless/                   the profile delorun headless boots: upstream's headless template with @delorun/bundle-headless linked
  sessions/, attachments/, cache/, storages/, spill/, dsh-runtimes/, ...   upstream data
  logs/                                upstream startup reports and the operational logs of C20
  runtimes/                      0700  Delorun: the runtime store
  staging/                       0700  Delorun: runtime installs in progress
  packs/<release>/<pack>/        0700  Delorun: plugin packs, unpacked per release and sealed read-only like an installation
  trust/                         0700  Delorun: the verified release root, timestamp and log checkpoint (C2, C18), and the installations' identity records
  status/                        0700  Delorun: each installation's update status record (C3)
  catalogue/                     0700  Delorun: the verified catalogue index and revocation list (C13)
  secrets/                       0700  Delorun: secret files, 0600 each
  run/<profile>/                 0700  Delorun: home lock, start token, sockets, update record, update check, setup progress, start overlays
  data-copies/                   0700  Delorun: the session-data copy an update took, and a restore's journal (C3)
  data-set-aside/                0700  Delorun: chat data a rollback set aside (C3)
  trash/                         0700  Delorun: trashed chats and workspaces until retention ends or a restore (C8)
  archive/                       0700  Delorun: workspace archive imports, staged and published (C8)
  supervisor/                    0700  Delorun: the Docker supervisor's roots file (C9)
  bin/                           0700  Delorun: the launcher copy used by the install script and login items
  alerts/                        0700  Delorun: signed certificate-alert files (C5)
  trash/                         0700  Delorun: deleted chats and workspaces until a purge, and the retention record (C8)
  archive/                       0700  Delorun: imports in progress and imported workspaces (C8)
  changes/                       0700  Delorun: approved plugin content, the change log, protection, work sessions and harness edits (C21)
```

The operational logs that [C20](c20-operational-logs.md) defines live in per-surface directories under upstream's `logs/`, beside upstream's `startup-*.log` reports. The home tree creates `status/`, `catalogue/`, `supervisor/`, `bin/` and `alerts/` empty, and nothing writes into them: the features that own them are not built or not reached ([status](#status)).

The types package's `DELORUN_HOME_ENTRIES` lists every Delorun entry above, and its `home-entries` spec fails when Delorun's code builds a top-level entry under the home that neither that list nor upstream's entries name.

- **`trust/`.** `root.json` is the newest root that verified, `timestamp.json` the newest timestamp that verified, whose `version` is the highest one stored ([C2](c02-release-manifest.md)), `checkpoint.json` the latest log checkpoint that verified ([C18](c18-release-log.md)), and `release-log.json` the release-log check state of each installed release, `verified` or `unchecked` with the reason, which an install writes once the runtime store has installed the release and the start check updates ([C18](c18-release-log.md#check-states)). Each is replaced atomically and never with an older version; the CLI launcher and the desktop updater share them. `roots/<n>.root.json` holds one file per root version an install walked, oldest first, which is the proof a start holds a stored root newer than every root the launcher ships to ([C2](c02-release-manifest.md#key-rotation)). `channel.json` records where the home's releases come from, `{"v":1}` with the `channelOrigin` and `logOrigin` the installing launcher was built with, each absent for the production value; a launcher writes it once the store has installed a release from it, and `delorun update` fetches from those origins and anchors on the stored roots, which must chain, each signed by the one before it. No environment variable, setting or runtime command of Delorun moves the channel: Delorun changes it only when the person runs a launcher built for another channel, in a terminal. The file lies under `trust/`, which the sandbox keeps confined commands from writing; an unconfined process of the same user, a Host plugin included, can write it as it can every file of the home, so the record decides only where releases are fetched from, and a release installs only when it verifies under the stored roots. `runtime-files/delorun-<version>-<platform>.json`, at mode 0600, is the identity record of an installed runtime that C2's start check reads; the runtime store writes it under `store.lock` and retention removes it with its version, and it lies outside every read exemption of confined commands. `runtime-files/packs/<release>/<pack>.json`, at mode 0600, records the digests of the files an external npm package put into an installed pack; a pack install writes it under `store.lock` with the sealed pack, and retention removes it with the release.
- **`status/`.** `cli-home.json` and `desktop-host.json` are the status records of [C3](c03-update-report.md); each installation writes only its own record and reads the other.
- **`run/<profile>/`.** Besides the lock, the token and the sockets, it holds `setup-progress.json`, the record that lets an interrupted setup resume ([C11](c11-setup-answers.md)), and the overlays a start passes to upstream's profile runner: `sandbox.patch.yml`, the confinement rules of [this contract](#confinement-rules), and `safe-mode.patch.yml` while safe mode is on. A start rewrites the overlays; they are not the person's configuration. While the home process's debugger listens (`delorun start --inspect`), it also holds `inspector.json`, mode 0600, with the process id, the debugger's address and when it opened, removed when the process exits ([requirement 16](#requirements)).
- **`run/<profile>/update.json`.** The update record of [C19](c19-home-process.md#interrupted-updates) and [C3](c03-update-report.md#rollback): the two versions, whether the chat data differs, whether a copy was taken and `targetStarted`, written at mode 0600 and synced before the target's process is spawned. It stays with phase `committed` after an update commits, so a later rollback reads it, and goes when a rollback completes.
- **`run/<profile>/update-check.json`.** The update check's record ([C3](c03-update-report.md#update-check)): when the profile's last check ran, the newest release it verified and why the last check failed, written atomically at mode 0600 and removed by a start whose profile switches the check off.
- **`run/<profile>/update-result.json`.** How the last update or rollback ended ([C19](c19-home-process.md#the-outcome-record)): the outcome, the two versions, the refusal code and the failed health criterion, written by the home process at mode 0600 at every end, so the studio can say what happened after a switch it could not watch; the person's dismissal in the studio removes it, and the next update or rollback replaces it.
- **`run/<profile>/update.previous.json`.** The committed record of the previous update while a newer update runs: it goes back to `update.json` when the newer update ends before switching or is rolled back, and is removed when the newer update commits.
- **`run/<profile>/changes-boot.json`.** Which plugins under Changes loaded at the profile's last start, or the start's failure, written by the home process after each start at mode 0600 and read by `delorun doctor` ([C21](c21-changes.md#what-verify-and-doctor-report)). No start reads it.
- **`run/<profile>/changes-work.json`.** The last failed reload in a work session, `{"schema":"delorun.changes-work/1","plugin","at","error"}` at mode 0600, written when Delorun went back to the content that last loaded and removed when a reload in a work session succeeds or a session starts ([C21](c21-changes.md#work-sessions)). `delorun doctor` and the studio read it; nothing decides from it.
- **`changes/harness/`.** The person's edits to the harness itself ([C21](c21-changes.md#harness-edits)): `log.json`, the harness's change log, and per installed runtime `<runtime>/approved.json`, the files whose approved content differs from the signed release's, `<runtime>/copy/app/`, the person's writable copy of the runtime's `app/` directory (files 0600, executable ones 0700), `<runtime>/scan-cache.json`, `<runtime>/pending.json`, the file of each change the last read of the copy found, and `<runtime>/run/<digest>/`, the composed tree a start runs, whose unedited files are hard links to `runtimes/<runtime>/` and whose files and directories are read-only. `runtimes/` itself is never written by Changes. A start removes the composed trees it no longer runs and the directories of runtimes the store no longer has installed.
- **`run/data-users/<pid>`.** One file per process that uses the shared stores, `sessions/`, `storages/` and the rest beside them, and `runtimes/current`, at mode 0600, holding `{"mode":"shared"|"exclusive","command":"<name>"}` with the holder's `processStart` and `pidNamespace` ([the home lock](#the-home-lock)) where the platform reports them. Every home process registers as `shared` with `"command":"start","profile":"<profile>"` from before it takes its home lock until it exits, `delorun headless` and `delorun plugin` register as `shared`, `delorun trash`, `export` and `import` as `exclusive` while they also hold the home lock of every profile, and `delorun recover rollback` with no home process running, unless `--profile-only`, as `exclusive` with `"command":"recover"` while it holds its profile's home lock. An exclusive user refuses while any other live process is listed, a shared user refuses while an exclusive one is, and a home process refuses to start while an exclusive one is or an update or a rollback of another profile is between its snapshot and its end. An update's prepare, session-data copy, restore and runtime switch, and a rollback, refuse while any other live process is listed, another profile's home process included, and name it; an update checks before it writes its update record and again after, right before its Host stops for the switch, so a process listed in between is found. The process's own file never counts. A file whose process has exited, or whose recorded start identity differs from the live process's, is not live and is removed; a file that records a Linux boot other than the running one is not live and is removed, whatever pid namespace it records; a file of this boot that records another pid namespace is live and kept; a file that cannot be read counts as an exclusive use. `data-users` is never a profile's run directory: it is a [reserved profile name](#profiles).
- **`data-format.json`.** At the home root, mode 0600: `{schema: "delorun.home-data-format/1", delorun, dsh, formats}`, the release that last started over the home and that release's `data-formats.json` ([C3](c03-update-report.md#data-formats)). Each start writes it before a Host opens data, from the running release's `data-formats.json`; a start of an older release leaves a record that shows newer data as it is. A home made before the record has none, and readers then treat the home's data formats as unknown. `delorun repair` compares it with the release it installs.
- **`import-preview.txt`.** At the home root, mode 0600: the full list of what `delorun setup`'s import section would copy from DeepSeek Harness's home and what stays behind, written when the section asks its question so the person can read it later ([C11](c11-setup-answers.md)). Each question rewrites it; nothing reads it back.
- **`runtimes.set-aside-<time>/`.** The program store `npx delorun@latest repair` replaced, kept whole. Nothing removes it but the person, through `delorun recover discard`; `delorun recover status` lists it.
- **`data-copies/`.** `<version>/` holds the session-data copy the update to that version took: real copies of `sessions/` and `storages/` beside `copy.json`. An older copy is removed when a newer update commits, and a copy of an update that ended before switching is removed with it. `restore.json` is the journal of a restore in progress, completed before any Host starts. An update's data-safety step writes the copy and a rollback the journal, both through `delorun/packages/update`.
- **`data-set-aside/`.** `<version>-<time>/` holds the `sessions/` and `storages/` a rollback replaced with a copy. Nothing removes it but the person, through `delorun recover discard`. The rollback of `delorun/packages/update` writes it.
- **`trash/`.** `items/<item>/` holds one trashed item: its `item.json` and the chats moved out of `sessions/`, until the home process's retention pass or `delorun trash purge` purges it or a restore moves it back; `retention.json` records the last retention pass. The studio's trash plugin and `delorun trash` write it ([C8](c08-archive-and-trash.md#trash-and-purge)).
- **`archive/`.** `staging/` holds an import in progress and `imported/<workspace>/` each workspace `delorun import` published; no row of the shipped composition reads it ([C8](c08-archive-and-trash.md)).
- **`catalogue/`.** `index.json` and `revocations.json` are the newest catalogue index and revocation list that verified, and `state.json` holds each one's `sequence` and fetch time ([C13](c13-catalogue-revocation.md)).

## Modes and the refusal rule

On Linux and macOS the home and every directory Delorun creates under it have mode 0700, and every protected file has mode 0600. Delorun creates each of them with these modes through exclusive creation, so the process umask can only narrow them.

- **Protected files.** Every file under `secrets/`, `trust/`, `status/` and `catalogue/`, `run/<profile>/start-token`, `supervisor/roots.json` and the [C20](c20-operational-logs.md) log files. Upstream's `.credentials.yaml` and `.env` follow upstream's own check, which refuses a file that another user can read.
- **The refusal rule.** A component that reads a protected file first checks it with `lstat`. It refuses the file with `SECRET_FILE_MODE` when the path is a symbolic link or not a regular file, when its owner is not the process's user, or when any group or other permission bit (`0o077`) is set. The error names the path and the fix `chmod 600 <path>`.
- **Directories.** The home process refuses to start with `HOME_MODE` when the home, `secrets/` or `run/<profile>/` has a group or other bit set, is a symbolic link or belongs to another user. The error names the path and the fix `chmod 700 <path>`.
- **Windows.** Windows has no mode bits, and the checks above are skipped there; no check reads a path's DACL. The DACL check is in the [native confinement design](../design/native-confinement.md#windows).
- **Checks.** `delorun doctor` checks the modes of the home, `secrets/` and `run/<profile>/`. `delorun verify` reports its `home-modes` check as not run ([native confinement design](../design/native-confinement.md#checks-at-each-start)).

## Secrets

Delorun's secrets are the home-auth keys, the relay and TLS keys, and the session secrets that C4 to C7 define. Each lives in one file under `secrets/<owner>/`, where the owning contract names the file and its format. Upstream's model keys and its browser session secret stay in upstream's `.credentials.yaml`, which also lies under the home.

- A secret never appears in a profile, `cordis.yml`, a patch file, a command's environment, a command line or a log.
- A plugin's credential, a config field whose schema gives it the role `secret` such as the DeepSeek API key of the web search plugins, is no exception. A configuration edit that would save its value into the profile patch is refused before the file is written, whether it comes from the studio's Settings, the agent, the import of an old `settings.yaml` or another caller of upstream's configuration editor; the listeners are registered before the Loader mounts its first row. The profile history saves no version whose files hold one; it lists its versions with the reason, and undo and restore still work. At each start, before the Host serves, a value the profile patch or the home patch holds is moved into `.credentials.yaml` through upstream's credentials provider wherever the plugin names a stored key in a `credential-ref` field beside it, such as `apiKeyEnv`: it is only deleted when the file already holds it under the name that field gives, the schema's default included, and otherwise it is stored under a new POSIX-identifier name, never over a name that holds another value, and the field is set to it. Names are chosen from the credentials file as it is on disk, under the home patch's writer lock, which every settling start takes, so two starts never take the same name; at most 100 names are tried before the value stays. The credentials file and its directory are flushed to disk before the patch is rewritten. A value that cannot be moved, because its field has no reference field beside it or it is an expression, stays, and every start names it on its output and in its log with the way to move it, `!!js process.env.NAME`. Empty and null values are unset, and a `!!js` expression counts as a value unless it only reads one environment variable. An update's snapshot is refused while it holds one, and when no Host runs to tell which fields are secret. Only rows of loaded plugins are checked, because only a loaded plugin's schema marks its secret fields; an inserted row without an id is matched by its plugin name.
- `secrets/permission-defaults/` also holds the per-workspace permission and network stores, which are consents and settings rather than secrets, and while a Host runs, its egress proxies' sockets under `proxy/<pid>/`; they lie there so confined commands can neither read nor change them.
- In the CLI profile, the home's confinement rules deny confined commands reads of `secrets/` and of upstream's credential files wherever the dialect enforces `home-read` ([confinement rules](#confinement-rules)).
- Delorun does not store these secrets in the OS key store. On Linux the Secret Service is reached over D-Bus, which stays reachable for confined commands, and on macOS a keychain item's access list trusts the runtime's `node` executable, which confined commands also run. A file in a directory that every dialect denies keeps them from confined commands wherever the dialect enforces the read rule.

## Sockets and the start token

The update channel ([C19](c19-home-process.md)) and the Docker supervisor ([C9](c09-runtime-supervisor.md)) are the two channels that refuse confined commands. Both listen under the home and accept a request only when it carries the current start token. No command launches the supervisor, so only the update channel listens.

- **Socket paths.** On Linux and macOS the update channel is the Unix socket `run/<profile>/update.sock` and the supervisor is `run/<profile>/supervisor.sock`. Both are pathname sockets; Delorun never listens on an abstract-namespace socket. A socket is created after the start token is written and is set to mode 0600 after it binds.
- **Path length.** A socket path is at most 103 bytes. A longer path stops the start with `SOCKET_PATH_TOO_LONG`, which names the path and asks for a shorter `DELORUN_HOME`.
- **Windows.** The update channel is a filesystem socket path on every platform; no named pipe and no pipe DACL exists. The named pipes are in the [native confinement design](../design/native-confinement.md#windows).
- **The start token.** Each home-process start writes a new token to `run/<profile>/start-token` before either channel listens: 32 bytes from the operating system's cryptographic random source, encoded as base64url without padding (43 characters) and followed by one newline. The file is replaced atomically with mode 0600 and removed when the home process stops cleanly.
- **Token lifetime.** A token is valid only while the home-process start that wrote it runs. A token file left by a crashed process is replaced at the next start, and no listener accepts its value.
- **Token handling.** The token exists only in the home process's memory, in the supervisor's memory and in the token file. It never appears in a command line, an environment variable, a URL, a response or a log. `delorun` client commands read the file when they send a request.

## The home lock

One home process per profile holds `run/<profile>/home.lock` for its lifetime ([C19](c19-home-process.md)). `delorun update` and `delorun recover` hold it while they change the store with no home process running.

- **Creation.** The lock is created by exclusive creation with mode 0600. It holds one JSON object: `{"v":1,"pid":<integer>,"startId":"<32 lowercase hexadecimal digits>","runtime":"<version>","startedAt":"<RFC 3339 UTC time>"}`, with `"processStart":"<start identity>"` and `"pidNamespace":"pid:[<inode>]"` where the platform reports them. `startId` is random and identifies one start in [C19](c19-home-process.md)'s protocol and in [C20](c20-operational-logs.md)'s records; it is not a secret.
- **Start identity.** A holder's start identity tells its process from a later one with the same process id. On Linux it is `linux:<boot id>:<start time>`, the boot id from `/proc/sys/kernel/random/boot_id` and field 22 of `/proc/<pid>/stat`; on macOS it is `darwin:<milliseconds since the epoch>`, the start time `ps -o lstart=` reports. Windows has none, and a record without one, as Delorun wrote before it existed, is judged by its process id alone: a process that reuses that id reads as the holder.
- **Boot.** A Linux `processStart` begins with the boot id, which every pid namespace of one boot reads the same. A record whose boot id differs from the running system's names a process of an earlier boot, which has exited whatever its process id or pid namespace now names, so a restart never leaves a lock that reads as alive.
- **One kernel.** A home is shared only by processes of one running kernel: containers, sandboxes and WSL distros of one VM, never machines or virtual machines with their own kernels. The boot id and the update socket judge a lock on that assumption, so a holder on another kernel that shares the home folder reads as an earlier boot and its lock is taken over.
- **Pid namespace.** On Linux a record names the pid namespace its `pid` is numbered in, the writer's own, as `/proc/self/ns/pid` links to it: `pid:[<inode>]`. A holder in another pid namespace, such as a container or a sandbox that shares the home, records a process id that names nothing in the reader's, so a reader whose own namespace differs from the record's, or cannot be read, does not judge the holder and treats it as alive. A record without `pidNamespace`, as Delorun wrote before it existed, as other platforms write, and as Linux writes when `/proc/self/ns/pid` cannot be read, is judged by its process id and start identity alone. A `pidNamespace` that is present but not of that form makes the record malformed.
- **Stale lock.** A contender replaces the lock only when the record names an earlier boot, or names no pid namespace or the contender's own and the recorded process no longer exists (`ESRCH`) or the record carries a start identity and the live process with that id has another.
- **Abandoned lock, same boot.** A record of this boot that names another pid namespace cannot be looked up, as after a WSL distro restarts while its VM keeps running. The holder writes `"listening":true` into its record, atomically and with its other fields unchanged, once its update channel is bound, and removes it before it closes the channel; a handed-over record has none until the successor's channel listens. A contender takes such a lock over only when the record says `listening` and the connection to the holder's update socket is refused (`ECONNREFUSED`, so no process listens on it), judged again against the record read under the takeover guard. A live listener never refuses, and a live holder unmarks before it closes, so a refusal after `listening` means the holder closed the channel and is dying or dead. A record that never reached `listening`, a timeout, a missing socket or token file, any other failure and any answer keep the refusal; the error then names the remedy in plain words. The takeover writes one warning to the start's log.
- **Unresponsive holder.** When the recorded process exists, with the recorded start identity where there is one, or the record names another pid namespace, but its update channel does not answer `status` within 2 seconds, the contender stops with `HOME_UNRESPONSIVE` and names the process id. It never takes the lock over.
- **Scope.** The lock is per profile. The desktop app's upstream lock `profiles/desktop/lock` is a different file, which Delorun never takes, writes or waits for.

## Profiles

- **The CLI profile** is `default`, at `profiles/default/`, in upstream's profile layout (`package.json`, `cordis.patch.yml`, `pnpm-workspace.yaml`, `node_modules/`). Beside upstream's files, `delorun-migrations.json` holds `{"v":1,"done":[<id>…]}`, the one-time profile changes a fresh start completed, such as adding the studio bundle to a profile an earlier release set up, at mode 0600. A fresh start runs each change not listed under the home lock before its Host boots, and an update's successor runs none. A record that does not read runs no change: the start warns on its output and in its log, naming the file and that removing it lets the next start apply the changes, and boots the profile unchanged. A profile with no record takes over `run/<profile>/migrations.json`, where an earlier release kept it, once. The profile history does not track the record, so a restore leaves it as it stands. `DELORUN_PROFILE` or `--profile` selects another CLI profile, whose name is 1 to 32 lowercase letters, digits, hyphens or underscores, starting with a letter or a digit (`PROFILE_NAME_PATTERN`); the launcher and `delorun` refuse any other name with the same rule. Each CLI profile has its own `run/<profile>/` directory, lock, token and channels.
- **Reserved names.** No CLI profile takes a name that something else in the same home uses under `profiles/` or `run/`, or that a `delorun` command boots as its own profile (`RESERVED_PROFILE_NAMES`): `desktop`, the desktop app's profile; `headless`, the profile `delorun headless` boots, which Delorun composes with the sandbox overlay and `@delorun/bundle-headless`; `data-users`, because `run/data-users/` holds the home-wide exclusion's records, which a profile's run directory there would escape; `node_modules`, upstream's package layer `profiles/node_modules/`, which upstream refuses as a profile; and the Windows device names `con`, `prn`, `aux`, `nul`, `com1` to `com9` and `lpt1` to `lpt9`, which no folder can take on Windows. A reserved name is refused in any letter case. Upstream's template names that nothing boots in a Delorun home, such as `web` and `tui`, stay usable. The launcher and every `delorun` command that takes `--profile` or `DELORUN_PROFILE` refuse a reserved name with the usage exit code before they read or change the profile or its run directory, naming the name and why (`profileNameProblem`), and setup's profile question asks again. `delorun plugin` and `delorun logs`, whose own parsers read `--profile` again, check every `--profile` value the command line carries, as `--profile <name>` or `--profile=<name>`, and refuse values that differ; a home holding a CLI profile under a reserved name is refused the same way until the person moves it to another name.
- **The headless profile** is `headless`, at `profiles/headless/`, in upstream's profile layout. The first `delorun headless` run creates it from upstream's `headless` template and links `@delorun/bundle-headless` into it as the one-time change `headless-bundle`, which `profiles/headless/delorun-migrations.json` records like a CLI profile's changes; every `delorun headless` run applies the changes the record does not list, under upstream's profile file lock and without a home lock, and a record that does not read runs none. The same run brings the bundle to a profile an earlier release created. A profile whose loader does not load the bundle stops `delorun headless` before boot, naming the bundle; removing `profiles/headless/delorun-migrations.json` lets the next run link it again, and removing the `profiles/headless/` folder lets Delorun create the profile again. The rows the bundle adds are held to [C19](c19-home-process.md#host-invariants)'s Host invariants.
- **The desktop profile** is upstream's `desktop` profile at `profiles/desktop/`, which only the desktop app manages. `delorun` refuses the name `desktop` for its own runs and for `delorun plugin`, as upstream's CLI refuses it.
- **`delorun plugin`** is upstream's `dsh plugin`, run against the home: under upstream's profile file lock it runs pnpm in a CLI profile's directory, changing its `package.json`, lockfile and `node_modules/`, and records the bundle list. It boots no Host, so the [confinement rules](#confinement-rules), the start overlays and C19's Host invariants do not apply: pnpm runs unconfined with the command's environment, runs a dependency's install scripts only when the profile's `pnpm-workspace.yaml` allows its build, and runs whatever a pnpm command such as `exec` or `dlx` names. It imports no plugin code. It registers in `run/data-users/` as a shared user while it runs.
- **Shared data.** Sessions, workspaces, attachments, credentials and the home patch stay at upstream's places under the home, so the CLI and the desktop app share them as upstream's surfaces do.

## The runtime store

The runtime store holds the installed runtime closures and names the active one. Each command-line start runs exactly one runtime, the one `current` names.

```text
runtimes/
  store.json              {"layout":1}
  current                 the active version and one newline
  previous                the version kept for rollback and one newline; absent before the first switch
  store.lock              taken by install, switch and removal
  <version>/              one complete, verified runtime closure
  delorun-<version>.manifest.json            the verified release manifest, beside its installation
  delorun-<version>-<platform>.files.json    the verified runtime file list
  delorun-<version>.manifest.log.json        the release-log bundle
```

- **Version names.** A directory name is a Delorun release version: SemVer 2.0 without build metadata, matching `^[0-9]+\.[0-9]+\.[0-9]+(-[0-9A-Za-z.-]+)?$`, at most 64 characters.
- **Pointer files.** `current` and `previous` hold UTF-8 text: exactly one version and one newline, at most 65 bytes. A pointer is replaced by writing a sibling `<pointer>.tmp-<16 hex>` through exclusive creation with mode 0600, flushing it to disk, renaming it over the pointer and, on Linux and macOS, flushing the `runtimes/` directory. A symbolic link is never used, because creating one needs a privilege on Windows and a running `node.exe` locks its directory.
- **Windows rename.** When the rename reports `EPERM`, `EBUSY` or `EACCES`, it is retried with backoff for at most 2,000 ms in total. A rename that still fails stops with `POINTER_REPLACE_FAILED` and leaves the old pointer unchanged.
- **Reading a pointer.** A reader reads the whole file. A missing, empty, oversized or malformed pointer, or one that names a version with no installed directory, is `NO_ACTIVE_RUNTIME`; the launcher then offers reinstall or rollback and never picks a directory on its own.
- **Switch order.** A switch writes `previous` with the old version first and `current` with the new version second, so a process killed between the two writes leaves `current` naming the old, whole version.
- **Who switches `current`.** Only four events switch it: the first install when no `current` exists; an update through [C19](c19-home-process.md)'s handshake; a rollback the person requests through [C19](c19-home-process.md) or `delorun recover`; and [C19](c19-home-process.md)'s automatic rollback after a failed health check. A launcher never switches `current` on its own, whether it is newer or older than the active runtime.
- **`store.lock`.** The lock holds `{"v":1,"pid":<integer>,"id":"<32 lowercase hexadecimal digits>"}` at mode 0600, with the holder's `processStart` and `pidNamespace` as the home lock records them, and is created and replaced as the home lock is ([the home lock](#the-home-lock)): a lock in the reader's pid namespace, or without one, whose holder has exited or whose recorded start identity differs from the live process's is stale.
- **Installing.** An install takes `store.lock`, waiting at most 30 seconds before it stops with `STORE_BUSY`. It downloads into `~/.delorun/staging/<16 hex>/`, which lies outside `runtimes/` on the same filesystem, and runs the client verification of [C2](c02-release-manifest.md): the root and timestamp walk, the manifest's signature and freshness, the release-log bundle and online check ([C18](c18-release-log.md)), and the archive's and file list's digests. It extracts with path checks (no absolute path, no `..` segment, no link, no device file and no entry outside the file list), checks every file against the file list, then renames the staging directory to `runtimes/<version>/` and places the manifest, file list and bundle beside it. Nothing appears under `runtimes/` before every check passes, and a failed install removes its staging directory and changes nothing else.
- **Installed files.** After the rename, directories under `<version>/` have mode 0555 and files 0444, or 0555 for executables; on Windows they carry the read-only attribute. The launcher's start check ([C2](c02-release-manifest.md#client-verification)), which hashes every file or compares the identities recorded after the last hash, is the integrity control; the modes stop accidental writes only.
- **Retention.** After a switch commits, the store keeps the versions that `current` and `previous` name, with their release files and identity records, and removes every other `<version>/` with its release files and identity record, and every directory under `staging/` that no install holds. A removal that fails, such as a Windows directory still in use, is retried at the next start. At most two versions and one staging directory exist at once.
- **Rollback scope.** A runtime rollback changes no file outside `runtimes/` and its identity records under `trust/runtime-files/`. Restoring the profile from its history, and the chat data from a copy the person took, are [C3](c03-update-report.md#rollback)'s steps, and every rollback goes through C3's table.

## Launcher and store compatibility

A launcher runs the active runtime only when it understands both the store and the runtime's launch interface.

- `store.json` carries the store layout number, which is 1. The layout number changes only when an entry of the store moves or changes meaning.
- Each runtime's signed manifest ([C2](c02-release-manifest.md)) carries its launch protocol number, which is 1. The launch protocol fixes the runtime's entry file, the arguments the launcher passes and the environment variables it sets (`DSH_HOME`, `DELORUN_HOME`, `DELORUN_PROFILE`, and `DELORUN_LAUNCHER_ROOTS`, the directory of the release roots the launcher ships, which `delorun verify`, every update, every rollback and the health check's start check anchor the stored root on. A runtime started without it installs, updates and rolls back to nothing, refusing with `ROOT_NOT_ANCHORED`, and its `delorun verify` holds the stored root to its own signatures only and says so; and `DELORUN_LAUNCHER_VERSION`, the launcher package's own version, which `delorun setup` pins its install of the `delorun` command to and `delorun verify` compares with the release's signed `npm` entries. The launcher drops every inherited `DELORUN_LAUNCHER_*` variable, so the runtime sees only the values it sets. A runtime started without the version offers no install of the command, and the variable is optional within launch protocol 1, so a launcher that sets none still starts every runtime of that protocol; and `DELORUN_START_CHECK`, the JSON record `delorun.start-check/1` of what the start check of the runtime's files did, when it ran and which launcher ran it, which `delorun verify` and the studio report without hashing again; any program running as the person can set it, so it decides nothing, and a runtime without it reports the start check as unknown). Every process that starts a runtime (the launcher, an update's successor, the studio's Check now) passes on its own environment without the variables that load code into a Node, its dynamic loader or OpenSSL (`DROPPED_LAUNCH_ENV`: `NODE_OPTIONS`, `NODE_PATH`, `NODE_EXTRA_CA_CERTS`, `NODE_TLS_REJECT_UNAUTHORIZED`, `NODE_COMPILE_CACHE`, `NODE_V8_COVERAGE`, `NODE_ICU_DATA`, `OPENSSL_CONF`, `OPENSSL_MODULES`, `OPENSSL_ENGINES`, `GCONV_PATH`, `LOCPATH`, `LD_*`, `DYLD_*`, in any letter case); only the launcher also drops `DELORUN_LAUNCHER_*`, because an update's successor and the studio's Check now pass the launcher's values on.
- The launcher runs `current` when it supports the store's layout number and the runtime's launch protocol number. Otherwise it stops with `RUNTIME_INCOMPATIBLE`, names both numbers and offers the update flow when the runtime is the older side, or a launcher update when the launcher is the older side. It changes neither `current` nor any other file of the store.

## The npm launcher and the install script

- **No runtime in the package.** The npm package `delorun` is the launcher only. It has no runtime dependencies and carries no runtime closure.
- **Download.** To install a version, the launcher downloads the release files that [C2](c02-release-manifest.md) names, over HTTPS only: every file from `releases.delorun.com` (the root and timestamp at its root, the manifest, its bundle, the file list and the per-platform archive (`.tar.gz`, or `.zip` on Windows) at `releases/download/v<version>/<file>`). Only when that host fails on the network or by HTTP status, or serves a file whose bytes do not match the signed reference, does it try the next origin: the GitHub Releases of Delorun's public repository for release files, then the spare host `releases.delo.run` for every file. A mirror's bytes pass the same checks, and the install reports which origin was skipped and which served. It follows redirects only to `releases.delorun.com`, `releases.delo.run`, `github.com`, `objects.githubusercontent.com` and `release-assets.githubusercontent.com`, and refuses any other host with `DOWNLOAD_REFUSED`, which no mirror retries. The release-log check reaches the host of the root metadata's `log.origin`, as [C18](c18-release-log.md) states. The channel's origin is a build constant of the launcher, and so is the log's origin in a build for a local log (a production build reads the log its trusted root names): the build passes them to the bundler, which writes them into the code, and no setting, argument or environment variable moves them afterwards. A build that names neither is the production launcher, with the hosts above. A build for a local channel may name an `https:` origin, or an `http:` origin on the computer's own loopback address, serving `timestamp.json`, `root/<n>.root.json` and `releases/download/v<version>/<file>` below it; the downloader then allows that origin's host and no other.
- **Download limits.** An archive is at most 1,073,741,824 bytes (1 GiB) and a manifest at most 4,194,304 bytes (4 MiB). A connection that does not open within 30 seconds, or that delivers no byte for 60 seconds, fails the download.
- **Verification before install.** The launcher verifies the archive against the signed manifest ([C2](c02-release-manifest.md)) and the manifest's entry in the release log ([C18](c18-release-log.md)) before any file appears under `runtimes/<version>/`, as [the runtime store](#the-runtime-store) states.
- **Without network.** The launcher runs the installed `current` after its offline start check. An install always needs the network and the log inclusion proof.
- **A `current` that fails its check.** When `current` fails the start check and `previous` passes it under the same anchored root, a bare `delorun`, `delorun start` or `delorun recover rollback`, each with only `--profile` options and nothing after `--`, makes the launcher print one line saying so and start `previous` with `delorun recover rollback`, the profile passed in `DELORUN_PROFILE`; that command applies [C3](c03-update-report.md#rollback)'s rollback table and refuses with `NO_UPDATE_RECORD` when no update to `current` is recorded. Every other command is refused: the launcher starts no release and changes nothing, names the release that failed its start check with the check's reason, names `delorun recover rollback` as the command that starts `previous` to roll back to it, and exits 1. Without such a `previous`, and whenever a release was named with `--release`, the start's refusal stands. The launcher switches no pointer itself.
- **Trust anchor.** `npx delorun` runs the launcher that npm serves before any Delorun check can run. No workflow publishes the package, so no build attestation ties it to the public repository; publication with an attestation, and install scripts trusted through a published hash, are in the [release workflow design](../design/release-workflow.md).
- **The launcher copy.** No install script exists and `delorun start` installs no login item, so nothing writes `bin/`.

## Confinement rules

Upstream's sandbox dialects confine file writes only. In the CLI profile, which `delorun setup` creates and `delorun` or `delorun start` boots, Delorun's settings on upstream's sandbox provider add the rules below for every command that runs under `read-only` or `workspace-write`. `delorun headless` boots under the same overlay; `delorun plugin` boots no Host, and none of these rules applies to its commands. A command that runs under `danger-full-access`, whether set by the person or approved as an escalation, runs unconfined, and no rule in this section applies to it.

| Rule | Confined commands cannot |
| --- | --- |
| `home-write` | create, change or delete anything under the home |
| `home-read` | read anything under the home except the read exemptions |
| `token-read` | read the start token |
| `home-connect` | connect to a socket or pipe of the home's channels |
| `docker-connect` | connect to the Docker socket at its real path |
| `wsl-interop` | start a Windows program through WSL's interop, by path, by bare name or as a copy |
| `vsock` | create a virtual-machine (`AF_VSOCK`) socket, the transport between a virtual machine such as WSL and its host, or an io_uring instance, whose requests create sockets without the `socket` call |
| `session-escape` | connect to a socket in the person's runtime directory `/run/user/<uid>`, the system bus's `/run/dbus`, a tmux server's `/tmp/tmux-<uid>`, GNU screen's `/run/screen`, the X server's `/tmp/.X11-unix`, WSLg's `/mnt/wslg`, or Docker Desktop's `/mnt/wsl/docker-desktop/shared-sockets` and `~/.docker/desktop`, through which a program starts outside the sandbox or acts with the person's authority |
| `daemon-connect` | connect to Docker Desktop's `/run/docker-cli.sock` or tailscaled's LocalAPI socket (`/run/tailscale/tailscaled.sock`, `/var/run/tailscaled.socket`) |
| `agent-connect` | connect to the ssh-agent socket `SSH_AUTH_SOCK` names when `delorun start` runs |
| `private-tmp` | read or connect to anything in the host's `/tmp` outside a workspace that lies in it |
| `network` | open a connection to a network host their workspace's network setting does not allow: none under `off`, only the listed hosts and ports through Delorun's egress proxy under `allowlist`; `open`, the default, allows every host. The rule covers the connections the command opens itself and the daemons rule 19 hides; a daemon behind another pathname socket the command reaches, such as an ssh ControlMaster socket or gpg's `S.dirmngr` under the person's home, can still open one for it |

- **Read exemptions.** Confined commands may read and execute `runtimes/`, `skills/` and `dsh-runtimes/`. The PTC worker and other confined processes run the runtime's own `node` from `runtimes/`, commands run the person's skill scripts from `skills/`, and the desktop app's workspace dependencies run from `dsh-runtimes/`. The CLI profile's start adds one more read-only entry, the profile's approved plugin copies at `changes/profiles/<profile>/active/`, so a plugin that hands an agent the path of its own tool works; the entry holds only approved copies, never pending or unapproved content, another profile's copies, or the records and log beside them, and a confined command cannot write it. No secret is written under an exemption; a component that keeps a secret uses `secrets/`. The model-facing file and search tools may also read the calling chat's own directory under `spill/`, where tool output too long for that chat is saved for the model to read, and no other chat's; confined commands may not read `spill/`, and no runner grants it.
- **Writable roots.** The home is never inside a writable root. `workspace-write` is refused with `HOME_IN_WRITABLE_ROOT` when the workspace root or an additional writable root, after resolving symbolic links, equals the home, lies inside it or contains it. A workspace whose root contains the home, such as `~`, still runs `read-only` commands.
- **The Docker socket.** The socket lies outside the home. `delorun start` resolves its path from the active Docker context: `/var/run/docker.sock` for a rootful engine, `$XDG_RUNTIME_DIR/docker.sock` for a rootless one, or the path Docker Desktop's context names. The rule covers the context's path, its resolved real path, every other mount on Linux that reaches the same socket found when a command is wrapped (such as Docker Desktop's `/mnt/wsl/docker-desktop-bind-mounts/<distro>/docker.sock` under WSL), and on macOS Docker Desktop's sockets `docker.raw.sock` and `docker.sock` under `~/Library/Containers/com.docker.docker/Data/` and `~/.docker/run/docker.sock` when they exist at the start. Docker Desktop's other control sockets are denied too: `delorun start` names `/mnt/wsl/docker-desktop/shared-sockets` and `~/.docker/desktop` as escape socket directories (`session-escape`) and denies `/run/docker-cli.sock`, which serves its backend's API to the `docker` group, by path (`daemon-connect`). Its macOS control directories `~/Library/Containers/com.docker.docker/Data/` and `~/.docker/run/` are not hidden whole; that is in the [native confinement design](../design/native-confinement.md#docker-desktops-control-sockets). A context whose endpoint is TCP or SSH uses the network, which no dialect confines, so `docker-connect` is not enforced for it.
- **Session sockets.** The directories of `session-escape` hold the sockets of the person's session: in `/run/user/<uid>`, the session bus `bus` and the user manager's `systemd/private`, through which `systemd-run --user` starts any program as a user unit outside every namespace with the host's network and the whole home, gpg-agent and its ssh socket, the keyring, the display and audio servers, editors' and terminals' control sockets, and rootless Docker and Podman; the system bus, which acts with the polkit authorisations of the person's session; tmux and screen servers, which run commands in the person's terminal sessions; the X server, which takes input for the person's other windows; under WSL, WSLg's display and audio sockets and its second mounts of `/run/user/<uid>` and of `/`; and Docker Desktop's control sockets under WSL and on Linux, among them its backend's API, whose routes include its settings, the engine's `daemon.json` and container actions. `delorun start` names the same directories on every machine with a user id, from the user id and the OS home alone, and the provider checks at each wrap which exist. A runtime directory that `XDG_RUNTIME_DIR` names elsewhere and a tmux socket directory under `TMUX_TMPDIR` are not named.
- **The ssh-agent.** An agent signs with the person's keys for any client that connects. Confined commands do not inherit `SSH_AUTH_SOCK`, `agent-connect` denies the socket it names at the start, and `private-tmp` and `session-escape` hide the places agents listen by default. No profile setting forwards an agent to confined commands; a command that needs one, such as `git push` over ssh, runs through an approved `danger-full-access` escalation.
- **The host's `/tmp`.** Under bwrap a `workspace-write` command already gets an empty writable `/tmp`; `private-tmp` gives a `read-only` command an empty read-only one, with a workspace root that lies under `/tmp` bound back read-only, and hides every other mount of the host's `/tmp`, such as WSLg's `/mnt/wslg/distro/tmp`, in both modes. A `read-only` command, and the `glob` and `grep` searches, which run `read-only`, therefore find nothing in `/tmp` outside the workspace; a search rooted there fails with `ENOENT`.
- **Other sockets.** Other pathname sockets, such as those under the person's home or a runtime directory that `XDG_RUNTIME_DIR` names elsewhere, abstract sockets, and the network of a workspace whose network is `open`, stay reachable for confined commands ([what this does not prove](#what-this-does-not-prove)).
- **The network setting.** `@delorun/plugin-permission-defaults` keeps each workspace's network in `secrets/permission-defaults/network.json` at mode 0600, keyed by the workspace's canonical path; a workspace without an entry has the `network` and `allowedHosts` of the row `delorun-permission-defaults`, `open` and none by default. It mounts the `sandboxNetwork` resolver, so each confined command's policy carries `off` or the egress proxy's socket. The proxies listen on `secrets/permission-defaults/proxy/<pid>/<list>.sock`, one per distinct allowlist, before any policy names them; bwrap binds a command's own socket inside the home's tmpfs, so no other socket under the home becomes reachable. The setting is read and changed only through `/api/delorunNetwork.list` and `/api/delorunNetwork.set`, which answer only a request on the loopback listener under a loopback `Host`, and a change that loosens it needs the person's confirmation there. A store that is laxer than 0600, a link or another format counts every workspace as `off` until the person fixes it. The person's [guide](../guide/safety-and-updates/prompt-injection.md) states what each setting closes.
- **Reporting.** No probe runs at start, and `delorun verify` reports the `confinement-rule` check of [C15](c15-verification-checks.md) as not run, so nothing reports which rules hold on a machine. The sandbox provider computes whether it found every other mount of the home and of each denied socket (alias coverage), and nothing reads that result. The probes, the check and setup's Docker labels are in the [native confinement design](../design/native-confinement.md#checks-at-each-start).
- **The escalation prompt.** The approval prompt for a `danger-full-access` escalation is upstream's, which names the requested mode and the operation and does not say that full access reaches Delorun's home, its keys and tokens or the update channel. The statement is in the [native confinement design](../design/native-confinement.md#full-access).

## Consumers

- `delorun/apps/cli`: the `delorun` command and the CLI profile, through `delorun/packages/home`.
- `delorun/packages/home`: home resolution, the home tree and its modes, reading and writing protected files under the refusal rule, and the home lock.
- `delorun verify` and `delorun doctor` (`delorun/apps/cli`): `doctor` checks the home's directory modes and, on Linux, whether bwrap creates a sandbox, naming Ubuntu's AppArmor user-namespace restriction when it is on; the `verify` checks of modes and of each confinement rule are not built.
- Upstream's `packages/sandbox/sandbox-local` and `packages/sandbox/sandbox`: the per-dialect profiles and the writable-root refusal.
- `delorun/apps/install` and `delorun/apps/npm-launcher`: the download, verification and the launcher copy.
- `delorun/packages/runtime-store`: the store, the pointer files, install, switch and retention.
- `delorun/packages/home-process`: holding the lock through `delorun/packages/home`, the start token and the update channel's socket ([C19](c19-home-process.md)).
- `delorun/packages/supervisor`: the supervisor's socket and its token check ([C9](c09-runtime-supervisor.md)); no command launches it.
- `delorun/packages/home-auth`: the secret files under `secrets/home-auth/`, read and written through `delorun/packages/home`; every CLI profile loads it. `delorun export` writes the home key there.

## Compatibility

- The tree changes only by adding entries. Moving an entry, renaming it or changing its meaning raises the store layout number or is a breaking change with an upgrade guide under `delorun/docs/upgrade-guide/`, and the runtime that makes the change reads both forms.
- `DELORUN_HOME`, `DELORUN_PROFILE`, the CLI profile name and the channel paths are external interfaces; changing one is a breaking change with an upgrade guide.
- Upstream's entries keep upstream's layout and compatibility rules, including its Session format.
- The launch protocol number rises only with a change to the entry file, the arguments or the environment that the launcher passes. A launcher supports every launch protocol number of the runtimes it can install.
- The types package follows Delorun's version and changes in the same pull request as this page.

## Security

### Requirements

1. The home has mode 0700 and its protected files 0600. A component refuses a protected file that is laxer, a symbolic link or another user's, and the home process refuses to start on a laxer home, `secrets/` or `run/<profile>/`. `delorun verify` checks every one of them and prints the `chmod` fix, or on Windows the `icacls` fix. Not built: the `verify` check and every Windows check.
2. Delorun's secrets live in files under `secrets/`, a directory every dialect denies reads of where it enforces `home-read` in the CLI profile. Upstream's credential files lie under the home and fall under the same rule. No secret is written to a read exemption, a profile, a patch file, a command's environment or command line, or a log. A value for a loaded plugin's secret-role config field is refused by the configuration editor and the profile history, and moved into the credentials file at start where the plugin can name it ([secrets](#secrets)).
3. Confined commands cannot write anything under the home on any dialect, and cannot read anything under it except the read exemptions wherever the dialect enforces `home-read`.
4. Confined commands cannot connect to the home's channels or to the Docker socket at its real path wherever the dialect enforces `home-connect` and `docker-connect`. bwrap mounts an empty tmpfs over the home and binds `/dev/null` over the Docker socket's real path, never over its parent directory, which can hold sockets that this rule does not name. Seatbelt denies `file-read*` on the home and denies `network-outbound` to the `remote unix-socket` path literal of each channel socket and of both Docker socket paths. Landlock cannot deny a connect to a pathname socket, so `home-connect` and `docker-connect` are reported as `not-enforced` there.
5. Under Landlock the read denial on the home keeps the start token unreadable, so a confined command can connect to either channel but its request fails authentication, and `delorun verify` reports that state. Not built: the report.
6. Both channels accept a request only with the token of the current home-process start; a missing token, a wrong token and a previous start's token are refused alike. The token is 256 bits from the OS random source, is never logged or passed in a command line or environment, and is compared in constant time.
7. The protection rests on confining the agent's commands. A process of the person's user that runs outside the sandbox can read the token and can already run `delorun` and `docker` itself, and this contract claims no protection against it. No root-owned helper exists.
8. Commands under `danger-full-access` run unconfined; none of the rules above applies to them, and `delorun verify` reports `unconfined` for a workspace in that mode. The approval prompt for that mode states that full access reaches Delorun's home, its tokens, the Docker supervisor and the update channel. Not built: the report and the prompt's statement.
9. The home is never inside a writable root, and `workspace-write` with a root that equals, lies inside or contains the home is refused.
10. A launcher never switches `current` on its own. An install verifies the archive, the manifest's signature and freshness, its log inclusion and every file hash before any file appears under `runtimes/<version>/`, and a pointer is replaced only by an atomic rename.
11. Delorun never reads or writes upstream's `~/.dsh`.
12. On a Landlock-only system with a rootful Docker socket, `delorun verify` reports the socket as not enforced, and setup names it and offers the rootless engine. Not built.
13. Every command that boots a Host applies rules 2 to 4 and 9. Not built: `delorun plugin` boots no Host and applies none of them.
14. Under WSL, the kernel's `WSLInterop` binfmt handler starts any executable with a Windows header, wherever it lies, by sending a request to a socket in `/run/WSL`, which it finds whether or not `WSL_INTEROP` is set; the Windows process runs outside every Linux namespace, mount rule and protected home, with the person's Windows account. `delorun start` names `/run/WSL` as an escape socket directory on every machine, and the provider checks at each wrap whether it exists. Where it does, bwrap mounts an empty read-only tmpfs over it, so the program fails to start whichever way the command reaches the handler through those sockets: by its `/mnt/<drive>` path, by bare name through `PATH`, as a copy, through `/init` called directly, or with `WSL_INTEROP` naming a socket. A confined command sees `binfmt_misc` only read-only and without the handler's registration. A dialect that cannot deny socket connects, Landlock on Linux, refuses every confined command with `SANDBOX_UNSUPPORTED_POLICY` while the directory exists. WSL's kernel offers virtual-machine sockets to Windows, which rule 15 refuses. A workspace on a Windows drive stays readable and writable as its policy says. Not built under `delorun plugin`, as rule 13 states.
15. Wherever the kernel offers virtual-machine sockets, as `/proc/net/protocols` lists `AF_VSOCK` at a wrap, or an escape socket directory exists, or the list cannot be read, bwrap starts every confined command under a seccomp filter. It refuses `socket(AF_VSOCK, …)` with `EAFNOSUPPORT` and `io_uring_setup` with `ENOSYS` on x86-64 (x32 numbers included), i386, AArch64 and 32-bit Arm, and refuses every call of an architecture it does not name with `ENOSYS`. A kernel that loads vsock only on a first call has no hypervisor transport loaded, and such a socket reaches only the local loopback transport. The filter applies on any virtual machine with vsock, not only under WSL, and there: a program that requires io_uring fails; a 32-bit program that creates sockets through `socketcall`, as 32-bit glibc older than 2.23 does, cannot create any socket, because the filter cannot read that call's family; and on a host whose architecture the filter does not name, such as RISC-V, every confined command fails with a bwrap diagnostic. bwrap reads the filter from descriptor 9, so the wrap starts it from `/bin/sh`; a caller's descriptors 3 to 7 reach the command and its descriptors 8 and 9 do not, a missing `printf` or a closed standard input fails with a `bwrap:` diagnostic before the command starts, and the shell stays bwrap's parent, so a command whose bwrap is killed by a signal reports exit status 128 plus the signal's number. Landlock applies no seccomp filter; under WSL it refuses every command by rule 14, and on other virtual machines it leaves vsock and io_uring open. Not built under `delorun plugin`, as rule 13 states.
16. Confined commands cannot reach the pathname sockets of the person's session that start a program outside the sandbox or act with the person's authority. `delorun start` names the directories of `session-escape` as escape socket directories on every machine, and the provider checks at each wrap which exist. Where one does, bwrap mounts an empty read-only tmpfs over it and over every other mount of it the mount table lists, so `systemd-run --user` and `busctl --user` find no bus at a path, `tmux` and `screen` find no server, and an X client finds no display socket under `/tmp/.X11-unix`. Abstract sockets are not hidden: bwrap shares the host's network namespace, so an X server's `@/tmp/.X11-unix/X<n>` on a Linux desktop and a session bus whose address `dbus-launch` made abstract stay reachable, and through such a bus `systemd-run --user` starts a program outside the sandbox. Seatbelt denies `network-outbound` to the path literal of each entry present at the wrap. Landlock, which cannot deny a connect to a pathname socket, refuses every confined command with `SANDBOX_UNSUPPORTED_POLICY` while one of them exists, which on Linux is wherever logind, elogind or WSLg made the runtime directory or a system bus listens. Because an escape socket directory exists on nearly every Linux machine, rule 15's filter applies there too, and a program that requires io_uring fails in a confined command. A path inside a hidden directory gets no mount of its own: the hidden directory already covers it. Not built under `delorun plugin`, as rule 13 states.
17. `delorun start` adds the ssh-agent socket that `SSH_AUTH_SOCK` names in its launch environment, and the socket's real path, to the denied sockets, and the sandbox row sets `privateTmp`. bwrap binds `/dev/null` over the agent's socket and gives every confined command a `/tmp` without the host's files and sockets, as `private-tmp` states; Seatbelt denies the agent's path literals and, like Landlock, does not express `private-tmp`, under which a `read-only` command reads the host's `/tmp`. No layer can turn `privateTmp` off: the start's overlay sets it, the start refuses a booted row without it, and an update's H3 refuses a successor whose row turns it off.
18. `delorun start` denies the daemon sockets of `daemon-connect` on every machine with a user id, whether or not they exist at the start: Docker Desktop's `/run/docker-cli.sock` under WSL, which serves its backend's API to the `docker` group, and tailscaled's LocalAPI socket, through which its operator changes the node's settings. bwrap binds `/dev/null` over each that exists at a wrap and Seatbelt denies its path literals; Landlock cannot deny the connect. Not built under `delorun plugin`, as rule 13 states.
19. A confined command's network follows its workspace's setting ([confinement rules](#confinement-rules)). Under bwrap, `off` and `allowlist` start the command in a network namespace of its own, which holds only a loopback interface and none of the host's abstract sockets; under `allowlist` the egress proxy's socket is the only path out, the proxy refuses a host or port that is not listed before looking it up, refuses a listed name that resolves to an address the fetch guard refuses, connects only to the addresses it checked, and sends a plain-HTTP request with the host it checked. bwrap binds the proxy's socket after the hidden directories and the home's read-only remount and before `/tmp` turns read-only. Under both settings, bwrap also hides systemd-resolved's varlink directory, nscd's, avahi's and snapd's sockets, CUPS's `/run/cups`, the system D-Bus and tailscaled's socket, so the command cannot reach those daemons. A namespace does not cut off pathname sockets: every pathname socket that neither this rule, `session-escape`, `daemon-connect` nor `agent-connect` hides stays reachable, and a daemon behind one can open connections for the command, such as an ssh ControlMaster socket, or gpg's `S.dirmngr` where gpg has no runtime directory, under the person's home. Landlock, Seatbelt and windows-acl refuse every command of such a workspace with `SANDBOX_UNSUPPORTED_POLICY`. `web_fetch` follows the same setting. The setting changes only at the home's computer, a loosening only after the person confirms it, and no tool of the model and no `plugin_manager` change reaches it. A command under `danger-full-access` reaches the network whatever the setting.
20. None of these guarantees holds while the debugger of `delorun start --inspect` listens: any process on this computer that reaches `127.0.0.1:9229`, a confined command included, can run code as the home process, outside the sandbox. The start opens it only after the person confirms at a terminal or with `--yes`, never in safe mode, and keeps `run/<profile>/inspector.json` (mode 0600) while it listens, which `delorun status` reports.

### What this does not prove

- **Landlock and sockets.** Landlock cannot deny a connect to a pathname socket. On a Landlock-only system without any escape socket directory, such as a container, a confined command reaches a rootful Docker socket, which is equivalent to root, and the ssh-agent socket, and nothing reports it; no Delorun mechanism closes it there. The update channel stays closed only because the start token is unreadable.
- **Sockets outside the named places.** `session-escape`, `agent-connect` and `private-tmp` cover the places session services listen by default, not every socket a person's program may create. A socket under the person's home stays reachable, such as gpg-agent's `~/.gnupg/S.gpg-agent` on a system without a runtime directory, an agent the start's `SSH_AUTH_SOCK` did not name, a password manager's agent or an editor's server, and so do a runtime directory that `XDG_RUNTIME_DIR` names elsewhere, a tmux server under `TMUX_TMPDIR`, and a group-owned daemon socket that grants root, such as libvirt's, LXD's or Incus's, which `docker-connect` does not cover. Abstract sockets stay reachable on every dialect, as the WSL item below states; on a Linux desktop an X server also listens on the abstract name `@/tmp/.X11-unix/X<n>`, so `display-denied` does not keep a confined command from that X server there, and a session bus that `dbus-launch` started on an abstract address is not hidden by `session-escape`, so `systemd-run --user` through it starts a program outside the sandbox. A private network namespace, or Landlock's abstract-socket scope from Linux 6.12 applied inside bwrap, would close both; bwrap applies neither.
- **Sockets recreated after a command starts.** bwrap binds `/dev/null` over a denied socket's path when the command is wrapped; a socket that is removed and created again at that path afterwards, such as after a Docker engine restart, is a new file that the bind does not cover, so a command that started before is not denied it. A component that keeps confined commands running for long, such as a terminal or a background job, rewraps or stops them when a denied socket is recreated; that component's contract carries this requirement.
- **Filesystems that hide their aliases.** Aliases are found by matching a path's device in `stat` against the mount table. btrfs and bcachefs subvolumes and overlayfs layers report devices the table does not tie to their other mounts, so on those filesystems aliases may go unfound; the provider reports alias coverage as `unknown` there, and no rule that depends on it reads `enforced`. A filesystem that exposes the home elsewhere under another device, such as a FUSE mirror, is not detected on any filesystem.
- **Bind mounts of replaced files.** A bind mount of a file under the home stays attached to that file after it is deleted or replaced, such as a key rotated by an atomic rename. The mount table then marks its root deleted, alias detection skips it, and its mount point still reaches the old contents; no profile covers it.
- **The write tools' check-then-write window.** The in-process write fence checks a path and then writes by path, so a confined command running at the same time can swap a directory on that path for a link in between; [descriptor-based writes](https://github.com/twickas/delorun/issues/71) would close it.
- **Mounts and links added later.** The profiles cover the other mounts of the home's filesystem and of each denied socket that exist when a command is wrapped. A mount added while it runs, and a hard link made outside the sandbox to a file under the home, are not covered.
- **Landlock and the home's ancestors.** Landlock grants reads by directory tree, so the profile grants every entry beside the way from `/` to the home rather than those directories themselves: a confined command cannot list `/`, the OS home or any other directory on that way, and an entry created in one of them after the command starts is unreadable to it. The entries are listed when the command is wrapped, so an entry removed before the launcher applies the ruleset makes the launcher refuse the run; the command does not run, unconfined or otherwise.
- **Windows.** windows-acl confines writes only. A confined command on Windows can read everything under the home, Delorun's secrets, upstream's credential files and the start token included, so the token does not keep it from the update channel, and the home's modes are not checked there.
- **Commands outside the CLI profile.** `delorun headless` boots under the same sandbox overlay as the CLI profile, so its confined commands get the rules above, and its profile loads `@delorun/bundle-headless`: the fetch guard, the instruction write, MCP and schedule consents, the full-access consent and the turn gate apply, protected from plugin management, a guard that asks a person refuses because the profile composes no approval answerer, and full access is refused for a working directory without a grant, which the person records at the home's computer in the studio or with `delorun workspace full-access`; under `delorun plugin`, which boots no Host and applies no overlay, a command that a plugin operation runs can read the whole home, the start token included, and connect to the update channel's socket.
- **WSL below the interop sockets.** Under bwrap the `vsock` filter refuses vsock sockets and io_uring. Abstract Unix sockets stay reachable on every dialect: a connect names its address in memory, which a seccomp filter cannot read, and the only kernel rule that scopes them, Landlock's abstract-socket scope from Linux 6.12, is not available on the 6.6 kernel WSL ships and is not a rule bwrap applies. WSL itself listens on none: its interop sockets are pathname sockets under `/run/WSL`, and the abstract names a WSL install lists belong to the connected ends of systemd's bus connections, which accept no connection. A program the person runs that listens on an abstract socket is reachable from confined commands. Hiding them all takes a network namespace (`--unshare-net`), which also removes network access, so only commands of a workspace whose network is `allowlist` or `off` lose them. WSLg's display and audio sockets (`/tmp/.X11-unix`, `/mnt/wslg`) are hidden by `session-escape`; the inherited `WSL_INTEROP` and `WSLENV` variables stay visible and name only the hidden socket and the shared variable names.
- **The desktop app as a user of the chat data.** The desktop app shares `sessions/` and the stores beside it, but no file under the home shows whether it runs: `profiles/desktop/lock` is held only while the app prepares its profile, and its single-instance lock is the platform's, outside the home. So the home-wide exclusion of `run/data-users/` does not count it, and an update's copy, restore or rollback, `delorun trash`, `export` and `import` can run while the desktop app writes the same stores. This is an accepted gap because Delorun does not ship the desktop app.
- **Docker over the network.** A Docker context whose endpoint is TCP or SSH is reachable by any command with network access on every dialect.
- **Full access.** Commands under `danger-full-access` can read every secret under the home and the start token, and can reach the update channel; no rule applies, and upstream's escalation prompt does not say so.
- **Which bundle declares a protected row.** The start's check that the sandbox row and each Delorun row come from the bundle that declares them ([C19](c19-home-process.md#host-invariants)) recognises that bundle by its package name, `@deepseek-ai/dsh-base` or a name in the `@delorun/` scope, not by the package directory it resolved to. A package of that name that the profile resolves from somewhere other than the running release passes the check.
- **The person's own processes.** A process of the person's user outside the sandbox can read and change everything under the home; the modes protect against other users, not against it.

- **Linux without bwrap.** Where unprivileged user namespaces are unavailable, bwrap fails its probe and upstream's provider selects Landlock. Where neither works, upstream's provider refuses to run confined commands, and every rule reads `unconfined` for a workspace the person runs in `danger-full-access`.
- **Landlock grants.** The layered ruleset grants each sibling along the path from `/` to the home, so a file created during a confined command directly in one of the home's ancestor directories is unreadable to that command.
- **macOS paths.** Seatbelt matches resolved paths, so the profile names `/private/var/...` for `/var/...` and both the Docker Desktop context path and its real path.
- **WSL2.** Delorun inside WSL2 is Linux, and the Linux columns apply. The Windows host's processes are outside the sandbox; `wsl-interop` and `vsock` keep confined commands from starting them and from reaching Windows over the virtual-machine transport.
