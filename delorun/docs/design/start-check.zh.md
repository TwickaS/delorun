# 启动检查与身份记录

[English](start-check.md) | 中文

## 摘要

在这项更改之前，每条 `delorun` 命令在运行任何东西之前，都会读取并哈希已安装运行时的每个文件，大约 35,000 个文件和 770 MB：每条命令约 9 秒，而同一条命令不带检查只需 0.4 秒。现在，普通的启动像以前一样列出安装内容，并把每个文件的身份（inode、模式、大小，以及以纳秒计的修改时间和更改时间，在安装所在的设备上）与文件上次被哈希或写入之后写下的一份记录进行比较，只对记录无法担保的内容做哈希。完整的哈希仍然保留在安装时、`delorun verify` 和 studio 的 Check now 之前及其内部、默认每 7 天一次，以及记录或文件系统无法担保的任何地方；更新会对它读取并启动的运行时运行启动检查，因为它在写入新运行时的文件时就已经对它们做了哈希。这份记录不带密钥，所以以此人的权限运行的程序可以重写它，并向普通的启动隐藏已被更改的文件（包括运行时的 Node 和 `delorun` 自己的文件），直到下一次完整哈希；`delorun verify` 和 Check now 会先对每个文件做哈希，从而发现它。规则见[约定 C2](../contracts/c02-release-manifest.zh.md#client-verification)；本页保留理由、局限和测量结果。

## 每次启动的哈希保护什么

已安装的文件具有只读模式，并且受限命令在任何方言上都无法在 home 之下的任何位置写入（[C1](../contracts/c01-home-layout.zh.md#confinement-rules)），所以每次启动的哈希并不是阻止受限命令的东西。它阻止的是文件已通过其他途径发生变化的运行时在无人注意的情况下启动：人或工具编辑或替换了文件、部分或不匹配的恢复或同步、杀毒软件的隔离、故障磁盘，以及以此人自己的权限运行、在更改运行时文件的同时没有更改启动器的程序。C2 已经陈述了这一局限：同时更改启动器、已存储的根或检查本身的、拥有此人权限的进程可以击败它。

## 决定

- **普通启动时使用身份，而不是哈希。**在受信任的文件系统上，没有任何非特权进程可以把更改时间调回去，所以身份不变就意味着文件未被写入，这对启动检查以前所阻止的每个行为者都成立。对缺失、多余和不规则条目的列举在每次启动时仍然进行。
- **跨运行不使用设备号。**WSL2 和 device-mapper 会在重启时重新编号设备，这会使每份记录在一次重启之后都不可用。因此，每个文件的设备必须等于安装目录当前的设备，而记录会绑定该目录的 inode。
- **竞争条目。**与 git 的 racy-clean 规则一样，更改时间落在记录捕获时间之后 2 秒之内的身份不能担保任何东西，会被哈希，直到之后的一次捕获把它抛在后面：在同一个时钟步长内的写入，或在只存储整秒的文件系统上同一秒内的写入，可以保持住更改时间。安装会等到它写入的最新文件已有 2 秒之久才进行捕获，所以其后的第一次启动不需要对任何东西做哈希。
- **只从哈希或写入进行捕获。**哈希在读取之前和之后对它自己的描述符取 `fstat`，只有当两者相等且在安装所在的设备上时才记录身份；安装则记录最后一次写入之后解压的 `fstat`，并在树移入之前用 `lstat` 加以确认。记录在 `store.lock` 之下以原子方式写入；启动或完整检查不等待该锁，并在安装、切换或移除持有它期间让记录保持原样。按需的完整检查只在有新的内容要记录时才写入，所以 `delorun verify` 和启动器在拒绝某条命令之前对 `previous` 所做的检查，会让完好的 home 保持原样。
- **在所有读取豁免之外。**记录位于 `trust/runtime-files/` 之下，模式为 0600，而不是位于受限命令可以读取的 `runtimes/` 之下。它的绑定（schema、版本、平台、文件列表和 manifest 的 SHA-256、目录的 inode、文件系统的类型和捕获时间）使另一个发布版本、安装或文件系统的记录不可用，而任何不可用都意味着完整哈希，而绝不是通过。
- **没有密钥。**每个能写入这份记录的进程（在沙箱之外以此人自己的权限运行的、root 的，或对磁盘的离线编辑），也都能读取同一个 home 下的任何密钥、更改运行时的文件并替换启动器。签名或 MAC 不会阻止启动检查以前未能阻止的任何人。
- **受信任的文件系统。**Linux 上的 ext2 到 ext4、XFS、Btrfs、F2FS 和 tmpfs，在安装上用 `statfs` 读取并在每次启动时重新检查。其他一切都在每次启动时对每个文件做哈希：NFS、SMB、FUSE、virtiofs、9p 和 WSL 的 drvfs 报告的是由另一方选择的时间；overlayfs 无论其各层位于何处都报告它自己的类型，所以 NFS 或 FUSE 下层会冒充本地下层，而位于不同设备上又没有 `xino` 的各层无论如何都会使每次启动对每个文件做哈希；Windows 允许文件的所有者设置它的更改时间（NTFS 的 `ChangeTime`）；macOS 则要等待一项在 APFS 上的测试来证明非特权进程无法在那里把更改时间调回去（内核在 `setattrlist` 中忽略 `ATTR_CMN_CHGTIME`，但这里没有在 macOS 上运行的测试）。
- **间隔。**`DELORUN_RUNTIME_FULL_CHECK_DAYS`，为 0 到 30 的整数天，未设置时为 7；0 表示每次启动都对每个文件做哈希，任何其他值都会让启动器带着其用法说明停止。它是环境变量，因为启动器不读取设置文件；一旦那里读取设置，它就属于 [C15](../contracts/c15-verification-checks.zh.md#modes) 的 `integrity.mode`。
- **更新中的启动检查。**更新在打开渠道之前检查正在运行的运行时，对较早一次 `delorun update --check` 安装的目标像任何启动那样检查它，在切换之前检查目标，并作为健康检查的 H1 再次检查目标，每次都使用启动检查和启动器的间隔。完整哈希在这些时间点上没有增加任何东西：正在运行的运行时在启动时通过了启动检查，目标的每个文件都是根据安装所写入的字节做的哈希，而安装当时捕获的记录担保每个身份此后没有变化的文件；身份发生变化的文件则像在任何启动中一样被哈希。紧接着安装之后的完整遍历还会从页面缓存读回这些字节，所以它同样发现不了存储这些字节失败的磁盘。更新的准备在存储的 `shareChecks` 之内运行：渠道打开器对正在运行的运行时的检查、目标的安装或完好检查，以及更新报告的 `running`、`target` 和 `data` 读取器，对每个运行时共享一次文件检查；启动检查共享那里对该运行时的任何较早检查，完整检查只共享完整检查或安装。回退的目标在回退启动它之前仍然要进行完整哈希，因为回退是从可能已损坏的发布版本返回的途径。
- **Check now 通过启动器运行。**studio 的 Check now 通过启动记录所指名的启动器，在运行时自己的 Node 之下，把 `delorun verify --json` 作为子进程运行，而不是在 Host 内部运行 `verify` 阶段，因为 Host 所加载的代码是普通启动凭记录的一句话接受下来的。当没有启动器启动运行时，或者它的入口无法解析时（例如源码启动），Host 自己运行该阶段，并且面板会连同这一局限说明这一点，并指向终端中的 `delorun verify`。
- **`delorun verify` 在运行之前先做哈希。**启动器给 `delorun verify` 的间隔为 0，所以在命令开始之前，无论记录怎么说，每个运行时文件都会被哈希，然后命令用它自己的代码再次对每个文件做哈希。

## 身份检查能检测什么

在 Linux 上，非特权进程无法设置文件的更改时间：`utimensat` 设置访问时间和修改时间，并把更改时间移到现在，而设置时钟需要 `CAP_SYS_TIME`。每一次对该路径的写入、截断、`chmod`、`chown`、链接或重命名，都会给文件一个新的更改时间或新的 inode。所以对照记录，身份检查能检测到：

- 通过路径或硬链接，用 `write` 或 `truncate` 就地更改的文件，无论是否恢复了它的大小、模式和修改时间：它的更改时间会移动。通过共享可写内存映射的写入是个例外：内核在页面上一次被写回之后对该页面的第一次写入时才移动时间，所以通过在记录被捕获之前打开的映射所做的写入，在那之前可以让这些时间保持不变；
- 通过重命名替换、或被删除后又创建的文件，即使大小、模式和时间都相同：新的 inode，或相同的 inode 号但更晚的更改时间；
- 从保留修改时间的备份中恢复的文件：恢复会给它新的 inode 和更改时间，所以它会被哈希；当它的字节与列表匹配时，它会被重新记录，否则启动停止；
- 通过列举发现的缺失、多余、链接或不规则的条目，与完整哈希一样；
- 被复制、同步或重新安装的 home：安装的 inode 不同，所以记录不可用，启动会对每个文件做哈希；
- 被特权进程移动的时钟：身份是按相等来比较的，所以在任何时钟跳变之后所做的更改，除非落在同一个时间戳步长上，否则仍然会得到与记录不同的更改时间；时钟被调回到最后一次完整遍历之前会使下一次遍历立即到期，时钟被调快则只会使它提前到期。

## 本设计不防护什么

- **没有更改时间的内容更改。**存储的静默损坏、对块设备的写入，或从另一个系统对磁盘的编辑，会在没有写入所带来的更改时间的情况下改变字节。下一次完整遍历（最迟在配置的间隔之后）和 `delorun verify` 会发现它；在那之前，启动不会。这是相对于每次启动都做哈希的唯一真实的损失，它是可靠性缺口，而不是攻击者的收获，因为攻击者需要 root 或此人自己的权限才能做出这样的更改。
- **与安装自己的写入处于同一时钟步长内的写入。**安装在从与列表匹配的字节写入每个文件之后，立即记录它的身份。在内核时钟的同一步长内（几毫秒，在只存储整秒的文件系统上最多一秒）对该文件的写入，然后用 `chmod` 改回安装时的模式，可以使身份保持不变，于是安装会记录下它并没有写入的字节。只有拥有此人自己权限的进程才能写入 0700 的暂存目录，而本威胁模型已经将其排除在外；下一次完整遍历会发现这一更改。
- **伪造的记录。**以此人自己的权限运行的进程可以更改任何运行时文件，包括 Node 可执行文件和 `delorun` 自己的文件，并把记录重写为它的新身份，将其最后一次完整遍历设为现在；此后普通的启动会通过，并在命令加载被更改的文件时运行它，直到此人运行 `delorun verify` 或 Check now，因为计划的完整遍历只在记录所指的时间到期。通过启动器，`delorun verify` 会在运行之前对每个文件做哈希并发现这一更改；studio 的 Check now 以同样的方式运行它。同一个进程也可以改为更改启动器、已存储的根或 `delorun verify` 本身，这是 [C2 的局限](../contracts/c02-release-manifest.zh.md#what-this-does-not-prove)已经陈述过的；以此人的权限运行的任何检查都无法在那种情况下幸存。

## 测量

`node_modules/.bin/tsx delorun/packages/runtime-store/tests/timing/start-check-timing.ts` 在一个临时 home 中构建一个与真实运行时大小相同（35,287 个文件，769 MiB）的已签名合成运行时，并为存储自己的操作计时；“之前”的行运行同样的代码，但对每个文件都做哈希，就像存储在这项更改之前所做的那样。2026-11-10 20:22 UTC 的记录：22 个 CPU（Intel Core Ultra 9 185H），WSL2 内核 6.6，ext4，Node 24.22.0，一台与其他运行共用的机器（平均负载 11 到 21，I/O 压力 1.2% 到 1.8%），页面缓存已预热；启动检查是三次的中位数，其余是单次采样。

| 操作 | 之前 | 之后 |
| --- | --- | --- |
| 启动检查，在测量进程中 | 9.1 s | 0.60 s |
| 启动检查，在通过 `tsx` 加载模块的新进程中 | 9.8 s | 0.92 s |
| 启动器式安装之后的第一次启动 | 9.1 s | 0.45 s |
| 安装在填充自身的写入之外的存储工作 | 12.0 s | 3.3 s（其中最多 2 s 是等待记录稳定的时间） |
| 更新在填充的写入之外的准备：打开器的检查、安装以及报告读取器的四次检查 | 83.6 s | 16.5 s |

等待时间基准的第一份记录，在同一台机器上、同一天，在这项更改之前通过启动器测量了每条命令：`--version` 9.9 s（运行时自己的 Node 为 0.4 s，仅启动器为 0.1 s），`status` 约 16 s，之后的 `start` 10.0 s，`stop` 8.8 s，在一次更新中构建更新报告 68.6 s。启动检查是这些命令中这项更改所触及的唯一部分，所以每一条现在大约少用 9 秒；`--version` 大约为 0.4 s 加上启动器和 0.6 到 0.9 s 的启动检查。这些命令没有在真实的 closure 上做端到端计时，因为主干的发布配方目前还无法构建出一个。

studio 中的 Check now 通过启动器运行 `delorun verify`，所以它对每个文件要付出两次代价：先是启动器间隔为 0 的启动检查，然后是命令自己的完整检查，再然后是在线的发布日志检查。同一个探测在 2026-11-11 13:17 UTC 于同一台机器上（平均负载 5 到 20，页面缓存已预热）对一个 35,287 个文件、769 MiB 的合成运行时测量了各个部分：对每个文件做哈希的启动检查在带模块加载的新进程中需要 9.5 s，仅完整检查在进程内需要 8.8 s；加上启动运行时命令的约 0.4 s，Check now 在在线检查之前需要约 19 s，而在线检查的时间取决于网络。整条路径没有在真实的 closure 上计时，因为主干的发布配方目前还无法构建出一个。

2026-11-12 的重复测量于 18:30 UTC 结束，在同一台机器上（来自其他运行的平均负载 17 到 22，I/O 压力低于 1%），启动检查保持现状，测得稳定后的启动检查在进程内为 452 ms，在新进程中为 749 ms，而对每个文件都做哈希时分别为 6.9 s 和 7.3 s。

在剩下的 0.6 s 中，大约一半是 5 MB 文件列表的签名检查，每次启动都会保留它：即 `@delorun/release` 的严格 JSON 解析器，以及它为签名对列表所做的规范化重新序列化。另一半是对 35,287 个文件的列举和 `lstat`。

更新在更新运行启动检查而不是完整哈希之前和之后的检查，与更新套件的其他步骤一起记录在[更新耗时](../performance/update-timings.md#start-checks-and-parallel-unpacking)中。

所有文件的更改时间都恰好在启动之前发生变化的运行时（例如用硬链接复制的 home，因为每个 `link` 都会移动共享文件的更改时间，而等待时间基准用 `cp -al` 复制它的 home），会在接下来的两次启动中被完整哈希：第一次启动的记录无法担保更改时间落在其捕获时间之后 2 秒之内的条目，所以第二次启动会再次对它们做哈希。2026-11-11 在负载较高的机器上（平均负载 5 到 12）用存储的 `prepareLaunch` 在一个真实的 32,449 个文件的运行时的副本上测得：10.5 s、11.1 s，然后是 0.8 s。基准的 `start` 套件在它的第一次 `delorun stop` 时遇到这种情况（见[命令与启动](../performance/commands-and-start.md#where-the-time-goes)）。已安装或已更新的 home 不会遇到这种情况，因为安装会在捕获记录之前等待这 2 秒过去。

## 拒绝测试

规格是 `delorun/packages/runtime-store/tests/identity.integration.spec.ts`（在 C2 现有的行旁边）和 `delorun/apps/npm-launcher/tests/launcher.spec.ts`。

| 测试 | 证明什么 |
| --- | --- |
| `c02-start-stops-on-changed-byte` | 改动了一个字节而被重写的运行时文件，在记录存在的情况下会使启动停止。 |
| `c02-start-catches-in-place-change` | 改动了一个字节、但文件的大小、模式和修改时间被 `utimes` 恢复的情况，会使启动停止，并且失败的启动让记录保持原样。 |
| `c02-start-catches-renamed-replacement` | 以相同的大小、模式和修改时间重命名覆盖原文件的文件会使启动停止。 |
| 多余、缺失、符号链接、`chmod` | 多余、缺失和链接的条目会使启动停止；改变的模式会强制重新哈希，它通过并记录新的身份。 |
| 竞争条目 | 更改时间在捕获时间之后 2 秒之内的条目会被哈希，它所隐藏的更改会使启动停止。 |
| `c02-start-missing-record-hashes-every-file` | 缺失、被截断、无法解析、更宽松、被链接、过大、来自别处或被重新绑定的记录，以及不同 schema、版本、平台、文件列表、manifest、根 inode、文件系统或长度的记录，每一种都会使启动对每个文件做哈希。 |
| `c02-start-record-forgery-out-of-scope` | 被重写为已更改的 manifest、Node 可执行文件、`delorun` 入口或依赖文件的身份、并把其最后一次完整遍历设为现在的记录，会让普通的启动通过：这是有文档说明的局限。 |
| `c02-verify-start-hashes-every-file` | 启动器给 `delorun verify` 的间隔 0，在同一份伪造的记录之下发现每一个这样被更改的文件。 |
| `c15-verify-sees-past-forged-record` | 在启动器规格中，用真实的存储和这样一份伪造的记录，另一条命令会启动，而 `delorun verify` 会被拒绝，并指出被更改的文件。 |
| `c02-verify-always-hashes` | `delorun verify` 和回退报告背后的完整检查，即使每个身份都匹配，也会对每个文件做哈希。 |
| `c02-update-start-check-catches-in-place-change` | 更新所运行的启动检查，会在改动了一个字节、但文件的大小、模式和修改时间被恢复时停止；对伪造的记录它会像启动那样通过，而完整检查会拒绝；没有记录、完整遍历到期或间隔为 0 时，它会对每个文件做哈希；并且在同一个 `shareChecks` 范围内，完整检查从不共享启动检查。 |
| `c02-start-periodic-full-hash` | 最后一次完整遍历早于间隔、或晚于时钟，或者间隔为 0，会使启动对每个文件做哈希。 |
| 不受信任的文件系统 | NFS、`statfs` 无法命名的文件系统以及 macOS 会使启动对每个文件做哈希；在那里的安装不写入记录。 |
| 更改时间无法被调回去 | 在系统的临时目录和 `/dev/shm` 中，各自在测试机器上它位于受信任的文件系统上的情况下（这里是 ext4 和 tmpfs），一次写入后再用 `utimes` 调回旧的时间，会留下更晚的更改时间；否则测试失败。 |
| 锁 | 在另一个操作持有 `store.lock` 期间，重新哈希的启动让记录保持不动。 |

没有任何受限命令能在任何方言上写入这份记录：它位于 home 之下，而 C1 的 `home-write-denied` 涵盖每个文件；并且它位于读取豁免之外，而 C1 的 `home-read-denied` 在方言强制执行读取的地方涵盖这一点。

## 实现状态

本页的一切都已为 CLI 启动器、`delorun verify`、更新的准备、后继者启动之前的检查以及 H1 健康检查而构建。尚未构建的有：macOS 在 APFS 上的测试运行之前仍保留完整哈希；在启动器读取设置之前，间隔是一个环境变量，而它目前并不读取设置。
