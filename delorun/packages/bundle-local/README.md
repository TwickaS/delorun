# @delorun/bundle-local

English | [中文](README.zh.md)

## Summary

`@delorun/bundle-local` is the bundle that Delorun's CLI profiles add after upstream's `web` profile template. Its patch holds Delorun's local integration rows, each listed with its reason in [`LOCAL_ROWS`](src/rows.ts), so a Delorun CLI profile composes upstream's web profile with those rows changed or added and nothing else. It turns off upstream's two opt-ins, DeepSeek's session-log upload and the desktop app's analytics, and adds the Privacy section in Settings, where the person turns each one on after a consent dialog and off again, the About section and the release check's General row ([C11](../../docs/contracts/c11-setup-answers.md)). It mounts Delorun's consent and guard plugins with their switches on — the instruction-layer write consent with the consent for writes to approved plugins, the MCP add-time consent, the per-workspace permission defaults with the one full-access consent, the scheduled-task consent, the fetch guard and the plugin changes held for review — mounts the update gate, which refuses new turns while `delorun update` or `delorun stop` waits for running chats, and sets C1's home protection on upstream's sandbox row, so a confined command cannot read the consent stores under the home's `secrets/` on Linux and macOS; the Windows runner does not confine reads. It sets the folder of the studio's first-use workspace on upstream's `workspace-controller` row to the one `delorun start` resolves, so the studio has a default workspace where upstream's documents lookup finds none. Only the CLI profile loads this bundle: `delorun headless` loads [`@delorun/bundle-headless`](../bundle-headless/README.md), which mounts the same consent and guard plugins, protects them the same way and turns session-log upload off, and `delorun plugin` and the desktop app run upstream's own profiles, in which none of these rows applies and session-log upload stays on. It also turns on upstream's one-time launch tokens, so a studio sign-in link works once, within one minute.

## Use this bundle

- **The bundle list.** [`DELORUN_PROFILE_BUNDLES`](src/profile.ts), exported from `@delorun/bundle-local/profile`, is the ordered `dsh.profile.bundles` list of a Delorun CLI profile: upstream's `web` template, read from `@deepseek-ai/dsh-official-bundles`, followed by `@delorun/bundle-local` and then [`@delorun/bundle-studio`](../bundle-studio/README.md) (`STUDIO_BUNDLE`), which mounts the studio additions. Upstream's own templates do not list this bundle, so `dsh --profile web` and the recorded-session replay compose upstream's bundles alone.
- **What `delorun` owns.** `delorun`, which creates the CLI profiles under `~/.delorun/profiles/` ([C1](../../docs/contracts/c01-home-layout.md#profiles)), writes `DELORUN_PROFILE_BUNDLES` into each CLI profile it creates, and refuses to start a CLI profile when upstream's profile loader reports this bundle in `skippedBundles`, because the privacy defaults hold only while the bundle loads. This package does neither itself.
- **Layer order.** The bundle applies after every upstream bundle and before the profile's own `cordis.patch.yml`, the home patch and `--patch` overlays, so a person's setting in the profile still wins over a row here ([upstream's profile layers](../../../apps/cli/README.md#profiles)). The Privacy section writes to the profile's `cordis.patch.yml`.
- **Reading the composition.** `dsh --profile <name> --dump-config` prints every composed row under a `# ==` line naming the bundle that inserted it and each bundle that patched it; a row this bundle writes names `@delorun/bundle-local` there.
- **Loading.** The bundle declares no `engines.dsh` range and no upstream peer, so upstream's compatibility check never skips it after a version change; a profile whose bundle list names it and cannot resolve it reports the bundle as skipped.
- **The update check.** The `delorun-update-check` row mounts [`@delorun/bundle-local/update-check`](src/update-check.ts), the C16 switch `update_check`, which provides the `delorunUpdateCheck` service and serves its notice at `GET /api/delorunUpdateCheck.notice`; whether the switch is on or off, it also serves `GET /api/delorunUpdateCheck.channel`, which answers `{ host }` with the host of the channel origin that a launcher built with `--channel-origin` recorded in `trust/channel.json`, or `null` on the production channel, so the General row's copy names the host the check contacts ([C3](../../docs/contracts/c03-update-report.md#update-check)). `delorun`'s Host attaches the check with `attach(source)`, whose disposer detaches it; the row then runs a check at once when the last one is at least `intervalHours` old (24 by default), and again each interval, with a deadline of `timeoutSeconds` (15 by default), and never waits for one. One check is attached at a time. With the switch off, the plugin's default, it provides no service, registers no route and no check runs; Settings → General → Updates turns it off in the profile's own patch.
- **The trust bill.** The `delorun-trust` row mounts [`@delorun/bundle-local/trust`](src/trust.ts), which provides the `delorunTrust` service and serves the trust bill (`@delorun/bundle-local/trust-bill`, contract [C15](../../docs/contracts/c15-verification-checks.md)) at `GET /api/delorunTrust.bill` as `{ bill }`, `null` while no source is attached. `delorun`'s Host attaches the source with `attach(source)`, whose disposer detaches it, and one source is attached at a time ([trust host](../../apps/cli/src/verify/trust-host.ts)). The row asks the source for the start bill once, which the launcher's start check and the stored release-log record make without hashing anything, and then answers the last bill it holds, so the studio's reads never hash. `POST /api/delorunTrust.check` runs the `verify` stage and answers `{ bill }`: the Host runs `delorun verify --json` through the launcher that started it, in a child process, so every runtime file is hashed before the command runs, and runs the stage in its own process, saying so in the bill's `checkedBy`, only when no launcher can be run from there; `checkTimeoutSeconds` (600 by default, 30 to 3600) stops a check that takes longer; concurrent requests share one run, a failure answers `{ error, message }` with `TRUST_SOURCE_MISSING` (503), `TRUST_CHECK_FAILED` (500) or `TRUST_JSON_REQUIRED` (415, a request without a JSON body) and keeps the last bill, and a failed read answers `TRUST_READ_FAILED` (500). A device the home approved may read the bill: the bill route admits a `reach-device` Peer's `GET`. The check route admits no Peer but the owner, so Check now runs only from the studio on the home's own computer. With `enabled` off, the plugin's default, it provides no service and registers no route.
- **The workspace rename tool.** The `delorun-workspace-rename` row mounts [`@delorun/bundle-local/workspace-rename`](src/workspace-rename.ts), the C16 switch `rename_workspace_tool`, which registers the `rename_workspace` tool. The tool takes a workspace's id or current name and a new name, so the agent never edits the registry file by hand. It checks the request against upstream's workspace registry first and refuses what the studio's rename refuses (a blank or over-long name, an unknown or ambiguous workspace, a name another workspace uses), in `WORKSPACE_RENAME_REFUSED` words and before it asks. It then asks the person inside the call through upstream's approval service, so only `allowed-once` runs it and no `tools/pre-execute` listener can let it through unasked; any other answer, or no approval service, ends as `WORKSPACE_RENAME_DECLINED` and changes nothing. After the answer it checks the name again, then renames. It returns `from`, `to` and `changed`, which draw the studio's row (`@delorun/plugin-onboarding`). The `headless` profile does not mount it, because a one-shot run has no one to answer the ask. With the switch off, the plugin's default, it registers no tool.
- **The update gate.** The `delorun-update-gate` row mounts [`@delorun/bundle-local/update-gate`](src/update-gate.ts), the C16 switch `update_turn_refusal`, which provides the `delorunTurnGate` service. `delorun`'s Host attaches its chat gate's held state with `attach(isHeld)`, whose disposer detaches it; while any attached source is held, the plugin's `agent/pre-step` listener, which runs before every other, refuses the first step of every new turn by throwing `UpdatePendingError` (code `UPDATE_PENDING`). The loop ends that turn as `error` with the error's message, which says that the message was not sent and to send it again once Delorun is back, and makes no model request; a later step of a turn that was already running goes on. With `holdUntilChecked` on, the first step of every turn also waits for `release()`, which `delorun` calls once its check of the booted Host passes, for at most `checkWaitSeconds` (a whole number from 1 to 3600, default 60): a turn still waiting then ends as `error` with `StartCheckPendingError` (code `START_CHECK_PENDING`), whose message says that the start's check did not finish and to start Delorun with `delorun start`, and the first waiting turn is logged once at warn on the Host log. With the switch off, the plugin's default, it provides no service and refuses nothing ([C19](../../docs/contracts/c19-home-process.md)).
- **The version row.** The harness half prints Delorun's version (from `delorun`'s `DELORUN_VERSION`) and the DeepSeek Harness version upstream reports into each page as the global `delorunVersions`; the browser half validates it and then registers Settings' version row under the stock row's id `current-version` at rank -1, so it takes that row's place and reads "Delorun version" alone. It also registers the General row `delorun-versions` (`VERSIONS_ITEM`, order 99), which names Delorun's version alone, "Delorun 0.1.0" or "Delorun source build". The DeepSeek Harness version is in Settings → About. A harness that `delorun` did not start prints nothing, so the stock row stays and the line is not registered.
- **The notice service.** The browser half provides `ctx.delorunNotice` (`acknowledged()`, `acknowledge()`), so a flow that shows the preview notice's copy itself, such as `@delorun/plugin-onboarding`'s first screen, records the acknowledgement and this bundle's notice step completes without showing a second time.
- **Statements.** The `./statements` export is the Privacy section's English dictionary (`src/client/locales.ts`), which the CLI's setup reads for the statements of its privacy note; the section itself shows the feedback statement only.
- **Delorun's rows come from this installation.** `delorun` refuses to start a profile in which a row of this bundle, or the bundle itself, resolves to a package outside this Delorun's own packages (`runtimes/<version>/app`, or the source checkout), such as a same-named package in the profile's `node_modules` ([`compose.ts`](../../apps/cli/src/compose.ts)). To change one of Delorun's packages, fork it under a new name (for example `@yourscope/plugin-fetch-guard`), install it with `delorun plugin --profile <profile> add <path or spec>`, and point a row of your profile's `cordis.patch.yml` at the new name, leaving Delorun's row in place.
- **Building.** `pnpm --filter @delorun/bundle-local run build` writes `lib/index.js`, the Host half of the `delorun-privacy` row, and `lib/client.js`, the browser half. Upstream's `pnpm run build:artifacts` does not build Delorun's packages.

## The Privacy section

The browser half (`src/client/index.ts`) also registers Delorun's preview notice (`src/client/DelorunNotice.tsx`) in the `settings.onboarding` slot, ahead of the model-provider onboarding. Its copy is in the locale dictionary, and it shows once per notice version on a browser (`NOTICE_VERSION`), recorded in local storage as a per-viewer convenience. It also registers the `settings.section` `delorun-privacy` (`PRIVACY_SECTION_ID`), after upstream's Plugins section, and the sidebar brand occupants `sidebar.brand.name` and `sidebar.brand.mark` (`src/client/brand.tsx`), which show the hex jack mark, its plug in the accent, and the name Delorun. Both come from the one `delorun-privacy` row, so the parity composition, which disables that row, keeps upstream's brand. The same row overrides the common dictionary's `brand.localBuild` text with the product name in every language the locale service lists (`src/client/title.ts`). Upstream's frame titles the page with that text in a build without `DSH_CLIENT_TITLE`, such as a source checkout's, and with the variable in a build that sets it, as Delorun's release and `delorun/apps/tools/src/build-web.ts` do with `Delorun`, so the tab reads "Delorun" either way once the frame renders; until then the boot page keeps the `<title>` the build wrote into the page, which a build without the variable leaves as "DSH Local Build". The section opens with one sentence, that Delorun sends nothing about the person unless they turn it on there, then the group Data sharing with one row per opt-in and C11's feedback statement (sending feedback includes a session-log prefix and happens only on sending). The feedback statement describes upstream's feedback send, which this bundle's rows remove, so the CLI profile sends no feedback. The release check's switch is the General row `delorun-update-check` (`UPDATE_CHECK_ITEM`, order 98), which Delorun's look places under Updates, with the same dialog (`src/client/UpdateCheckRow.tsx`); both render one `OptInRow`:

- **DeepSeek session-log upload** edits `session-log-deepseek`, **Desktop analytics** edits `product-analytics`, and the General row's **Check for new releases** edits `delorun-update-check`, each through upstream's configuration form for that row (`OPT_IN_ROWS`; the opt-ins' rows from `@delorun/contract-setup-answers`). A write changes only that row's `config.enabled`. The release check is on in Delorun's composition; the opt-ins are off.
- **Turning on** opens a dialog that names what is sent or requested and where; nothing is written until the person chooses Turn on, and Cancel writes nothing. **Turning off** writes at once.
- The switch shows the value the Host accepted. A refused or failed write leaves it unchanged and says so in the row.
- A profile that does not serve a switch's row shows no switch for it; for desktop analytics the row says that only the desktop app collects it, and for the release check that the profile does not check for new releases.
- **Ask a public npm mirror when a download fails** is not on this page: it is the section `delorun-plugin-installs` (`PLUGIN_INSTALLS_SECTION_ID`, order 16, `src/client/PluginInstallsSection.tsx`), which Delorun's layout places under the plugin inventory in Settings, Plugins. It writes `npmMirror` of `delorun-plugin-install-check` with the same dialog and shows nothing in a profile that does not load the install check.

The **About** section (`delorun-about`, `ABOUT_SECTION_ID`, after Network, `src/client/AboutSection.tsx`) holds a Versions group (Delorun's version and the DeepSeek Harness version, shown when the page carries them), then two more groups: Licences, which says that Delorun and the DeepSeek Harness it includes are MIT-licensed and links the licence file, and Project links, which links the documentation, the source code, the issue tracker and the support address. Every link opens in a new tab. Each group of a Delorun section is a card of [`@delorun/settings-controls`](../settings-controls/README.md), an `h3` heading over a bordered box; the heading reads the card-heading properties of a grouped Settings layout, so it matches the layout's cards, and each section keeps its own title for a page that does not title itself.

The `delorun-trust` row also registers the **trust badge** at the sidebar's foot (`sidebar.footer.action` `delorun-trust`, `src/client/TrustBadge.tsx`). It is always shown: a shield with a short label in the wide sidebar ("Verified", "Checked at start", "Checked in the studio", "Changes to review", "Needs attention", "Check failed", "Not checked" or "Unknown", followed by a neutral count such as "12 of your changes" when the person has changes), and the shield alone with a tooltip on the 56px rail. ## The PIN mode section

The **PIN mode** section (`delorun-pin-mode`, right after Devices, `src/client/PinModeSection.tsx`) is where the person at the home's own computer turns PIN mode on and off. It reads `GET /auth/pin/mode` and sends `POST /auth/pin/set`, `/off` and `/resume` (`src/client/pin-api.ts`), the computer-only routes of [`@delorun/home-auth`](../home-auth/README.md). It shows whether the mode is on, with a PIN or a passcode, and whether the PIN and Face ID are paused.

- **Turn on.** A PIN or passcode typed twice in masked fields (16 px, so a phone does not zoom); the stored idle minutes and lock-when-hidden go with it unchanged, since no device holds a window for them to end. `src/client/pin-rules.ts` checks the length, repeat, run and common-PIN rules and the match before any request; the home's own check stays the authority and its sentence shows in place.
- **Change PIN.** A separate Change PIN disclosure holds the two secret fields, the same rules and its own Save new PIN button.
- **Secret handling.** The secret lives in the component's state until the request leaves, is cleared whatever the answer, and is never written to storage.
- **Turn off and resume.** Turn off needs no secret but asks one in-place confirmation ("Turn PIN mode off? A phone without Face ID then takes its sensitive actions at your computer."). Resume appears while the PIN and Face ID are paused home-wide after too many wrong tries.
- **On a device.** The section shows one line saying PIN mode is set at the computer, and sends no request. The home refuses a device's request with `LOOPBACK_REQUIRED` either way.

Onboarding's Phone access step recommends the mode in one line and points at this section and `delorun devices pin set`.

## Limits

- The bundle list is a constant for `delorun` to write; no shipped upstream template names it, so the recorded-session replay mounts this bundle only through the parity overlay.
- A profile created before a change to `DELORUN_PROFILE_BUNDLES` keeps the list it was created with.
- Only the CLI profile that `delorun` starts loads this bundle. `delorun headless` loads `@delorun/bundle-headless` instead, which carries the same consents, the fetch guard, the turn gate and their protection from plugin management, and not the Privacy section.
- The privacy defaults hold only while the profile loads this bundle. Upstream reports a bundle it cannot load as skipped and starts without it, and session-log upload is then on; `delorun`'s refusal to start such a profile is what keeps the defaults.
- `delorun` attaches the trust bill's source only to a Host it runs from the runtime store, so a source checkout's studio reads no bill and its badge shows unknown.
- Desktop analytics mounts only in upstream's `desktop` profile, which `delorun` does not run, so a Delorun CLI profile's section shows that row's reason instead of a switch.
