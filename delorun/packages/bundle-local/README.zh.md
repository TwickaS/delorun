# @delorun/bundle-local

[English](README.md) | 中文

> 英文页面是当前版本；本页可能落后于它。

## 摘要

`@delorun/bundle-local` 是 Delorun 的 CLI profile 在上游 `web` profile 模板之后加入的组合包。它的 patch 保存 Delorun 的本地集成行，每一行的理由都列在 [`LOCAL_ROWS`](src/rows.ts) 中，因此 Delorun 的 CLI profile 在组合上游的 web profile 时，只改变或新增这些行，其他一概不变。它关闭上游的两个选择加入项，即 DeepSeek 的会话日志上传与桌面应用的分析，并在设置中新增“隐私”分区（本人在其中经同意对话框后逐项打开，也可再关闭）、“关于”分区以及发布检查所在的“通用”行（[C11](../../docs/contracts/c11-setup-answers.zh.md)）。它挂载 Delorun 的同意与守卫插件并打开其开关：指令层写入同意（连同对已批准插件的写入同意）、MCP 添加时同意、带有唯一一次完全访问同意的按工作区权限默认值、计划任务同意、抓取防护，以及留待审查的插件变更；它还挂载更新闸门，在 `delorun update` 或 `delorun stop` 等待运行中的 chat 结束时拒绝新的轮次；并在上游的 sandbox 行上设置 C1 的 home 保护，使受限命令在 Linux 与 macOS 上无法读取 home 的 `secrets/` 之下的同意存储，Windows 运行器不隔离读取。它在上游的 `workspace-controller` 行上，把 studio 首次使用的工作区所在文件夹设为 `delorun start` 解析出的文件夹，使上游的文档目录查找找不到文档目录时，studio 仍有默认工作区。只有 CLI profile 加载本组合包：`delorun headless` 加载 [`@delorun/bundle-headless`](../bundle-headless/README.zh.md)，它挂载同样的同意与守卫插件，以同样的方式保护它们，并关闭会话日志上传；`delorun plugin` 与桌面应用运行上游自己的 profile，其中这些行都不适用，会话日志上传保持打开。它还打开上游的一次性启动令牌，因此 studio 登录链接只能在一分钟内使用一次。

## 使用本组合包

- **组合包列表。**[`DELORUN_PROFILE_BUNDLES`](src/profile.ts) 从 `@delorun/bundle-local/profile` 导出，是 Delorun CLI profile 有序的 `dsh.profile.bundles` 列表：先是上游的 `web` 模板（从 `@deepseek-ai/dsh-official-bundles` 读取），然后是 `@delorun/bundle-local`，再然后是挂载 studio 附加功能的 [`@delorun/bundle-studio`](../bundle-studio/README.zh.md)（`STUDIO_BUNDLE`）。上游自己的模板不列出本组合包，因此 `dsh --profile web` 与记录会话回放只组合上游的组合包。
- **`delorun` 的职责。**`delorun` 创建 `~/.delorun/profiles/` 之下的 CLI profile（[C1](../../docs/contracts/c01-home-layout.zh.md#profiles)），把 `DELORUN_PROFILE_BUNDLES` 写入它创建的每个 CLI profile；当上游的 profile 加载器在 `skippedBundles` 中报告本组合包时，它拒绝启动该 CLI profile，因为隐私默认值只在本组合包加载时才成立。本包自身两件事都不做。
- **层顺序。**本组合包在每个上游组合包之后、profile 自身的 `cordis.patch.yml`、home patch 与 `--patch` overlay 之前生效，因此本人在 profile 中的设置仍然优先于此处的行（[上游的 profile 层](../../../apps/cli/README.zh.md#profiles)）。“隐私”分区写入 profile 的 `cordis.patch.yml`。
- **读取组合结果。**`dsh --profile <name> --dump-config` 会在每个 `# ==` 行之下打印全部组合后的行；该行写明插入此行的组合包，以及修补过此行的每个组合包。本组合包写入的行，在那里写作 `@delorun/bundle-local`。
- **加载。**本组合包未声明 `engines.dsh` 范围，也没有上游的对等依赖，因此版本变更之后，上游的兼容性检查从不会跳过它；若 profile 的组合包列表列出了它却无法解析，则会把该组合包报告为已跳过。
- **更新检查。**`delorun-update-check` 行挂载 [`@delorun/bundle-local/update-check`](src/update-check.ts)，即 C16 开关 `update_check`，它提供 `delorunUpdateCheck` 服务，并在 `GET /api/delorunUpdateCheck.notice` 提供其提示。无论开关打开与否，它还提供 `GET /api/delorunUpdateCheck.channel`，返回 `{ host }`：即以 `--channel-origin` 构建的启动器记录在 `trust/channel.json` 中的通道来源的主机；在生产通道上返回 `null`。这样“通用”行的文案就能写明检查所联系的主机（[C3](../../docs/contracts/c03-update-report.zh.md#update-check)）。`delorun` 的 Host 以 `attach(source)` 挂接该检查，其返回的销毁器会解除挂接；随后该行在上一次检查距今至少 `intervalHours`（默认 24）时立即运行一次检查，此后每隔一个间隔再运行一次，期限为 `timeoutSeconds`（默认 15），并且从不等待某次检查完成。同一时间只挂接一个检查。开关关闭时（插件的默认值），它不提供服务、不注册路由，也不运行检查；“设置 → 通用 → 更新”会在 profile 自己的 patch 中把它关闭。
- **信任账单。**`delorun-trust` 行挂载 [`@delorun/bundle-local/trust`](src/trust.ts)，它提供 `delorunTrust` 服务，并在 `GET /api/delorunTrust.bill` 以 `{ bill }` 的形式提供信任账单（`@delorun/bundle-local/trust-bill`，约定见 [C15](../../docs/contracts/c15-verification-checks.zh.md)）；没有挂接来源时返回 `null`。`delorun` 的 Host 以 `attach(source)` 挂接来源，其返回的销毁器会解除挂接，同一时间只挂接一个来源（[trust host](../../apps/cli/src/verify/trust-host.ts)）。该行向来源请求一次启动账单，由启动器的启动检查与已保存的发布日志记录生成，不对任何内容做哈希；此后它返回手中最近的账单，因此 studio 的读取从不做哈希。`POST /api/delorunTrust.check` 运行 `verify` 阶段并返回 `{ bill }`：Host 通过启动它的启动器在子进程中运行 `delorun verify --json`，因此每个运行时文件都在命令运行之前被哈希；只有在那里无法运行任何启动器时，才在自己的进程中运行该阶段，并在账单的 `checkedBy` 中说明。`checkTimeoutSeconds`（默认 600，范围 30 到 3600）会终止耗时更长的检查；并发请求共用一次运行；失败时返回 `{ error, message }`，错误码为 `TRUST_SOURCE_MISSING`（503）、`TRUST_CHECK_FAILED`（500）或 `TRUST_JSON_REQUIRED`（415，即请求没有 JSON 请求体），并保留最近的账单；读取失败则返回 `TRUST_READ_FAILED`（500）。home 已批准的设备可以读取账单：账单路由放行 `reach-device` Peer 的 `GET`。检查路由除所有者之外不放行任何 Peer，因此“立即检查”只能在 home 所在计算机的 studio 中运行。`enabled` 关闭时（插件的默认值），它不提供服务，也不注册路由。
- **后台完整检查**（[`src/trust-schedule.ts`](src/trust-schedule.ts)，A628）。当启动检查只对它的身份记录无法担保的文件计算了哈希、且启动器可以运行该检查时，该行会自行运行与 Check now 相同的启动器检查：在 studio 启动之后、且任何 chat 的轮次连续 `idleSeconds`（默认 45，5 到 3600）没有运行过（按上游 `agent/status` 所报告的那样），以 `nice` 10 运行，在 Linux 上使用最低的尽力而为 I/O 类别（在 Windows 上低于 normal）。开始的轮次会停止它，而在下一个空闲时段之后它会从头再次运行；本人用 Check now 加入的运行从不被停止。一个关键时刻会在最后一次 `loader/volatile-update`（添加、更新、开启或关闭、移除插件，或加载本人的更改）之后 `keyMomentSeconds`（默认 60，60 到 600）重新读取插件与更改分节而不对运行时计算哈希，绝不在轮次或另一个检查运行时进行，也绝不覆盖其间已完成的 Check now 的账单；已应用的更新会启动新发布，其行会安排自己的完整检查。该检查从不自行在 Host 内运行：源码会拒绝启动器无法运行的后台检查，该行随后保持 `unavailable` 并给出原因，而 `autoCheck: false`（默认开启）会关闭它。停止该运行的轮次也会给 Check now 一次自己的运行，因此本人的检查绝不会加入正在被停止的那一次。失败的运行会被记录；新鲜度只显示 `failed`，因为已配对的设备也会读取它。
- **工作区重命名工具。**`delorun-workspace-rename` 行挂载 [`@delorun/bundle-local/workspace-rename`](src/workspace-rename.ts)，即 C16 开关 `rename_workspace_tool`，它注册 `rename_workspace` 工具。该工具接收工作区的 id 或当前名称以及新名称，因此 agent 无需手工编辑注册表文件。它先对照上游的工作区注册表检查请求，并在询问之前，以 `WORKSPACE_RENAME_REFUSED` 的措辞拒绝 studio 的重命名所拒绝的情形（名称为空或过长、工作区未知或有歧义、名称已被其他工作区使用）。然后它在调用内通过上游的批准服务询问本人，因此只有 `allowed-once` 才会执行，任何 `tools/pre-execute` 监听器都无法不经询问放行；其他任何回答，或没有批准服务，都以 `WORKSPACE_RENAME_DECLINED` 结束，且不改变任何内容。得到回答之后，它再次检查名称，然后重命名。它返回 `from`、`to` 与 `changed`，用于绘制 studio 的行（`@delorun/plugin-onboarding`）。`headless` profile 不挂载它，因为一次性运行没有人可以回答询问。开关关闭时（插件的默认值），它不注册任何工具。
- **更新闸门。**`delorun-update-gate` 行挂载 [`@delorun/bundle-local/update-gate`](src/update-gate.ts)，即 C16 开关 `update_turn_refusal`，它提供 `delorunTurnGate` 服务。`delorun` 的 Host 以 `attach(isHeld)` 挂接其 chat 闸门的保持状态，其返回的销毁器会解除挂接；只要任一已挂接的来源处于保持状态，插件的 `agent/pre-step` 监听器（先于其他所有监听器运行）就通过抛出 `UpdatePendingError`（错误码 `UPDATE_PENDING`）拒绝每个新轮次的第一步。循环以 `error` 结束该轮次，并带上该错误的消息，其中说明消息未发送，待 Delorun 恢复后请重新发送，且不发出任何模型请求；已在运行的轮次的后续步骤照常进行。开启 `holdUntilChecked` 时，每个轮次的第一步还要等待 `release()`，`delorun` 在其对已启动 Host 的检查通过后调用它，最长等待 `checkWaitSeconds`（1 到 3600 的整数，默认 60）：届时仍在等待的轮次以 `error` 结束，错误为 `StartCheckPendingError`（错误码 `START_CHECK_PENDING`），其消息说明启动时的检查没有完成，请用 `delorun start` 启动 Delorun；第一个等待的轮次会在 Host 日志中以 warn 级别记录一次。开关关闭时（插件的默认值），它不提供服务，也不拒绝任何内容（[C19](../../docs/contracts/c19-home-process.zh.md)）。
- **版本行。**Host 部分把 Delorun 的版本（来自 `delorun` 的 `DELORUN_VERSION`）与上游报告的 DeepSeek Harness 版本，作为全局 `delorunVersions` 打印到每个页面中；浏览器部分校验它，然后以 stock 行的 id `current-version`、排序 -1 注册设置中的版本行，因此它取代该行，只显示“Delorun 版本”。它还注册“通用”行 `delorun-versions`（`VERSIONS_ITEM`，排序 99），只写明 Delorun 的版本，即“Delorun 0.1.0”或“Delorun 源码构建”。DeepSeek Harness 版本在“设置 → 关于”中。不是由 `delorun` 启动的 harness 什么也不打印，因此 stock 行保留，该行不注册。
- **提示服务。**浏览器部分提供 `ctx.delorunNotice`（`acknowledged()`、`acknowledge()`），因此自行显示预览提示文案的流程（例如 `@delorun/plugin-onboarding` 的第一个屏幕）会记录确认，本组合包的提示步骤随之完成，不会再显示第二次。
- **声明文字。**`./statements` 导出是“隐私”分区的英文词典（`src/client/locales.ts`），CLI 的 setup 读取其中的声明作为隐私说明；该分区本身只显示反馈声明。
- **Delorun 的行来自本次安装。**本组合包的某一行或组合包本身解析到本 Delorun 自身的包（`runtimes/<version>/app` 或源码检出）之外的包时，例如 profile 的 `node_modules` 中同名的包，`delorun` 拒绝启动该 profile（[`compose.ts`](../../apps/cli/src/compose.ts)）。要修改 Delorun 的某个包，请以新名称派生它（例如 `@yourscope/plugin-fetch-guard`），用 `delorun plugin --profile <profile> add <path or spec>` 安装，并让你的 profile 的 `cordis.patch.yml` 中的某一行指向新名称，同时保留 Delorun 的那一行。
- **构建。**`pnpm --filter @delorun/bundle-local run build` 写出 `lib/index.js`（即 `delorun-privacy` 行的 Host 部分）与 `lib/client.js`（即浏览器部分）。上游的 `pnpm run build:artifacts` 不构建 Delorun 的包。

## 行

[`LOCAL_ROWS`](src/rows.ts) 列出 Delorun CLI profile 与上游 web profile 不同的每一行，以及该行在 C16 对等组合中的形式：

| 行 | 类型 | 在 Delorun CLI profile 中 | 在上游 web profile 中 | 在对等组合中 |
| --- | --- | --- | --- | --- |
| `plugin-manager` | 已更改 | `config.protectedPlugins` 列出本组合包挂载的同意与守卫插件（其中包括 `@delorun/plugin-changes`）、更新闸门、更新检查、信任账单以及 sandbox 各行的插件：完全访问无需提示即可运行的 `plugin_manager` 工具，既不能禁用这些行、更改它们的设置，也不能取消选择或移除本组合包，因此无法关闭对 agent 的插件安装与移除进行留待审查的那道审查 | 只保护管理器自己的组件 | 上游的组合：overlay 不包含此行，因此 `plugin_manager` 像上游一样列出并拒绝所记录场景的各行 |
| `session-log-deepseek` | 已更改 | `config.enabled: false`：模型请求不带 `dsh_session_log` 字段 | 插件的默认值，`true` | 上游的组合：overlay 不包含此行，因为它遵循每次回放的根配置，该配置按语料设定上传 |
| `deepseek-account` | 已更改 | `disabled: true`：没有 DeepSeek 账号登录，没有 Platform、用量或充值页面；没有账号时 `llm-deepseek-account` 保持闲置 | 启用 | 上游的组合：overlay 不包含此行 |
| `product-analytics` | 已更改 | `config.enabled: false`，重述上游的 `appVersion`，并保留上游的 `disabled` 条件，因此该行只在桌面 profile 中挂载，且在那里不接受任何事件 | `config.enabled: true` | 如此处所写；回放不挂载桌面 Host |
| `session-telemetry-otel` | 已更改 | `disabled: true`：没有会话日志前缀随反馈离开本机；上游的反馈导出器会把它发送到 DeepSeek 的收集器 | 启用，`FEEDBACK_ONLY` | 上游的组合：overlay 不包含此行 |
| `sandbox` | 已更改 | `config.protectedHome` 是 harness home，C1 为每个运行时进程把它设为 Delorun home，并带有 C1 的读取豁免（`runtimes`、`skills`、`dsh-runtimes`；`delorun start` 会加入 profile 已批准的插件副本）：在 bwrap、Landlock 与 Seatbelt 下，受限命令无法读取 `<home>/secrets` 之下的同意存储，而 Windows 运行器不隔离读取；`read`、`read_image`、`apply_patch`、`glob` 与 `grep` 在每个挂载它们的行（包括每个 agent preset 的行）中都拒绝相同的路径 | 该行以空配置挂载，因此提供方不保护任何 home，工具也不拒绝任何内容 | 上游的组合：overlay 不包含此行，因此回放运行上游的隔离，工具像上游的一样搜索 |
| `command-feedback` | 已更改 | `disabled: true`：没有 `/feedback` 命令 | 启用 | 上游的组合：overlay 不包含此行 |
| `ui-message-feedback` | 已更改 | `disabled: true`：没有“赞”“踩”或反馈对话框；上游没有提供会打开外部页面的行 | 启用 | 上游的组合：overlay 不包含此行 |
| `ui-settings-account` | 已更改 | `disabled: true`：没有账号菜单项、登录对话框或账号分区 | 启用 | 上游的组合：overlay 不包含此行 |
| `ui-account-notifications` | 已更改 | `disabled: true`：账号通知会轮询 DeepSeek 的服务器，获取显示在账号菜单旁的卡片，而 `ui-settings-account` 已将其移除 | 启用 | 上游的组合：overlay 不包含此行 |
| `connection` | 已更改 | `config.oneTimeLaunchTokens: true`（即 C16 开关 `one_time_launch_tokens`），重述 web 组合包的 `trustedHosts` 表达式，并把 `reopenHint` 设为 `run delorun open to open the studio`：每个 studio 登录链接只能在 60 秒内使用一次，且只有 `delorun open` 与启动会生成链接（[C4](../../docs/contracts/c04-admission.zh.md#launch-tokens)） | 在 Host 的整个生命周期内使用同一个可重复使用的启动令牌 | 上游的组合：overlay 不包含此行，因此回放使用可重复使用的令牌登录 |
| `workspace-controller` | 已更改 | `config.defaultWorkspaceDirectory` 是 `!!js process.env.DELORUN_DEFAULT_WORKSPACE`（[`src/profile.ts`](src/profile.ts) 中的 `DEFAULT_WORKSPACE_ENV`），`delorun start` 在启动前于 Host 进程中设置它：当平台查找到的文档文件夹不是 home 目录时为 `<documents>/Delorun/default-workspace`，否则为 `<home>/Delorun/default-workspace`，并且都与 Delorun home、stock home 及临时文件夹保持距离（[`default-workspace.ts`](../../apps/cli/src/default-workspace.ts)）。由其他方式启动时该键保持未设置，因此适用上游的查找；本人可通过在 profile 自己的 `cordis.patch.yml` 中重述该行来选择其他文件夹 | 该行不设置文件夹：首次使用的工作区位于 `<Documents>/deepseek-harness/default-workspace`；平台报告没有文档文件夹时（如没有 XDG Documents 文件夹的 Linux 与 WSL）则没有文件夹 | 上游的组合：overlay 不包含此行，即 C16 存在开关 `default_workspace_directory` 的对等值 |

## “隐私”分区

浏览器部分（`src/client/index.ts`）还在 `settings.onboarding` slot 中注册 Delorun 的预览提示（`src/client/DelorunNotice.tsx`），排在模型提供商引导之前。它的文案在 locale 词典中，每个提示版本（`NOTICE_VERSION`）在一个浏览器上只显示一次，并作为每位查看者的便利记录在本地存储中。它还在上游的“插件”分区之后注册 `settings.section` `delorun-privacy`（`PRIVACY_SECTION_ID`），以及侧边栏品牌占位项 `sidebar.brand.name` 与 `sidebar.brand.mark`（`src/client/brand.tsx`），它们显示六边形插孔标志（插头为强调色）与 Delorun 名称。二者都来自同一个 `delorun-privacy` 行，因此禁用该行的对等组合保留上游的品牌。同一行还在 locale 服务列出的每种语言中，用产品名称覆盖通用词典的 `brand.localBuild` 文本（`src/client/title.ts`）。在没有 `DSH_CLIENT_TITLE` 的构建（例如源码检出的构建）中，上游的框架以该文本作为页面标题；在设置了该变量的构建中，则以该变量为标题，Delorun 的发布与 `delorun/apps/tools/src/build-web.ts` 就把它设为 `Delorun`，因此框架渲染之后，标签页无论如何都显示“Delorun”；在此之前，引导页保留构建写入页面的 `<title>`，没有该变量的构建会把它保留为“DSH Local Build”。该分区以一句话开头，说明除非本人在这里打开，Delorun 不发送任何关于本人的内容；随后是“数据共享”组，每个选择加入项一行，再加上 C11 的反馈声明（发送反馈包含会话日志前缀，且只在发送时发生）。反馈声明描述的是上游的反馈发送，而本组合包的行已将其移除，因此 CLI profile 不发送反馈。发布检查的开关是“通用”行 `delorun-update-check`（`UPDATE_CHECK_ITEM`，排序 98），Delorun 的外观把它放在“更新”之下，使用同一个对话框（`src/client/UpdateCheckRow.tsx`）；二者都渲染同一个 `OptInRow`：

- **DeepSeek 会话日志上传**编辑 `session-log-deepseek`，**桌面分析**编辑 `product-analytics`，“通用”行的**检查新版本**编辑 `delorun-update-check`，每一项都通过上游针对该行的配置表单进行（`OPT_IN_ROWS`；各选择加入项的行来自 `@delorun/contract-setup-answers`）。一次写入只改变该行的 `config.enabled`。发布检查在 Delorun 的组合中是打开的；各选择加入项是关闭的。
- **打开**会弹出对话框，写明发送或请求的内容及其去向；在本人选择“打开”之前不写入任何内容，“取消”不写入任何内容。**关闭**立即写入。
- 开关显示 Host 已接受的值。被拒绝或失败的写入会使开关保持不变，并在该行中说明。
- 不提供某个开关所对应行的 profile，不显示该开关；桌面分析的行会说明只有桌面应用才收集它，发布检查的行会说明该 profile 不检查新版本。
- **下载失败时询问公共 npm 镜像**不在这一页：它是分区 `delorun-plugin-installs`（`PLUGIN_INSTALLS_SECTION_ID`，排序 16，`src/client/PluginInstallsSection.tsx`），Delorun 的布局把它放在“设置 → 插件”的插件清单之下。它用同一个对话框写入 `delorun-plugin-install-check` 的 `npmMirror`，在没有加载安装检查的 profile 中不显示任何内容。

**关于**分区（`delorun-about`，`ABOUT_SECTION_ID`，位于“网络”之后，`src/client/AboutSection.tsx`）包含一个“版本”组（Delorun 的版本与 DeepSeek Harness 版本，页面带有它们时显示），以及另外两组：“许可证”说明 Delorun 及其所包含的 DeepSeek Harness 均为 MIT 许可并链接许可证文件，“项目链接”链接文档、源代码、问题跟踪器与支持邮箱地址。每个链接都在新标签页中打开。Delorun 每个分区的每一组都是 [`@delorun/settings-controls`](../settings-controls/README.zh.md) 的一张卡片，即带边框的框之上的 `h3` 标题；该标题读取分组式设置布局的卡片标题属性，因此与布局的卡片一致，且每个分区都保留自己的标题，供不自带标题的页面使用。

`delorun-trust` 行还在侧栏底部注册**信任徽章**（`sidebar.footer.action` `delorun-trust`，`src/client/TrustBadge.tsx`）。它始终显示：宽侧栏中是一个带简短标签的盾牌（“Verified”、“Checked at start”、“Checked in the studio”、“Changes to review”、“Needs attention”、“Check failed”、“Not checked” 或 “Unknown”，当本人有更改时后面跟一个中性的计数，例如 “12 of your changes”），在 56px 的窄栏上则只有盾牌加提示。它的状态与颜色只来自 `trustRows` 与 `trustBadge`：检查失败为红色，未验证的发布、未检查或未知的发布日志或严重的安全公告为琥珀色，未知的插件安装检查或未知的 Changes 为中性色，对于启动检查只对其中一部分计算了哈希、而后台完整检查仍在等待或运行的发布（“Checking files”），或没有任何完整检查能到达的发布（“Checked at start”，附原因），或在 studio 内由 Check now 检查过的发布，以及等待本人审查的更改，同样为中性色；只有当每一行都验证通过时才使用成功色，而对发布来说这需要每个运行时文件都由完整检查计算过哈希；本人的更改从不为它着色。缺失的路由、失败的请求或无法验证的主体读作没有账单，即未知且为琥珀色（`src/client/trust-api.ts`，它用 zod 验证协议）。页面在启动时、每次连接重置时、窗口重新获得焦点时以及定时器上读取账单：检查运行期间每 3 秒，后台完整检查等待期间每 15 秒，其他情况每 60 秒。徽章会打开安全概览（[`src/client/SecurityOverview.tsx`](src/client/SecurityOverview.tsx)、[`src/client/security-overview.ts`](src/client/security-overview.ts)）：五行按固定顺序排列（智能体能做什么、撤销、谁能访问 studio、附加功能、这份 Delorun 副本），每一行根据其原因显示绿色、琥珀色“你的选择”、琥珀色“需要看一眼”或红色，颜色旁有图标和文字。当每一行都是绿色且完整检查已通过时，它显示 “Protected as Delorun intends” 并折叠各行；在完整检查仍在等待或运行时显示 “Checking this copy of Delorun”；不是绿色的行会自行展开，说明它意味着什么、为什么、这是选择还是故障，以及一个修复按钮。这些事实来自 Host 已有的路由（运行设置、权限默认值、Changes、设备、PIN 模式、MCP 与外部智能体的同意、更新通知和信任账单），各自独立，因此某台设备不得读取的路由，或某一行所需的任何无法读取的事实，都只会让那一行请求看一眼。插件行从不说安全：它的绿色读作 “reviewed, no advisory”。高级视图（studio 会记住的一个开关）会细分每一行，并在这份 Delorun 副本之下显示四个信任行（已签名发布、发布日志、插件与你的更改），每一行都带 “Checked 3 minutes ago”（悬停时显示确切时间）或 “Checking…”，并从账单中披露其细节、带进度的 Check now 及其已运行的秒数，以及之后它是通过启动器还是在 studio 内运行及其原因，还有指向 `delorun verify` 以获取完整报告的指引，以及一句说明这些检查以本人的访问权限运行、而以该权限运行的程序可以更改它们。远程会话显示 Check now 被禁用，并说明它只在 home 自己的电脑上运行。文案有英文和中文（`src/client/trust-locales.ts`）。

setup 与其他界面通过 `ctx.settingsShell.openSection('delorun-privacy')` 打开该分区。上游自己的“设置 → 通用”中的会话日志上传开关编辑同一行但不弹出对话框；[`@delorun/plugin-settings-layout`](../plugin-settings-layout/README.zh.md) 在 Delorun 的外观中隐藏它，stock 外观则显示它。该分区的文案有英文与中文两种。

同一行注册**设备**分区（`delorun-devices`，紧接在“隐私”之后，`src/client/DevicesSection.tsx`，导航中通过 `settings.section.icon` 带有链接图标）：远程访问状态、已批准的设备（移除需确认）以及“添加设备”，后者打开 home 的批准窗口，并在窗口打开期间每两秒读取一次待处理的请求，这一切都通过同源请求完成（`src/client/devices-api.ts`，引导流程导入其 `readReachStatus`）。没有远程访问的 profile 改为显示一行文字；远程 studio 收到的每个 `LOOPBACK_REQUIRED` 拒绝，都会就地显示为“这需要你在自己的计算机上操作”以及对应的操作。在该计算机上（页面所在位置为 `away`），该分区只为拒绝而显示某台设备等待中的旧代码解锁请求，只为结束而显示正在运行的解锁，并附一行说明解锁不再让设备做任何事；两者都没有时不显示这一块。在设备上，它不提供解锁，也不提供“添加设备”：它说明每个敏感操作在执行时会要求 Face ID 或 PIN，并说明新设备要在计算机上添加（如果那里重新出现“解锁”、“显示代码”、“立即锁定”或“添加设备”，`tests/unlock.client.spec.tsx` 和 `tests/devices-section.client.spec.tsx` 就会失败）。该分区的每个按钮在触摸屏上至少 44 px 高。`src/client/unlock.ts` 只告诉 studio 页面在计算机上还是在设备上。该行还注册一个 `shell.overlay` 提示（`src/client/RemoteNotice.tsx`），每当 home 以 `LOOPBACK_REQUIRED` 拒绝页面对转发提示的回答时显示，例如从远程 studio 回答的完全访问授权：上游的 Client Remote 服务将该拒绝报告为 `remote/answer-refused`，对完全访问、工作区管理、外部 agent 或真实浏览器的提示，提示写明回答未获确认并要求 Face ID 或 PIN，对其他任何提示则写明“这需要你在自己的计算机上操作”以及该操作。

在 home 自己的电脑上，该行还注册配对弹窗（`shell.overlay` 中的 `delorun-pairing-notice`，`src/client/PairingNotice.tsx`，C5 [弹窗配对](../../docs/contracts/c05-device-approval.zh.md#pop-up-pairing)），它基于 `src/client/pairing-source.ts`，每两秒读取 `GET /auth/devices/pending`。当 `pairing.showRequest: dialog`（默认值）时，一个请求会在设置引导的框架中打开 studio 的 `Modal`：设备的详情和一个倒计时、8 位数字输入框（`CodeCells`，数字，粘贴的分组代码整体接收）、**Not you making this request?**（拒绝）、**Don't show this pop-up again**（关闭时通过 `src/client/pairing-writer.ts` 写入 `showRequest: notice`，后者按路径写入每个字段，从不重述该分节）以及 **Submit**（在 8 位数字之前禁用）。粘贴内容若不恰好是 8 位数字则整体被拒绝，因此不消耗任何尝试次数。在 “Not you” 或 Close 之后，来自同一 Tailscale 用户和地址的后续请求在本次 studio 会话的剩余时间里只显示为通知，因此再次请求也无法让弹窗回来。请求一次显示一个，带 “1 of 2”；Close 和 Escape 会让它们继续等待，并列在“设置”→“设备”中，其配对卡片提供三种显示方式，各带一句说明。当焦点位于正在输入的字段中时，改为显示通知，弹窗会在本人选择 **Enter code** 或离开该字段后打开（`tests/pairing.client.spec.tsx`）。

远程访问页面在 home 轮换其会话之后会重新登录（C4：设备批准或移除、通行密钥注册、远程访问方式更改）。页面失去连接时，`src/client/session-rotation.ts` 发送一次 `HEAD /`；准入只对已轮换、已登出或已过期的会话应答 `401`，此时页面重新加载，home 把重新加载导向其登录页面，设备在那里用它的密钥签署一个新的挑战后返回。计算机上的页面从不探测。

设置中有一个 **Face ID** 分区（`src/client/FaceIdSection.tsx`）。手机列出它自己的通行密钥，并在 Face ID 确认之后列出每台设备的通行密钥；计算机列出每台设备的通行密钥，一键移除其中一个或一台设备，并接收手机显示的用于添加通行密钥的代码（`PasskeyDevices.tsx`、`FaceIdEnrol.tsx`）。计算机批准配对之后，配对叠层提供一次 **Set up Face ID**（`FaceIdPairingOverlay.tsx`）。**Skip for now** 以 `GET /auth/passkey/state` 返回的设备 id 为键，存储在此来源的本地存储 `delorun.faceId.pairingSkipped` 之下：重新加载不会再次提供该步骤，作为新设备再次配对的浏览器会再次被提供，此后 Settings → Face ID 仍提供它。敏感操作打开一个底部操作面板（`FaceIdSheet.tsx`、`FaceIdGrantFlow.tsx`）：操作的图标和标题（`face-id-icon-keys.ts`）、请求所指名的工作区和 chat 的列表、它允许什么以及持续多久（`face-id-lasts.ts`）、带有 Face ID 图标的整宽 **Confirm**，以及朴素的 **Cancel**；打开时没有任何东西获得焦点。它向 home 请求列出这次点按所发起的每个调用的选项，像 home 那样对每个调用做哈希（`face-id-hash.ts`），向浏览器请求通行密钥，并在 `Delorun-Grant` 中发送授权凭证 id。取消或失败的流程会显示 **Use PIN instead**，它把数字键盘（`FaceIdPin.tsx`）在同一个对话框内滑入；没有通行密钥的设备直接以键盘打开，带一行上下文（工作区、chat，以及它持续多久或什么保持不变），不能使用 Face ID 的浏览器则以 **Confirm with PIN** 作为主按钮；没有设置 PIN 时，面板改为显示 **Approve at the computer**。路由是 [`@delorun/home-auth`](../../docs/contracts/c14-oidc-passkeys.zh.md#face-id-unlock) 的路由。

<a id="pin-mode-on-a-device"></a>
## 设备上的 PIN 模式

设备不持有 PIN 解锁，也看不到 PIN 锁屏：PIN 模式开启时，home 对每台设备以 `ELEVATION_REQUIRED` 拒绝 `POST /auth/pin/unlock`，studio 从不发送它。设备用 Face ID 确认每个敏感操作；没有通行密钥的设备则用输入到 Face ID 授权面板（`src/client/FaceIdPin.tsx`）中的 PIN 或口令确认，该面板发送 `/auth/passkey/pin` 并为那一次调用签发授权凭证。studio 不持有窗口，也不持有解锁令牌。

- **状态。** `src/client/pin-lock.ts` 在加载时和每次连接重置之后，通过 `src/client/pin-api.ts` 读取一次 `GET /auth/pin/state`，只保存该模式是否开启，以及它采用 PIN（至少六位的数字键盘）还是口令（文本字段）。Face ID 面板读取它来选择键盘。模式关闭的 home、较旧的 home（404）和 home 自己的计算机都使状态保持 `off`。
- **拒绝测试。** 如果锁屏或对 `/auth/pin/unlock` 的调用重新出现，`tests/no-pin-window.client.spec.tsx` 就会失败。

<a id="the-pin-mode-section"></a>

## PIN 模式分区

**PIN 模式**分区（`delorun-pin-mode`，紧接在“设备”之后，`src/client/PinModeSection.tsx`）是 home 所在计算机旁的本人打开和关闭 PIN 模式的地方。它读取 `GET /auth/pin/mode`，并发送 `POST /auth/pin/set`、`/off` 和 `/resume`（`src/client/pin-api.ts`），这些是 [`@delorun/home-auth`](../home-auth/README.zh.md) 只限计算机的路由。它显示该模式是否开启、采用 PIN 还是口令，以及 PIN 和 Face ID 是否已暂停。

- **打开。** 在遮蔽的字段中输入两次 PIN 或口令（16 px，使手机不会缩放页面）；已存储的空闲分钟数和隐藏时锁定原样随之保留，因为没有设备持有可供它们结束的窗口。`src/client/pin-rules.ts` 在任何请求之前检查长度、重复、连号和常见 PIN 规则以及两次输入是否一致；home 自己的检查仍是权威，其句子就地显示。
- **更改 PIN。** 单独的 Change PIN 折叠区包含两个密码字段、同样的规则和它自己的 Save new PIN 按钮。
- **密码处理。**密码在请求发出之前一直存在于组件的状态中，无论回答如何都会清空，也从不写入存储。
- **关闭与恢复。** 关闭不需要密码，但会就地要求一次确认（“Turn PIN mode off? A phone without Face ID then takes its sensitive actions at your computer.”）。在错误尝试过多而使 PIN 和 Face ID 在整个 home 范围内被暂停之后，会出现 Resume。
- **在设备上。**该分区显示一行文字，说明 PIN 模式在计算机上设置，并且不发送任何请求。无论如何，home 都会以 `LOOPBACK_REQUIRED` 拒绝设备的请求。

引导流程的“手机访问”步骤用一行文字推荐该模式，并指向这一分区与 `delorun devices pin set`。

<a id="the-consent-surfaces"></a>
## 同意界面

同一行承载它所挂载的两个同意插件的 studio 界面，每个界面都基于其插件的路由，通过同源请求完成（`src/client/consents-api.ts`，基于共享的 `src/client/host-api.ts`）。开关关闭的 profile（用“少问（像 DeepSeek Harness）”设置的 profile，或没有该插件的组合）不挂载任何路由，因此该分区只说明该 profile 不询问，权限控件像上游一样切换。除等待中 MCP 服务器的名称之外，每个路由都只回应 home 所在的计算机：远程 studio（例如手机）会在每个界面上被告知要在计算机上批准，并附带适用于该计算机的命令，且没有任何回答途径。文案有英文与中文两种（`src/client/consents-locales.ts`）。

- **完全访问同意**（`delorun-full-access-consent`，`src/client/FullAccessConsent.tsx`）是一个 `shell.overlay` 对话框，它用一句话说明该工作区的 agent 此后可以在沙箱之外运行命令并在任何位置更改文件而不再询问，再用一句话说明这些命令可以读取本人的密钥与令牌；“详情”下写明文件夹以及这些命令能触及的内容：本人在工作区之外的文件、Delorun 的 home 及其密钥与令牌、Docker 监管器以及 Delorun 的更新通道，并说明它只涵盖该工作区。“允许完全访问”会连同它展示的审查一起记录授权，当批准卡片的操作要求时，还会把该 chat 切换到完全访问；“取消”、Escape 与关闭按钮都不记录任何内容；对期间已发生变化的工作区给出的回答会让对话框保持打开，并指出已陈旧的审查。
- **权限控件。**该行提供上游的 `permissionSwitchConsent` 客户端服务（[`@deepseek-ai/dsh-client-ui-permission-presets`](../../../packages/client/ui-permission-presets/README.zh.md)）：本人在 chat 的权限控件或 `/permission` 选择器中选择完全访问时，在上游自己的风险确认之后，若 chat 所在的工作区没有授权，则先显示同意，记录授权即在同一次调用中切换该 chat，因此控件不再提交任何其他内容，设备也只需确认一次点按。其他所有切换，以及已有授权的工作区中的所有切换，都立即提交。
- **工作区同意服务。**该行还提供 `ctx.delorunFullAccess.askForWorkspace(path)`，本人为新工作区选择完全访问时由 `@delorun/plugin-new-workspace` 调用：它为该文件夹的工作区显示同一个同意，授权记录后或工作区已有授权时回答 true。主目录未列出的文件夹以及没有按工作区同意的配置不询问，直接回答 false；远程 Studio 显示同意的远程形式，不记录任何内容。
- **批准卡片的“在此 chat 中允许”选项**（上游 `conversation.approval.choice` 列表 slot 中的 `delorun-allow-for-chat`，[`src/client/AllowForChat.tsx`](src/client/AllowForChat.tsx)；该 slot 属于 [`@deepseek-ai/dsh-client-ui-approval`](../../../packages/client/ui-approval/README.zh.md)）显示在沙箱升权卡片的决定行中，位于“拒绝”和“允许一次”之后，后两者随即绘制为次要按钮。点击它会通过编辑器发送的同一个 `/permission <preset>` 命令，把 chat 的权限 preset 切换到请求所要求的模式，因此该切换与其他切换一样被记录并告知模型，随后以允许来回答卡片；此后 chat 中的命令以该模式运行而不再询问，直到本人在编辑器中调低它。要求工作区写入的请求立即切换；要求完全访问的请求先显示针对此 chat 的那个完全访问对话框，该工作区没有授权时它会记录授权并随之切换该 chat，因此不会再发送第二次切换，取消它则卡片继续等待。已处于或高于请求模式的 chat 不提供此选项，远程 studio（例如手机）对完全访问也不提供。若 host 拒绝切换，卡片保持未回答，host 的句子显示在按钮之下。卡片一旦已回答、正在发送回答或不再接受回答，按钮即被禁用，已在进行中的点击不再切换或记录任何内容：它在点击时、本人确认对话框时以及切换之前，都会读取卡片的 `canAnswer()`。
- **批准卡片的完全访问提示行**（上游 `conversation.approval.action` 列表 slot 中的 `delorun-full-access`，[`src/client/FullAccessAction.tsx`](src/client/FullAccessAction.tsx)）只在远程 studio 上、请求完全访问的卡片中显示：“请在你的计算机上批准。”，因为 home 在那里拒绝工作区审查。在 home 所在的计算机上它什么也不显示。
- **批准卡片的 Face ID 步骤**（`conversation.approval.action` 列表 slot 中的 `delorun-face-id-answer`，[`src/client/FaceIdAnswerAction.tsx`](src/client/FaceIdAnswerAction.tsx)）适用于在远程 studio 上请求完全访问、工作区管理、外部 agent 或真实浏览器的请求。它设置卡片的允许门控，因此“允许一次”、Enter 和其他允许选项会先打开 Face ID 操作面板；授权凭证恰为该请求的会话 id、调用 id 和授权标记并带取值 `allowed-once` 而签发，回答只在其之后发送。取消的面板不发送任何内容，卡片仍可回答；面板的退路是 PIN 键盘，没有设置 PIN 时则是 Cancel。面板和键盘作为模态 `<dialog>` 打开在浏览器的顶层（[`src/client/FaceIdLayer.tsx`](src/client/FaceIdLayer.tsx)），位于每个 studio 对话框和面板之上；在其中按下的按键止于其中。Reject、不授予任何东西或没有调用 id 的请求，以及 home 自己的计算机，从不询问。同样的流程通过 `ctx.delorunFaceGrant`（[`src/client/face-grant.ts`](src/client/face-grant.ts)，`FaceIdGrantOverlay.tsx`）服务其他插件：状态表明需要 Face ID 的 Changes 或更新控件会请求一个恰好覆盖其调用的授权凭证，面板用它自己的话（`change.<control>.title` 和 `.body`）指明该控件。
- **每个敏感调用的 Face ID 步骤**（[`src/client/face-retry.ts`](src/client/face-retry.ts)）适用于远程 studio。home 以 `elevation-required:` 拒绝的 Remote 调用（经网关的 `$liftDenials`），以及指明其授权 `action` 的插件路由 `403 ELEVATION_REQUIRED`（经 `ctx.delorunFaceGrant.fetch`，Packs、新建工作区和 Trash 插件以及本 bundle 自己的分区，包括问题报告的详情，都通过它发送），会打开同一个面板，没有通行密钥的设备先显示键盘。授权凭证恰好覆盖那一次调用：Remote 参数的 `hashArgs`，或方法、带查询的路径和正文的 `hashRequest`；`terminal/create` 携带它所创建的终端的保持窗口，`terminal/attach` 携带它重新打开的现有终端的保持窗口（`terminal/retain` 随后沿用它），`directoryPicker/list` 携带选择器的保持窗口，因此新终端只在创建时询问一次，屏幕上重新加载的终端标签页只在附加时询问一次（它的大小、shell 和列表读取是免费的，每个已保存标签页打开的 retain 从不询问）；被拒绝的流打开也会询问，并重新打开一次；面板等待或显示期间被取消的调用会关闭它。随后该调用再发送一次，Fetch 调用带 `Delorun-Grant`。面板的文字来自 `face-id-locales.ts` 中的 `ACTION_COPY`，按操作名称取用，并有一个朴素的后备。Cancel 不发送任何内容，并留下该界面自己的那一行，对本 bundle 的分区而言，那一行说明该操作每次都需要 Face ID 或 PIN；任何这样的拒绝都不打开解锁对话框。home 自己的计算机从不被拒绝，因此从不询问。`NEVER_ASKED` 中的 Remote 调用（studio 在加载时、重新连接时、收到 home 广播时或自行发送的调用：模型编写的插件运行器的调用和聊天标题的终端名单）从不被询问，在手机上仍被拒绝。页面的每次确认，包括 Changes、更新和批准卡片的确认，都在同一个 `confirmationQueue` 中排队等候。
- **危险模式。**setup 的“危险”回答打开期间，编辑器切换到完全访问的开关与批准卡片的“在此 chat 中允许”都无需对话框就切换该 chat，在计算机和远程 studio 上都是如此，且远程的“请在你的计算机上批准。”提示行会隐藏。studio 从 `GET /api/delorunPermission.everywhere` 读取该状态，已解锁的远程 studio 可以读取，被锁定的则读为关闭。此时“权限”会显示一张卡片，“危险模式已打开：任何 chat 都可以不经询问切换到完全访问”，附日期、句子“在这里或用 `delorun setup prompts` 关闭它”以及一个“关闭”按钮，有正在运行的解锁的远程 studio 也可以点按它，因为关闭只会收紧。模式打开期间，侧边栏徽标下方会在每个 studio 上显示一个小的“危险模式”徽章，并打开“设置 → 权限”；它在挂载时以及窗口重新获得焦点时读取状态，“关闭”会立即将其隐藏。它所填充的 slot `sidebar.brand.badge` 由侧边栏声明。
- **权限**（`delorun-permissions`，位于“设备”之后，`src/client/PermissionsSection.tsx`；Delorun 的外观把它放在 [`@delorun/plugin-settings-layout`](../plugin-settings-layout/README.zh.md) 的“权限”页面上）列出本人给出的每项授权，每项带有一键“撤销”；每次回答的结果是各组之上的一行文字，不属于任何列表行，因此列表刷新不会移除它，每个列表在得到回答之前都会说明正在加载。“完全访问”与“MCP 服务器”两组各以一句话开头，说明 Delorun 询问的是什么。“完全访问”之下列出持有授权的工作区及其起始时间，并说明那里的新 chat 以完全访问开始；“撤销”会立即收回授权，把该工作区中已打开的完全访问 chat 放回更安全的 preset 并说明数量，其他工作区则放在一个展开区之后，在那里“允许完全访问”会打开同意。“MCP 服务器”之下列出每个等待本人确认的 stdio 服务器，以及自其被允许以来的变化（新服务器、其命令、参数、文件夹或具名环境变量、无法读取的已允许服务器列表，或在 Delorun 开始分别记住每个服务器之前记录的接受），其中“审查”打开 MCP 服务器审查，“拒绝”使服务器保持停止；然后是本人已拒绝或已撤销的服务器，它们保持停止直到被允许，也不会产生提示；再后是每个已允许的服务器，附其启动命令与被允许的时间，其中“撤销”收回它的接受，使它停止直到再次被允许，并说明停止了多少行。
- **外部 agent**（`delorun-external-agents`，`EXTERNAL_AGENTS_SECTION_ID`，紧接在“权限”之后，`src/client/ExternalAgentsSection.tsx`；Delorun 的外观把它放在 [`@delorun/plugin-settings-layout`](../plugin-settings-layout/README.zh.md) 的“外部 agent”页面上）在标题为“运行前”的卡片中，包含开关**外部 agent 运行前询问**、开关**完全访问的对话无需询问即可启动智能体**与以分钟计的运行时间限制，它们通过上游的设置服务写入 `delorun-delegation-consent` 行的 `enabled`、`fullAccessStartsAgents` 与 `runTimeoutMinutes`，无需重启即可生效；时间限制在输入框失去焦点或按下 Enter 时写入，且只能是 1 到 1440 的整数。被拒绝的写入会说明这一点并保留 Host 持有的值；在远程 studio 上三者都被禁用，第一个开关会说明关闭它需要计算机，第二个开关在关闭时会说明打开它需要计算机。处于完全访问的顶层 chat（记录的审批策略 `never` 与沙箱模式 `danger-full-access` 同时成立，且其日志中没有委派设置的策略，因此从不是本地 subagent 的）在外部 agent 的启动之下显示一行“已启动，未经询问 · 完全访问”，这是一个 Chat 行（`src/client/full-access-start.ts`），由记录的 `approval/policy`、`sandbox/mode` 和 `subagent/catalog` 事件折叠而成。第二张卡片“已允许的 agent”列出每个被允许在工作区中不经询问启动的 agent，附其“撤销”；撤销的结果是各卡片之上的一行文字。
- **MCP 服务器审查**（`delorun-mcp-review`，`src/client/McpServerReview.tsx`）是一个 `shell.overlay` 对话框，从“权限”和等待服务器提示打开，它用一句话说明该服务器以本人的访问权限在这台计算机上、在沙箱之外运行它自己的命令，再用一句话说明只应从受信任的来源允许它；它写明发生了什么变化，并在“详情”下列出命令、参数、文件夹和环境变量，只对会改变所运行内容的变量（`NODE_OPTIONS`、`LD_PRELOAD`、`LD_LIBRARY_PATH`、`DYLD_*`、`PATH`、`PYTHONPATH`）显示其值。回答记录期间，“取消”被禁用；完全访问同意的做法相同。“允许并启动”会连同它展示的审查一起记录，之后服务器启动；“取消”不记录任何内容，期间已变化的审查会让对话框保持打开，并指出已陈旧的审查。
- **启动卡片**（`delorun-mcp-waiting`，`src/client/McpStartCard.tsx`）是 `conversation.input.dock` Slot 上的一张紧凑卡片，位于消息框上方，宽度随内容，绝不覆盖 chat。它在 studio 打开时、窗口重新获得焦点时以及每 10 秒读取等待中的服务器，并显示第一个：“<server> wants to start”，一行柔和的文字指名该服务器来自哪里（“From plugin …”、“From your editor”、“From a place Delorun could not identify”；在 Always ask 之下还有本人的设置、Settings 或某个包），有多个时显示 “1 of N”。在 home 的电脑上，**Allow** 会立即接受该服务器的审查，并由一条 toast（`delorun-consents-toast`，`src/client/ConsentToast.tsx`）说明它是否已启动；**Not now** 会在本次 studio 会话的剩余时间里为该次审查隐藏卡片，而服务器仍在“设置”→“权限”中等待；**Details** 会打开完整审查。远程 studio 不显示 Allow：它会说明在电脑上允许该服务器，或在危险模式下在“设置”→“权限”中审查它。“设置”→“权限”中的 **Which MCP servers ask first** 选择通过 `src/client/mcp-ask-writer.ts` 按其路径写入同意行的 `ask`。

**网络**分区（`delorun-network`，紧接在“外部 agent”之后，`src/client/NetworkSection.tsx`）通过 [`@delorun/plugin-permission-defaults`](../plugin-permission-defaults/README.zh.md) 仅限回环的路由（`src/client/network-api.ts`）为沙箱内的命令与 `web_fetch` 设置每个工作区的网络：“开放”、带每行一个主机的编辑器和可添加的常用注册表主机的“允许列表”，或“关闭”，以及该工作区是否遵循默认值和“使用默认值”。收紧会立即保存；Host 以 `NETWORK_UNCONFIRMED` 拒绝的更改会打开一个对话框，写明它将开放什么，只有对话框的“允许”才会带着 `confirmed: true` 重新发送。没有这些路由的 profile 显示一行文字，`LOOPBACK_REQUIRED` 拒绝会说明只有 home 所在的计算机才能读取和更改该设置，Host 对被拒绝更改的说明和存储的问题则就地显示。

**How Delorun runs** 分节（`delorun-setup-commands`，`SETUP_COMMANDS_SECTION_ID`，位于 About 之后，`src/client/SetupCommandsSection.tsx`）更改首次运行引导所略过的那些选择，每一项旁边都给出做出同样更改的确切命令：Delorun 询问多少（`delorun setup prompts`）、在后台运行（`delorun setup background`）、profile 名称与 studio 端口（`delorun setup profile`）以及手机访问（`delorun setup reach`）。页面读取 `GET /api/delorunRun.state`，并通过 `delorun-run-settings` 行的路由（[`src/run-settings.ts`](src/run-settings.ts)）更改答案，这些路由经由 [`@delorun/setup-apply`](../setup-apply/README.zh.md)、在 profile 的写锁之下写入 `delorun setup` 所写入的内容。任何已登录的 studio 都可以读取该状态。设备可以把 Delorun 询问多少设为 Ask me first 而无需确认，而设为 Ask less 或设置后台运行则需要对该调用进行 Face ID 或 PIN 确认；没有 PIN 的设备会被拒绝，而 Face ID 通行期绝不覆盖 Ask less。危险模式、studio 端口和手机访问只在回环监听器上、在 home 的电脑上应答：已配对的设备无论解锁了什么都会得到 `403 LOOPBACK_REQUIRED`，在危险模式下也是如此，而且每项更改都必须来自 studio 自己的页面。开启危险模式需要两次请求：`dangerousBegin` 应答警告和一个持续五分钟的一次性代码，而 `dangerousConfirm` 接收该代码、一个 yes 以及输入的短语 `full access everywhere`，home 在写入各行、授权文件和答案记录之前会检查它们；错误或用过的代码、错误的短语、缺少 yes 以及 root 用户都会被拒绝，且不写入任何内容。页面先显示带 No 的警告，然后显示该短语。更改端口会拒绝被占用的端口、正在使用的端口、Web 浏览器屏蔽的端口（6000、6665 到 6669、6697 和 10080）以及手机访问所监听的端口（`400 BAD_REQUEST`），并说明需要重启以及登录地址会改变（`delorun open`）。提示词答案与危险模式在 home 重新加载 profile 之后应答 `restartNeeded`（即 `changes.reload` 所运行的重新组合，位于热重载服务的队列中）：当该服务未挂载、重新加载失败或它指名了重启原因时为 true，因为同意插件随后只在下次启动时读取新行，而页面会显示其重启说明。开启手机访问会先显示地址和信任声明（`reachPreview`），而确认会携带一个针对该预览所读取的 Tailscale 名称的一次性票据，因为开启它会更改 Tailscale；serve 访问检查在写入任何内容之前运行，而行会在写锁之下为这次写入再次读取。关闭手机访问会让每台已配对设备退出登录（`signAllDevicesOut`：会话与 Face ID 通行期结束，已配对列表保留），并重置谁可以在没有窗口的情况下请求配对，因此再次开启不会恢复任何会话；该行用一句话说明这一点。危险模式代码在任何可能拒绝该调用的检查之前就被用掉，并按摘要比较，而请求主体会按其声明长度或在到达时被拒绝超过 2048 字节的内容。setup 未运行过的 profile 没有答案记录，每项更改都会以 `409 NOT_SET_UP` 被拒绝。Delorun 的设置布局把该分节放在 General 页面上。

<a id="the-browser-page-routes"></a>
## “浏览器”页面路由

`delorun-requirements` 行还为设置中的“浏览器”页面提供两个路由（[`src/browser-check.ts`](src/browser-check.ts)），只供 home 所在的计算机使用：每个都是不带正文的 `POST`，不准入任何已配对设备，并在任何东西运行之前，以 `403` 和 `reason: 'at-computer'` 拒绝其 `Host` 不是回环名称的请求。两者都不启动模型轮次。studio 通过 [`src/client/browser-check-api.ts`](src/client/browser-check-api.ts) 读取它们，它只接受不超过 600000 个字符的 PNG 数据地址作为缩略图。

- `POST /api/delorunBrowser.test` 在 Browser 插件包的浏览器中打开一个随 Delorun 提供的固定页面（没有脚本、链接或请求），该浏览器以无窗口方式在新的 profile 中启动，并带着每个 harness 子进程的环境（`scrubbedParentEnv`），并应答带缩略图的 `{ ok: true, image, title }`，或带 `not-added`、`not-installed`（Chromium 构建尚未下载）、`unreadable` 或 `failed` 以及程序最后一行错误的 `{ ok: false, reason, message }`。它在 60 秒后停止。
- `POST /api/delorunBrowser.install` 通过运行 Browser 插件包中已有的 Playwright MCP 包的 `install-browser chromium` 来下载 Chromium 构建，从不使用注册表中的包，并应答 `{ ok: true }` 或 `{ ok: false, reason, message }`。它在 15 分钟后停止，并一次只运行一个下载：第二个请求等待正在运行的那个。启动自己的 Chrome 的计算机，或指名了可执行文件的行，没有可下载的内容，应答 `failed`。

## 测试

`node_modules/.bin/vitest run --config delorun/vitest.config.ts delorun/packages/bundle-local` 运行本包的 spec，它们导入上游已构建的包，因此需要 `pnpm run build:artifacts`；构建缺失时，Delorun 的检查运行器会启动它。

- [`browser-check.spec.ts`](tests/browser-check.spec.ts) 用一套替身工具包和程序覆盖这两个路由：固定页面、缩略图检查、各项拒绝、下载、Host 检查和 studio 的读取器。不会启动真实的浏览器。
- [`composition.integration.spec.ts`](tests/composition.integration.spec.ts) 在临时的 `DSH_HOME` 下构建一个 Delorun CLI profile，并通过上游真实的 `dsh --profile <name> --dump-config` 读取它：列表中的每个组合包都加载，没有被跳过的；转储在每个标签之下打印全部行，标签中的写入方都是列表中的组合包，第一个标签之前不打印任何内容，stderr 上也没有任何内容，并且列出的恰好是由本组合包写入的 `LOCAL_ROWS` 的各行；该组合与上游的 `web` profile 逐行相等，只有 `LOCAL_ROWS` 的各行除外，它们按各条目所述就地更改，或加在上游各行之后。它还要求每个启用的行只使用它所写明的 DeepSeek 主机：只允许出现 `api.deepseek.com`，即本人自己密钥下的模型提供商 API，反馈导出器、账号界面与反馈界面都不在组合中。
- [`privacy-defaults.spec.ts`](tests/privacy-defaults.spec.ts) 用每个 profile 所组合的行挂载上游自己的插件，并对照本地网络 fixture。使用 Delorun CLI profile 的行时，发往模拟 DeepSeek API 的模型请求体都不带 `dsh_session_log`，本地 OTLP 收集器也收不到任何分析记录；使用上游 web profile 的行时，同样的 fixture 两者都能收到。组合中的任何字符串（包括 `!!js` 表达式）都不指向 Delorun 主机，指向 Delorun 包的行只有本组合包自己的浏览器部分、它挂载的六个同意与守卫插件、它的更新闸门以及回收站。
- [`confinement.integration.spec.ts`](tests/confinement.integration.spec.ts) 读取已组合的 `sandbox` 行，并用它配置上游的本地沙箱提供方：该行的 `protectedHome` 是 Delorun home，其 `protectedHomeReadable` 是 C1 的读取豁免，由该提供方隔离的工作区命令无法读取 `<home>/secrets` 之下的 canary，而同一命令不受隔离时可以读取，豁免之下的文件仍然可读。home 位于操作系统临时目录之外（上游的 profile 会把临时目录替换为私有的 `/tmp`），因此拒绝来自受保护的 home，而不是来自私有目录。
- **Setup 版本。**`delorun-profile-versions` 行（[`src/profile-versions.ts`](src/profile-versions.ts)）提供 `delorun recover` 与插件管理共用的历史。`list` 与 `changes` 回应任何已登录的 studio；`save` 与 `switch` 由 Connection 的 `connection/request` 钩子上的 `requireComputer` 在读取请求体之前，以 `403 LOOPBACK_REQUIRED` 回应，除非请求在回环监听器上并带回环 `Host` 到达；若不是来自 studio 自己的来源，则回应 `403 FOREIGN_ORIGIN`。保存与切换使用历史的 `plugin-manager/before-record` 准入，因此带有密钥值的设置文件不会被保存为版本。浏览器部分（`src/client/VersionsSection.tsx`）是 `settings.section` `delorun-setup-versions`（位于“网络”之后，排序 24.5）；Delorun 的设置布局把它放在“数据”之下。远程访问的设备能看到列表和变更，但没有按钮；服务器无论如何都会强制执行。服务器无法重启 Delorun，因此切换之后，页面会告诉本人运行 `delorun stop` 与 `delorun start`。

<a id="limits"></a>
## 限制

- 组合包列表是供 `delorun` 写入的常量；没有任何已发布的上游模板列出它，因此记录会话回放只通过对等 overlay 挂载本组合包。
- 在 `DELORUN_PROFILE_BUNDLES` 变更之前创建的 profile 保留它创建时的列表。
- 只有 `delorun` 启动的 CLI profile 加载本组合包。`delorun headless` 改为加载 `@delorun/bundle-headless`，它带有同样的同意、抓取防护、轮次闸门以及它们免受插件管理影响的保护，但没有“隐私”分区。
- 隐私默认值只在 profile 加载本组合包时成立。上游会把无法加载的组合包报告为已跳过并在没有它的情况下启动，此时会话日志上传是打开的；`delorun` 拒绝启动这样的 profile，正是这一点保持了这些默认值。
- `delorun` 只把信任账单的来源挂接到它从运行时仓库运行的 Host 上，因此源码检出的 studio 读不到账单，其徽章显示为未知。
- 桌面分析只在上游的 `desktop` profile 中挂载，而 `delorun` 不运行该 profile，因此 Delorun CLI profile 的分区显示该行的原因，而不是开关。
