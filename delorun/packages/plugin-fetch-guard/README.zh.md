# @delorun/plugin-fetch-guard

[English](README.md) | 中文

> 英文页面是当前版本；本页可能落后于它。

## 摘要

`@delorun/plugin-fetch-guard` 提供 `fetchGuard` 服务，[`@deepseek-ai/dsh-web-fetch-http`](../../../packages/web/web-fetch-http) 的 `http` 抓取提供方在一次抓取的每一跳之前——初始请求与每个重定向目标——都会询问它。提供方先解析跳的主机名，因此守卫分类的是连接实际会使用的地址，而不只是名称；拒绝会抛出一个类型化错误，作为抓取的失败向外传播，模型原样读到它，并且不建立任何连接。该服务对消费方是可选的：提供方在每一跳用 `ctx.get()` 读取它，因此挂载或卸载本插件会改变下一个请求，而无需重新加载提供方；没有挂载守卫时，每一跳不做解析。stock 的组合不挂载本插件，因此 stock 的 `web_fetch` 会抓取回环与私有网络目的地。`@delorun/bundle-local` 将它挂载为开启，因此 `delorun` 启动的 CLI profile 会拒绝这些目的地；`@delorun/bundle-headless` 为 `delorun headless` 将它挂载为开启；两种启动都要求该行，若该行未能启动或 `fetchGuard` 服务不存在，Host 会在启动后被停止，因此 `web_fetch` 在它们之下从不无守卫地运行（[`compose.ts`](../../apps/cli/src/compose.ts)）；桌面应用运行上游的 profile，它们不挂载本插件，与 stock 一样抓取这些目的地；Config 默认值仍是对等值——关闭，而对等组合让该行保持禁用，于是录制下来的 stock 场景仍然不加守卫地重放。这就是 Delorun 的 C16 开关 `fetch_guard`。

## 约定

- **拒绝矩阵。** 开关打开时，解析到的任一地址属于回环地址（`127.0.0.0/8`、`::1`）、链路本地地址（`169.254.0.0/16`、`fe80::/10`）、RFC1918 私有地址（`10/8`、`172.16/12`、`192.168/16`）或已弃用的 IPv6 站点本地地址（`fec0::/10`）、IPv6 唯一本地地址（`fc00::/7`）、共享地址（`100.64.0.0/10`，tailnet 及其 API 所在的运营商级 NAT 网段）、组播地址（`224.0.0.0/4`、`ff00::/8`）、保留地址（`240.0.0.0/4`，其中含广播地址 `255.255.255.255`，以及 IPv6 的 IPv4 转换地址 `::ffff:0:0:0/96`）或未指定地址（`0.0.0.0`、`::`）时，守卫拒绝该跳。能到达某个 IPv4 地址的 IPv6 目的地按该 IPv4 地址分类：IPv4 映射、IPv4 兼容或 NAT64（`64:ff9b::/96`，以及按 /96 部署的本地使用前缀 `64:ff9b:1::/48`）地址按其低 32 位，6to4 地址（`2002::/16`）按前缀之后的 32 位，Teredo 地址（`2001::/32`）按其客户端地址，即取反后的低 32 位。分类器无法解析的地址同样被拒绝：说不清连接会去向何处的守卫不会放行。其余地址全部放行（[`guard.ts`](src/guard.ts)）。IP 字面量目的地（包括 URL 方括号中的 IPv6，如 `http://[::1]/`）直接按该地址分类，不做查询。
- **拒绝。** 被拒绝的抛出 `FetchGuardRefusedError`，带有代码、请求所写的主机名，以及只点名这两者的消息——不含解析到的地址，不含接口名——因此拒绝可以原样引用进工具结果，而不泄露多出被请求内容的信息。
- **每一跳。** 守卫位于提供方的重定向循环之外：初始请求与每个同源重定向目标都在其连接建立之前被解析并检查，因此在两跳之间重绑定到私有地址的主机名会在那一跳被拒绝。
- **钉住连接。** 守卫批准的地址是该跳唯一可以连接的地址：提供方把直连的跳发往一个 agent，其解析器只回答这些地址、并按守卫看到的顺序回答，对未经批准的主机名则让该跳失败。因此，对守卫的查询与对连接自身的解析给出不同回答的解析器，无法把抓取带往守卫从未见过的地址。由已安装代理路由的跳保留代理的 dispatcher，因为目标由代理自行解析。
- **开关关闭。** `enabled: false` 是默认值，也是对等值。此时插件不提供任何服务，提供方在每一跳读到它不存在，于是不加守卫地运行，每一跳也不做主机名解析：抓取与 stock 逐字节相同。
- **消费方。** 服务按名称读取，而不是导入：任何提供 `fetchGuard` 的插件都会守卫提供方的每一跳，守卫变化时提供方无需重新加载。`web_fetch` 工具以与其他抓取失败相同的类型化错误报告拒绝；守卫只覆盖 `http` 提供方——命令，以及你配置的代理或远程抓取提供方，都在它之外。

<a id="configuration"></a>

## 配置

| 字段 | 默认值 | 含义 |
| --- | --- | --- |
| `enabled` | `false` | 在每次连接建立之前拒绝拒绝矩阵中的目的地。关闭时——C16 开关 `fetch_guard`——插件不提供任何服务，`web_fetch` 的行为与 stock 相同。 |

<a id="known-limitations"></a>

## 已知限制

- 守卫判定的是 `node:dns` 为该跳主机名解析到的地址，而钉住的连接随后只连接这些地址，因此在守卫的查询与连接之间的重绑定无法把该跳改道。钉住覆盖的是直连：由已安装代理路由的跳由代理解析，在钉住之外。
- 拒绝只点名主机与原因，不点名解析到的地址；一跳因若干地址中的一个被拒绝时，报告既不指出是哪一个，也不列出其余的。
- 守卫只覆盖 `http` 抓取提供方。`deepseek` 提供方自己的 API 调用与代理策略都在它之外。

## 测试

[`tests/guard.spec.ts`](tests/guard.spec.ts) 覆盖脱离 Cordis 的拒绝矩阵：每个被拒绝的网段与拼法、放行的貌似公开的地址，以及类型化拒绝的各字段。[`tests/service.spec.ts`](tests/service.spec.ts) 挂载服务，覆盖它的开关、它的拒绝，以及卸载对名称的影响。[`tests/provider-guard.spec.ts`](tests/provider-guard.spec.ts) 把真实的提供方插件与守卫插件作为兄弟挂载，并 mock 掉 `node:dns` 与 `undici`——不运行任何网络——证明整条链：连接之前的主机名解析、任何连接之前的类型化拒绝、重绑定重定向跳的拒绝、被批准的跳发往钉住它的 agent、按名称被提供方询问的作为兄弟挂载的 stub 守卫插件、晚于提供方挂载的守卫从下一跳起被读取，以及完全没有解析的不加守卫的运行。[`tests/pinned-connection.spec.ts`](tests/pinned-connection.spec.ts) 在真实传输上证明钉住：一个回环监听器会返回响应体，解析器对守卫回答一个文档地址、对连接则会回答回环，而抓取既没有到达监听器，也没有拿到响应体。
