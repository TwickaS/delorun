# @delorun/plugin-mcp-consent

English | [中文](README.zh.md)

## Summary

This package is the `mcpAddConsent` provider of Delorun's MCP add-time consent, the protection the C16 switch [`mcp_add_consent`](../../docs/contracts/c16-parity-composition.md) turns on. A stdio MCP server command runs as a local child process outside the agent sandbox, so before such a server starts, the mcp-client plugin asks the mounted `mcpAddConsent` service whether the configured start is granted. This package answers from the acceptance store, one JSON file under the home's protected state that holds one acceptance per configured server name: a server whose acceptance covers exactly the command, arguments, working directory and configured environment under review, and the absolute executable path, command shell and working directory they resolve to, and whose pinned files still hold the contents accepted, starts at once, and every other review holds the server stopped with a refusal that names the command. Which servers ask depends on where their definition lives and on the `ask` setting ([Origins and the ask mode](#origins-and-the-ask-mode)); by default a server the person's own configuration or one of Delorun's packs brings starts unasked. The person accepts a held server at the home's own computer, in the studio's Settings, Permissions, or with `delorun mcp accept`, and the server then starts without a restart; the person declines it, or revokes an acceptance there or with `delorun mcp revoke`, and that server stays stopped until its start changes or the person accepts it ([Pending reviews](#pending-reviews)). Off, or without a mounted provider, an mcp-client starts every configured server exactly as upstream does; `@delorun/bundle-local` mounts it on in the CLI profile that `delorun` starts, `@delorun/bundle-headless` mounts it on in the profile `delorun headless` runs, and the desktop app runs upstream's profiles, which do not mount it.

## The service

`DelorunMcpConsent` extends the abstract `McpAddConsent` service of the `@deepseek-ai/dsh-mcp-client` seam, whose `review` the mcp-client consults before it starts each configured stdio server. The review never waits for a person: allowing a start starts the server, and refusing one fails the mcp-client's activation with the typed refusal that names the command and its arguments and carries the provider's reason, so the server stays stopped. A refusal repeats at every boot of the server row until the start is accepted, and an acceptance given after a refusal lets the next boot start the server.

A review is shown the server's whole start: the server name, the command, its arguments, its working directory and its configured environment entries, with the absolute executable path and canonical working directory the mcp-client resolved them to, and on Windows the canonical `COMSPEC` that runs a `.cmd` or `.bat` file. The mcp-client resolves an empty or relative working directory against the Host's working directory and looks a bare command up in the `PATH` the server would be started with, then spawns the server with those resolved paths, so an accepted start runs the executable the person accepted even when the Host starts in another directory or its `PATH` changes. A command it cannot resolve stops the server with `McpServerStartUnresolvedError` before any review. The refusal names the resolved executable, the working directory and the names of the configured environment variables but none of their values, because a value may be a credential. The review also pins the contents of the executable and of each file an argument names ([Pinned files](#pinned-files)), but not the files the program loads by itself: when the working directory or a pinned file lies where chats can write, a module written there later runs outside the sandbox at the next start or reconnect, and the review says so instead of refusing it ([Places chats can write](#places-chats-can-write)).

With `expandTemplates`, the mcp-client fills `${credential:NAME}` parts of arguments and ordinary environment values from stored credentials at start, so the review sees and pins the template text and no secret. Three rules keep a stored credential from changing what the review approved. A template in `command`, `cwd` or the value of a run-affecting variable (the names [`showsEnvValue`](src/wire.ts) lists) is refused when the server loads, naming the server and field; write the value directly or use another variable name. The reviewed command and working directory are always the ones the server spawns, so a file named like a template is never expanded. An argument that is wholly a template and resolves to a value starting with `-` is refused at start, naming the server and argument index and never the value; a partial template such as `--token=${credential:NAME}` stays allowed. The review shows a templated argument unresolved with a note that it is filled from stored credentials at start.

The module exports `providesMcpAddConsent` as `true`, the declaration the mcp-client's consent lookup reads under the Loader: an mcp-client row that finds no `mcpAddConsent` service waits until every row has imported its module and this row has started, so a server never starts unreviewed because its row started before this one. If this row fails to start, the server stays stopped with `McpConsentUnavailableError`; with the switch off, the row starts and registers nothing, and the server starts as upstream starts it.

The mcp-client asks for the review at every boot of a server row and again before every reconnect spawns the server after its connection dropped. A refusal at a reconnect stops the reconnect loop and unregisters the server's tools; the row stays active, its review is pending, and accepting it starts the row again.

The service resolves the home the process runs with for every review: `resolveDelorunHome` of [`@delorun/home`](../home/README.md) resolves it from `DELORUN_HOME` or `~/.delorun`, so a home that cannot be resolved is one more review that asks again.

## The acceptance store

The store is `secrets/mcp-add-consent/acceptances.json` under the resolved home. It is a protected file of contract C1 ([`@delorun/home`](../home/README.md)): it is read through the refusal rule and written at mode 0600 into a directory created at mode 0700, under the home's `secrets/` directory, which the sandbox's confinement rules deny to confined commands on Linux and macOS (the Windows runner does not confine reads) — a command an acceptance would let run outside the agent sandbox can neither read the list nor add itself to it.

The file is one JSON object `{ v, acceptances, setAside }` whose `v` is the format version, 7:

- `acceptances` maps a configured server name to the start accepted for it: the command, the argument list, the configured working directory, the absolute executable path and canonical working directory they resolved to, for a Windows batch file the canonical `COMSPEC` as `resolvedShell` (absent otherwise), the environment as each variable's name with a SHA-256 digest of its name and value, the pinned files (`files`, see [Pinned files](#pinned-files)), the acceptance time, and the origin of the server's definition the person accepted it for (`origin`, one of `profile`, `settings`, `chat`, `unknown`, `pack:<plugin>` or `plugin:<plugin>`, at most 300 characters; absent when the acceptance was recorded before origins were kept). An acceptance covers a server of its own origin, or of any origin when it holds none ([`acceptanceCovers`](src/store.ts)), so accepting a server of one origin does not accept a server of the same name from another. Different server names never share or overwrite an acceptance, so two servers started with `npx` keep separate acceptances; accepting a changed start of the same server replaces its acceptance. An acceptance's id ([`acceptanceIdOf`](src/store.ts)) is a digest of the server name and the whole start, resolved paths included, so a revoke names one acceptance.
- `setAside` maps a server name to the start the person declined or whose acceptance the person revoked: the state, `declined` or `revoked`, and a digest of the whole start, resolved paths included ([`startDigest`](src/store.ts)). A review of that exact start is refused in that state without waiting for an answer, across restarts; a review of another start of the server, or of the same start that now resolves elsewhere, drops the entry and waits, and accepting the server drops it.

A version-6 store, which recorded no origin, is read forward: its acceptances and set-aside starts are kept, each acceptance with no origin, so it counts for its server name from any origin until the person accepts that server again, and the next write is version 7. The store holds no environment value in plain text, and the digests are the same whatever order the environment's keys were written in. A store that exists but is not this format — no JSON document, not an object, a version other than 7 and 6, an unknown field, an origin that is not one of the forms above, a wrong entry, a resolved path that is not absolute — is refused as a whole: no review counts anything as accepted, the provider never writes into it, and every refusal names the file and asks the person to fix or remove it and accept each server again.

Every change to the store (an acceptance, a decline, a revoke, a dropped set-aside start) reads, changes and writes it while holding its lock file, `acceptances.json.lock` beside it, `@delorun/home`'s lock file: the store is shared by every profile of the home, so a revoke in one profile's process and an acceptance in another's never overwrite each other. A live holder is waited for up to ten seconds, after which the change is refused and records nothing; a dead holder's lock is removed.

## Reviews

`review(command, client)` answers one configured server start; `client` is the context of the mcp-client plugin that starts it, which the origin is judged from ([Origins and the ask mode](#origins-and-the-ask-mode)). A server that does not ask under the `ask` setting is allowed at once, with no pending review and no acceptance. Otherwise:

- the server name's acceptance of exactly the reviewed command, arguments, working directory, environment, resolved executable path, command shell and resolved working directory allows the start;
- an absent store, an unreadable or not this version's format store, a server with no acceptance, a changed command, argument list or working directory, an added, removed or changed environment variable, a command that now resolves to another executable, a batch file that now runs through another `COMSPEC` or none, a working directory that now resolves to another directory, a start the person set aside, and a home that cannot be resolved all refuse with the reason that asks the person again. A reason names changed variables and resolved paths but no environment value, and another server name's acceptance of the same start never counts.

### Origins and the ask mode

The review decides by where a stdio server's definition lives, judged from the plugins that mounted the server's mcp-client ([`originOf`](src/origin.ts)) and never from the server's name, command or configuration, so a server a plugin brings cannot pass for the person's by naming itself after one. The origin is one of [`ServerOrigin`](src/wire.ts):

- `profile`: a row of the profile's configuration;
- `settings`: a server of the MCP manager's Settings list;
- `pack`: mounted by a plugin of one of Delorun's packs, by the row's module; [`src/pack-plugins.ts`](src/pack-plugins.ts) lists those modules from each pack's `cordis.patch.yml`, [`tests/pack-plugins.spec.ts`](tests/pack-plugins.spec.ts) checks the list, and a pack that adds a row updates it;
- `plugin`: any other plugin, or a server a plugin registers through the MCP manager;
- `chat`: mounted by one chat's own setup, which an editor's ACP session uses for the servers it brings;
- `unknown`: no Loader row owns the mount, or the mcp-client passed no context.

The `ask` field of the consent row decides which origins wait for the person ([`asksFor`](src/wire.ts)): `outside`, the default, asks for `plugin`, `chat` and `unknown` servers; `always` asks for every stdio server; `never` asks for none. Settings, Permissions offers the three as "Ask for project servers", "Always ask" and "Never ask". An acceptance is keyed by origin and server name ([The acceptance store](#the-acceptance-store)), so accepting a server from one origin does not accept the same name from another.

### Pinned files

Each review pins the files the start runs ([`src/pins.ts`](src/pins.ts)): the resolved executable, with every symbolic link followed to the file itself, so a `node_modules/.bin` entry pins the script it points to, and each argument that, resolved against the resolved working directory, names an existing regular file, such as `server.js` in `node server.js`, followed through its links the same way. An argument of the form `--option=value`, such as `--import=./hook.js` or `--require=./hook.js`, pins the file its value names when the whole argument names none. Each pin is the canonical path and a SHA-256 digest of the contents, read through one handle opened without waiting and without following a final symbolic link, so a path swapped for a FIFO or a device is refused at once instead of hanging the review; the handle's own status must name a regular file, its device, inode, size, modification and change times must agree before and after the read, and the path must resolve to the same file afterwards. An acceptance holds the pins its review showed; a review whose pins differ is refused with the change `contents`, naming the file: a rewritten file, a path that now resolves to another file, or an argument that names a file now or no longer. A file that cannot be read refuses the start with `contents` and no pins. Every review reads each file again; no digest is kept between reviews, because a file system that does not maintain change times (drvfs, 9p, some FUSE mounts) lets an in-place rewrite keep every status value. Hashing a 121 MiB Node.js binary takes about 0.15 s.

An allowed start is spawned with the canonical path of its pinned executable (the decision's `spawnCommand`), not the path the command resolved to, so a symbolic link such as a `node_modules/.bin` entry pointed elsewhere after the review does not change the file that runs; the review shows that file when it differs from the resolved command. The spawned file sees the configured command as its `argv[0]`, so a program that locates itself by the name it was invoked by runs as it would from that command: a virtual environment's `python` link finds its virtual environment, and a multi-call binary such as BusyBox sees the applet name. On Windows this is untested, and a `.cmd` or `.bat` shim keeps the `argv[0]` of the command shell that runs it.

Pins cover those files only. A file the program loads by itself (another module of the script, the rest of a package, a shared library, the interpreter's own modules, a module `python -m` names, a file `NODE_OPTIONS` names), a directory an argument names, an option whose value is joined without `=` (`-r./hook.js`), the interpreter a script's `#!` line looks up in the server's `PATH` after the spawn, and code a package runner (`npx`, `pnpm dlx`, `bunx`, `uvx`, `pipx run`) downloads when it starts are not pinned. Between the last review and the spawn, a pinned file rewritten in place, or a link an argument passes through pointed elsewhere, runs unreviewed until the next review; the review runs immediately before each spawn to keep that time short.

### Places chats can write

A pending review names the canonical working directory and the pinned files that lie inside a place this profile's chats can write ([`src/writable.ts`](src/writable.ts)): a workspace of the profile's workspace registry, or `/tmp` and the platform's temporary directory, which every confined command may write. The studio's review and `delorun mcp accept` show them before the person answers, because a chat can change such a file, or a module loaded from such a directory, and the change to a module is not reviewed. A chat with full access writes outside these places as well; those are not detected.

Every refusal's reason ends with where the person accepts the server: `delorun mcp accept <name>` at the home's computer while Delorun runs, or the studio's Settings, Permissions ([`acceptHint`](src/review.ts)).

## Recording an acceptance

`accept(start, files?)` records that the person accepted a server start — the server name, the command, its arguments, its working directory, its configured environment and the resolved executable path, command shell and working directory a review was shown — as that server name's acceptance, with the pinned files given, or pinned now when omitted; a start whose resolved paths are not absolute, or whose files cannot be pinned, is refused. Accepting a server again replaces its earlier acceptance, so a changed start is granted by accepting it as it now is. The acceptance drops the server's declined or revoked start. The store's acceptances grow only through it; `acceptReview` calls it with the start a pending review showed.

## Pending reviews

Every refused review is kept, in this process, as the server's pending review: one per server name, the latest, so a start that changed after a review replaces that review. The service is also provided as `mcpReviews` ([`src/review.ts`](src/review.ts)):

- `pending()` lists each pending review as a surface shows it ([`PendingServer`](src/wire.ts)): the server name, its origin (`origin`), the command, its arguments, its working directory, the absolute executable (`resolvedCommand`) and canonical working directory (`resolvedCwd`) the start resolves to and, on Windows, the command shell that runs a batch file (`resolvedShell`), so a surface shows the file that runs before the person answers, the configured environment variables, the pinned files (`files`), the working directory and pinned files that chats can write (`writableByChats`), the refusal's reason, what the review asks about, the changed variables, its state, when it was reviewed and its review id — a digest of every field of the start, the environment through its digest ([`mcpReviewId`](src/review.ts)). An environment variable's value is shown only when [`showsEnvValue`](src/review.ts) holds for its name: `PATH`, `BASH_ENV`, `ENV`, `GCONV_PATH`, `JAVA_TOOL_OPTIONS`, the program selectors and every name starting `LD_`, `DYLD_`, `NODE_`, `PYTHON`, `PERL5`, `RUBY` or `OPENSSL_` (the list of `isRunAffectingEnv` in `@deepseek-ai/dsh-mcp-client`, which also refuses a credential template in them), which change what runs; every other value is never shown. `change` is one of [`SERVER_CHANGES`](src/wire.ts): `new` for a server with no acceptance or an absent store; `command`, `arguments`, `directory` or `environment` for the first part of the start that differs from the server's acceptance, with `changedVariables` naming each variable added, removed or changed; `resolved` for a start configured as accepted whose command now resolves to another executable, whose working directory resolves to another directory, or whose batch file runs through another command shell; `contents` for a start whose pinned files differ from the acceptance's or cannot be read; `unreadable` for a refused store or a home that cannot be resolved. `state` is one of [`SERVER_STATES`](src/wire.ts): `waiting`, `declined` or `revoked`.
- `acceptReview(serverName, reviewId, confirmed)` first resolves the shown start's command and working directory again with the mcp-client's `resolveServerStart` and pins its files again; when they now resolve to another executable, directory or command shell, a file differs from the shown pin, or the start or a file no longer resolves or reads, it records nothing and refuses with `STALE_REVIEW`, and a start that resolves elsewhere or runs other contents is reviewed again, so the list shows the new paths and files under a new review id. Otherwise it records exactly the start and pins that review showed through `accept`, in any state, removes the review, and starts each Loader row of that server again with its own configuration, a row this consent refused at its boot and an active row whose reconnect it refused, and the MCP manager's server of that name when a failed start stopped it (`mcpManager.restart`), so the server runs without a restart of the studio; without a Loader, the next start runs it. A chat that is open gets the server's tools from its next model request, because the agent loop resolves tools at each step. `declineReview(serverName, reviewId)` keeps the review listed as `declined`, records the start as declined and records no acceptance; the server stays stopped until its start changes or the person accepts it. While the store cannot be read or written, the decline holds in this process only and a warning says so.
- `accepted()` lists each acceptance ([`AcceptedServer`](src/wire.ts)): its id, the server name, the command, its arguments, its working directory, the executable, working directory and command shell it resolved to, its environment variables, its pinned files, the acceptance time, and whether a configured Loader row has the server name; a variable's value appears only where `showsEnvValue` holds and the server's configured row sets the value whose digest the acceptance holds. It lists none while the store is absent or cannot be read. `revokeAcceptance(acceptanceId, confirmed)` removes that acceptance, records its start as revoked, then applies each Loader row of that server name again with its own configuration, so its review refuses the start as `revoked` and the server stops until its start changes or the person accepts it again; it answers how many rows stopped and leaves every other acceptance.
- The answers refuse with `McpReviewError` and record nothing for `UNCONFIRMED` (an accept or revoke without `confirmed: true`), `STALE_REVIEW` (the server has no pending review with that id because it was reviewed again or accepted after it was shown, its start now resolves to other paths than the review showed, or no acceptance has the revoked id because it was replaced or revoked) and, for an acceptance or a revoke, `STORE_REFUSED`, which also refuses a shown start whose resolved paths are not absolute. Each answer logs one line.
- Where a Connection serves the studio, five exact routes under `/api` carry them ([`src/wire.ts`](src/wire.ts), [`src/routes.ts`](src/routes.ts)): `GET /api/delorunMcpConsent.pending` (the pending reviews and the accepted starts), `GET /api/delorunMcpConsent.waiting`, `POST /api/delorunMcpConsent.accept`, `POST /api/delorunMcpConsent.decline` and `POST /api/delorunMcpConsent.revoke`. Each but `waiting` answers only a request that arrived on the loopback listener under a loopback `Host`; a reach device is refused with `403 LOOPBACK_REQUIRED` before the body is read, so a server is accepted or revoked only at the home's computer, unless dangerous mode holds: then a device that holds an unlock is admitted to the four routes ([`@delorun/home-auth`](../home-auth/README.md#dangerous-mode)). `waiting` also admits the Peer of a device that reach admitted (`admitPeer`) and answers only the name and `change` of each review in state `waiting`, never a declined or revoked one and never a command, arguments, directory or environment, so a phone can say that a server waits and is approved at the computer. The studio's Permissions section, the MCP server review and the card above the message box that says a server wants to start live in [`@delorun/bundle-local`](../bundle-local/README.md#the-consent-surfaces); `delorun mcp` reaches the same calls through the home process's `mcp.list`, `mcp.accept`, `mcp.decline` and `mcp.revoke` ([C19](../../docs/contracts/c19-home-process.md)), which only the person's own command may answer.

## The mcp_add_consent switch

The `enabled` config field, the C16 switch `mcp_add_consent`, decides whether the plugin registers the service. It defaults to off — the parity value — and Delorun's composition turns it on; a `cordis.yml` row mounts the package and names the switch's value. Off, the plugin registers nothing and every configured server starts exactly as upstream starts it. The `ask` field (`outside`, `always` or `never`, default `outside`) then decides which servers ask ([Origins and the ask mode](#origins-and-the-ask-mode)). `enabled` and `ask` are computer-only switches of `@delorun/home-auth`: a reach device's settings write to either is refused, because turning the consent off or changing which servers ask lets a server start unasked. Changing the ask mode restarts the consent row, and the restarted consent reviews again each server the previous mode left stopped, a Loader row that failed with a consent refusal or an MCP manager server whose start failed (`DelorunMcpConsent.startRefused`): a server the new mode no longer asks for starts at once without a restart, and one it still asks for is refused again and listed.

## Development

`tests/consent.spec.ts` covers the store, its refusal of every other version, its lock and the reviews; `tests/reviews.spec.ts` covers the pending reviews with what changed, which variables and which values are shown, the declined and revoked states across a new service instance, the restarted row, the accepted starts kept apart per server name and their revoke, and the routes, with the denial cases: a reach device reads only the waiting servers' names and what changed and is refused every other route, and an unconfirmed or stale answer or revoke records nothing. `tests/pinning.spec.ts` and `tests/pin-races.spec.ts` cover the pins and their denial cases: a rewritten executable or script, a retargeted `.bin` link, a removed or newly named argument file, an unreadable file, a file that changes while it is read, a canonical path replaced by a link, a rewrite no status value shows, the path an allowed start is spawned with, the paths chats can write, and an answer to a review whose file changed after it was shown. `tests/pin-fifo.integration.spec.ts` covers a path that names a FIFO, refused without waiting, and `tests/store-lock.integration.spec.ts` a second process that holds the store's lock while a revoke waits for it. `tests/restart.spec.ts` runs the acceptance and the revoke under a real Loader, and a script rewritten while its server runs, which the reconnect reviews again and holds until the person accepts it. The specs run with `node_modules/.bin/vitest run --config delorun/vitest.config.ts delorun/packages/plugin-mcp-consent`, and the package typechecks with `node_modules/.bin/tsc --noEmit -p delorun/packages/plugin-mcp-consent/tsconfig.json`.

## When the service fails

A consent row whose service fails to start is not active, and the MCP client leaves every stdio server stopped with an error that names the row ([`fail-closed.spec.ts`](tests/fail-closed.spec.ts)). With `enabled` off the servers start as stock.
