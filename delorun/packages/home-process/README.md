# @delorun/home-process

English | [中文](README.zh.md)

## Summary

This package is the home process of [contract C19](../../docs/contracts/c19-home-process.md): one process per CLI profile that holds the profile's home lock under `~/.delorun`, writes a new start token at each start, serves the update channel on `run/<profile>/update.sock`, launches the Docker supervisor ([C9](../../docs/contracts/c09-runtime-supervisor.md)) when its caller passes a supervisor setup, and runs the profile's Host in the same process. `delorun start` passes no supervisor setup, so no supervisor runs ([the supervisor](#the-supervisor)). An update reaches it only through the update channel and moves the profile to a new runtime only after no chat runs on the old one, so `current` never switches under a running chat. It logs to [C20](../../docs/contracts/c20-operational-logs.md)'s `home-<profile>` surface through [`@delorun/logs`](../logs/README.md). The protocol's types and limits come from [`@delorun/contract-home-process`](../contract-home-process/README.md); the lock, the token and the channel's listener come from [`@delorun/home`](../home/README.md). `delorun start`, `stop` and `status` ([`delorun/apps/cli`](../../apps/cli/README.md)) drive it.

## Starting a home process

`HomeProcess.start(options)` runs C19's start sequence in order and stops at the first failure, which it logs and throws after undoing what the start created:

1. check that the home, `secrets/` and `run/<profile>/` are private (`HOME_MODE`);
2. take the home lock with the caller's `startId`, asking a live holder for its `status` through the update channel within 2 seconds (`HOME_RUNNING`, `HOME_UNRESPONSIVE`);
3. finish an interrupted update from the journal ([interrupted updates](#interrupted-updates));
4. write a new start token with `writeNewStartToken` and register it with the log's redactor;
5. listen on the update channel, which answers `status` with `starting` from here;
6. launch the supervisor when `options.supervisor` is set;
7. boot the Host through `options.host`;
8. the confinement probes are not run ([not implemented](#not-implemented));
9. enter `running`.

An `exit` listener removes this start's token file and socket and releases the lock while each is still this start's, however the process ends. Once the lock is held, the process registers its one `SIGTERM` and `SIGINT` listener through `options.onSignal` (`listenProcessSignals` in a real process): the first signal runs `HomeProcess.shutdown` with code 0 for `SIGTERM` or 130 for `SIGINT`, and a second one while that stop runs calls `options.exit` at once. The listener stays across every Host the process boots, so the Host's profile runner is booted without its own signal handlers. A start that fails once its Host booted stops that Host through `RunningHost.suspend`, which ends no process, waiting at most `REFUSED_HOST_STOP_S` (5 seconds), before the rest of its failure handling; `refuseBootedHost` gives a Host that a check refused inside `HostRunner.boot` the same wait. A teardown that fails or takes longer turns the failure into a `HostNotStoppedError` whose `cause` is the original failure: the Host may still use the data, so the start rolls nothing back, starts nothing again, removes its signal listener and keeps the lock until the process ends. A second start for the same profile finds the lock held and fails with `HOME_RUNNING`; the desktop app's `profiles/desktop/lock` is a different file, which the home process never reads or writes.

## The update channel

`listenUpdateChannel` serves `@delorun/home`'s token channel with C19's limits: one request line of at most 16,384 bytes per connection, arriving within 5 seconds (`REQUEST_TOO_LARGE`, `REQUEST_TIMEOUT`), and at most 8 open connections (`BUSY`). The token is compared in constant time before anything else in the line is read; a missing, malformed, wrong or previous start's token receives `UNAUTHENTICATED` with no other field, and refusals are logged without the presented value at most once per second. `checkUpdateRequest` then checks the closed schema: an unknown `op`, an unknown field at any depth, a `v` other than 1 or a value outside its type is refused with `SCHEMA_VIOLATION`, so a request names at most a version, never a path, an archive, a URL or a command. A request runs on when its caller disconnects, and that caller's connection no longer counts towards the 8.

Confined commands reach neither the channel nor the token where C1's rules hold: `delorun` boots the CLI profile with upstream's local sandbox provider set to protect the home and deny the channel's socket ([the CLI's start](../../apps/cli/README.md#the-home-process)); under Landlock a confined command can connect but cannot read the token, so its request fails `UNAUTHENTICATED`. The Windows runner confines neither reads of the token nor connections to the socket, and `delorun headless` runs upstream's profile, whose sandbox protects no home, so a command confined there can read the token and use the channel. `sendHomeRequest` is the client side for `delorun`: it reads the token file when it sends a request and retries a `BUSY` answer. `updateChannelProbe` is the holder probe the lock uses. A Host reaches the channel only through the `UpdateChannelAccess` it receives at boot, which holds the Host's channel token in memory: a second token each start creates and never writes to a file, which the channel accepts for every operation but `studio.open-token`. The Host that `delorun start` boots does not use it, and the studio has no update or rollback action: updates and rollbacks go through `delorun update` and `delorun recover`. `studio.open-token` ([studio link](src/studio-link.ts)) asks the Host's `RunningHost.studioLink` for a studio sign-in link and is accepted only with the start token from the token file, so a request sent with the Host's channel token, such as one the Host forwards for a studio session, cannot obtain a link; the response line is not logged. The split does not confine Host code: a Host plugin runs unconfined in this process and can call upstream's `authenticatedUrl` itself or read the token file.

`devices.approve` (`src/devices-approve.ts`) is C5's local approval: without arguments it opens the approval window of `@delorun/home-auth` through `RunningHost.devices` and answers once a request is pending or the window closed; with `requestId` and `typedCode` it approves that request; with `cancelRequestId` alone it cancels that pending request. It is accepted only with the token file's token, and the Host's token is refused with `LOOPBACK_REQUIRED` before anything opens (the `the channel token cannot call devices.approve` spec).

The consent operations (`src/consents.ts`) reach the Host's consents through `RunningHost.consents`: `permission.reload` makes the Host read the per-workspace permission store again and answers the digest of the entries it now holds; no Delorun process sends it, because each Host watches the store itself; `mcp.list` answers the stdio MCP servers the add-time consent holds stopped, each with the part of its start that changed since the server's acceptance (`change`, with the changed variables) and whether the person declined or revoked it (`state`), and the accepted starts, one per server name (`accepted`); `mcp.accept` and `mcp.decline` answer one server by the review id `mcp.list` showed, and `mcp.revoke` withdraws one server's acceptance by the acceptance id `mcp.list` showed and stops that server. Those three are accepted only with the token file's token, and the Host's token is refused with `LOOPBACK_REQUIRED` before any consent is read (the `the channel token cannot answer an MCP server` spec); a review the server no longer has, or an acceptance the store no longer holds, is refused with `STALE_REVIEW`, and a profile without the consent with `CONSENT_UNAVAILABLE`.
`changes.reload` carries nothing: while the process is `running` and no update or rollback runs (`UPDATE_IN_PROGRESS` otherwise), it asks the Host to load what the profile's files now name and answers `{"reload":{"ok":true}}` or `{"reload":{"ok":false,"error":"…"}}`. `delorun changes` sends it after it changed the profile's files ([C21](../../docs/contracts/c21-changes.md#commands)); it changes no file itself.

## The update handshake

`UpdateHandshake` runs C19's phases, writing the update record `run/<profile>/update.json` at mode 0600 at the start of each phase from `snapshot` on, with the version the `previous` pointer named before the update, whether the data differs, whether a copy is taken, `targetStarted`, the profile history version's id (`snapshot`) and the report's health expectations (`health`). The successor marks the record `committed`. Every rollback rewrites it with phase `rolling-back` before the table's first step, and the record goes only once the runtime rolled back to has passed its health check. Before an update writes its first record, the previous update's `committed` record moves to the stash `run/<profile>/update.previous.json`; it moves back when the update ends without committing and goes when the update commits. One update, prepare or rollback runs at a time (`UPDATE_IN_PROGRESS`).

- **`update.prepare`** runs the store's `checking`, `installing` and `reporting` phases and returns a `reportId` and the report, kept for 600 seconds (`REPORT_EXPIRED` after that or once applied).
- **`update.apply`** runs `snapshot`, then `waiting`: from its start, the Host's chat gate refuses new turns with `UPDATE_PENDING`. `drain` waits for running chats to reach zero for at most `drainTimeoutS` (`DRAIN_TIMEOUT`), `abort-if-busy` ends `aborted` with `CHATS_RUNNING` when a chat runs, and `cancel` cancels running turns and jobs and waits for them to end. `update.cancel` ends an update that has not begun `switching`, with `current` unchanged.
- **`switching`** runs only while the gate reports no running chat and still refuses new turns. `SessionDataCopies.confirmSoleUser` checks again that no other process uses the chat data, which `plan` checked before the record existed; another process refuses the update with `CHATS_RUNNING`, nothing changed and the record removed. The home process then stops its Host and its supervisor, writes the session-data copy when `dataCopy` asks for it (checked to fit before `snapshot`, `DATA_COPY_NO_SPACE` otherwise), the store writes `previous` and then `current`, the record's `targetStarted` is written, and the successor starts ([the handover](#the-handover)).
- **`health-check`**: the successor answers `ready` or `failed` within 120 seconds. On `ready` the update ends `committed`. On `failed`, an exit or silence, the successor is stopped with every process of its process group, such as the composed tree's `delorun` it handed off to, and `SessionDataCopies.rollback` applies C3's table with both pointers restored; this process boots its Host on the old runtime again and the update ends `rolled-back` with `HEALTH_CHECK_FAILED`. When the table refuses, nothing is restored, the record gains `refused`, the update ends `failed` with `ROLLBACK_NEEDS_DATA_COPY`, and the process stops once the final line is sent. When a step fails after the rollback began, the update ends `failed`, the record stays `rolling-back`, and the process stops without running its Host again.
- **`rollback`** reads the update record, needs a `committed` update to the running version (`NO_UPDATE_RECORD`), waits for running chats, stops the Host and applies C3's table through `SessionDataCopies.rollback`; it then starts the version rolled back to as a successor, which removes the record once its health check passed, or with `profileOnly` runs this Host again and removes the record. A refusal (`ROLLBACK_NEEDS_DATA_COPY`, `ROLLBACK_TARGET_UNUSABLE`) leaves everything as it was and the Host runs again. A failure after the first step, or a successor that fails its health check, ends the rollback `failed`: the Host does not run again, the process stops, and the next start completes the rollback. The home log records each phase it announces as `rollback phase` and a successor that took over as `rollback committed`, as it records an update's phases as `update phase` and its commit as `update committed`.

## The handover

The predecessor starts the successor from the target's runtime with the store's command and a pipe inherited as file descriptor 3, in its own process group so a signal to the requester's terminal does not reach it, and with its own environment less the variables that load code into a Node, its loader or OpenSSL (`DROPPED_LAUNCH_ENV`, which a `.env` file may have set after the launcher dropped them) and less `DELORUN_START_CHECK`, which describes its own start (`successorEnvironment`), and writes one handover line: the home, the profile, both versions, the start id it assigns to the successor and the plugins the report named as disabled. No token passes. `HomeProcess.takeOver` boots the successor's Host in `standby` and runs its C3 health check against the handover line's expectations: the plugins and rows the report named, the bundle list it predicted, the rows the predecessor's Host could not load and every row it had at boot, read before that Host stopped. It answers `ready` or `failed`. On `ready` the predecessor rewrites the lock atomically with the successor's process id and start id (`HomeLock.handOver`), sends the requester the final `committed` line, closes its channel, removes its token file and writes `commit`; the successor then adopts the lock, writes a new start token, listens, launches its supervisor, enters `running` and settles the record: an update's record is marked `committed`, only its copy is kept (`SessionDataCopies.commit`) and the stash goes; a rollback's record goes and the stashed record returns. A successor whose predecessor dies before `commit` takes over only when the lock already names it.

## Interrupted updates

A requester that disconnects never changes a running update. Before step 3, the start runs `HomeProcessOptions.preStart`, the CLI's ordered pre-start steps, which complete an interrupted restore of a copy before any Host boots. Without the runtime store (`options.updates` is `undefined`), step 3 keeps a stash and a `committed` record and fails the start with `NO_RUNTIME_STORE`, leaving the record and booting no Host, for any other record. With the store, step 3 settles the record a killed home process left, as C19's "Interrupted updates" lists: a stash without a record moves back; a `refused` record fails the start with `ROLLBACK_NEEDS_DATA_COPY`; a `committed` record stays while `current` names its target (a stash beside it goes) and goes once `current` names its source; a phase before `switching`, or `current` still naming `from`, means nothing switched, so the update's copy is discarded, the record is removed and the stash returns. With `switching` or `health-check` and `current` naming `to`, which this process runs, the start records `targetStarted` and its own Host boot is the health check of `to`, H1 to H5 against the record's `health`; when it fails, the start stops its Host and closes its other parts, applies C3's table while it still holds the lock with both pointers restored from the record (`current` to `from`, and `previous` to the record's `previous`, or removes it when the record has none), releases the lock, starts a home process from `from` with the store's command and fails with `HEALTH_CHECK_FAILED`; the record stays `rolling-back` until that start's Host boots. When the table refuses, the record gains `refused`. A `rolling-back` record with `current` naming `to` is completed through the table before any Host boots, and the start fails and starts again on `from`; with `current` naming `from`, the start's Host boot is its check and the record then goes.

## Stopping

`stop` with `drain` refuses new turns and waits for running chats for at most 1,800 seconds; `cancel` cancels them first. A stop sent while another waits joins it and returns the same final line, and a joining `cancel` cancels the running chats first, so `delorun stop --now` ends a draining stop. The final line is sent before the process closes the Host, removes the token file, closes the channel, stops the supervisor and releases the lock, in that order. An accepted stop always answers and ends the process: a failed cancellation is logged and the stop goes on, and a status that cannot be read is left out of the final line. A stop while an update or rollback runs is refused with `UPDATE_IN_PROGRESS`. `HomeProcess.shutdown` runs the same order at once, for a termination signal; a Host that fails to close is logged, and the later steps still run.

## The supervisor

`delorun start` passes no `SupervisorSetup`, and no setup step writes one, so no shipped command launches the supervisor and no Docker workspace runs. When a caller passes one, `launchSupervisor` spawns `@delorun/supervisor`'s entry module with the command in `SupervisorSetup` and writes one launch line to the pipe on file descriptor 3 with this start's home, profile, start id and token, the verified manifest's images and the supervisor's timing ([the supervisor's launch](../supervisor/README.md#launching-the-supervisor)). The token never appears in its command line or environment. Ending the pipe stops the supervisor; the next start launches a new one with the new token, which refuses the previous start's.

## The operational log

`openHomeLog` opens the `home-<profile>` surface with a redactor; every record carries the start id. The start token is registered with the redactor before the channel listens, and `captureHomeOutput` captures the process's standard output and standard error into the same log, passing them through to a terminal in `delorun start --foreground`. A record names a request's `op` and outcome, never its body. `openedHomeLog()` returns the log this process opened, with its profile; `delorun`'s last-resort report writes a fatal failure's full detail there and redacts its terminal refusal with the log's redactor. C20's denial suite runs over this surface through `tests/log-driver.ts`.

## Not implemented

- The CLI's Host holds no scheduled delivery: a delivery that falls due while the gate is held is recorded as delivered and its turn is refused with `UPDATE_PENDING`. Work that began before the Host reported it is not counted.
- Step 8's confinement probes and their results, and `delorun verify`'s report of a dialect that cannot enforce C1's rules. The home process wraps no confined command itself; the probes, when they land, retry once a Landlock wrap refused with exit code 125 because an entry on the path to the home changed between the wrap and the launch, before reporting it.
- A supervisor launched by `delorun start`, and the setup step that writes the supervisor's roots file.
- The retry of an `unchecked` release-log check while the home process runs ([C18](../../docs/contracts/c18-release-log.md)).
- Start at login (`--at-login`) and `delorun status --follow`.
- The Windows named pipe with C1's DACL: the channel listens only on a Unix socket.

## Tests

`node_modules/.bin/vitest run --config delorun/vitest.config.ts delorun/packages/home-process` runs the specs: one home process per profile, the token on each start and the refusal of a previous start's, the closed schema and the limits, the update that waits for a running chat, `abort-if-busy` and `update.cancel`, a requester killed in `waiting` and in `health-check`, the rollback after a failed health check, interrupted updates, the desktop app's independence, the Host's way to the channel, the supervisor launch and the drain timeout on a fake clock. The confinement specs run each sandbox dialect the host provides through upstream's sandbox provider, configured as `delorun` configures the CLI profile's (the home protected with C1's read exemptions, the channel's socket denied), and skip Landlock, with the reason, where its launcher is not usable; one spec applies C1's bwrap mechanism as the contract states it to show that the socket and the token file lie where it hides them. `delorun/apps/cli`'s real-runner spec runs the same denial under a started CLI profile.
