# @delorun/changes

English | [中文](README.zh.md)

## Summary

A person's harness is the signed release plus the changes they made, each recorded; with protection on, only those they approved at their computer. This package keeps the approved copy of every plugin the profile links from a folder, computes what a folder changed against that copy, and makes the profile load the approved copy, never the folder. With protection off, the default, it makes the folder's content the approved copy at each start and each save while Delorun runs, and logs it as a change decided `unreviewed`. It also keeps the person's changes to the harness itself: their writable copy of an installed release, the files they approved, and the composed tree a start runs instead of the signed installation, which it never writes. The contract is [C21](../../docs/contracts/c21-changes.md).

## Use this package

```text
import { enforceApprovedContent, pluginChange, startNotice } from '@delorun/changes'

const changes = await enforceApprovedContent({ home, profile, profileDir })
output(startNotice(changes))
```

`delorun start` and `delorun headless` call `enforceApprovedContent` through `delorun/apps/cli/src/changes/start.ts` in their pre-start step `changes`, before upstream prepares the profile. `enforceApprovedContent` ends by checking the links and active directories (`checkLoadedContent`), refusing with `LOAD_REFUSED` when one is not what Changes keeps, and by collecting the store (`collectStore`, [C21](../../docs/contracts/c21-changes.md#collecting-the-store)). `prepareReload` is the same check before every recomposition of a running Host, which `@delorun/plugin-changes` provides to upstream's hot reload as `profileReconcileCheck` and `delorun plugin` runs after upstream's operation: it moves links to folders to their active directories where the profile write lock allows and refuses anything else that differs. `checkChangesInvariants` adds that every approved version reads back from the store, for `delorun verify` and `delorun doctor`, and the composition's approved plugin content step refuses a start when it returns any invariant that does not hold. `changesStatus` gives what `delorun verify` and `delorun doctor` report and writes nothing; `writeBootRecord` and `readBootRecord` keep `run/<profile>/changes-boot.json`, which plugins under Changes loaded at the last start.

## Where the files are

Everything is under `changes/` in the Delorun home, which confined commands can neither read nor write (contract C1). `store/objects/` holds file contents by SHA-256 and `store/versions/` the file list of each content version, named by the SHA-256 of its entries. `profiles/<profile>/active/<plugin>/` is the directory the profile's `link:` dependency names; `active.json` says what each holds, `log.json` is the change log and `work-session.json` the work session. A plugin's load copy is removed when the plugin is: `delorun plugin remove` forgets `active/<plugin>` and the `active.json` entry for it, so a plugin a person installs, tries and removes leaves nothing to load again, while the log and the store keep what undoing a change made while it was installed needs. `protection.json` holds the protection setting, `notices.json` the protection changes made from a paired device and `migration.json` the profiles the home held at the first start under Changes. The profile's `package.json` records each approved plugin's folder and version under `delorun.changes`, so every profile history version holds it. Anything a plugin writes into its own active directory, such as a cached token, is readable by sandboxed commands, so a plugin keeps its secrets in the credentials store.

## How the profile loads approved content

pnpm resets the `node_modules` link of a `link:` dependency on every operation, so the start moves the recorded dependency itself: `package.json`, the lockfile's importer entry and the link name the active directory. The active directory holds the approved version, or nothing for a plugin with none, so upstream skips it, and in a work session the folder's content. With protection off a start first makes the folder's content the approved version ([Loading without review](#loading-without-review)), unless the person declined exactly that content. Files that differ from what the directory should hold are replaced in place, so upstream's hot reload replaces exactly the changed modules.

The first start under Changes of each profile the home held when Changes began approves every linked plugin as it is (`migratesAtUpgrade`), and starts name those plugins until a terminal showed them (`markShownAtUpgrade`). A plugin linked later, or by a profile created later, waits for review with protection on and loads without review with protection off. Links into the runtime store and to the directory the running installation carries for that package are the harness, not plugins, and are left alone: a source checkout runs the whole harness from the checkout. Inside a plugin's folder, a link whose real path, with every link and `..` resolved, lies in the active runtime's installed packages (`runtimes/<current>/app/node_modules/`) stays a link to that signed package in the copy, as a plugin pack links the packages the release carries; no runtime bytes are copied. The version records the package's path below that folder, so an update or a rollback leaves the approved version as it is, and the next start re-points the copy's link to the release that runs. A plugin's links to sibling workspace packages (a directory with a `package.json` linked at `node_modules/<name>`) and to installed packages (below a `node_modules` directory) are included in its content by hash, an installed package with the dependencies installed beside it, within 50,000 files, links and directories and 512 MiB, each file read no further than the size counted. Any other link out of the folder, and any other link into the Delorun home (another runtime version's included), `/proc`, `/sys` or `/dev`, is left out of the copy. A link whose folder is missing is moved to its empty active directory like any other, so a folder created there later waits for review. A folder over the limits, or one that cannot be read, never stops a start: the approved content keeps running and the start names the plugin, except that with protection off a folder over the limits only with its installed packages loads them from where they are installed.

## Pending changes and the risk summary

`pluginChange` stores the folder's content as a version and compares it with the approved one: the files added, changed and removed, a unified diff bounded at 256 KiB with files larger than 1 MiB and binary files named only, and a risk summary. The change id is derived from the plugin, its folder and both versions, so applying an id applies exactly the content that was shown. `reviewChange(input, checks)` runs the nine built-in checks, `not-shown` among them, which names each new file whose lines the diff leaves out: a binary file Node loads, a file above or past the diff's limits, and a dependency's files inside the folder; it is the one place a later extension point adds registered checks. The summary is a help to the reader and not a protection: a plugin's code can do anything Delorun can.

## Records and who writes them

Every record is a 0600 file whose reader refuses an unknown field, value or mode with `RECORD_UNREADABLE`. `readProtection` answers `on` or `off`, `off` for a home without `protection.json`. `setProtection` accepts a proof from any of three attest functions, so turning protection off rests on the terminal's proof, on the studio's, or on a paired device's, with a grant for the request. `attestTerminal` requires standard input and output to be terminals. `attestStudio` issues the studio's proof for a request at the computer (the loopback listener under a loopback `Host`, with the studio's credential, a same-origin request, not a remote session). `attestDevice` issues a studio proof for a paired device that holds a grant for the request, never the approval grace; it names the device. Only `@delorun/plugin-changes`' routes call `attestStudio` and `attestDevice`, and they call `attestDevice` only where the control's class lets a device act ([C21](../../docs/contracts/c21-changes.md#who-may-do-what-from-where)). The change log records both studio proofs as `decidedFrom: "studio"`, and a device's decision names the device in `decidedOn`, which `withoutDecision` clears before any later decision. A proof is refused unless an attest function issued it. The proof does not tell a person from a model, whose terminal tool has a real pseudo-terminal; a confined model is kept out by the sandbox, which lets it write nothing under the home. `pluginSlug` refuses a name that is not a package name before any path is built from it. `noteLoaded` and `noteFailed` record what the Host loaded or failed to load in the open work session and need no proof. `writeWorkFailure` and `readWorkFailure` keep `run/<profile>/changes-work.json`, the last failed reload in a work session.

`src/notices.ts` keeps `changes/notices.json`, schema `delorun.changes-notices/1`: at most 20 protection changes made from a paired device, oldest first, so the computer can tell the person. `readNotices` lists them, `addProtectionNotice` is called by `changeProtection`, and `dismissNotice` takes a terminal or computer proof and refuses a proof that names a device, so a phone cannot dismiss what it changed. The record is separate from the change log, which keeps its schema.

## What a person does with a change

`src/actions.ts` holds the operations `delorun changes` and the studio's Changes routes call. `listChanges` computes what each plugin's folder holds against its approved content, hides a change discarded for that content, and returns the changes a failed start left out (`leftOut`) and the other logged changes newest first, the plugins whose folder is gone, the protection setting and any work session; `showChange` returns one change or its log entry. `recordedChanges` (`src/state.ts`) gives the studio's `state` route the plugins under Changes with their folders and the agent's requests waiting for review from the approved record and the change log alone, writing nothing and reading no folder. `applyChange`, `discardChange`, `undoChange`, `turnOff`, `turnOn` and `changeProtection` take an `AtComputer` proof and refuse one the attest functions did not issue before they read anything; `changeProtection` logs turning protection off as an applied `guard-weakening` change decided where the proof says, and, for a proof that names a device, adds a protection notice. `applyChange` approves exactly the version the id names and refuses with `CHANGED_SINCE_REVIEW` when the folder holds anything else; `turnOff` and `turnOn` edit only `dsh.profile.bundles` and refuse Delorun's own bundle.

`src/install-actions.ts` (also the entry `@delorun/changes/install`) holds the agent's plugin requests ([C21](../../docs/contracts/c21-changes.md#the-agent-and-plugins)). `recordPluginRequest`, which `@delorun/plugin-changes` calls when the agent's `plugin_manager` would install, update or remove a plugin, writes one pending `plugin-install`, `plugin-update` or `plugin-remove` entry with `subject.spec` and nothing else. `applyInstallChange` takes an `AtComputer` proof, runs the injected upstream plugin operation (`add <spec>` or `remove <name>`, given the folder a spec names so the operation checks its package) under the profile write lock, records one history version and reloads the Host; after a failed or refused operation it puts `package.json` and `pnpm-lock.yaml` back, records the build scripts pnpm held back with upstream's `recordPendingBuilds`, and leaves the request pending with the failure; a spec that names a folder is linked to the plugin's active directory, empty until the person applies the folder's content, which it records as a pending folder install. `listChanges` returns the waiting requests as `requests`; `applyChange` refuses them and `undoChange` refuses an applied one.

Each runs under upstream's profile write lock and records one profile history version naming the change id; discarding and the protection setting record none. An action that changes what the Host runs then calls the injected `ReloadHost`, which `delorun changes` implements with the update channel's `changes.reload` and which answers `undefined` when Delorun is not running; the home process's answer to `changes.reload` and the studio's routes both reload with `reloadProfile(hmr)` ([reload](src/reload.ts)), upstream's hot reload in the Host's own process. When the reload fails, the action goes back: the approved record, the active directory and `active.json`, or the bundle list, return to what they held, a second history version records it, the change is pending again with `lastFailure`, and the Host is reloaded once more.

## Loading without review

`src/agent-actions.ts` holds the agent's `plugin_manager` actions that ran with protection off ([C21](../../docs/contracts/c21-changes.md#the-agents-plugin-actions-with-protection-off)). Their entries live in `agent-log.json` beside `log.json` (`readAgentLog` in `src/records.ts`, schema `delorun.changes-agent-log/1`), a file a release without it never reads, so `log.json` stays as that release reads it and going back to it still starts the profile; a start reads `log.json` only, and `list`, `show`, `undo` and the studio's state read both. `planAgentAction(ctx, call)` reads, before the tool runs, what the call will be recorded as (an install, update or removal with its spec, or a `plugin-setting-change`), the profile's latest history version and a digest of the files plugin management writes, and checks that both logs can be read. `beginAgentAction` writes the entry before the tool runs, saying Delorun has not seen how it ended, so nothing the action loads goes unrecorded. `finishAgentAction` completes it from the history versions written since: `historyVersion` and `historyBefore` (the version just before it, so a person's own edit made by hand stays), no version when two chats acted at once, removal when nothing changed, and `unsaved` when files changed but the history saved no version. `isAgentAction(entry)` names such an entry. `undoAgentAction(ctx, id, presence, { reload, run })`, which `undoChange` calls for an id the agent-action log holds when given the plugin operation, restores only the files plugin management writes (`scope: 'manager'` of `planRestore` and `applyRestore` in `@delorun/profile-safety`), keeps the plugins the safety record keeps disabled disabled, installs that dependency set through `run` (`install --ignore-scripts`, then `rebuild --pending`) under the profile write lock, records one history version and reloads, and goes back and leaves the entry applied with `lastFailure` when the install or reload fails. It refuses when those files are no longer as the action left them. A failed start leaves nothing out when the newest decision is such an entry.

`src/unreviewed.ts` holds what loads without review while protection is off ([C21](../../docs/contracts/c21-changes.md#loading-without-review)). Each writer reads the setting again under the profile write lock, or the harness lock, and writes nothing when it is on; none takes a proof of presence. `enforceApprovedContent` and `prepareReload` make a linked plugin's new folder content its approved content and log an applied `plugin-edit` or `plugin-install` decided `unreviewed` (`unreviewedEntry`), and `startNotice` prints `unreviewedWords` for each. `unreviewedFolders(ctx)` names the folders the home process watches, and `loadUnreviewed(ctx, plugin, reload)`, which only `delorun/apps/cli/src/changes/unreviewed-watch.ts` calls, approves and loads one folder's content in the running Host, reading the folder into the store before it takes the profile write lock and deciding under the lock with the records read again, recording one history version, and on a failed reload puts the approved record, the active directory and `active.json` back and leaves the change pending with `lastFailure`. `declinedByPerson(log, plugin, version)` holds back content whose newest decided content change was undone or discarded. `applyUnreviewedHarnessChanges(ctx)` in `src/harness.ts`, which only `delorun/apps/cli/src/changes/harness-start.ts` calls, applies every change waiting in the harness's writable copy before the signed start composes the tree, and reports a copy it cannot read instead of applying anything. `changesStatus` and `harnessStatus` mark what loaded without review (`unreviewed`) for `verify` and `doctor`.

## Work sessions

`startWork(ctx, plugin, proof, { reload, minutes })` opens a work session on an approved plugin for 1 to `WORK_SESSION_MAX_MINUTES` (480) minutes, records its end as `endsAt`, and loads its folder's content at once. `reviewWork(ctx, plugin)` stores the folder's content and returns it with its difference from the approved content the session started from, for `done` to show; `finishWork(ctx, plugin, proof, { reload, approve })` approves exactly the content `approve` names as one applied `plugin-edit` change and one history version `Work on <plugin>: <from> → <to>`, loading it first when the Host does not run it yet, and refuses with `CHANGED_SINCE_REVIEW` when the folder holds anything else. Both refuse a proof the attest functions did not issue. While the session lasts, `loadWorkSession(ctx, reload)` loads the folder's content when it is new to the session: it copies it into the active directory and reloads the Host, and when the reload fails it puts the content that last loaded back, reloads again, notes the failure and writes `changes-work.json`, leaving the session open; after `endsAt` it loads nothing, and a start that finds the session past `endsAt` ends it without the person before it loads anything. `workSessionFact(home, profile)` gives the open session, its end and its last failed reload for `delorun status` and the studio's badge.

The plugin keeps loading from its active directory, so the home process watches the folder itself (`delorun/apps/cli/src/changes/work-watch.ts`) instead of setting upstream's `hmr.root`, which would watch files that are not loaded. When Delorun stops, when a start finds a session a home process that did not stop left open, and at `endsAt`, `finishWorkWithoutPerson(ctx, why, reload?)` ends the session without the person and approves nothing: the approved content stays the version the session started from, the active directory holds it again, and the folder's content waits for review as the ordinary pending change. It needs no proof, so it is exported only from `@delorun/changes/stop`, which only the CLI's start module imports.

## When a start fails

`src/left-out.ts` leaves out the change that broke a start ([C21](../../docs/contracts/c21-changes.md#when-a-start-fails)). `newestLeavableChange(ctx)` names it: the newest decision that changed what runs, when it applied a person's `plugin-edit`, `plugin-install`, `plugin-update` or `plugin-on` to a plugin linked to its active directory that holds the change's content; otherwise nothing, so a second failure leaves nothing more out. `leaveOutNewestChange(ctx, failure)` writes only the change log under the profile write lock, marking the entry `left-out-at-start` with the failure; it takes no proof, and only `delorun/apps/cli/src/changes/retry.ts` calls it. From then on `enforceApprovedContent` makes the plugin's active directory hold the change's `from`, or nothing, with `active.json` kind `left-out`, and names it with `leftOutWords` in `startNotice`, until `applyChange` loads it again or `undoChange` undoes it. `listChanges` returns such changes as `leftOut`; `leftOutFacts(home, profile)` gives them to the studio and `changesStatus` to `delorun doctor`.

## Changes to the harness itself

`src/harness.ts` keeps the person's edits of an installed runtime's `app/` files ([C21](../../docs/contracts/c21-changes.md#harness-edits)). Every function takes a `HarnessContext`: the home, the running runtime version and `signed()`, the installation with the signed file list the runtime store's start check verified, read only when needed; every byte read from the installation is checked against that list. `createHarnessCopy` makes `changes/harness/<runtime>/copy/app/`, after `checkHarnessCopySize` refused a copy its scan could not read with `CONTENT_TOO_LARGE`; `harnessChanges` computes one pending `harness-edit` change per file of the copy that differs from what runs, and refuses a copy that is not a directory, passes the scan's limits or cannot be read with `HARNESS_COPY_UNREADABLE`; `showHarnessChange` stores both sides and reviews them; `applyHarnessChange`, `discardHarnessChange`, `undoHarnessChange` and `discardAllHarnessChanges` decide under `withHarnessLock`, each taking a proof of presence, and log in `changes/harness/log.json`; `applyHarnessChange` takes an optional `reviewedTo`, the full content version a review showed, and refuses another with `CHANGED_SINCE_REVIEW`. `ChangesHarnessHost` is the service the home process gives the Host (`changesHarness`) so the studio's routes decide against the signed file list the home process verified. `listHarness` gives `list` the waiting, left-out and logged changes. `src/harness-tree.ts` builds and checks the composed tree (`prepareComposedTree`, `checkComposedTree`), removes the trees and directories no start needs and no start chose within `TREE_RETENTION_GRACE_MS` (`retainHarness`), and reports a runtime's harness for `verify` and `doctor` without writing (`harnessStatus`). `newestLeavableChange(ctx, runtime)` and `leaveOutNewestChange(ctx, failure, runtime)` leave a harness change out when it is the newest decision across both logs; `leaveOutNewestHarnessChange(home, runtime, failure)` leaves out the runtime's newest harness change whatever the profile's log holds, for a composed tree whose `delorun` failed before its start ran, and `newestAppliedHarnessChange(home, runtime)` names the change the words after a second such failure offer to undo.

## Harness changes across an update

`src/harness-merge.ts` decides what an update does with each approved file of the harness ([C3](../../docs/contracts/c03-update-report.md#reasons)). `mergeHarnessFile({ base, mine, theirs })` merges the running release's signed file, the approved content and the target's signed file, each with its execute bit or `undefined` for no file: `same` when the target already holds the approved content, `carried` with the content the target runs when the target left the file as it was or the patch from the base to the approved text (jsdiff's `structuredPatch`) applies to the target's text with no fuzz and no line-ending conversion, and `conflict` with its reason otherwise. Both sides changing a file that is binary, not UTF-8 or larger than `DIFF_FILE_LIMIT` conflicts, and so do a file the target removes after the person changed it, a file the person removed after the target changed it, and a file both add with different content. `planHarnessCarry(home, record, readSigned)` reads each file's base and approved content from the store by the record's `signed` and `version`, asks `readSigned` for the target's verified file, and returns a `HarnessCarryPlan` with all three sides and the outcome of every file, in path order; it writes nothing. A version that is not a one-file version of its path is refused with `RECORD_UNREADABLE`. `mergedDiffs(plan)` gives each file that carries by merging (`carried` with carry `merged`) its unified diff from the target's file to the merged content, with `old mode` and `new mode` lines when the execute bit differs, bounded by `DIFF_FILE_LIMIT` per side and `DIFF_TOTAL_LIMIT` across the plan; a binary or too large side, and every diff once the total is passed, shows no lines and says why (`notShown`). The update report's `harness` items are built from the plan by `delorun/apps/cli/src/update/harness-items.ts`, over `runningHarnessRecord`, which leaves out a change a failed start left out. `carryHarness(request, switchRuntime)` is the update's one call right before its switch, under the harness lock throughout: it refuses with `HARNESS_CHANGES_PENDING` while a change waits for review in the running runtime's copy, removes whatever an earlier install left under `changes/harness/<to>/`, plans again against the target's verified files and passes the plan to the request's `confirm`, which compares it with what the person confirmed and throws to refuse before anything is written, then writes the target's record with each carried file (its `signed` the target's file) and one applied `harness-edit` log entry each with `decidedFrom: "update"`, writes the target's writable copy with `writeHarnessCopy` when the running runtime has one or a file conflicts, keeps the person's content of each conflicted file there as `<file>.mine` (`keepBeside`), and then runs the switch. A failure before the switch removes the target's directory; the running runtime's record, copy and log entries are never written.

## Plugin packs across an update

`src/update-baseline.ts` makes the release's own pack files the baseline across an update ([C21](../../docs/contracts/c21-changes.md#plugin-packs-across-an-update)). A pack's folder under `packs/` holds one release's signed files, so after an update the approved content, the previous release's files, and the folder differ by what the release replaced. `enforceApprovedContent` takes an optional `updateBaseline`, `{ from, to, packsFor }`, which only the first Host boot of an update's successor sets (`repointForSuccessor` in `delorun/apps/cli/src/changes/start.ts`, which an update's successor runs because it has no pre-start steps), for an update to a newer release. Each release's packs file is verified when the baseline is built, but `packsFor(name)` gives a pack's signed files (`openSignedPacks` of `@delorun/runtime-store`; no installed file is hashed, and `text(path)` reads one installed `package.json` or `pnpm-lock.yaml` only after its bytes match the signed digest) only when a waiting change touches that pack, once per pack. `repointForSuccessor` builds the baseline and runs Changes' start only when `baselineMayApply` finds an approved plugin linked from `packs/` that one of the releases lists (`lists(name)` reads the packs file alone), and gives that start and the re-pointing one `createScanMemo()`: an in-memory, per-boot memo of the digests the active copies' files gave, used only by the rewrite-or-not checks (`holdsVersion`, `holdContent`), dropped for what a boot writes, and never used by the load check (`holdsVersionUnder`) or `materialize`'s check after a write. The scan cache file keeps entries per scanned folder (schema `/2`), so scans of two plugins' folders do not replace each other's. `supersededByUpdate` judges only the entries that differ between the approved content and the folder: each entry the folder now holds must be a file with the digest and execute bit `to` signs, each approved entry the folder no longer holds as it is must be a file `from` signs, a file `to` signs must not be missing from the folder, an entry the approved content lacks must not be signed by `from` either, and a link or an unsigned entry among them leaves the change waiting; a `package.json` or `pnpm-lock.yaml` approved from a release up to `LAST_RELEASE_WITH_BUILD_PATHS` (0.1.0-preview.2.1, a security invariant; an update that leaves any later release matches byte for byte) also counts when it equals the text of an installed, signed one apart from the build's temporary folder names (`withoutBuildFolder`), which no other file is allowed. A start that passes both replaces the approved content with the folder's as one applied `plugin-edit` decided `update`, with one history version and `replacedByUpdate` in what the start reports; any other difference, including a person's edit mixed with release files, waits for review as before. A start without a baseline, a reload and a plugin outside `packs/` never replace anything, and neither does a rollback's successor, whose handover line names `purpose: rollback`. The successor applies it once per update: a boot after a failed health check never does. `followApprovedContent` is for a Host that boots again after a failed health check: the rollback restored the approved record but not `active.json`, so each active copy that loads approved content is set to the restored approved version before the boot, and the predecessor resumes with nothing advanced. A predecessor older than that step has none, so the successor puts back the approved-record and `active.json` entries the baseline changed before it reports a failed health check (`revertDecisions`, run through the Host runner's `abandon`), and keeps any entry changed since, filling each active directory of an entry it puts back with that entry's content again (or with nothing for an entry the start added), so that predecessor's resume finds the directories and `active.json` agreeing.

## Setup export and import

`@delorun/changes/setup-transfer` ([`src/setup-transfer/`](src/setup-transfer/index.ts)) moves a profile's setup between computers. `collectSetup` reads the plugins the person added (an exact version and the lockfile's integrity, or the files of the approved copy) and the patch entries the policy ([`policy.ts`](src/setup-transfer/policy.ts)) carries: the default model and the model providers, the studio's look, and the rows of the carried plugins. The policy never carries a package of the `@delorun/` or `@deepseek-ai/` scope, an entry that belongs to one computer (sandbox, permissions, network, devices, reach, credentials), a `!!js` expression or an endpoint that is not https, and it stops an export that would carry a credential. `planSetupImport` lists what an import replaces under the person's choices: the model entries always, the other settings unless turned off (those the archive lacks go back to their defaults), the plugins the archive lists, and the plugins it does not list only when the person chose to remove them. An export can leave the settings out, carry chosen plugins, name a person's own plugins without their code, and add a note. `applySetupImport` saves the version "Before importing a setup", then records and applies each removal and installation as an agent's plugin request, so upstream's compatibility checks, the install check, the held build scripts and the review of local code are the ones a hand install meets; a local plugin's files are written to a new folder under `archive/setup-plugins/<profile>/` and linked from it, which leaves its content waiting for review. A registry package whose lockfile checksum is not the archive's, or cannot be checked, stops the import. The settings are written last as one history version. [Contract C8](../../docs/contracts/c08-archive-and-trash.md#the-setup-archive) states the archive; `delorun setup export` and `delorun setup import` ([`@delorun/cli`](../../apps/cli/README.md)) reach it.

## Not covered

- Plugin code runs with the harness's full authority; nothing here confines it.
- A changed file of the signed installation is refused by the runtime store's start check in both protection settings; the person's edits run only from the composed tree, once applied.
- With protection off, nothing reviews a change before it loads: whoever writes a linked plugin's folder, or the harness's writable copy, changes what runs; this package records it and the person undoes it.

## Development

`node_modules/.bin/vitest run --config delorun/vitest.config.ts delorun/packages/changes` runs the specs; `node_modules/.bin/tsc --noEmit -p delorun/packages/changes/tsconfig.json` typechecks.
