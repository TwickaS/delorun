# @delorun/plugin-changes

[English](README.md) | 中文

> 英文页面是当前版本；本页可能落后于它。

## 摘要

只要「变更」的保护处于开启状态，`@delorun/plugin-changes` 就会阻止 agent 更改 harness 运行哪些插件。在其 C16 开关 `plugin_changes_pending` 开启且保护开启时，动作为 `install_bundle` 或 `remove_bundle` 的 `plugin_manager` 调用不会运行：`tools/pre-execute` 监听器把它作为待处理变更记录到 profile 的变更日志中（[C21](../../docs/contracts/c21-changes.zh.md#the-agent-and-plugins)），并以模型可读的结果拒绝该调用：`Recorded as a change waiting for the person's review at their computer: delorun changes show <id>. Nothing was installed.` 对这些动作，该工具永远不会到达它自己的完全访问审批，本人在自己的电脑上通过 `delorun changes` 或在 studio 中应用或丢弃该变更。agent 其他会更改运行内容的 `plugin_manager` 动作（`set_bundle`、`set_plugin`、`configure`、`set_version_exemption`、`undo`、`restore`）以 `PLUGIN_CHANGE_AT_COMPUTER` 拒绝，且不记录任何内容。保护关闭（默认）时，每个这样的调用都继续交给上游，仅由上游的完全访问审批决定。无论开关如何，该插件都提供上游热重载的 `profileReconcileCheck`，在任何内容停止之前检查 profile 的每次重新组合（[C21](../../docs/contracts/c21-changes.zh.md#reloads-and-restores)）。无论开关如何，它还在 `/delorun/changes/` 下注册 studio 的「变更」路由，供上游的启动页读取，用于其恢复屏幕（[C21](../../docs/contracts/c21-changes.zh.md#routes-and-the-recovery-screen)），其浏览器一半添加设置中的「变更」部分和工作会话徽章，它们通过同样的路由执行操作（[C21](../../docs/contracts/c21-changes.zh.md#the-studios-changes-section)）。开关关闭（默认值，也是一致性值）时，插件不注册监听器或守卫，工具的运行和询问方式与上游相同。

## 约定

- **保护设置。** 对每个动作会更改运行内容的 `plugin_manager` 调用，监听器都读取该 profile 的 Delorun home 的 `readProtection`，所以 `delorun changes protection on|off` 在运行中的 Host 的下一次调用时生效。设为默认的 `off` 时，对每个这样的调用它都调用 `next()`，与开关关闭时完全相同，因此由上游的完全访问审批决定，Creator 模式也可以在 chat 中开启 bundle。已运行的、来自文件夹的安装（`link:<folder>`）在它引起的重新组合时纳入「变更」管理：重新加载之前的检查把插件链接到其活动目录，并把该文件夹的内容记录为已应用的 `plugin-install`，决定为 `unreviewed`。注册表安装或移除不在「变更」管理之下；上游记录的 profile 历史就是它的记录，插件对此不记录任何内容。无法读取的保护记录会拦下调用：以 `PLUGIN_CHANGE_UNRECORDED` 拒绝，并说明无法读取该设置。以下内容均在保护为 `on` 时成立。
- **被拦下的内容。** `install_bundle` 记录为 `plugin-install`；当规格是 profile 已有插件的某个注册表版本时，记录为 `plugin-update`；该工具不提供更新动作，所以 agent 以此方式请求更新。`remove_bundle` 记录为 `plugin-remove`。其他所有动作和工具继续交给下一个监听器。
- **记录的内容。** `@delorun/changes/install` 的 `recordPluginRequest` 在 profile 写锁之下，向 Host 所运行的 profile（`ctx.profileContext`）写入一个带 `subject.spec` 的待处理条目；当规格指明插件时，还带 `subject.plugin`。它不写入清单、锁文件、`node_modules` 或批准记录。仍在等待的请求保留其 id；对已决定请求的重复是一个新变更。
- **模型读到的内容。** 已记录的请求以错误码 `PLUGIN_CHANGE_PENDING` 和该变更的 id 被拒绝；更新时写 `Nothing was installed or updated.`，移除时写 `Nothing was removed.` 没有目标的调用、pnpm 不会接受的规格、移除并非依赖项的名称、没有 profile 的 Host，或无法写入的日志，都以 `PLUGIN_CHANGE_UNRECORDED` 及原因被拒绝，且不记录任何内容。拒绝就是该工具调用的已记录结果，所以不增加任何 session 事件。
- **由本人完成的内容。** `set_bundle`、`set_plugin`、`configure`、`set_version_exemption`、`undo` 和 `restore` 不会运行：模型读到的是该变更由本人在自己的电脑上、在 studio 中或用 `delorun plugin` 完成，错误码为 `PLUGIN_CHANGE_AT_COMPUTER`，且不记录任何内容。
- **守卫。** 若某个 `pre-execute` 监听器不调用 `next()` 就放行了这样的调用，会跳过本插件的监听器。本插件的工具守卫在所有监听器之后运行且无法被覆盖，在两种保护设置下，它都会拒绝其监听器未处理的每个这样的调用；保护关闭时监听器放行的调用算作已处理。
- **重新加载之前的检查。** `profileReconcileCheck.check(profile)` 为 Host 所运行的 profile 运行 `@delorun/changes` 的 `prepareReload`：在 profile 写锁允许时，指向某个文件夹的 `link:` 依赖会被移动到插件的活动目录；与「变更」所保存内容不同的链接或活动目录，会以 `LOAD_REFUSED` 拒绝这次重新组合，所以不会停止任何内容，也不会加载任何内容。当链接指向运行时存储，或指向 Host 已用来加载该包的目录（`loadedLinks`）时，它算作 harness 自己的链接。
- **The studio's routes.** Once the web server and Connection are present, [`src/routes.ts`](src/routes.ts) registers `GET /delorun/changes/state` and `show`, and `POST` `apply`, `discard`, `undo`, `off`, `on`, `work`, `done`, `safe-mode`, `exit-safe-mode`, `create`, `request` and `reveal`, the harness routes `harness-apply`, `harness-undo`, `harness-discard` and `harness-copy`, `restart` and `restart-cancel` ([`src/restart-route.ts`](src/restart-route.ts), the level of `harness-apply`), `protection-on`, `protection-off` and `notice-seen`, and the plugin names their prefix to the boot page through the index global `dshRecoveryRoutes`. Every request is admitted by Connection first; any admitted session reads, and a `POST` is decided before its body is read, in this order. First the site: a browser request another site sent is answered `403 CROSS_SITE` (at the computer, by `Sec-Fetch-Site` or an `Origin` that is not the request's loopback origin; from a paired device, by an `Origin` that is not `https://<Host>` or a foreign `Sec-Fetch-Site`). Then the control's level ([`src/access.ts`](src/access.ts)): the person at the computer (a loopback `Host`, the credential, and a session Connection's `isReachPeer` does not name; a Connection without `isReachPeer` gets no route) may use every control, attested with `attestStudio`; a paired device uses a control under its class in `AUTH_CLASSES` (`free`: protection on, update check, cancel and dismiss; `face`: every other control except `notice-seen`, with a one-action grant for exactly the request, read through `gateByClass` and never the approval grace; `computer`: `notice-seen`), attested with `attestDevice`. Anything else is answered `403 LOOPBACK_REQUIRED`, or `403 ELEVATION_REQUIRED` for a device without a grant. Both proofs are logged as decided in the studio ([C21](../../docs/contracts/c21-changes.zh.md#who-may-do-what-from-where), [C14](../../docs/contracts/c14-oidc-passkeys.zh.md#face-id-unlock)). `apply` and `done` answer `409 CONFIRM_RISK` until the person confirms a flagged change again; `apply` of an agent's plugin request always answers `409 CONFIRM_RISK` first, naming its spec (kinds `dependency-or-build` and, for an install or update, `not-shown` with the spec, since nothing of what pnpm installs is shown), and once confirmed runs `applyInstallChange` with the Host's plugin operation, `@delorun/changes/plugin-operation`'s `upstreamPluginOperation`, the operation `delorun changes apply` runs, from the profile launcher's directory with its installation anchor and pnpm and its output in the Host's log, answering the applied entry, how the Host reloaded and, for a folder spec, the change that holds the folder's content; `apply`, `discard` and `undo` refuse a change to Delorun itself from the harness's log with `409 HARNESS_ROUTE`, because the harness routes decide it against the running runtime's signed file list, which the home process gives the Host as `changesHarness` (`409 HARNESS_UNAVAILABLE` on a Host without it, such as a source checkout); `harness-apply` takes the full `to` version that `show?pending` listed and answers `409 CHANGED_SINCE_REVIEW` for another; and an action reloads the Host in its own process with `reloadProfile`. `protection-off` answers `409 CONFIRM_PROTECTION` with `willLoad {plugins, harnessFiles}` until the request repeats with `confirmed: true`; that second ask stops a misclick and is no defence against someone at the computer. A protection change from a paired device writes a notice that `state.notices` shows the computer and `notice-seen` dismisses, at the computer only. `state` also names `access` (the requester and what each control needs: nothing, an unlock, Face ID or the computer), `harnessAvailable`, `unreviewedSinceOff` and `restart`. A decided change to one of the studio's built client assets is served at once through exact web-server routes under Connection's fence, and any other waits for the Restart, which the home process's `changesRestart` service runs ([`src/live-apply.ts`](src/live-apply.ts), [C21](../../docs/contracts/c21-changes.zh.md#live-changes-and-restart)). `state` reads the records only (`recordedChanges` of `@delorun/changes` and the harness's log), writing nothing and reading no plugin's folder; `show?id=` of a change to Delorun itself reviews its two versions from the store; `show?pending` reads the folders and stores their content. An answer never carries the Delorun home's path: a refusal whose words name it answers its code and a fixed sentence and logs the words, and a recorded failure names the home as `<Delorun home>`.
- **线路格式。** [`src/wire.ts`](src/wire.ts) 存放路由的路径、拒绝码以及每个路由应答的 JSON 字段，且不导入任何内容；路由构造这些字段，浏览器一半读取它们，所以 Host 一旦不再发送某个字段，就会使 Host 的类型检查失败。启动时被遗漏的条目，携带该次启动记录的失败，作为 `leftOut`。
- **Face ID on a paired device.** When the state says a control needs `face`, the controller asks `ctx.delorunFaceGrant` (shared as the source-only type [`src/client/face-grant.ts`](src/client/face-grant.ts), exported as `./face-grant`; `@delorun/bundle-local` provides it) for a grant covering exactly that call, action `changes/<control>`, and sends the call with the grant's id in `Delorun-Grant`. A control with two calls, such as the update's Prepare and Apply, asks once per call. A cancelled sheet sends nothing. Without the service the call is sent plain and the home refuses it. The button's hover text for such a control is "Confirm with Face ID first".
- **setup 路由。** `POST /delorun/changes/setup-export`、`setup-inspect` 与 `setup-apply`（[`src/setup-actions.ts`](src/setup-actions.ts)）通过 `@delorun/changes/setup-transfer` 把 profile 的 setup 写成已签名的文件、检查文件并规划其导入，以及应用已规划的导入（[合约 C21](../../docs/contracts/c21-changes.zh.md)、[C8](../../docs/contracts/c08-archive-and-trash.zh.md#the-setup-archive)）。它们只回答在电脑上发出的请求，到达与站点检查与动作相同，且发生在读取请求体之前。被检查的文件以随机的一次性令牌保存在内存中十分钟；`setup-apply` 接收令牌，而不是文件。超过 32 MiB 的文件请用命令迁移。
- **没有其他决定入口。** 除路由之外，插件不导入任何用于应用、丢弃或撤销变更、打开或结束工作会话或更改保护设置的函数；`delorun/packages/changes/tests/reach.spec.ts` 约束它这一点，并约束路由使用 `attestStudio`、`attestDevice`、`changeProtection` 和 harness 操作，而不使用 `attestTerminal`、`setProtection` 或 `discardAllHarnessChanges`。这些路由用 `applyInstallChange` 和 studio 的证明来应用 agent 的插件请求。

## studio 的「变更」部分

浏览器一半 [`src/client/index.ts`](src/client/index.ts)（`@delorun/plugin-changes/client`）随 `delorun-plugin-changes` 行加载，并注册：

- the `settings.section` `delorun-changes` ([`ChangesSection.tsx`](src/client/ChangesSection.tsx)): the work session with Done, or the plugins of the last start with Start working; the changes a start left out with Apply again and Undo; the changes waiting for review, each opened by Review ([`ChangeDetail.tsx`](src/client/ChangeDetail.tsx)) with Apply and Discard; the agent's plugin requests with the terminal command, Apply and Discard; the recent changes with Undo; the changes to Delorun itself ([`SelfGroup.tsx`](src/client/SelfGroup.tsx)): Make my copy, the changes waiting in the copy with Review (Apply sends the `to` version the review read) and Discard, and the decided changes with Review and Undo, each with when it takes effect and, for a paired device's decision, its name, and the terminal command `delorun changes edit-harness --discard` as the only one left; and the protection switch ([`ProtectionGroup.tsx`](src/client/ProtectionGroup.tsx)), which turns protection on after one confirmation and off after the one confirmation that names what would load without review from the route's `409 CONFIRM_PROTECTION`, with the notices of a paired device's protection change and Dismiss at the computer; with protection off, a note under the introduction says that changes load without review and a linked plugin reloads live each time it is saved. A change the checks flagged asks a second confirmation, opened by the route's `409 CONFIRM_RISK` and naming the kinds and the files the diff does not show, before Apply or Done sends `confirmedRisk`; Apply of an agent's request asks a first confirmation, then the second one the route asks for every request, which names the request and its spec. Every control reads `state.access.may[control]` ([`AccessNote.tsx`](src/client/AccessNote.tsx) shows who acts on a device): a control that needs the computer is disabled with "Needs your computer"; one that needs an unlock stays enabled with "Unlock this phone first", one that needs Face ID with "Confirm with Face ID", and the route's `403 ELEVATION_REQUIRED` emits `remote/call-denied` for `delorunChanges/<control>`, which opens the studio's unlock dialog; a `403 LOOPBACK_REQUIRED` answer toasts "This needs you at your computer." and disables nothing else. [`RestartCard.tsx`](src/client/RestartCard.tsx) shows `state.restart` above the groups: Restart now with a dialog that names the running chats it waits for or stops, Restarting with Cancel restart while it waits, and a failed restart with its reason, the change left out with Undo, and Try again; the controller reads `state` every 2 seconds while a restart is under way;
- `sidebar.footer.action` `delorun-changes.work-badge`（[`WorkBadge.tsx`](src/client/WorkBadge.tsx)），在工作会话持续期间显示插件名称，位于 Delorun 的撤销通知之后；
- 一个 `shell.overlay` toast（[`ChangesToast.tsx`](src/client/ChangesToast.tsx)），用于每个操作的结果。

[`controller.ts`](src/client/controller.ts) 负责每个请求以及两者读取的状态；它在加载时、每次操作之后以及页面可见期间每隔 `STATE_REFRESH_MS`（15 秒）读取 `state`。该部分在打开时、每次操作之后以及本人要求时，通过一次 `show?pending` 读取插件的文件夹和本人的 Delorun 副本，从不在 15 秒的读取中读取，并在新的应答到达之前保留屏幕上上一份列表。文案位于带类型的英文和中文字典（[`locales.ts`](src/client/locales.ts)），命名空间为 `delorunChanges`。

**构建。** harness 一半像 Delorun 其他没有 studio 界面的插件那样从 `src/index.ts` 运行；`pnpm --filter @delorun/plugin-changes run build` 只用上游的客户端预设（[`tsdown.config.ts`](tsdown.config.ts)）写出浏览器一半 `lib/client.js`。编译面为 `tsconfig.host.json`（harness 一半及其规格）、`tsconfig.client.json`（浏览器一半）和 `tsconfig.tests.client.json`（其规格），位于解决方案 `tsconfig.json` 之下。

<a id="configuration"></a>

## 配置

| 字段 | 默认值 | 含义 |
| --- | --- | --- |
| `enabled` | false | Delorun 的 C16 开关 `plugin_changes_pending`：保护开启时，agent 的插件变更等待本人处理。`@delorun/bundle-local` 在其 `delorun-plugin-changes` 行中以 `enabled: true` 挂载该插件；一致性叠加层把该行重述为禁用。 |
| `restartWaitSeconds` | 600 | studio 的 Restart 在让 Delorun 保持现状之前，等待运行中的对话的时长，单位为秒，取值 10 至 86,400。等待期间新回合被拒绝。 |
| `installationBundles` | `[]` | studio 安全模式持续加载的 bundle。`@delorun/bundle-local` 的行重述 Delorun 的 profile bundle 列表（本插件无法导入它），其 `plugin-changes-row.spec.ts` 约束二者相等。为空时，安全模式路由应答 `503 SAFE_MODE_UNAVAILABLE` 并指出 `delorun recover safe-mode`。 |

<a id="known-limitations"></a>

## 已知限制

- 配置中遗漏了 `delorun-plugin-changes` 行的 profile，在下次启动之前重新加载时没有该检查。

## 测试

[`tests/plugin-changes.spec.ts`](tests/plugin-changes.spec.ts) runs upstream's `plugin_manager` tool through the real tool pipeline: with protection on, an install, an update and a removal each record a pending change, leave the profile's files byte for byte as they were and never reach the approval; a call that cannot be recorded is denied; a listener that allows the call first is overruled by the guard; other actions keep upstream's approval; the actions the person makes are denied; with protection off, the default, every such call reaches upstream's approval and manager and the guard lets it run; a protection record that cannot be read holds the call; toggling the record between two calls of the same plugin instance switches the behaviour without a restart; and with the switch off, install and remove ask the tool's approval as upstream does. [`tests/reload-check.spec.ts`](tests/reload-check.spec.ts) boots a real profile with the plugin manager and hot reload: a tampered active directory loads nothing; with protection on, a restore naming a folder and another process's `link:<folder>` install load nothing and upstream evaluates nothing of a plugin with no approved content; with protection off, such an install loads the folder, logged as an applied change decided `unreviewed`. [`tests/unrecorded.spec.ts`](tests/unrecorded.spec.ts) covers a failure that is not an `Error`; [`tests/host-operation.spec.ts`](tests/host-operation.spec.ts) the Host's plugin operation; [`tests/loaded-links.spec.ts`](tests/loaded-links.spec.ts) the harness-link rule. [`tests/routes.spec.ts`](tests/routes.spec.ts) serves the routes on a loopback port: a caller without the credential, a remote session and another site are refused with the body withheld, each answered within 2 seconds, no route changes the protection setting, malformed requests are refused, and no answer names the home's path; [`tests/routes-state.integration.spec.ts`](tests/routes-state.integration.spec.ts) holds `state` to writing nothing and reading no folder; [`tests/routes.integration.spec.ts`](tests/routes.integration.spec.ts) acts on a real profile with its history, the second confirmation of a flagged change included, and applies a queued agent's install with protection on through the plugin operation after the second confirmation, refusing a remote session and another site; [`tests/restart-route.spec.ts`](tests/restart-route.spec.ts) holds Restart to the class of `harness-apply`, `CROSS_SITE` first, and checks the `restart` part of `state`; [`tests/live-apply.spec.ts`](tests/live-apply.spec.ts) serves a live asset only through the fence, never a server file, and keeps the previous bytes and leaves the change out when a live read fails; [`tests/routes-plugin.spec.ts`](tests/routes-plugin.spec.ts) covers the registration, and no registration without `isReachPeer`. [`tests/changes-section.client.spec.tsx`](tests/changes-section.client.spec.tsx) renders the browser half against a stand-in harness: each part of the state, a review with its risk summary, the files the diff does not show and the diff, the second confirmation before a flagged change is applied or approved, Apply of an agent's request with both confirmations, the protection setting with the live-reload note when it is off, turning it off with the second confirmation that names what would load, and a phone's protection notices with Dismiss, the changes to Delorun itself with Make my copy, Apply sending the version its review read, a second confirmation for a flagged one and Discard after a confirmation, Undo, Apply again, Discard, Start working and Done with exactly the version shown, each outcome's toast, a locked phone, whose refused unlock opens the unlock dialog, and a phone that confirms with Face ID, and the work-session badge while a session lasts and gone after.
