# @delorun/plugin-changes

English | [中文](README.zh.md)

## Summary

`@delorun/plugin-changes` keeps the agent from changing which plugins the harness runs while Changes' protection is on, and records what it changes while protection is off. With its C16 switch `plugin_changes_pending` on and protection on, a `plugin_manager` call whose action is `install_bundle` or `remove_bundle` does not run: a `tools/pre-execute` listener records it in the profile's change log as a pending change ([C21](../../docs/contracts/c21-changes.md#the-agent-and-plugins)) and denies the call with a result the model reads, `Recorded as a change waiting for the person's review at their computer: delorun changes show <id>. Nothing was installed.` The tool never reaches its own full-access approval for these actions, and the person applies or discards the change at their computer with `delorun changes` or in the studio. The agent's other `plugin_manager` actions that change what runs (`set_bundle`, `set_plugin`, `configure`, `set_version_exemption`, `undo`, `restore`) are denied with `PLUGIN_CHANGE_AT_COMPUTER` and record nothing. With protection off, the default, every such call goes on to upstream, whose full-access approval alone decides it, and an action that changed the profile is then recorded in Changes as an applied change decided `unreviewed`, which the person undoes with `delorun changes undo` or in the studio ([C21](../../docs/contracts/c21-changes.md#the-agents-plugin-actions-with-protection-off)). Whatever the switch says, the plugin provides upstream hot reload's `profileReconcileCheck`, which checks every recomposition of the profile before anything stops ([C21](../../docs/contracts/c21-changes.md#reloads-and-restores)). Whatever the switch says, it also registers the studio's Changes routes under `/delorun/changes/`, which upstream's boot page reads for its recovery screen ([C21](../../docs/contracts/c21-changes.md#routes-and-the-recovery-screen)), and its browser half adds the Changes section in Settings and the work-session badge, which act through the same routes ([C21](../../docs/contracts/c21-changes.md#the-studios-changes-section)). With the switch off, the default and the parity value, the plugin registers no listener or guard and the tool runs and asks as upstream's does.

## Contract

- **The protection setting.** The listener reads `readProtection` of the profile's Delorun home at each `plugin_manager` call whose action changes what runs, so `delorun changes protection on|off` takes effect at the next call in a running Host. With `off`, the default, it calls `next()` for every such call, exactly as with the switch off, so upstream's full-access approval decides, and Creator mode can turn bundles on from a chat. Before the call runs, `planAgentAction` of `@delorun/changes` reads what the call will be recorded as and the profile's latest history version, and `beginAgentAction` writes the entry into the profile's `agent-log.json`, so nothing the action loads goes unrecorded; a history or change log that cannot be read or written denies the call with `PLUGIN_CHANGE_UNRECORDED`. A `tools/post-execute` listener, registered ahead of the others, then runs `finishAgentAction`, which completes the entry with the version upstream wrote (`historyVersion`) and the one before it (`historyBefore`, after the person's own edit made by hand when there was one), removes it when the action changed nothing, and reports `PLUGIN_CHANGE_UNRECORDED` to the model when the files changed but the history saved no version or the entry cannot be completed. An entry whose post-execute never ran stays with the words that Delorun did not see how it ended. An install from a folder (`link:<folder>`) is also under Changes at the recomposition it causes: the check before a reload links the plugin to its active directory and logs the folder's content as an applied `plugin-install` decided `unreviewed`, and the plugin then reloads when its folder settles. A protection record that cannot be read holds the call exactly as with protection on: it is denied with `PLUGIN_CHANGE_UNRECORDED`, saying the setting cannot be read, and is never read as `off`. Everything below holds with protection `on`.
- **What is held.** `install_bundle` records a `plugin-install`, or a `plugin-update` when the spec is a registry version of a plugin the profile already has; the tool offers no update action, so this is how the agent asks for one. `remove_bundle` records a `plugin-remove`. Every other action and tool goes on to the next listener.
- **What is recorded.** `recordPluginRequest` of `@delorun/changes/install` writes one pending entry with `subject.spec` and, when the spec names it, `subject.plugin`, under the profile write lock, into the profile the Host runs (`ctx.profileContext`). It writes no manifest, lockfile, `node_modules` or approval. A request that still waits keeps its id; a repeat of a decided request is a new change.
- **What the model reads.** A recorded request is denied with error code `PLUGIN_CHANGE_PENDING` and the change's id; an update says `Nothing was installed or updated.` and a removal `Nothing was removed.` A call with no target, a spec pnpm would not accept, a removal of a name that is no dependency, a Host without a profile, or a log that cannot be written is denied with `PLUGIN_CHANGE_UNRECORDED` and the reason, and records nothing. The denial is the tool call's logged result, so no session event is added.
- **What the person makes with protection on.** `set_bundle`, `set_plugin`, `configure`, `set_version_exemption`, `undo` and `restore` do not run: the model reads that the person makes that change at their computer, in the studio or with `delorun plugin`, with error code `PLUGIN_CHANGE_AT_COMPUTER`, and nothing is recorded.
- **The guard.** A `pre-execute` listener that allowed such a call without calling `next()` would skip the plugin's listener. The plugin's tool guard, which runs after every listener and cannot be overruled, denies every such call its listener did not handle, in either protection setting; a call the listener passed on with protection off counts as handled.
- **The check before a reload.** `profileReconcileCheck.check(profile)` runs `prepareReload` of `@delorun/changes` for the profile the Host runs: a `link:` dependency that names a folder is moved to the plugin's active directory where the profile write lock allows, and a link or active directory that differs from what Changes keeps refuses the recomposition with `LOAD_REFUSED`, so nothing stops and nothing loads. A link counts as the harness's own when it is into the runtime store or names the directory the Host already loads that package from (`loadedLinks`).
- **The studio's routes.** Once the web server and Connection are present, [`src/routes.ts`](src/routes.ts) registers `GET /delorun/changes/state` and `show`, and `POST` `apply`, `discard`, `undo`, `off`, `on`, `work`, `done`, `safe-mode`, `exit-safe-mode`, `create`, `request` and `reveal`, the harness routes `harness-apply`, `harness-undo`, `harness-discard` and `harness-copy`, `restart` and `restart-cancel` ([`src/restart-route.ts`](src/restart-route.ts), the level of `harness-apply`), `protection-on`, `protection-off` and `notice-seen`, and the plugin names their prefix to the boot page through the index global `dshRecoveryRoutes`. Every request is admitted by Connection first; any admitted session reads, and a `POST` is decided before its body is read, in this order. First the site: a browser request another site sent is answered `403 CROSS_SITE` (at the computer, by `Sec-Fetch-Site` or an `Origin` that is not the request's loopback origin; from a paired device, by an `Origin` that is not `https://<Host>` or a foreign `Sec-Fetch-Site`). Then the control's level ([`src/access.ts`](src/access.ts)): the person at the computer (a loopback `Host`, the credential, and a session Connection's `isReachPeer` does not name; a Connection without `isReachPeer` gets no route) may use every control, attested with `attestStudio`; a paired device uses a control under its class in `AUTH_CLASSES` (`free`: protection on, update check, cancel and dismiss; `face`: every other control except `notice-seen`, with a one-action grant for exactly the request, read through `gateByClass` and never the approval grace, hashed over the body without `confirmedRisk` and `confirmed` and used up when the action proceeds, so the `409` that asks a second confirmation leaves it for the confirmed retry; `computer`: `notice-seen`), attested with `attestDevice`. Anything else is answered `403 LOOPBACK_REQUIRED`, or `403 ELEVATION_REQUIRED` for a device without a grant. Both proofs are logged as decided in the studio ([C21](../../docs/contracts/c21-changes.md#who-may-do-what-from-where), [C14](../../docs/contracts/c14-oidc-passkeys.md#face-id-unlock)). `apply` and `done` answer `409 CONFIRM_RISK` until the person confirms a flagged change again; `apply` of an agent's plugin request always answers `409 CONFIRM_RISK` first, naming its spec (kinds `dependency-or-build` and, for an install or update, `not-shown` with the spec, since nothing of what pnpm installs is shown), and once confirmed runs `applyInstallChange` with the Host's plugin operation, `@delorun/changes/plugin-operation`'s `upstreamPluginOperation`, the operation `delorun changes apply` runs, from the profile launcher's directory with its installation anchor and pnpm and its output in the Host's log, answering the applied entry, how the Host reloaded and, for a folder spec, the change that holds the folder's content; `apply`, `discard` and `undo` refuse a change to Delorun itself from the harness's log with `409 HARNESS_ROUTE`, because the harness routes decide it against the running runtime's signed file list, which the home process gives the Host as `changesHarness` (`409 HARNESS_UNAVAILABLE` on a Host without it, such as a source checkout); `harness-apply` takes the full `to` version that `show?pending` listed and answers `409 CHANGED_SINCE_REVIEW` for another; and an action reloads the Host in its own process with `reloadProfile`. `protection-off` answers `409 CONFIRM_PROTECTION` with `willLoad {plugins, harnessFiles}` until the request repeats with `confirmed: true`; that second ask stops a misclick and is no defence against someone at the computer. A protection change from a paired device writes a notice that `state.notices` shows the computer and `notice-seen` dismisses, at the computer only. `state` also names `access` (the requester and what each control needs: nothing, an unlock, Face ID or the computer), `harnessAvailable`, `unreviewedSinceOff` and `restart`. A decided change to one of the studio's built client assets is served at once through exact web-server routes under Connection's fence, and any other waits for the Restart, which the home process's `changesRestart` service runs ([`src/live-apply.ts`](src/live-apply.ts), [C21](../../docs/contracts/c21-changes.md#live-changes-and-restart)). `state` reads the records only (`recordedChanges` of `@delorun/changes` and the harness's log), writing nothing and reading no plugin's folder; `show?id=` of a change to Delorun itself reviews its two versions from the store; `show?pending` reads the folders and stores their content. An answer never carries the Delorun home's path: a refusal whose words name it answers its code and a fixed sentence and logs the words, and a recorded failure names the home as `<Delorun home>`.
- **The wire.** [`src/wire.ts`](src/wire.ts) holds the routes' paths, their refusal codes and the JSON fields each answers with, and imports nothing; the routes build those fields and the browser half reads them, so a field the Host stops sending fails the Host's typecheck. An entry left out at a start carries the failure the start recorded as `leftOut`.
- **Face ID on a paired device.** When the state says a control needs `face`, the controller asks `ctx.delorunFaceGrant` (shared as the source-only type [`src/client/face-grant.ts`](src/client/face-grant.ts), exported as `./face-grant`; `@delorun/bundle-local` provides it) for a grant covering exactly that call, action `changes/<control>`, and sends the call with the grant's id in `Delorun-Grant`. A control with two calls, such as the update's Prepare and Apply, asks once per call. A cancelled sheet sends nothing. Without the service the call is sent plain and the home refuses it. The button's hover text for such a control is "Confirm with Face ID first". The same module shares `grantingFetchOf(ctx)`, the `fetch` other plugins send their home requests through: the service's `fetch`, which asks for Face ID when the home refuses a call for want of a grant and sends it once more, or the page's own without the service. A face refusal of these routes names its grant action, `{ action: "changes/<control>" }`.
- **The setup routes.** `POST /delorun/changes/setup-export`, `setup-inspect` and `setup-apply` ([`src/setup-actions.ts`](src/setup-actions.ts)) write the profile's setup as a signed file, check a file and plan its import, and apply a planned import, through `@delorun/changes/setup-transfer` ([contract C21](../../docs/contracts/c21-changes.md), [C8](../../docs/contracts/c08-archive-and-trash.md#the-setup-archive)). They are decided like the other `plugin-other` controls: the person at the computer may use them, and a paired device needs one Face ID or PIN grant for exactly that call, with the same arrival and site checks as an action and before the body is read. An inspected file waits in memory under a random single-use token for ten minutes; `setup-apply` takes the token, never a file. A file over 32 MiB is moved with the commands.
- **No decisions elsewhere.** Apart from the routes, the plugin imports no function that applies, discards or undoes a change, opens or ends a work session, or changes the protection setting; `delorun/packages/changes/tests/reach.spec.ts` holds it to that, and holds the routes to `attestStudio`, `attestDevice`, `changeProtection` and the harness actions without `attestTerminal`, `setProtection` or `discardAllHarnessChanges`. The routes apply an agent's plugin request with `applyInstallChange` and the studio's proof.

## The studio's Changes section

The browser half, [`src/client/index.ts`](src/client/index.ts) (`@delorun/plugin-changes/client`), loads with the `delorun-plugin-changes` row and registers:

- the `settings.section` `delorun-changes` ([`ChangesSection.tsx`](src/client/ChangesSection.tsx)): the work session with Done, or the plugins of the last start with Start working; the changes a start left out with Apply again and Undo; the changes waiting for review, each opened by Review ([`ChangeDetail.tsx`](src/client/ChangeDetail.tsx)) with Apply and Discard; the agent's plugin requests with the terminal command, Apply and Discard; the recent changes with Undo; the changes to Delorun itself ([`SelfGroup.tsx`](src/client/SelfGroup.tsx)): Make my copy, the changes waiting in the copy with Review (Apply sends the `to` version the review read) and Discard, and the decided changes with Review and Undo, each with when it takes effect and, for a paired device's decision, its name, and the terminal command `delorun changes edit-harness --discard` as the only one left; and the protection switch ([`ProtectionGroup.tsx`](src/client/ProtectionGroup.tsx)), which turns protection on after one confirmation and off after the one confirmation that names what would load without review from the route's `409 CONFIRM_PROTECTION`, with the notices of a paired device's protection change and Dismiss at the computer; with protection off, a note under the introduction says that changes load without review and a linked plugin reloads live each time it is saved. A change the checks flagged asks a second confirmation, opened by the route's `409 CONFIRM_RISK` and naming the kinds and the files the diff does not show, before Apply or Done sends `confirmedRisk`; Apply of an agent's request asks a first confirmation, then the second one the route asks for every request, which names the request and its spec. Every control reads `state.access.may[control]` ([`AccessNote.tsx`](src/client/AccessNote.tsx) shows who acts on a device): a control that needs the computer is disabled with "Needs your computer"; one that needs an unlock stays enabled with "Unlock this phone first", one that needs Face ID with "Confirm with Face ID", and the route's `403 ELEVATION_REQUIRED` emits `remote/call-denied` for `delorunChanges/<control>`, which opens the studio's unlock dialog; a `403 LOOPBACK_REQUIRED` answer toasts "This needs you at your computer." and disables nothing else. [`RestartCard.tsx`](src/client/RestartCard.tsx) shows `state.restart` above the groups: Restart now with a dialog that names the running chats it waits for or stops, Restarting with Cancel restart while it waits, and a failed restart with its reason, the change left out with Undo, and Try again; the controller reads `state` every 2 seconds while a restart is under way;
- the `sidebar.footer.action` `delorun-changes.work-badge` ([`WorkBadge.tsx`](src/client/WorkBadge.tsx)), which names the plugin while a work session lasts, after Delorun's undo notice;
- a `shell.overlay` toast ([`ChangesToast.tsx`](src/client/ChangesToast.tsx)) for each action's outcome.

[`controller.ts`](src/client/controller.ts) owns every request and the state both read; it reads `state` at load, after each action and every `STATE_REFRESH_MS` (15 seconds) while the page is visible. The section reads the plugins' folders and the person's copy of Delorun through one `show?pending` when it opens, after each action and when the person asks, never on the 15-second read, and keeps the last list on screen until the new answer arrives. The copy is in typed English and Chinese dictionaries ([`locales.ts`](src/client/locales.ts)), namespace `delorunChanges`.

**Building.** The harness half runs from `src/index.ts` like Delorun's other plugins without a studio face; `pnpm --filter @delorun/plugin-changes run build` writes only the browser half, `lib/client.js`, with upstream's client preset ([`tsdown.config.ts`](tsdown.config.ts)). The compiler faces are `tsconfig.host.json` (the harness half and its specs), `tsconfig.client.json` (the browser half) and `tsconfig.tests.client.json` (its specs), under the solution `tsconfig.json`.

## Configuration

| Field | Default | Meaning |
| --- | --- | --- |
| `enabled` | false | Delorun's C16 switch `plugin_changes_pending`: with protection on, the agent's plugin changes wait for the person. `@delorun/bundle-local` mounts the plugin with `enabled: true` in its `delorun-plugin-changes` row; the parity overlay restates that row disabled. |
| `restartWaitSeconds` | 600 | How long the studio's Restart waits for running chats before it keeps Delorun running as it is, in seconds, from 10 to 86,400. New turns are refused while it waits. |
| `installationBundles` | `[]` | The bundles safe mode from the studio keeps loading. `@delorun/bundle-local`'s row restates Delorun's profile bundle list, which this plugin cannot import, and its `plugin-changes-row.spec.ts` holds the two equal. Empty, the safe-mode route answers `503 SAFE_MODE_UNAVAILABLE` and names `delorun recover safe-mode`. |

## Known limitations

- A profile whose configuration leaves the `delorun-plugin-changes` row out reloads without the check until its next start.

## Tests

[`tests/plugin-changes.spec.ts`](tests/plugin-changes.spec.ts) runs upstream's `plugin_manager` tool through the real tool pipeline: with protection on, an install, an update and a removal each record a pending change, leave the profile's files byte for byte as they were and never reach the approval; a call that cannot be recorded is denied; a listener that allows the call first is overruled by the guard; other actions keep upstream's approval; the actions the person makes are denied; with protection off, the default, every such call, turn-ons, undo and restore included, reaches upstream's approval and manager, the guard lets it run, and each action that changed the profile is recorded in the agent-action log as an unreviewed change with the version before it, written before the action runs and completed after, while a call the person does not approve runs and records nothing; an action that ran but could not be recorded is reported, one whose history saved no version is recorded without an undo, a blocking post-execute listener cannot leave the entry unfinished when it is registered before this plugin's, and a call whose records cannot be read does not run; `log.json` is left as a release without the agent log reads it; a protection record that cannot be read holds every call as with protection on; toggling the record between two calls of the same plugin instance switches the behaviour without a restart; and with the switch off, install and remove ask the tool's approval as upstream does. [`tests/reload-check.spec.ts`](tests/reload-check.spec.ts) boots a real profile with the plugin manager and hot reload: a tampered active directory loads nothing; with protection on, a restore naming a folder and another process's `link:<folder>` install load nothing and upstream evaluates nothing of a plugin with no approved content; with protection off, such an install loads the folder, logged as an applied change decided `unreviewed`. [`tests/unrecorded.spec.ts`](tests/unrecorded.spec.ts) covers a failure that is not an `Error`; [`tests/host-operation.spec.ts`](tests/host-operation.spec.ts) the Host's plugin operation; [`tests/loaded-links.spec.ts`](tests/loaded-links.spec.ts) the harness-link rule. [`tests/routes.spec.ts`](tests/routes.spec.ts) serves the routes on a loopback port: a caller without the credential, a remote session and another site are refused with the body withheld, each answered within 2 seconds, no route changes the protection setting, malformed requests are refused, and no answer names the home's path; [`tests/routes-state.integration.spec.ts`](tests/routes-state.integration.spec.ts) holds `state` to writing nothing and reading no folder; [`tests/routes.integration.spec.ts`](tests/routes.integration.spec.ts) acts on a real profile with its history, the second confirmation of a flagged change included, and applies a queued agent's install with protection on through the plugin operation after the second confirmation, refusing a remote session and another site; [`tests/restart-route.spec.ts`](tests/restart-route.spec.ts) holds Restart to the class of `harness-apply`, `CROSS_SITE` first, and checks the `restart` part of `state`; [`tests/live-apply.spec.ts`](tests/live-apply.spec.ts) serves a live asset only through the fence, never a server file, and keeps the previous bytes and leaves the change out when a live read fails; [`tests/routes-plugin.spec.ts`](tests/routes-plugin.spec.ts) covers the registration, and no registration without `isReachPeer`. [`tests/changes-section.client.spec.tsx`](tests/changes-section.client.spec.tsx) renders the browser half against a stand-in harness: each part of the state, a review with its risk summary, the files the diff does not show and the diff, the second confirmation before a flagged change is applied or approved, Apply of an agent's request with both confirmations, the protection setting with the live-reload note when it is off, turning it off with the second confirmation that names what would load, and a phone's protection notices with Dismiss, the changes to Delorun itself with Make my copy, Apply sending the version its review read, a second confirmation for a flagged one and Discard after a confirmation, Undo, Apply again, Discard, Start working and Done with exactly the version shown, each outcome's toast, a locked phone, whose refused unlock opens the unlock dialog, and a phone that confirms with Face ID, and the work-session badge while a session lasts and gone after.
