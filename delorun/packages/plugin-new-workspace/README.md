# @delorun/plugin-new-workspace

English | [中文](README.zh.md)

Delorun's new-workspace flow. Its Host half serves the routes the flow's screens call: where to start looking, a bounded folder search, one folder's preview, adding an existing folder, making a new folder with an optional Git repository, cloning from Git with an optional branch, and each workspace's defaults. It also starts each new chat in a workspace on that workspace's model. Its studio half is the dialog that calls the routes.

## Routes

Every route is an exact `POST` under `/api/delorunNewWorkspace`, served while upstream's workspace registry is present. Each answers the computer, and a paired device only while it holds an unlock (`ELEVATION_REQUIRED` otherwise); any other arrival is refused `LOOPBACK_REQUIRED` before the body is read. The four routes that change something (`add`, `create`, `clone`, `setDefaults`) renew the device's unlock.

| Route | Body | Answer |
| --- | --- | --- |
| `.places` | none | The recent workspaces whose folders still exist, the suggested folders that exist inside a root, the home folder, and where a new folder goes. |
| `.search` | `{ query }`, 1 to 100 characters | Up to 50 folders whose name contains the query (any letter case), nearest first, and why the search stopped: `complete`, `limit` or `time`. |
| `.preview` | `{ path }` | Whether the folder is empty, code or files; the stacks its marker files name (Node.js, TypeScript, Deno, Python, Rust, Go, Java, Ruby, PHP, .NET, Swift, Elixir, C and C++); whether it is a Git repository, on which branch, and the subject and time of its latest commit; whether it has an `AGENTS.md`; and its first 24 visible names, folders first, each file with its size in bytes. |
| `.add` | `{ path }` | `added` with the workspace's id, canonical path and kind, or `refused` with the reason. |
| `.create` | `{ parent, name, git }` | Makes `parent/name` and registers it; with `git` it runs `git init` and writes a starter `.gitignore`. |
| `.clone`, `.cloneStatus` | `{ url, parent, name, branch? }`, then `{ job }` | Starts a clone into `parent/name` and reports its progress, then registers the folder. |
| `.defaults`, `.setDefaults` | `{ path }`, then `{ path, defaults }` | One workspace's model, thinking level and browser choice. |

## Where a workspace may go

Every path is checked twice: against the folders Delorun never adds (the home folder itself, the Delorun home, the stock home and the system folders `workspaceLocationProblem` of `@delorun/home` lists), and, for a search, a preview, a new folder or a clone, against the configured `roots` with symbolic links resolved. A new folder's or clone's parent is created when missing and checked again after it exists, so a link planted in the meantime is refused. A refusal names the reason and creates nothing.

A preview reads the folder's top-level names, the size of each listed file, `.git/HEAD` and, for a repository whose `.git` is a real folder inside it, the subject and time of the latest commit, at most 2000 entries within `searchTimeMs`; it opens no file's contents and follows no link. The commit comes from one `git log -1` run with the user's and the system's Git configuration off, replacement refs ignored, no lazy fetch and no transport (a partial clone's missing object is never fetched, so its `core.sshCommand` never starts), Git kept from looking above the folder or treating it as a bare repository, the repository's `core.fsmonitor`, `core.hooksPath` and `log.showSignature` overridden, no prompt, a two-second bound and a 4 KB output bound. At most three such runs are in flight on the Host and 24 wait; a request past that gets no commit. A repository whose `.git/objects/info/alternates` names other folders to read objects from gets no commit. Format and control characters (bidirectional marks included) are removed from the subject. A search walks breadth-first from each root, at most `searchDepth` folders deep, `searchFolders` folders and `searchTimeMs` long. It never follows a link and skips hidden folders, dependency and build folders (`node_modules`, `vendor`, `dist`, `target`, `venv` and similar), the Delorun home and the stock home.

## Git

`create` and `clone` run Git with hooks, LFS filters and the person's templates off, and with no system or global configuration, askpass program or terminal prompt. A clone takes `https` addresses without a user name or password, and `ssh` and scp-like addresses; it skips submodules, and checks out with every `filter` attribute unset; `.git/info/attributes` is removed once it finishes. A branch name is checked against Git's rules before Git runs. `@delorun/plugin-workspaces`' import clone builds its arguments from the same `cloneArguments` and `createCloneTemplate`.

## Each workspace's model and browser

`.setDefaults` keeps one workspace's model (`provider`, `model`, optional `reasoningEffort`) and browser choice in `<Delorun home>/secrets/new-workspace/defaults.json`, mode 0600, keyed by the folder's real path, under a lock file. The same file keeps the last folder a new folder or clone went in, which `.places` offers as the next place.

When a top-level chat starts in a workspace whose defaults hold a model, the plugin appends upstream's `model/selection` event before the first request, so the chat's log records the model it starts on. A resumed, forked or delegated chat, a chat that already records a model, and a workspace whose model's provider is not connected are left alone; the last one is logged.

The plugin also provides `browserUseAdmission`, which the Browser plugin pack's isolated browser (`@deepseek-ai/dsh-experimental-browser-use-playwright-mcp`) asks at each chat start and each browser tool call. The nearest workspace at or above a chat's folder that has a stored browser choice decides: under No browser the chat gets no browser server and its browser tool calls are refused, so a workspace set to Isolated browser inside one set to No browser still gets the browser. The choices are held in memory, read before the service is provided and again after each `.setDefaults` change; each running chat whose answer changed is reported through the `browser-use/admission-changed` event, so its browser server stops or starts at once, and new chats follow the new choice. While a store that exists cannot be read, no chat gets the isolated browser, and the log says why. While this plugin's row is off or failed, nothing provides the admission and every chat gets the isolated browser, whatever was stored. No browser covers only the isolated browser: the person's own browser (`@delorun/browser-use-browse`, `use_my_browser`) can still be asked for in that workspace, because each use needs the person's own approval for that chat.

## Configuration

| Field | Default | Meaning |
| --- | --- | --- |
| `roots` | `['~']` | Where new folders and clones may go and where a search looks. |
| `suggested` | `~/Projects`, `~/src`, `~/code`, `~/Documents`, `~/Desktop` | Folders offered as places to start, when they exist inside a root. |
| `firstParent` | `~/Projects` | Where a new folder or clone goes before the person has made one; created at first use. |
| `searchDepth` | 4 | Folders below each root a search looks. |
| `searchFolders` | 20000 | The most folders one search reads. |
| `searchTimeMs` | 2000 | The most time one search or one preview read takes. |
| `cloneTimeoutMs` | 600000 | The most time one clone takes. |

## The studio half

It loads only while the Delorun look is on; the stock look keeps upstream's flow. It occupies upstream's three directory-flow holes at priority -1, below upstream's pickers, so the sidebar's Add workspace, the new-chat workspace picker and the hero's workspace choice open the dialog and receive the workspace's folder as a picked folder, which upstream then adopts and opens. `ctx.delorunNewWorkspace.open({ from })` opens one large dialog, `min(1040px, 92vw)` by `min(720px, 88vh)` and full screen on a phone, and resolves `created` with the workspace's id, its folder and what the folder holds (`code`, `files` or `empty`; a new folder is `code` with Git, else `empty`), or `cancelled`. A second `open` while one is open resolves the first as `cancelled`. Closing the dialog never cancels a clone: it keeps running on the Host.

Screen 1 asks how to start (New folder, Folder on this computer, Clone from Git) and lists the recent workspaces, one click from use. Screen 2 depends on the card. The folder browser has one top row: clickable crumbs from Home, the folder-name search and a New folder icon button. The folders fill the width, each with a hint read from its preview (its stack or kind, and its Git branch), until a folder is selected; then a summary of it opens beside the list with its stack labels, branch and latest commit, top-level files with sizes, and Use this folder. It also picks the place for a new folder or a clone. On a phone the folders fill the screen and the summary opens as a full-screen step with Back. The other screens fit their content, so the dialog has no empty lower half; the folder browser keeps the full height. The new-folder screen takes a name, a place and whether Git starts, ticked by default. The clone screen takes an address, an optional branch, a place and a name, and starts the clone, which keeps running while the next screens show. Continue on screen 2 goes to the browser screen, and nothing is made at that point.

Screen 3 is the browser: "Can agents in this workspace use a web browser?" is one group of choices from `@delorun/browser-setup`, the component the setup guide's Browser step also draws. Isolated browser and No browser can be chosen; "Use my browser" shows disabled with its Preview chip and records nothing. The choice opens on Isolated browser when the Host lists the Browser plugin pack and on No browser when it does not, and follows what the Host reports as it loads until the person picks; a pick stays. While Isolated browser is chosen the screen says whether Browser is ready, read from the Host's requirement check when the screen opens and whenever the window regains focus, with Try again for a failed read and the Settings section or command that meets a need. When the pack is not in the profile the screen says "The Browser plugin is off for this home." with an Open Plugins button, offered only while the page has a Settings shell. The choice is stored for the workspace with the model, and No browser keeps the isolated browser from the workspace's chats (see [Each workspace's model and browser](#each-workspaces-model-and-browser)).

Screen 4 is the model: "New chats here start with" a Model and a Thinking level, read from the studio's `remote.session` model catalogue and prefilled with the home's default ("<model> (your default)"). Thinking lists the levels the chosen model supports. When the catalogue cannot be read, the screen says chats start on the home's model and Continue still works. The workspace stores the model and level it shows whether or not the person changed them, so it keeps them if the home's default changes later; with no catalogue no model is stored. Screen 5 is safety: Change files in this folder (selected, recommended) or Full access, which asks once for this workspace, and then Internet for commands: Open (default), Only sites I list (one host name per line, checked as host names and at most 200) or Off. Read only is not offered here. The model and safety screens end with the same block about what one chat can switch (model, permission, and that the network stays for the whole workspace). Screens 3 and 4 offer Create now, which finishes with the choices made so far; the last screen's primary button is Create workspace. A recent workspace chosen on screen 1 is added as it is and keeps what it has.

Finishing makes the workspace and then sets it up in a fixed order, with "Setting up…" in the footer: first `.setDefaults` with the stored model and browser choice in one call, then, when the network is not Open, the home's own `POST /api/delorunNetwork.set` with `{ path, network: { access, hosts } }`, then, when Full access was chosen, `ctx.delorunFullAccess.askForWorkspace(path)`, and only then `created`. The path is the canonical one the Host returned. A step that fails is shown in place on a final view and the workspace still opens from its Open workspace button (closing the view opens it too); a declined consent leaves the workspace on Change files and opens it without a note, and a page without the consent service says to turn Full access on later from the permission menu in a chat. A refusal of the folder, name or clone returns to screen 2 with the reason.

Every screen opens with the safe choice already made. A route's answer is parsed with its wire schema, and a failure comes back as a value: `locked` asks the studio for the unlock prompt through `remote/call-denied`, `refused-arrival` says the step needs the computer, and each refusal shows in place as one sentence. Paths show the home folder as `~` and nothing else about the computer. On a phone the dialog is the whole screen: the cards stack, the folder browser shows one column at a time, and the footer buttons share one row while Back, Create now and Continue fit, with Create now on its own row above when they do not.

## Tests

`tests/routes.spec.ts` mounts the plugin and checks the browser admission it provides and, for each route, the refused arrivals, the locked device and the computer. `create.spec.ts`, `clone.spec.ts`, `places.spec.ts` and `search.spec.ts` cover the home folder, the Delorun home, a folder outside the roots and a link leaving them; `defaults.spec.ts` covers the store's mode and format and the seed's conditions. The studio half's specs are `tests/*.client.spec.tsx` (the dialog, the API client and the service), `finish-flow.client.spec.tsx` (including the setup order) and `flow.spec.ts` (the flow's state machine); `setup.client.spec.tsx` covers the model and safety screens and the finish paths, `browser.client.spec.tsx` the browser screen, and `models.client.spec.tsx` the catalogue mapping and host list. `browser-admission.spec.ts` covers the admission: a chat in a workspace that chose No browser, or in a folder inside one, is refused, the nearest workspace's choice decides, a refused store admits no chat, and a changed choice applies to the next chat and is reported for each running chat whose answer changed.
