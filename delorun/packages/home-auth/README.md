# @delorun/home-auth

English | [中文](README.zh.md)

## Summary

This package is the home of the authenticator provider of [contract C4](../../docs/contracts/c04-admission.md#authenticator), with the owner claim and device approval of [C5](../../docs/contracts/c05-device-approval.md), the identity factors of [C14](../../docs/contracts/c14-oidc-passkeys.md) and the server-side reach sessions of C4. It provides the `authenticator` with sign-in by an approved device's key, the approval window and local approval, the `tailnet-membership` identity factor and the allowlist of what an approved device may call, and every CLI profile loads it as the row `delorun-home-auth`. The loopback studio is still admitted by upstream's launch token and cookies, and a reach listener serves only while a reach provider asks for it, so with reach off no reach route answers. The first half is the owner claim and device list: the records under `~/.delorun/secrets/home-auth/`, the routes that answer them, and the removal that ends a device's live sessions. C4's admission denial suite proves the upstream half of the seam and lives with the CLI, which composes the studio, in `delorun/apps/cli/tests/denial/`: upstream's connection declares the `Authenticator` Service Definition and opens reach listeners with `ctx.connection.openReachListener`, and the web server runs each reach listener's dispatcher before any route, upgrade or the fallback. The contract's identifiers, codes and limits come from [`@delorun/contract-admission`](../contract-admission/README.md).

## The owner claim and device list

`src/home-auth.ts` is the coordinator over `~/.delorun/secrets/home-auth/`, and `src/service.ts` mounts it as the `homeAuth` service, which registers `POST /auth/owner/claim`, `GET /auth/devices` and `POST /auth/devices/remove` with the web server inside `ctx.effect()`. Each rule below is what one spec under `tests/` pins:

- **The owner code** (`owner-code.json`). 128 bits written as 26 base32 characters, printed once and kept only as a SHA-256 digest. A code is single-use and expires 10 minutes after it was printed; a wrong code leaves the outstanding one in place, and a new code replaces it.
- **The claim** (`owner.json`, `devices.json`). Loopback only, and a `Host` naming a reach address is refused even when nothing stamped the request. The claim records the listener's own origin, `http://127.0.0.1:3080`, whatever spelling of loopback the request used — `localhost`, `127.0.0.1`, `[::1]`, a `.localhost` name, with or without a port, through SSH port forwarding — and refuses a `Host` that is no authority at all with `BAD_REQUEST`, so a header an attacker wrote never becomes a device's address. One home has one owner: a second claimant with a fresh valid code is refused with `ALREADY_OWNED` and the first owner keeps the home, and two claims that race are serialised, so exactly one wins the owner seat. The code is consumed before a record is written, so a code that claimed a home never claims a second one, and a home that records devices but no owner refuses a claim with `STORE_INVALID` rather than taking ownership of them.
- **The arrival**. A request is a loopback request only when it carries no reach listener's stamp and the loopback listener's own socket accepted it: its local port is the web server's bound port and its local address a loopback address. Anything else is never loopback (the `a request without a listener stamp is not loopback` spec), so a forwarded request that missed its stamp gains nothing.
- **The arrival of the device routes**. `GET /auth/devices` and `POST /auth/devices/remove` answer on the loopback listener only: both decide the arrival before they read anything, answer a request a reach listener admitted with `403 LOOPBACK_REQUIRED`, refuse a `Host` that names another address with `421 HOST_MISMATCH`, and the removal additionally refuses a page on another origin — an `Origin` other than the request's own, or a foreign `Sec-Fetch-Site` — with `403 ORIGIN_MISMATCH`. That is what keeps a page served from a name that resolves to `127.0.0.1` (DNS rebinding) from reading the home's records or removing a device, and a cross-site form from posting the removal. Every device route on loopback — the list, the removal, the approval window, the pending requests and the approval — also needs the studio's own credential, which `connection.requestRejection` checks as it does for upstream's own routes: the browser's signed launch cookie or a live API credential. A request without it is refused with `401 NOT_SIGNED_IN`, so another program on the computer, a command a chat runs or another user reaches the port and nothing else. A state change also needs an `Origin` equal to the studio's own loopback origin; a request without one is refused with `403 ORIGIN_MISMATCH`. `delorun devices` uses the home socket's `devices.approve` and `devices.remove`, never these routes. No route returns a match code: the pending list carries the request's label, platform, address and times only.
- **The device list**. The owner and every trusted device, without key material. An unclaimed home refuses the listing and the removal with `NO_OWNER`, rather than answering as if it had an empty device list. The owner record and the device list are cross-checked, so a copied `owner.json` naming a first device this home does not record is a `STORE_INVALID` failure rather than an owner, and no listing, session or removal acts for it.
- **The sessions** (`sessions.json`). A token is handed out once and kept as the SHA-256 digest that keys its record, so a copy of the file signs nobody in. A session is minted only for a recorded device at the address it is trusted on: a home with no owner refuses with `NO_OWNER`, an owner record that cannot be read with `STORE_INVALID`, and a key this home does not record — a device of another home, one at another address, or one just revoked — with `DEVICE_NOT_TRUSTED`. A session reads as live only while its device is still recorded at the session's address, so a token whose device is gone answers nothing even when its own record survived.
- **The removal**. Deletes the device's record, invalidates every live session of its tokens, rotates every other session, disposes the device's Peers and closes the reach connections those sessions admitted through `ctx.connection.closeReachConnections({ deviceId })`, all before it returns; a device with no record still has its sessions ended. `signAllDevicesOut` is the removal's sibling for every device: it removes every session record, so each token is refused from that call on, ends every Face ID pass, unlock, grant and hold, and closes the reach connections the sessions admitted. The device records and their passkeys stay: the list is kept, and a device signs in again. Turning device access off calls it (Settings' phone-access switch and `delorun reach off`; a home that is not running has its stored sessions removed the same way), so turning access on again restores no session.
- **The limits**. A home trusts at most 32 devices (`DEVICE_LIMIT_REACHED`, `429`) and one device holds at most 16 live sessions (`SESSION_LIMIT_REACHED`, `429`); a session record whose lifetime passed is dropped before the bound is counted, so a device that signs in again after its sessions expired is never refused by them. The sign-in challenge route issues at most `challenges.perSourcePerMinute` (60 by default) challenges a minute to one source and `challenges.perDevicePerMinute` (10) to one trusted device, and refuses the next with `CHALLENGE_RATE_LIMITED` (`429`); both fields are bounded from 1 to 600 and fail the load outside them.
- **The records**. Every file is read through [contract C1](../../docs/contracts/c01-home-layout.md)'s protected-file check, so a file another user can read, or one that is not this package's JSON, refuses with `STORE_INVALID` instead of reading as empty and letting a claim replace it.

## Reach sign-in

`src/authenticator.ts` is the provider of upstream's `authenticator` ([C4](../../docs/contracts/c04-admission.md#authenticator)), which the service loads as a child plugin. It keeps upstream's admission on the loopback listener and serves a reach listener only while a reach provider asked `homeAuth.serve()` for it, with the identity factor the provider declares; only `tailnet-membership` on a `ts.net` address of the Tailscale private listener is accepted (`TAILNET_IDENTITY_UNAVAILABLE` otherwise). `admit` is synchronous over an in-memory copy of the stores, which every change rereads before it returns; it stamps each request with its listener, answers the pre-login routes, and admits a `__Host-delorun-session` cookie as one Peer per device and listener, which speaks for the device's `reach-device` principal and never for the owner, refusing `SESSION_EXPIRED` past 12 hours unused or 14 days old and `ROTATION_REQUIRED` after a device approval or removal; the session's open reach connections close at those same moments, without waiting for a request. A request without `Upgrade` on a session whose token is 24 hours old receives a new token in `setCookie`; the old token admits for 30 more seconds and is then deleted, and neither extends the absolute limit.

- **The approval window and local approval** ([C5](../../docs/contracts/c05-device-approval.md#approval-window)). `POST /auth/devices/window` on loopback, or the home socket's `devices.approve`, opens a 5-minute window and claims a home that has no owner for the local person. `POST /auth/device/request` outside a window answers `APPROVALS_CLOSED` before it reads the body. `GET /auth/devices/pending`, `POST /auth/devices/approve` and `POST /auth/devices/cancel` are the loopback approval form, behind the studio's credential; the third wrong match code cancels that request only, `Approvals.cancel` cancels a pending request at the person's choice (the home socket's `devices.approve` with `cancelRequestId`), and an approval records the approver `local`, rotates every session and closes the window. A full home refuses a sixth request and replaces none. A label or platform carrying a control or bidirectional formatting character is refused with `BAD_REQUEST`.
- **Sign-in**. `POST /auth/device/challenge` and `POST /auth/session` check an ECDSA P-256 signature over `delorun-signin-v1`, the address and a single-use 60-second challenge; on the Tailscale private listener the signature of an approved device alone creates a full session with the factor `tailnet-membership`. The sign-in page (`GET /auth/sign-in`) loads two content-hashed assets from `assets/`, keeps the device key non-extractable in IndexedDB and computes the match code with the same derivation as `src/match-code.ts`. A browser that opens any other page of the address without a live session, the address itself, a deep link or a mistyped path, is sent to the page with `303`, and the page's `next` keeps the target when it is a plain path outside `/auth`, so the device lands there once signed in. The page answers any other `next`, an absolute or scheme-relative URL included, with `303` to itself without it, so it never sends a device off the address. A script's request, a state change and an upgrade keep the `401` JSON refusal, and the loopback listener never redirects. Its markup, `assets/sign-in.html`, has no text and no inline script, style or handler; `assets/sign-in.js` holds every text in English and Chinese, chosen from the browser's languages, and shows one view per state: checking the device, the steps and device name of a new device, the match code to type at the computer with its remaining time while the page reads the request's state every 2.5 seconds, signing in, and each refusal with its next step (approval closed at the computer, five requests waiting, too many requests, a device holding its most sign-ins, cancelled, expired, the home unreachable, a browser without WebCrypto or IndexedDB key storage, and any other refusal with its code). The studio's bundle does not load before sign-in, so the stylesheet the page loads is one asset: `@delorun/brand`'s `tokens.css`, the studio's default look (Soft) page, card and text colours from `@delorun/brand/soft-surfaces`, and `assets/sign-in.css`, which reads the `--dl-*` colours and type stacks and holds no colour literal, so the page matches the studio a person reaches after signing in; `@delorun/plugin-theme`'s `tests/soft-surfaces.spec.ts` keeps those colours equal to the Soft palette. The markup takes the mark and the `theme-color` values from the brand through `src/sign-in-template.ts`. `gates:brand-drift` covers `assets/`, and `tests/sign-in-contrast.spec.ts` keeps every text pair at 4.5:1 in both schemes.
- **The refusals of the home's own computer** ([C14](../../docs/contracts/c14-oidc-passkeys.md#tailnet-membership)). The window, approval and removal routes answer a reach session `403 LOOPBACK_REQUIRED` naming the action. The provider also supplies upstream's `remoteAnswerGuard`: a granting answer (any answer but `rejected`, `cancelled` or `unavailable`) from a reach Peer to an approval prompt that carries `grants: "full-access"` (an escalation to `danger-full-access`, `plugin_manager`'s included, or a workspace's full-access consent) or `grants: "workspace-management"` (the main chat's account tools and its guarded tool calls, and an instruction-layer write that `@delorun/plugin-instruction-consent` asks about) is refused with `LOOPBACK_REQUIRED` naming `full-access-escalation` or `workspace-management` and not applied, so the prompt stays open for the studio on the home's computer. A refusal from the device applies. Another Delorun plugin's route that only the home's computer may use calls `requireComputer` (`src/computer-only.ts`) from its `connection/request` listener: a request that did not arrive on the loopback listener under a loopback `Host`, or any request while no `homeAuth` is mounted, is answered `403 LOOPBACK_REQUIRED` naming the action before the route reads its body.
- **Pop-up pairing** (C5, [Pop-up pairing](../../docs/contracts/c05-device-approval.md#pop-up-pairing)). `src/pairing.ts` resolves the plugin's `pairing` configuration in one `resolvePairing` step (Delorun's defaults; the schema holds the bounds, so a value out of bounds fails the load or the Settings write; the section is a volatile field, read at each use, so a change applies without a restart) and reads the `Tailscale-User-Login` and `Tailscale-User-Name` headers `tailscale serve` sets. Outside an approval window, `POST /auth/device/request` is accepted only for an identity that `pairing.mayAskWithoutWindow` allows (`own-user` compares with `ServedListener.computerUser`, which `@delorun/reach` reads from `tailscale status --json`), with at most `pairing.pendingPerIdentity` waiting per Tailscale user and the global cap of 5, of which requests without a window hold at most 4, so a request through a window the person opened always has room; any other request is answered `APPROVALS_CLOSED` before its body is read. The headers are a quota and display hint, never authorisation: a request still needs the match code typed at the computer. `GET /auth/devices/pending` (loopback only) returns each request's identity, window-less mark and wrong-code count, and the `pairing` values the studio's pop-up and notice follow; `pairing.showRequest` defaults to `dialog`, the pop-up. The service registers the `pairing` section as a computer-only setting, so a reach device cannot write it.
- **What a device may call** ([C14](../../docs/contracts/c14-oidc-passkeys.md#what-a-device-may-call)). `src/reach-access.ts` declares the `reach-device` principal, whose fields are the device id and the listener its Peer sits on, and the remote access policy the provider registers for it with upstream's `remoteAccess.registerPolicy`. Upstream's Gateway asks the policy before it dispatches each call of a reach Peer and before it forwards each event to one. The policy refuses by default: it binds the actions of `REACH_ALLOWED_ACTIONS` (what the person does at the computer with chats and workspaces, by the owner's rule that an approved device can already prompt the agent) and of `REACH_ELEVATED_ACTIONS` on the global resource, on every Workspace of the Workspace registry and on every Session of a Workspace or live in the Host, for a device that holds a Peer on the principal's listener; snapshots are recomputed when a Session or Workspace changes. `createCondition` decides per call: an elevated action is refused with `elevation-required: <action>` unless the device holds an unlock on that listener; a `session/create` outside the known workspaces is refused the same way with `CREATE_OUTSIDE_WORKSPACES`; a settings write that could turn a computer-only switch off (a field a mounted plugin registered with `HomeAuthService.registerComputerOnlySwitch`, such as the external-agent consent's `enabled`, written other than as the switch's literal `safeValue`, which is `true` unless the registration names `false`, as the consent's `fullAccessStartsAgents` does so that only the computer turns it on, or arguments it cannot read) is refused with `switchOffRefusal(label, safeValue)`, a settings write that would loosen a permission-preset row's `defaultPreset` (a looser sandbox mode or approval policy than the current preset's, an unknown preset, a removed field, or any change while the current preset cannot be read, read by `defaultPermissionOf` from the running presets) with `DEFAULT_PERMISSION_REFUSAL`, `pluginManager/setPluginEnabled` on a protected row (one whose module the `plugin-manager` row's `protectedPlugins` names, read from the Loader by `protectedEntryIdsOf` through `protectedPluginsIn`, the reader the CLI's update check shares) with `PROTECTED_ROW_REFUSAL`, and a `commands/execute` whose line the commands service's parser does not resolve to a name of `REACH_DEVICE_COMMANDS` with `UNLISTED_COMMAND_REFUSAL`, each under an unlock as well; and a workspace-file call is refused when its path's real path lies outside the chat's workspace or inside the Delorun home (`HomeAuthService.delorunHome`, two levels above the secrets directory), which the service itself would follow wherever it points, through a symbolic link included. The unlock (`src/elevation.ts`, C14's [Elevation](../../docs/contracts/c14-oidc-passkeys.md#elevation); `src/elevation-routes.ts` serves the device's request, state and lock on its reach listener and the computer's list, approval and revoke on loopback only) lives in the memory of this profile's Host against the device, the listener and the session that asked, starts only with the 8-digit code the device shows typed at the computer, and ends at its minutes, a revoke at the computer, the device's lock, the session's end, the device's removal, the listener's stop or the Host's; its end closes the device's reach connections, since the Gateway decides a stream only when it opens, and each start, ending and admitted call is logged. Every other action, each one of `REACH_DENIED_ACTIONS` with its reason or one no table names, is refused with `remote-access/denied` and the reason `loopback-required: <action>`; an allowed or elevated action on a Session the policy cannot name, such as a stored Session outside every Workspace that is not live, is refused with `resource-unlisted: <action>`.
- **Loosened settings** ([C14](../../docs/contracts/c14-oidc-passkeys.md#elevation)): a default-preset loosening or a consent turn-off a device makes with a grant under dangerous mode is recorded in `reach-dangerous-settings.json` (`src/dangerous-settings.ts`) before it proceeds, and `HomeAuthService` sets the previous value back through the settings service at the first read of the mode that finds it ended and at start; a field the person changed since stays.
- **Terminals** ([C14](../../docs/contracts/c14-oidc-passkeys.md#elevation)) are class `face` in `AUTH_CLASSES`: the condition refuses every `terminal/*` action to a device that holds no grant for the call and no live Face ID pass, on every resource, whatever dangerous mode, a workspace's full-access grant or an earlier version's `reach-terminal.json` says. Nothing reads that file now; a home that still has it keeps working, and the file can be deleted. `reachFullAccessGrants`, declared in `src/full-access-grants.ts`, supplies dangerous mode's state only.
- **Which paths a device reaches** ([C4](../../docs/contracts/c04-admission.md#pre-login-allowlist)). After sign-in, `admit` passes a reach request only when its target is a plain path on `REACH_DEVICE_PATHS` (`src/reach-paths.ts`), a table with one reason per entry: the studio page `/`, its `/assets` and install-time files, `/api` with its `/api/remote.mux` upgrade, the client plugin bundles under `/plugins`, this package's `/auth` routes and `/delorun/reach/status`. Every other target, of any exact, prefix or upgrade route or the fallback, is refused with `403 LOOPBACK_REQUIRED` before its route runs, after the session's own refusals and without rolling the session, so a route that only checks that its request was admitted, such as upstream's `open-in-app`, never answers a device. A target is plain when parsing it changes nothing and it holds no empty segment and no escaped `/` or `\`; only its path is matched, never its query. Under `/api`, each exact Fetch route answers a device only when it admits that Peer, and none of Delorun's does. `delorun/apps/cli/tests/denial/reach/reach-paths.integration.spec.ts` boots the whole CLI composition, requests every registration of the web server as a signed-in device, and fails on a registration the device reaches that it does not list and on an exact Fetch route without a recorded decision.

Not built here: passkeys, OpenID Connect, the recovery kit, reset, alerts, and the records of loopback credentials with their idle limit that C4 describes. Loopback credentials are upstream's launch cookie and API credential, admitted by upstream's built-in admission; no per-credential record exists, so no loopback request is refused for lacking one.

## The admission denial suite

`delorun/apps/cli/tests/denial/admission/` boots the web composition of Delorun's CLI profiles in the test process: upstream's web template, which Delorun's profiles extend, with the web server on a port the operating system assigns. Delorun's own bundle layer is left out of that composition; `delorun/apps/cli/tests/denial/reach/reach-paths.integration.spec.ts` boots the whole CLI profile, Delorun's bundles and their web routes included, and requests every registration as a signed-in device. The suite then loads a stand-in provider, `StandInHomeAuth`, which admits one session cookie and delegates the loopback listener to Connection's built-in admission, and a fixture community plugin with an exact route, a prefix route and an upgrade route. It opens all three reach listeners: `reach-tailscale-private` and `reach-tailscale-funnel` on `127.0.0.1` ports, and `reach-self-hosted-relay` on streams a local TCP server hands to it with a certificate from the stand-in stack's test authority.

The tests are named after C4's denial table:

| Test | What it proves |
| --- | --- |
| `every route and upgrade answers 401 before sign-in on each reach listener` | Every exact route, prefix route, upgrade route and the fallback the booted composition registers, and the fixture plugin's, answers 401 on each reach listener, and no fixture handler runs; with a session the same fixture route and upgrade run. |
| `a plugin route is pre-login only when the profile lists it` | A fixture route the provider answers as pre-login is refused until the listener's policy lists it, and refused again when the listing is removed. |
| `a pre-login request never reaches the fallback or another route` | An allowlisted path with no registered route is refused rather than served by the fallback. |
| `a cookie minted with upstream's secret is refused on a reach listener` | A `dsh-auth-*` cookie that upstream minted for the reach listener's own authority, and that admits on the loopback listener, is refused with `UPSTREAM_COOKIE_REFUSED`, also beside a session cookie. |
| `launch tokens and /connect are refused on a reach listener` | The process launch token in a `token` query and requests for `/connect` are refused, and no cookie is set. |
| `a loopback Host is refused on a reach listener` | `localhost`, `127.0.0.1` and `[::1]` in `Host` are refused with `HOST_MISMATCH`, on requests and upgrades. |
| `each listener refuses a Host its rule does not allow` | Each reach listener refuses the other listeners' addresses and a foreign name; the relay listener refuses an SNI other than its name with `SNI_MISMATCH`; the loopback listener refuses a foreign `Host` with upstream's 403. |
| `an upgrade with a foreign or absent Origin is refused` | An upgrade to `/api/remote.mux` without `Origin`, with another origin or with `null` is refused with `ORIGIN_MISMATCH`; the listener's own origin reaches the upgrade handler. |
| `removes Tailscale identity headers before admission` | The provider never sees a `Tailscale-*` header on any reach listener, on a request or an upgrade, and the Gateway's WebSocket still accepts the upgrade. |
| `no reach listener runs without home-auth` | Removing the provider closes every reach listener and its open connections; no reach listener opens without a provider, the loopback listener admits as upstream does, and a replacement provider that serves no reach listener opens none. |

A type-level check holds C4's `Admission` and `ListenerPolicy` types assignable to the upstream seam's, and a spec holds the dispatcher's refusal statuses equal to C4's.

## The reach access denial suite

`delorun/apps/cli/tests/denial/reach/` boots the same web composition, loads this package's service, opens a session for an approved device and admits it through the provider, then calls the Gateway with the Peer it returns. Each family `REACH_DENIED_ACTIONS` lists is refused naming the action, a settings write in every settings namespace the composition describes included; reading the chat list, the redacted settings, the plugin list and the files of a chat's own workspace, starting a chat, sending a message, choosing a preset and stopping the run succeed, and the device's event stream carries the chat events and no plugin management event. The suite also lists every Remote method the composition registers and every event it forwards, and fails on one that neither table names and on a table entry that names none, so a new method is refused by default and its classification is a decision.

## Dangerous mode

While dangerous mode holds, a signed-in device does what the computer does with a grant for each call, except the actions of class `computer`. The fact is `HomeAuthService.dangerousMode()`, read when asked from the `reachFullAccessGrants` service that [`@delorun/plugin-permission-defaults`](../plugin-permission-defaults/README.md) provides: true only when the row sets `fullAccessEverywhere` and the grant file `delorun setup` wrote is valid, and false without that plugin or while its store cannot be read. Removing the grant file or turning the row off restores every refusal at the next call. Each lifted refusal below still needs a grant for that call (Face ID, or the PIN), which a live Face ID pass of the device replaces for a `face` row that is not `alwaysAsk`.

| Refusal | Safer prompts and Same as stock | Dangerous mode |
| --- | --- | --- |
| A settings write that moves a computer-only switch off its safe value (`loopback-required: turning … off`, or `… on` for a switch whose safe value is `false`) | Refused, unlocked or not | Decided by a grant for the call |
| A settings write that loosens the permission new chats start in | Refused, unlocked or not | Decided by a grant for the call |
| `pluginManager/setPluginEnabled` on a protected row (the plugin manager still refuses a change to a guard plugin itself) | Refused, unlocked or not | Decided by a grant for the call |
| `commands/execute` of a command a device does not run | Refused, unlocked or not | Decided by a grant for the call |
| An approval prompt marked `full-access`, `workspace-management`, `external-agent` or `real-browser` answered from a device | Given only with an answer grant for that prompt and value (Face ID, or the PIN) or within a live Face ID pass of the device; `LOOPBACK_REQUIRED` without either, whatever unlock or grace the device holds | Unchanged |
| The permission-defaults routes that review and grant a workspace's consent (`delorunPermission.workspaces`, `.review`, `.setFullAccess`) | `.workspaces` and `.review` admitted to every approved device; `.setFullAccess` needs a grant for the call | Unchanged |
| The network routes (`delorunNetwork.list`, `.set`) | `.list` admitted to every approved device; `.set` needs a grant for the call | Unchanged |
| The MCP consent routes (`delorunMcpConsent.pending`, `.accept`, `.decline`, `.revoke`) | `.accept` needs a grant for the call; the others are admitted to every approved device | Unchanged |
| The external-agent consent routes (`delorunDelegationConsent.*`) | `.allow` needs a grant for the call; the others are admitted to every approved device | Unchanged |
| Everyday settings: a `settings/update`, `/mutate` or `/replace` to a namespace of `REACH_EVERYDAY_SETTINGS` (`ui-theme`, `ui-chat`, `ui-conversation`, `ui-settings-general`, `locale`, `delorun-theme`, `delorun-onboarding`, `delorun-sidebar`, `delorun-chat-states`, `delorun-cost-meter`, `delorun-thinking-rsvp`) | An approved device is admitted without an unlock, and PIN mode does not gate it: it follows ordinary device writes such as sending a message. A computer-only switch, a protected row and the default permission still refuse first. Two namespaces keep some fields at the computer (`REACH_EVERYDAY_FIELDS`): onboarding admits `done`, `step` and `pausedStart` (not `plugins` or `optionalRows`), and chat states omit `maxRecords` and `pruneMinutes`; a write of `delorun-sidebar`'s `workspaceIcons` that sets anything but valid icons (markup, an unknown field or an unlisted shape), a `settings/replace` of those namespaces, or a write that cannot be read as named fields, needs an unlock | A write to any other namespace needs an unlock (`elevation-required`) |
| Turning Delorun's own plugins on or off: `pluginManager/setPluginEnabled` on a row of `REACH_SHIPPED_ROWS` and `pluginManager/setBundleEnabled` on a package of `REACH_SHIPPED_BUNDLES` (the optional rows and recommended packages onboarding offers). The plugin metadata reads (`listBundles`, `listPlugins`) and the recommended plugins' purposes (`/api/delorunOnboarding.recommend`) are admitted to every approved device | Admitted without an unlock, PIN mode or not; a protected row is still refused | Any other row or package needs an unlock |
| Installing a package (`installBundle`), removing one, updates, undo and restore, MCP server changes, device approval, listing and removal, PIN set, options and off, reach, change protection and its approvals, and the trust and verify actions | Refused to an approved device without an unlock, or at the computer only (`loopback-required`) | Unchanged |
| Provider keys (`credentials/describe`, `.set`, `.unset` and the two `credentials` events, `REACH_KEY_ACTIONS`) and the key test (`/api/delorunOnboarding.keyTest`), which answer presence, writability and each provider's result and never a saved key or any part or length of one (`credentials/describe` leaves out `masked` for a device); the key actions name only references the model providers declare (`UNDECLARED_KEY_REFUSAL`) | An approved device is admitted without an unlock while no PIN is set and no passkey is enrolled; otherwise a key save or removal needs a grant for that call (`elevation-required` without one), and the key test answers every device `403` once a PIN or any passkey exists | Same as a device without an unlock |
| Opening a chat's folder in an application on the computer (`session/openWorkspacePath`, `session/workspacePathApplications`) | `loopback-required` | Unchanged |
| A workspace-file call (`workspaceFiles/*`, `officeKit/render`) with a path outside the chat's workspace | `loopback-required: … with a path outside the chat's workspace` | Decided by a grant for the call; the Delorun home stays out of reach. The lift equals what full access already gives a chat in the mode |

Each consent and permission route above is registered at one of the access levels of `src/route-access.ts` (`PLUGIN_ROUTE_ACCESS`), and `tests/route-access.spec.ts` fails on a registered route that is missing from it or whose registration does not match its level. `R` routes admit any approved device with no unlock (`admitApprovedDevice`). `U` routes admit only an unlocked device and answer a locked one `403 ELEVATION_REQUIRED` (`gateByUnlock`, which takes `renews: true` or `false` and `{ grace: false }`). `C` routes answer a device `403 LOOPBACK_REQUIRED` whatever its unlock (`requireComputerOrDevice` lets the computer or an approved device through and `requireComputer` the computer only). `K` routes admit a device that holds no PIN lock (`admitKeyDevice`). Dangerous mode no longer lifts any of these: `REACH_DANGEROUS_ACTIONS` is empty, and `session/openWorkspacePath` and `session/workspacePathApplications` are computer-only. The reach policy decides the actions; `COMPUTER_ONLY` lists the computer-only ones, and the `dsh-base`, `dsh-sdk-minimal`, `dsh-headless`, `bundle-local`, `bundle-headless`, `bundle-studio` and `bundle-webhooks` bundles (`COMPUTER_ONLY_BUNDLES`) are computer-only too, which a test checks against every shipped patch. A device may not write the settings of the `home-auth`, reach, `sandbox-local` and `sandbox-policy` rows, or of the webhook server row (`@delorun/bundle-webhooks/server`), which decides the address the GitHub webhook endpoint listens on, in any mode (`PROTECTED_ROW_REFUSAL`). `mcpManager/watch` needs an unlock because its `lastError` is free text. For a signed-in device, `/auth/devices` omits `address`, `approvedBy` and the owner's `firstDeviceId`, and adds `current` and `unlocks`.

**Unlocks.** A computer-approved unlock lasts `elevationMinutes` after the last action that needed it (`HomeAuth.touchUnlock`, `Elevations.touch`), never beyond `unlockCapMinutes` from its start (1 to 1440, 480 by default; a listener whose `elevationMinutes` exceeds it is refused at serve). Only the actions of `RENEWING_ACTIONS` (state-changing calls) and typed input in an attached terminal (`src/typed-renewal.ts`, at most once a minute) renew it. The reads and watches of `ELEVATED_READS`, terminal reconnects (`terminal/attach`, `retain`), polled unlock routes (`renews: false`) and a call the condition refuses after the unlock check never do; a test fails on an elevated action in neither list. A page unlock from a PIN and the approval grace do not slide. A newly approved device starts with an approval grace of `approvalGraceMinutes` (0 to 60, 15 by default; `POST /auth/elevation/end-grace` ends it), so setting up from a phone needs no unlock prompts. The grace never opens a terminal (`GRACE_REFUSED_ACTIONS`, every elevated `terminal/*` action) and never covers a settings write to a protected row (the namespace of any plugin-manager `protectedPlugins` row, in entry-id and row-`id` forms; refused with `GRACE_PROTECTED_ROW_REFUSAL`, which names no grant, until the grace ends), and `gateByUnlock(…, { grace: false })` makes the four actions that loosen consent or guard rows without a settings write (MCP accept, delegation allow, `setFullAccess`, the network allowlist set) need a code or PIN unlock. With PIN mode on there is no grace: none starts, and a running one is hidden (`elevationOf`, `elevationState`) when the mode turns on. The server admits a locked page to every `R` route; the PIN is asked only at a `U` route or action (`403 ELEVATION_REQUIRED`, or `elevation-required:` for an action) and for the key actions, and the client prompts at that action.

These stay at the computer in every mode: turning the mode on (only `delorun setup` and the computer-only `POST /api/delorunRun.dangerousConfirm` write the grant, and no other route or call does), approving a device and opening the approval window, the device sign-in, approving or revoking an unlock, removing a device, and the home's reset, recovery kit and reach settings. Account actions and opening the settings document stay in `REACH_DENIED_ACTIONS`. `tests/dangerous-mode.spec.ts` proves each lifted refusal in both modes and fails when one of the routes that approve, sign in, remove a device or change remote access reads the mode.

## PIN mode

PIN mode lets a person who holds an approved device confirm one action at a time with a PIN or passcode, as Face ID does ([C14, "PIN mode"](../../docs/contracts/c14-oidc-passkeys.md#pin-mode)). Version 1 serves the Tailscale private address only. The mode is off until the person sets a PIN at the computer; while it is off, every route and refusal of this package is as described above. No device holds a page unlock (A483): `POST /auth/pin/unlock` answers every device `403 ELEVATION_REQUIRED` without reading the request, so a device with no passkey reaches exactly what a device with one reaches.

- **Store.** `src/pin-mode.ts` keeps `pin-mode.json` (whether the mode is on, the secret's kind, a salted `scrypt` hash with its parameters, the idle minutes) and `pin-attempts.json` (wrong tries per device and across the home), both through the protected-file helpers at mode 0600. `reach-pin-settings.json` (the same ledger as `reach-dangerous-settings.json`, 0600) holds the settings a page unlock of an earlier build loosened; nothing records one now, and turning the mode off sets each back unless the person changed it since.
- **Grants.** `POST /auth/passkey/pin` (`src/passkey-auth.ts`) checks the secret through `src/pin-unlocks.ts` and mints the same one-action grant a passkey assertion mints, for a device with or without a passkey. No unlock window, code from the computer, approval grace or dangerous mode admits a `face` action or a reserved granting answer in its place, and a correct PIN never opens a Face ID pass.
- **Tokens.** `src/unlock-token.ts` still reads and strips the `Delorun-Unlock` header and the `delorun-unlock.<token>` WebSocket subprotocol from every header view before any route sees the request; no route mints a token, so a token a page sends is refused with `401 UNLOCK_INVALID`.
- **Wrong tries.** A try is counted and written before the secret is compared, one at a time per device. The fifth wrong try removes the device exactly as a removal at the computer does. Ten wrong tries across the home within 24 hours pause the PIN and Face ID until the computer resumes them. A restart keeps both counts.
- **Routes.** `src/pin-routes.ts` answers `GET /auth/pin/state` for a device on the private listener and refuses `POST /auth/pin/unlock`; `/touch` and `/lock` name no running unlock. `GET /auth/pin/mode` and `POST /auth/pin/set`, `/options`, `/off` and `/resume` answer the person at the computer only; a device is refused with `LOOPBACK_REQUIRED`. `/options` changes only the idle minutes (1 to 60) and lock-when-hidden of a mode that is on, with no secret, and is refused with `PIN_MODE_OFF` while the mode is off.
- **What is not built.** The Funnel and relay addresses, and setting the PIN from a device.

`tests/pin-mode.spec.ts` proves each defence by a test that fails without it: the unlock refused to every device with the right PIN, a wrong one or no body, counting and minting nothing; a forged token admitting nothing; and, through the PIN grant, the count before the comparison, the device removal, twenty parallel guesses spending at most five, the home-wide pause, the address rule, the old PIN refused after a change or the mode turning off, nothing minted for a removed device, an ended session or a stopped listener, and the PIN in no file, log or answer. `tests/authenticator.spec.ts` proves a no-passkey page that holds an old unlock token gets no `face` action and no reserved answer, and `tests/dangerous-settings.spec.ts` that it lifts nothing.

## Face ID unlock

A paired device confirms a `face` action with a passkey or its PIN as a one-action grant, or with one Face ID that opens a pass. `auth-classes.ts` holds `AUTH_CLASSES`, the one table that puts every action and route in `free`, `face` or `computer`, with an `alwaysAsk` mark on the `face` rows a pass never admits; a Fetch route declares its row with `gateByClass` (`auth-gate.ts`); the reach policy and `checkAnswer` read the same grants (`grants.ts`). Passkeys are stored in `passkeys.ts`, enrolled and asserted in `passkey-auth.ts` and served by `passkey-routes.ts`. The rules are in C14, "Face ID unlock". `unlockModeEnabled()` (a PIN is set or any passkey is enrolled) is the only reading behind the locked-device refusals. The denial specs are `tests/denial/face-grants.spec.ts`, `tests/denial/face-pass.spec.ts` and `tests/denial/passkey-auth.spec.ts`, which use a software authenticator (`tests/fixtures/virtual-authenticator.ts`).

**The pass.** One Face ID (a passkey assertion with user verification) on a paired device opens a pass for that device when the pass setting is above 0. While the pass is live, the device's `face` actions (installs, terminal, settings writes, model keys, Changes and updates, and approval answers that grant something other than full access) are admitted with no per-call grant, so no Face ID sheet appears. The pass is bound to the device and the listener (`GrantStore.openPass` keys it on those two alone; a device holds no page unlock, and a call that carries one matches no pass), is fixed from the moment of the Face ID, does not slide with use and lives in memory only. `src/pass-setting.ts` keeps the person's choice of Settings → Face ID → "Ask again after" (Every time, 5, 15, 30 or 60 minutes) in `face-id-pass.json` in the secrets directory; until they choose, the config field `faceIdPassMinutes` applies (one of 0, 5, 15, 30 or 60; 15 by default; any other value fails the load). "Every time" (0) opens no pass: one Face ID per action. A change ends every live pass.

**What never opens a pass.** The PIN (`POST /auth/passkey/pin`), on a phone with no passkey or as the fallback on a passkey phone; a code from the computer; the approval grace after pairing; dangerous mode. A phone with no Face ID confirms one PIN per action.

**The always-ask rows.** `src/pass-policy.ts` names every `face` row of `AUTH_CLASSES` once, in `PASS_ADMITS` or `PASS_ALWAYS_ASK`; `checkAuthTable` reports a `face` row in neither and `stalePassEntries` an entry that names no `face` row. A row marked `alwaysAsk` is never admitted by a pass and needs a one-action grant for that call even during a pass: `auth:/auth/devices/remove` (still Face ID only, never the PIN), `auth:/auth/passkey/remove`, `auth:/auth/passkey/devices` `auth:/auth/passkey/pass (write)` (which needs a grant a passkey minted, never the PIN), `changes:protection-off`, `route:plugin-permission-defaults/src/routes.ts#PERMISSION_ROUTES.setFullAccess` and `answer:full-access` (action `answer/full-access`, the approval answer that grants full access; a Face ID on an answer still opens a pass, since only an always-ask action entry stops one). A Face ID that confirms one of them opens no pass. Reach settings and PIN mode settings stay computer-only, as the `computer` rows do.

**Routes.** `GET /auth/passkey/pass` answers `{ minutes, choices, pass }`, with `pass` as `{ startedAt, endsAt, remainingMs }` or `null` (always `null` at the computer). `POST /auth/passkey/pass` with `{ minutes }` changes the setting: at the computer like any setting there, from a device only with a passkey-minted grant for action `auth/passkey/pass` whose hash is the SHA-256 of the JCS text of the body; a value outside the choices is `400 BAD_REQUEST`. `POST /auth/passkey/verify` also answers `pass: { startedAt, endsAt, remainingMs }` when one is live. `POST /auth/passkey/lock` with `{}` answers `{ ended }`; it is a `free` route and ends the device's own pass.

**What ends it.** Its end time; 5 minutes with no request from the device on that listener (`touchPass` from `admitToken` and from each Remote call; an idle end never extends the pass); Lock now, which ends the device's pass on every tab, so one tab hidden that long locks the others too; the studio page hidden for 5 minutes, which the client checks by a timer and again on return, since a phone suspends a hidden page and its timers, calling Lock now before anything else; a change of the pass setting, from a device or at the computer (reason `setting-changed`); the Peer's disposal; the end of the device's session or its sign-out; the device's removal; a rotation of every session; a restart.

**Terminals.** Terminal holds are unchanged: under a pass `terminal/create` is admitted with no sheet and opens the terminal's hold, so the terminal stays open under the hold's limits (5 minutes unused, 60 minutes in total) after the pass ends.

**Logs.** `home-auth: pass.started device=… listener=… minutes=…`, `home-auth: pass.ended device=… listener=… reason=<expired|idle|lock-now|setting-changed|peer-ended|session-ended|device-removed|sessions-rotated>` (an expired or idle pass is logged when the home next looks at it) and, for a granting answer a pass admitted, `home-auth: pass.used device=… listener=… answer=… grants=…`. The pass is not model-visible, so it has no session event.

## Notes for the provider

- **Pre-login asset routes.** A handler for `GET /auth/assets/<asset>` resolves the segment against a fixed table of built asset names. It never decodes the segment and then joins it to a directory path, because a decoded `..` or separator would leave the asset directory.
- **The claim's arrival.** The claim route decides where the request arrived before it reads the body, and its refusal names the loopback listener and SSH port forwarding; a reach listener answers the same refusal through `reachClaimRefusal()` before any route is consulted.
- **The device routes' arrival.** The listing and the removal decide the arrival before they read anything, and both refuse a request whose `Host` names another address; the removal also refuses a page on another origin. A device is listed, approved and removed only at the home's own computer, so a reach session's request is answered `LOOPBACK_REQUIRED`.
- **Revocation.** Removing a device or ending a session calls `ctx.connection.closeReachConnections({ deviceId })` or `({ sessionId })` before it returns, so streams and upgraded sockets that carry no Peer, such as `/plugins/events` and plugin upgrade routes, end with the session; disposing the device's Peer ends the streams that speak for it.
- **Expiry and rotation.** A rotation trigger closes every session's reach connections with `({ sessionId })` before it writes the rotation marks. Each session also has one unref'd timer for the earliest of its idle limit, its absolute limit and, for a token a roll replaced, the end of its 30-second grace; when it fires with no request admitted since, it closes that session's connections whether or not a request arrives, and stopping the service clears every timer. Use is an admitted HTTP request or upgrade on the session's token: bytes on a connection admitted earlier never reach `admit`, so an open stream or WebSocket keeps nothing alive. Frames a client sends on an open WebSocket do not count either, because neither the reach dispatcher nor this provider sees them, and the connection layer cannot tell a Remote call from the automatic Pong answering the Gateway's heartbeat Ping; the served studio sends its unary calls over HTTP, so a person using it keeps the session live. Connections close per session, never per device, because a device holds up to 16 sessions. A session a re-sign-in replaced keeps its open connections until its own idle or absolute limit, so the sign-in's own response is never cut.
- **Loopback credentials.** Upstream's connection emits `authenticator/minted` for each loopback mint, before it writes the response that sets the credential. This package does not listen to the event; a provider that records loopback credentials must record each mint before that response is written.

## Tests
