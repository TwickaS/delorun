# @delorun/plugin-permission-defaults

English | [中文](README.zh.md)

## Summary

Upstream composes one permission for the whole deployment: every new chat starts on the same preset, and choosing `danger-full-access` takes effect at once. This plugin makes the preset a property of the workspace instead. A new chat starts on the preset the person chose for its folder — `workspace-write` for a workspace nobody has chosen for — whatever the deployment default is, and full access happens only after one consent for that workspace. The person gives it at the home's own computer: in the studio when picking full access, from the approval card of a request that asks for full access, or in Settings, Permissions, or with `delorun workspace full-access`. The consent is written to the home's protected state, so it covers that folder until the person chooses another preset there; explicitly choosing the safer preset withdraws it, so returning to full access asks again.

The guard that refuses an unconseted full-access switch runs before the session records anything. A refused switch therefore appends no `sandbox/mode` event and no preset identity, the session keeps resolving the mode it had, and a command started in the same synchronous step runs inside the sandbox. The guard covers the whole selection, not only a mode change: a preset that keeps the mode and drops the approval policy is refused too, so the approval prompts are not a way around the consent. A per-call `sandbox_permissions` escalation is not a mode switch: it goes through upstream's per-call approval, which this guard does not see. The refusal's words name the workspace and where the person allows full access — the approval card's "Allow for this chat", the studio's Settings, Permissions, or `delorun workspace full-access "<folder>" on` with the workspace's folder ([`fullAccessRefusal`](src/index.ts)) — so the model reads them rather than a stack trace.

The plugin also gives each workspace a [network for its sandboxed commands](#the-network-of-sandboxed-commands), `open`, `allowlist` or `off`, which `web_fetch` follows too.

Everything, the routes included, sits behind the switch `permission_defaults`, off by default; `@delorun/bundle-local` turns it on in the CLI profile that `delorun` starts and `@delorun/bundle-headless` in the profile `delorun headless` runs, so a headless task in a folder without a grant cannot switch to full access; the desktop app runs upstream's profiles without it. Off, the plugin mounts nothing: the deployment default reaches every new chat exactly as upstream seeds it, and every mode switch is recorded, which is what the parity composition asserts.

## Which preset applies

Three tiers decide a chat's permission, strongest first:

1. The chat's own log. A preset identity or a knob event the chat already holds outranks its workspace's default, so a resumed, forked or seeded chat keeps the permission it recorded. An explicit `sandbox/mode` switch also outranks the preset identity — another surface's control, an approved escalation or a delegation seed — and the chat then reports `custom` while its knobs match no configured preset; `select()` re-asserts the chosen preset when the person picks again.
2. The workspace's default. `select()` records it, and this plugin seeds it into new chats only: the seed runs on a chat that holds no permission choice yet and was never seeded.
3. The deployment default. `sandbox-policy`'s mode and the approval policy's default sit beneath both: they apply to a chat whose workspace has no entry, and to any knob a chat never overrode.

## What it provides

- `permissionDefaults` — the service behind the switch. `defaultPreset(cwd)` and `granted(cwd)` read a workspace's recorded preset and whether it holds a full-access grant, `select(agent, preset)` is the one write path a surface uses to choose a workspace's preset, and `review(session, mode)` is the guard's verdict. The entries are kept in memory, so the guard answers synchronously; before every decision (a full-access switch, the preset of a new or restored chat, a surface's listing) the service compares the store file's identity (device, inode, size, modification time) with the one it read, and reads the file again synchronously when another process changed it. A grant withdrawn by another profile's Host, `delorun workspace full-access` or a running `delorun headless` task therefore stops counting at this service's next decision, and the open chats of the workspace that lost it are set back to the safer preset right after. The service also watches the store's file ([`src/watch.ts`](src/watch.ts): `fs.watch` on the store's directory, which it creates at the private directory mode, filtered to the store's file name and debounced by 100 milliseconds) and reads it again through `reload()` after another process's write, so the open chats of every Host of the home, of any profile, go back within a second of a withdrawal without any message between processes. A watch that cannot start or fails later is named once in the Host's log as a warning, and the decision-time read is then the only one. A running `delorun headless` task does not mount this service, so it reads the store at its next decision. `storeProblem` names a store that could not be read.
- `sandboxModeGuard` — the mode-switch hook of `@deepseek-ai/dsh-sandbox-policy`'s session-mode seam, mounted so `setSandboxMode` refuses a switch to full access in a workspace nobody consented to. It is the seam's one provider, so a composition turns on this consent or another plugin's guard, never both.
- The store — [`src/store.ts`](src/store.ts) holds the format and the file handling: one entry per workspace, keyed by the workspace's canonical path ([`src/workspace.ts`](src/workspace.ts)), in the home's `secrets/` directory at mode 0600, changed only while holding its lock file `workspaces.json.lock` (`@delorun/home`'s lock file, waited for up to 10 seconds), so a change never overwrites another process's change it did not read; so a confined command can neither read the consents nor grant itself one; on Windows, where the runner does not confine reads, it cannot write them but can read them. A store that is a symbolic link, is laxer than 0600, or holds another format is refused, and no consent counts until the person fixes it.
- `select()` asks through the composed approval service, naming the folder and what full access drops, and refuses with `FullAccessConsentRefusedError` on every answer but a grant: nothing is recorded and the workspace keeps the safer preset. It reads the store again before it decides whether to ask, and full access it did not ask for is recorded only while the store, read again under its lock, still holds the grant; otherwise it refuses with `FullAccessConsentRefusedError` and records nothing, so a grant another process withdrew is asked for again. Choosing the safer preset withdraws the workspace's grant, so a later full-access selection asks again; the workspace's other open chats that run with full access go back to the safer preset, as when full access is turned off, and every other Host reads the change through its watch. The approval service asks only inside a chat's open turn, so no studio surface calls it.

## The consent surfaces

The studio and the CLI ask the consent themselves and record the answer through the service, at the home's own computer only. The consent's words come from [`fullAccessNote`](src/review.ts): commands in the workspace may then run outside the sandbox and write anywhere, read everything the person's user can, Delorun's home with its keys and tokens included, and reach the Docker supervisor and Delorun's update channel; the answer covers that workspace only.

- **Service calls.** `workspaces()` lists every workspace a surface shows — the registered ones, those the store holds and the folders of open chats — each with its full access and a review id ([`src/review.ts`](src/review.ts)); `reviewChat(sessionId)` is one open chat's workspace. `setFullAccess({ workspace, reviewId, on, confirmed, chat })` records the person's answer (the Host cannot verify who set `confirmed`; it enforces the loopback arrival the routes check); turning full access on for a folder Delorun never adds as a workspace (a filesystem root, the home folder, the Delorun home, the stock home, or a folder containing one) is refused with `UNKNOWN_WORKSPACE`, as the CLI refuses it: on records the grant and the full-access preset and, with `chat`, the open chat the consent was asked from, switches that chat to full access so it stops asking; off withdraws the grant and sets every open chat of the workspace that runs with full access back to the safer preset, which appends that chat's `sandbox/mode` and `permission/preset` events; the other Hosts of the home read the change through their watch. It refuses with `FullAccessChangeError` and records nothing for `UNCONFIRMED` (no `confirmed: true`), `UNKNOWN_WORKSPACE`, `UNKNOWN_CHAT` (a `chat` that is not open in the workspace), `STALE_REVIEW` (the workspace's full access changed after the consent was shown) and `STORE_REFUSED`. Each change reads the store from disk first, so a change the CLI wrote is never undone, and logs one line without the folder's path.
- **Reading the store again.** `reload()` reads the store after `delorun workspace full-access` or another profile's Host wrote it, sets the open chats of a workspace that lost a grant any decision since they were last set read back to the safer preset, and answers the entries' digest with how many workspaces gained (`added`) and lost (`lost`) a grant. The store's watch calls it, and so does the home process for the update channel's `permission.reload` ([C19](../../docs/contracts/c19-home-process.md)), which no Delorun process sends.
- **Routes.** Where a Connection serves the studio, three exact routes under `/api` ([`src/wire.ts`](src/wire.ts), [`src/routes.ts`](src/routes.ts)): `GET /api/delorunPermission.workspaces`, `POST /api/delorunPermission.review` and `POST /api/delorunPermission.setFullAccess`. Each answers only a request that arrived on the loopback listener under a loopback `Host`; a reach device is refused with `403 LOOPBACK_REQUIRED` before the body is read ([C14](../../docs/contracts/c14-oidc-passkeys.md#tailnet-membership)), except that while dangerous mode holds an unlocked device is admitted ([`@delorun/home-auth`](../home-auth/README.md#dangerous-mode)). The studio's consent, the approval card's full-access action, its Permissions section and the `permissionSwitchConsent` question upstream's permission control asks live in [`@delorun/bundle-local`](../bundle-local/README.md#the-consent-surfaces).

## The network of sandboxed commands

Each workspace also has a network for the commands the model runs in the sandbox: `open`, the host's network as stock gives it; `allowlist`, only the hosts the person listed; or `off`, none. A workspace without its own setting has the row's default, `open` unless `network` says otherwise, so a fresh install behaves as stock. [`src/command-network.ts`](src/command-network.ts) is the `delorunCommandNetwork` service:

- It mounts the `sandboxNetwork` resolver of `@deepseek-ai/dsh-sandbox-policy`, so each confined command's policy carries `off`, or under `allowlist` the socket of the egress proxy for that list. `open` carries no network, which is upstream's policy unchanged, unless the workspace accepted the abstract-socket risk (below). The sandbox enforces `off` and `allowlist` under bwrap and refuses every command of such a workspace on Landlock, Seatbelt and Windows ([sandbox-local](../../../packages/sandbox/sandbox-local/README.md#network)).
- One [egress proxy](src/egress-proxy.ts) per distinct allowlist listens on a Unix socket under `secrets/permission-defaults/proxy/<pid>/` before any policy names it, and closes when no setting names its list, so a running command loses hosts its list no longer has. It serves `CONNECT host:port` and absolute `http://` requests; it refuses a host or port the list does not admit before any lookup, refuses a listed name that resolves to an address the fetch guard's matrix refuses, connects only to the addresses it checked, sends a plain-HTTP request with the `Host` of the URL it checked, answers each refusal with a sentence the command prints, and logs it. It holds at most `proxyMaxConnections` connections, refusing one more with `503`, and closes a connection idle for `proxyIdleTimeoutMs`. It does not read a tunnel's bytes, so it cannot check the name a TLS handshake or an inner request names. An entry is a host name of at least two labels, a `*.` name that matches every name below its domain but not the domain, or a public IP address; it admits ports 80 and 443, and one written `host:port` admits that port instead ([`src/network.ts`](src/network.ts)).
- A monotonic tool guard refuses `web_fetch` under `off`, and under `allowlist` for a URL whose host and port no entry admits; `web_fetch` follows same-origin redirects only, so the URL's host is every hop's.
- With `open`, a Linux runner refuses a command while a host abstract Unix socket (the display server, the session bus) listens, because the namespace is shared and no mount rule hides it; the check runs when the command starts, so a listener that starts later is not caught. A workspace accepts that risk with `acceptAbstractSockets` under `open`, set in Settings, Network (**Run commands even when desktop sockets are reachable**); the resolver then carries the sandbox's `host` network, the command runs and the sandbox reports partial enforcement. Accepting the risk loosens the network, so the change needs the person's confirmation like any other loosening; the setting is stored beside the access and is valid only with `open`. The row's `acceptAbstractSockets` gives a workspace without its own setting the same acceptance while `network` is `open`. Before a `bash` command the runner would refuse for this reason, `abstract-socket-consent.ts` asks the person once per workspace (`bash` and `pwsh`, only under the local sandbox provider, and only when the runners' own `refuseAbstractSockets` would refuse) through the composed approval service (`grants: 'full-access'`, so a Host keeps the answer at the home's own computer); an allow records the same acceptance through `acceptAbstractSockets()`, a decline or an `unavailable` answer (`delorun headless`) leaves the runner's refusal and is not asked again until restart, and a cancelled ask is asked again; an allow is not remembered, so after a revocation in Settings the next refusal asks again.
- [`src/network-store.ts`](src/network-store.ts) keeps the settings in `secrets/permission-defaults/network.json` at mode 0600, under the same refusal rule as the permission store. While a store that exists cannot be read, every workspace counts as `off` and no change is recorded.
- Two Fetch routes serve the studio's Network section: `GET /api/delorunNetwork.list` and `POST /api/delorunNetwork.set`. Both refuse with `LOOPBACK_REQUIRED` a request that did not arrive on the loopback listener under a loopback `Host`, before its body is read, through `@delorun/home-auth`'s `requireComputerUnlessDangerous` and `routedPathname`, so no spelling of a route passes the check; while dangerous mode holds, a reach device that holds an unlock passes it. A change that loosens the network, to a less restrictive access or with a host the old list did not admit, is refused with `NETWORK_UNCONFIRMED` until the request carries the person's confirmation; a tightening applies at once. The model has no tool that reaches the setting, and plugin management cannot reconfigure this row.

## Dangerous mode

With `fullAccessEverywhere` set and a valid grant file, `granted(cwd)` is true for every workspace, the guard admits a switch to full access and `select` records the workspace default without asking and without a grant time. `everywhere()` reports `{ on, grantedAt?, problem? }`, and the workspaces listing carries it. When the grant file is removed or the row turns it off, the store's watch reads the change within a second and open full-access chats in workspaces without their own grant go back to the safer preset.

Two routes serve it. `GET /api/delorunPermission.everywhere` reads the state and `POST /api/delorunPermission.everywhereOff` removes the grant file; the computer's own request and a reach device with a running unlock may call either, because reading and turning off only tighten, and every other device is refused before the body is read. A workspace's full access that an unlocked device turns on through `setFullAccess` while the mode holds is recorded in `device-grants.json` beside the store and withdrawn when the mode ends, at the next reload or at start: the workspace records the safer preset and its open full-access chats go back to it. While the mode is off such a grant never counts at a read, even when writing its withdrawal failed; the retry at the next reload only cleans the store. A grant the computer made, or one the workspace already held, stays. No route of this plugin turns the mode on: only `delorun setup` and the computer-only `POST /api/delorunRun.dangerousConfirm` of `@delorun/bundle-local` write the grant file, through `writeDangerousGrant` in `@delorun/plugin-permission-defaults/store`.

## Configuration

| Option | Default | What it does |
| --- | --- | --- |
| `enabled` | `false` | Delorun's C16 switch `permission_defaults`, off in the parity composition; on, the plugin seeds each new chat from its workspace, mounts the guard that refuses full access for a workspace nobody consented to, and gives each workspace's sandboxed commands its network. |
| `network` | `open` | The network of a workspace without its own setting: `open`, `allowlist` or `off`. |
| `acceptAbstractSockets` | `false` | While `network` is `open`, whether a workspace without its own setting accepts that host abstract Unix sockets stay reachable to its commands. `false` refuses a command while such a socket listens. |
| `allowedHosts` | `[]` | The list of a workspace without its own setting, used under `allowlist`; an invalid entry fails the load. |
| `proxyConnectTimeoutMs` | `30000` | How long the egress proxy waits for a connection to a listed host to open. |
| `proxyMaxConnections` | `256` | The most connections one allowlist's egress proxy holds at once; one more is refused with `503`. |
| `proxyIdleTimeoutMs` | `300000` | How long a connection through the egress proxy may carry no byte either way before the proxy closes it. |
| `fullAccessEverywhere` | `false` | Dangerous mode, written only by `delorun setup`'s third prompts answer. True makes full access available to every chat, with no workspace consent and no dialog, but only while the grant file `secrets/permission-defaults/full-access-everywhere.json` is also present and valid (mode 0600, no symbolic link, `{ v: 1, grantedAt, warning: 1 }`); either half missing leaves each workspace's own consent in force and names a refused file in the store problem. A device's settings write and the plugin manager cannot set it. |

## Tests

`tests/watch.spec.ts` covers the watch: one report per burst of changes to the store's file, none for its lock and temporary files, a change that names no file, a failed watch closed and reported once, and a pending change dropped on close. `tests/store.spec.ts` covers the store's path, its format's round trip, the refusals that make a store count for nothing (a laxer mode, a symbolic link, another format), the entry lookups, and the workspace key that makes one directory one workspace. `tests/permission-defaults.spec.ts` covers the switch off, the seed a new workspace gets, the consent asked once per folder, the refusal that records nothing, the mode switch the guard refuses, the workspace that already holds a grant, and a full-access selection after another process withdrew the grant, which asks again, or records nothing when the withdrawal lands after the selection read the store. `tests/surfaces.spec.ts` covers the surfaces' calls and routes: the workspaces listed, a grant that lets the switch through and switches the chat the consent was asked from, and only that chat, to full access, a withdrawal that sets open chats back, a store the CLI wrote kept and read again, a withdrawal by another Host, by a chat's return to the safer preset or by the CLI's locked write that sets a second Host's open full-access chats back within a second without a decision there and without reading any profile's token, a watch that cannot start, which is logged and leaves the decision-time read, and a reread that fails, which is logged, and the denial cases — a reach device, an unconfirmed answer, a stale review and a chat that is not open in the workspace record nothing. `tests/network.spec.ts` covers allowlist entries, host matching, which changes loosen, and the network store; `tests/egress-proxy.spec.ts` runs the proxy on a real socket with documentation addresses mapped to local listeners; `tests/command-network.spec.ts` mounts the service and covers the resolver, the store, confirmations, the refused store, the `web_fetch` guard and the routes; and `tests/egress.integration.spec.ts` runs confined commands under a real bwrap through the whole chain, skipping where bwrap is unusable.

## When a service fails

If the permission or network service fails to start while `enabled` is on, the row fails to start and mounts, on the root context, a resolver that gives every confined command no network and, once the failed row's own services are removed, a guard that refuses `danger-full-access` whenever the real guard is missing, whichever service failed. The booted-Host check of the CLI reports each such stand-in as an unhealthy row. The log names the row and the failure; the answers are removed when the row starts again. With `enabled` off the row mounts nothing and commands share the host's network, as stock.

The stand-ins also mount when the row refuses its own configuration (an invalid `allowedHosts` entry, or a proxy limit of 0, which has no meaning), including on a hot reload, which does not run the boot check. A row whose plugin never loads leaves the seams absent while the Host runs; the boot check at `delorun start` is the only cover for that case.
