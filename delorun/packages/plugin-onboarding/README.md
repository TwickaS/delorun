# @delorun/plugin-onboarding

English | [中文](README.zh.md)

## Summary

The studio's first minute is one dialog that ends in a chat. On the first open it has three steps, Welcome, Models and Ready, with Workspace only where there is no default workspace for the first chat and the PIN step only where phone access is set up and PIN mode is off; the guide opened again from Settings → General → Getting started has every step, described next. Welcome sets the language and shows the preview notice. Models connects the model providers: cards to tick, a walk through each ticked provider and a summary. Look sets the colour scheme, theme and accent beside a small chat in that look. Agents offers Claude Code and Codex with their sign-in on this computer and asks the person to confirm what adding one means. Recommended plugins offers the configured plugins, those that fit the person's connections first. Phone access shows how far Tailscale is from serving the studio, while reach is off. Workspace chooses the default workspace or opens the new-workspace dialog, which adds a folder on this computer, makes a new one or clones a repository from Git. Ready lists what the guide set and opens the first chat; Ready itself offers three ideas to try, each with a Copy button. On a first open Ready lists only the model and the workspace, then says that Look, agents, plugins and phone access are in Settings and that Settings → General → Getting started opens the full guide. Every step sits in one frame: the step's name and "Step n of N" with a progress bar, where N counts only the steps this person will see (Phone access is left out on a phone and once it is set up, and a step the terminal setup covered is left out) stay at the top, the body scrolls, and Skip, Back and Continue stay at the bottom, the same at every width; the last step has no Skip. Cards (icon slot, title, one-line summary with More, Add, Adding… with a thin bar of the download, or ✓ Added) and full-width state lines under them are shared by Models, Agents and Recommended plugins. While a package downloads, a muted line under its card gives the speed and, once the size is known, the time left, measured the way the terminal's install display measures them; the line keeps its height until the speed is known and is blank while the download stands still. Onboarding leaves out what the terminal setup already covered, shows again from Settings → General → Getting started, and loads only while the Delorun look is on.

## The Browser page in Settings

The studio half also registers the `delorun-browser` `settings.section` (order 17, right after the plugin downloads section; [`src/client/browser/BrowserSettings.tsx`](src/client/browser/BrowserSettings.tsx)), served with the rest of this plugin's registrations. The page reads and writes the home's choice through the same hook as the guide's Browser step ([`src/client/browser/use-browser.ts`](src/client/browser/use-browser.ts), the rule and the states in [`@delorun/browser-setup`](../browser-setup/README.md#the-homes-choice-and-the-pages-states)).

- **Built-in browser.** A switch, then the status in plain words: off, checking, adding, slow, restart needed, ready, needs setup with the Host's reason, or a failure (offline, not available here, the plugin manager's own words, an unreadable check or declaration) with Try again. Only a new home (setup not finished) that never chose adds the pack when the page opens, and it records `on`; an existing home that never chose and has no pack shows Off and adds nothing until the person switches it on, and a home that chose off is never added to. On adds the pack, or switches back on a pack Plugins turned off. Off turns the pack off through the plugin manager and records `off`; the pack stays downloaded. While `on` is recorded, a pack that is removed or turned off in Plugins is recorded as `off` the next time the page or the step opens. While `off` is recorded, the page notes whether the pack reads disabled or enabled (`browserPack`); a pack seen enabled after it was seen disabled was switched on again in Plugins and is recorded as `on`, while a pack that stays enabled because its turn-off waits for a restart is never seen disabled and stays off.
- **Download.** While the unmet need is the Chromium build, the page offers **Download the browser**, which asks the Host to run the Browser pack's own installer, with the command shown for a terminal. A need that is Google Chrome shows its command only.
- **Test browser.** While Browser is ready, the button asks the Host to open a fixed page in the built-in browser and shows its thumbnail; no model turn runs. The Host routes are [`@delorun/bundle-local`'s](../bundle-local/README.md#the-browser-page-routes) and answer the home's own computer only; a phone sees where to run the test.
- **Your own Chrome.** Where the `@delorun/bundle-real-browser` pack stands: **Add your Chrome** while it can be added, then whether the browse extension is paired, with **Finish in Plugins** for the pairing steps and the approval that each chat asks for.
- **Phones.** A studio opened from a phone cannot add packs or turn them off, so the switch, the download and the test are held and the page says where to change Browser.

The first chat that uses Browser still asks once to allow the browser tool; the page does not allow it, because no review exists until a chat starts the server.

## Contract

- **Stock look.** The studio half injects `delorunStudio` inside `apply` (`ctx.inject(['delorunStudio'], applyStudio)`), so its entry stays active under the stock look, which upstream's web boot requires of every entry. `@delorun/plugin-theme` provides that service only while the Delorun look is on, so without it the plugin registers nothing and provides no service. `settingsShell`, upstream's Settings shell, is not injected: Run setup again looks it up with `ctx.get('settingsShell')` when pressed, so the entry also stays active where a plugin turns upstream's general Settings (`ui-settings-general`) off and draws its own Settings, as DS Bot does. Without the shell, Run setup again only marks the guide unfinished, and it shows at the next reload.
- **The onboarding step** is a `settings.onboarding` entry with the id `delorun-onboarding` at order -200, before `delorun-notice` (-100) from `@delorun/bundle-local` and upstream's DeepSeek key step `deepseek-official`. It registers only while the host serves the row `delorun-onboarding`. With `done` set and no `explicit` flag it calls `complete()` at once, and so does a row that cannot be read. The Models step saves keys through the studio's own remote credential and settings namespaces, as Settings → Models does. Start a chat also calls `completeStep('deepseek-official')`, because the Models step offered the same providers. `@delorun/bundle-studio` sets `credentialOnboarding: false` on `ui-settings-models`, so upstream's key step never opens, also after Skip or a reload. The dialog owns the page's inert root while it shows, takes focus to the step's heading at each step and is closed only by its buttons. When it closes, focus moves to the message box (on a phone or tablet, to the message box's card, so the keyboard stays down), or else to the page's first control.
- **Progress** is the row's volatile configuration: `done`, and `step` (the id of the step reached, which resumes the flow). Run setup again writes `done: false` and an empty `step` before it asks the Settings shell, where one exists, to open the step. A write that fails is logged and the flow goes on.
- **Look** writes only the theme row's `palette` and `accent` through `ctx.configForms`, and the colour scheme through upstream's theme service. Choosing Stock calls `ctx.delorunStudio.useStockLook()`, which unloads this plugin. Palette and accent labels come from `@delorun/plugin-theme`'s dictionary `settings.delorunAppearance`, and the preview colours in [`src/client/previews.ts`](src/client/previews.ts) are copies that a test compares with the theme's own.
- **Bundled rows** <a id="bundled-rows"></a>are read with `listBundles` and `listPlugins`, which find the row by its id and its live entry. Turn on calls the plugin manager's `setPluginEnabled` for that entry, the call the Plugins page makes, so its checks apply to this button too: protected and unaddressable rows are refused, and the profile's own patch records the change, never this plugin. `applied` shows On with no restart, `restart-required` says Delorun needs one, and anything else, a row no bundle declares or one that cannot be changed shows a failure or Not included in this installation, with a button that opens Plugins.
- **Deferred steps** <a id="deferred-steps"></a>are the steps only the home's own computer can do, which a phone defers with **Do it on my computer**. They are kept in `onboarding-deferred.json` in the profile's directory (`{ "version": 1, "deferred": [...] }`, at most three ids from the closed list, mode 0600, replaced whole through a temporary file and a rename, writes applied one after another), not in the browser, and served as `deferred` on the setup record. A missing, oversized or unusable file reads as none, with a warning that does not quote it. On a phone the PIN step says it is done on the computer and why, and is left out when it was already deferred or PIN mode is on. At the computer, the `sidebar.footer.action` entry **Finish setup** (the way back into the guide while it is unfinished, and the only such entry: there is no chip above the message box) reads **Finish setup · N left** once the guide is finished and counts the deferred steps that have a screen (`reach`, `pin`), clears a step whose work is done (reach is set up, PIN mode is on) when it reads, opens the guide with only those steps through the Settings shell, and is absent at zero or away from the computer. That guide saves no place, starts no chat and closes after its last step.
- **Agents and plugins** use the plugin manager's remote namespace, read from the store as the `remote.pluginManager` service. `listBundles` only reads. A bundle the installation ships is switched on with `setBundleEnabled`; a catalogue entry is installed from its `installTarget` with `installBundle` and then enabled. `applied` shows Added, `restart-required` shows that Delorun needs a restart, and anything else, or a plugin manager that cannot be asked, shows a failure line under the card with Try again. A catalogue entry with no install target, or with an error beside its target, shows Not included in this installation. Nothing installs without a press.
- **Routes.** The harness half requires `connection` and serves these exact routes ([`src/wire.ts`](src/wire.ts)), each answering JSON uncached. The studio parses every answer strictly and shows an honest state for a route it cannot read. Every route answers the home's own computer. A paired device reaches the routes `@delorun/home-auth`'s route table lists for it: the reading routes and `deferStep` once it is approved, `keyTest` once it is approved and, under PIN mode, unlocked, and `agentModels` only while it holds an unlock (`ELEVATION_REQUIRED` otherwise); any other arrival is refused before the route. Adding a folder and cloning are `@delorun/plugin-new-workspace`'s routes, which the Workspace step calls.

  | Route | Answers |
  | --- | --- |
  | `GET /api/delorunOnboarding.setupRecord` | `{ sections?, reachSetUp, deferred? }`: the terminal setup record, and the steps a phone deferred to the computer (see [Deferred steps](#deferred-steps)). |
  | `POST /api/delorunOnboarding.deferStep` | Body `{ id, deferred }` with `id` one of `reach`, `pin` or `approve`. Defers or clears one step and answers `{ deferred }`, every step deferred now. A paired device may call it without an unlock, because it records a note and changes no setting. Any other id is refused with 400. |
  | `GET /api/delorunOnboarding.start` | `{ startId }`: a random id of this start of Delorun, kept only in memory. |
  | `GET /api/delorunOnboarding.readiness` | Claude Code's and Codex's sign-in (`found`, `missing` or `unknown`) and Tailscale's state with this computer's DNS name. |
  | `GET /api/delorunOnboarding.workspaceNotice` | The names of the files the workspace registry set records aside into when it started, oldest first (at most 64); empty when none. |
  | `POST /api/delorunOnboarding.keyTest` | Each model provider route's name and result: `works`, `rejected`, `unreachable`, `no-key` (no credential configured), `untested` (a credential or none needed, but no model listing) or `failed`. |
  | `POST /api/delorunOnboarding.recommend` | Each configured plugin's declared connections, where they were read, and whether the registry was reached. |
  | `GET /api/delorunOnboarding.localModels` | `{ servers }`: each local model server the step recognises (Ollama, LM Studio) that answered its model listing on its loopback address, with its address and models. |
  | `POST /api/delorunOnboarding.agentModels` | Body `{ agent }` with `claude-code` or `codex`: `listed` with the models that installed agent offers, from its own process, or `unavailable` with `not-running`, `timeout` or `failed`. |

- **The setup record** is read from `setup-answers.json` in the CLI profile's directory (`ctx.profileContext.dir`), which `delorun setup` writes and onboarding never writes. `reachSetUp` is true when `reach.option` is a non-empty string other than `none`; `sections` lists the section ids whose status is `seen` or `answered` (at most 32, each up to 40 characters). Only these fields are read; a file over 64 KiB, one that is not a regular file, or one that is missing, unreadable or invalid answers `{ reachSetUp: false }`, so every step shows. A reason is logged without quoting the file. A section named `look`, `agents` or `plugins` leaves that step out; Welcome, Workspace and Ready are never left out.
- **Readiness** only reads. The sign-in check tests whether `~/.claude/.credentials.json` or Codex's `auth.json` (in `CODEX_HOME`, else `~/.codex`) exists and never opens it (Claude Code's file is in `CLAUDE_CONFIG_DIR` when that is set); on macOS, where Claude Code keeps its sign-in in the keychain, a found `~/.claude.json` answers `unknown`. The Tailscale check runs `tailscale version`, `tailscale status --json` and `tailscale serve status --json` through `@delorun/reach`'s runner, and no command that changes anything.
- **The key test** asks each provider route for its model listing, never a completion, so it spends no tokens. A route that needs a key and has no configured credential reads `no-key` before any listing is tried: its settings profile's `apiKeyEnv` reference must name one that the credentials service describes as configured, and a route the configurable directory does not list has none. A route needs a key when its profile names a reference or the adapter reports environment variables its authentication reads; a keyless route, such as a local model server, goes straight to discovery. A route whose adapter registered a model discovery is asked through upstream's `llm.discoverModels`, which uses the stored key inside the harness; the official DeepSeek route is asked through `@deepseek-ai/dsh-llm-deepseek`'s listing request with the key its credential reference resolves to. Each route has `keyTestTimeoutMs`. The answer names each route and its result, never a key, an address or a provider's message. A listing answered with a success status and a body that is not a model list, such as a captive portal's page, reads as Could not test this key, never as working.
- **Recommendations** read each configured package's `package.json` `delorun.connections` (see [Connections](#connections)) from the installed package; a package that is not installed is read from `registry` only when the request says `registry: true`, within `registryTimeoutMs`, and is `unknown` otherwise. The registry request is this route's only network request.
- **Key status.** The plugin provides `ctx.modelKeyStatus` (declared by `ui-settings-models`): the latest free key-test result per model route, kept in memory and never the key. The guide's Models card, the no-key banner and Settings → Models read it, so one key shows one state everywhere.
- **No-key banner.** An entry in `conversation.input.dock` (id `delorun-onboarding.key-banner`, order 5) shows "Add a model key to start chatting" with a button that opens Settings → Models (`ctx.settingsShell.openSection('models')`) while the key test finds no provider that works or might: every route is `no-key` or `rejected`, or there is none. A route that works, is unreachable, failed or is `untested` (it has a credential, or needs none as a local model server does, and its models cannot be listed), and a key test that cannot be read, show nothing. The banner asks once when the box mounts and every 5 seconds while it shows, so it leaves once a key is added; it never opens a dialog. It registers only while the Delorun look is on.
- **Set-aside notice.** An entry in `conversation.input.dock` (id `delorun-onboarding.set-aside`, order 6) shows "Some workspace records could not be read and were set aside: <files>. Run delorun doctor for details." with a Dismiss button when the workspace registry started with records set aside. It reads `GET /api/delorunOnboarding.workspaceNotice` once when the box mounts, which lists the set-aside file names (not paths) from the registry's `quarantined`; nothing is shown for an empty list or an unreadable answer. Dismissing hides it until the studio is loaded again. It registers only while the Delorun look is on.
- **`rename_workspace` row.** A keyed `tool.call.toolview` entry draws `@delorun/plugin-workspaces`' tool call as the old name, an arrow and the new name, taken from the result's persisted `from` and `to`, or as the refusal in the agent's words. It registers whenever the plugin loads while the Delorun look is on, and falls back to the generic row elsewhere.
- **First chat.** When the dialog opens it calls `ctx.workspaces.initializeDefault()` once, which the host answers with the existing default workspace and creates one only while it holds no workspace and no chat. Start a chat calls `ctx.uiWorkspace.openWorkspace` with the chosen workspace. Where the lookup resolves nothing and other workspaces exist and the person chose none, the workspace UI's own New Session applies. Without `ctx.uiWorkspace`, New Session applies. While the dialog shows it holds the workspace UI's `defaultWorkspaceFailed` notice through `ctx.uiWorkspace.holdDefaultWorkspaceNotice()`; when it closes the notice is dropped if Workspace said there is no default workspace, and shows otherwise.
- **`ctx.delorunOnboarding.registerStep(step)`** adds an `OnboardingStep` (`id`, `order` 600 to 999, `title`, `component` taking `next`) and returns its disposer; a step with an earlier step's id replaces it.
- **Copy** is in English and Chinese ([`src/client/locales.ts`](src/client/locales.ts)) under the namespace `delorunOnboarding`; another studio language falls back to English. The Plugins page names the plugin from [`locale/`](locale/en.json). CSS uses theme tokens only. Below 768 px the dialog is the whole window, the list of steps becomes a count with a bar, and the footer stays at the bottom; rows grow to 44 px for a coarse pointer.

## Connections

A plugin says which of a person's connections it is for in its own `package.json`, and the Recommended plugins step reads that field and nothing else:

```json
{
  "name": "@scope/codex-quota",
  "delorun": { "connections": ["agent:codex"] }
}
```

An id is `provider:<id>` for a model provider route as Settings → Models lists it (such as `provider:deepseek-official`), `agent:claude-code` or `agent:codex` for a coding agent signed in on this computer, or `tool:tailscale` once Tailscale is installed; at most 16 per package. A package that declares none fits any setup. The repository's package-state gate accepts the field on a Delorun package.

## Configuration

The row `delorun-onboarding` has these fields ([`src/config.ts`](src/config.ts)), validated when the configuration loads. The first seven are volatile and change while the studio runs.

| Field | Default | Meaning |
| --- | --- | --- |
| `done` | `false` | Whether the person finished or skipped onboarding. |
| `step` | empty | The id of the step reached. |
| `browser` | empty | What the person chose for Browser, in Settings or in the guide: `on` or `off`. Empty while they never chose: a new home then adds the pack, and an existing home shows Browser off. A home that turned the pack off in Plugins reads as off too. |
| `browserPack` | empty | While `browser` is `off`: whether the Browser pack was last seen `enabled` or `disabled` (turned off or removed). A pack seen enabled after `disabled` was switched on again in Plugins. Each recorded choice clears it. |
| `pausedStart` | empty | The start of Delorun in which the person pressed Finish later, from `GET /api/delorunOnboarding.start`. The guide stays closed while it names the current start, in any tab or after a reload, and the next start shows it again. Opening the guide again from the sidebar footer's Finish setup entry clears it. |
| `plugins` | empty | Up to twelve npm package names the Recommended plugins step offers. With none, and no `optionalRows`, the step is left out. |
| `optionalRows` | empty | Up to twelve row ids, such as `delorun-cost-meter`, of rows a bundle inserts disabled; the step offers to turn each on. Each must be a row of the profile, or the plugin stops at load with an error that names it. |
| `registry` | `https://registry.npmjs.org` | The `https://` npm registry a package that is not installed is read from, only when the person asks. |
| `registryTimeoutMs` | `10000` | The most time the registry requests may take together, 1000 to 60000. |
| `keyTestTimeoutMs` | `15000` | The most time one provider's key test may take, 1000 to 60000. |
| `hiddenProviders` | `[]` | Model provider route ids the key test and the guide's provider list leave out. The routes stay mounted. |

[`@delorun/bundle-studio`](../bundle-studio/README.md) sets `plugins` to five experimental plugins that ship with DeepSeek Harness: session search, the terminal bundle, the worktree tool, session titles and the DeepSeek website chat import (an optional bundle, off until turned on), and `optionalRows` to the Thinking tab (`delorun-thinking-rsvp`) and the cost meter (`delorun-cost-meter`).

## Limits

- **Delegation consent.** Adding Claude Code or Codex asks for the two presses on its card. Later, an agent that starts from a chat is subject to Delorun's own delegation consent, which the Agents step describes: Delorun asks on this computer first unless the person allowed it for that workspace, a phone cannot answer, read-only chats never start one, and a run stays in the chat's workspace and stops after 30 minutes. This plugin does not implement that consent; the step's copy has to follow it.
- **Key results.** Upstream's pi-ai discovery reports a refused key and an unreachable endpoint with the same code, so such a route shows Could not test this key for either, where the official DeepSeek route tells The provider rejected this key from Could not reach the provider.
- **Connections.** No shipped plugin declares connections, so every seeded plugin fits any setup. No Codex quota or Command Code plugin was found to recommend.
