# Delorun tools

English | [中文](README.zh.md)

`@delorun/tools` is Delorun's fork tooling, a private package in `delorun/apps/tools`.
It holds the divergence-ledger checker, which keeps every difference between this tree and its pinned upstream commit recorded, and the count of that difference.
It also holds the gates that check each change, the commit standard, and the list of the workflows this repository keeps and removes.
The check runner, [`src/run-checks.ts`](src/run-checks.ts), orders and runs those gates and the other local checks described below; the stand-in stack serves the reach and sign-in tests, and the repository holds no other fork tools.

## Modules

- `src/fork-boundary.ts` holds the ledger schema, the upstream source predicate, the matchers for fork-owned paths and path rules, the entry and rule errors, the boundary errors and the divergence total.
- `src/check-fork-boundary.ts` is the command-line gate. It reads the ledger, checks the repository against it, prints each path rule's coverage, and prints the count with `--count`.
- `src/ledger-record.ts` writes the ledger: stub entries, removals of entries that no longer differ, and security digests, as the divergence ledger section below describes.
- `src/ledger-digests.ts` computes and compares the digests of security entries.
- `src/demo-home.ts` builds the demonstration home that the pictures are taken from, as the demonstration home section below describes.
- `src/fresh-home-smoke.ts` starts the shipped studio from a fresh scratch home on a port in 18600–18619 and fails when it does not listen, its log reports a start-up failure, or the onboarding setup record does not answer. Run it after `pnpm run build:artifacts` and a build of the `delorun/packages`, and after every merge into an integration branch.
- `src/ledger-merge.ts` is git's merge driver for the ledger. It merges the entries by path and the rules by pattern, and the rules are in the divergence ledger section below.

- `src/checks/types.ts` and `src/checks/gates/index.ts` describe each gate as one command that the check runner executes.
- `src/checks/gates/` holds the gate modules and their data: licence, package states, secrets, personal data, infrastructure, DCO, documentation times and the documentation checks.
- `src/check-jsdoc.ts` applies upstream's JSDoc rules to every `src` tree under `delorun/`.
- `src/check-docs-site.ts` launches the documentation website's build, which includes its dead-link check, and refuses to run until the site's dependencies are installed.
- `src/run-checks.ts` is the check runner: the tiers, the selection, the report.
- `src/with-slots.ts` runs an ad-hoc heavy command inside the machine-wide slot budget the runner's runs share.
- `src/coverage.ts` measures the coverage of named specs or packages inside the slot budget, into a report directory of its own, and lists every file in scope with its four measures, fully covered files included: `node_modules/.bin/tsx delorun/apps/tools/src/coverage.ts [--include <glob>]... <spec file or package directory>...`; by default the files in scope are the `src` files of the packages the paths lie in, and it exits 1 when one is below 100 %.
- `src/batch/` is the integrator's batch tool, which lands several lanes through one merge-tier gate and reports each failure to the lane that caused it.
- `src/checks/` holds the check catalogue (`plan.ts`), the scheduler (`run.ts`), the machine budget (`machine.ts`), the pass cache (`cache.ts`), the machine-wide pass store (`shared-cache.ts`) with the rules for which passes it serves (`sharing.ts`), and the budgets (`budgets.json`).
- `src/pairing-staged.ts` is the pre-commit and pre-merge-commit bilingual-pairing check. It runs upstream's `verify-translation-pairing.ts --cached` on the staged records and on the same pairs as `HEAD` holds them (a staged rename is followed to the old path), and fails only for a violation `HEAD` did not have. Drift that already exists prints as a short "existing drift, not blocking" list; a new record is checked strictly. `delorun/lefthook.yml` overrides upstream's job of the same name to run it.
- `src/setup-worktree.ts` sets up a checkout or worktree in one command: the hooks file (written when missing; an existing one that does not extend `delorun/lefthook.yml` is refused), the install, the documentation site's own install, the hooks, the ledger merge driver and a warning when Node differs from `.nvmrc`. The check runner refuses to run a gate on any other Node major; only the pre-commit tier and the read-only listings run anyway.
- `src/build-web.ts` builds the web studio's client with Delorun's product name: `DSH_CLIENT_TITLE` set to `Delorun` unless the caller sets it, through upstream's `build:web` and a rebuild of `@deepseek-ai/dsh-client-ui-layout`'s client bundle, which embeds the title. The release closure sets the same variable.
- `src/network-log.mjs` is a Node preload for network fixtures: with `NODE_OPTIONS="--import <path>"` and `DELORUN_NETWORK_LOG` set, it appends the host and port of every TCP connection the process and its children open to that file.
- `src/git.ts` runs git for the modules and reports exit statuses.
- `src/parity/composition/` holds contract C16's parity overlay, the `parity-switches` check (`check-parity-switches.ts`, with `switches.ts`, `contributions.ts`, `overlay.ts` and `sweep.ts`) and the staged switch-on scenarios; the parity composition section below describes them.
- `src/issues/` turns maintainer-written work briefs into GitHub issues: `brief.ts` holds the fields, the rules and the issue body, `references.ts` the links and paths a brief may carry, `labels.ts` the label file, `gh.ts` the `gh` calls, and `issues.ts` the command line.

## The divergence ledger

[`delorun/upstream-patches.json`](../../upstream-patches.json) records how this tree differs from upstream; the [divergence index](../../docs/reference/parity-with-deepseek-harness/divergence/README.md) defines upstream source, the path rules, the classes and the feature ids.
`upstream.commit` pins the upstream commit that the differences are measured against.
`forkOwned` lists paths and globs that Delorun owns outright. `*` matches within one path segment and `**` across segments. An entry covers the paths it matches and every path below a matching directory.
`rules` lists path rules, each with a `pattern`, a `kind` and a `reason`. A rule covers the differing paths its glob matches that are not upstream source; only an exact `generated` rule may name a source file, and no rule covers a path under `vendor/`. Patterns are matched whole and case-sensitively by `path.posix.matchesGlob`, whose `*` and `**` do not match a segment that starts with `.`.
`patches` lists each upstream path that needs an entry, with its `class` (`delorun-feature`, `generic-fix` or `security`) and a `reason`. A `security` entry records the `sha256` of its file; any other entry names its `feature` and records no digest. A `security` entry may also list `nonModelVisibleHunks`, each a `sha256` of one hunk of the file's zero-context diff against the pinned commit and a one-line `reason`: hunks the lead reviewed as not model-visible although they touch a statement that registers a model-visible contribution, which `parity-switches` then passes (see [What `parity-switches` detects](#what-parity-switches-detects)).
`retired` lists entries whose change upstream absorbed. Each names the upstream commit that absorbed it and the hunks it had.

The checker fails when:

- the ledger does not parse, or a patch lacks its class or reason;
- a reason or feature is `TODO`, a feature is not a kebab-case id, a security entry records no digest or names a feature, or another entry records a digest or `nonModelVisibleHunks` or names no feature;
- `nonModelVisibleHunks` is empty, or a record's digest is not a SHA-256 or its reason is not one line that holds a non-space character;
- a rule is a bare `**`, repeats a pattern, has no reason, or matches a source path in the tree or one of the checker's source probes that it may not cover, naming the pattern and that path;
- a non-security entry names a path that a rule also covers;
- the pinned commit is not in the clone or is not an ancestor of HEAD;
- an absorbing commit is not in the history of the pinned commit;
- an upstream path differs from the pinned commit and is neither fork-owned, listed nor covered by a rule, which an upstream source file never is;
- a source file that a `generated` rule covers does not hold `Generated by scripts/` in its first five lines;
- a listed patch no longer differs from the pinned commit;
- a retired entry still differs from the pinned commit;
- a security entry's recorded digest differs from its file at HEAD;
- a fork-owned tree holds a compiled twin of a TypeScript source.

It prints how many differing paths each rule covers, and a warning line for a rule that covers none; such a rule does not fail the check. `--count` prints the listed entries and their hunks, and the rule-covered paths and their hunks. A hunk is one `@@` header of `git diff --unified=0` against the pinned commit. Only tracked files count: a new file joins once it is added to the index. Retired entries are credited and listed separately; they are not part of the count.

[`src/ledger-record.ts`](src/ledger-record.ts) writes the ledger, so no person or agent writes entries or digests by hand:

```sh
node_modules/.bin/tsx delorun/apps/tools/src/ledger-record.ts [--check]
node_modules/.bin/tsx delorun/apps/tools/src/ledger-record.ts --non-model-visible-hunk <path>:<line> --reason "<one line>"
```

It compares the working tree with the pinned commit. It adds a stub entry, class `delorun-feature` with `TODO` as its feature and reason, for each differing path that neither an entry nor a rule covers; removes each entry whose path no longer differs; and re-records the digest of each security entry whose file changed, printing the old and new digest. It exits 3 when it re-recorded a security digest, because the changed file needs the lead's re-review, 1 when a security entry holds no file to digest, and 2 for a bad command line or an unusable ledger. `--check` changes nothing and exits 1 when a run would change the ledger. Agents run only `--check`; the lead runs the writing form when merging a lane, fills each stub's class, feature and reason, and writes the path rules.

`--non-model-visible-hunk` makes the same run and also adds one record to the path's security entry's `nonModelVisibleHunks`: the digest of the hunk the working tree's file has at the line, with the reason. The line is one the hunk adds or, for a deletion-only hunk, the line before the deletion. It exits 3 after writing, because the entry's verdict now covers the record and needs the lead's review. It exits 2 and writes nothing when the path has no security entry, the pinned commit lacks the file, no hunk is read at the line, the hunk touches no top-level statement that registers a model-visible contribution, every hunk with that digest already has its record, or the reason is empty, blank or spans lines.

[`src/ledger-merge.ts`](src/ledger-merge.ts) is git's merge driver for the ledger, and [`.gitattributes`](../../../.gitattributes) routes `delorun/upstream-patches.json` to it. Each clone configures the driver once, and every worktree of that clone shares the setting:

```sh
git config merge.delorun-ledger.driver 'node_modules/.bin/tsx delorun/apps/tools/src/ledger-merge.ts %O %A %B'
```

Without the setting, git merges the ledger as text. With it, the driver merges entries by `path` and rules by `pattern`. An entry or rule that one side changed takes that side's version, and so does one that one side removed while the other side left it alone. An entry or rule that both sides added or changed identically is kept once, so the rules are the union of both sides by pattern. An entry without `sha256` merges as any other. `forkOwned` is the ordered union of both sides, `upstream` must match on both sides, and `$schema` merges as one entry does. An entry or rule that the sides changed differently stays in conflict, including one that one side removed while the other changed it and one pattern that both sides added with different kinds or reasons: the driver wraps only those elements in conflict markers, names each on standard error, and exits 1. It also exits 1, after writing the merge, when the result fails the ledger parser or the entry rules. `forkOwned` keeps an entry while either side still lists it, so an entry leaves the ledger only when both sides have removed it.

## The rehearsal merge

[`src/rehearse-upstream.ts`](src/rehearse-upstream.ts) rehearses the merge of an upstream commit and holds the result to the [divergence budget](../../docs/reference/parity-with-deepseek-harness/divergence/README.md#divergence-budget). Run it from the repository root with exactly one of `--tag` and `--ref`:

```sh
node_modules/.bin/tsx delorun/apps/tools/src/rehearse-upstream.ts --tag <tag>
node_modules/.bin/tsx delorun/apps/tools/src/rehearse-upstream.ts --ref <ref>
```

It reads the ledger at `HEAD` and adds a scratch worktree in a temporary directory, detached at `HEAD`. `--tag` fetches the tag from the ledger's `upstream.repository`; the fetch writes only the scratch worktree's `FETCH_HEAD`. `--ref` takes a commit or branch the clone already holds, such as `upstream/master`, and fetches nothing. In the scratch worktree it merges that commit without committing, with hooks and recorded resolutions off, and it removes the scratch worktree whatever the outcome. The checkout's refs, branches, index and working tree stay unchanged, and its uncommitted changes are not measured.

It prints the conflicted paths with their class and conflict regions, and the conflicted hunks as a share of the ledger's hunks at the merged commit. It then prints, for each class (`delorun-feature`, `generic-fix`, `security`, `ruled`, `unlisted`), the entries and hunks measured against the pin and against the merged commit with their growth, and the total beside the caps. A differing path that no entry lists is counted as `ruled` when a path rule covers it, so the growth of rule-covered paths is measured too, and as `unlisted` otherwise. A conflicted file is measured with its conflict markers, so a conflict region usually counts as two hunks at the merged commit. An entry that differs from the pin but not from the merged commit is absorbed: it is listed as credited, and the count at the merged commit leaves it out. While no release baseline is recorded, the caps are the budget's floors, 20 entries and 150 hunks. Generated paths are counted under `ruled`, and the output says so.

It exits 1, with one line per failure, when the total growth in entries or in hunks exceeds its cap, when the conflicted hunks exceed 15 % of the ledger's hunks at the merged commit, and for each conflicted `security`-class file, because the ledger records no maintainer decision. It exits 2 with a usage line unless exactly one non-empty `--tag` or `--ref` is given, when the ref names no commit in the clone, and with git's error when the fetch or the merge fails.

## The gates

[`src/checks/gates/index.ts`](src/checks/gates/index.ts) lists each gate as a command that the runner executes from the repository root. A gate passes when its command exits 0. A staged gate accepts paths as trailing arguments, which the runner appends at pre-commit. A range gate compares the commits from `origin/main` to HEAD unless it is given `--base <rev>`, and leaves out the commits that the upstream commit pinned in `delorun/upstream-patches.json` reaches, because upstream signs and words its own commits. `DELORUN_RANGE_BASE=<rev>` replaces `origin/main` as the base of every range gate and of the tree pass record, for a clone whose `origin/main` is an old branch and for the first push to an empty repository. A base that names no commit stops the run before any check starts, and the run header names an override. A gate runs in every gate tier unless it names a lighter one: `gates:docs` and the upstream gates that take more than about ten seconds skip the lane tier, and the upstream gates that take more than about a minute, build a site or read upstream's built output run in the merge tier only ([local checks](#local-checks)).

### Gate debt

[`src/checks/gates/debt.json`](src/checks/gates/debt.json) lists the gates that fail on `main`, each with a one-line reason; [`src/checks/gates/debt.ts`](src/checks/gates/debt.ts) reads it. The runner runs a listed gate through `debt.ts`, which runs the gate's own command in its usual tier: a failure prints the gate's findings and `reported, not failing`, and passes; a pass fails the run with `passes, so remove its entry`, so the change that fixes a gate also removes its entry, and the list only shrinks. A gate that cannot start, or ends by a signal, fails the run, because it reported nothing. Loading the catalogue fails when an entry names no gate, and the list's JSON is refused when an entry has no reason or a reason that spans lines, so an entry is added only with its reason. The list is one of each listed gate's inputs, so editing it reruns that gate.

## Translation command (specified, not built)

Authoring is English-only. A page's Chinese counterpart (`*.zh.md`) and its consistency record (`*.i18n.yaml`) are written in one translation pass, so the bilingual-pair check of `gates:docs` reports a missing or out-of-date pair without failing the gate.

The command is `node_modules/.bin/tsx delorun/apps/tools/src/translate-docs.ts [--check] [path…]`. It is not in the repository.

- It finds every in-scope source whose `.zh.md` is missing or whose record is out of date, using the same discovery as upstream's pairing check.
- For each source, it writes the Chinese counterpart with a model, line-aligned as [docs/i18n/README.md](../../../docs/i18n/README.md) requires, and then records the pair with `scripts/verify-translation-pairing.ts --write`.
- `--check` lists what it would write and exits 0.
- It needs a model key, and only the lead runs it, never a lane agent.
- When it has run and its list is empty, remove `reportOnly` from the bilingual-pairs entry in [`docs.ts`](src/checks/gates/docs.ts), so the pairing check fails a change again.

## Workflows

This repository keeps three workflows in [`.github/workflows`](../../../.github/workflows) and removes every other workflow upstream wrote: each needs DeepSeek's secrets, runners or accounts, builds or publishes a release, or deploys a site. [`src/opening/workflows.ts`](src/opening/workflows.ts) lists each kept and removed workflow with its reason, and a workflow in neither list fails the check until someone classifies it. `node delorun/apps/tools/src/opening/workflows.ts --repo <checkout> --apply` deletes the removed files and drops every job of `ci.yml` except `node-24`, `node-24-lint` and `all-checks-passed`. Nothing here enables a workflow: GitHub runs one only when the repository's Actions settings allow it, and that setting is the owner's.

| Workflow | Triggers | Needs DeepSeek secrets or infrastructure | What it checks |
|---|---|---|---|
| [`gates.yml`](../../../.github/workflows/gates.yml) | `pull_request`, `push` to `main` | None; GitHub-hosted runner | Delorun's gates, as [the gates](#the-gates) describe |
| [`expected-filenames.yml`](../../../.github/workflows/expected-filenames.yml) | `pull_request`, by path | None; GitHub-hosted runner | No tracked file name contains "golden" |
| [`ci.yml`](../../../.github/workflows/ci.yml) | `pull_request` | None needed. Upstream's runner labels apply only in upstream's repository (see the note below) | `node-24` runs upstream's static gates, `node-24-lint` its lint and duplication checks, and `all-checks-passed` is the one verdict that waits for both |

`ci.yml` needs no secret, so it is kept. Each job keeps upstream's runner expression as the branch that applies in upstream's repository, where DeepSeek's runner labels such as `dsh-ubuntu-24-04-16core` stay in use. Every other repository runs the job on `ubuntu-latest`, so this repository never waits for a DeepSeek runner. The ledger's `.github/**` path rule covers the file. [`scripts/ci-workflow.spec.ts`](../../../scripts/ci-workflow.spec.ts) pins the three jobs, their runner routing and their temporary-storage and pnpm settings.

## Brief issues

`src/issues/issues.ts` turns a briefs file into brief issues.
A briefs file is a JSON array of objects.
Each object holds the sixteen fields of the [brief template](../../../.agents/skills/delorun-delegation/SKILL.md#write-the-brief) under their labels, and also a `title`, the `labels` that the issue carries and its `milestone`.
The issue form [`brief.yml`](../../../.github/ISSUE_TEMPLATE/brief.yml) asks for the same fields in the same order, and [`labels.yml`](../../../.github/labels.yml) defines the labels.

Run the tool from the repository root in one of three modes:

- `--input <briefs.json> --dry-run` validates the briefs and prints each issue body.
- `--input <briefs.json> --create --repo <owner/name>` validates the briefs and checks that `gh` is signed in as a maintainer of the repository. Then, for each brief, it creates the issue and locks it, or, when an issue with the same title exists, locks that issue if it is unlocked and skips it if it is locked.
- `--sync-labels --repo <owner/name>` creates or updates each label in `labels.yml` with `gh label create --force`.

```sh
node_modules/.bin/tsx delorun/apps/tools/src/issues/issues.ts --input delorun/apps/tools/tests/issues/fixtures/briefs.valid.json --dry-run
```

Every problem prints one line on standard error and exits 1 before any GitHub call.
A brief has a problem when:

- a field is missing, blank or unknown, or the file is not a non-empty JSON array of briefs;
- `Model` is not one of Haiku at medium, high or max effort, or Opus at medium or high effort, so Opus at max effort is refused;
- a link is neither an `https://` URL on github.com/twickas/delorun or docs.delorun.com nor a relative path that the repository tracks;
- a backticked path, whose first segment is a top-level directory of the repository, names no tracked file or directory, except in `You own`, where a new file or directory is allowed when its nearest existing parent directory is tracked;
- the text names `delorun/docs/plans/`, the private plan directory, or a machine path such as one that starts with `/home/`, `/Users/` or `~/`;
- a label is not defined in `labels.yml`, the labels omit `brief`, or the brief carries a `kind/*` label, which belongs to pull requests;
- a field adds a Markdown heading to the body, two briefs share a title, or two issues already share a brief's title.

Paths are checked against `git ls-files`, so a file must be in the index before a brief names it outside `You own`.
A new path in `You own` is refused when its nearest existing parent directory in the working tree is not tracked.
The rendered body links each tracked path to its place on branch `main` of the public repository: a file to its `blob` and a directory to its `tree`.
Links that the brief already carries are rewritten the same way.
Code spans that hold a command, and fenced code blocks, stay as written.
Create the labels and the milestone in the repository before `--create`, because `gh issue create` fails on a label or milestone that the repository does not define.

Known limits:

- `gh` 2.45 has no flag for the native Issue Type, so an issue that `--create` makes carries no Issue Type.
- Links point at branch `main`, so a path that exists only on the brief's own branch resolves after that branch merges.
- The title check reads at most 1000 issues and refuses a listing that reaches that count.

The specs in `tests/issues/` run the tool in scratch repositories with a fake `gh` first on `PATH`, and no spec reaches GitHub.

## Local checks

[`src/run-checks.ts`](src/run-checks.ts) runs the local checks. The catalogue is [`src/checks/plan.ts`](src/checks/plan.ts), which selects checks by change and by package; [`src/checks/run.ts`](src/checks/run.ts) starts each check once its needs pass and its CPUs and memory are free; [`src/checks/machine.ts`](src/checks/machine.ts) sets the memory ceiling; and [`src/checks/cache.ts`](src/checks/cache.ts) serves unchanged checks from the pass cache. The repository gates come from [`src/checks/gates/index.ts`](src/checks/gates/index.ts), and the budgets from [`src/checks/budgets.json`](src/checks/budgets.json).

Heavy runs share the machine through a slot budget under the system's temporary directory ([`src/checks/slots.ts`](src/checks/slots.ts)), instead of one run at a time. The machine has CPU slots (its CPUs, or `DELORUN_CHECKS_SLOTS`), the memory the runner budgets, and three disk-heavy places (`DELORUN_CHECKS_DISK_RUNS`) for builds, generators, the documentation site and the fork suite, because a shared machine's disk saturates before its CPUs. A run asks for the slots its checks that will really run can keep busy (checks a stored pass serves ask for nothing, and a run with nothing left to run takes no slots), at least four when it can use them, the memory of its largest check, and a disk-heavy place when it needs one ([`src/checks/demand.ts`](src/checks/demand.ts)). It writes a request `req-<priority>-<milliseconds>-<pid>.json` in the user's own `delorun-checks-<uid>.slots/`, which it creates with mode 0700 and refuses when it is a link, belongs to another user or is open to others, and is granted, first come, first served within a priority, once its minimum fits beside the holders and every earlier request has started; a request that touches no disk may pass one that waits only for a disk-heavy place. The grant is what the run asks for up to the free slots, and at most the machine less a quarter of its slots, so a small run always starts beside a large one; the trunk's priority (a pre-push whose pushed refs include the trunk, or `DELORUN_GATE_PRIORITY=trunk`) goes ahead of every waiting request, may take that quarter too, and never interrupts a holder. A granted run narrows its test runners' `--maxWorkers` to its slots, which no pass key records, and records its grant as `held-<pid>.json` until it ends or is interrupted; each file records its process's start time, so the files of a dead process are removed by whichever run notices them even when a later process reuses its id, and two runs that overfill the slots, the memory or the disk-heavy places by claiming at once are resolved by the later claim on that resource stepping back. A waiting run prints why it waits, its position and how long it has waited whenever that changes and every 30 seconds, and the run's summary and `report.json` (`waitedSeconds`, `slots`, `ioPressureAtStart`, `ioPressureAtEnd`) record the wait, the grant and the disk pressure (`/proc/pressure/io`, `some avg10`) at its start and end. `run-checks --queue` prints the holders with their slots, memory and how long each has held, and the waiting requests in serving order. A run whose checks that will run each keep one CPU busy, are neither `exclusive` nor `mergeOnly`, and have memory budgets that sum to at most 4 GiB (`isLightPlan`), such as the range gates and the boundary check of a push right after a passing run of the same tree, takes no slots, and neither do the pre-commit tier and `--preflight`. A check planned only as another check's need, such as the native addon's build, does not run when stored passes serve every check that needs it. Runs of older worktrees still take a ticket in `delorun-checks.queue/` or the lock file `delorun-checks.lock`: a live holder there holds the whole machine for new runs, an older ticket waiting there is served before a later request here, and every request here also holds a waiting ticket there, held once granted, so older and newer runs keep one first-come order and an older run waits for new holders as it waited for one holder.

A run's temporary files go to a scratch directory under the system's temporary directory, on the disk. `DELORUN_CHECKS_SCRATCH=memory` puts them on a memory file system instead (`/dev/shm`, else `$XDG_RUNTIME_DIR`) when it has `DELORUN_CHECKS_SCRATCH_GIB` (default 4) free, and the run's memory budget gives up that much; when none has the room the run says so and uses the disk. `DELORUN_CHECKS_SCRATCH=disk` is the default, because a memory file system makes `fsync` do nothing and some specs prove durability or a file system's own behaviour.

[`src/with-slots.ts`](src/with-slots.ts) runs an ad-hoc heavy command inside the same budget, so an agent's own builds, compiler runs and focused test runs count against the machine like the runner's: `node_modules/.bin/tsx delorun/apps/tools/src/with-slots.ts [--slots <n>] [--disk] [--memory-gib <n>] -- <command> [args...]` waits for `--slots` slots (default 4) and a disk-heavy place with `--disk`, runs the command with the grant in `DELORUN_SLOTS` (pass it to a test runner as `--maxWorkers=$DELORUN_SLOTS`), releases the slots when the command ends or is interrupted, and exits with the command's status. The repository, its worktrees, the pnpm store and the caches must live on the Linux file system: on WSL the runner drops the Windows directories (`/mnt/<letter>/...`) from the `PATH` of every check it starts, and a checkout under `/mnt/` would put every file read on the Windows disk.

Each check has a budget, its resident memory at the peak and its CPUs, which the runner keeps inside the run's ceiling, and a tier, the invocations that select it: `pre-commit` runs over the staged paths, `changed` selects by change (`--changed` and the pre-push hook), and `full` is the full gate.

A change run also has a gate tier, which says how much of its selection it pays for. The lane tier is what a push of a non-trunk branch runs: the boundary check, the JSDoc rules (`jsdoc`), every repository gate that names no lighter tier (`gates:docs` and the slower upstream gates name the agent tier, the heaviest the merge tier), the typecheck of the Delorun programs in the changed packages (and `typecheck:upstream`, which they read), and both phases of the fork suite over the changed packages only, without their dependents; the checks those need, such as a stale build, run too. The agent tier is what a lane's agent runs while it works: every check the changed paths select except the merge-only ones, dependents included. The merge tier runs the merge-only ones too, and only a merge-tier pass lets a commit reach the trunk. The agent tier is the default for `--changed`, `--base` and explicit paths; `--tier lane|agent|merge` chooses, and it is a usage error with `--pre-commit` or the full gate, which has no tier and runs everything. A check is merge-only when the catalogue marks it `mergeOnly`, which a gate asks for with `tier: 'merge'`; `--only <id>` still runs it in any tier, and `--plan` lists what a lighter tier left out as "left for the merge tier".

`--preflight` is the lane tier of `--changed` without the test lanes, for the rules a change trips first: the commit standard and sign-offs, the changelog fragment, whitespace and final newlines, secrets and deployment identifiers, the JSDoc rules, the boundary check and the typecheck of the changed packages. It waits in no queue and takes no memory scope.

| Merge-only check | Why it waits for the merge |
| --- | --- |
| `parity-replay` | An uncached replay of about 100 s |
| `parity-replay:control` | A replay of one scenario |
| `tests:snapshots` | An uncached replay of about 100 s |
| `tests:web-changed` | The browser lane, after the official client build |
| `tests:closure` | The runtime closure, built and booted |
| `tests:docker` | Specs against the Docker engine |
| `journey` | A release build and its install in containers, about 15 minutes |

The Docker lane and the journey never pass without Docker. At plan time the runner asks the engine (`docker info`, 30 seconds); when none answers, the lane is declined with the reason and how to start one (Docker Desktop, or the engine), and in the merge tier that decline fails the run, because only a merge-tier pass lets a commit reach the trunk and the lane did not run. One probe decides both. The same holds for a merge-only check too large for the run's memory ceiling. A decline for nothing to run, as the web lane's when no spec maps to the change, fails nothing. The lane sets `DELORUN_DOCKER_SPECS=1`: the image build spec runs only with it, and the supervisor spec fails, naming what a person must do, where it would otherwise skip for want of an engine or a repository digest for its fixture image (the engine needs the containerd image store). Run by hand without the variable, the specs skip. On an engine that does not offer the S2 transport, the workspace-container spec is skipped and the lane still passes, so the lane does not prove container workspaces on such an engine.

A change to an upstream package that holds a `security` ledger entry always runs its direct dependents' specs in the merge tier, whatever their number, in any dependency section (a development dependency counts, because a spec of the dependent can load the package). The 150-spec budget still applies to every other package, and in the agent tier to this one: there the dependents over the budget are left out and `--plan` names them with "left for the merge tier".

A push takes the merge tier when any pushed ref is the trunk, `refs/heads/main`, whatever `DELORUN_TIER` or `--tier` says, or when `DELORUN_TIER=merge` is set; `DELORUN_TIER=agent git push` takes the agent tier; any other push takes the lane tier. A tree pass record serves a run of its own tier or a lighter one, so a lane-tier record never covers the merge tier. `pnpm check:merge` is `--changed --tier merge`, which the lead runs once before fast-forwarding the trunk.

The `pre-commit` tier runs within a budget of 5 seconds (`budgets.json`) and reports a run that exceeds it. The web lane (`tests:web-changed`, [`src/checks/web.ts`](src/checks/web.ts)) runs the Chromium e2e specs under `apps/web/tests` that a change reaches. A change reaches the lane when a non-documentation path lies under `packages/client` or `apps/web`, or under a package that a spec in that inventory imports. A spec is selected when its own file changed, or when it maps to a changed package; a changed spec file selects only itself and does not make its package changed. A spec maps to the packages its imports reach: a package by its name, and a relative import by the package its resolved path lies in, so each spec maps to `apps/web` through its helper imports. A spec whose imports map no package maps by its file name, to a package whose directory name is a dash-delimited run of that name. No spec names a route or a client surface that maps to a package, so no page target is mapped. In the merge tier, a change that reaches the lane always runs specs: when more than 12 specs reach it, or none maps to it, the lane runs a bounded selection of at most 12, namely the smoke specs (`WEB_SMOKE_SPECS`: boot to a selected conversation, DeepSeek account sign-in, opening a recorded conversation and the settings surface) and then the reached specs in this order: a changed spec, a spec whose file name carries a changed package's directory name, a spec of the changed package the fewest specs map to, then by path. `--plan` and the run's summary say how many reached specs it left out, and a smoke spec missing from the inventory stops the plan. Outside the merge tier, a selection above 12 specs is declined with the count. A run that names neither a change nor a target would select the whole inventory, so the same cap declines it. The merge tier declines the lane only when this host cannot run it (its memory exceeds the run's ceiling), which fails the merge tier like any merge-only check that did not run. The lane runs `pnpm run build:artifacts` with `DSH_BUILD_CLIENT_PROFILE=official` first, then the selected specs under upstream's `vitest.web.config.ts`, one at a time, with `DSH_SNAPSHOT=replay` and without `DEEPSEEK_API_KEY`. Its budget is 5 GiB, 8 CPUs, alone, and 1200 seconds of wall clock, which the command reports when a run exceeds it. The lane runs Chromium only. Eleven specs launch WebKit inline and offer no switch that runs their Chromium part alone, so the lane leaves those eleven files out until the host has WebKit's system libraries; CI runs them with WebKit. The lane declares no inputs, so it runs whenever a change reaches it. The fork lane leaves `*.docker.spec.ts` files to the Docker lane. The built-package specs, the workflow checks and the Cordis check arrive with the packages that need them.

The fork suite runs in two phases so that the specs that start processes never share the CPUs with the unit phase's workers. A spec belongs to a phase by its name: `*.integration.spec.ts` runs in the integration phase and any other `*.spec.ts` or `*.spec.tsx` in the unit phase, so a new spec needs no list entry. A spec that runs git, Node or `tsx` children, composes a real profile, builds a release tree or makes many durable writes to a real file tree (an install, the trash, an update copy, release records) is an integration spec, since its time follows the disk's load and not the CPU's; `gates:spec-lanes` refuses a unit spec that starts a process. A unit test that runs 10 s is hung, not slow, and fails while the run is still short. A failed unit phase leaves the integration phase unrun.

Upstream's `build:artifacts` does not build Delorun's packages, so the runner looks at them separately. A Delorun package with a `build` script is stale when a runtime file its manifest names under `lib/` (a JavaScript file in `exports` or `files`, without a pattern or a declaration file) does not exist, or when its newest `src` file is newer than its newest output; the `build:delorun` check then builds the stale packages after `build:artifacts`, under the run's lock and memory budget, and the lanes that load built code wait for it: both phases of the fork suite, `tests:snapshots`, `tests:upstream-changed`, `parity-replay` and `parity-replay:control`. A spec never builds a package itself; one that needs a built package and finds it missing fails, naming `--only build:delorun`. A package without a `build` script, or whose manifest names no such file, is never stale. A worktree that a rebase gave a new built package therefore builds it in the run, and a lane does not build it by hand.

Every check inherits the runner's environment without git's repository variables and, on WSL, without the Windows directories on `PATH` and the Windows-side variables, `NoDefaultCurrentDirectoryInExePath` among them ([`src/checks/machine.ts`](src/checks/machine.ts)). A run that plans a check that runs pnpm, or `tests:upstream-changed`, whose specs start pnpm themselves, gives every check the environment `pnpm run` gives a script: the pinned pnpm first on `PATH` and as `npm_execpath`, and `pnpm_config_verify_deps_before_run=false`. Upstream's whole unit suite is not a lane; the green base runs it with the procedure and prerequisites in the [parity baseline](../../docs/reference/parity-with-deepseek-harness/parity-baseline.md#green-base-on-main).

Commands, from the repository root:

```sh
pnpm check                       # --changed, agent tier: what changed since main, without the merge-only checks
pnpm check:merge                 # --changed --tier merge: the same with the merge-only checks
pnpm check:full                  # the full gate, with no pass cache
pnpm check -- --plan             # the selection with each reason, cache state, expected time and budget; runs nothing
node_modules/.bin/tsx delorun/apps/tools/src/run-checks.ts --list        # the whole catalogue
node_modules/.bin/tsx delorun/apps/tools/src/run-checks.ts --queue       # who holds the machine's slots and who waits
node_modules/.bin/tsx delorun/apps/tools/src/with-slots.ts --slots 4 -- node_modules/.bin/tsc -p delorun/apps/tools/tsconfig.json --noEmit
node_modules/.bin/tsx delorun/apps/tools/src/run-checks.ts --only tests:fork    # both phases of the fork suite: unit, then integration
node_modules/.bin/tsx delorun/apps/tools/src/run-checks.ts delorun/apps/tools    # targets: that package's specs, and the typechecks of the packages that depend on it
node_modules/.bin/tsx delorun/apps/tools/src/run-checks.ts --only tests:web-changed apps/web/tests/forge-panel.e2e.ts    # the web lane for named specs, after the official client build
```

Options: `--changed`, `--pre-commit`, `--pre-push` and `--preflight` each select an invocation, so give one; `--queue` prints the slot budget's holders and waiting runs; `--tier lane|agent|merge` sets the gate tier of a change run; `--base <ref>` measures `--changed` from another ref (default `main`); `--only` and `--skip` take check ids or groups (`boundary`, `gates`, `whitespace`, `docs`, `typecheck`, `tests`, `generate`, `parity`), comma-separated; `--plan` and `--list` print without running; `--no-cache` skips the pass cache; `--no-shared-cache` keeps the run to this worktree's passes; `--bail` stops at the first failure; `--workers <n>` sets the fork suite's unit workers, and the integration phase takes at most 4 of them; `--no-scope` runs without the systemd user scope.

A check that declares its inputs passes once per key ([`src/checks/cache.ts`](src/checks/cache.ts)): the sha256 of the check's id; the sorted list of its input files' git blob ids (the blob id of a tracked, unmodified file; the content hash of a modified, deleted or untracked one); the source and manifest of the Delorun package whose code its command runs and of every Delorun package that package depends on (`scripts/**` for upstream's scripts); the lockfile and pnpm's copy of the lockfile it last installed from (`node_modules/.pnpm/lock.yaml`), so a worktree whose install is stale has another key; the Node and pnpm versions; the platform; the clone (its git common directory); HEAD, for a check that reads history; the command, its budget entry and the values of the environment variables it lists; and the values of every `DELORUN_*`, `DSH_*`, `DOCKER_*`, `VITEST*`, `NODE_OPTIONS`, `NODE_PATH`, `TZ`, `LANG` and `LC_*` variable, with the repository root written as `<root>`, and whether each `DEEPSEEK_*` variable is set. The variables that steer the runner (`DELORUN_TIER`, `DELORUN_GATE_PRIORITY`, `DELORUN_FULL_GATE`, `DELORUN_PUSH_SKIP`, `DELORUN_CHECKS_SCOPE`) reach no check and are not keyed. A stored pass with the same key is reported as `cached pass (<key prefix>)`, and the check does not run. The cache is off for `--no-cache`, `pnpm check:full`, a push with `DELORUN_FULL_GATE=1`, and when `CI` is set. A check without declared inputs always runs: the replays, the builds, the native addon, the range gates and the staged whitespace check.

Passes are kept in the worktree (`node_modules/.cache/delorun-checks/pass/`) and, for the checks whose key covers everything their result depends on, in a machine-wide store that every worktree of the clone reads ([`src/checks/shared-cache.ts`](src/checks/shared-cache.ts)): `$DELORUN_CHECKS_SHARED_CACHE` when set (an absolute path), otherwise `$XDG_CACHE_HOME/delorun/checks`, otherwise `~/.cache/delorun/checks`. Its entries are named by their key and written through a file renamed into place, so concurrent runs from many worktrees each leave a whole entry; an entry older than 14 days is removed. The runner refuses, before any check starts, a store directory inside the repository, a symbolic link, and a directory that another user owns or that the group or others can reach (mode other than 0700); `chmod 700` or `--no-shared-cache` resolves it. A pass the store cannot write, such as on a full disk, is reported and changes no result. A pass served from the store is reported as `cached pass (shared, <key prefix>)`.

Each phase of the fork suite remembers a pass per package ([`src/checks/units.ts`](src/checks/units.ts)), and a phase's pass serves only that phase. Each Delorun package with specs is a unit, whose key covers the package's own files, the files of the Delorun packages it depends on directly or not, the files of the upstream packages those depend on directly or not, the shared test configuration (`delorun/vitest*`, `delorun/package.json`, the root configuration files, `vendor/`, `native/` and the DOM setup script) and what every key covers. A run starts each phase over the packages without a stored pass for it only, and reports how many ran and how many were served from this worktree or shared; `--plan` lists the packages to run. Only a run in which every started package passed records passes; a run that fails records none, so its packages all run again. Documentation outside the packages, such as `delorun/docs/` and the changelog fragments, is in no package's key, so a change to it reruns no spec, while a change to any file a package's key names reruns that package and every package that depends on it. The audit of what each package's specs read beyond that is `UNIT_RULES` in the same module: a package whose specs read other packages' files names them; `delorun/packages/bundle-local` and `delorun/packages/home-auth`, whose specs boot a profile, are keyed on the whole tree; and the packages in `UNSHAREABLE_PACKAGES` are keyed on the whole tree and HEAD and keep their passes in the worktree. The whole suite is not split into packages while a directory with specs is not a package of the tree, and a run of named spec files is keyed as one check.

[`src/checks/sharing.ts`](src/checks/sharing.ts) holds the rule and its reason for each check, from an audit of what each command reads. A check the rules do not name is not shared. Shared today: `gates:package-states`, `parity-switches`, the `typecheck:delorun:*` programs that read no emitted declarations (no project references, not the CLI, no Delorun dependency with a build), `tests:upstream-changed` (its key adds the generated file whose existence switches a module alias), and the per-package passes of both phases of the fork suite (`tests:fork:integration` takes the `tests:fork` rule), except those of the packages whose specs read the home directory, Docker or the real repository's git state (`delorun/apps/cli`, `delorun/apps/release`, `delorun/apps/tools`, `delorun/packages/home-process`, `delorun/packages/supervisor`). Every other check keeps its passes in its worktree: the boundary check and the range gates read history; `typecheck:upstream` writes the declarations later checks read; `gates:docs`, `jsdoc`, `gates:licence`, `docs-site` and `generated:notices` read git-ignored or built files that no key covers; the Docker, web and replay lanes read the engine, the official build or declare no inputs.

The merge tier, a run with `DELORUN_GATE_PRIORITY=trunk` and a full gate without `--only` are the trunk's last line: they read no shared pass, and their security-class checks and merge-only checks run whatever any cache holds. They still store the passes they prove. The security-class checks are `boundary`, `gates:secrets`, `gates:personal-data`, `gates:infrastructure` and `gates:fundamentals`, and the test lanes whose scope runs a package that enforces a security fundamental (a package of a file `gates:fundamentals` names) or an upstream package with a `security` ledger entry or a direct dependent of one. `--plan` names each check's cache state and whether its pass is shared, with the reason when it is not; the run's summary counts the passes served from this worktree and from the store, and `report.json` records each check's `cacheSource` and the run's counts under `passCache`.

A pre-push run, or a change run (`--changed`, `--base`), of a clean tree that passes every check it selects writes a tree pass record, `<git common directory>/delorun-checks/trees/<tree>-node<major>.json`, keyed on HEAD's tree and the Node major ([`src/checks/tree-pass.ts`](src/checks/tree-pass.ts)). The record names its gate tier, and a record without one counts as an agent-tier pass. A record serves a run of its own tier or a lighter one, so a push of the trunk, which needs the merge tier, reruns everything the merge tier selects unless a merge-tier record covers it (the pass cache still serves checks that declare inputs, apart from the security-class and merge-only ones). Every worktree of the clone shares that directory, so a pass in one worktree serves the same tree in another, and a pass on one Node major never serves another. A later run of that tree reports the pass and starts nothing when the record covers each check it selects: the record names the check, the check's scope lies within the recorded scope (the packages or specs a narrowed suite ran), and the lockfile, the Node and pnpm versions and the environment variables the checks list all match. The boundary check and the range gates read HEAD's history and the commits from `origin/main` to HEAD, which a tree does not determine, so they are covered only at the same HEAD commit and `origin/main`. A branch push measures from the older of its remote tip and its merge base with `origin/main`, so a fast-forward of `main` to the commit that it checked starts nothing, as long as `origin/main` has not moved, while a different commit with the same tree reruns the checks that read history. A dirty working tree, `--no-cache`, `CI` and `DELORUN_FULL_GATE=1` neither read nor write a record. A covered run is answered before the slot budget, so it does not wait for slots.

To install the hooks, write a one-line `lefthook-local.yml` at the root with `extends: [delorun/lefthook.yml]` (git ignores it), then run `node scripts/install-lefthook.mjs`. The installed `commit-msg`, `pre-commit` and `pre-push` hooks exit 1 and name the install command when they cannot find Lefthook, so a missing binary fails the hook instead of passing it. In a tree with `delorun/lefthook.yml`, a push also exits 1 and names `setup-worktree.ts` while `lefthook-local.yml` is missing or no uncommented line of it names `delorun/lefthook.yml`, since a push would then run upstream's hooks alone and none of Delorun's checks. Two places enforce this: the installed `pre-push` hook file, and the first `pre-push` job of upstream's `lefthook.yml`. Lefthook rewrites the hook file with its plain template when it syncs, for example on a bare `lefthook install` or when the checksum file shared by every worktree of the clone differs, and the rewrite drops the hook-file check; the job stays, because Lefthook runs it whichever template it wrote. `setup-worktree.ts` restores the hook-file check. The `pre-commit` hook runs the `pre-commit` tier. The `pre-push` hook runs `--pre-push`: what changed since the older of the remote branch's tip and its merge base with `origin/main` (for a new branch, its merge base with `main` when `origin/main` is absent). `DELORUN_PUSH_SKIP=<check or group>,… git push` leaves checks out of a push of another branch; a push of the trunk with `DELORUN_PUSH_SKIP`, `--skip` or `--only` is refused, because it runs every check of the merge tier. `DELORUN_FULL_GATE=1 git push` runs the full gate. Merging by fast-forward after the branch push does not rerun the gate. The `commit-msg` hook runs `check-commits.ts --message <file>` on each commit message.

Reports and logs are under `node_modules/.cache/delorun-checks/`: `report.json` holds each check's status, whether a cached pass served it and from where, its reason, log, duration and peak memory, and the run's cache counts; `logs/<check>.log` holds its full output; `pass/` holds this worktree's passes, the machine-wide store is outside the repository as described above, and the tree pass records are in the git common directory, shared by the worktrees; `durations.json` holds each check's last duration, which orders the next run; `tsbuildinfo/` holds the incremental typecheck state.

The ledger check alone is `pnpm --filter @delorun/tools check`. One gate runs with `node_modules/.bin/tsx delorun/apps/tools/src/checks/gates/<name>.ts`, such as `licence`, and the range gates take `--base <rev>`. The specs run with `node_modules/.bin/vitest run --config delorun/vitest.config.ts`, and this package typechecks with `node_modules/.bin/tsc -p delorun/apps/tools/tsconfig.json --noEmit`.

The [delorun-dev-workflow skill](../../../.agents/skills/delorun-dev-workflow/SKILL.md) states when to run each check.

## Batch integration

[`src/batch/batch.ts`](src/batch/batch.ts) lands several lanes at once: `node_modules/.bin/tsx delorun/apps/tools/src/batch/batch.ts --lanes <branch>[,<branch>...] [--trunk main] [--remote origin] [--no-land]`, run from the root of a clean integrator worktree on a branch. It refuses a dirty worktree, a detached HEAD, a lane branch that names no commit, and a lane name that is not a branch name. `--plan` prints the order, each lane's commit count and packages, and which lanes each check would suspect, without fetching or changing anything.

The tool fetches `<remote>/<trunk>`, creates the candidate branch `batch/<id>` there (the id is the UTC start time, `YYYYMMDD-HHMMSS`), and replays each lane's commits from its merge base with the trunk one at a time with `git cherry-pick`, keeping authors, author dates, messages and sign-offs. A commit the candidate already holds is dropped. A lane with merge commits or no commits is set aside before it is applied, and a lane that conflicts is undone and set aside with the conflicting paths.

The gate is the batch's own run of `run-checks.ts --changed --base <start> --tier merge` on the candidate commit. It passes only when the runner exits 0 and has stored a merge-tier tree pass record whose head is that commit; a missing record, another tier or another head is a gate error. A landing batch then pushes the candidate with `git push <remote> batch/<id>:refs/heads/<trunk>` and `DELORUN_TIER=merge`, whose pre-push hook finds that record, and `--no-land` stops after the gate. A push the remote refuses because the trunk moved stops the batch; the tool never rewrites the remote and never passes `--force`, `--force-with-lease`, `--no-verify`, a `+` refspec, `--tier agent`, `DELORUN_TIER=agent` or `DELORUN_PUSH_SKIP` to any process ([`src/batch/process.ts`](src/batch/process.ts)).

A batch refuses to start or resume, with `hooks-bypassed`, when the pre-push hook could be skipped: `LEFTHOOK` other than `1` or `true`, `LEFTHOOK_EXCLUDE`, `LEFTHOOK_BIN`, `DELORUN_PUSH_SKIP` or any `GIT_CONFIG*` variable in the environment, a `core.hooksPath` that is not the installer's `dsh-hooks` directory, a `pre-push` hook that does not run lefthook, a `lefthook-local.yml` that does not include `delorun/lefthook.yml`, or a missing `node_modules/.bin/lefthook`. These variables never reach the batch's own processes, and no process it starts gets `--skip` or a `core.hooksPath` override, apart from `git cherry-pick --skip`, which drops a commit the candidate already holds.

When the gate fails, the tool reads the failing checks from the runner's report and rereads each log's first failure, failing spec files and named commits at once. It reruns the failing checks once on the same candidate; a check that passes is reported flaky, and a second round that fails only on flaky checks stops the batch. A lane is a suspect for a check when the runner's selection over the lane's own changed paths picks it. A test lane's named specs narrow the suspects to the lanes whose selection reaches them, and a range gate's named commits narrow them to the lanes that contributed those commits. Attribution reruns only the failing checks with `--only` on candidates without some lanes ([`src/batch/attribute.ts`](src/batch/attribute.ts)): a lane whose removal alone fixes the failure is at fault. When several single removals fix it, the ones that fail alone on the trunk are at fault, and if none does they are reported as failing together. When no single removal fixes it, every suspect is removed; if the failure persists it is not attributable and nothing lands, and otherwise the suspects that fail alone are at fault. A candidate on which a lane no longer applies counts as no evidence. The candidate is then rebuilt without the faulted lanes and gated again, and the pass cache serves its unchanged checks.

Each step's outcome is written to `<git common dir>/delorun-batch/<id>/state.json` through a temporary file renamed into place before the next step starts. `--resume <id>` ends a cherry-pick an interruption left behind, resets `batch/<id>` to the last recorded candidate and continues from the first unfinished step; a push is recorded only after it returns. Beside the state, `summary.md` lists the lanes landed, set aside, faulted and flaky and the commit the trunk moved to. Each lane set aside or faulted gets `<lane>.md` with the reason, each failing check's first failing test and assertion or first error lines, the lanes it fails together with, and the commands that reproduce it in the lane's own worktree: `git fetch <remote> && git rebase <remote>/<trunk>` for a conflict, and `node_modules/.bin/tsx delorun/apps/tools/src/run-checks.ts --only <check> --changed --tier merge` and, for a spec, `node_modules/.bin/vitest run --config <config> <spec>` for a failure.

The exit status is 0 when the candidate landed, or passed with `--no-land`, 1 when the batch stopped without landing, and 2 when it was refused before anything changed.

## The stand-in stack

[`src/stack/`](src/stack/index.ts) holds local stand-ins for the outside services that reach and sign-in talk to, so their tests reach no live provider. `startStandInStack()` starts one test authority and four stand-ins on `127.0.0.1`, each on an ephemeral port and served over HTTPS with a certificate from that authority; a client trusts `authority.certificate.pem` and nothing else. Each stand-in also starts alone. The stand-ins are test infrastructure: they model a provider's documented behaviour, and their hooks produce the responses that the contracts' denial tests must refuse.

| Stand-in | Stands in for | What it serves | Hooks for refusal tests |
| --- | --- | --- | --- |
| `startOidcStandIn` ([`oidc-provider.ts`](src/stack/oidc-provider.ts)); the stack starts two, `issuerA` and `issuerB` | The person's own OpenID Connect provider ([C14](../../docs/contracts/c14-oidc-passkeys.md)) | Discovery, the key set, the authorisation code flow with S256 PKCE, `nonce` and the RFC 9207 `iss` parameter, `client_secret_basic` at the token endpoint, RFC 7591 and 7592 dynamic registration. It has no login page: each authorisation signs in its configured subject with `auth_time` now. It signs RS256, PS256, ES256 or EdDSA | The next ID token with changed or missing claims (another `aud`, several audiences without `azp`, another `iss`, `sub` or `nonce`, an old `iat` or `auth_time`); a forged token (`alg: none`, HS256 keyed by the public key, an unknown key, no `kid`, a broken signature); another or no `iss` response parameter; key publication, rotation and retirement, and signing with a retired key; changed metadata; any endpoint's raw answer or silence |
| `startAcmeStandIn` ([`acme.ts`](src/stack/acme.ts), [`caa.ts`](src/stack/caa.ts)) | The named certificate authority's ACME server ([C7](../../docs/contracts/c07-reach-providers.md#own-domain-reach)) | RFC 8555 directory, nonces, accounts, orders, authorisations, challenges, finalisation, download and revocation, with every request's JWS, nonce and URL verified. Each authorisation offers `http-01`, `dns-01` and `tls-alpn-01`, a wildcard only `dns-01`. TLS-ALPN-01 (RFC 8737) connects to the loopback target the caller names for the identifier; DNS-01 reads TXT records the caller supplies. Before issuing it applies the caller's CAA records, with `accounturi` and `validationmethods`, as the CA whose CAA identity is `letsencrypt.org` | Every challenge a client starts is recorded, so a spec proves that a home started no HTTP-01 or DNS-01 challenge; a certificate issued for another account; revocation by the CA; a problem document in place of an endpoint's next answer |
| `startCtStandIn` ([`certificate-transparency.ts`](src/stack/certificate-transparency.ts)) | Cert Spotter's issuance search, the default certificate source of [C6](../../docs/contracts/c06-relay-protocol.md#certificate-monitoring) | `GET /v1/issuances` with `domain`, `include_subdomains`, `match_wildcards`, `after` and `expand`, in Cert Spotter's fields and error form; `sourceUrl` is the contract's source with the stand-in's origin | Fixtures logged by the spec, such as `*.example.com` or a multi-name certificate; a certificate held back until a log includes it; revocation; an error such as `rate_limited` in place of the next answer |
| `installNetworkGuard` ([`network-guard.ts`](src/stack/network-guard.ts)) | Nothing: it watches the test process | Refuses, before any packet is sent, every TCP or TLS connection, UDP send or bind, listener and DNS query whose target is not a loopback address, and records each connection that reaches its peer | Name lookups resolve only `localhost`, so a stand-in is addressed by its IP literal |

The stack logs every certificate the ACME stand-in issues in the Certificate Transparency stand-in and marks the ones it revokes. A spec that must prove nothing leaves loopback installs the guard before it starts the stack and reads `guard.connections` and `guard.refusals` at the end. The guard patches `node:net`, `node:dgram` and `node:dns` in its own process only: it does not see child processes, worker threads, native addons that open sockets themselves, or sockets opened before it was installed.

The stand-ins use three maintained libraries, each declared in this package's manifest:

- [`jose`](https://github.com/panva/jose) signs and verifies JSON Web Tokens and JWS, exports JSON Web Keys and computes thumbprints. A full provider library such as `oidc-provider` from the same author was not used, because its token endpoint cannot issue the forged, wrong-audience and mixed-issuer tokens the denial tests need, and its interaction flow needs a login page driven by the spec.
- [`pkijs`](https://github.com/PeculiarVentures/PKI.js) with [`asn1js`](https://github.com/PeculiarVentures/ASN1.js) makes certificates and PKCS #10 requests and reads their extensions over Node's Web Crypto, so no stand-in shells out to `openssl`. It is already in the lockfile through the desktop build. `@peculiar/x509` was not used, because it needs a global `reflect-metadata` polyfill.
- The ACME server is the stand-in's own code: Pebble, the reference test server, is a Go binary that cannot run inside the test process under the guard. The specs drive it with a spec-side client; `acme-client` was not added, because its `axios` dependency changes the resolution of upstream's website dependencies in the lockfile.

The specs in [`tests/stack/`](tests/stack/) prove that the OpenID Connect stand-in's discovery metadata and ID tokens, in each allowed algorithm, pass every C14 check and that each hook produces the response C14 refuses with its code; that the ACME stand-in issues for a test name after a TLS-ALPN-01 challenge answered on loopback and refuses tampered requests and CAA records that name another account, method or CA; that the Certificate Transparency stand-in answers exact, wildcard and multi-name searches; and that, with the guard installed, a sign-in, an issuance and a search open connections to loopback only, while a connection, lookup, listener or UDP send that would leave loopback is refused.

## Parity composition

[Contract C16](../../docs/contracts/c16-parity-composition.md) states that Delorun, with its model-visible additions switched off, replays upstream's recorded scenarios at `dsh-v0.2.2-rc.1` with no difference from their expected output. This package checks that statement with two checks: `parity-replay` runs upstream's replay through the parity overlay, and `parity-switches` checks that every model-visible Delorun change has a registered switch that the overlay turns off.

### The overlay

[`src/parity/composition/parity.overlay.yml`](src/parity/composition/parity.overlay.yml) is a Cordis patch file. Each recorded-session adapter reads `DSH_SNAPSHOT_PATCH` through upstream's `snapshotPatchOverlay` in `packages/test-support/session-snapshot/src/snapshot-patch.ts` when its module loads. It places the named file after the root configuration of every process it starts and before every scenario layer: the headless, SDK and ACP adapters pass it as a `--patch` argument, and the Web scaffold applies it after the shipped bundle layers. In `DSH_SNAPSHOT=record` or `refresh` mode an adapter that receives the variable throws before it starts a process. No shipped profile, bundle or command-line option names the file, and the `dsh` command does not read the variable.

A patch row replaces its entry's whole `config` and reaches only entries of the root tree, so the overlay sets a switch only where no earlier layer configures the entry. Every other built switch is at its parity value through its validated Config default:

| Switch | How the parity composition sets it |
| --- | --- |
| `plugin_manager_read_exemption`, `profile_history` | The overlay row `tool-plugin-manager`, `name: '@deepseek-ai/dsh-plugin-manager/tools'`, sets `readActionsExempt: false` and `profileHistory: false`. |
| `preset_inspect` | Config default `false`. The row sits in each Web preset's plugin list, which a patch reaches only by replacing the whole preset row. |
| `container_denial_marker` | Config default `false`. The bundles and the root configurations set `sandbox-policy`'s mode and workspace root, which an overlay row would erase. |
| `sandbox_protected_reads` | Config default `false`. The bundles set the search tools' over-cap sampling choice, which an overlay row would erase. |
| `one_time_launch_tokens` | Config default `false` of `@deepseek-ai/dsh-client-connection`'s `oneTimeLaunchTokens`. The `connection` row carries the web bundle's `trustedHosts` expression, which an overlay row would erase. |
| `default_workspace_directory` | A presence switch: the overlay leaves `@delorun/bundle-local`'s `workspace-controller` row out, so upstream's row sets no `defaultWorkspaceDirectory` and upstream's own documents lookup places the first-use workspace. |
| `doctor` | Config default `false`. Only the `doctor` profile mounts the app, and the replay starts no doctor process. |
| `studio_additions`, `main_chat` | Config defaults `false` of `@delorun/plugin-theme`'s `studioAdditions` and `@delorun/plugin-main-chat`'s `enabled`. The replay composes upstream's bundles, which mount neither `@delorun/bundle-studio` nor the main chat. |

The overlay also mounts [`@delorun/bundle-local`](../../packages/bundle-local/README.md): after the switch rows it restates that bundle's `cordis.patch.yml` in the parity form each `LOCAL_ROWS` entry gives, and `parity-switches` fails when the restatement differs from `parityPatches` of the bundle's file (`localBundleErrors` in [`overlay.ts`](src/parity/composition/overlay.ts)). The session-log upload row, C16's changed default, is left out, so it keeps upstream's value: the overlay follows each replay's root configuration, which turns upload off for the headless and ACP corpora and leaves it on elsewhere. Desktop analytics keeps Delorun's `false`, and the Privacy section row is present and disabled. The studio bundle is not part of the replay's composition, and the main chat is mounted by no profile; the preset default keeps upstream's value (`standard`).

### What `parity-switches` detects

The check reads the TypeScript sources under `delorun/**/src` and every ledgered upstream source under `packages/` and `apps/`, without specs. It fails when:

- a property of an interface named `Config`, or of the interface a `const Config: z<…>` schema is typed by, whose JSDoc names `` C16 switch `<id>` `` has no built registry entry with that field, or its entry is still planned;
- a built entry's source has no such field, the field's `z.boolean().default(…)` is not the parity value, the entry's parity value equals its default, or a model-visible entry names no source file or no scenario `<profile>/delorun-<id>`;
- a Delorun-owned source calls a model-visible registration API, or a ledgered upstream edit changes a line inside a top-level statement that calls one, and no built, model-visible entry lists that file in its sources;
- a security entry's `nonModelVisibleHunks` hold a digest whose record count differs from the number of the file's diff hunks with that digest that touch such statements, or the entry's file is not one the check reads.

A hunk's digest is the SHA-256 of `@@ -<old count> +<new count> @@` followed by each of its lines as `git diff --unified=0` prints them, `-`, `+` or `\` marker included, every line ending in a newline. It leaves out the start lines and the function context, so an edit elsewhere that shifts a hunk keeps its digest. A hunk touches a statement when a line it adds, or for a deletion-only hunk the line before the deletion, lies in it. A record passes the changed lines of one hunk with its digest, a deletion-only hunk as any other. The hunks with one digest pass only when the records with that digest are exactly as many, so a record covers no second hunk with the same lines, and a record that matches no such hunk is stale. Any further change inside or next to a recorded hunk, such as a deleted registration call that the diff joins to it, changes its digest, so its lines count again. Records on an entry of another class pass nothing.
- an overlay row names a module with no built switch, sets a key that is no switch of that module or a value that is not the parity value, or sets anything besides `id`, `name` and `config`, or a built switch is neither in the overlay nor in `DEFAULT_PARITY` in `overlay.ts` with its reason;
- a model-visible built switch has neither a recorded scenario nor a staged one.

The model-visible registration APIs are `systemPrompt.section`, `systemPrompt.context` and `systemPrompt.suppressRuntimeContext`; `tools.register`, `tools.restrict`, `tools.setExecutor` and `tools.guard`; `defineTool`; and listeners registered with `on` for `system-prompt/assemble`, `agent/request`, `agent/pre-step`, `request/context`, `tools/execute`, `tools/pre-execute`, `tools/post-execute` and `tools/result`.

### What it cannot detect

The scan matches names, not types or data flow, so it misses:

- text that reaches the model through a helper outside the registering statement, such as a renderer module or a constant at the top of a file, when no changed line falls inside a registering statement;
- a call through another receiver name, an alias or a dynamic property, and a model-visible event that is not in its list;
- a recorded non-model-visible hunk whose same removed and added lines move to another place in a registering statement: a record binds a hunk's lines and counts, not its place;
- whether a listed switch really gates the contribution at its parity value. The replay proves that for the scenarios that reach the contribution, and the switch-on scenario proves the switch's on-path once it is recorded.

It also accepts any contribution in a listed source file, so a second, unswitched contribution added to the same file passes the scan and must fail the replay.

### The switch sweep

Each model-visible built switch has a switch-on scenario `snapshots/<profile>/delorun-<id>` whose `runtime.cordis.yml` sets only that one switch to its non-parity value, plus the scenario-local `agent-default-model` pin that selects the corpus model `deepseek-v4-flash`. Once recorded, `parity-replay` replays it with the rest of the corpus under the overlay, so the switch under test is the only behavioural difference from the parity composition. A Web scenario runs through an e2e driver under `apps/web/tests`, which turns `preset_inspect` on with `launchWebScaffold`'s `presetInspect` option and, on replay, selects the same model through the agent default model.

Five of the fifteen switch-on scenarios are recorded: `session/delorun-plugin-manager-read-exemption`, `session/delorun-profile-history`, `session/delorun-container-denial-marker`, `session/delorun-tool-failure-guard` and `web/delorun-preset-inspect`. The tool-failure guard's model is scripted (`recording: authored`): it was recorded keyless against `pnpm run mock:llm`. Their directories are under `snapshots/`, and they replay keyless with and without the overlay (the Web scenario through `test:web:built`). The other ten wait for their recording: `web/delorun-main-chat`, `web/delorun-default-workspace-directory`, `session/delorun-permission-defaults`, `session/delorun-fetch-guard`, `session/delorun-scheduled-task-consent`, `session/delorun-instruction-layer-consent`, `session/delorun-mcp-add-consent`, `session/delorun-external-agent-consent`, `session/delorun-sandbox-protected-reads` and `session/delorun-update-turn-refusal`. Each keeps its configuration under [`src/parity/composition/scenarios/`](src/parity/composition/scenarios/), and `parity-switches` reports it as `pending recording`.

To record one, move its directory to `snapshots/<profile>/`, run upstream's record command for that scenario without `DSH_SNAPSHOT_PATCH`, review the outputs, and remove `input.task` once the Session fixture carries the task. A recording reads its task from a Session fixture already in the scenario directory when one exists, so move any earlier fixture out before recording with a changed `input.task`.

### Commands

```sh
node_modules/.bin/tsx delorun/apps/tools/src/run-checks.ts --only parity
DSH_SNAPSHOT_PATCH=delorun/apps/tools/src/parity/composition/parity.overlay.yml pnpm run test:snapshot
node_modules/.bin/tsx delorun/apps/tools/src/parity/composition/check-parity-switches.ts
```

`pnpm run test:snapshot` replays the session, SDK and ACP scenarios through their adapters and checks every scenario of the corpus, Web included, against upstream's corpus gate. The Web scenarios replay through their e2e drivers in `test:web`, which reads the same variable through the scaffold: `DSH_SNAPSHOT=replay DSH_SNAPSHOT_PATCH=<overlay> pnpm run test:web:built`.
