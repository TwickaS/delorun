# @delorun/cli

[English](README.md) | 中文

> 英文页面是当前版本；本页可能落后于它。

## 摘要

本应用即 `delorun` 命令。在任何上游代码运行之前，它通过 [`@delorun/home`](../../packages/home/README.zh.md) 解析并准备 Delorun home（该包实现 [约定 C1](../../docs/contracts/c01-home-layout.zh.md) 的 home），选择 CLI profile，并通过上游的 profile 运行器、以 Delorun home 作为 `DSH_HOME` 运行该 profile。新 home 先进入 setup 的入口。启动会运行该 profile 的 [`@delorun/home-process`](../../packages/home-process/README.zh.md) home 进程（[约定 C19](../../docs/contracts/c19-home-process.zh.md)），它持有该 profile 的 home 锁，因此每个 profile 只运行一个 home 进程，`stop` 与 `status` 通过它的更新通道与之通信。

## 命令

每个命令都回应 `--help`、`-h` 与 `delorun help <command>`，它们都来自 [`src/help.ts`](src/help.ts) 中的同一张表，该表不加载任何命令；错误的选项会指向该帮助。

| 命令 | 作用 |
| --- | --- |
| `delorun [--profile <name>] [--foreground]` | 在没有 CLI profile 的 home 上运行 setup；否则像 `delorun start` 一样启动 home 进程（除非 setup 的回答是否，或给出了 `--foreground`，否则在后台运行），并像 `delorun open` 一样打开 studio，同时打印 `delorun status`、`delorun logs --follow` 与 `delorun stop` |
| `delorun setup [<section>] [--profile <name>] [--yes \| --config <file>] [--provider <id> [--model <id>] [--base-url <url>] [--key-env <NAME>]] [--prompts <safer\|stock\|dangerous> [--accept-dangerous-mode]] [--phone-powers <careful\|full>] [--check-key] [--no-update-check] [--list]` | Setup：在终端中回答用例问题，或用 `--yes` 采用全部默认值，或用 `--config` 提供答案文档；已完成的 setup 在终端中会再次询问，并选中当前的选择，用 `--yes` 或 `--config` 则保持不变。`--provider` 及其标志为 `--yes` 与 `delorun setup key` 指定模型提供商。`--no-update-check` 在任何形式下都关闭发布检查。`--phone-powers` 为 `--yes` 记录手机权限级别；在终端中运行时，打开远程访问之后会询问它。`<section>` 重新运行一个分区，`--list` 列出它们 |
| `delorun start [--foreground] [--profile <name>] [--patch <file>]... [--inspect [--yes]]` | 启动与终端分离的 home 进程，并最多等待 120 秒让它报告 `running`；`--foreground` 在当前终端中运行它，setup 的回答选择不使用后台的启动也是如此；`--open` 在它运行之后打开 studio；`--patch` 加入本人的 overlay，`--inspect` 只有在本人于终端确认或给出 `--yes` 之后才打开调试端口（[inspector](src/inspector.ts)） |
| `delorun open [--print] [--port <n>] [--profile <name>]` | 向运行中的 home 进程请求 studio 链接（C19 的 `studio.open-token`）并在默认浏览器中打开；`--print` 改为只打印一次，供没有浏览器的计算机或 SSH 端口转发使用。该链接只能在一分钟内登录一次，且只在它所写明的地址上有效；`--port` 为转发到 studio 的回环端口生成链接。没有 home 进程运行时退出码为 3，端口超出 1 到 65535 时为 2 |
| `delorun stop [--now] [--profile <name>]` | 在运行中的 chat 结束后停止 home 进程，最多等待 1,800 秒；`--now` 先取消它们，并结束在 60 秒内不回答的、或接受之后 120 秒仍未退出的 home 进程：先发 `SIGTERM`，30 秒后再发 `SIGKILL`，信号只发给经进程 id、启动标识和 pid 命名空间确认为锁持有者的进程；未确认的持有者以及 Windows 上的任何持有者都不发信号，命令以退出码 1 退出并指出它 |
| `delorun status [--profile <name>] [--json]` | 用平实的语言打印 Delorun 是否在运行、已打开的工作会话及其开始与结束时间、Host 提供服务之后的 studio 地址、版本和运行中的 chat；`--verbose` 增加 home、profile、被 `delorun` 忽略的继承 `DSH_HOME`、进程 id、启动 id、运行时版本和进行中的更新；Host 提供 studio 之后，还有它的回环地址（不含任何查询、片段或令牌）以及这一行：`Run delorun open to open the studio in your browser.`；`--json` 只打印它的 `status` 回答 |
| `delorun doctor [--port <n>]` | 检查 home、Docker 引擎、模型提供商密钥的格式和 studio 的端口，在 Linux 上还检查 bubblewrap 能否为命令提供沙箱，然后打印 `changes` 各行：保护设置、两种设置下的 `pass`、任何工作会话及其最近一次失败的重新加载，以及对每个从文件夹链接的插件，它在最近一次启动时是否加载、运行的是它已批准的内容还是在保护关闭时未经审查就加载的内容、它的 `engines.dsh` 与 `engines.delorun`，以及它注册了哪些会改变同意、守卫或沙箱策略的内容，对未加载的插件则指出要撤销的变更（[约定 C21](../../docs/contracts/c21-changes.zh.md#what-verify-and-doctor-report)），然后读取运行中发布所记录的发布日志检查：验证通过时为 `pass`，`warn` 附带它已保持未检查的时长和记录的原因（或没有记录任何检查），发布日志拒绝它时为 `fail`。不带 `--port` 时，端口检查涵盖 CLI profile 的 studio 所用的端口：即 profile 自己的 `cordis.patch.yml` 在 `webserver` 行上设置的 `port`（由 setup 的 profile 分区写入），或在 profile 没有设置时上游的 3080。当本 home 的该 profile 的 home 进程对其 `status` 请求回答了该端口上的 studio 地址时，被占用的端口按 Delorun 自己的算通过，被其他任何进程占用时则失败。它还报告该 profile 最近一次更新检查，该检查不发出任何请求。每项检查一行；它不联系任何模型，不启动任何容器，除只读的 `docker version` 探测外不运行任何命令。只有接入了导入记录读取器的构建才会打印 stock home 导入行，而这个构建没有 |
| `delorun trash list [--json] \| restore <id> \| purge <id> [--clear-logs] \| empty [--clear-logs] [--profile <name>]` | 列出已删除的 chat 与工作区，以及每项在回收站 30 天中还剩几天，并列出每个已损坏的项目目录及其原因；恢复一个 chat；在终端回答是之后，从会话各代、投影缓存、没有其他 chat 引用的附件、spill 文件和回收站中永久删除一项或每一项，并指出触及的每个存储以及保留了多少个共享附件。它说明片段可能在运行日志中保留 14 天；`--clear-logs` 立即清除 home 的每个运行日志，而不只是该项的记录，并报告无法清除的每个日志。工作区在 studio“设置”的“回收站”分区中恢复，它会再次注册该工作区。`restore`、`purge` 与 `empty` 在持有每个 profile 的 home 锁时运行，任何 profile 的 home 进程运行期间都会被拒绝（[约定 C8](../../docs/contracts/c08-archive-and-trash.zh.md)） |
| `delorun export <chat-or-workspace-id> --out <file> [--profile <name>]` | 把一个 chat，或一个工作区连同它的 chat 与它们所引用的附件，写成以 home 密钥 `secrets/home-auth/home-key.pem`（首次导出时创建）签名的归档。在 chat 历史中发现的密钥按类型和 chat 指出，在本人回答是之前不写入任何内容；文件以 0600 模式新建，从不替换已有文件。它在持有每个 profile 的 home 锁时读取存储，任何 profile 的 home 进程运行期间都会被拒绝 |
| `delorun import <file> [--profile <name>]` | 在写入任何内容之前完整检查归档，先按密钥指纹打印签名者，再打印归档自己声明的字段（每个都带引号，控制字符已转义），并在回答是之后导入。签名无法验证的会被拒绝；home 不信任的密钥需要键入指纹；未签名的归档只有键入 `unverified` 之后才导入。它读取最大 1 GiB 的文件和最大 512 MiB 的条目，在持有每个 profile 的 home 锁时运行，并先完成被崩溃中断的导入。工作区落在 home 的 `archive/imported/` 之下，不进入任何模型请求；studio 目前不打开已导入的 chat，定制内容只列出，不应用 |
| `delorun setup export --out <file> [--profile <name>]`、`delorun setup import <file> [--dry-run] [--profile <name>]` | 把一个 profile 的插件、模型选择与设置作为一个归档在电脑之间迁移（[合约 C8](../../docs/contracts/c08-archive-and-trash.zh.md#the-setup-archive)、[`src/changes/setup-transfer.ts`](src/changes/setup-transfer.ts)）。导出以 home 密钥签名，携带此人添加的插件（确切版本与校验和，或已批准副本的文件）以及 `@delorun/changes` 的策略所携带的模型与插件设置，从不携带密钥、chat、设备、豁免或 setup 的回答；被携带的设置含凭据时停止并指出位置。导入需要终端，把未签名或签名者未知的归档按未验证连同密钥指纹打印，列出每个将添加、移动或移除的插件与每个将设置或恢复默认的设置，询问，保存版本“Before importing a setup”，并通过插件请求操作应用，因此安装检查与对插件代码的审阅依然有效；`--dry-run` 无需终端即可列出，且不更改任何内容。导出接受 `--no-settings`、`--plugin <name>`（可重复）、`--no-local-code` 与 `--note`；导入接受 `--no-settings`（设置保持原样）与 `--remove-others`（移除文件未列出的插件；默认只动文件所列的插件）。 |
| `delorun update [--check \| --report \| --yes] [--data-copy \| --no-data-copy] [--profile <name>]` | 请求 home 进程获取并验证通道上最新的发布，打印[约定 C3](../../docs/contracts/c03-update-report.zh.md) 的报告，进行询问，并通过更新握手应用它；`--yes` 确认没有被禁用、被移除或未验证内容的报告、没有任何 harness 文件被合并进两个发布都没有的内容、且发布日志检查已通过，并进行会话数据复制；合并的 harness 文件连同其差异一起打印，`--no-data-copy` 拒绝复制。低于运行中发布的目标会在安装任何内容之前被拒绝（`TARGET_LOWER`）；`delorun recover rollback` 是唯一回退的途径。`--check` 则立即运行[更新检查](../../docs/design/update-notice.zh.md)，不需要 home 进程也不用 git：它验证通道的已签名元数据，打印提示的那一行和发布的摘要，或者说明本发布已是最新，检查失败时退出码为 1。更新所验证的每个根都是 `trust/root.json`，它锚定在启动 Delorun 的启动器的发布根上，这些根在 `DELORUN_LAUNCHER_ROOTS` 中指明；不是由该启动器启动的 Delorun 会以 `VERIFY_FAILED` 与 `ROOT_NOT_ANCHORED` 拒绝更新，并指出该启动器。Host 为切换而进行的拆除失败或超过 `drainTimeoutS` 时，更新以 `HOST_STOP_FAILED` 结束为 `aborted`，不切换任何内容，Host 再次运行。`--report` 打印完整报告，包括更新将禁用的每个插件及原因，且不应用任何内容 |
| `delorun recover [status \| rollback [--profile-only] \| restore <version> \| safe-mode [--reason <text>] \| exit-safe-mode \| discard <path> \| workspaces [--yes] \| packs]` | 更新之后 profile 所处的状态，附更新记录和保留的 chat 数据；通过 C3 的回滚表回退的方式，有 home 进程运行时通过它，否则（除非给出 `--profile-only`）注册为 home 存储的独占使用者，并在另一个进程使用它们时拒绝；profile 历史版本；安全模式；删除一个保留的副本或搁置的目录；以及 `workspaces`，它在显示将被替换的内容并征得确认后（脚本可用 `--yes` 代为确认），恢复工作区列表的上一份完好副本，并把当前文件保留在一旁。`packs` 会对照已签名的文件列表，对运行中发行版的每个已安装插件包计算哈希，并从该 home 安装时所用的通道，重新获取任何不再匹配的插件包；无法获取的插件包保持移除状态，因此下次启动不会加载被改动的插件包。回滚会用启动器的根所锚定的根来检查它要回到的版本，没有这些根时以 `ROOT_NOT_ANCHORED` 拒绝；`current` 未通过启动检查时，启动器自己用 `delorun recover rollback` 启动 `previous` |
| `delorun changes [list \| show <id> [--diff] \| apply <id> \| discard <id> \| undo <id> \| off <plugin> \| on <plugin> \| protection [on\|off] \| work <plugin> [--for <minutes>] \| done <plugin> \| edit-harness [--discard]] [--profile <name>] [--json]` | 来自该 profile 所链接插件的文件夹、等待你审查的内容和最近的变更，以及已配对手机所做的保护变更（列在“Changed from a phone:”下，`list` 打印到终端时会将其清除）；一项变更连同它的文件、风险行和差异；并且只在终端中、回答是之后，才能应用、丢弃或撤销一项变更、关闭或打开一个插件、打开或关闭保护（默认关闭，此时变更未经审查就加载并被记录；关闭时会再问一次，并说明届时哪些内容会未经审查就加载，这只防误点，不防坐在电脑前的人；[保护设置](../../docs/contracts/c21-changes.zh.md#the-protection-setting)），以及开启一个工作会话，会话中保存在插件文件夹里的每次编辑都会实时加载，最长 `--for` 分钟（默认 120，最多 480），直到 `done` 显示该文件夹的版本并恰好批准它；没有本人批准就结束的会话不批准任何内容（[工作会话](../../docs/contracts/c21-changes.zh.md#work-sessions)）。Delorun 运行期间，运行中的 Host 通过更新通道的 `changes.reload` 重新加载，加载失败的变更会回退，保护关闭时，home 进程会在保存某个已链接插件的文件夹时重新加载它；否则命令持有该 profile 的 home 锁（[约定 C21](../../docs/contracts/c21-changes.zh.md#commands)）。在已安装的发布中，`edit-harness` 生成本人可写的 `app/` 文件副本，保存的编辑是对 Delorun 自身的变更，由同样的子命令决定，或在保护关闭时由下次启动不经审查应用，`--discard` 撤回每一项；已应用的变更从下次启动起运行，已签名的安装会把它交给组合树（[harness 编辑](../../docs/contracts/c21-changes.zh.md#harness-edits)） |

<a id="the-home"></a>
## home

- **解析。**home 在设置了且不为空白的 `DELORUN_HOME` 时就是它，否则是 `~/.delorun`；`@delorun/home` 以 `HOME_INVALID` 或 `HOME_IS_DSH_HOME` 拒绝 C1 所禁止的 home。
- **`DSH_HOME`。**在任何上游代码运行之前，`delorun` 把 `DSH_HOME` 与 `DELORUN_HOME` 设为该 home，把 `DELORUN_PROFILE` 设为该 profile，因此上游、它的 `.env` 层以及每个子进程都使用 Delorun home。继承的 `DSH_HOME` 会被忽略，`delorun status` 会指出它。
- **`~/.dsh`。**`delorun` 从不读取、写入或迁移上游的 home。
- **`DELORUN_VERSION`。**每次调用都在任何上游代码运行之前，把 Delorun 自己的版本导出为 `DELORUN_VERSION`，因此启动预检与插件管理器会对照本 Delorun 检查插件的 `engines.delorun`（[约定 C17](../../docs/contracts/c17-plugin-versions.zh.md)）；每个子进程都继承它。要求另一个 Delorun 版本、或其 `engines.delorun` 不是范围的插件，在安装时被拒绝，在启动时被禁用，消息同时指出 Delorun 与 DSH 的版本。未声明 `engines.delorun` 的插件不受影响。
- **目录树。**除 `status` 之外的每个命令都用 `ensureHomeTree` 以 0700 模式创建 home 的目录树，当 home、`secrets/` 或 `run/<profile>/` 的权限更宽松时，以 `HOME_MODE` 停止并给出修复办法 `chmod 700 <path>`。`delorun` 自己不改变任何模式。

## Profile

CLI profile 是 `default`，或由 `DELORUN_PROFILE` 或 `--profile` 选定的名称，遵循[约定 C1](../../docs/contracts/c01-home-layout.zh.md#profiles) 的 profile 名称规则，启动器也应用该规则：1 到 32 个小写字母、数字、`-` 或 `_`，以字母或数字开头，且不是保留名称 `desktop`、`headless`、`data-users` 与 `node_modules`。保留名称无论大小写都会被拒绝，退出码为用法错误，消息指出该名称及原因：`desktop` 是桌面应用的 profile，`headless` 是 `delorun headless` 所启动的 profile，`run/data-users/` 保存 home 范围排他的记录，`profiles/node_modules/` 是上游的包层。`delorun plugin --profile desktop` 被上游自己的解析器拒绝，因此 `delorun` 从不运行、初始化或更改 `profiles/desktop/` 或它的锁。Setup 的入口以 [`@delorun/bundle-local`](../../packages/bundle-local/README.zh.md) 的 `DELORUN_PROFILE_BUNDLES` 创建 CLI profile：即上游的 `web` profile 模板（其 Web 应用提供 studio 服务），后面是 `@delorun/bundle-local`。然后它让每个 Delorun 组合包可被导入，方式与上游让它自己的组合包可被导入相同：上游的运行时解析已经提供的组合包（已发布的安装把它放在上游的包旁边）保持不动；只有这个 `delorun` 携带的组合包（如在源码检出中）用上游自己的 `dsh plugin add link:<directory>` 操作添加，该操作把它记录在 profile 的 `package.json` 中并用 pnpm 安装。该操作的输出进入 profile 的 `home-<profile>` 运行日志，每条记录一行，终端显示一行进度 `Linking Delorun's parts into the profile…`，后接 `done` 或 `failed`；失败的操作的错误会指出该日志的文件。

启动像上游的启动一样加载该 profile，并在某个 Delorun 组合包（`@delorun/` 作用域中的任何组合包）因无法解析、读取或接受而被跳过时拒绝启动它。否则上游会用其余的层和它自己的默认值启动，而这些默认值会把会话日志上传到 DeepSeek。错误会连同上游给出的原因和修复办法指出每个被跳过的组合包：在源码检出中，对这个 `delorun` 携带的组合包使用 `delorun plugin --profile <name> add link:<directory>`；否则重新安装 Delorun 或运行 `delorun plugin --profile <name> install`。在 profile 启动、其 Loader 稳定之后，启动还会检查 Delorun 组合包插入的每一行以及模块位于 `@delorun/` 作用域中的每一行：当某个已启用的行没有激活时，例如导入失败，`delorun` 会通过它自己的拆除（不会结束任何进程）拆除应用，最多等待 5 秒，然后释放锁并以退出码 1 退出，在上游自己带有原因的警告之下指出每一行及其修复办法。失败或耗时更长的拆除会并入拒绝的原因；此时启动不回滚任何内容、不再启动任何内容并保持锁，拒绝打印之后进程以退出码 1 退出。`delorun headless` 以同样的方式拆除被拒绝的 profile，并在其拆除未完成时，于拒绝打印之后把进程交给上游有界的关闭流程。Web 应用在其 Loader 稳定时于浏览器中打开 studio，因此被拒绝的启动可能在已停止的服务器上留下一个打开的 studio 页面。被跳过的上游组合包和未激活的上游行按上游的报告方式报告，不会阻止启动。

插件的密钥从不进入 patch 文件（[约定 C1](../../docs/contracts/c01-home-layout.zh.md#secrets)）。在它启动的每个 Host 上，`delorun` 都会在 Loader 挂载某一行之前注册两项拒绝：一是拒绝这样的配置编辑，即会把配置字段（其 schema 角色为 `secret`，例如上游的 web 搜索插件的 DeepSeek API 密钥）的值保存进 profile 的 patch，无论请求来自 studio 的设置、agent 的 `configure` 操作、旧 `settings.yaml` 的导入，还是配置编辑器的其他调用方；二是拒绝其 patch 中含有这样的值的任何 profile 历史版本，包括更新的快照；没有 Host 运行时所拍的快照同样被拒绝。在启动或 `delorun headless` 运行提供服务之前，profile 的 patch 或 home 的 `cordis.patch.yml` 中已有的值，只要插件在它旁边的 `credential-ref` 字段中指明了已存储的密钥，就会通过 Host 的凭据提供方移入 `.credentials.yaml`，启动会打印它更改的每个文件和字段，但从不打印值；无法移动的值保持原处，每次启动都会在标准错误和 home 日志中打印它以及移动它的办法，同时历史不保存任何版本（[secret 字段](src/secret-fields.ts)）。启动无论如何都继续，因此从曾把密钥保存在 patch 中的 Delorun 更新能够提交。

在加载 profile 之前，启动会向这样的 CLI profile 添加 `@delorun/bundle-studio`：其组合包列表指明了 `@delorun/bundle-local` 却没有 studio 组合包，这是 studio 组合包出现之前 setup 创建的 profile（[`studio-bundle.ts`](src/studio-bundle.ts)），所用的是 setup 用来链接 Delorun 组合包的操作，其输出进入 home 进程的日志。它打印进度行，并在添加了该组合包之后打印一行；已列出该组合包的 profile，或不是由 Delorun 的 setup 创建的 profile，保持不变。无法添加该组合包时，启动以 stock 外观继续并说明原因。该添加是 profile 的一次性变更之一：一旦完成，profile 的 `delorun-migrations.json` 就会列出它，以后的启动不再添加该组合包，因此移除 studio 组合包的人保留 stock 外观。无法读取的记录不会添加任何内容：启动会发出警告，指出该文件，并说明删除它即可让下次启动应用这些变更（[C1](../../docs/contracts/c01-home-layout.zh.md#profiles)）。

## Setup

Setup（[`src/setup/`](src/setup/index.ts)）回答[约定 C11](../../docs/contracts/c11-setup-answers.zh.md) 的问题并写入 CLI profile。三种形式产生相同的答案，因此产生相同的写入：

- **问题**需要终端。第一屏询问“你将如何使用 Delorun？”（只在这台计算机上自己用、也从手机或其他设备使用，或用于脚本和自动化），这决定默认值并决定主流程询问什么：隐私说明；当 `~/.dsh` 是目录而 Delorun home 中没有 chat 时，对 stock home 的 chat、附件和工作区列表的复制，除非本人回答是，否则回答为否（[`src/import-home/section.ts`](src/import-home/section.ts)）；带密钥的模型提供商与 prompts 问题；以及手机用例的远程访问。审查屏列出每个答案，它的“更多设置”选项询问其余的内容：是否检查新发布（预选“是”），以及后台、远程访问和 profile 分区。第一个之后的每个问题都可以回到上一个（选择题用“← 返回”，文本或密钥问题用空输入），审查屏会在写入任何内容之前列出答案。提供商问题在下文描述。键入的密钥在存储之前，会用一次对提供商来源的实时请求检查；检查失败时会说明原因，并让本人重新输入密钥或继续，本人选择继续的密钥会在审查屏上显示为未验证并附原因。隐私说明是 [`@delorun/bundle-local`](../../packages/bundle-local/README.zh.md) 的，从它的 `./statements` 导出读取。Setup 不再询问它只是记录的那四个问题（命令在哪里运行、studio 附加功能、对其他模型的帮助、桌面分析）；上游的两个选择加入项保持关闭，由“设置 → 安全 → 隐私”更改它们。
- **`--yes`** 采用每个默认值，除非 `--provider <id>` 指明了一个，否则不设置任何模型提供商；没有指明时，它会打印如何添加。`--model <id>` 指明模型（除 DeepSeek 之外的每个提供商都需要），`--base-url <url>` 指明 `openai-compatible` 的端点，`--key-env <NAME>` 指明每次启动时读取密钥的变量，默认是提供商自己的变量；密钥从不取自命令行。变量未设置时，setup 以指明该变量的错误停止。除非给出 `--check-key`（它需要 `--provider`），否则不会对密钥做实时检查。与其他形式一样，带 `--no-update-check` 时发布检查是关闭的。
- **`--config <file>`** 读取答案文档。它会拒绝以下文档：启用远程访问或 stock home 导入的（后者需要先在终端中显示它的预览）；打开变更保护的（只有终端证明才能做到）；带有 setup 已不再询问的密钥的（消息指出已移除的键）；在任何字段中带有凭据值的；指明了 setup 不提供的提供商、或其已安装目录中没有列出的模型的；或指明了 4、3、2 之外的 schema 版本的；版本 2 的文档没有 `updateCheck`，读作检查开启，版本 2 或版本 3 的文档的提供商读作 DeepSeek 及 profile 的默认模型，这是这些版本所应用的。拒绝信息指出字段，从不回显值。

模型提供商（[`src/setup/provider-section.ts`](src/setup/provider-section.ts)、[`src/setup/providers.ts`](src/setup/providers.ts)）是[约定 C11](../../docs/contracts/c11-setup-answers.zh.md#model-providers) 中按名称列出的提供商之一，或者暂时不设：DeepSeek 使用上游的 DeepSeek 适配器，无需安装；Anthropic、Google Gemini、Groq、Mistral、Moonshot AI、OpenAI、OpenRouter、Together AI、xAI 以及任何 OpenAI 兼容端点使用上游的 pi-ai 适配器。该分区先询问提供商；对 OpenAI 兼容端点，则询问它的基础 URL（其中不得含用户名、密码、查询或片段，对指向另一台计算机的纯 `http` 会发出警告）及其模型 id；然后询问密钥的来源（现在键入，或每次启动时取提供商的变量）以及密钥。模型来自提供商的已安装目录，从提供商推荐的模型开始，除 DeepSeek（其默认值是 profile 的）之外的每个提供商都会询问；`delorun setup key` 对 DeepSeek 也会询问。“稍后选择”不改变任何提供商行，并说明新 chat 仍然以哪个模型开始。密钥检查是对提供商来源上的模型列表或密钥端点的一次带认证的 `GET`，重定向会被拒绝，绝不是一次补全。写入的是 studio“设置 → Agent → 模型”与模型选择器所保存的行：带有自己变量和默认模型的 DeepSeek 不写入任何行，因此 profile 的组合方式与 stock DeepSeek Harness 相同；pi-ai 提供商在 `llm-pi-ai` 上设置其路由，并由 `agent-default-model` 选择模型。`delorun setup key` 再次询问，或接受 `--provider` 及其标志而不询问任何内容。

每个主题都是 [`src/setup/sections.ts`](src/setup/sections.ts) 的注册表中的一个分区，每个用例有一份计划：`privacy` 在主流程中显示它的说明，并在“更多设置”下询问它的问题；`import`、`key` 与 `prompts` 在主流程中询问（`import` 不用于脚本和自动化）；`background`、`reach`（远程访问，[`src/reach/setup-section.ts`](src/reach/setup-section.ts)）与 `profile` 在“更多设置”下询问，`reach` 在手机用例的主流程中询问。`delorun setup privacy` 询问是否检查新发布，并像“设置 → 通用 → 更新”一样写入答案。`delorun setup <section>` 在已设置的 profile 上再次运行一个分区，`delorun setup --list` 列出它们。在终端中对已完成的 profile 运行 `delorun setup` 会再次运行整个流程（[`src/setup/current.ts`](src/setup/current.ts)）：每个问题都从配置当前持有的答案开始，由与该分区的写入配对的读取器读取（`readUpdateCheckRow`、`readPromptsRows`、`readProviderAnswer`、`profileStudioPort` 与 `readReachRowAt`），对于用例、后台选择以及 patch 中没有行的 profile，则以答案记录作为后备。profile 名称问题被跳过，密钥问题首先提供 `Keep the saved key`，其 `unchanged` 方法表明答案即当前答案的分区不写入任何内容并报告为保持不变，审查屏标出已更改的答案。保持危险模式时，只要其授权有效，就不再询问第二次同意；打开它则两者都询问。被中断的重新运行像首次运行一样，从它的运行记录恢复。以后的包用 `SectionRegistry.register(section, { order })` 添加它的分区；`order` 把它放在其他分区之间。分区的写入会收到 home、profile 目录、键入的密钥以及 `delorun` 继承的环境。

prompts 的答案会生效：“先问我”与“少问（像 DeepSeek Harness）”把 `delorun-permission-defaults`、`delorun-instruction-consent`、`delorun-mcp-consent` 与 `delorun-schedule-consent` 各行的 `config.enabled` 写为 Delorun 的默认值和约定 C16 注册表中对应开关的对等值。抓取防护是拒绝而不是提示，保持开启。“从不询问（危险）”（[`src/setup/dangerous.ts`](src/setup/dangerous.ts)）在警告并键入短语 `full access everywhere` 之后选择，或用 `--yes --prompts dangerous --accept-dangerous-mode`，或在 `--config` 文档中写 `acceptDangerousMode: true`，对 root 用户则被拒绝。它把三个同意行设为它们的对等值，在权限默认值行上设置 `fullAccessEverywhere`，并在权限存储的锁之下写入授权文件 `secrets/permission-defaults/full-access-everywhere.json`；选择另一个答案则删除该文件。该模式开启期间，`delorun` 的启动、`delorun status` 与 `delorun doctor` 会显示它。

Setup 按顺序运行它的步骤：创建 CLI profile（用 profile 分区所选的名称），然后把每个分区的写入（发布检查行、不含其凭据的 stock home 导入、以 0600 模式写入上游 `.credentials.yaml` 中提供商密钥变量之下的键入密钥以及提供商的各行、prompts 各行、studio 端口行）写入 profile 的 `cordis.patch.yml`。关闭发布检查时，写入 `delorun-update-check` 行，其形式是上游的设置服务保存它的形式，即它的 id、插件名称和带有 `enabled: false` 的完整配置；打开时，setup 不在该行上留下配置。每次写入都在运行开始之前完成，因此在 setup 中关闭的检查不发出任何请求。运行尚未结束时，`run/<profile>/setup-progress.json` 保存不含任何密钥的答案以及已完成的步骤，因此被中断的运行会从第一个未完成的步骤恢复。每个步骤都完成后，setup 删除该文件，并把答案（包括哪些分区被看过、被回答或被跳过）写入 `profiles/<profile>/setup-answers.json`，供 studio 的引导和启动命令读取；[`readBackgroundAnswer`](src/setup/background.ts) 返回后台答案。在其分区存在之前，凭据转发记录为关闭。

每种形式都在 [`src/setup/ending.ts`](src/setup/ending.ts) 中以打印后续步骤结束，且不启动任何内容：如何用 `delorun` 启动并打开 studio，以及安装指南的首次 chat 一节（`FIRST_CHAT_PAGE`）；手机用例的 `delorun devices approve`；脚本用的 `delorun headless`；在有启动本次运行的启动器版本（`DELORUN_LAUNCHER_VERSION`）时，以该版本安装 `delorun` 命令；以及如何用 `delorun setup <section>` 更改答案。在任何问题处按 Ctrl-C 都以退出码 130 退出，并说明未保存任何内容。

<a id="the-home-process"></a>
## home 进程

`delorun start --foreground` 与不带参数的 `delorun` 用 `HomeProcess.start` 在本进程中运行 home 进程：它持有 `run/<profile>/home.lock`，写入新的启动令牌，在更新通道 `run/<profile>/update.sock` 上监听，并通过上游的 profile 运行器启动该 profile 作为它的 Host。在它持有锁之前，它在 `run/data-users/` 之下注册为该 profile 的 home 进程，直到它退出，因此在它运行期间，另一个 profile 的更新准备、复制、恢复或回滚会以 `CHATS_RUNNING` 拒绝；而在 `delorun trash`、`export` 或 `import` 运行或另一个 profile 的更新进行中时，它拒绝启动（[约定 C19](../../docs/contracts/c19-home-process.zh.md#the-home-process)）。它写入 `home-<profile>` 运行日志，在前台时终端也显示它的输出。无论启动多少次，恰好一个持有锁，包括越过已死亡持有者的锁。对存活的持有者，会通过更新通道询问其状态：它回答时，第二次启动打印正在运行的进程并以退出码 0 退出；它在 2 秒内不回答时，启动以 `HOME_UNRESPONSIVE` 停止。无论进程因何结束，锁、令牌文件和套接字都随之消失；被 `SIGKILL` 杀死的进程会把它们留下，下次启动会替换它们。

启动以 C1 的隔离在上游的本地沙箱提供方上启动该 profile（`sandbox` 行）：`protectedHome` 是规范化的 Delorun home，`protectedHomeReadable` 是 C1 的读取豁免加上该 profile 已批准的插件副本（`changes/profiles/<profile>/active`，来自 `@delorun/changes` 的 `activeCopiesEntry`；该条目在每次包装时解析，因此之后批准的副本立即可读，且只读），`deniedSockets` 是 `run/<profile>/` 之下更新通道的和监管器的套接字（没有监管器运行，因此只存在更新通道的套接字）、活动 Docker 上下文的套接字及其真实路径，以及存在时 `~/Library/Containers/com.docker.docker/Data/` 与 `~/.docker/run/` 之下 Docker Desktop 的 macOS 套接字，因此在方言强制执行这些规则的地方，受限的工作区命令既不能读取 home 或令牌，也不能连接到任一通道：bwrap 与 Seatbelt 强制执行全部规则，Landlock 强制执行读写规则而没有套接字规则，Windows 运行器只隔离写入。WSL 与 Linux 下 Docker Desktop 的控制套接字目录不被拒绝。这些设置通过一个 overlay patch 传递，即 Host 运行期间存在的 0600 模式的 `run/<profile>/sandbox.patch.yml`。该 overlay 是启动所传入的最后一个 patch，因此它应用于每个设置该行的层之上：profile 的组合包、它自己的 `cordis.patch.yml`、应用于每个 profile 的 home 的 `cordis.patch.yml`，以及安全模式的 overlay。某一层的 `config` 会替换该行的整个配置，因此 overlay 按配置它的最后一层所设置的样子保留该行的其他设置，并保留每一层所列出的被拒绝套接字。当组合后的设置含有无法带过去的表达式时，启动会拒绝它们；对设置运行器本身（`runnerCommand` 或 `runnerFailureSignatures`）的任何层，启动也会拒绝并指出每个文件：运行器命令会跳过提供方的内置选择，在提供方报告完全强制执行的同时以不受隔离的方式启动该行。

不带 `--foreground` 的 `delorun start` 会启动与终端分离的 `delorun start --foreground`，标准输入关闭，输出进入它的日志，并最多等待 120 秒让 home 进程报告 `running`；先退出或未能及时报告 `running` 的 home 进程会用一句平实的话报告，该句指向 `delorun logs`，studio 端口被占用时则连同已知的占用程序一并指出。`delorun stop` 与 `delorun status` 读取令牌文件，并通过更新通道发送 `stop` 或 `status`；没有存活的锁持有者时，`stop` 打印 Delorun 没有运行并以退出码 0 退出，`status` 以退出码 3 退出。

当命令从 C1 存储的 `runtimes/<version>/` 运行时，home 进程获得 `src/update/` 的更新支持：存储、锚定在 `trust/` 之下根链上的 `@delorun/install` 发布通道、基于 profile 和暂存目标读取器的 C3 报告、profile 历史以及会话数据副本。从源码检出运行时，它没有存储，并拒绝更新请求。从存储运行时，启动还会把更新检查（[notice-host](src/update/notice-host.ts)）挂接到 Host 的 `delorunUpdateCheck` 服务，该服务在到期时于启动时运行它，并按其间隔运行，对每个更新的发布只打印一次它的那一行，并向 studio 提供它的提示；其 profile 关闭了该检查的启动会删除它的记录。后台启动在 home 进程报告 `running` 之后，打印最近一次检查的那一行。Host 根据上游的 `agent/status` 事件统计它运行中的 chat，因此 `delorun stop` 与更新会等待运行中的 chat（包括它们等待期间开始的轮次）；它的健康检查是 C3 的 H1 到 H5（[host](src/update/host.ts)）。描述符 3 为套接字或管道的进程被启动为更新的后继进程：它从中读取交接并运行 `HomeProcess.takeOver`。

每个 Host 都经过 [`src/compose.ts`](src/compose.ts)，它使已组合和已启动的行符合 C19 的 [Host 不变量](../../docs/contracts/c19-home-process.zh.md#host-invariants)：每个必需的行（`sandbox` 以及 Delorun 组合包插入的每一行）由声明它的组合包恰好插入一次并运行该组合包的插件，任何其他层对其 id 的第二次插入都会被拒绝，安全模式不豁免其中任何一行，启动之后，这类行所提供的每个服务（`sandbox`、`fetchGuard`、各同意服务、`delorunTurnGate`）都必须由该行的 fiber 提供。在 CLI profile 和 `headless` profile 中，更新闸门保持每个轮次的第一步，直到启动在该检查之后释放它。在 Host 启动之前，[`src/pre-start.ts`](src/pre-start.ts) 运行 `delorun start --foreground` 与 `delorun headless` 共用的一份有序步骤列表：被中断导入的撤回与更新提示的检查（两者目前都是什么也不做的槽位）、被中断恢复的完成，以及 profile 的一次性变更。Host 的启动环境是上游的 `.env` 层叠加在 `delorun` 启动时所带的环境之上；`main` 只捕获该环境一次并向下传递，设置了 `DELORUN_` 名称的 `.env` 层会在任何层应用之前被拒绝。

<a id="opening-the-studio"></a>
## 打开 studio

[`src/open/`](src/open/studio.ts) 打开 studio。`delorun open` 用令牌文件中的启动令牌通过更新通道发送 `studio.open-token`；home 进程向其 Host 的连接请求指向 studio 回环根的启动 URL（[host link](src/open/host-link.ts)），在 Delorun 的组合下，该 URL 的令牌只能使用一次，并在 60 秒后过期（约定 C4，“启动令牌”）。链接交给 `xdg-open`（它自己读取 `BROWSER`）、macOS 上的 `open` 或 Windows 上的 `cmd.exe /c start`。在 WSL 下，设置了 `BROWSER` 时交给该变量所指明的程序（其以冒号分隔的列表中的第一项，链接作为它的唯一参数），只有 `BROWSER` 未设置或为空时才交给 Windows 默认浏览器 `cmd.exe /c start`。命令写出的其他任何内容都不含该链接。要完全不打开任何东西，请使用 `--print`。`--print` 写出链接以及一行说明它只能使用一次的话。链接指明 studio 的回环主机和端口，并且只能在那里登录：通过 `localhost` 而非 `127.0.0.1`、或通过 `ssh -L` 转发到另一个本地端口来访问 studio 的浏览器，会被一个指明该链接所生成的地址的页面拒绝，而 `delorun open --print --port <n>` 为转发端口生成链接。其 studio 监听回环之外的地址、或把它发布在公开 URL 上的 Host 不提供链接（`STUDIO_UNAVAILABLE`，附原因），持有通道却在 2 秒内不回答的 home 进程会被报告为没有回答，而不是没有运行。

直接在 Delorun CLI profile 上运行上游的 `dsh`、而不是 `delorun start`，无法通过打印出的地址登录：开关打开时，`dsh web:` 行不带令牌，而 `delorun open` 需要 `delorun` 的 home 进程。只有 `dsh` 自己的浏览器交接（它生成一次性链接）才能在那里登录。请用 `delorun start` 启动该 profile，并用 `delorun open` 打开 studio。启动从不向上游的浏览器交接传递链接（`--no-open`）：它打印 `Run delorun open to open the studio in your browser.`，而 `delorun start --open`、不带参数的 `delorun` 以及 setup 的结尾，会在 home 进程运行之后通过同一个请求打开 studio。

<a id="how-delorun-runs-upstream"></a>
## delorun 如何运行上游

`delorun` 只通过上游的 profile 运行器启动应用，这是根 `AGENTS.md` 的要求。启动与 `headless` 调用来自 `@deepseek-ai/dsh/profile-boot` 的上游 `runProfile`，分别针对 CLI profile 与 `headless` profile，就像桌面 Host 对它的 profile 所做的那样，每次都经过 Delorun 的组合（[`src/compose.ts`](src/compose.ts)）；两者都传入 `failLoud: false`，因为入口点唯一的最后手段处理器会报告崩溃并释放已注册的 Host；启动还传入 `signals: false`，因为它的 home 进程唯一的信号监听器服务于它启动的每个 Host，而 `headless` 保留上游的信号处理器；`plugin` 调用上游的 `runCli`，并把它的 `argv` 选项设为 `dsh` 会收到的参数。该选项是 Delorun 为这个命令对上游所做的唯一更改，记录在差异台账中，类型为 `generic-fix`；上游已经从 `DSH_HOME` 解析它的 home，因此 home 无需更改。

<a id="extension-points"></a>
## 扩展点

- **命令**是一个导出一个 `CliCommand`（`src/command.ts`）的模块，并在 `src/main.ts` 的 `COMMANDS` 中添加一行。`delorun doctor` 属于 `src/doctor/`，`delorun logs` 属于 `src/logs/`，各自通过这一行接入。
- **`delorun doctor` 的密钥查找。**被检查的密钥是新 chat 所用提供商的密钥：即 profile 的 `agent-default-model` 行的路由，或 profile 没有设置时 DeepSeek 的，从路由所在行指明的 `apiKeyEnv` 或提供商自己的变量中读取。不指明变量的路由会作为警告报告，因为它的适配器自己找到密钥。读取按以下顺序，检查第一个持有密钥的来源：setup 存储在 home 的 `.credentials.yaml` 中的引用、进程环境变量、调用目录的 `.env`，然后是 home 的 `.env`。检查只报告来源的名称，从不打印密钥；它离线检查格式，包括 DeepSeek 密钥的 `sk-` 前缀，而对 OpenAI 兼容端点没有长度规则，并且不会把密钥发送给提供商。
- **Setup** 是 `src/setup/index.ts` 中的 `runSetup`，`delorun setup` 与首次运行都调用它。它的分区在 `src/setup/sections.ts` 中，带有回退能力的步骤运行器是 `src/setup/steps.ts`，位于 `src/setup/prompts.ts` 的 `Prompter` 接口之后，因此测试可以对着脚本化的提示器运行它们。
- **home 进程的依赖**是 `src/start.ts` 中的 `StartDependencies`：profile 的准备与运行器、环境加载器、持有者探测（更新通道的 `status` 请求）、退出钩子、输出捕获和 studio 打开器，因此 spec 可以对着替身运行一次启动。

<a id="not-implemented"></a>
## 未实现

CLI 不包含以下内容；[路线图](../../docs/guide/roadmap.zh.md)说明了 Delorun 不做什么。

- 登录时启动（`delorun start --at-login`、`delorun stop --at-login`）、`delorun status --follow`，以及启动序列的隔离探测。
- chat 闸门不保持任何计划投递：更新等待期间到期的投递，其轮次会以 `UPDATE_PENDING` 被拒绝。报告不读取撤销列表，因为没有任何发布发布过撤销列表（[`@delorun/update`](../../packages/update/README.zh.md#not-implemented)）。
- Setup 的远程访问问题。Setup 将远程访问记录为关闭。
- Windows 的 DACL 检查（[#48](https://github.com/Delo-Run/delorun/issues/48)）：在 Windows 上，目录检查什么也不检查，受保护文件的检查只看文件类型。
- `reach`、`devices` 与 `dev`。
- 在 studio 中打开已导入的 chat。
- `delorun verify --mode`，以及除 `release-signature` 与 `runtime-files` 之外的每个已注册检查。`delorun verify` 报告默认模式 `warn`，因为没有任何东西读取 `integrity.mode`。

<a id="development"></a>
## 开发

从检出运行 `delorun`，使用 `pnpm --filter @delorun/cli delorun <command>`；这需要先运行 `pnpm run build:artifacts` 与 `pnpm --filter @delorun/bundle-local run build`，因为上游的构建不构建 Delorun 的包；setup 把该组合包链接到 CLI profile 中。spec 用 `node_modules/.bin/vitest run --config delorun/vitest.config.ts delorun/apps/cli` 运行，应用用 `node_modules/.bin/tsc --noEmit -p delorun/apps/cli/tsconfig.json` 做类型检查。spec 使用临时的操作系统 home，从不触及真实的 `~/.delorun` 或 `~/.dsh`。
