# @delorun/cli

English | [中文](README.zh.md)

## Summary

This app is the `delorun` command. Before any upstream code runs, it resolves and prepares the Delorun home through [`@delorun/home`](../../packages/home/README.md), which implements [contract C1](../../docs/contracts/c01-home-layout.md)'s home, selects the CLI profile, and runs that profile through upstream's profile runner with the Delorun home as `DSH_HOME`. A new home goes to setup's entry point first. A start runs the profile's home process of [`@delorun/home-process`](../../packages/home-process/README.md) ([contract C19](../../docs/contracts/c19-home-process.md)), which holds the profile's home lock, so one home process runs per profile, and `stop` and `status` reach it through its update channel.

## Commands

Exit codes: 0 done, 1 failed, 2 a wrong command line, 3 no home process runs for the profile (`status`, `update`). A failure prints, on standard error and in the format the npm launcher shares (`@delorun/home`'s `renderRefusal`), a line saying what Delorun did, a `Why:` line with the error's code, such as `HOME_MODE`, and the path or detail it concerns, and the commands or steps that help under `What you can do:`, naming the `--profile` the command line gave. A command-line error prints its own message. A failure no package describes prints `Delorun stopped: <message>`, without a stack; `delorun` keeps no log of its own failures. Every refusal passes `@delorun/logs`'s redactor before it is printed, the one the operational logs use, so a key, token or credential path in an error's message prints as `[redacted:<kind>]`; in the home process the redactor is its log's, which also knows the start token. A failure no command caught, such as an unhandled rejection after `main` returned while upstream's profile runner owns the process, prints the same redacted refusal instead of a Node stack and exits 1: `src/last-resort.ts` installs upstream's `installFailLoud` once per process, before anything else registers, with its diagnostic routed into the refusal, so its handling of the activation rejections upstream's boot already reported still applies. Without a registered teardown it exits at once, inside the listener. The home process and `delorun headless` register their current Host's teardown (`registerFatalRelease`), which the exit awaits for at most upstream's 2 seconds, so a crash disposes the Host before the process ends. The last remedy says where the full detail is: in the home process, an `error` record in its `home-<profile>` log with the stack, which `delorun logs home --profile <name>` shows; a plain command, `delorun headless` and `delorun plugin` keep no log, and the remedy says so. The stack never reaches the terminal. `src/refusals.ts` composes the describer each package exports next to its errors, and a spec fails when an exported error class of a fork package is neither described there nor named as one that never reaches `delorun`; the spec reads each package's exports, its `exports` entry points mapped to their sources and every module under `src/`, through TypeScript's checker, so export lists, renamed and default exports and re-exports count.

## The home

- **Resolution.** The home is `DELORUN_HOME` when it is set and not blank, otherwise `~/.delorun`; `@delorun/home` refuses the homes C1 forbids with `HOME_INVALID` or `HOME_IS_DSH_HOME`.
- **`DSH_HOME`.** `delorun` sets `DSH_HOME` and `DELORUN_HOME` to the home and `DELORUN_PROFILE` to the profile before any upstream code runs, so upstream, its `.env` layers and every child process use the Delorun home. An inherited `DSH_HOME` is ignored, and `delorun status` names it.
- **`~/.dsh`.** `delorun` never reads, writes or migrates upstream's home.
- **`DELORUN_VERSION`.** Every invocation exports Delorun's own version as `DELORUN_VERSION` before any upstream code runs, so the start preflight and the plugin manager check a plugin's `engines.delorun` against this Delorun ([contract C17](../../docs/contracts/c17-plugin-versions.md)); every child process inherits it. A plugin that requires a Delorun this one is not, or whose `engines.delorun` is not a range, is refused at install and disabled at start, and the message names both the Delorun and the DSH version. A plugin that declares no `engines.delorun` is unaffected.
- **The tree.** Every command except `status` creates the home's tree at mode 0700 with `ensureHomeTree` and stops with `HOME_MODE` and the fix `chmod 700 <path>` when the home, `secrets/` or `run/<profile>/` is laxer. `delorun` changes no mode itself.

## Profiles

The CLI profile is `default`, or the name `DELORUN_PROFILE` or `--profile` selects, under [contract C1](../../docs/contracts/c01-home-layout.md#profiles)'s profile-name rule, which the launcher applies too: 1 to 32 lowercase letters, digits, `-` or `_`, starting with a letter or a digit, and none of the reserved names `desktop`, `headless`, `data-users` and `node_modules`. A reserved name is refused in any letter case with the usage exit code and a message that names it and why: `desktop` is the desktop app's profile, `headless` the profile `delorun headless` boots, `run/data-users/` holds the home-wide exclusion's records, and `profiles/node_modules/` is upstream's package layer. `delorun plugin --profile desktop` is refused by upstream's own parser, so `delorun` never runs, initialises or changes `profiles/desktop/` or its lock. Setup's entry point creates the CLI profile with [`@delorun/bundle-local`](../../packages/bundle-local/README.md)'s `DELORUN_PROFILE_BUNDLES`: upstream's `web` profile template, whose Web application serves the studio, followed by `@delorun/bundle-local`. It then makes each Delorun bundle importable as upstream makes its own bundles importable: a bundle that upstream's runtime resolution already supplies, as a released installation carries it beside upstream's packages, is left alone; one that only this `delorun` carries, as in a source checkout, is added with upstream's own `dsh plugin add link:<directory>` operation, which records it in the profile's `package.json` and installs it with pnpm. The operation's output goes to the profile's `home-<profile>` operational log, one record per line, and the terminal shows one progress line, `Linking Delorun's parts into the profile…` followed by `done` or `failed`; a failed operation's error names that log's file.

A start loads the profile as upstream's boot does and refuses to boot it when a Delorun bundle, any bundle in the `@delorun/` scope, was skipped because it could not be resolved, read or accepted. Upstream would otherwise start with the remaining layers and its own defaults, which upload session logs to DeepSeek. The error names each skipped bundle with upstream's reason and its fix: in a source checkout, `delorun plugin --profile <name> add link:<directory>` for the bundle this `delorun` carries; otherwise reinstalling Delorun or `delorun plugin --profile <name> install`. After the profile boots and its Loader settles, the start also checks every row a Delorun bundle inserts and every row whose module is in the `@delorun/` scope: when an enabled one did not activate, for example because it failed to import, `delorun` tears the application down through its own teardown, which ends no process, waiting at most 5 seconds, then releases the lock and exits 1, naming each row and its fix, below upstream's own warning with the cause. A teardown that fails or takes longer joins the refusal's reason; the start then rolls nothing back, starts nothing again and keeps the lock, and the process exits 1 once the refusal is printed. `delorun headless` tears a refused profile down the same way and, when its teardown does not finish, hands the process to upstream's bounded shutdown once the refusal is printed. The Web application opens the studio in the browser when its Loader settles, so a refused start can leave a studio page open on a stopped server. A skipped upstream bundle and an inactive upstream row are reported as upstream reports them and do not stop the start.

A plugin's key never lands in a patch file ([contract C1](../../docs/contracts/c01-home-layout.md#secrets)). On every Host it boots, `delorun` registers, before the Loader mounts a row, the refusal of a configuration edit that would save a value for a config field whose schema role is `secret`, such as the DeepSeek API key of upstream's web search plugins, into the profile patch, whether the studio's Settings, the agent's `configure` action, the import of an old `settings.yaml` or another caller of the configuration editor asks, and the refusal of any profile history version, an update's snapshot included, whose patch holds one; a snapshot taken while no Host runs is refused too. Before a start or a `delorun headless` run serves, a value the profile patch or the home's `cordis.patch.yml` already holds is moved into `.credentials.yaml` through the Host's credentials provider wherever the plugin names a stored key in a `credential-ref` field beside it, and the start prints each file and field it changed, never the value; a value it cannot move stays, and each start prints it on standard error and in the home log with the way to move it, while the history saves no version ([secret fields](src/secret-fields.ts)). The start goes on either way, so an update from a Delorun that had saved a key in a patch commits.

Before it loads the profile, a start adds `@delorun/bundle-studio` to a CLI profile whose bundle list names `@delorun/bundle-local` but not the studio bundle, as setup made profiles before the studio bundle existed ([`studio-bundle.ts`](src/studio-bundle.ts)), with the operation setup uses to link Delorun's bundles, its output in the home process's log. It prints the progress line and one line when it has added the bundle; a profile that lists the bundle, or that Delorun's setup did not make, is left as it is. When the bundle cannot be added the start goes on in the stock look and says why. The addition is one of the profile's one-time changes: once it completes, the profile's `delorun-migrations.json` lists it and no start adds the bundle again, so a person who removes the studio bundle keeps the stock look. A record that does not read adds nothing: the start warns, naming the file and that removing it lets the next start apply the changes ([C1](../../docs/contracts/c01-home-layout.md#profiles)).

## Setup

Setup ([`src/setup/`](src/setup/index.ts)) answers the questions of [contract C11](../../docs/contracts/c11-setup-answers.md) and writes the CLI profile. The three forms produce the same answers, and so the same writes:

- **The questions** need a terminal. On a new home the main flow is short: the privacy line (a note with a link), "Use Delorun from your other devices too? (phone, tablet, another computer, over Tailscale)" (No, or Yes over Tailscale), the copy of the stock home's chats, attachments and workspace list when `~/.dsh` is a directory and the Delorun home has no chat, answered with Yes, Later or a list of what stays behind ([`src/import-home/section.ts`](src/import-home/section.ts)), and the port question only when 3080 is busy. Setup then starts Delorun in this terminal and opens the studio (`src/setup/foreground.ts`); with a Yes to other devices it asks the PIN, which the running home stores, and it asks whether to keep the `delorun` command. It does not ask how the person will use Delorun, for the model key (the studio's Models step does), the prompts answer, the background answer, the release check or the profile name: those take their defaults, and `delorun setup key`, `prompts`, `background`, `privacy` and `profile` ask them. Each question can return to the one before it ("← Back" on a choice, an empty entry on a text or key question). The provider question is described below. A typed key is checked with one live request to the provider's origin before it is stored; a failed check says why and lets the person enter the key again or continue. The statements `delorun setup privacy` shows are [`@delorun/bundle-local`](../../packages/bundle-local/README.md)'s, read from its `./statements` export. The flags `--phone` (alias `--devices`), `--import-dsh` and `--port <n>` answer the first, second and third question, in a terminal as a preselected choice and in a run that asks nothing as the answer. Setup no longer asks the four questions it only recorded (where commands run, the studio additions, help with other models, desktop analytics); the two upstream opt-ins stay off, and Settings → Safety → Privacy changes them.
- **`--yes`** takes every default and sets up no model provider unless `--provider <id>` names one; without one it prints how to add one. `--model <id>` names the model, which every provider but DeepSeek needs, `--base-url <url>` the endpoint of `openai-compatible`, and `--key-env <NAME>` the variable the key is read from at each start, the provider's own by default; a key is never taken from the command line. Setup stops with an error that names the variable when it is unset. The key is not checked live unless `--check-key` is given, which needs `--provider`. With `--no-update-check`, as in the other forms, the release check is off.
- **`--config <file>`** reads an answers document. It refuses a document that enables reach or the stock-home import, which shows its preview in a terminal first, that turns changes protection on, which only a terminal proof does, that carries a key setup no longer asks (the message names the removed keys), that carries a credential value in any field, that names a provider setup does not offer or a model its installed catalogue does not list, or that names a schema version other than 4, 3 or 2; a version-2 document has no `updateCheck` and reads as the check on, and a version-2 or version-3 document's provider reads as DeepSeek with the profile's default model, which those versions applied. A refusal names the field and never echoes a value.

The model provider ([`src/setup/provider-section.ts`](src/setup/provider-section.ts), [`src/setup/providers.ts`](src/setup/providers.ts)) is one of the providers of [contract C11](../../docs/contracts/c11-setup-answers.md#model-providers), listed by name, or none: DeepSeek on upstream's DeepSeek adapter, which needs no install, and Anthropic, Google Gemini, Groq, Mistral, Moonshot AI, OpenAI, OpenRouter, Together AI, xAI and any OpenAI-compatible endpoint on upstream's pi-ai adapter. The section asks the provider, then for an OpenAI-compatible endpoint its base URL, which may hold no user name, password, query or fragment and draws a warning for plain `http` to another computer, and its model id, then where the key comes from (typed now, or the provider's variable at each start) and the key. The model comes from the provider's installed catalogue, starting on the provider's recommended model, and is asked for every provider other than DeepSeek, whose default is the profile's; `delorun setup key` asks it for DeepSeek too. "Choose later" changes no provider row and says which model new chats still start on. The key check is one authenticated `GET` of the provider's model listing or key endpoint at its origin, with redirects refused, never a completion. The writes are the rows the studio's Settings → Agent → Models and the model picker save: DeepSeek with its own variable and default model writes none, so the profile is composed as stock DeepSeek Harness composes it; a pi-ai provider sets its route on `llm-pi-ai` and `agent-default-model` selects the model. `delorun setup key` asks again, or takes `--provider` and its flags and asks nothing.

Each topic is a section in the registry of [`src/setup/sections.ts`](src/setup/sections.ts), with a main-flow placement: `privacy` shows its line without a question; `reach` (phone access, [`src/reach/setup-section.ts`](src/reach/setup-section.ts)) and `import` are asked in the main flow (`import` only when a stock home exists), `profile` only when the default port is busy, and `changes-protection` after a phone Yes; `key`, `prompts` and `background` are asked only by `delorun setup <section>`. `delorun setup privacy` asks whether to check for new releases and writes the answer as Settings → General → Updates does. `delorun setup <section>` runs one again on a profile that is set up, and `delorun setup --list` lists them. `delorun setup` on a finished profile in a terminal runs the whole flow again ([`src/setup/current.ts`](src/setup/current.ts)): every question starts on the answer the configuration holds now, read by the reader that pairs with the section's write (`readUpdateCheckRow`, `readPromptsRows`, `readProviderAnswer`, `profileStudioPort` and `readReachRowAt`), with the answers record as the fallback for the use case, the background choice and a profile whose patch has no rows. The profile-name question is skipped, the key question offers `Keep the saved key` first, and a section whose `unchanged` method says its answer is the current one writes nothing and is reported as kept. Staying on dangerous mode asks no second consent while its grant is valid; turning it on asks both. An interrupted re-run resumes from its run record like a first run. A later package adds its section with `SectionRegistry.register(section, { order })`; the `order` places it among the others. A section's writes receive the home, the profile directory, the typed key and the environment `delorun` inherited.

The prompts answer takes effect: "Ask me first" and "Ask less (like DeepSeek Harness)" write `config.enabled` of the rows `delorun-permission-defaults`, `delorun-instruction-consent`, `delorun-mcp-consent` and `delorun-schedule-consent` to the Delorun default and the parity value of the matching switch in contract C16's registry. The fetch guard is a refusal, not a prompt, and stays on. "Never ask (dangerous)" ([`src/setup/dangerous.ts`](src/setup/dangerous.ts)) is chosen after a warning and the typed phrase `full access everywhere`, or with `--yes --prompts dangerous --accept-dangerous-mode`, or `acceptDangerousMode: true` in a `--config` document, and is refused for a root user. It sets the three consent rows to their parity values, sets `fullAccessEverywhere` on the permission-defaults row and writes the grant file `secrets/permission-defaults/full-access-everywhere.json` under the permission store's lock; choosing another answer removes the file. `delorun` start, `delorun status` and `delorun doctor` show it while on.

Setup runs its steps in order: create the CLI profile (under the name the profile section chose), then each section's writes (the release-check row, the stock-home import without its credentials, the typed key into upstream's `.credentials.yaml` at mode 0600 under the provider's key variable with the provider's rows, the prompts rows, the studio port row) into the profile's `cordis.patch.yml`. The release check turned off writes the `delorun-update-check` row in the form upstream's settings service saves it, its id, plugin name and whole config with `enabled: false`; turned on, setup leaves no config on the row. Every write lands before the run's start, so a check turned off in setup makes no request. While a run is unfinished, `run/<profile>/setup-progress.json` holds the answers without any key and the steps that finished, so an interrupted run resumes at the first step that did not finish. When every step has finished, setup removes that file and writes the answers, including which sections were seen, answered or skipped, to `profiles/<profile>/setup-answers.json`, which the studio's onboarding and the start commands read; [`readBackgroundAnswer`](src/setup/background.ts) returns the background answer. Credential forwarding is recorded as off until its section exists.

A fresh run in a terminal ends by starting Delorun in this terminal (`src/setup/foreground.ts`) and printing `foregroundEnding`: Ctrl+C stops it, `delorun start --background` keeps it running, and how to change an answer. A run that starts nothing (no terminal, `--yes`, `--config` or a re-run of a finished setup) ends in [`src/setup/ending.ts`](src/setup/ending.ts) by printing the studio's address and the next steps: how to start and open the studio with `delorun` and the install guide's first-chat section (`FIRST_CHAT_PAGE`), `delorun devices approve` for the phone use case, `delorun headless` for scripts, the install of the `delorun` command at the version of the launcher that started the run (`DELORUN_LAUNCHER_VERSION`) when there is one, and how to change an answer with `delorun setup <section>`. Ctrl-C at any question exits with code 130 and says nothing was saved.

## The home process

`delorun start --foreground` and a bare `delorun` run the home process in this process with `HomeProcess.start`: it takes `run/<profile>/home.lock`, writes a new start token, listens on the update channel `run/<profile>/update.sock` and boots the profile through upstream's profile runner as its Host. Before it takes the lock it registers under `run/data-users/` as the profile's home process until it exits, so an update's prepare, copy, restore or rollback for another profile refuses with `CHATS_RUNNING` while it runs, and it refuses to start while `delorun trash`, `export` or `import` runs or another profile's update is in progress ([contract C19](../../docs/contracts/c19-home-process.md#the-home-process)). It logs to the `home-<profile>` operational log, and in the foreground the terminal also shows its output. Of any number of starts, exactly one holds the lock, including over the lock of a holder that died. A live holder is asked for its status over the update channel: when it answers, a second start prints the running process and exits 0; when it does not answer within 2 seconds, the start stops with `HOME_UNRESPONSIVE`. Whatever ends the process, the lock, the token file and the socket go with it; a process killed with `SIGKILL` leaves them, and the next start replaces them.

The start boots the profile with C1's confinement on upstream's local sandbox provider (row `sandbox`): `protectedHome` is the canonical Delorun home, `protectedHomeReadable` C1's read exemptions and the profile's approved plugin copies (`changes/profiles/<profile>/active`, from `activeCopiesEntry` in `@delorun/changes`; the entry is resolved at each wrap, so a copy approved later is readable at once, and read-only), and `deniedSockets` the update channel's and the supervisor's sockets under `run/<profile>/` (no supervisor runs, so only the update channel's socket exists), the active Docker context's socket with its real path, and Docker Desktop's macOS sockets under `~/Library/Containers/com.docker.docker/Data/` and `~/.docker/run/` when present, so a confined workspace command cannot read the home or the token or connect to either channel where the dialect enforces those rules: bwrap and Seatbelt enforce all of them, Landlock enforces the read and write rules and no socket rule, and the Windows runner confines writes only. Docker Desktop's control-socket directories under WSL and on Linux are not denied. The settings travel in an overlay patch, `run/<profile>/sandbox.patch.yml` at mode 0600, which exists while the Host runs. The overlay is the last patch the start passes, so it applies over every layer that sets the row: the profile's bundles, its own `cordis.patch.yml`, the home's `cordis.patch.yml`, which applies over every profile, and safe mode's overlay. A layer's `config` replaces the row's whole config, so the overlay keeps the row's other settings as the last layer that configures it sets them, and keeps the denied sockets every layer lists. A start refuses the composed settings when they hold expressions it cannot carry over, and refuses any layer that sets the runner itself (`runnerCommand` or `runnerFailureSignatures`), naming each file: a runner command skips the provider's built-in selection and would boot the row unconfined while the provider reports full enforcement.

`delorun start` without `--foreground` starts `delorun start --foreground` detached from the terminal, with standard input closed and its output in its log, and waits at most 120 seconds for the home process to report `running`; a home process that exits first or does not report `running` in time is reported with a plain sentence that points to `delorun logs`, and a busy studio port with the program that holds it where known. `delorun stop` and `delorun status` read the token file and send `stop` or `status` over the update channel; with no live lock holder, `stop` prints that Delorun is not running and exits 0, and `status` exits 3.

When the command runs from `runtimes/<version>/` of C1's store, the home process gets the update support of `src/update/`: the store, the release channel of `@delorun/install` anchored on the root chain under `trust/`, C3's report over readers of the profile and the staged target, the profile history and the session-data copies. Run from a source checkout, it has no store and refuses update requests. From the store, the start also attaches the update check ([notice-host](src/update/notice-host.ts)) to the Host's `delorunUpdateCheck` service, which runs it at start when it is due and on its interval, prints its line once per newer release, and serves its notice to the studio; a start whose profile has the check switched off removes its record. A background start prints the line from the last check after the home process reports `running`. The Host counts its running chats from upstream's `agent/status` event, so `delorun stop` and an update wait for running chats, a turn begun while they wait included; its health check is C3's H1 to H5 ([host](src/update/host.ts)). When H3 finds a protected row's settings changed that the report did not name, the successor reads both releases' signed bundle rows (`src/update/release-settings.ts`) and accepts exactly the change the release brings (C3, rows a release changes). A process whose descriptor 3 is a socket or a pipe was started as an update's successor: it reads the handover from it and runs `HomeProcess.takeOver`.

Every Host goes through [`src/compose.ts`](src/compose.ts), which holds the composed and the booted rows to C19's [Host invariants](../../docs/contracts/c19-home-process.md#host-invariants): each required row, `sandbox` and every row a Delorun bundle inserts, is inserted once by the bundle that declares it and runs that bundle's plugin, a second insert of its id by any other layer is refused, safe mode exempts none of them, and after boot each service such a row provides (`sandbox`, `fetchGuard`, the consent services, `delorunTurnGate`) must be provided by that row's fiber. In the CLI profile and in the `headless` profile the update gate holds every turn's first step until the start releases it after that check. Before the Host boots, [`src/pre-start.ts`](src/pre-start.ts) runs one ordered list of steps that `delorun start --foreground` and `delorun headless` share: an interrupted import's withdrawal and the update notice's check, both slots that do nothing, the completion of an interrupted restore and the profile's one-time changes. The Host's launch environment is upstream's `.env` layers over the environment `delorun` was started with; `main` captures that environment once and passes it down, and a `.env` layer that sets a `DELORUN_` name is refused before any layer applies.

## Opening the studio

[`src/open/`](src/open/studio.ts) opens the studio. `delorun open` sends `studio.open-token` over the update channel with the start token from the token file; the home process asks its Host's connection for a launch URL to the studio's loopback root ([host link](src/open/host-link.ts)), and with Delorun's composition that URL's token works once and expires after 60 seconds (contract C4, "Launch tokens"). The link goes to `xdg-open`, which reads `BROWSER` itself, `open` on macOS, or `cmd.exe /c start` on Windows. Under WSL it goes to the program `BROWSER` names when that variable is set (the first entry of its colon-separated list, with the link as its one argument), and to `cmd.exe /c start`, the Windows default browser, only when `BROWSER` is unset or empty. Nothing else the command writes contains the link. To open nothing at all, use `--print`. `--print` writes the link and a line that says it works once. A link names the studio's loopback host and port and signs in only there: a browser that reaches the studio through `localhost` instead of `127.0.0.1`, or through an `ssh -L` forward to another local port, is refused with a page that names the address the link was made for, and `delorun open --print --port <n>` makes a link for a forwarded port. A Host whose studio listens on an address other than loopback, or that publishes it at a public URL, gives no link (`STUDIO_UNAVAILABLE`, with the reason), and a home process that holds the channel but does not answer within 2 seconds is reported as not answering rather than as not running.

Running upstream's `dsh` directly on a Delorun CLI profile, rather than `delorun start`, cannot sign in through a printed address: with the switch on, the `dsh web:` line carries no token, and `delorun open` needs `delorun`'s home process. Only `dsh`'s own browser handoff, which mints a one-time link, signs in there. Start the profile with `delorun start` and open the studio with `delorun open`. A start never passes upstream's browser handoff a link (`--no-open`): it prints `Run delorun open to open the studio in your browser.`, and `delorun start --open`, a bare `delorun` and setup's ending open the studio through the same request once the home process runs.

## How delorun runs upstream

`delorun` launches applications only through upstream's profile runner, as the root `AGENTS.md` requires. A start and `headless` call upstream's `runProfile` from `@deepseek-ai/dsh/profile-boot`, with the CLI profile and the `headless` profile, as the desktop Host does for its profile, each through Delorun's composition ([`src/compose.ts`](src/compose.ts)); both pass `failLoud: false`, because the entry point's one last-resort handler reports a crash and disposes the registered Host; a start also passes `signals: false`, because its home process's one signal listener serves every Host it boots, and `headless` keeps upstream's signal handlers; `plugin` calls upstream's `runCli` with its `argv` option set to the arguments `dsh` would receive. That option is Delorun's one change to upstream for this command, recorded as a `generic-fix` in the divergence ledger; upstream already resolves its home from `DSH_HOME`, so the home needs no change.

## Extension points

- **A command** is a module that exports one `CliCommand` (`src/command.ts`) and adds one row to `COMMANDS` in `src/main.ts`. `delorun doctor` belongs in `src/doctor/` and `delorun logs` in `src/logs/`, each through this row.
- **`delorun doctor` key lookup.** The key checked is the one of the provider new chats start on: the route of the profile's `agent-default-model` row, or DeepSeek's when the profile sets none, read from the `apiKeyEnv` the route's row names or the provider's own variable. A route that names no variable is reported as a warning, since its adapter finds the key itself. It is read in this order, and the first source that holds one is checked: the reference setup stored in the home's `.credentials.yaml`, the process environment variable, the invoking directory's `.env`, then the home's `.env`. The check reports the source's name only and never prints the key; it checks the format offline, a DeepSeek key's `sk-` prefix included and no length rule for an OpenAI-compatible endpoint, and does not send the key to the provider.
- **Setup** is `runSetup` in `src/setup/index.ts`, which both `delorun setup` and a first run call. Its sections are in `src/setup/sections.ts` and the step runner with the way back is `src/setup/steps.ts`, behind the `Prompter` interface of `src/setup/prompts.ts`, so a test runs them against a scripted prompter.
- **The home process's dependencies** are `StartDependencies` in `src/start.ts`: the profile preparation and runner, the environment loader, the holder probe (the update channel's `status` request), the exit hooks, the output capture and the studio opener, so a spec runs a start against stand-ins.

## Not implemented

The CLI does not include the following; the [roadmap](../../docs/guide/roadmap.md) covers what Delorun does not do.

- Start at login (`delorun start --at-login`, `delorun stop --at-login`), `delorun status --follow`, and the confinement probes of the start sequence.
- The chat gate holds no scheduled delivery: a delivery that falls due during an update's wait has its turn refused with `UPDATE_PENDING`. The report reads no revocation list, because no release publishes one ([`@delorun/update`](../../packages/update/README.md#not-implemented)).
- Setup's reach question. Setup records reach as off.
- The Windows DACL check ([#48](https://github.com/twickas/delorun/issues/48)): on Windows the directory check checks nothing and the protected-file check looks only at the file type.
- `reach`, `devices` and `dev`.
- Opening imported chats in the studio.
- `delorun verify --mode`, and every registered check but `release-signature` and `runtime-files`. `delorun verify` reports the default mode, `warn`, because nothing reads `integrity.mode`.

## Development

Run `delorun` from a checkout with `pnpm --filter @delorun/cli delorun <command>`; it needs `pnpm run build:artifacts` and `pnpm --filter @delorun/bundle-local run build` first, because upstream's build does not build Delorun's packages; setup links the bundle into the CLI profile. The specs run with `node_modules/.bin/vitest run --config delorun/vitest.config.ts delorun/apps/cli`, and the app typechecks with `node_modules/.bin/tsc --noEmit -p delorun/apps/cli/tsconfig.json`. The specs use temporary OS homes and never touch the real `~/.delorun` or `~/.dsh`.
