# Delorun release tooling

English | [中文](README.zh.md)

`@delorun/release` is Delorun's release tooling, a private package in `delorun/apps/release`. It holds the changelog gate, the release-notes assembly, the published recipe that builds the runtime closures, the comparison of two builds that signing requires, the release's SBOM, the dependency advisory check, the signing and verification of release metadata, the release log, and the S2 and S3 images. The [release manifest contract](../../docs/contracts/c02-release-manifest.md) (C2) defines the release files, the reproducibility scope and the signing rules this package implements.

## Modules

- `src/changelog/paths.ts` classifies a path as a product file, which needs a changelog entry, or as a fragment.
- `src/changelog/fragment.ts` parses a fragment's front matter and body, and lists the unreleased folder.
- `src/changelog/version.ts` accepts release versions.
- `src/changelog/check.ts` is the gate `gates:changelog`. It checks each commit of a range and every fragment in the working tree.
- `src/changelog/assemble.ts` assembles a release's notes, its `CHANGELOG.md` block and its moved fragments.
- `src/build-closure.ts` is the closure recipe's command; `src/closure/` holds its steps: the recipe files (`config.ts`), the pinned downloads (`sources.ts`), the native addon's compile (`native-build.ts`), Delorun's packages in the closure (`delorun.ts`), the files the launcher starts a closure with (`launch.ts`), the staged tree and the runtime file list (`tree.ts`), the native-code check (`native.ts`) and the archiving (`archive-closure.ts`).
- `src/local-release.ts` builds one signed release into a directory laid out as a release channel; `src/local/release.ts` holds its steps and `src/local/production-keys.ts` reads the production-keys registry (see [Local release](#local-release)).
- [`@delorun/release-formats`](../../packages/release-formats/README.md) holds the formats this tooling shares with the shipped verifiers: the deterministic tar, gzip and ZIP writers and readers and the inspection of the deterministic form (`archive/`), the signature envelope, canonical JSON, the readers of each signed file and client verification (`sign/`), the release-log entry, bundle, signed notes, Merkle proofs and tiles (`log/`), and the version and digest brands. Nothing it ships depends on this package, so the runtime closure carries none of the tooling.
- `src/compare-rebuild.ts` is the rebuild comparison's command; `src/rebuild/` holds the comparison; the PE normalisation of its first exception is `@delorun/release-formats/archive/pe`.
- `src/record-rebuild.ts`, `src/sign-release.ts`, `src/sign-root.ts` and `src/sign-timestamp.ts` are the signing commands, and `src/draft-root.ts` writes the root draft `sign-root.ts` signs; `src/rebuild/record.ts` holds the rebuild record's facts and `src/sign/` the timestamp content, the release source checks (`source.ts`), the npm tarball check (`npm-package.ts`) and signing.
- `src/sbom/` writes the SPDX SBOM from the runtime archives; `src/check-advisories.ts` and `src/advisory/` run the dependency advisory check.
- `src/build-images.ts` and `src/images/` build the S2 and S3 images from `images.json` and `images/`; `src/log-release.ts` and `src/log/client.ts` submit the release-log entry and write its bundle.
- `tests/` holds the specs. The changelog specs run both entry points on temporary git repositories; the archive, closure and rebuild specs build fixture closures in temporary directories and serve pinned downloads from a local HTTP stand-in, the signing specs sign fixture releases with keys generated in the test, and the release-log specs run a local log and witness stand-in, so none needs the network or a real key. `tests/images/images.docker.spec.ts` builds both images twice, and `tests/closure/native-build.docker.spec.ts` compiles the native addon for both Linux platforms from two directories and compares the binaries with each other and with `prebuilt-pins.json`; both run only with `DELORUN_DOCKER_SPECS=1`, because the check runner has no Docker lane. `tests/closure/boot.closure.integration.spec.ts` sets up a new home from a built closure, starts the CLI profile and requires every `@delorun/` row to be active; it runs only when `DELORUN_CLOSURE_ARCHIVE` names a built `linux-x64` closure archive, and the release workflow must run it on the `linux-x64` archive it publishes.

## The gate

`node_modules/.bin/tsx delorun/apps/release/src/changelog/check.ts --base <rev>` checks each commit after `<rev>`. A commit that changes a product file adds a fragment under `delorun/changelog/unreleased/` or carries a `Changelog: none (<reason>)` trailer. Product files are every path outside the documentation, tooling, release, workflow and changelog trees, except Markdown files and bilingual pairing records (`*.i18n.yaml`), which are documentation wherever they are. The gate also refuses a reason-less trailer and every fragment that does not parse. It prints one line per violation and exits 1.

## Assembly

`node_modules/.bin/tsx delorun/apps/release/src/changelog/assemble.ts --version <version> [--date <YYYY-MM-DD>] [--dry-run] [--first-public-release]` assembles the unreleased fragments into one version. The version is a preview sub-version `0.x.y-preview.N` (N from 1), a private test build `0.x.y-preview.N.M` (M from 1) between `N` and `N+1`, a release `0.x.y`, or an `-alpha.N`, `-beta.N` or `-rc.N` pre-release; `1.0.0` is refused unless `--first-public-release` is passed. Assembling `0.x.y` folds the entries of its previews and test builds into it.

The assembly writes `delorun/changelog/changelog.json` (the standing comparison with the upstream release in `upstream.ref` of `delorun/upstream-patches.json`, and every version), renders `CHANGELOG.md` at the repository root from it, writes the release notes to `delorun/changelog/releases/<version>.md`, and moves each consumed fragment into `delorun/changelog/releases/<version>/`. Pending fragments are never assembled. A version that is already assembled is refused. The release commit that adds `CHANGELOG.md` to the repository also adds its divergence-ledger entry.

`--dry-run` prints the entry and the notes and writes nothing; `--list-unreleased` prints the unreleased fragments by area and the pending ones with what each waits for. The fragment format, the areas and the data file are described in [`delorun/changelog/README.md`](../../changelog/README.md).

## Runtime closures

A runtime closure is one platform's installable runtime: the pinned Node executable and its licence under `node/` (`node/bin/node`, or `node/node.exe` on Windows), pnpm under `pnpm/`, and the closure root package's `package.json`, `pnpm-lock.yaml` and production dependencies under `app/`. The root package is the one `closure.json` names, [`@delorun/runtime-closure`](../runtime-closure/README.md): upstream's `dsh-python-runtime-closure` (`python/sdk-runtime`), the dependency-only manifest whose dependencies are the `dsh` command with every plugin its shipped profiles load and their workspace peers, which upstream's `verify-runtime-closure` check keeps complete, and `@delorun/cli` with Delorun's packages. The `delorun` command's entry file is `app/node_modules/@delorun/cli/src/bin.js`, and the `dsh` command's `app/node_modules/@deepseek-ai/dsh/lib/bin.js`.

`closure.json` lists the release platforms, the platforms this release publishes a runtime for: `linux-x64` and `linux-arm64`; Windows is served by WSL2, which runs the Linux runtime. The build, the SBOM, the rebuild record's required outputs and signing cover exactly these, and reading the recipe fails when the list names a platform whose native addon `toolchain.json` marks `unbuilt`. It also names the client title, `Delorun`, which the client artifacts present as the page title, the home-screen title and the web manifest's name, and the install anchor: `@deepseek-ai/dsh`, whose `package.json` upstream's runtime resolution reads to decide what a profile's plugin rows can import, with the Delorun bundles it must declare (`@delorun/bundle-local` and `@delorun/bundle-studio`, every `@delorun/` bundle a new CLI profile lists). Without that declaration, `delorun` refuses every start because a Delorun plugin row fails to import. `closure.json` also lists `foreignPrebuilds`: packages that carry other platforms' prebuilds in their main package (today `@deepseek-ai/libreoffice-kit`'s `frame-forwarding/prebuilds` for the macOS and Windows platforms), with the platform directories to drop. The build removes exactly those directories from each closure, logs one line per directory, and does so before the native-code check; a foreign prebuild that is not listed still fails the check, and a directory named for the closure's own platform is never removed. Each listed directory must exist in the closure, or the build fails before it removes anything, and a rule whose directory resolves outside its package, through a `..` segment or a symlink, is refused in the same way. The recipe refuses a `directory` with a `.` or `..` segment at read time. `closure.json` also lists `packExternals`, the package names (an exact name, or a prefix ending in `*`) that a pack never carries because the publisher's licence forbids redistribution: Claude Code's `@anthropic-ai/claude-agent-sdk` package and its platform programs `@anthropic-ai/claude-agent-sdk-*`, and Codex's `@openai/codex-*`. The packs file pins each by npm tarball URL and SHA-512, and turning the pack on fetches it from the registry and checks it.

A pack's `package.json` and `pnpm-lock.yaml` are the same bytes in every build of the same sources. `pnpm deploy` writes a workspace package it injects as `<name>@file:///<absolute source path>`, which names the build's temporary folder, so the pack build writes the exact version of the package the pack carries instead, in `package.json` and in the lockfile's `importers`, `packages` and `snapshots` (its `directory` becomes `node_modules/<name>`, and a variant's peer suffix stays). It also deletes the deploy metadata the runtime closure deletes (`DEPLOY_METADATA`: `pnpm-workspace.yaml`, `node_modules/.modules.yaml`, `node_modules/.pnpm-workspace-state-v1.json` and `node_modules/.pnpm`), which hold the build's folders, the pnpm store's folder and timestamps. It then refuses a pack that still carries any of those files, or whose `package.json` dependency fields (`bundleDependencies` included), the `package.json` of any Delorun or vendor package it carries at any depth, or lockfile still hold an absolute path (any value starting with `/` or a drive letter), a `file://` URL, a path outside the pack or a temporary or home folder, naming the pack, the file and the field (`src/closure/pack-specifiers.ts`). `node_modules/.bin/tsx delorun/apps/release/scripts/pack-probe.ts --source <tree> --scratch <empty dir> --out <empty dir> --name <package> --stage <dir>` runs one real `pnpm deploy` and the pack step for one package, without signing, and prints the archive digests; running it from two copies of one tree and comparing the digests shows whether a pack depends on where it was built (the header of the script says how to make `--stage`).

No shipped file names the builder. When the build has written every file, `build-closure.ts` from source (`--artifacts build`) refuses any file of its output, and any entry of each `.tar.gz` archive in it, that holds the building user's home directory (`os.homedir()`), the user name as a folder (`/<name>/` or `\<name>\`) or a unique build root `delorun-release-build-*`, and names every such file (`@delorun/release-formats/gate/home-paths`; the shared `/var/tmp/delorun-release-build/source` is not a finding). The scan reads bytes, so it covers JavaScript, JSON, YAML, source maps and text, and binary files for the same strings; it does not read UTF-16 text or the inside of a `.zip`. A build from existing artifacts (`--artifacts existing`) embeds the worktree's paths, so `build-closure.ts` prints the findings as warnings for it and `local-release.ts` refuses them before it signs anything. Nothing bypasses that by default: `cut-rc.ts` (whose `--artifacts` default is `existing`) and `local-release.ts` accept `--allow-builder-paths`, which the person running them passes for a local iteration candidate and which replaces the refusal with one warning per offending file. A public cut uses `--artifacts build` and never the flag. The npm launcher's package is built apart from the closure, and `npm-launcher/src/build.ts` runs the same refusal over its own output before it packs, so no launcher tarball names the builder; `node_modules/.bin/tsx delorun/apps/release/scripts/home-path-gate.ts <directory>...` runs the scan on any directory, names each offending file and exits 1.

`node_modules/.bin/tsx delorun/apps/release/src/build-closure.ts --version <version> --out <dir> [--commit <rev>] [--platform <platform>]... [--cache <dir>]` builds the closures of every release platform, or of the named ones, from a commit (`HEAD` by default). It runs on Linux or macOS with a Docker engine, which the native step needs, refuses to run under a Node or pnpm version other than `toolchain.json` pins, and refuses a platform that is not a release platform. For each build it:

1. exports the commit's tree to the build root `closure.json` fixes, `/var/tmp/delorun-release-build/source`, so the absolute paths that bundlers embed in client artifacts are the same on every builder; the build holds the lock file `/var/tmp/delorun-release-build.lock`, which records its process id, so a second build on the computer refuses and names the holder instead of removing the first one's tree, and a directory at that path that the command did not create is refused, never removed;
2. runs `pnpm install --frozen-lockfile` and `pnpm run build:artifacts` there with only the builder's `PATH`, `HOME`, `USER`, `TMPDIR` and proxy variables, plus `SOURCE_DATE_EPOCH` (the commit's committer time), `-ffile-prefix-map=<build root>=.` in `CFLAGS` and `CXXFLAGS`, `TZ=UTC`, `LC_ALL=C`, the commit id the client artifacts embed, `DSH_BUILD_SOURCE_COMMIT` (the same commit id) and `DSH_BUILD_SOURCE_TREE=clean` (the export holds exactly the commit's tracked files), which the build stamp uses because the exported tree has no `.git`, and `DSH_CLIENT_TITLE` set to the client title, so upstream's own client build presents it; a build in a tree with neither `.git` nor those two variables fails with an error naming them, and never assumes a commit or a clean tree; then it builds Delorun's packages that have a `build` script (`pnpm --filter ./delorun/packages/* run build`), which `build:artifacts` does not build;
3. compiles upstream's native system addon in `native/system` for each platform whose route is `source`, as [Native code](#native-code) states, into the platform package's `bin/`;
4. for each platform, runs `pnpm deploy --prod --ignore-scripts` of the root package with that platform's `--os`, `--cpu` and `--libc`, a hoisted `node_modules` and copied files, replaces package links with files, shares each workspace package between its consumers as upstream's executable build does, removes pnpm's deploy metadata and the root package's other files; transpiles each `@delorun/` package's `src/**/*.ts` to JavaScript beside itself, with relative imports and `package.json` entry points rewritten to `.js`, and removes the package's `tests`, because Node does not run TypeScript from `node_modules`; stamps the release version into `@delorun/cli`'s `package.json`, where `delorun --version` and the plugin version checks read it (the workspace holds `0.0.0`); adds each Delorun bundle the anchor must declare to its `package.json` dependencies at the bundle's staged version; the deploy carries the platform package of the native addon with the binaries the previous step compiled;
5. adds the Node executable from the distribution archive `toolchain.json` pins by SHA-256, and pnpm from the tarball it pins by integrity, each downloaded once into the cache (`~/.cache/delorun-release` by default) and used only when its bytes match;
6. checks every ELF, Mach-O and PE file outside `node/` against the platform's `files` entry in `prebuilt-pins.json`: an unlisted file, a changed digest or a listed file that is absent stops the build;
7. refuses to archive a closure that lacks launch protocol 1's files, `node/bin/node` (`node/node.exe` on Windows) and `app/node_modules/@delorun/cli/src/bin.js`, which the runtime store requires before the launcher starts a runtime; then writes `delorun-<version>-<platform>.tar.gz` (`.zip` for `win32-x64`) and its unsigned runtime file list `delorun-<version>-<platform>.files.json` to `--out`, which never replaces an existing file; after building every platform, it writes the SBOM `delorun-<version>.spdx.json` there too.

`--write-pins` records the native files of the built platforms in `prebuilt-pins.json` instead of checking them; the recorded change is reviewed like any other change to the recipe.

`--artifacts existing` builds a closure for a local release from artifacts already built in the worktree, instead of running `pnpm run build:artifacts` in the exported tree. It refuses unless the worktree is at `--commit`, its tracked files are clean, and every package whose `main` names a file under `lib/` has that file and a `lib/` newer than its `src/` (the artifact build through the check runner, `run-checks.ts --only build:artifacts`, makes them current). The ignored `lib/` directories and the client bundles are then copied into the exported tree, and the native step compiles the native addon there as in a release build, replacing any binaries copied with it, so the closure's native files are checked against `prebuilt-pins.json` too. Such a closure embeds the worktree's paths, so it is for a local release only, never for signing. Because its paths are local anyway, it builds in a fresh directory `/var/tmp/delorun-release-build-<suffix>` of its own, removed when the build ends, and holds no lock, so local builds of several worktrees run side by side.

### Native code

Upstream's native system addon in `native/system`, the static Landlock launcher `landlock-run` and the flock Node-API addon `system.node` for glibc and for musl, is compiled by the recipe for each platform whose route in `toolchain.json`'s `native.platforms` is `source`: `linux-x64` and `linux-arm64`. It is C that compiles against the C library, the kernel headers and Node's headers only, so it has no third-party source to lock.

1. The builder image is built from `native/Dockerfile` over the Debian base `images.json` pins by digest, with the packages `native.builder.packages` pins at exact Debian versions (GCC 12.2.0, binutils 2.40, the glibc 2.36 and Linux 6.1 headers, musl 1.2.3) installed from the Debian snapshot `native.builder.snapshot` names, for the platform's OCI architecture. This is the step that uses the network; the image's tag is a digest of the Dockerfile, the base, the snapshot, the packages and the architecture, so an existing image with that tag is reused.
2. The recipe lists the image's installed versions of the pinned packages and refuses an image whose versions differ.
3. It unpacks `bin/node` and the headers of the platform's pinned Node distribution and runs upstream's `native/system/scripts/build.ts`, unchanged, with that Node inside the image, with no network, a read-only root filesystem, the builder's user, `TZ=UTC`, `LC_ALL=C` and `SOURCE_DATE_EPOCH`. The `linux-arm64` image runs under emulation on an x64 builder, as the image build does: Docker Desktop provides it, and a Docker Engine host needs QEMU registered with `binfmt_misc`.

Upstream's build script passes its own compiler flags and reads no `CFLAGS`, so the prefix map does not reach it; the binaries embed neither the build directory nor a time, and the same image compiling the tree mounted at another path gives the same bytes. `prebuilt-pins.json` pins those bytes, so any build that differs stops before archiving.

`darwin-x64` and `darwin-arm64` are `unbuilt`: the recipe has no pinned toolchain that compiles the macOS binaries, so `closure.json` cannot list them, `build-closure.ts` refuses either platform before any step runs, and a release publishes no macOS runtime until one exists. `win32-x64` is `none`: `native/system` has no Windows package. A release publishes no `win32-x64` runtime and `closure.json` does not list it; the recipe keeps the code that stages and archives a Windows closure (`node/node.exe`, a `.zip` archive, the PE checks) so a later release can list it, and `build-closure.ts` refuses the platform until then. Every other native file in a closure is a prebuilt file from an npm tarball the lockfile pins by integrity, and `prebuilt-pins.json` pins its digest as well.

### Archive format

Both formats hold only regular files, in byte-wise UTF-8 path order, with no directory, link or device entry, and with mode `0644`, or `0755` for a file that any execute bit marks in the staged tree.

- **tar.gz**: POSIX ustar headers with uid and gid 0, empty user and group names and every mtime `SOURCE_DATE_EPOCH`; a path the name and prefix fields cannot hold gets a pax header with one `path` record. The archive ends with two zero blocks. The gzip member has mtime 0, no file name, operating system byte 255, and deflate at level 9.
- **ZIP**: "version made by" Unix 2.0 with the mode in the external attributes, UTF-8 names, no extra fields, comments, data descriptors or ZIP64 records, DOS time `SOURCE_DATE_EPOCH` in UTC rounded down to an even second, and each entry deflated at level 9 unless storing it is smaller. An archive holds at most 65,535 entries.

An archive is at most 1 GiB, the download limit of [C1](../../docs/contracts/c01-home-layout.md).

## Local release

`node_modules/.bin/tsx delorun/apps/release/src/local-release.ts --version <version> --summary <text> [--security] --out <channel dir> --root <root file>... --targets-key <targets.pem> --timestamp-key <timestamp.pem> --state <state.json> --log-submit <url> --log-checkpoint <url> --log-tiles <url> [--log-entry-key <type>=<key.pem>]... [--platform <platform>]... [--commit <rev>] [--closures-from <dir>] [--cache <dir>] [--production-keys <file>] [--allow-builder-paths]` builds and signs one release from a commit into a directory laid out as a release channel, for a launcher built with that directory's origin as its channel origin (`delorun/apps/npm-launcher`). It composes the steps above and adds no cryptography:

1. Before it builds anything, it refuses production trust material: a `--root` file whose SHA-256 the [production-keys registry](#production-keys) lists, and a root that lists such a key in any role or in `keys`, or a `--targets-key` or `--timestamp-key` whose key id it lists. `--production-keys` names the registry, the repository's `delorun/release/production-keys.json` by default. It then checks the roots as a client does and that `--targets-key` is the newest root's one active targets key.
2. It builds the closure of each `--platform`, a release platform `closure.json` lists (`linux-x64` alone when none is named), from `--commit` (`HEAD` by default) with `build-closure.ts`'s recipe and the same toolchain checks, or, with `--closures-from`, takes each platform's `delorun-<version>-<platform>` archive and `.files.json` that a `build-closure.ts` run left there. `--version` names the release whatever the commit holds, so the same commit builds as two versions and an update exists to take.
3. It signs each file list and writes the manifest, signed by the targets key, as `sign/release.ts` does. The manifest's source is the public repository, the tag `v<version>` and the commit; its builder is "local release (no independent rebuild)": until 1.0 the maintainer builds and signs every release on the maintainer's PC with this command, and a launcher built for the production channel installs such a 0.x release under the preview root it pins by digest; a 1.0 release or any other root refuses it. Its `runtime` lists exactly the platforms the command was given. Its `summary` is `--summary`, which must be one plain line of at most 200 characters, and its `security` is true with `--security` and false without. The manifest schema requires files that a local release does not build (the desktop installers, the images, the SBOM, the install scripts, the rebuild record, the advisory report), and those are zero-length placeholders that the channel does not serve. `source.tag` need not exist.
4. It submits the manifest's Rekor v2 entry to the log that `--log-submit`, `--log-checkpoint` and `--log-tiles` name and writes the bundle when it verifies with the root's log and witness keys. It signs with the root's `active` log-entry keys it holds, each `--log-entry-key <type>=<key.pem>` (a mode-0600 private key of that type) and the targets key when the root lists it as an Ed25519ph key, in the root's order, and refuses before building anything when it holds none or the root lists no `logEntryKeys`; it verifies each request under the root before submitting it, and moves to the next key only when the log answers HTTP 400 with one of C18's two key-type refusal messages, printing a warning. Any other answer stops the release, and the entry it writes is the one the log accepted. The packs file is logged with the same key or a later one. The command asks for a witnessed checkpoint at most 60 times, 30 seconds apart. Name only a log you run, unless this release is meant for the public log.
5. It signs the next timestamp with `--timestamp-key` from the signer's state in `--state` (created for a channel's first signing, as `sign-timestamp.ts --init-state --first` does, and replaced after each signing), naming the release for both channels. A version below the one the channel serves is refused.

The channel directory then holds `timestamp.json`, `root/<n>.root.json` for each `--root` and, for each version, `releases/download/v<version>/` with the manifest, its log bundle and entry request, and each platform's archive and signed file list. The release files go in first and the timestamp last, so a failed build leaves the channel serving what it served, and a version already in the channel is never replaced. Serve the directory with any static server, and build the launcher with `--channel-origin` set to its origin, as the [launcher's README](../npm-launcher/README.md#building-the-package) describes.

A local release is not a published one: no second builder rebuilt it, no advisory check ran, and its keys are whatever `--root`, `--targets-key` and `--timestamp-key` name, except that production keys are refused. `tests/local/e2e.integration.spec.ts` runs the whole path on throwaway keys and local servers: it signs a release with this command, builds and packs a launcher for it, installs the release through `npm exec` with the log unreachable and checks the printed steps and the warning, the record in `trust/release-log.json` and the runtime's start. Its runtime is a fixture whose entry file prints its stamped version. With `DELORUN_CLOSURE_FILES` naming a directory that holds the `delorun-0.1.0-linux-x64` archive and file list a `build-closure.ts --version 0.1.0` run wrote, one more spec installs that real closure through the packed launcher and runs its `delorun --version`. `tests/closure/boot.closure.integration.spec.ts`, with `DELORUN_CLOSURE_ARCHIVE` naming the archive (and `DELORUN_CLOSURE_EXISTING_ARTIFACTS=1` for a build from existing artifacts), sets up a home from the closure, starts the CLI profile with every Delorun row active, and starts the Host as the home process and requests the studio's index on loopback.

## The journey

`tests/journey/journey.docker.spec.ts` installs a release built from the worktree in a clean container and walks what a person does with it, in order, in one container whose home carries over from step to step. The check runner runs it as the merge-only check `journey` ([checks](../tools/README.md#local-checks)); run it alone with `node_modules/.bin/tsx delorun/apps/tools/src/run-checks.ts --only journey`. It needs a Docker engine with the pinned Debian base of `images.json` already pulled, and a worktree whose tracked files are committed, because release 1 is built with `build-closure.ts --artifacts existing`, which refuses a dirty tree, a missing artifact or one older than its sources, naming each.

Its parts, all made by the spec and removed after it:

- **Trust.** A throwaway root, targets, timestamp and log key, as `tests/local/support.ts` makes them; no key from the person's home.
- **Releases.** Release 1 (`0.1.0`) from `build-closure.ts`. Releases 2 (`0.2.0`), 2b (`0.2.1`), 3 (`0.3.0`) and a tampered release (`0.4.0`) are release 1's closure extracted, given another version with the recipe's `stampDelorunVersion`, changed where the release needs it and archived again with the recipe's `archiveClosure` ([`derive.ts`](tests/journey/derive.ts)), each in a process of its own while steps 1 to 3 run. Release 2b's studio has no index, so its Host never answers the health check. Release 3 raises one of Delorun's own versioned records: the `delorun_chat_states` storage unit at version 2, which reads version 1 and stamps itself 2 when its plugin starts, with `data-formats.json` naming the new version, so the report names the data change and release 1, which refuses a unit stamped 2 and refuses to start without that Delorun row, starts again only when a rollback restores the copy. The tampered release's archive has one byte of `data-formats.json` changed after the archive was made, under the honest signed file list. `local-release.ts --closures-from` signs and logs each release into the channel when its step begins.
- **Servers**, in the spec's process: the channel, the release log (agreeing, silent or contradicting at one origin), and upstream's `llm-mock-server`, which answers every chat with one scripted reply.
- **Launcher.** `npm-launcher/src/build.ts` with the run's root and the channel and log origins as build constants.
- **Machine.** An image from the pinned Debian base and the pinned Node distribution of `toolchain.json`, both from this computer's caches, with Debian's `git`, which the profile history needs, an unprivileged account and nothing of the repository; the image build reaches the network for `git` only, and the machine has no pnpm. Its containers sit on a Docker network created `--internal`, so they reach neither the internet nor this computer; one gateway container on that network and Docker's default bridge forwards exactly the spec's server ports to `host.docker.internal`, and a forwarder in each container listens on its loopback address on those ports, because the launcher accepts an `http:` origin only on loopback ([`machine.ts`](tests/journey/machine.ts)). The first test proves it: a request from the container to an outside address, an outside name and this computer directly fails. A stand-in browser records each address the Host hands it, as a desktop browser would open it, and [`probe.mjs`](tests/journey/probe.mjs) then talks to the studio with the cookie that browser keeps.

The steps: (1) `npm exec` of the packed launcher installs release 1 with the log agreeing, printing the five progress lines and recording the check; the launcher is installed with `npm install --global`, as setup offers; `delorun setup --config` runs; `delorun` starts in the background and opens the studio, whose index answers 200 with the cookie and 401 without; every enabled row is active; a chat completes and is on disk; (2) with the log silent a fresh install warns and records `unchecked`, and with it contradicting a fresh install refuses and installs nothing; (3) `delorun plugin` adds a plugin with the pnpm the release carries; two plugins added from files, one bundle turned off again, a row turned off, a theme row, a preset row and a skill; (4) without git on `PATH`, `delorun update` refuses before it fetches anything; `delorun update` to release 2 names the fixture plugin before anything changes and applies after the person confirms; (5) `delorun recover rollback`; (6) the update to release 2b rolls back on its own; (7) the update to release 3 with the copy, a second chat, and the rollback that restores the first and sets the second aside; (8) the same update with `--no-data-copy`; (9) the tampered release refused by a fresh install and by an update; (10) `delorun verify` before and after a runtime file changes; (11) the trash, export, and import into a second container. A step that fails because the product does not do what it promises is marked `it.fails` with the defect; the spec prints the wall time of each part. While working on the spec, `DELORUN_JOURNEY_CLOSURE=<dir>` names a directory holding release 1's archive and file list from an earlier `build-closure.ts --version 0.1.0 --platform linux-x64 --artifacts existing` run, which the spec uses instead of building one, and `DELORUN_JOURNEY_KEEP=1` leaves the containers running after the run to look inside them; the check sets neither.

The journey does not cover the npm registry and its attestation, the install script, the shipped root, the public release log, the tailnet, the desktop Host, other Node majors than the pinned one, or native Windows and macOS, which Delorun 0.1.0 does not run on.

## The rehearsal

`node_modules/.bin/tsx delorun/apps/release/scripts/rehearsal.ts [--work <dir>] [--closure <dir>] [--only <id>,...] [--keep]` walks the update journey on this computer with the release tooling and no test harness, as a person would. It needs Node 24, `git`, `script` (util-linux) and a worktree whose tracked files are committed, because it builds release 1 with `build-closure.ts --artifacts existing`; `--closure` names a directory that already holds release 1's archive and file list (`0.1.0-rc.1`, `linux-x64`) from such a build. It uses no Docker machine, no model key and no network beyond loopback. Its home, `HOME` and npm cache sit under `--work` (a new directory under the system temporary directory by default), which it removes unless `--keep` is given. Every run stops the Delorun it started before it exits, with or without `--keep`. With `--keep` it prints the command that removes the kept folder; the installed program store is read-only, so that command first restores write permission with `chmod -R u+w`.

It signs `0.1.0-rc.1` and later test versions with throwaway keys (the production keys are refused) and `local-release.ts`, serves the channel and a stand-in release log over HTTP on loopback, packs `delorun/apps/npm-launcher` with those origins and the run's root, and installs it as `npx --package=<tarball> -- delorun` does. The channel is HTTP because the launcher accepts `http:` only on loopback and `https:` for any host, but the launcher never passes `NODE_EXTRA_CA_CERTS` or `NODE_OPTIONS` to the runtime, so a runtime cannot update from a channel with a self-signed certificate. The release log is the stand-in of the test fixtures, not the public log.

Its scenarios, in order, each printing `PASS` or `FAIL` with what the person saw:

| Id | What it proves |
| --- | --- |
| `install` | `npx` of the packed launcher installs release 1, prints the progress lines and records the log check |
| `setup` | the pinned command installs, `delorun setup --config` runs without questions, and Delorun starts |
| `update` | `delorun update --yes` takes the next release and keeps the person's file |
| `rollback-auto` | a release whose Host never answers rolls back on its own and names the failed criterion |
| `tampered` | one changed archive byte is refused by a fresh install and by an update, and the store is left alone |
| `clock` | the launcher run with its clock 4 days ahead (a preload for `Date`; there is no `faketime` here) refuses a fresh install naming the expiry and starts an installed release |
| `update-after-clock` | with the clock back, the next signed release updates with no other action |
| `repair` | `delorun repair` replaces a program whose file changed and keeps the data, and `delorun recover status` and `recover discard` list and remove the program store it set aside |
| `from` | `delorun update --from <folder>` installs with the channel switched off, and a lower release is refused |
| `by-hand` | the steps of [Last resort, by hand](../../docs/guide/help/troubleshooting.md#by-hand), typed literally, give a working program |

The launcher removes `NODE_OPTIONS` from the runtime's environment, so the clock preload reaches the launcher and not the runtime; the runtime's own timestamp check at `delorun update` is covered by `c02-refuses-expired-timestamp` and by the launcher's identical check. The disk it needs is large: each release unpacks to about 1.5 GB, and the by-hand scenario copies the home as the guide's step 2 says, leaving out `runtimes/` when the disk could not hold the copy.

`--windows` runs a shorter probe from WSL for Windows: the packed launcher runs under the Windows `node.exe` (`REHEARSAL_WINDOWS_NODE` overrides `/mnt/c/nvm4w/nodejs/node.exe`) with a home in a new folder under the Windows temporary directory. Releases publish no Windows runtime, so the probe needs no closure and its one scenario, `win-refuses`, checks that the launcher stops before it downloads, says Delorun 0.1.0 runs in WSL2, and writes nothing into the home. It is a manual check; it does not exercise the named pipes a native Windows runtime would need, which the release does not yet support. The folder is left in place for you to remove. The rehearsal does not cover macOS, the public release log, the npm registry or the production hosts.

## The local RC channel

`node_modules/.bin/tsx delorun/apps/release/scripts/local-channel.ts serve --channel <dir> --port <n> --state <state.json> --timestamp-key <timestamp.pem> [--host 127.0.0.1] [--resign-hours 24]` serves a release channel directory from this computer, so release candidates update through the real updater. It adds no signing code: it serves the output of [`local-release.ts`](#local-release) and re-signs the timestamp with the signer of `sign/timestamp.ts`.

- **Server.** It answers GET and HEAD for regular files below `--channel` and nothing else: no directory listing, no `..` or encoded separator, no symlink that points outside the directory (each answers 404), and 405 for other methods. `--host` is `127.0.0.1` or `::1`; any other address stops the command. JSON is `application/json`, archives `application/gzip`, and `timestamp.json` carries `Cache-Control: no-store`. It logs one line per request error and per re-signing; it never prints key material.
- **Re-signing.** On start, and every `--resign-hours` (24 by default; at most 48, because a timestamp lives 72 hours), it writes the next `timestamp.json`: the same channel entries and root, the version plus one, `issued` one hour before now and `expires` 72 hours after it. The signer state in `--state` moves with it, written first, and both files are replaced through a temporary name, so a reader never sees half of one. If a re-signing fails (a bad key, a state that no longer matches the served timestamp), the old files stay and the log says why; the next interval tries again. Updates and fresh installs refuse a timestamp that has expired, so keep the command running.
- **Start.** Sign rc.1 into a new channel directory with `local-release.ts` (the [runbook](#local-release) options, `--out <channel dir>`, `--state <state.json>`, and `--log-submit`, `--log-checkpoint` and `--log-tiles` for the release log), build the launcher with `npm-launcher/src/build.ts --channel-origin http://127.0.0.1:<port>` (the launcher accepts `http:` on loopback only), then run the `serve` command with the same directory, state and the timestamp key. The port is part of the launcher, so use the same one every time.
- **Add an RC.** Run `local-release.ts` again with the next `--version`, the same `--out` and the same `--state`, while the server runs. The release files go in first and the timestamp last; the server needs no restart, and the next re-signing continues from the timestamp the release wrote. A version that is not higher, or already in the channel, is refused.
- **Stop.** Send the process `SIGINT` or `SIGTERM`; it closes the server and exits. Nothing is installed or left behind.
- **What the person's updater sees.** The launcher fetches `http://127.0.0.1:<port>/timestamp.json`, then the root chain, the manifest named there and the release files under `releases/download/v<version>/`, and verifies them as it does for any channel. An installed `~/delorun-rc` that finds a higher version offers the update; while the server is stopped, updates fail and the installed runtime keeps starting.

To keep it running, save this as `~/.config/systemd/user/delorun-local-channel.service`, then run `systemctl --user enable --now delorun-local-channel` (`loginctl enable-linger $USER` keeps it running after you log out). Replace the paths with yours. The unit runs `node_modules/tsx/dist/cli.mjs`, not `node_modules/.bin/tsx`, which pnpm makes a shell script that `node` cannot run, and sets `PATH` to the directory of the same `node` so the scripts it starts find it:

```ini
[Unit]
Description=Delorun local RC channel

[Service]
Environment=PATH=%h/path/to/node-directory:/usr/bin:/bin
ExecStart=%h/path/to/node-directory/node %h/path/to/repo/node_modules/tsx/dist/cli.mjs %h/path/to/repo/delorun/apps/release/scripts/local-channel.ts serve --channel %h/delorun-rc-release/channel --port 18080 --state %h/delorun-rc-release/timestamp-state.json --timestamp-key %h/.config/delorun/preview-release/timestamp.pem
Restart=on-failure

[Install]
WantedBy=default.target
```

**Installed smoke on local closures.** `node_modules/.bin/tsx delorun/apps/release/scripts/local-smoke.ts --previous-closure <dir> --previous-version <v> --closure <dir> --version <v> [--work <dir>] [--channel-port <n>] [--studio-port <n>] [--budget-minutes <n>] [--log <file>] [--keep]` signs the two releases from closure directories that `build-closure.ts --platform linux-x64` wrote, with throwaway keys and a stand-in release log, into a new channel, and runs `scripts/installed-smoke.ts` on it, so step 6 updates the previous release to the candidate through the real updater. It signs nothing with a production key, and it refuses builder paths in the candidate as `local-release.ts` does; the previous release, only the update's starting point, may carry them. `installed-smoke.ts` itself prints the last 200 lines of the home log of the home a failed run was in, and with `--keep-home` (or `--keep-going` after a failure) keeps the scratch home and prints its path. Step 6 starts from the newest release older than `--version` in the channel directory; `--previous <version>` (`cut-rc.ts --smoke-previous <version>`) starts it from another release, which must be in the channel and older, and step 1 fails at once otherwise. After the update, the change log must hold a change applied by the update for a pack exactly when the previous and the new release's signed files for that pack differ (`packsChangedBetween`), and no change waiting for review: a pack with equal files in both releases has nothing to replace, so a change for it is an error too.

## Cutting a preview or release candidate

`node_modules/.bin/tsx delorun/apps/release/scripts/cut-rc.ts --version 0.1.0-preview.<n>[.<m>]|0.1.0-rc.<n>[.<m>] --channel <dir> --state <signer state file> --keys <dir> --root <root file> --commit <sha> [--highlights <file>] [--summary <text>] [--work <dir>] [--closures-from <dir>] [--artifacts build|existing] [--platform <platform>]... [--log-submit <url> --log-checkpoint <url> --log-tiles <url>] [--log-poll-seconds <n>] [--smoke-previous <version>] [--allow-builder-paths] [--dry-run]` turns the steps of the release runbook into one command, run from a checkout of `--commit`. Run it with `--dry-run` first: it prints the plan and the commands, and runs nothing. A public cut passes `--artifacts build`; `--artifacts existing`, the default, embeds the worktree's paths and is refused at signing (see the builder-path refusal under the runtime closures) unless `--allow-builder-paths` is passed, for a local iteration candidate only.

1. **Tree.** `--commit` must be `HEAD` and tracked files must be clean.
2. **Log probe.** Before it builds anything, [`scripts/probe-log.ts`](scripts/probe-log.ts) submits to `--log-submit` one entry over random bytes for each log-entry key type `--root` lists as `active`, each signed by a key made for the probe, and prints `probe-log: <type> accepted|refused (<answer>)` for each. When the log accepts none, the cut stops and names the runbook section on rotating the root. `node_modules/.bin/tsx delorun/apps/release/scripts/probe-log.ts --root <root file> --log-submit <url>` runs it alone: exit 0 when the log accepts a listed type, 1 when it accepts none, 2 on a usage error, a root whose signatures do not verify or a root without `logEntryKeys`. Each probe leaves one entry in the log.
3. **Changelog.** When `delorun/changelog/changelog.json` has no entry for the version, it assembles one with [`assemble.ts`](#assembly) and stops with exit code 3 so you can review and commit the changed files; run it again with the new `--commit`. With an entry, it goes on.
4. **Release notes.** It writes the notes (`assemble.ts --highlights`) to `--highlights` (`<work>/notes-<version>.txt` by default) and signs them into the manifest as `notes` through `local-release.ts --notes`.
5. **Closure.** It removes stale build stages (directories beside the build root that carry its marker, and a lock whose process has gone), then runs [`build-closure.ts`](#runtime-closures) into `<work>/closure-<version>`. `--closures-from` signs closure files an earlier run built and skips both steps, which is the rerun after a logging failure.
6. **Sign.** [`local-release.ts`](#local-release) signs, logs and writes the candidate into `--channel` with the key files in `--keys` (`targets.pem`, `timestamp.pem`, and `log-entry-ecdsa.pem`, passed as `--log-entry-key PKIX_ECDSA_P256_SHA_256=<file>` when it exists) and the signer state in `--state`. Only the key files' paths appear in the plan and the log. The log endpoints default to the public Rekor v2 instance of the runbook; a checkpoint wait can take up to 30 minutes (`--log-poll-seconds`, 60 polls), so run the command in the background.
7. **Verify.** It checks the channel as a client does: root chain, timestamp, the manifest the timestamp names, the signed notes against their bytes, and the manifest signature of every other release in the channel, so the previous candidate is still there to update from. A private test build `preview.N.M` (M from 1) requires `preview.N` in the channel for M = 1 and `preview.N.(M-1)` otherwise. A plain candidate requires the newest lower candidate of its series, which may be a test build: `preview.2` after `preview.1` and `preview.1.1` requires `preview.1.1`. preview.1 and rc.1 require no earlier release, and a version already in the channel is refused. Versions order as preview.1, preview.1.1, preview.2, rc.1, rc.2 and then 0.1.0.

Every step is logged with its duration; all command output goes to `<work>/cut-rc-<version>.log`. A failure names the step and the next action, and the channel still serves what it served. If the log submission succeeded but the wait timed out, run `log-release.ts` with the same endpoints rather than submitting again. The command never tags, pushes or touches an installed home. It ends by printing those commands: the tag and its push, keeping the [local channel](#the-local-rc-channel) served, and `rc update --check` / `rc update` in the installed `~/delorun-rc` home with the runbook's wrapper. `tests/local/cut-rc.integration.spec.ts` cuts `preview.1`, its test build `preview.1.1` and `preview.2` with throwaway keys into a scratch channel and checks that each signs its notes and that the one before stays offered as the release to update from.

## Rebuild comparison

`node_modules/.bin/tsx delorun/apps/release/src/compare-rebuild.ts <first> <second>` compares two output directories of the same release, such as the release workflow's and the targets-key holder's rebuild. It exits 0 when the two hold the same file names and every file matches, printing each difference that an entry of `rebuild-exceptions.json` accepts with that entry's id. It exits 1 on any other difference, printing each one, and signing refuses such a rebuild. It exits 2 on a usage error, an unreadable directory or an exceptions file that does not validate.

- A runtime archive matches when both copies are in the deterministic form (re-encoding the entries reproduces the archive's bytes), hold the same paths with the same modes and mtime, and every entry has the same bytes or a difference an exception accepts.
- A runtime file list matches when each copy equals the list derived from its own archive, and the SBOM when each copy equals the SBOM derived from the archives beside it.
- Any other file matches when it is byte-identical.

`rebuild-exceptions.json` lists each accepted difference with an id, the comparison it applies (`pe` is the only one) and its reason; unknown fields fail validation. Its first entry, `pe-authenticode`, applies only to the Windows archive: it compares a PE file without its Authenticode certificate table, the security data directory entry and the header checksum, padded with zeros to 8 bytes, because the release workflow signs the Windows closure's PE files and a rebuild outside it cannot. The table must consist of `WIN_CERTIFICATE` entries of revision 2.0 and type PKCS #7 SignedData that fill it to the end of the file, each holding one DER SEQUENCE followed by fewer than 8 zero bytes, with only zero bytes padding entries to 8 bytes; any other appended or hidden bytes are a difference.

## SBOM

`delorun-<version>.spdx.json` is an SPDX 2.3 JSON document derived only from the runtime archives of the release platforms and from `toolchain.json`: one package per archive with its SHA-256, the pinned Node and pnpm, each Debian package `toolchain.json` pins in the native builder image as a `BUILD_TOOL_OF` each archive whose native code that image compiled (`pkg:deb` purls with the image's architecture), and one package per installed npm package version found as `node_modules/<name>/package.json` in an archive, with its `pkg:npm` purl, its declared licence when that is a licence expression, and the SHA-512 the closure's lockfile records for it. Each package's SPDX id is its kind and the first 128 bits of the SHA-256 of its kind, name and version, so names that differ only in characters an SPDX id cannot hold stay distinct, and an id that two packages would share fails the build. `created` is the archives' `SOURCE_DATE_EPOCH`, so the same archives always give the same document. When the output holds `delorun-<version>.images.json`, the document also describes the S2 and S3 images by index digest, each descended from the digest-pinned base, with the S3 image containing the Linux closures; it does not list the Debian packages inside the base.

## Dependency advisory check

`node_modules/.bin/tsx delorun/apps/release/src/check-advisories.ts --version <version> --release <dir> [--commit <rev>] [--feed <url>]` reads every runtime archive in `--release` and sends every package version it holds to npm's bulk advisory API: each registry version `app/pnpm-lock.yaml` locks, each installed package version the SBOM lists, which includes dependencies bundled inside another package that the lockfile does not list, and the pnpm version `toolchain.json` pins at `--commit`. Local `file:` and `link:` packages are the release's own source and are left out. The API is `https://registry.npmjs.org/-/npm/v1/security/advisories/bulk`, and writes `delorun-<version>.advisories.json`. An advisory affects a checked version when the version satisfies the advisory's vulnerable range; a range the check cannot read is a malformed answer, which fails the check rather than matching nothing. The check passes only when each affecting advisory has an entry in [`delorun/release/advisory-acceptances.yaml`](../../release/advisory-acceptances.yaml), as committed at `--commit` (`HEAD` when omitted; the release's tag in the release workflow and its commit when signing), with the same advisory and package, a range the locked version satisfies, a `lapsesAfter` at or above the release, and an `approver` whom `.github/CODEOWNERS` at the same commit names as an owner of that file. Each entry also records `added`, the date it was added (`YYYY-MM-DD`), which the release notes show. It fails on any other affecting advisory, on a lapsed acceptance or one whose approver is not an owner, on an entry without `added`, on an acceptances file with an unknown field or a duplicate key, and when the feed cannot be reached or answers malformed; it exits 1 then.

The report holds `schema` (`delorun.release-advisories/1`), `version`, `feed`, `packages` (how many locked versions were checked), `findings` (each affecting advisory with its package, version, severity, title and vulnerable range, and the covering acceptance, or why its acceptance lapsed in `lapsed` or was refused in `unapproved`), `result` (`pass` or `fail`) and `problems`. Signing runs the check again and refuses unless the published report is, as JSON, the report its own run gives. `assemble.ts --advisories <report> --manifest <signed manifest>` adds the section "Accepted advisories" to the release notes, listing each accepted advisory with its package, range, reason, approver, date and lapse release; it refuses a report other than the file the signed manifest names by length and SHA-256, one whose accepted ids differ from the manifest's, a report of another release and one that failed.

## Signing

Signing happens on the targets-key holder's machine, outside CI, after the release workflow has built the release from the tag `v<version>` and the holder has rebuilt it:

1. Download the release workflow's files of the draft release, including its `manifest-draft.json`, into a directory, such as `release/`.
2. Check out the tag in the repository and build it with the same recipe, attesting the output: `node_modules/.bin/tsx delorun/apps/release/src/build-closure.ts --version <version> --commit v<version> --out rebuild/ --attestation-key ~/.config/delorun/rebuild-attestation.key --attestation rebuild.attestation.json`, then the images over the same output: `node_modules/.bin/tsx delorun/apps/release/src/build-images.ts --version <version> --out rebuild/ --oci rebuild-oci/ --attestation-key ~/.config/delorun/rebuild-attestation.key --attestation rebuild.attestation.json`, which first checks that the attestation verifies with the key and covers exactly the files in `rebuild/`, and then extends it, with its commit, to the images file and the rewritten SBOM; it gives no attestation to a directory this machine's build did not write.
3. Record the rebuild: `node_modules/.bin/tsx delorun/apps/release/src/record-rebuild.ts --version <version> --release release/ --rebuild rebuild/ --record delorun-<version>.rebuild.json --builder <name> --compared-with <workflow run URL>`. It compares every rebuilt file with the workflow's file of the same name under `rebuild-exceptions.json` as committed at the tag, writes the record to `--record` outside `release/`, and exits 1 when the comparison finds a difference. It refuses to run with `CI` or `GITHUB_ACTIONS` set, and refuses a rebuild that lacks any platform's archive or file list or the SBOM.
4. Sign: `node_modules/.bin/tsx delorun/apps/release/src/sign-release.ts --release release/ --rebuild rebuild/ --record delorun-<version>.rebuild.json --attestation rebuild.attestation.json --attestation-key ~/.config/delorun/rebuild-attestation.key --key <targets.pem>`, with the release branch fetched, as `git fetch origin main`. Add `--release-branch <revision>` only to sign against another branch than `origin/main`; the allowed-signers file and the production-keys registry are read as that branch commits them, never from the working tree. Add `--first-of-line` only when the version is a patch version, such as `0.1.3`, and no earlier release of its major and minor was ever published.

`sign-release.ts` refuses with a message naming the required source, "a rebuild made by the targets-key holder on their own machine, outside CI, with the published recipe", when the rebuild record is missing or does not read; when `release/` already holds `delorun-<version>.rebuild.json`, or `--record` or `--rebuild` lies in `release/`; when the record says `ci: true` or reports a difference; when `CI` or `GITHUB_ACTIONS` is set; when `--rebuild` is not a directory on this machine, its files do not reproduce the record's digests, or it lacks any platform's runtime archive or file list or the SBOM; when the record's commit is not the commit the tag names, or its recipe digest or toolchain (Node.js, pnpm, compiler and linker) is not the recipe's at that commit; when the attestation is missing, lies in `release/` or `rebuild/`, or does not verify with the attestation key over the version, the commit and every file in `rebuild/`; or when comparing the workflow's files with the rebuild again finds a difference. It also runs the dependency advisory check again against npm's feed, with the acceptances committed at the release's commit, and refuses when it fails or accepts other advisories than the draft's `advisories.accepted`. It also refuses a draft whose SBOM is not `delorun-<version>.spdx.json`, whose runtime entries are not `delorun-<version>-<platform>.tar.gz` (`.zip` for `win32-x64`) and `delorun-<version>-<platform>.files.json` for their own platform, or whose files are not in the release directory with the lengths and digests it lists. It also refuses a draft without `security` (whether the release is a security fix) or `summary` (its one-line summary, at most 200 characters with no control, format or line-break character, no lone UTF-16 surrogate and no whitespace at either end), which every signed manifest carries for the update notice. When every check passes, it writes each signed runtime file list, the record as `delorun-<version>.rebuild.json` and `delorun-<version>.manifest.json`, whose `rebuild` names the record and the holder with `ci: false`, under temporary names in `release/`, then renames them into place with the manifest last; a failure before the renames leaves `release/` unchanged.

Before it reads the rebuild, `sign-release.ts` checks the release's source. It refuses a tagged commit that is not on the release branch (`git merge-base --is-ancestor`) or a release branch that names no commit. It refuses a targets key the [production-keys registry](#production-keys) does not list, and every key while the registry lists none. It refuses a tag `v<version>` that is lightweight, that is an annotated tag without an SSH signature or made for another tag name, or whose signature `git verify-tag` (with `gpg.format=ssh` and `ssh-keygen`) does not verify with a key the [allowed-signers file](#release-tag-signers) lists, and it refuses every tag while that file lists no key. Both files are read with `git show <branch>:<path>` from the release branch. It refuses a draft whose `install.sh` or `install.ps1` is not a zero-length placeholder, because the install scripts are not in the rebuild comparison yet. After checking the draft's files, it refuses each `npm[]` entry whose packed tarball, `<name>-<version>.tgz` as `npm pack` names it (`delorun-<version>.tgz`), is not in `release/`, whose integrity, `sha512-` and the base64 SHA-512 of the tarball's bytes as npm's `dist.integrity`, is not the entry's, or whose `package/package.json` names another package or version; so `release/` holds the packed launcher the workflow publishes.

The patch rule (`src/sign/patch-rule.ts`) runs before anything is written. The draft's `dsh` must be the `version` of `packages/boot/app-boot/package.json` at the tagged commit. A release is a patch of every lower `v<major>.<minor>.<patch>` tag with the same major and minor and no pre-release suffix (`0.1.3-rc.1` counts as `0.1.3`), and signing refuses a patch whose upstream version, `docs/persistence-schema.json`, `delorun/packages/update/src/data-records.json` or `covered` list in `delorun/packages/contract-plugin-versions/plugin-interface.json` differs from such a release's, whose tagged commit no longer declares a covered service or reads a covered manifest field, or when one of those files is missing, naming the earlier release, what differs and the next minor to release instead. So a security fix ships as a patch that disables no plugin and copies no data, and a release that moves the upstream base is at least a minor.

A missing tag must not skip the rule, so for a patch version (patch number above 0) signing first checks the earlier releases the local tags name. It refuses when an earlier tag's commit is not an ancestor of the release commit (`git merge-base --is-ancestor`); when `delorun/changelog/changelog.json` at the release commit is missing or unreadable, does not list an earlier tag's version, or lists a non-pre-release version of the same major and minor below the release that has no tag; and when no earlier release is found and `--first-of-line` is not given, naming the option, because a checkout without the published tags would otherwise compare the patch with nothing. `--first-of-line` is refused for an `X.Y.0` version and when an earlier release is tagged. The changelog records versions, not commits, so the check does not prove that a tag names the commit its release was published from.

The inventory lists every `interface Context` member (`service`) and `interface Events` member (`event`) declared in `declare module '@deepseek-ai/cordis'` in the `.ts`, `.tsx` and `.d.ts` files under `delorun/packages/*/src` and `delorun/apps/*/src`, as `covered` (offered to plugins) or `internal`, and `tests/sign/plugin-interface.spec.ts` fails when a declared service or event is missing from it or a listed entry is no longer in its source.

### Release tag signers

`delorun/release/allowed-signers` lists the SSH keys allowed to sign release tags, one `<principal> namespaces="git" <key type> <base64 key>` line each, in git's `gpg.ssh.allowedSignersFile` format ("ALLOWED SIGNERS" in `man ssh-keygen`). It lists no key, so `sign-release.ts` refuses every tag until the owner adds the public half of each release signer's SSH signing key; a change to the file needs CODEOWNERS review. A signer tags the release commit with `git -c gpg.format=ssh -c user.signingkey=<private key file> tag -s -m "Delorun <version>" v<version>`.

### Production keys

`delorun/release/production-keys.json` (`delorun.production-keys/1`) lists Delorun's production trust material: `roots`, each production root file's `version` and the SHA-256 of its bytes, and `keyids`, the key id of every production root, targets and timestamp key, which is the SHA-256 of the raw Ed25519 public key as root metadata lists it under `keys`. It lists nothing yet, because no production key exists. After the key ceremony, the owner adds each signed `root/<n>.root.json` with the digest `sha256sum` prints and every key id that root lists in `roles.root.keyids`, `roles.targets.keys` and `roles.timestamp.keyids`, in a reviewed commit, and after each rotation adds the new root and keys without removing any. The Trust page and the README publish the same root SHA-256 and key ids. `local-release.ts` refuses every listed root and key, and `sign-release.ts` and `sign-timestamp.ts` refuse every key the release branch's registry does not list, so an empty registry stops production signing. Releases before 1.0 do not use the production path: they are built with `local-release.ts` and the preview root and keys, which the registry does not list (listing them would make `local-release.ts` refuse them), and `release-channel/src/publish-release.ts` uploads the channel directory; the registry stays empty until the 1.0 key ceremony; the reader refuses a file above 64 KiB, an unknown or missing field, a repeated JSON key and an entry listed twice.

### The targets key

The targets key is an Ed25519 private key in a PKCS #8 PEM file that only its owner can read; `sign-release.ts` refuses a key file with any group or other permission. The repository holds no key. The owner creates the key in the signing ceremony on the offline machine that signs releases, for example with OpenSSL 3:

```sh
umask 077
openssl genpkey -algorithm ed25519 -out targets.pem
openssl pkey -in targets.pem -pubout -out targets.pub.pem
```

The public key goes into the root metadata's `keys` and `roles.targets`, signed by the root key ([C2](../../docs/contracts/c02-release-manifest.md#root-metadata)); the private key never enters CI, a cloud service or a machine the release workflow can reach.

### The rebuild attestation key

The attestation key is a secret of at least 32 bytes at `~/.config/delorun/rebuild-attestation.key` on the holder's signing machine, readable by its owner only; it never leaves that machine. The holder creates it once:

```sh
mkdir -p ~/.config/delorun && umask 077
openssl rand -out ~/.config/delorun/rebuild-attestation.key 32
```

`build-closure.ts --attestation-key` writes an HMAC-SHA256 over the release version, the commit and the length and SHA-256 of every file in `--out`, and `sign-release.ts` checks it. It catches the mistake of pointing `--rebuild` at a directory this machine's build did not write, such as a downloaded copy of the release workflow's output. It cannot stop a holder who sets out to cheat, who holds the key and can attest any directory; C2 already states that a rebuild's independence cannot be proven.

### Root and timestamp metadata

`node_modules/.bin/tsx delorun/apps/release/src/sign-root.ts --draft <file> --key <root.pem>... [--previous <root file>] --out <root/<n>.root.json>` signs root metadata in the owner's ceremony: the draft is the root's `signed` content, and the file is written only when it verifies with its own root threshold, has not expired and, for a rotation, verifies as the version after `--previous` with that root's threshold too.

`node_modules/.bin/tsx delorun/apps/release/src/draft-root.ts --root-key <root.pub.pem>... --targets-key <pub.pem> --timestamp-key <pub.pem> --catalogue-key <pub.pem> --log-origin <origin> --log-vkey <vkey> --witness <vkey>... --log-entry-key <type>=<public.pem>... [--earlier-log <vkey>]... [--version <n>] [--root-threshold <n>] [--witness-threshold <n>] [--issued <time>] [--days <n>] --out <draft.json>` writes that draft from the roles' Ed25519 public key files (`openssl pkey -pubout`), so the draft step reads no private key and refuses a file that holds one. Each key id is the SHA-256 of the raw public key, the targets key is the one `active` targets key, `issued` is now unless `--issued` names a UTC time, and `expires` is `--days` after it, 365 by default and at most. The log verifier key must name `--log-origin`, each witness's name is the one its verifier key carries, and both must parse as C2SP signed-note verifier keys. Each `--log-entry-key` adds an `active` entry to `logEntryKeys` in the order given, from a public key file of that type (`PKIX_ECDSA_P256_SHA_256` or `PKIX_ED25519_PH`), and at least one is required; `logs` lists the current log, then each `--earlier-log`, a log named by its verifier key. It never replaces an existing file.

`node_modules/.bin/tsx delorun/apps/release/src/sign-timestamp.ts --state <state.json> --root <file>... [--first] --stable <manifest> --beta <manifest> [--replaced <manifest>]... --out <timestamp.json> [--release-branch <revision>]` signs the next timestamp with the online key from the `DELORUN_TIMESTAMP_KEY` environment variable, which must be a timestamp key the [production-keys registry](#production-keys) lists as `--release-branch` (`origin/main` by default) of the repository it runs in commits it, continuing from the last timestamp the state holds, and writes the new state before the timestamp. `--root` starts at the root the state trusts and repeats after a rotation, newest last. The state's last timestamp must match the digest and version the state records and verify with the timestamp key of the root it names and with that root file's digest; it may have expired. No caller passes a previous timestamp. `--first` signs without one, only while the state records none. Each channel's manifest must verify with the newest root's targets keys; the stable channel names a stable release and the beta channel a beta or stable release; and no channel moves to a lower version. A channel moves to another manifest of the release it names only when that named manifest, passed with `--replaced`, differs from the new one in signatures alone, or also in `published` once the named one no longer verifies with the newest root's targets keys, as after a targets-key rotation; any other change to the signed content is refused. The new version is one above `--previous` and expires 3 days after issue.

The state file (`delorun.release-timestamp-state/1`) holds the root the signer trusts and the last timestamp signed, with its version, SHA-256 and bytes, so a genuine older timestamp served by the untrusted metadata host cannot roll a channel back. The owner writes it once in the root ceremony with `node_modules/.bin/tsx delorun/apps/release/src/sign-timestamp.ts --init-state --root root/1.root.json --state state.json`, and stores its content as the variable `DELORUN_TIMESTAMP_STATE` of the release workflow's protected `release` environment, never on the metadata host. Each signing job restores the variable to a file, signs, and writes the new state back to the variable with a token that may write that environment's variables and is available only to jobs in it. The owner's release workflow file, which is not written yet, must:

- put every job that signs a timestamp in one `concurrency` group, so two signings never start from the same state;
- write the new state back to `DELORUN_TIMESTAMP_STATE` before it publishes the timestamp, so a published timestamp is always the one the state holds.

`node_modules/.bin/tsx delorun/apps/release/src/sign-timestamp.ts --import-from <timestamp.json | https origin> --root <root file>... --state <state.json>` brings the state level with the channel after the release-channel Worker's daily re-signing moved it on (before 1.0, the local signer and the Worker both write the channel's timestamp). It reads the file the channel serves, from a downloaded copy or from `<origin>/timestamp.json` (HTTPS; HTTP on loopback only; at most the timestamp size limit; no redirect), verifies it as a client does (the timestamp role's signature under a key of the root it names, the contract's lifetime, not expired, not issued in the future; the root chain starts at the state's root and the file names its newest), and writes the state with that file as the last timestamp. It needs no key. It refuses a file that does not verify, one signed by another key, a lower version than the state's last, a different file of the same version, one that moves a channel back to a lower release, and an expired one; a refusal leaves the state as it was. The same file as the state's last is a no-op. The next signing then issues version plus one. The two writers stay ordered by the publish: `publish-release.ts` only replaces `timestamp.json` with a higher version, conditional on the entity tag it read, and posts it to the Worker's high-water mark, so a signing from a stale state, or one the Worker overtook after the import, is refused at the publish with nothing replaced; import again from what the channel now serves, sign again and publish. Run the import immediately before each local release when the channel has been published before.

## Verification

`@delorun/release-formats/sign/verify` applies C2's client verification: `trustRootChain` walks root versions from the root the caller holds, each signed by the previous root threshold and its own, issued before it expires, living at most 365 days, and with the newest not past its expiry; a root that gives one key two roles or does not have exactly one `active` targets key fails to read; `verifyTimestamp` checks the timestamp role's signature, the 3-day lifetime, an issue time not after the local clock, expiry with no clock tolerance (its refusal names the expiry and the local clock), the stored version, and the root version and file digest it names; `verifyChannelManifest` accepts only the manifest file the fresh timestamp names for the channel, at the release and on the channel the timestamp names (the beta channel also names stable releases), signed by a targets key valid for the release (an `active` key, or a `retired` key whose `lastRelease` is at or above it; never a `revoked` one); `verifyFileList` and `checkFileRef` check each file's length and SHA-256 against the manifest. Every signed file is read with its size limit before parsing, and a duplicate JSON key, an unknown field or an unknown `schema` fails the read. `@delorun/release-formats/sign/json` holds the RFC 8785 serialisation that signatures cover.

## Images

`node_modules/.bin/tsx delorun/apps/release/src/build-images.ts --version <version> --out <dir> --oci <dir> [--attestation-key <file> --attestation <file>]` runs after `build-closure.ts` on the same output. It builds the images `images.json` names, each for `linux/amd64` and `linux/arm64` from the Debian base it pins by digest, with BuildKit's `rewrite-timestamp` at the closures' `SOURCE_DATE_EPOCH`, no cache and no SLSA build or SBOM attestation, whose build times and invocation ids would differ between builds. The Dockerfiles pin their frontend by digest.

- The S2 workspace image (`images/s2/`) adds the empty helper socket directory `/run/delorun-helper`. The S2 helper and the egress proxy are not in it.
- The S3 harness image (`images/s3/`) adds the users `delorun` (uid 1000) and `delorun-harness` (uid 1001) and each architecture's Linux runtime closure, read-only, at `/opt/delorun/runtime`, and runs as `delorun-harness`.

The command writes the OCI layout of each image to `--oci` and `delorun-<version>.images.json` to `--out`: each image's repository with its index and per-platform manifest digests, the Docker Engine and BuildKit versions that built them, and each image's installed Debian packages per platform, read from the dpkg status of the topmost layer that carries one. The rebuild comparison compares the file byte for byte, so a rebuild by another Docker or BuildKit version, or with other packages, differs; the command also refuses to build with versions other than `toolchain.json`'s `images` pins. When `--out` holds every platform's closure, it rewrites the SBOM to describe both images, the base and their Debian packages as `pkg:deb/debian` purls. The release workflow pushes the layouts by digest, and the manifest's `images` copies the file's image references. The images file is one of the files every rebuild and signing comparison must cover, signing refuses a draft whose `images` differ from it, and signing derives the SBOM's image entries with the base that `images.json` names at the release's commit.

Each image's entry in `images.json` also names its seccomp profile and the profile's licence, committed files in this directory: `images/seccomp.json` for both images, Docker Engine 29.9.2's default profile (`github.com/moby/profiles/seccomp` v0.2.4, `default.json`), under the Apache-2.0 licence in `images/seccomp.LICENSE`. The command copies them to `delorun-<version>.<image>.seccomp.json` and `delorun-<version>.<image>.seccomp.LICENSE` in `--out`, so the release publishes the licence beside each profile, and the image's reference in the images file carries the profile as the `seccomp` file reference that contract C9's supervisor runs the image's containers under. Each listed profile and its licence are files every rebuild and signing comparison must cover, and the rebuild record the manifest signs lists their digests; and signing refuses a profile whose length or SHA-256 differs from the draft's reference.

## Release log

`sign-release.ts` also writes `delorun-<version>.manifest.entry.json`, contract C18's Rekor v2 `hashedRekordRequestV002`: the manifest file's SHA-512, the targets key's Ed25519ph signature over the manifest file's bytes with key details `PKIX_ED25519_PH`, and the targets public key in DER. Node's crypto has no Ed25519ph, so `src/log/entry.ts` signs and verifies it with `@noble/curves`. `node_modules/.bin/tsx delorun/apps/release/src/log-release.ts --root <file> --manifest <file> --entry <file> --submit <url> --checkpoint <url> --tiles <url> --out <bundle>` runs in the release workflow: it submits the request to `--submit`, the log's `/api/v2/log/entries`, polls `--checkpoint` every 30 seconds, at most 60 times, for a signed-note checkpoint that a witness the root lists has cosigned and that covers the entry, computes the entry's inclusion proof in that checkpoint's tree from the tiles the log serves below `--tiles` (C2SP `tlog-tiles`, as Rekor v2 serves its tree, reading a partial tile from its full tile once the log no longer serves it), and writes `delorun-<version>.manifest.log.json` only when the bundle verifies; otherwise it exits 1 and the release is not published.

`@delorun/release-formats/log/bundle` verifies a bundle offline in C18's five steps: the manifest digest, the entry's Rekor v2 format and its signature by a log-entry key the root lists (`log/entry-keys`; a root without `logEntryKeys` verifies no entry), which refuses a pure Ed25519 entry, the RFC 6962 inclusion proof, the checkpoint's origin, size, root hash and log signature, and cosignatures from at least the root's threshold of listed witnesses. A checkpoint without such a cosignature fails, whatever its log signature says, and each failure carries C18's reason code. `log/note` reads C2SP signed notes with Ed25519 note keys and `cosignature/v1` witness keys, `log/merkle` verifies inclusion and consistency proofs, and `log/tiles` computes an inclusion proof from a log's tiles.

## Open items

These parts of the release are not built here; each belongs to the work package named.

- The SBOM does not describe the desktop installers, which Delorun does not build because it has no desktop app ([roadmap](../../docs/guide/roadmap.md)).
- The recipe has no pinned toolchain for the macOS binaries of upstream's native system addon, so `darwin-x64` and `darwin-arm64` are not release platforms ([Native code](#native-code)).
- The S2 image does not carry the S2 helper or the egress proxy, and the S3 image does not carry the egress proxy at `/usr/local/bin/delorun-egress-proxy`, the path C9 names.
- The release-log specs use local stand-ins; a first submission to the live log (`log2025-1.rekor.sigstore.dev`) is an owner action, because it publishes. Read-only requests to that log show its layout: `GET https://log2025-1.rekor.sigstore.dev/api/v2/checkpoint` answers a C2SP signed note whose origin line is `log2025-1.rekor.sigstore.dev`, signed by the log and cosigned by several witnesses, and `GET https://log2025-1.rekor.sigstore.dev/api/v2/tile/<L>/<N>` answers 8,192-byte hash tiles (`/api/v2/tile/entries/<N>` the entry bundles), while `/checkpoint` and `/proof/consistency` at the host's root answer `404`. The launcher reads that layout from the host in the root's `log.origin`. The `--submit`, `--checkpoint` and `--tiles` values for the live log are therefore `https://log2025-1.rekor.sigstore.dev/api/v2/log/entries`, `https://log2025-1.rekor.sigstore.dev/api/v2/checkpoint` and `https://log2025-1.rekor.sigstore.dev/api/v2/`; the submission path is C18's and has not been exercised.
