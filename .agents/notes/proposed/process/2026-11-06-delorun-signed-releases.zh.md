# Agent Note: Delorun 发布以离线密钥签名，附带 SBOM 与公开透明日志记录，并与重新构建的结果一致

Status: proposed

[English](2026-11-06-delorun-signed-releases.md) | 中文

## 问题

本人安装 Delorun 时，需要核实某个发布来自已标记的源代码。未签名的发布无法提供这种核实。由构建 runner 上的密钥签名的发布，可以被该流水线中运行的任何代码签署，因此签名并不能证明维护者批准了该发布。使用长期有效 token 的 npm 发布，则无法记录是哪个源代码构建了它。

## 提案

Delorun 发布将以签名者持有的离线密钥签名，而不是以保存在 CI runner 上的密钥签名。每个发布都将附带一份软件物料清单（SBOM）与一条公开透明日志记录。

签名者在 CI 之外的机器上，对已标记的源代码进行重新构建，必须复现出发布产物。只有重新构建结果一致之后，才可以把发布描述为「从已标记的源代码按已发布的流程复现」。

npm 发布将通过可信发布（trusted publishing）进行，并为每次发布附带 OIDC attestation。桌面应用的发布签名将与[桌面打包决策](../../implemented/architecture/2026-08-25-electron-desktop-packaging-and-updates.zh.md) 为 Windows 所描述的离线安排一致，即私钥保存在硬件令牌（token）上。该决策保留发布身份、签名与更新要求的归属，本提案不改变这一归属。

## 相关决策

[npm 发布序列决策](../../implemented/process/2026-08-10-npm-release-sequences.zh.md) 管理上游的三条 npm 发布序列，使用 `@deepseek-ai` 作用域。它记录了基于 token 的发布方式，并陈述了 OIDC 证明适用的条件。Delorun 的包将使用 Delorun 的 npm 作用域与可信发布，因此两项决策覆盖的是不同的包。

[生成的第三方声明决策](../../implemented/process/2026-07-30-generated-third-party-notices.zh.md) 从清单生成许可披露文件。该文件与 SBOM 相互独立，后者将描述每个发布的内容。

## 考虑过的替代方案

**未签名的发布。** 本人无法核实发布的来源，而重新构建也没有可对照的依据。

**由 CI 持有签名密钥。** 发布流水线中运行的任何代码都能使用这样的密钥，因此签名证明的是流水线运行过，而不是维护者批准了该发布。

## 验收标准

- 每个发布记录都包含一份 SBOM、各产物的摘要，以及一条公开透明日志记录，第三方可以据此对照签名进行核对。
- 签名者在 CI 之外的机器上重新构建，能依据已标记的源代码与已发布的流程，复现出每个产物的摘要。
- Delorun 包的每次 npm 发布都附有 OIDC attestation，且它写明了已标记的源代码与发布工作流。
- 对工作流配置的审阅表明，没有任何 CI 任务持有发布签名密钥。

## 风险

重新构建需要字节级一致的输出，而上游的 npm 决策记录了字节级可复现性（byte reproducibility）是被假定而未经度量的，因此在该性质未经度量时，任何发布都不能声称已复现。

离线密钥的处理需要一位指定的签名者与一套流程，这使每次发布都成为手工操作，并依赖该签名者的可用性。

可信发布要求包的 `repository` 字段指向运行发布工作流的仓库，这会约束 Delorun 仓库的托管位置。
