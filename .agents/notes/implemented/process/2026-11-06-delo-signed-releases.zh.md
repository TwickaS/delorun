# Agent Note: Delo 发布以离线密钥签名，附带 SBOM 与公开透明日志记录，并与重新构建的结果一致

Status: implemented

[English](2026-11-06-delo-signed-releases.md) | 中文

## 问题

本人安装 Delo 时，需要核实某个发布来自已标记的源代码。未签名的发布无法提供这种核实。由构建 runner 上的密钥签名的发布，可以被该流水线中运行的任何代码签署，因此签名并不能证明维护者批准了该发布。使用长期有效 token 的 npm 发布，则无法记录是哪个源代码构建了它。

## 决策

Delo 发布以签名者持有的离线密钥签名，而不是以保存在 CI runner 上的密钥签名。每个发布都附带一份软件物料清单（SBOM）与一条公开透明日志记录。

签名者在 CI 之外的机器上，对已标记的源代码进行重新构建，必须复现出发布产物。只有重新构建结果一致之后，才可以把发布描述为「从已标记的源代码按已发布的流程复现」。

npm 发布通过可信发布（trusted publishing）加 provenance 的方式进行。桌面应用的发布签名与[桌面打包决策](../architecture/2026-08-25-electron-desktop-packaging-and-updates.zh.md) 为 Windows 所描述的离线安排一致，即私钥保存在硬件令牌（token）上。该决策保留发布身份、签名与更新要求的归属，本决策不改变这一归属。

## 验证

签名者的重新构建将产物摘要与发布记录进行比较，不一致即停止发布。任何人都可以对照公开透明日志记录核对发布的签名。npm 为每次发布记录一份 provenance 声明。

## 相关决策

[npm 发布序列决策](../process/2026-08-10-npm-release-sequences.zh.md) 管理上游的三条 npm 发布序列，使用 `@deepseek-ai` 作用域。它记录了基于 token 的发布方式，并陈述了 OIDC 证明适用的条件。Delo 的包使用 Delo 的 npm 作用域与可信发布，因此两项决策覆盖的是不同的包。

[生成的第三方声明决策](../process/2026-07-30-generated-third-party-notices.zh.md) 从清单生成许可披露文件。该文件与 SBOM 相互独立，后者描述每个发布的内容。

## 曾考虑的替代方案

**未签名的发布。** 本人无法核实发布的来源，而重新构建也没有可对照的依据。

**由 CI 持有签名密钥。** 发布流水线中运行的任何代码都能使用这样的密钥，因此签名证明的是流水线运行过，而不是维护者批准了该发布。

## 后果

每次发布都需要签名者的离线密钥，并需要在 CI 之外的机器上重新构建，因此发布不是完全自动化的。

重新构建必须一致，因此必须对构建的字节级可复现性（byte reproducibility）进行度量。上游的 npm 决策记录了字节级可复现性是被假定而未经度量的。

可信发布要求包的 `repository` 字段指向运行发布工作流的仓库。上游的 npm 决策对 OIDC 证明记录了同样的条件。
