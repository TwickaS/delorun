# Changelog

Versions before 0.1.0-preview.2.6 were private previews and are not listed.

## Delorun compared with DeepSeek Harness dsh-v0.2.2-rc.3

This is everything that differs from DeepSeek Harness `dsh-v0.2.2-rc.3` in the latest assembled version.

### Install and update
- `delorun changes edit-harness` makes your own copy of the installed Delorun's program files and prints its folder. Each file you save, add or delete there is a change to Delorun itself, listed in `delorun changes list`. With protection off, the default, the next `delorun start` applies it without review, says so, and `undo` takes it back; with protection on it waits for your review, and `show`, `apply`, `discard` and `undo` decide it as they decide a plugin's change, at a terminal. An applied change runs from Delorun's next start, beside the installed release, which is never edited and is checked at every start as before; `delorun changes edit-harness --discard` takes every change to Delorun itself back, even from a copy Delorun can no longer read, and the next start runs the installed release unchanged. A release too large for Delorun to read your copy of is refused before anything is copied. When Delorun fails to start right after such a change, including when a changed file stops Delorun before it starts, it starts once more without it and names it; when it does not start without it either, it names `delorun changes undo <id>` and `delorun changes edit-harness --discard`. Safe mode runs the installed release without any of your changes to it. `delorun verify` and `delorun doctor` list the files you changed and never report a pass when the files Delorun would run with your changes differ from what you applied.
- Installing Delorun with `npx delorun` downloads the release it publishes, checks every file against the signed manifest and the public release log, and refuses to install anything that does not match. The runtime it installs is kept and reused, so starting Delorun again needs no network.
- `--release` is refused, with both versions named, when a runtime is already installed. `--` ends the launcher's own options, so the runtime keeps its own `--release` and `--profile`.
- An install whose download fills the disk stops with the launcher's own message.
- Installing Delorun with `npx delorun` prints one line for each step it takes: which release it found, that the signature checked out, whether the public release log agreed, the size of the download, and the install itself. If the release log or its witness cannot be reached, has not cosigned the log's latest checkpoint, or only cosigned it long ago, the install says why, warns that the release has not been checked against the log, goes on with the release's signature, and checks again at the next connection. A log or witness that answers and disagrees with the release, or whose cosignature does not verify, still stops the install.
- Running `npx delorun` on a Node older than the one Delorun needs stops at once with one line that names the version Delorun needs and where to get it.
- When the installed Delorun fails its start check because its files changed, the launcher says so in one line and, if the version before your last update is still installed and intact, starts that version's `delorun recover rollback` to take you back; otherwise it stops with the reason.
- Unpacking the runtime writes several files at once while it reads the archive.
- `delorun recover discard runtimes.set-aside-<time>` removes the program store that `delorun repair` set aside, although the installed program's folders are read-only.
- Delorun 0.1.0 runs on Linux (x64 and arm64) and on Windows through WSL2. A release publishes runtimes for Linux x64 and Linux arm64 only. Running `npx delorun` or `delorun update` on native Windows stops before downloading anything and says Delorun 0.1.0 runs in WSL2, with a link to the guide's WSL2 steps. On a Mac it stops the same way and says macOS joins in a later release. A computer whose platform a release does not list still stops with `PLATFORM_NOT_RELEASED`.
- `delorun verify` checks the installed release: its files against the signed manifest, the manifest's signature and timestamp, and the release's entry in the public transparency log, in a tree the log and a witness both signed. It trusts only the release root the launcher shipped and the roots an install walked from it, prints one line per check with a summary that says it is not a full verification of Delorun, and exits 1 when a check fails or the release signature could not be confirmed for a reason other than an unreachable log. It also names the directory of the launcher's roots it trusted and the release channel and log the installing launcher recorded. `--json` prints the same report for a machine, and `--offline` skips the log.
- The installer, the launcher's start and `delorun verify` run one release-log check and keep one record of the newest log checkpoint they verified. A log that cannot be reached, answers with an error or is not signed by the log's key leaves the release unchecked and never stops a start; a log that is signed and then contradicts an earlier checkpoint, serves a broken proof or carries an invalid witness signature stops the start and names `delorun verify`. The check gives up after 90 seconds, and a running Delorun retries an unchecked release every 15 minutes.
- A checkpoint stored by an earlier install is kept as the rollback floor only when the log proves it a prefix of its latest checkpoint; otherwise it is replaced, and the check says so. `delorun verify` says since when a release has stayed unchecked.
- `delorun repair` refuses to start an older program over chats when the home records which release wrote them and the release's data formats cannot be compared (`DATA_UNREADABLE`), and `--restore-copy` refuses a copy whose formats are newer than the release reads (`DATA_COPY_NEWER`). A restored copy's facts become the home's data-format record. A release signed by a local release build is refused from a `--from` folder as well when the launcher trusts the production keys, and `repair` reads the floor from the channel the home installed from.
- When a repair was killed during its download, the next start or repair names the set-aside program store (`runtimes.set-aside-*`) and prints the command that puts the old programs back.
- `npx delorun@latest repair` replaces a program that will not start with a verified release and keeps your chats, settings, keys, devices and trust records. It asks you first in a terminal, refuses while Delorun runs, refuses to put an older release over chats a newer release wrote, and keeps the old program in `runtimes.set-aside-<time>/`, which `delorun recover status` lists. `--restore-copy`, `--from` and `--reset-trust` cover the harder cases. Each start now records which release wrote your data in `data-format.json`.
- After `delorun update` and `delorun recover rollback` the trust badge reads what was checked at start. The new release checks its own signed manifest and files when it starts after the switch, and records the result; a release that fails that check does not start, so the update rolls back as a failed health check does.
- `delorun update` lists each change you made to Delorun itself and says whether it carries over to the new release. A change carries as it is when the new release left that file alone. When the new release changed the file without touching your lines, the two merge into a file neither had: `delorun update` prints its diff against the new release's file, and only you confirm it, not `--yes`. When the two overlap, the new release's file runs and yours is kept beside it as `<file>.mine` in your copy of the new release, and `--yes` does not confirm such an update either. An update refuses while changes to Delorun itself wait for your review, or when your copy of Delorun cannot be read, naming `delorun changes edit-harness --discard` and `delorun changes list`; it refuses before switching when what it would do with your changes no longer matches the report you confirmed, and asks you to run `delorun update` again. Going back to the previous release runs your changes to it again.
- `delorun update --from` with a folder that does not exist says the folder does not exist and that nothing was installed.
- `delorun update --from <folder or https address>` installs a release from files you downloaded from its release page when the release channel cannot be reached. It checks signatures, the release log and digests like a channel update. If the channel cannot confirm the release is current, it asks first in a terminal; `--yes` and a missing terminal refuse. A release below the one you run is refused. `npx delorun@latest repair --release <older> --from <folder>` asks in the same way. A repair now marks the whole home while it runs, so no Delorun starts meanwhile, not even for a new profile, and cannot run the program being set aside. A start during a repair says "Delorun is being repaired; wait for it to finish".
- Delorun tells you when a newer release exists: once a day, and at start when a day has passed, it checks your release channel's signed files and, when a newer release is out, prints one line in the terminal and shows a quiet notice in the studio's sidebar with the new version, whether it is a security fix, how many of your plugins it would turn off, and the command to run. Nothing is downloaded or installed until you run `delorun update`, and you can dismiss the notice for that version.
- The check sends nothing about you or your plugins; the release hosts see your computer's address. Setup asks whether to check for new releases under More settings, and `delorun setup privacy`, `--no-update-check` and an answers document's `updateCheck` turn it off; turned off in setup, it makes no request at all, not even at the first start. Turn it off later in Settings → General → Updates, and run it yourself any time with `delorun update --check`. `delorun update --report` shows everything an update would change, plugin by plugin, without applying it.
- An update lists every row the new release switches off through its own settings, and asks you before it applies them. A row switched off without being listed fails the health check.
- An update that fails its health check rolls back on its own even when the new release was stopped while it wrote a profile lock file.
- `delorun update` fetches the newest release on your channel, checks it, shows what it would change in your profile before anything changes, and applies it once you confirm. Running chats finish first, and an update whose new version fails its health check goes back on its own and names the check it failed; a plugin the report disables does not count as a failure when its rows are gone, and neither does a Docker socket that appeared, or a Docker context you switched, since Delorun started; a new version whose sandbox would protect less than the one it replaces goes back too. Updates come from the channel the launcher that installed Delorun was built for; no environment variable or setting moves it. Delorun keeps your profile's history with git, so an update and a rollback say so and stop before they fetch or change anything when git is not installed. A release that does not verify, a release channel that cannot be reached, or an update the home process could not finish, ends with a sentence that says what happened and what you can do.
- While an update or `delorun stop` waits for running chats to finish, a new message starts no turn: the chat shows that Delorun is updating and that the message was not sent, so you send it again once Delorun is back, and the wait ends once the running chats end. Background jobs count as running chats, and stopping with `--now` cancels them too.
- Before an update applies, Delorun works out what the new release would change in the person's profile: each plugin it would disable or remove and why, judged exactly as Delorun judges a plugin when it installs or starts one, so a plugin that names its DeepSeek Harness versions only through its peer dependencies is not shown as kept when the next start would turn it off, each bundle that leaves the bundle list or cannot load, and each row and Include that loads a plugin the update disables. The report marks every prediction it could not fully make from metadata it could read, so those are never counted as safe, and it shows both the CLI home's and the desktop Host's versions and update states, because the two update independently. Nothing applies until the person confirms, and `delorun update --yes` will not confirm a report that disables or removes anything or rests on metadata Delorun could not read.
- When an update changes the format of your chat data, the report says so and Delorun copies your chats and workspaces first, unless you choose to continue without the copy. Going back restores that copy and keeps the chats written since in a set-aside folder; nothing is deleted.
- `delorun recover status` says whether your last update committed, was rolled back or has not committed, lists the update you can go back from and every kept copy and set-aside folder with its size, `delorun recover rollback` goes back, `--profile-only` restores only your profile, and `delorun recover discard` removes a kept folder you no longer need. Delorun's home log records each step of a rollback as it records an update's, so `delorun logs home` shows where a slow rollback spent its time.
- An update or a rollback checks every release against the release roots of the launcher that started Delorun, so a root file replaced under the home is not trusted; a Delorun started without its launcher refuses to update or roll back and says to start it with the launcher. A studio that takes long to shut down for an update is waited for instead of ending Delorun in the middle of the switch, and one that does not shut down ends the update with nothing changed and Delorun running again.
- Contributors can measure where a person waits on Delorun with `pnpm run benchmark:delorun`: install and setup, start and stop, the everyday commands, `delorun update`, `update --check` and rollbacks step by step, recovery, export, import and the trash, plugins, a chat turn without a model, and the studio in a headless browser, all on local releases in throwaway homes with no network, with a mode that fails when a step exceeds its recorded ceiling.
- The studio's update card has a What's new button that opens the release's notes. The notes show only after their length and SHA-256 match the signed release manifest and their text passes the same plain-text checks as the release summary.
- The first-run guide has an optional PIN step after Phone access. At your computer, once phone access is on, choose a PIN or passcode so a paired phone unlocks sensitive actions, such as adding plugins or approving full access, by typing it instead of a code from your computer. Skip leaves PIN mode off, and Settings keeps every control.
- The recovery screen, which opens when the studio will not start, has **Roll back** next to Start in safe mode. It goes back to the release before the last update and says first that chats made since are set aside, not deleted; when the update took no copy of your chats it offers to go back with your settings only. It needs you at your computer, and a rollback waits for running chats to finish before Delorun restarts. **Leave safe mode** ends safe mode from the same screen.
- Settings → Changes starts and ends safe mode with a button, so safe mode no longer needs a terminal. Starting it changes nothing until Delorun next starts.
- Settings → Trash lists **Set aside by a rollback**: the chats a rollback moved out of use and the chat copies an update took, with their sizes. Each has a Remove button that asks first and, from a phone, needs the unlock you entered on it. Delorun never removes them on its own, and refuses to remove a copy a rollback of the last update still needs.
- Update Delorun from the studio, with no terminal. The update notice in the sidebar has an **Update now…** button, and Settings → Updates shows the release that runs, **Check now** and the newer release. The report dialog lists each plugin the update would turn off and each item it changes, offers a copy of your chat data (ticked by default), asks you to confirm each item that needs it, and lets you wait for running chats or stop them. While it runs, a card shows the wait or the switch and the page reconnects by itself, then reloads once on the new release. If the new release does not work, a card says why and that Delorun went back; your chats are unchanged.
- While an update waits for running chats, its alert in the sidebar has a ⋯ menu with Stop running chats and update. A confirm step names each chat that will stop and says whether it will continue after the update, then Delorun asks for your confirmation as it does for starting an update, stops the chats (keeping their work so far) and goes on. By default the updated Delorun sends each stopped chat one message to carry on; Settings → Updates has a switch, Continue stopped chats after an update, and with it off each stopped chat shows Stopped for the update with a Continue button.
- After an update, Settings → Updates offers **Go back…**, which returns to the release before it. It says that chats made since the update are set aside, not deleted, and can be removed later in Settings → Trash; when the update took no copy of your chats it offers **Go back, settings only…** and your chats stay as they are. You choose whether running chats are stopped now, and Delorun restarts on the earlier release. It needs the computer; a phone confirms with Face ID or its PIN first, and where a device may not do it the button reads "Update at your computer".
- Delorun is an agent harness that you shape to your own work: the themes, the sidebar, the plugins, the modes, even Delorun itself. It is built on DeepSeek Harness, runs its plugins and imports your chats, and adds a studio you open in a browser, a guided first run, undo for every change to your setup, protections for what agents may do, and reaching your home from your phone. This first public version, 0.1.0-preview.2.6, is described below: everything that differs from stock DeepSeek Harness, grouped by where you meet it.
- Run it with `npx delorun`. The first run checks the download against the signed release manifest and the public release log, then guides you through setup. Delorun runs on Linux (x64) and on Windows through WSL2.
- This is a preview. Releases are signed with preview keys through the 0.x versions, and no outside security review has taken place; [What you trust when you use Delorun](https://github.com/Delo-Run/delorun/blob/main/delorun/docs/guide/trust.md) says what that means. The rough edges you may meet are on the [known issues](https://github.com/Delo-Run/delorun/blob/main/delorun/docs/guide/known-issues.md) page, each with what to do.
- `delorun update --report` and `delorun update` show, under a plugin the update turns off because its DeepSeek Harness version range excludes the new release, the command that accepts the risk for that exact version and say that the health check after the switch rolls the update back if the plugin then fails to load. A new guide page, "Update Delorun with many plugins", walks through saving, checking, updating and going back.
- The launcher names the version it is installing when it refuses native Windows or macOS, and the install guide's sample output shows a preview version.
- While the connection is lost, Delorun is reconnecting, or an update waits or switches, the state shows as a compact alert in the sidebar until it ends, with its Cancel update button; on a phone it also shows as a toast at the top that you can close. After an update, the outcome card shows up to five one-line highlights from the release notes of every version the update skipped, with a Read more button that opens the full change log of those versions in a sheet (full screen on a phone). It reads the notes the update shipped, so it works offline. The card keeps each version number on one line and shows the finish time in your own time zone.
- Until `1.0.0`, a release that the maintainer built and signed on the maintainer's PC installs from the release channel at releases.delorun.com, so `npx delorun` installs it. Nothing rebuilds such a release independently, and the trust page says so. A `1.0.0` release, or a release under a later signing root, that was built this way is refused.
- Container images are published at ghcr.io/twickas, and the plugin catalogue lives at github.com/TwickaS/delorun-plugins.
- An install, `delorun update`, `delorun repair` and a plugin pack download show a live bar with size, speed and time left, then a checklist with a tick and a time for each step. A log or a pipe gets one plain line per step and one line for each tenth of a download.
- The `delorun` package page on npm says what Delorun is, what the launcher needs, and links to the website, the docs and the issue tracker.
- The source code moved to github.com/twickas/delorun; the old address redirects.
- **Fixed:** `delorun recover restore` and `rollback` no longer say "Your rows and settings are unchanged" when the restore changed your profile's `cordis.patch.yml`. They say whether your rows and settings now match that version or already did, and say nothing when the file could not be read.
- **Fixed:** An update no longer rolls back with "the settings of protected row delorun-reach changed" after you turned remote access on or off with `delorun reach` while Delorun was running. The running version now hands the health check the remote-access settings it applied, not the ones it started with. A new version that boots with remote-access settings other than the ones applied still fails the check unless the update report names the change.
- **Fixed:** Updating from an earlier preview no longer fails and rolls back when plugin packs were added with protection off. The new release now points the saved copies of those packs at its own files before it starts, so its safety check no longer refuses them.
- **Fixed:** Delorun starts again after the computer restarts, or after a Windows Subsystem for Linux distro restarts while its virtual machine keeps running. A lock left behind by the run before no longer stops the next start.
- **Fixed:** An update no longer fails its check and goes back when the Claude Code or Codex plugin was installed on an earlier release: the plugin loads on the new release as it did before.
- **Fixed:** An update with the Claude Code plugin installed completes again. The two previous previews were built without the fix and went back to the release before.
- **Fixed:** An update whose new release fails its health check leaves the previous release running again, with its plugin copies pointed at it, instead of stopping Delorun until you start it by hand.
- **Fixed:** A chat-data registration left behind before a restart no longer blocks `delorun update`. An update run from an earlier preview release can still be refused.
- **Fixed:** An installed release carries every built file of the agent seats plugin, so Delorun starts after an install or update.
- **Fixed:** Settings → Updates opens with its content again. It showed an empty panel, with no title, because the page failed to read its Continue stopped chats switch.
- **Fixed:** The update report no longer says the release's freshness passed when it was never checked. A release installed with `delorun update --from` after you agreed that the release channel cannot confirm it is current now shows "freshness unchecked". `delorun update --yes` does not confirm it, and the studio asks you to tick that you want to update anyway, as it does when the release log could not be reached.
- **Fixed:** Updates no longer leave a pending review on Claude Code. The pack that adds Claude Code named the build's temporary folder in its dependency list, which differed with every build, so Changes showed a dependency change after each update. A pack now names the exact version of each package it carries and no longer ships the install state pnpm leaves behind, and the release build refuses a pack whose files name a folder on the build machine. An update also makes the release's own pack files the new baseline in Changes, once Delorun has checked them against the signed release, so it no longer leaves the previous release's files waiting for review, including the review the earlier build left behind. An edit of your own to a pack, or to any other file of it, still waits.
- **Fixed:** An update to a release that changes a protected setting no longer fails its health check and goes back. A release can turn a setting on in a row Delorun protects, such as External agents for live agents. An older release's update report could not name that change, so the health check refused it. The new release now reads its own signed files and the previous release's, accepts exactly the changes they bring, and shows them with the update's outcome in Settings → Updates. A setting you changed yourself, a weaker sandbox and a row that disappears still fail the check. The update report of this release and later ones names these changes before you update: `Delorun <version> changes the settings of the External agents row (delorun-agent-seats): turns on live agents.`
- **Fixed:** An update that waits for your running chats now notices when the last background job ends, as it does when a chat finishes. Before, a job that ended while the update waited could leave it waiting until it gave up with a timeout. A job that has already finished is no longer counted as running work, and an update still waits for every job and chat that is really running.
- **Fixed:** `yarn add delorun` and `yarn dlx delorun` now install and start Delorun with Yarn 4's default Plug'n'Play, as `npx` does. They stopped with `TRUST_STATE_INVALID: the trust file cannot be written`. The launcher starts one plain Node process for itself under Plug'n'Play, and its package asks Yarn to unpack it. If Yarn keeps the package in a zip, the launcher says so in one line and names `nodeLinker: node-modules` and `npx delorun`.
- **Fixed:** Building a release on a machine whose Docker engine is rootless now compiles the native addon as the container's own root user, which owns the mounted source, instead of as the caller's user id, which the rootless engine cannot write with. A rootful engine builds exactly as before.
- **Security:** Starting an installed runtime does not trust a release root merely because a file under `~/.delorun/trust/` names a newer version: the launcher keeps the root chain the install walked, checks that it leads from a root the launcher carries, and otherwise stops and offers a reinstall. It starts a runtime only when the release root the home stored is one the launcher ships.
- **Security:** An installed runtime is made read-only before its files are hashed, so nothing can change a file between its check and the mode that protects it.
- **Security:** The runtime starts without the `NODE_OPTIONS`, `NODE_PATH`, `LD_*`, `DYLD_*`, `NODE_EXTRA_CA_CERTS` and `NODE_TLS_REJECT_UNAUTHORIZED` variables that the shell passed in, so the shell that started `delorun` cannot stand between the runtime and the connections it verifies. A profile name that would leave the Delorun home is refused before anything is read.
- **Security:** The release-log check accepts every consistency proof the log serves and refuses only one that does not reproduce both tree roots. It also refuses a bundle that names a different manifest file than the release's own, a release version that is not a version, and a checkpoint that no listed witness has signed, even when the trusted root carries no witness requirement of its own. A log entry whose signing key cannot be read says why in its refusal.
- **Security:** The Linux runtime's sandbox launcher and file-lock addon are compiled from the release's own tagged source in a pinned toolchain without network access, so a rebuild of the release reproduces them byte for byte, signing covers them and the release's software bill of materials names the compiler packages that built them.
- **Security:** A Delorun release and its freshness timestamps are signed only with keys the public repository records as Delorun's production keys, so nothing is signed until those keys are recorded. A release is signed only when its version tag carries the signature of a release signer that the release branch of the public repository lists, not a local copy of that list, and the tagged code is on the release branch, and only when the `delorun` npm package it records, by name, version and checksum, is the package the release built. Until install scripts are rebuilt and compared like the rest of a release, no release lists one.
- **Security:** A test release built on someone's own computer can never be signed with Delorun's real release keys, so a launcher that trusts Delorun's releases never accepts one.
- **Security:** Each start checks the installed release under the newest release root the launcher ships, never an older root the home stored, so a signing key a newer root revoked stops the start. The launcher passes on no `DELORUN_LAUNCHER_` setting it inherited.
- **Security:** A start stops when the release-log bundle kept beside an installed release is missing; the message names the missing file and offers `delorun recover rollback` or putting the file back, and `delorun verify` fails on it.
- **Security:** A launcher that installs from Delorun's published release channel refuses a release that the local release tool built.
- **Security:** `delorun update` never moves to a release lower than the one running: a channel or a request that names a lower release is refused before anything is downloaded, and `delorun recover rollback` stays the only way back.
- **Security:** The update report says when the release log could not be reached as the release was installed, and does not show its log check as passed, and `delorun update --yes` does not confirm such a release.
- **Security:** Release root 2 lists the keys allowed to sign a release's log entry, ECDSA P-256 first and Ed25519ph as the alternative, and the logs whose checkpoints count. Delorun accepts a log entry only when a key the root lists for its type signed it, in a listed log cosigned by a listed witness, and verifies no release under a root without these lists, so a log that stops accepting one key type, or a new log shard, needs a root rotation by the offline root key and no client release. An earlier log listed after such a rotation verifies only the releases up to its last one, and a locally built 0.x release keeps installing under later roots that follow from root 2 and keep its targets key. Copies on 0.1.0-preview.2.7 or earlier cannot read root 2: run `npx delorun@latest repair` once; your home, chats and settings stay.

### Setup
- The Models step of the first-run guide makes adding another provider obvious. Under the providers it found, an "Add another provider" list offers every provider a key alone connects, such as OpenAI, Anthropic, OpenRouter, Google Gemini, Groq, Mistral and xAI, and an OpenAI-compatible endpoint you name yourself. The summary has an "Add another provider" button that returns to the list and keeps what you have set up.
- An agent that this installation does not include says only that it is not included, never also "Signed in on this computer".
- Setup ends by saying once that Delorun is running in the background, and the review screen says when the key check failed and the key is not verified.
- In a source checkout, the package manager's output while Delorun links its parts into the profile goes to the home process's log, and the terminal shows one progress line.
- `delorun status` prints the studio's address, without any token, and "Run delorun open to open the studio in your browser."
- The `delorun` command keeps your data in your own Delorun home, `~/.delorun` or the directory `DELORUN_HOME` names, readable only by you, and never touches DeepSeek Harness's `~/.dsh`. Its first run sets up the command-line profile; after that it starts Delorun in your terminal and opens the studio. Only one Delorun runs per profile.
- If the profile's `cordis.patch.yml` sets the sandbox row's `runnerCommand` or `runnerFailureSignatures`, `delorun start` refuses with an error naming them and asking for their removal: your home's protection runs through the sandbox's built-in runner selection.
- `delorun import-home` copies your DeepSeek Harness home, `~/.dsh` or the folder `--from` names, into your Delorun home. It only reads `~/.dsh`, which stays exactly as it was. After one yes it copies your chats, exactly as they were saved, the images and files they refer to, and your workspace list.
- Then it asks about each of these on its own, and each starts on no: your profiles, your settings, your `AGENTS.md` instructions, your skills and your DeepSeek key. It shows each before it asks: each profile's plugins as carried, to install, added or not carried, the exact settings that would land, the first lines of your instructions, each skill's description, and your stored keys by name and never by value. `--dry-run` shows the preview and writes nothing.

### Chats and workspaces
- `delorun export <chat-or-workspace> --out <file>` writes a chat, or a workspace with its chats and their attachments, as an archive signed by your home. It warns about secrets it finds in the chat history, naming each by kind and never by value, and writes nothing until you confirm.
- `delorun import <file>` checks the whole archive before it writes anything, shows who signed it and what it holds, and imports it after you confirm. An archive whose signature does not verify, whose bytes disagree with its manifest, whose paths leave the destination, that holds a link, or that is past its size or compression limits is refused; an archive from a home you do not know is imported only after you type its key's fingerprint, and an unsigned one only after you accept it unverified. Imported chats are kept apart and stay out of every model request.
- Importing an archive brings a person's exported chats, attachments and workspaces into the home in one step that writes nothing until the whole archive has been checked: a path that climbs out of the destination, an absolute path, a link, a device, an archive past its size or compression limits and an archive whose bytes disagree with its manifest are all refused before anything is staged. The import states whether the archive's signature is verified, and shows the customisation the archive carries as a diff before any row is applied; an export warns about the secrets it finds in chat history before it writes the file.
- An archive that hides a configuration expression behind JSON escapes is refused, so a customisation value that reads as a tagged expression is caught after it is decoded as well as in the file's raw text.
- An archive with two entries whose names are the same word written in different Unicode forms is refused, because both would land on one file.
- A new Delorun home has a default workspace on every platform: `Delorun/default-workspace` in your documents folder when the computer reports one that is not your home folder, otherwise `Delorun` directly in your home folder. `delorun start` picks the folder, and it is created when the studio first needs it. Restating the `workspace-controller` row in the profile's `cordis.patch.yml` with your own `defaultWorkspaceDirectory` chooses another folder.
- A chat can be snoozed until later or settled when it is done, from its menu or its card; it moves to a folded Snoozed or Settled shelf at the bottom of the chat list and comes back when its snooze ends or when you send it a message. The snooze times and an optional rule that settles chats left idle for some days are set under Settings → Sidebar. The states are kept on your computer and never reach the model.
- Deleting a chat or a workspace moves it to the trash: "Move to trash" in a chat's or a workspace's menu archives its chats, stops their running work and takes them out of the sidebar. The Trash section in Settings lists what was deleted with the days each item has left, restores an item where it was, and deletes one or every item forever from every place Delorun keeps it, with an offer to clear the operational logs at once. Items older than 30 days are deleted when Delorun starts. `delorun trash list`, `restore`, `purge` and `empty` do the same from the terminal while Delorun is stopped.
- Trash deletes a chat or a workspace into a 30-day retention, restores it before the retention ends, and purges it from every store that holds its content: the full-text index, the session generations, the attachments, the spill files and the browser drafts. It offers to clear the affected process logs, current and rotated, at once.
- Permanently deleting a chat also removes the copy the session list keeps for it, so the chat's title, first message, plan, goal and todos are not left on disk after the purge.
- A damaged workspace list does not leave the studio empty. Delorun starts with every workspace record it can read, sets the rest aside in a dated file next to the list (it never deletes one), and logs where it is. It also keeps the previous good copy of the list, `delorun doctor` checks the list, and `delorun recover workspaces` brings the previous copy back after asking you. See [The workspace list](../../docs/guide/troubleshooting.md#the-workspace-list).
- The agent can rename a workspace with the new `rename_workspace` tool, after you allow it.
- When some workspace records were set aside, the studio says so above the message box, names the file and points to `delorun doctor`; you can dismiss it. A `rename_workspace` call in a chat shows the old and new name, or why it was refused.
- A new workspace can be an existing folder, a new folder with a Git repository started for it, or a clone from Git on a branch you name. Folder search, recent and suggested folders and a preview of each folder help you find the right one.
- Each workspace can have its own model and thinking level, which every new chat there starts with, and can turn the isolated browser off for its chats.
- When you set up a workspace you choose whether chats there can change files or have Full access (asked once, the same question as in a chat) and whether commands reach the whole internet, only sites you list, or nothing. Every choice starts on the safe one, and Create now skips the rest.
- Delorun never makes or adds a workspace in your home folder itself, in its own home or in system folders, or outside the folders it is set to use, even through a link.
- A folder you open starts on the safer permission, so a chat can write inside it and asks before doing more; turning on full access for a folder takes one answer covering that folder, and a chat whose folder was never answered stays in the sandbox even when something tries to switch it.
- Choosing the safer permission for a folder again withdraws that folder's full-access answer, so turning full access back on asks once more, and puts the folder's other open full-access chats back on the safer permission within a second, in every running profile. A chat picking full access after another profile or `delorun workspace full-access` withdrew it asks again.
- The model now knows it is working in Delorun and which model is answering, and mentions DeepSeek Harness only when you ask how Delorun is built. On an installed copy it no longer receives the program folder or the studio address, and creator chats point to the plugin-authoring skill and the Changes page. Guidance for terminals, workflows and delegation is sent only when those tools are on offer, the file-link rules are shorter, and the time note no longer says the elapsed time is unavailable.

- **Fixed:** The agent now knows that a file it writes to `/tmp` while a command runs in the sandbox does not persist: each sandboxed command can have its own `/tmp`, discarded when the command ends. Before, it could report a file in `/tmp` as saved when no later command could see it. The agent is told to keep files it needs under the workspace.

### Safety and privacy
- On Linux, a sandboxed command on a workspace with the Open network is now refused while a program on your computer listens on an abstract socket, such as the display server or the session bus. The sandbox cannot hide those sockets, so a command could have used them to act outside it. The refusal names the sockets and the fixes: set the workspace's network to Allowlist or Off, or switch on "Run commands even when desktop sockets are reachable" beside Open in Settings, Safety, Network. With that switch on the command runs, and the sandbox reports that it confines only in part. The check runs when a command starts, so a socket that starts listening later is not caught.
- With changes protection on, before the agent first writes to the folder of a plugin you approved, the chat asks you, names the plugin and shows the diff, because the agent is changing what your harness runs; once you allow it, the rest of that chat's writes to the plugin go ahead, and what it wrote still waits for your review in `delorun changes`. A link or a `..` in the path asks the same way.
- With changes protection on, when the agent asks to install, update or remove a plugin, nothing is installed or removed: the request waits in `delorun changes` and the studio's Changes section for you to apply or discard it at your computer, and the agent is told so. With protection off, the default, the agent's plugin requests run as in DeepSeek Harness and a plugin it installs from a folder is recorded as loaded without review. Applying a plugin from a folder adds it with nothing loaded, and its content waits for your review as its own change.
- With setup's Dangerous answer on, a phone or browser signed in over remote access, with its unlock running, can do what the computer does: change the settings and plugin rows the computer alone changes with the other answers, run any slash command, loosen the permission new chats start in, answer the questions for MCP servers, external agents and a workspace's network, give the approvals that reserve full access, use terminals, save or remove provider keys (a saved key is never sent back), open a chat's folder in an application on the computer, and read files outside the chat's workspace. A workspace's full access that a device turns on ends with the mode, while what you set at the computer stays. Only the computer turns the mode on, approves a new device or an unlock, removes a device, changes the remote-access settings or signs a device in. Settings, Permissions now shows `delorun setup prompts` as code in the Dangerous mode card.
- With setup's Dangerous answer on, any chat can switch to full access with no dialog and no per-workspace consent, from the studio at the computer, a phone signed in over remote access, a scheduled task, a bot or `delorun headless`. Settings, Permissions shows a card with the date and a Turn off button, which also works from a remote studio, and a small "Dangerous mode" badge under the sidebar logo opens it. New chats still start on Workspace Write unless the workspace's default says otherwise.
- Before an external agent such as Claude Code or Codex runs, Delorun asks you at the home's own computer, saying that it runs outside the sandbox, can reach your files and Delorun's home, and uses your own account. A phone signed in over remote access cannot answer.
- "Allow for this workspace" on the approval card, or `delorun workspace external-agents <folder> <agent> on`, lets an agent start there without asking; Settings, External agents and `delorun workspace external-agents <folder> <agent> off` revoke it.
- A read-only chat and a chat without a workspace folder never start an external agent, a run cannot start outside the chat's workspace, the question names the folder the agent runs in, and each run stops after 30 minutes. A full-access chat and `delorun headless` cannot ask, so they start an agent only where you allowed it for the workspace.
- The model can no longer install or turn on an external-agent plugin, such as Claude Code, Codex or the ACP one, through plugin management.
- Settings, External agents has its own switch, **Ask before external agents run**, on by default, and the run time limit, from 1 to 1440 minutes. Setup's prompts answer does not change either, and only the home's own computer can turn the question off.
- A Privacy page in Settings states that Delorun has no telemetry of its own and turns DeepSeek's session-log upload and desktop analytics on, after showing what each sends and where, or off again.
- When a command in a workspace with the Open network would be refused because a program on the computer listens on a shared socket, such as a running `docker` command, the chat asks you once whether to let commands run anyway in that workspace. Allowing records the same choice as the switch in Settings, Network; declining keeps the refusal and the chat does not ask again.
- Claude Code and Codex each have a level in Settings → Safety → External agents: Careful, Standard, Your own settings or Unrestricted. It decides what the agent may do on its own when you hand it a task.
- Phone powers sets how much an unlocked phone may do, and you choose it at your computer only. **Careful**, the default, keeps the terminal, turning protection off, applying plugin changes, changing Delorun's own files or undoing a change to them, making your copy of Delorun and restarting it at the computer; an unlocked phone can still undo a plugin's change, discard any waiting change and turn protection back on. **Full** lets an unlocked phone do everything the computer can, each time with an unlock you entered on the phone: the 15 minutes after you approve a phone never count. `delorun setup` asks you to choose when you turn remote access on; Settings, Devices and `delorun devices powers` change it later, and a phone shows it read-only. Approvals you give from an unlocked phone, such as accepting an MCP server or giving a workspace full access, can still start programs outside the sandbox at either level.
- The studio's Changes section can now apply, undo and discard changes to your copy of Delorun, make that copy, and turn protection on or off. Turning protection off asks a second time and names what would then load without review; the second ask guards against a misclick, not against someone who has your computer. A protection change made from a phone shows as a notice at the computer.
- A chat whose tool calls keep failing stops on its own instead of using up tokens on workaround after workaround: after 6 failed calls in a row, or 8 of the last 12, the chat shows one notice saying it stopped, and your next message carries on. A call you refused does not count. In `delorun headless` a stopped task also prints one line saying why.
- When your Claude or ChatGPT plan's limit is reached, Delorun does not start Claude Code or Codex for a chat until the limit resets. The chat is told which limit is reached and when it resets, so it does the task itself or tells you instead. Figures whose reset time has passed never stop a start.

One sheet shows at a time, and the next waits until you answer it. Cancel sends nothing, and the screen shows that the action did not go through. ### Commands
- `delorun changes` lists the changes to your plugins, those that loaded without review and those that wait for your review, and shows each with its files, a diff and a summary of what it can do. `apply`, `discard` and `undo` decide about one change after you confirm in a terminal, with a second confirmation when the change runs commands, opens network connections or does anything else the summary names. A running Delorun loads an applied change at once and goes back to what ran before when it fails to load. `off` and `on` turn one plugin off and on again, and `protection on` makes changes wait for your review, which `protection off`, the default, ends; each says what it means, asks, and applies without a restart. `work <plugin> [--for <minutes>]` loads every edit you save in a plugin's folder live for up to two hours, or the minutes you give up to eight hours, going back to the last version that loaded when an edit fails to load. `done <plugin>` shows the folder's version with its files and diff and approves exactly that version as one change; a session that ends without you, when Delorun stops or its time is up, approves nothing and leaves the folder's content waiting for your review. `delorun status` names an open work session and when it ends. With protection on, a plugin you link with `delorun plugin --profile default add link:<folder>`, or bring back with a restore or undo, loads nothing from its folder until you apply its content, also while Delorun runs; the approved copy includes the plugin's installed packages; and a plugin folder Delorun cannot read no longer stops Delorun from starting. When Delorun fails to start right after you applied a change to a plugin or turned one on, it starts once more without that change, names it with `delorun changes apply <id>` and `undo <id>` at every start, in `delorun changes list` and in `delorun doctor`, and rewrites none of your files; when it fails again it points to `delorun recover safe-mode`.
- Every `delorun` command answers `--help` (and `-h`, and `delorun help <command>`) with a short usage, its options and its exit codes, and exits 0 without starting anything. A wrong option says which option and points to `delorun <command> --help`, and `delorun help` ends with a short list of the words the commands use: home, profile, studio, workspace, full access and reach.
- `delorun start` starts Delorun in the background, so you can close the terminal, and waits until it is running; `delorun start --foreground` runs it in your terminal. `delorun start --patch <file>` applies a patch file over your profile for that start only, as `dsh --patch` does, and Delorun's own checks still apply to it; `--inspect` lets a debugger attach to Delorun while you work on a plugin, after you confirm, since any process on the computer, the agent's sandboxed commands included, can then run code as Delorun; `--inspect --yes` confirms without a terminal, safe mode refuses it, and `delorun status` shows it while it is open. `delorun` on its own does the same and opens the studio, then prints the studio's address and how to see, follow and stop Delorun; if you chose during setup not to run Delorun in the background, or pass `--foreground`, it runs in your terminal.
- `delorun stop` stops Delorun once running chats end, or at once with `--now`.
- `delorun status` shows the home and profile in use, whether Delorun is running, its process, runtime version and running chats, or prints them as JSON with `--json`.
- `delorun plugin` and `delorun headless` work as their `dsh` counterparts do, inside your Delorun home; an installed Delorun runs plugin operations with the pnpm it carries, so you do not need pnpm on your computer. `delorun plugin` works on your Delorun profile without `--profile`. When pnpm refuses to run a package's build, as it does for a plugin installed from git, `delorun plugin` asks whether to allow that one package's build and tries again; `--allow-build <name>` allows it without asking, and nothing allows every build at once.
- When a `delorun` command or the launcher stops on a failure, it says what Delorun did, why, with the error's code and the file or detail concerned, and what you can do next, naming your `--profile`; it never prints a stack trace.

This first public version, 0.1.0-preview.2.6, is described below: everything that differs from stock DeepSeek Harness, grouped by where you meet it.
